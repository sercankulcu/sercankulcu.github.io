# Brief: language and content check (Turkish and English course pages)

Repo `C:\Users\Sercan\Documents\GitHub\sercankulcu.github.io`. You read a set of course pages end to end and propose corrections. **You do not edit the files.** You write your proposals as JSON lines to the output file named in your task; the main session applies them with `tools/proof/apply.py` (read its docstring: a proposal is applied only if `old` occurs exactly once in the file, the HTML tags in `old` and `new` are identical, and — unless `type` is `content` — the numbers are unchanged).

## Output format (one JSON object per line, UTF-8)
```
{"file": "files/<course>/notes/Chapter_03_..._Lecture_Notes.html", "old": "<exact text from the file>", "new": "<corrected text>", "type": "error|style|term|content", "why": "<short reason>"}
```
- `old` is copied **exactly** from the file source (including entities like `&amp;`, `&lt;`, `<code>` tags, line breaks inside it if any) and must be long enough to be unique in that file (usually a whole clause or sentence). Keep the same tags in `new`.
- `type`: `error` (spelling, grammar, wrong word, broken sentence), `style` (unnatural or unclear wording, translationese, repetition), `term` (term not consistent with the course's glossary/notes or across files), `content` (wrong fact, number, code, output, formula, wrong cross-reference; numbers may change only here).
- One problem per line. If the same wrong sentence appears in several files (note, slides, questions, book source), write one line per file.

## What to check
1. **Language.** English pages: natural, correct textbook English (no translationese, no Turkish word order, articles, prepositions, agreement, tense, plurals, hyphenation of compound modifiers, consistent spelling variant — follow the majority in that course). Turkish pages: TDK spelling and grammar (de/da, ki, -mi, apostrophes after abbreviations and numbers: k'dir, k'ye, BFS'in, JVM'in), punctuation, natural Turkish, the known error patterns: number–count mismatches ("üç durum" but two listed), stale references ("bu bölüm", "ekte"), "ancak ve ancak … ise", "hiçbir" + negative verb, "sonsuz/sonlu sayıda", inanimate plural subject + singular verb, "bire bir" not "başa baş", ambiguous "tam bir".
2. **Terms.** One term per concept within a course and across the two languages: use the course glossary (`files/<course>/Sozluk.html`, `files/<course>/Dictionary.html`) and the notes as reference. Turkish decisions already made: tam sayı, yapıcı (not kurucu, except where a course consistently uses kurucu for ADT), veri yolu, eş zamanlama, yol döngüsü (bus cycle); AGT: kuram, kazanç/fayda per its glossary, "Kağıt" and "işbirliği" stay as they are. Do not change person names, Turkish example names/places, TL amounts.
3. **Numbers and formats.** Turkish: thousands separator `.`, decimal `,`; English: thousands `,`, decimal `.`. Exceptions: code, byte/bit groups, trace panels (`data-vars`, `data-out`), one-off codes, label+number. Deliberate Turkish-locale demos in English pages (e.g. `3,14` explained as Turkish locale output) stay.
4. **Content.** Wrong statements, wrong numbers in examples and traces, code whose shown output does not match what it prints (run it if unsure: JDK 21 at `C:/Program Files/Eclipse Adoptium/jdk-21.0.3.9-hotspot/bin`, C via `python -m ziglang cc`, Python 3), formulas, off-by-one in step tables, inconsistencies between the note, the slides and the study questions of the same chapter, and between the Turkish and English twins (same facts, same numbers, same answers). A question whose marked correct option (`data-ok`) is not actually correct is a `content` error. English pages must contain no leftover Turkish text (except names/examples) and Turkish pages no stray English sentences.
5. **Do not** propose: rewording that only reflects taste when the text is already correct and natural; changes inside `ds-guard` blocks, scripts, `data-*` attributes, ids, URLs, CSS; changes that alter layout (making text much longer on slides — slides must still fit); renaming code identifiers (only comments and printed strings inside code may be fixed, and only if the expected output stays consistent).

Keep a running list; at the end write all lines to your output file (create its folder if missing) and verify every `old` occurs exactly once in its file with a tiny script (fix or drop the ones that don't). Report: number of proposals by type, the most important content errors (one line each), and anything you were unsure about (do not include unsure items as proposals; list them in the report instead). Do not edit repo files, no git, no browser pane, no helper agents.
