Introduction

What Question Does It Ask?

How is a model taken from the lab into production and kept running there?

MLOps applies software engineering and DevOps practice to ML so that models reach production and run reliably there. The course covers versioning data, code and models together, automating the pipeline, deploying, and monitoring the model in production.

Introduction

A Short History

2009

The first DevOpsDays is held in Ghent; DevOps, uniting development and operations, spreads.

2014

Docker 1.0 is released and Kubernetes announced: containers become the common unit of deployment.

2015

Sculley et al. expose hidden technical debt in ML systems: model code is a small part of the system.

2017

Google presents TFX and Uber presents Michelangelo; in-house ML platforms come into view.

2018

Databricks open-sources MLflow: experiment tracking and a model registry.

2021

Andrew Ng calls for data-centric AI: focus on data quality more than on the model.

The Course

Core Concepts

Pipeline

Automated steps from data preparation to deployment.

Versioning

Tracking and rolling back data, code and model together.

Experiment tracking

Logging the parameters, metrics and outputs of every run.

Model registry

Approved model versions kept in one place.

Feature store

The same features used in training and in production.

CI/CD/CT

Continuous integration, delivery and continuous training.

Model serving

Running as an online API or as a batch prediction job.

Data drift

Production data moving away from training data; must be monitored.

The Course

A Typical Workflow

Example: A bank's credit model is retrained every month on new applications. The best registered version is packaged in a container, first exposed to a small share of traffic, and rolled out to everyone if nothing breaks. When the applicant distribution drifts, the monitoring dashboard alerts the team and the cycle restarts.

Try It

The Model Silently Degrades in Production

A bank's fraud model flags unusually large transactions, while prices rise a little every week. Advance the weeks, watch drift (PSI) and accuracy, and retrain the model when the alarm goes off.

PSI compares this week's distribution with the training data over ten bins. Above 0.2 counts as an alarm. Labels arrive late; PSI is computed at once.
A model is not built once and left alone like ordinary software: MLOps sets up monitoring, alarms and an automated retraining pipeline. Drift is caught before accuracy drops.

Risks and Ethics

Silent decay

Without drift monitoring a model degrades with no errors; many demand forecasts lost their accuracy overnight in COVID-19.

Training-serving skew

If a feature is computed differently in training and production, a model that tested well predicts wrongly live.

Feedback loops

A model retrained on the outcomes of its own decisions, such as a recommender or credit model, amplifies its own bias.

Untraceable versions

A model whose training data and code are unknown cannot be explained in a complaint or audit, nor rolled back.

In depth: Explainable AI and AI Ethics.

Common Misconceptions

Common beliefIn fact
Once the model is trained, the job is done.Data changes in production; an unmonitored model silently degrades over time.
MLOps is just installing tools.Tools support the process; the real work is versioning, testing, ownership and rollback.
High test accuracy means good production performance.Production data may differ from training data; latency and cost are part of success too.
Most of an ML system is the model.Model code is a small part next to data, configuration, serving and monitoring infrastructure.
