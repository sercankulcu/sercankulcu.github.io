Chapter 2: Algorithm Complexity

To say which of two algorithms that solve the same problem is better, we need a yardstick. Time in seconds will not do, because it varies from machine to machine. Complexity analysis instead counts the basic operations an algorithm performs and looks at how that count grows as the input grows. These notes begin with the concepts of time and space complexity and distinguish the best, worst, and average cases. They then define the O, Ω, and Θ notations for growth rate and show how the constants are found. The following sections compute the step count of looping code with summation formulas and the running time of recursive code with recurrence relations. The recurrences are solved by unrolling, by recursion trees, and by the Master Theorem. All these tools are applied to six short Java functions (f1–f6), each representing a different growth class. The notes close with a brief look at amortized analysis.

2.1The concept of complexity

That an algorithm works correctly is the first requirement, but not the only one. A correct algorithm may finish in a second on an input of a thousand elements and take days on an input of a million. When choosing an algorithm one therefore also asks, “how many resources does it use?” This section explains how that question is measured. What is measured is not seconds but the number of basic operations; and what matters is how this number grows with the input.

2.1.1What is algorithm complexity?

Complexity theory studies the resources an algorithm uses while it runs. Two resources stand out: time and memory. Both depend on the size of the input. Sorting five numbers takes far less time than sorting five million. Resource use is therefore written not as a single number but as a function of the input size.

The input size is usually denoted n. For an algorithm that processes an array, n is the number of elements in the array. For a string algorithm it is the number of characters, and for a graph algorithm the number of vertices and edges. The time requirement is denoted T(n) and the memory requirement S(n). For example, T(n) = 3n + 3 says that the algorithm performs 3n + 3 basic operations on an input of size n.

Definition 2.1

Time complexity is the number of basic operations an algorithm performs on an input of size n, denoted T(n). Basic operations are those that finish in constant time, such as assignment, comparison, arithmetic, and array access.

Space complexity is the amount of memory the algorithm uses in addition to the input, denoted S(n). Local variables, auxiliary arrays, and the space that recursive calls occupy on the call stack all count toward this memory.

The purpose of analysis is not to measure seconds. The purpose is to see how the resource requirement grows as the input grows. The basic question is this: if the input size doubles, what happens to the running time? Does it stay the same, double, quadruple, or get squared? Figure 2.1 shows the answer to this question for several growth classes.

The factors in the figure come from simple arithmetic. If T(n) = n2, then T(2n) = 4n2 = 4 · T(n). If T(n) = n3, then T(2n) = 8n3. For the logarithm, log2(2n) = log2 n + 1, so the time grows by just one step. This one question alone makes the difference between algorithms plain. When the input grows a thousandfold, a cubic algorithm slows down a billionfold; a logarithmic algorithm works only about ten steps more.

Common mistake

Stating complexity as a single number, for example “this algorithm takes 12 steps.” Twelve steps is true only for a particular input. Complexity is always a function of n: “this algorithm takes 3n + 3 steps, which is 12 steps for n = 3.”

2.1.2Why timing is not enough

The first way that comes to mind to learn the speed of an algorithm is to run it and measure the time. In Java this is done by reading the system clock before and after the run and printing the difference:

long start = System.currentTimeMillis();
linearSearch(a, 10001);  // 10^8 elements
long end = System.currentTimeMillis();
System.out.println("Elapsed: "
    + (end - start) + " ms");

The code measures how many milliseconds a linear search takes on an array of 108 elements. System.currentTimeMillis() returns the current time in milliseconds. The difference between the two readings is the time the search used. This method is called experimental measurement. It gives a real number, but that number has three serious weaknesses.

  • The result depends on the machine. The same code may take 40 ms on a fast processor and 200 ms on an old laptop. In Java the situation is even more tangled. The JIT compiler (just-in-time compiler) translates frequently run code into machine code while the program runs; so the same measurement comes out slow on the first try and fast on later ones. The cache, the operating system's load at that moment, and the time when the garbage collector kicks in also change the result.
  • A single measurement does not predict the future. A search that took 40 ms on 108 elements, how long does it take on 109? The measurement does not say. If the algorithm grows linearly, the time grows tenfold to 400 ms; if it grows quadratically, it grows a hundredfold and reaches 4 seconds. The answer depends on the growth pattern of the algorithm, and a single measurement does not reveal that pattern.
  • The code must already be written. To compare two designs, both have to be coded, tested, and measured under the same conditions. At the design stage, when there is no code yet, no measurement can be made.

Figure 2.2 makes the second weakness concrete. Machine B is 2.5 times slower than A; but both lines are correct and grow in the same way. The dashed curve belongs to a different algorithm and grows quadratically. On small inputs this algorithm looks faster than the linear algorithm on both machines. The equality n2/4 = 5n holds at n = 20; beyond this point the quadratic algorithm falls behind even the linear algorithm on the slow machine, and the gap keeps widening. A measurement made on small inputs would have led us to pick the wrong algorithm here.

The remedy for these weaknesses is asymptotic analysis. Asymptotic analysis gives the step count as a function of n and looks only at what happens as n grows. It is independent of the machine; it can be done without writing code, from the description of the algorithm alone. Experimental measurement is not worthless: if two algorithms are in the same growth class, only measurement can tell which one is actually faster. The two methods complement each other. First analysis picks the right growth class, then measurement compares the constant factors.

2.1.3Counting steps and the RAM model

To count in a machine-independent way we imagine a simple, idealized machine. In this machine every basic operation takes exactly one unit of time. Every cell in memory is reached in the same time, whatever its address. Operations run one at a time, in sequence. This abstract machine is called the RAM model (random-access machine). Real computers do not work this way: data in the cache is read many times faster than data in main memory. But the model is accurate enough for finding the growth class, and it makes the calculation much easier.

Let us apply the model to linear search. Linear search looks at the elements of the array one by one from the beginning to the end. When the sought value (target) is found, it returns its index; if the array ends, it returns −1:

for (int i = 0; i < a.length; i++) {
  if (a[i] == target)
    return i;
}
return -1;

For the count we find how many times each operation runs. Consider the worst case: the target is not in the array, so the loop runs to the end. Let the length of the array be n.

  • The assignment i = 0 is performed once when the loop starts.
  • The condition i < a.length is checked at the start of each round. For each value of i from 0 to n − 1 the condition is true; that makes n checks. When i = n the condition is checked once more and turns out false. In all, n + 1 checks are made.
  • The comparison a[i] == target is made once per round: n times.
  • i++ is performed once at the end of each round: n times.
  • return -1 runs once at the very end.

The total is T(n) = 1 + (n + 1) + n + n + 1 = 3n + 3. This number carries two kinds of information. The coefficient 3 and the constant +3 depend on what is counted as a step and on the machine. Had the array access and the comparison been counted as two separate operations, the coefficient would have been 4; had the compiler merged the condition check with the increment, it would have been 2. What does not change is that the step count grows in direct proportion to n. When the array doubles in size, the step count roughly doubles too. Asymptotic analysis keeps this unchanging part and discards the rest: T(n) = Θ(n). Here Θ(n) is read as “grows at the same rate as n”; its precise definition is given together with the asymptotic notation.

Common mistake

Thinking the loop condition is checked n times. The condition is checked n + 1 times, counting the final check that ends the loop. This difference does not change the growth class, but it leads to a wrong result in questions that ask for the exact step count.

2.1.5Best, worst, and average case

The step count of linear search depends not only on n. In two arrays of the same length, if the target sits in different places, the step counts differ. If the target is in the first cell, the search ends at once; if it is absent, the whole array is scanned. So the question “how many steps does linear search take?” has no single answer. The question must be asked while saying which input is meant. Three measures are used for this.

Definition 2.2

Consider all inputs of size n.

  • Best case: the number of operations of the input that requires the fewest operations among these inputs.
  • Worst case: the number of operations of the input that requires the most.
  • Average case: the expected number of operations under a probability distribution over the inputs.

The three measures do not have the same value. The worst case is the most used, because it gives a guarantee: the algorithm never takes longer than this on any input. In a real-time system, in the control software of an aircraft, or on a web server, this guarantee matters. The best case gives a lower bound, but by itself carries little information. Almost every algorithm is fast on some lucky inputs. The average case can give the most realistic estimate in practice; but to compute it one must know with what probability the inputs arrive. This information is often missing, and if the assumed distribution is wrong, so is the result.

Example 2.1

The array is [7, 3, 9, 4, 8, 1] (n = 6). The number of comparisons of linear search is computed for three cases.

  1. Best case. The target is 7, the first element. It is found at the first comparison: 1 comparison. However long the array is, this number does not change: Θ(1).
  2. Worst case. The target 5 is not in the array. All six elements are examined: 6 comparisons. If the target were the last element (1), 6 comparisons would be needed as well. In general, n comparisons: Θ(n).
  3. Average case. Assume that the target is in the array and is equally likely (1/6) to be at each of the six positions. A target at position k is found with k comparisons. The expected value is (1 + 2 + 3 + 4 + 5 + 6) / 6 = 21 / 6 = 3.5. In general, (1 + 2 + … + n) / n = (n + 1) / 2 comparisons are made. This number is half the worst case, but it still grows linearly with n: Θ(n).

The result (n + 1)/2 in the average-case computation comes from Gauss's summation formula: 1 + 2 + … + n = n(n + 1)/2. The same formula appears often in loop analysis. The factor 1/2 between the average and the worst case is a constant of the kind that asymptotic analysis discards. This is why the average and worst cases of linear search fall in the same class. It is not so for every algorithm: quicksort takes Θ(n log n) on average but Θ(n2) in the worst case.

Common mistake

Rounding the average number of comparisons to n/2. If the target is equally likely at each position, the average is exactly (n + 1)/2; for n = 6 it is 3.5, not 3. The class is the same, but in questions that want an exact number this difference means a wrong answer.

2.1.6Space complexity

The second resource, as important as time, is memory. Space complexity is usually given for the auxiliary space. The input itself is not counted, because every algorithm has to keep its input somewhere; what we really want to know is how much memory the algorithm asks for on top of that. An algorithm that sums an array with a single total variable uses only a few variables however long the array is. Its auxiliary space is Θ(1).

In recursive code there is a memory item that is easy to overlook. When a method is called, a stack frame is opened on the call stack for its parameters, local variables, and return address. When the method finishes, the frame is removed. As a recursive function calls itself, frames pile up. The largest number of frames on the stack at one time is the depth of the recursion. The auxiliary space is at least this depth.

Table 2.4 shows an important fact: time and space can grow at different rates. The function f3, which calls itself twice with n − 1, makes an exponential number (2n − 1) of calls. Yet its memory is only linear. The reason is that the calls run one after another, not at the same time. f3(n) first calls the left f3(n − 1) and does not move to the right one until all subcalls of this call have finished and their frames have been removed. At any moment the stack holds only one chain: f3(n), f3(n − 1), …, f3(1). The length of this chain is n.

The same reasoning applies to f4. In f4 the input halves with each call, so the chain has the form n, n/2, n/4, …, 1 and its length is about log2 n + 1. For example, while f4(16) runs, the stack holds at most 5 frames (16, 8, 4, 2, 1).

Common mistake

Confusing the memory of a recursive function with the total number of calls. For f3 it is wrong to say “there are 2n calls, each opens a frame, so the memory is Θ(2n).” The frame of a finished call is removed and its space is reused for the next call. The memory is determined by the largest number of frames open at the same time, that is, by the recursion depth.

2.2Asymptotic notation

When the step count came out as 3n + 3, we said that the coefficients would be discarded and only the fact that the growth is “linear” kept. The rules for this “discarding” must be precise; otherwise two people could assign different classes to the same code. Asymptotic notation sets these rules. The word “asymptotic” says that we are concerned with what happens as n goes to infinity. Behavior on small inputs and constant factors are deliberately ignored. Three notations are used: O for an upper bound, Ω for a lower bound, and Θ for a tight bound.

The O notation appeared long before algorithms, at the end of the 19th century, in number theory. Paul Bachmann used it in 1894, and Edmund Landau popularized it. In a short article in 1976, Donald Knuth defined Ω and Θ in their present senses and proposed that the three be used together in the analysis of algorithms. Today all algorithms textbooks use these definitions.

2.2.1Big O

Big O states an upper bound. The statement “f(n) = O(g(n))” says that for every sufficiently large n, f does not exceed a constant multiple of g. Two details matter. First, the constant multiple is free: g may be multiplied by 4 or by 100. Second, small n are irrelevant: it is enough for the inequality to hold beyond a threshold value.

Definition 2.3

f(n) = O(g(n)) if and only if there exist a positive constant c and a threshold n0 such that for every n ≥ n0

0 ≤ f(n) ≤ c · g(n)

holds. In this case g is an upper bound for f. The notation is called Big O notation.

The definition has two constants, and each has its own job. c swallows constant factors. The factor-of-3 difference between 3n2 and n2 disappears by choosing c = 3. n0 leaves out small inputs. The function n2 + 100 is larger than 2n2 at n = 1; but once n ≥ 10 it does not exceed it. Because the definition is concerned only with what comes after n0, such differences at the start do not affect the result.

An example: the function f(n) = 3n2 + 5n + 2 is O(n2). Indeed, with c = 4, 3n2 + 5n + 2 ≤ 4n2 holds for every n ≥ 6. How these constants are found is shown step by step a little further down. Figure 2.5 shows the situation on a graph.

Because Big O is an upper bound, it can also be loose. 3n2 + 5n + 2 is O(n2), and also O(n3) and O(2n); all these statements are true. But their information value is not the same. The sentence “this algorithm runs in O(2n) time” is true but misleading for a quadratic algorithm. In analysis one usually gives the smallest upper bound that can be found.

The equals sign in the notation is also open to misunderstanding. f(n) = O(g(n)) actually means “f belongs to the set of functions bounded above by a constant multiple of g.” The statement is therefore one-directional. n = O(n2) is true; but it does not follow that “O(n2) = n.” For this reason some books write f(n) ∈ O(g(n)).

Common mistake

Saying “Big O represents the worst case.” Big O is a kind of bound; the worst case is a kind of input. The two are independent. An upper bound can be written for the worst-case running time, for the best-case running time, and for the average running time. “The best case of linear search is O(1)” is a valid sentence. The source of the confusion is that in practice Big O is mostly used for the worst-case running time.

2.2.2Big Omega and Big Theta

The opposite of an upper bound is a lower bound. To say that an algorithm takes “at least this much,” Ω (Big Omega) is used. If the two bounds meet at the same function, the growth rate is known exactly; Θ (Big Theta) expresses this.

Definition 2.4

f(n) = Ω(g(n)): there exist c > 0 and n0 such that for every n ≥ n0, f(n) ≥ c · g(n) ≥ 0. In this case g is a lower bound for f.

f(n) = Θ(g(n)): there exist c1, c2 > 0 and n0 such that for every n ≥ n0, c1 · g(n) ≤ f(n) ≤ c2 · g(n). In this case g is a tight bound for f.

The last column of the table is a handy analogy: O behaves like “less than or equal,” Ω like “greater than or equal,” and Θ like “equal.” The analogy also recalls the basic relation: a number that is both ≤ g and ≥ g equals g. In the same way,

f = Θ(g) ⇔ f = O(g) and f = Ω(g).

Θ means squeezing between two constant multiples. Figure 2.6 shows this on 3n2 + 5n + 2: for n ≥ 6 the function stays between 3n2 and 4n2. It is therefore Θ(n2). Although the same function is O(n3), it is not Θ(n3). Every lower curve of the form c · n3, however small c is chosen, overtakes the function at some point. This is because the ratio f(n)/n3 tends to zero as n grows.

The distinction between growth class and case must be made once more here. For linear search all of the following sentences are true: the worst-case running time is Θ(n); the best-case running time is Θ(1); over all inputs the running time is O(n) and Ω(1). But the sentence “linear search is Θ(n)” is incomplete unless it says which case is meant. Insertion sort is similar: it takes Θ(n2) in the worst case and Θ(n) on sorted input; a single Θ cannot be written for all inputs. Merge sort, on the other hand, takes Θ(n log n) on every input; for it, writing Θ without naming a case is correct.

Common mistake

Using Θ and O interchangeably. “3n2 + 5n + 2 = Θ(n3)” is wrong; what is correct is O(n3). Θ requires both a lower and an upper bound and gives the growth rate of the function exactly. In everyday speech, “this algorithm is O(n2)” often means Θ(n2); in a written analysis this distinction should be kept.

2.2.3Finding the constants

Proving a bound means finding the constants in the definition concretely. The method is the same every time: choose a c, solve the inequality, and find from which n on it holds. The constants are not unique; any valid pair suffices for a proof.

Example 2.2

We show that f(n) = 3n2 + 5n + 2 = Θ(n2). For this two inequalities are needed: an upper bound and a lower bound.

  1. Choosing c2 for the upper bound. Since the leading coefficient is 3, a number slightly larger than 3 is tried: c2 = 4. The desired inequality is 3n2 + 5n + 2 ≤ 4n2.
  2. Solving the inequality. Everything is collected on one side: n2 − 5n − 2 ≥ 0. The positive root of the quadratic equation is (5 + √33)/2 ≈ 5.37. The inequality holds for n larger than this root. Since the smallest integer is 6, n0 = 6.
  3. Checking the bound. At n = 5 the left side is 75 + 25 + 2 = 102 and the right side is 100; the inequality fails. At n = 6 the left side is 108 + 30 + 2 = 140 and the right side is 144; the inequality holds.
  4. Seeing that it keeps holding. When n increases by one, the left side grows by 6n + 8 and the right side by 8n + 4. For n ≥ 6, 8n + 4 > 6n + 8, so the right side grows more at every step. The gap (4) that opened at n = 6 therefore never closes; it only grows.
  5. The lower bound. Choose c1 = 3. The inequality 3n2 + 5n + 2 ≥ 3n2 is true for every n ≥ 1 because 5n + 2 > 0.
  6. Combining. Together the two inequalities hold for n ≥ 6: 3n2 ≤ f(n) ≤ 4n2. With c1 = 3, c2 = 4, n0 = 6 the definition is satisfied: f(n) = Θ(n2).

To see that the constants are not unique, another choice can be made. If c2 = 10 is chosen, then already at n = 1, 3 + 5 + 2 = 10 ≤ 10. Also, for every n ≥ 1, 5n ≤ 5n2 and 2 ≤ 2n2, so one can write 3n2 + 5n + 2 ≤ 3n2 + 5n2 + 2n2 = 10n2. This proof does not require computing the root: each term is bounded by the largest power and the coefficients are added. A large c means a small n0; a small c requires a larger threshold.

The same method applies to a linear function. To show that 2n + 10 = O(n), choose c = 3; then 2n + 10 ≤ 3n holds for n ≥ 10: c = 3, n0 = 10. With the term-by-term bounding method one writes 2n + 10 ≤ 2n + 10n = 12n, which gives c = 12, n0 = 1.

It is also possible to show that a bound is wrong. For this one proves that no pair of constants works, usually by contradiction. Suppose n2 = O(n). Then for some c and n0, for every n ≥ n0 we must have n2 ≤ c · n, that is, n ≤ c. But n can be chosen larger than both n0 and c, for example n = max(n0, ⌈c⌉ + 1). For this n, n ≤ c fails. Since the assumption leads to a contradiction, it is false: n2 ≠ O(n).

Common mistake

Trying only a single value of n in a proof. “At n = 10, f(10) ≤ 4 · 100, so it is O(n2)” is insufficient. The definition requires the inequality to hold for every n beyond n0. One has to solve the inequality algebraically or bound each term by the largest power.

2.2.4Rules of calculation

Searching for constants every time is laborious. A few rules that follow from the definitions often let us read off the class directly.

  • Constant factors are dropped. c · f(n) = Θ(f(n)); for example 5n = Θ(n) and n2/3 = Θ(n2). The constant factor is absorbed into the c of the definition.
  • Lower-order terms are dropped. In a polynomial the term with the largest power remains: 4n3 + 100n2 + 7 = Θ(n3). As n grows, 100n2 becomes negligible next to 4n3; at n = 1000 it is about a fortieth of it.
  • Sum rule: sequential code. The total running time of two pieces of code that run one after the other is the running time of the larger: O(f) + O(g) = O(max(f, g)). If a loop that takes Θ(n) is followed by a loop that takes Θ(n2), the total is Θ(n2).
  • Product rule: nested code. If a loop that runs n times contains work that takes O(g), the total is O(n · g). The rule assumes that the inner work is the same in every round. If the running time of the inner work depends on the counter of the outer loop, a sum is computed instead of a product.
  • The base of a logarithm is irrelevant. By the change-of-base formula, loga n = logb n / logb a. The difference between two bases is only a constant factor. This is why one writes O(log2 n) = O(log10 n) = O(log n) and often does not state the base.
  • In exponentials the base matters. 3n = O(2n) is false. The ratio 3n/2n = 1.5n goes to infinity; no constant factor can close this gap. Unlike logarithms, exponential bases are not related by a constant factor.

As a consequence of these rules, the common functions fall into a definite order of growth:

1 < log n < √n < n < n log n < n2 < n3 < 2n < n!

Here the sign “<” says that the one on the left becomes negligible relative to the one on the right: for large n the ratio goes to zero. For example the ratio log n / √n approaches zero, though slowly at first.

Common mistake

Leaving constants and small terms in the result: writing O(3n + 3) or O(n2/3 + n). These expressions are not wrong, but they go against the purpose of the notation. The correct forms are O(n) and O(n2). Similarly one writes O(2n) instead of O(2n+1), since 2n+1 = 2 · 2n; but 22n = 4n is not O(2n).

2.3Loop analysis

A piece of code without loops and without recursion performs a constant number of operations; its running time is Θ(1). What ties the running time to the input is loops and recursion. This section deals with loops. The method can be stated in one sentence: find how many rounds each loop runs, and for nested loops add up these round counts. The method is applied to three example functions: f1 with a single loop, f2 whose inner loop bound depends on the outer counter, and f6 whose counter grows at an unusual rate.

The six example functions of this chapter share a trick: each returns a counter x that increases with the work done. The return value thus becomes the step count itself. The formula found by analysis can be checked directly by running the function and looking at the return value. All the return values and call counts given in these notes were obtained by running the code in Java.

2.3.1f1: a single loop

public int f1(int n) {
  int x = 0;
  for (int i = 0; i < n; i++) {
    x++;
  }
  return x;
}

The code has three parts.

  • Initialization: the line int x = 0; assigns 0 to x. This is a single operation, independent of the input: O(1).
  • The loop: in the header for (int i = 0; i < n; i++), i starts at 0, increases by one each round, and goes up to n − 1. The values 0, 1, …, n − 1 number n; the loop runs n rounds.
  • The body: x++; runs once per round and is a constant-time operation: O(1).

By the product rule, a loop that runs n times doing O(1) work per round does n · O(1) = O(n) work in total. The initialization and the return outside the loop are constant work; by the sum rule they do not change the result:

T(n) = O(1) + n · O(1) = Θ(n)

Since the body runs exactly n times, the lower bound is also n; the result is therefore written with Θ. The function returns x = n: f1(16) = 16, f1(32) = 32. The return value is the step count itself, and it doubles when the input doubles. This is the signature of linear growth.

2.3.3f2: nested loops

public int f2(int n) {
  int x = 0;
  for (int i = 0; i < n; i++) {
    for (int j = 0; j < i * i; j++) {
      x++;
    }
  }
  return x;
}

In f2 two loops are nested. The outer loop is like the one in f1: i goes from 0 to n − 1 and runs n rounds. The bound of the inner loop, however, is not constant. j goes from 0 to i · i − 1; that is, in the current round of the outer loop the inner loop runs i2 times. At i = 0 the inner loop does not run at all, at i = 1 it runs once, at i = 2 four times, at i = 3 nine times.

Because the number of rounds of the inner loop depends on the current value of i, the product rule cannot be applied directly. To say “the outer loop runs n rounds, the inner loop n rounds, total n · n” is wrong, because the inner loop runs a different number of times in each round. The right way is to write down the inner round count for each outer round and add them up:

T(n) = 02 + 12 + 22 + … + (n − 1)2 = Σi=0n−1 i2

Common mistake

Automatically counting two nested loops as O(n2). The result is determined by the bound of the inner loop. In f2 the bound is i2, so the result is of order n3. With the bound j < i it would be quadratic, with j < 10 linear. If the outer loop advanced with i *= 2, the result would again come out different.

The seventh row is surprising. On the surface its structure resembles the previous one: a logarithmic outer loop with an inner loop inside it. But the bound of the inner loop is i, and i grows quickly. The total is a geometric series:

1 + 2 + 4 + … + 2k = 2k+1 − 1 < 2n

Here 2k is the largest power of two smaller than n; hence 2k+1 < 2n. Although the outer loop runs log n times, the total work is linear. At n = 16, 1 + 2 + 4 + 8 = 15 rounds are made. This is the property of a geometric series: the sum is determined by its last term, and the last term is larger than the sum of all the earlier ones.

Example 2.3

Find the number of x++ executions and the growth class of the following two pieces of code.

// first part

  2. Second part. The outer loop runs ⌊log2 n⌋ + 1 rounds, at i = n, n/2, n/4, …, 1. The inner loop runs n times in each round, because its bound is n. The total is n · (⌊log2 n⌋ + 1): Θ(n log n). For n = 10, i = 10, 5, 2, 1 and x++ is executed 4 · 10 = 40 times.

The outer loops of the two parts run a similar number of rounds; the difference comes from the bound of the inner loop. If the bound depends on the outer counter, the round counts are added; if it does not, they are multiplied.

Common mistake

Always counting an inner loop inside a logarithmic outer loop as Θ(n log n). The first part of the example above is only Θ(n), although the outer loop runs log n times. One does not decide without writing down the inner round count for each outer round and adding them up.

2.3.7f6: a loop with a shifting bound

public static int f6(int n) {
  int x = 0;
  // 1 << i equals 2^i (overflow is ignored)
  for (int i = 0; i < n; i = 1 << i) {
    x++;
  }
  return x;
}

At first sight the loop of f6 resembles a multiplicative loop, but its update is different.

  • Initialization: int i = 0; is a constant-time assignment.
  • Condition: i < n checks at the start of each round whether i is smaller than n.
  • Update: i = 1 << i. The left-shift operator << shifts the bits of the number 1 to the left by i places. In binary, shifting 1 to the left by i places multiplies it by 2i. The result is 2i, computed in a single operation, in constant time.

The critical point is this: the update is not i = 2 * i but i = 2i. In a multiplicative loop i doubles in each round. In f6, i itself becomes the exponent. This makes i grow much faster: the value 4 becomes not 8 in the next round but 24 = 16. And 16 becomes not 32 but 216 = 65,536.

2.3.9How many rounds does f6 really run?

The values of i in f6 grow like a tower of powers of two:

0 → 20 = 1 → 21 = 2 → 22 = 4 → 24 = 16 → 216 = 65,536 → 265,536

The last value is a number with 19,729 digits. The number of atoms in the universe is estimated at about 1080; next to this number, 1080 is tiny. Since no real input can be that large, f6 runs at most six rounds for any n one can imagine.

A common line of reasoning for this loop goes: “after k rounds i ≥ 2k; the loop stops when 2k ≥ n; so k ≈ log2 n and the time is O(log n).” The reasoning is correct for the loop i = 2 * i. For f6 the result is not wrong either, because i at least doubles, so the round count cannot exceed log2 n. But this bound is not tight. In f6, after k rounds i is a tower of height k − 1, and the round count is given by a function that grows much more slowly.

Definition 2.5

The iterated logarithm log* n gives the number of times log2 must be applied to n in succession until the result is less than or equal to 1. For example, since log2 16 = 4, log2 4 = 2, log2 2 = 1, we have log* 16 = 3.

The round count of f6 is exactly log* n + 1. This equality was checked for every value from n = 1 to 70,000 with a Python script. log* n does not exceed 5 for any input one can imagine: log* 65,536 = 4, and to reach 5, n must exceed 65,536. The smallest number with value 6 is larger than 265,536. This function, which behaves like a constant in practice, also appears in the analysis of the union-find data structure.

2.4Analysis of recursion

In looping code the round counts are added. In recursive code, the running time depends on the running time of the same function on smaller inputs. To find T(n), values such as T(n − 1) or T(n/2) are needed first. The equation that expresses this relation is called a recurrence relation. This section explains how the relation is set up and the most basic solution method, unrolling.

2.4.1The recurrence relation

Definition 2.6

A recurrence relation is an equation that defines T(n) in terms of the values of T on smaller inputs. For the running time of a recursive function, the general form is:

T(n) = (running times of the subcalls) + (work done outside the calls), T(base) = Θ(1)

The second equation gives the running time of the base case, which the recursion solves directly without calling itself.

To set up the relation, three questions are asked of the code:

  1. How many recursive calls are there? This number becomes the coefficient of T in the relation.
  2. By how much does the input of each call shrink? If the input decreases by one, write T(n − 1); if it halves, write T(n/2).
  3. How much work is done outside the calls? The running time of work such as splitting, merging, and adding enters the relation as an additional term.

Once the relation is set up, it has to be solved; that is, a closed form of T(n) not containing T is found. There are three methods:

  • Unrolling (substitution): the relation is substituted into itself repeatedly, a pattern is found, and when the base case is reached the terms are added up. Used for f3.
  • Recursion tree: each call is drawn as a node, the work at each level is added up, and then the level sums are added. Used for f3, f4, and f5.
  • Master Theorem: gives a ready-made result for relations of the form T(n) = aT(n/b) + f(n). Used for f4 and f5.

2.4.2f3: two calls, n − 1

public long f3(int n) {
  if (n <= 1) {
    return 1;
  }
  return f3(n - 1) + f3(n - 1);
}

f3 has two parts.

  • Base case: when n ≤ 1 the function returns 1. This is constant-time work: T(1) = c.
  • Recursive case: when n > 1, f3(n − 1) is called twice and the results are added. The addition and the comparison are constant work; this too is called c.

Once the three questions are answered, the relation emerges: there are two calls, each of size n − 1, and constant work is done outside the calls.

T(n) = 2T(n − 1) + c, n > 1;  T(1) = c

The input shrinks by only one in each call, but the number of calls doubles at every level. f3(4) calls two f3(3); each f3(3) calls two f3(2); each f3(2) calls two f3(1). The levels have 1, 2, 4, 8 calls, and the total is 1 + 2 + 4 + 8 = 15 = 24 − 1 (Figure 2.13).

This relation is not of the form T(n/b); the subproblem shrinks not by division but by subtracting one. The Master Theorem therefore does not apply, and the relation is solved by unrolling.

2.4.4Unrolling the recurrence

In the unrolling method, the T(n − 1) on the right-hand side of the relation is replaced by its own definition. After a few repetitions a pattern appears in the coefficients. The pattern is written in general form and the step at which the base case is reached is found.

Example 2.4

Solve the relation T(n) = 2T(n − 1) + c, T(1) = c by unrolling.

  1. The relation itself: T(n) = 2T(n − 1) + c. Two subcalls, constant extra work.
  2. Unrolling once: substitute T(n − 1) = 2T(n − 2) + c: T(n) = 2[2T(n − 2) + c] + c = 4T(n − 2) + 3c.
  3. Once more: substitute T(n − 2) = 2T(n − 3) + c: T(n) = 4[2T(n − 3) + c] + 3c = 8T(n − 3) + 7c.
  4. The pattern: the coefficients of T are 2, 4, 8; those of c are 1, 3, 7. The first are powers of two, the second are powers of two minus one. After k steps: T(n) = 2k T(n − k) + (2k − 1)c.
  5. Reaching the base case: when n − k = 1, that is, k = n − 1, use T(1) = c: T(n) = 2n−1c + (2n−1 − 1)c = (2n − 1)c.
  6. Result: T(n) = Θ(2n).

The result agrees exactly with the number of calls of f3: each call does c work and there are 2n − 1 calls. The formula can be checked with small values: T(1) = c, T(2) = 3c, T(3) = 7c. Counted in Java, f3(16) makes 65,535 calls and f3(32) makes 4,294,967,295; both equal 2n − 1. When n goes from 16 to 32, the number of calls grows by a factor of 65,537. This is the signature of exponential growth: when the input doubles, the time reaches a value close to its square.

In unrolling it is also possible to neglect the extra work (c) and write T(n) = 2k T(n − k). This gives T(n) = 2n−1 T(1) and the growth class does not change. The extra work only doubles the constant factor.

Unrolling also applies to other subtractive relations. Unrolling T(n) = T(n − 1) + n, T(1) = 1 gives T(n) = n + (n − 1) + … + 2 + 1 = n(n + 1)/2: Θ(n2). This relation arises in algorithms that do n work at each step and shrink the problem by only one. The worst case of quicksort is an example.

Common mistake

Memorizing the rule “two recursive calls mean exponential time.” In f3 two calls give Θ(2n) because the input shrinks by only one and the depth of the tree is n. If the input halved, the depth would be log2 n and the time would drop to linear. What decides is not the number of calls but the joint effect of the number of calls and the way the input shrinks.

2.5The Master Theorem

Unrolling works for every recurrence, but it is laborious. A large share of algorithms use the divide-and-conquer approach, which splits the problem into pieces of equal size. The recurrences of these algorithms always have the same form. The Master Theorem gives a ready-made result for recurrences of this form. The theorem rests on a general method published by Jon Bentley, Dorothea Haken, and James Saxe in 1980; the name “Master Theorem” became popular through the textbook of Cormen and colleagues.

2.5.1The divide-and-conquer recurrence

A divide-and-conquer algorithm splits a problem of size n into a subproblems of size n/b each, solves the subproblems recursively, and combines the results. Its recurrence is:

T(n) = a · T(n/b) + f(n), a ≥ 1, b > 1

  • a: the number of subproblems (recursive calls).
  • b: the shrinking ratio; each subproblem has size n/b.
  • f(n): the work the call itself does, that is, the work of splitting the problem and combining the results.

The recursion tree of this recurrence has a regular structure (Figure 2.16). There is a single node at the root, and it does f(n) work. Each node has a children; level j has aj nodes, each dealing with a problem of size n/bj. Since the input is divided by b at every level, the depth of the tree is logb n. The number of leaves at the last level is

alogb n = nlogb a

The equality of the two expressions is seen by taking logb of both sides: both give logb n · logb a. Since each leaf does constant work, the total work of the leaves is Θ(nlogb a). This quantity is at the center of the theorem: f(n) is always compared with it.

2.5.2The three cases

The theorem compares f(n) with the leaf work nlogb a. The comparison has three outcomes: the work near the root dominates, the work at the leaves dominates, or the levels are balanced. Below is the commonly used form of the theorem, written with the polynomial degree c of f(n).

Theorem 2.1 (Master Theorem)

Let a ≥ 1 and b > 1 be constants and T(n) = aT(n/b) + f(n).

  1. If f(n) = O(nc) for some c < logb a, then T(n) = Θ(nlogb a). (The leaves dominate.)
  2. If f(n) = Θ(nc) for c = logb a, then T(n) = Θ(nlogb a · log n). (The levels are balanced.)
  3. If f(n) = Ω(nc) for some c > logb a, and a constant k < 1 exists such that a · f(n/b) ≤ k · f(n) for every sufficiently large n, then T(n) = Θ(f(n)). (The root dominates.)
Table 2.16: The three cases of the Master Theorem (c: the polynomial degree of f(n)).
CaseConditionResultInterpretation
1f(n) = O(nc), c < logb aΘ(nlogb a)leaves dominate
2f(n) = Θ(nc), c = logb aΘ(nlogb a · log n)levels balanced
3f(n) = Ω(nc), c > logb a and a · f(n/b) ≤ k · f(n), k < 1Θ(f(n))root dominates

The use of different notations in the three cases is no accident. In Case 1 an upper bound on f(n) suffices, because the leaf work is already larger than f and swamps it. In Cases 2 and 3, writing only f(n) = O(nc) is not enough. For example f(n) = 1 is also O(n2); but the solution of T(n) = T(n/2) + 1 cannot be Θ(n2). This is why Case 2 requires f = Θ(nc), and Case 3 requires f = Ω(nc) and in addition the regularity condition. When these conditions hold, the results are given with Θ, that is, as tight bounds.

The regularity condition is specific to Case 3: a · f(n/b) ≤ k · f(n). It means that the total work of the root's children is no more than a constant fraction of the root's own work. Thus the work grows steadily toward the root. For polynomials such as f(n) = nc the condition holds automatically: a(n/b)c = (a/bc) nc, and since c > logb a, a/bc < 1; one can take k = a/bc.

2.5.3Why three cases? Level sums

Why the theorem has three cases becomes clear when we look at the level sums of the recursion tree. Let f(n) = nc. Level j has aj nodes, each doing (n/bj)c work. The total work of the level is

aj · (n/bj)c = nc · (a/bc)j

The level sums form a geometric series with ratio r = a/bc. T(n) is the sum of this series from j = 0 to logb n. The behavior of a geometric series depends only on the ratio:

  • r > 1: the series grows. The last term, that is, the leaves, determines the sum. This is Case 1. Example: for 4T(n/2) + n, r = 4/2 = 2; the level sums grow as n, 2n, 4n, … and the result is Θ(n2).
  • r = 1: the terms are equal. Every level does the same work; the total is the number of levels times the work per level. This is Case 2. Example: for 2T(n/2) + n, r = 2/2 = 1; each of the log n levels does n work and the result is Θ(n log n).
  • r < 1: the series shrinks. The first term, that is, the root, determines the sum. This is Case 3. Example: for 2T(n/2) + n2, r = 2/4 = 1/2; the level sums shrink as n2, n2/2, n2/4, …, their total does not exceed 2n2 and the result is Θ(n2).

The ratio being greater than 1 is the same as c < logb a: r > 1 ⇔ bc < a ⇔ c < logb a. The three cases of the Master Theorem thus correspond to the geometric series growing, staying constant, or shrinking. Instead of memorizing the theorem, it is enough to keep this picture in mind: a is compared with bc.

These results can also be checked with a small computation. When the recurrences are computed directly with T(1) = 1, for n = 16 the recurrence 2T(n/2) + n gives 80, which is the value of n log2 n + n. The recurrence 2T(n/2) + n2 gives 496, that is, 2n2 − n; the n2 = 256 at the root is more than half of the total.

2.5.4Example: 2T(n/2) + n

Example 2.5

Solve the recurrence T(n) = 2T(n/2) + Θ(n) with the Master Theorem.

  1. Reading the parameters. Two subproblems (a = 2), each of half the size (b = 2), linear merging work (f(n) = Θ(n)).
  2. The exponent of the leaf work. logb a = log2 2 = 1; the leaf work is n1 = n.
  3. The degree of f(n). f(n) = Θ(n1), that is, c = 1.
  4. Comparison. c = logb a = 1: the exponents are equal, and each level does the same amount (n) of work. Case 2.
  5. Result. T(n) = Θ(nlogb a · log n) = Θ(n log n).

This recurrence turns up in several of the best-known algorithms.

  • Merge sort: the array is split in two, the two halves are sorted separately, and the sorted halves are merged in Θ(n) time.
  • f5: one of the example functions of this chapter; it calls f1(n) (linear work) and calls itself twice with n/2.
  • Quicksort: if the pivot splits the array into two equal parts every time, the recurrence is the same.

2.5.6Recurrences the theorem does not cover

The Master Theorem is powerful, but it applies only to recurrences of a particular form. For recurrences outside this form another method is needed.

  • Subtractive recurrences. T(n) = 2T(n − 1) + c (f3) or T(n) = T(n − 1) + n: the subproblem is n − 1, not n/b. Unrolling is used.
  • A non-polynomial gap. T(n) = 2T(n/2) + n / log n: nlog2 2 = n is compared with f(n) = n / log n. f(n) is smaller than n, but only by a log factor, not by a polynomial factor like nε. So neither the condition of Case 1 nor that of Case 2 holds. (The solution of this recurrence is Θ(n log log n) and is found with a recursion tree.)
  • Unequal splits. T(n) = T(n/3) + T(2n/3) + n: the subproblems have different sizes. In the recursion tree the work at each level is at most n and the longest branch has depth log3/2 n; the result is Θ(n log n). Recurrences of this kind are generally solved by the Akra–Bazzi method.
  • Non-constant a or a < 1. T(n) = 2n T(n/2) + n or T(n) = ½ T(n/2) + n: the theorem's assumption that a ≥ 1 is constant is violated.

A commonly used extension of the basic form carries Case 2 over to logarithmic factors: if f(n) = Θ(nlogb a · logk n) and k ≥ 0, then T(n) = Θ(nlogb a · logk+1 n). For example, for T(n) = 2T(n/2) + n log n, k = 1 and the result is Θ(n log2 n). This extension also solves some recurrences that the basic form calls “not applicable.”

Common mistake

In Case 3, checking only the condition c > logb a and forgetting regularity. For polynomials the condition holds automatically, so the mistake usually does not change the result; but in examples where f(n) oscillates the condition fails. In the recurrence T(n) = T(n/2) + n(2 − cos n), c = 1 > 0; but for the values of n where cos n is near 1 and cos(n/2) near −1, the ratio f(n/2)/f(n) approaches 1.5 and no k < 1 satisfies the condition. When using Case 3, the inequality a · f(n/b) ≤ k · f(n) should be written out explicitly.

2.6Application: f4 and f5

This section solves two recursive functions with all three methods: tracing, the recursion tree, and the Master Theorem. f4 differs from f3 only in the argument of the recursive calls (n / 2 instead of n - 1); but this change brings the time down from exponential to linear. f5 adds linear work to f4 at each call and gives the recurrence of merge sort.

2.6.1f4: two calls, n/2

public int f4(int n) {
  if (n <= 1) {
    return 1;
  }
  return f4(n / 2) + f4(n / 2);
}
  • Base case: returns 1 when n ≤ 1; O(1).
  • Recursive case: when n > 1, f4(n / 2) is called twice and the results are added. The addition is constant work.

T(n) = 2T(n/2) + O(1), T(1) = O(1)

In Java n / 2 is integer division; the fractional part is discarded. In the analysis n is assumed to be a power of two, so that every division is exact. This assumption does not change the growth class.

The only difference from f3 is that the input is n/2 instead of n − 1. The number of calls still doubles at every level; but since the input halves at every level, the tree is only log2 n levels deep. For n = 8 the levels have 1, 2, 4, 8 calls and the inputs are 8, 4, 2, 1. In f3 a tree starting from 8 would descend 8 levels; here it ends at 4 levels.

Two calls do not always mean exponential time. What decides is how much the input shrinks. If the input decreases by one, the tree descends to depth n and reaches 2n leaves. If the input halves, the tree stays at depth log2 n and reaches 2log2 n = n leaves.

2.6.2The recursion tree of f4

In the recursion-tree method each call is drawn as a node and the work it does is written next to it. Then the work of each level is added up, and finally the level sums are added. For f4(8):

  1. Root: f4(8) does only constant work (c) and starts two calls. The work of level 0 is c.
  2. Level 1: two calls f4(4); total 2c.
  3. Level 2: four calls f4(2); total 4c. The work per level doubles at each step.
  4. Leaves: eight f4(1); total 8c = n · c.

The total is c(1 + 2 + 4 + 8) = 15c = (2n − 1)c; that is, Θ(n). The level sums grow geometrically and the last term, the work of the leaves, determines the sum. Counted in Java, f4(16) makes 31 calls and f4(32) makes 63; both equal 2n − 1. The return value of the function also equals the number of leaves: f4(n) = n.

If n is not a power of two, integer division comes into play. f4(10) first calls two f4(5), each f4(5) calls two f4(2), and each f4(2) calls two f4(1). The number of calls is 15 and the return value is 8. The result is as if it had worked for the largest power of two (8) not exceeding n; the growth class is still linear.

  2. Leaf work. logb a = log2 2 = 1; the leaf work is n1 = n.

The Master Theorem gives the result of the recursion tree without computing the sum. In the tree we counted 2n − 1 nodes; the theorem merely says “the leaves dominate,” and since the number of leaves is n, it arrives at Θ(n).

The memory of f4 is a different question. Because the calls run in sequence, the stack holds only one branch at a time: f4(n), f4(n/2), …, f4(1). The length of this branch is log2 n + 1; while f4(16) runs, the stack holds at most 5 frames. The time is Θ(n) and the auxiliary space is Θ(log n).

Common mistake

Saying of f4, “the input halves at every step, so it is O(log n).” This reasoning is correct for binary search, which makes a single call. f4 makes two calls, and both branches descend all the way. log n is only the stack depth, that is, it gives the memory; the time is Θ(n).

public int f5(int n) {
  if (n <= 1) {

  • Recursive case: when n > 1, f1(n) is called first. f1 is a loop that runs n rounds and does Θ(n) work. Then f5(n / 2) is called twice.

T(n) = 2T(n/2) + f1(n) = 2T(n/2) + Θ(n)

Its only difference from f4 is the linear work done at each call. The recurrence is the same as that of merge sort. A common mistake here is to consider the two parts separately and add them: “f1 is linear, the recursion is logarithmic, the total is O(n + log n) = O(n).” This is wrong. f1 is called not only at the root but at every node of the tree; each node does as much work as its input size. The sum of these works must be found.

2.7.2Amortized analysis

In some data structures most operations are cheap and an occasional few are expensive. In such a structure, looking at the worst case of a single operation overstates the total cost. Amortized analysis looks at the whole sequence of operations.

Definition 2.7

Amortized analysis finds the cost per operation by dividing the worst-case total cost of a sequence of operations by the number of operations. The value found is called the amortized cost.

The classic example is the dynamic array, such as Java's ArrayList. When the array is full, its capacity is doubled: a new array of twice the size is allocated and all the elements are copied into it. This insertion is expensive. Insertions made while there is room are a single write and cost 1 unit. The code below spells out this logic; the cost is the sum of the number of writes and the number of elements copied.

int[] data = new int[1];
int size = 0;
long cost = 0;

void add(int x) {
  if (size == data.length) {                // array is full
    int[] bigger = new int[2 * data.length]; // double the capacity
    for (int i = 0; i < size; i++) {
      bigger[i] = data[i];                  // copy: 1 unit
      cost++;
    }
    data = bigger;
  }
  data[size++] = x;                         // write: 1 unit
  cost++;
}
Example 2.8

Nine elements are added to an empty dynamic array of capacity 1. The cost of each insertion (1 write + the number of copies) is:

  1. Insertion 1: there is room, 1 write. Cost 1.
  2. Insertion 2: the array is full; capacity 1 → 2, 1 copy + 1 write. Cost 2.
  3. Insertion 3: full; capacity 2 → 4, 2 copies + 1 write. Cost 3.
  4. Insertion 4: there is room. Cost 1.
  5. Insertion 5: full; capacity 4 → 8, 4 copies + 1 write. Cost 5.
  6. Insertions 6, 7, and 8: there is room. Each costs 1.
  7. Insertion 9: full; capacity 8 → 16, 8 copies + 1 write. Cost 9.

The total is 1 + 2 + 3 + 1 + 5 + 1 + 1 + 1 + 9 = 24 units; the average per insertion is 24/9 ≈ 2.67. The worst cost of a single insertion is 9, but for the whole array 24 < 3 · 9 = 27 units were spent.

Theorem 2.2 (Amortized cost of doubling)

The total cost of n insertions into a dynamic array whose capacity starts at 1 and is doubled when full is less than 3n. The amortized cost per insertion is Θ(1).

Capacity increases occur when the array is full with 1, 2, 4, …, 2k elements, where 2k is the largest power of two smaller than n. The total number of copies is a geometric series: 1 + 2 + 4 + … + 2k = 2k+1 − 1 < 2n. Each insertion also makes one write; that is n units. The total is < 2n + n = 3n. Divided by n, the cost per insertion comes out below 3, that is, constant. □

The theorem rests on the moments when copying is expensive being rare. A capacity increase copies m elements, but after it m more insertions are done cheaply. The cost of the expensive operation is “spread” over the cheap operations that follow it. In a count done with Python, the total cost of 1000 insertions comes out to 2023; this is below 3n = 3000.

Why doubling matters becomes clear when it is compared with growing by a fixed amount. If the capacity were increased by just 1 when the array is full, every insertion would copy the whole array. The total cost of n insertions would be 1 + 2 + … + n = n(n + 1)/2, that is, Θ(n2); for n = 1000, 500,500 units. Even if the capacity were increased by a fixed k, the result would not change; only the constant factor would shrink.

Amortized analysis differs from average-case analysis. The average case rests on a probability distribution over the inputs and gives the “expected” time. In amortized analysis there is no probability: a guarantee is given for every sequence of operations, even the worst one. In a dynamic array a single insertion can take Θ(n); but whatever the order of insertions, the total of n insertions does not exceed 3n. There are three standard methods of finding the amortized cost: the aggregate method (used here), the accounting method, and the potential method.

Common mistake

Reading amortized Θ(1) as “every insertion takes constant time.” The amortized bound says nothing about the time of a single operation; the 9th insertion took 9 units. In real-time systems where every operation must be short, an amortized bound is not enough; a worst-case bound is needed.

2.8Common mistakes

The most important of the mistakes given in the boxes throughout the chapter are collected here:

  • Equating Big O with the worst case. O is an upper bound, while the worst case is a kind of input. “The best case is O(1)” is a valid sentence.
  • Writing constants and small terms. One does not write O(3n + 3) or O(n2/3 + n); O(n) and O(n2) suffice.
  • The rule “nested loops = n2.” The bound of the inner loop determines the result. In f2 the bound is i2, so the result is Θ(n3); a loop advancing with i *= 2 runs log n rounds.
  • The rule “two calls = exponential.” f3 (n − 1) is Θ(2n), f4 (n/2) is Θ(n). The way the input shrinks determines the result.
  • Applying the Master Theorem to every recurrence. The theorem does not hold for recurrences that contain T(n − 1), split unevenly, or have a non-polynomial gap such as f(n) = n / log n.
  • Forgetting regularity in Case 3. c > logb a is not enough; a · f(n/b) ≤ k · f(n), k < 1 must hold as well.
  • Confusing the memory of recursion with the call count. Memory is determined by the number of frames open at the same time, that is, the depth: Θ(n) for f3, Θ(log n) for f4.
  • Confusing a shift with a multiplication. i = 1 << i is 2i, not 2 * i. The tight bound for f6 is Θ(log* n).

2.9Summary

  • Time complexity T(n) gives how the number of basic operations grows with the input size n. Space complexity S(n) gives the memory used in addition to the input; in recursion the depth of the call stack counts toward this memory.
  • Timing depends on the machine and gives no prediction for large inputs. In the RAM model every basic operation counts as one unit; linear search takes 3n + 3 steps in the worst case and is Θ(n).
  • The best, worst, and average case concern different inputs of the same size. In linear search they make 1, n, and (n + 1)/2 comparisons respectively.
  • f = O(g) is an upper bound, f = Ω(g) a lower bound, and f = Θ(g) a tight bound. Bounds are proved by finding the constants c and n0; for 3n2 + 5n + 2, c1 = 3, c2 = 4, n0 = 6. The case (which input) and the bound (O, Ω, Θ) are separate notions.
  • Rules of calculation: constant factors and lower-order terms are dropped; for sequential code the larger remains, for nested code the round counts are multiplied or added; the base of a logarithm is irrelevant, while the base of an exponential matters. The order of growth: 1 < log n < √n < n < n log n < n2 < n3 < 2n < n!.
  • In loop analysis the inner round count is written for each outer round and added up. f1: Σ 1 = n, Θ(n). f2: Σ i2 = (n − 1)n(2n − 1)/6, Θ(n3). A multiplicative loop is Θ(log n); a multiplicative loop with j < i inside it is Θ(n) because of the geometric series.
  • In f6, i = 1 << i, that is, i ← 2i; the round count is log* n + 1. O(log n) is correct but not tight; the tight bound is Θ(log* n). In Java, for n > 65,536 the shift overflows and the loop does not terminate.
  • A recurrence relation is built from the number of calls, the way the input shrinks, and the extra work. f3: T(n) = 2T(n − 1) + c; by unrolling, (2n − 1)c = Θ(2n). Its memory is only Θ(n).
  • The Master Theorem compares f(n) in T(n) = aT(n/b) + f(n) with the leaf work nlogb a: leaves dominate (Case 1), levels balanced (Case 2, an extra factor log n), root dominates (Case 3, with the regularity condition). The three cases correspond to the geometric series with ratio a/bc growing, staying constant, or shrinking.
  • The theorem does not apply to subtractive recurrences, recurrences with unequal splits, a non-polynomial gap in f(n), or a non-constant a.
  • f4: 2T(n/2) + 1, Case 1, Θ(n); 2n − 1 calls, Θ(log n) memory. f5: 2T(n/2) + n, Case 2, Θ(n log n); f5(n) = n log2 n + n.
  • Amortized analysis divides the total cost of a sequence of operations by the number of operations. In a dynamic array that doubles, the total of n insertions is less than 3n; insertion is amortized Θ(1). Unlike the average case, it uses no probability.

2.11Test Yourself

  1. For the bound 5n3 + 2n + 8 = O(n3), c = 6 is chosen. What is the smallest n0 for which the inequality 5n3 + 2n + 8 ≤ 6n3 holds for every n ≥ n0?

    Answer

    5n3 + 2n + 8 ≤ 6n3 ⇔ n3 ≥ 2n + 8. At n = 2, 8 < 12 and the inequality fails; at n = 3, 27 ≥ 14 and it holds. As n increases, n3 grows faster than 2n + 8, so the inequality always holds from there on: n0 = 3. Check: at n = 3, 149 ≤ 162.

  2. How many times does the fragment for (i = 0; i < n; i++) for (j = i; j < n; j++) x++; execute x++ for n = 6? What is the growth class?

    Answer

    In round i the inner loop runs n − i times: 6 + 5 + 4 + 3 + 2 + 1 = 21. In general n(n + 1)/2, that is, Θ(n2). That the inner loop depends on the outer counter halves the total but does not change the class.

  3. For n = 64, how many rounds does the loop for (int i = 1; i * i <= n; i++) x++; run? What is the growth class?

    Answer

    The loop continues while i2 ≤ n, that is, i ≤ √n. For n = 64, i = 1, …, 8: 8 rounds. The class is Θ(√n); primality testing by trial division uses this pattern.

  4. Which of the statements 2n+1 = O(2n) and 22n = O(2n) is true?

    Answer

    The first is true: 2n+1 = 2 · 2n; c = 2, n0 = 1 suffice. The second is false: 22n = 4n and the ratio 4n/2n = 2n goes to infinity; no constant c can close this gap. A constant added to the exponent only brings a constant factor; a constant multiplying the exponent changes the base.

  5. What is the solution of the recurrence T(n) = 2T(n/4) + √n by the Master Theorem?

    Answer

    a = 2, b = 4, log4 2 = 1/2. f(n) = √n = n1/2, c = 1/2. Exponents equal: Case 2, T(n) = Θ(√n log n). Check: with T(1) = 1, T(256) = 80 = 16 · 4 + 16.

  6. What is the solution of the recurrence T(n) = 5T(n/2) + n2? Do the level sums grow or shrink?

    Answer

    log2 5 ≈ 2.32 > c = 2: Case 1, T(n) = Θ(nlog2 5) ≈ Θ(n2.32). The ratio is r = 5/22 = 1.25 > 1; the level sums grow by a factor of 1.25 at each level, and the leaves dominate.

  7. What is the closed form of the recurrence T(n) = T(n − 1) + 1, T(1) = 1, found by unrolling? Why does the Master Theorem not apply?

    Answer

    T(n) = T(n − 1) + 1 = T(n − 2) + 2 = … = T(n − k) + k. At k = n − 1, T(n) = T(1) + n − 1 = n: Θ(n). Because the subproblem is n − 1, not n/b, the recurrence does not fit the form of the Master Theorem. If the input of a recursion with a single call decreases by one at each step, the time is n times the work of each call.

  8. How many calls does f4(10) make and what does it return? (In Java n / 2 is integer division.)

    Answer

    f4(10) calls two f4(5), each f4(5) calls two f4(2), each f4(2) calls two f4(1). The calls number 1 + 2 + 4 + 8 = 15. Eight leaves return 1; the result is 8. The tree has the same shape as the tree for input 8.

  9. Seventeen elements are added to an empty dynamic array of capacity 1 that doubles when full. How many copies are made in all, what is the total cost, and what is the final capacity?

    Answer

    Capacity increases occur at insertions 2, 3, 5, 9, and 17; the copies are 1 + 2 + 4 + 8 + 16 = 31. With 17 writes the total is 48 units, which stays below 3 · 17 = 51. The final capacity is 32.

  10. What are the number of x++ executions and the growth class of the fragment for (i = 0; i < n; i++) for (j = 1; j < n; j *= 2) x++; for n = 10?

    Answer

    The inner loop is independent of the outer counter; it runs 4 rounds, at j = 1, 2, 4, 8. The outer loop runs 10 rounds; total 10 · 4 = 40. In general n · ⌈log2 n⌉, that is, Θ(n log n).
