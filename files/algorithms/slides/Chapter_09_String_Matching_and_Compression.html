Introduction

String Algorithms

  • Text is everywhere: email, chat messages, social media posts, news articles…
  • Our computers handle enormous amounts of text every day. How do we organize and analyze it?
  • String algorithms perform operations such as searching, replacing and comparing text.
  • Two core problems: string matching (finding a pattern in a text) and string compression (storing text in less space).
Where?

Ctrl+F in editors, grep, search engines, virus signature scanning, plagiarism detection, gene search in DNA, file formats such as ZIP/GIF/PNG.

Introduction

Basic Concepts and Notation

  • Alphabet Σ: the set of characters in use (e.g. {a, b, …, z}, {A, C, G, T}).
  • Text T[0..n−1] and pattern P[0..m−1], usually m ≤ n.
  • P occurs in T with shift s ⇔ T[s..s+m−1] = P. Valid shifts: 0 ≤ s ≤ n − m.
  • Prefix: P[0..k−1]; suffix: P[m−k..m−1]. A proper prefix/suffix is one not equal to the whole string.
  • Example: for "ababd" the prefixes are a, ab, aba, abab; the suffixes are d, bd, abd, babd.

The string matching problem: find all (or the first) shifts s at which P occurs.

Brute Force

The Brute-Force (Naive) Algorithm

  • The simplest way to search for a pattern in a text, hence the name "naive".
  • How it works:
    1. For each shift s = 0, 1, …, n − m, align the pattern under the text.
    2. Compare characters left to right; stop at the first mismatch.
    3. If all m characters match, report s; otherwise slide the pattern one position.
  • No preprocessing and no extra memory.
Complexity

Worst case: (n − m + 1) · m comparisons → O(n · m).

Best case: the first character mismatches at every shift → O(n).

n: text length, m: pattern length.

int bruteForce(String t, String p) {
  int n = t.length(), m = p.length();
  for (int i = 0; i <= n - m; i++) {
    int j = 0;
    while (j < m &&
      t.charAt(i + j) == p.charAt(j))
      j++;
    if (j == m) return i;
  }
  return -1;
}

The real flaw: what a mismatch teaches us (the characters that matched) is thrown away; the algorithm backs up in the text and rereads the same characters. KMP puts this information to use.

KMP

The Knuth-Morris-Pratt (KMP) Algorithm

  • Finds occurrences of a pattern in a text.
  • Developed by Donald Knuth and Vaughan Pratt and, independently, by James H. Morris; published jointly in 1977.
  • Key idea: on a mismatch, use what we already know about the part of the pattern that has matched; the text pointer never moves back.
  • That knowledge is precomputed from the pattern and stored in the LPS table (the prefix function π).
Complexity

Preprocessing: O(m)

Search: O(n)

Total: O(n + m), even in the worst case

Extra memory: O(m)

KMP

KMP: How It Works

1. PreprocessingFor each position of the pattern, record the length of the longest proper prefix that is also a suffix (LPS). On a mismatch, this table tells us where to resume in the pattern.
2. Pattern searchScan the text once, left to right. On a mismatch, the pattern pointer q falls back to the value read from the table (q = lps[q − 1]); the text pointer i stays put.
3. Match checkWhen q reaches m, every character of the pattern has matched: report position i − m + 1. To find all occurrences, continue with q = lps[m − 1].
Why is this correct? If P[0..q−1] has matched the text and P[q] mismatches, the next possible alignment is the one that overlaps the longest prefix of P[0..q−1] that is also its suffix. No shift in between can possibly match.

KMP

The LPS Table (Prefix Function)

lps[q] = length of the longest proper prefix of P[0..q] that is also a suffix of P[0..q].

  • lps[0] = 0 (a single character has no proper prefix).
  • Example: text "ababcababcabababd", pattern "ababd".
  • Pattern table: a: 0, b: 0, a: 1, b: 2, d: 0.

int[] computeLPS(String p) {
  int m = p.length(), k = 0;
  int[] lps = new int[m];
  for (int q = 1; q < m; q++) {
    while (k > 0 &&
      p.charAt(k) != p.charAt(q))
      k = lps[k - 1];
    if (p.charAt(k) == p.charAt(q))
      k++;
    lps[q] = k;
  }
  return lps;
}

KMP

The Three Phases of a KMP Search

Phase 1 · Find the first characterAdvance the text pointer (i) until it matches the first symbol of the pattern.
Phase 2 · Advance togetherWhile symbols match, both pointers advance. On reaching the end of the pattern, return (text position − pattern position).
Phase 3 · Fall back via LPSOn a mismatch only the pattern pointer (q) falls back via LPS; after a match or on reaching 0, return to Phase 2 (Phase 1 if q = 0).

int kmpSearch(String t, String p) {
  int n = t.length(), m = p.length();
  int[] lps = computeLPS(p);
  int q = 0;  // matched length
  for (int i = 0; i < n; i++) {
    while (q > 0 &&
      p.charAt(q) != t.charAt(i))
      q = lps[q - 1];
    if (p.charAt(q) == t.charAt(i))
      q++;
    if (q == m)
      return i - m + 1;
  }
  return -1;
}

KMP

KMP: Why O(n + m)?

  • The outer loop increments i n times; i never decreases.
  • q grows by at most 1 per step → total increase ≤ n.
  • Each fallback in the while loop decreases q by at least 1; q cannot go negative → total fallbacks ≤ total increase ≤ n.
  • Search: at most 2n comparisons → O(n). The same amortized argument gives O(m) for LPS.

Pros

  • Linear even in the worst case
  • Never backs up in the text: suits streaming data

Cons

  • Usually slower than Boyer-Moore in practice
  • Little to skip over with a small alphabet (DNA)

Boyer-Moore

The Boyer-Moore Algorithm

  • Searches for a pattern in a text; developed by Robert S. Boyer and J Strother Moore in 1977.
  • The pattern slides left to right, but characters are compared right to left.
  • On a mismatch, shift by the larger of two rules: bad character and good suffix.
  • Most text characters can be skipped without ever being read: very fast for long patterns over large alphabets (natural language); grep and editor search belong to this family.
Complexity

Best: O(n/m) — the first comparison fails at every attempt and we skip m.

Average: sublinear, faster than O(n) in practice.

Worst: O(n · m) with bad character alone; O(n + m) with good suffix + Galil's rule.

Boyer-Moore

Boyer-Moore: How It Works

  1. Preprocessing: build shift tables from the pattern: the last occurrence of each character in the pattern (bad character) and a shift amount for each suffix (good suffix).
  2. Search: align the pattern under the text; compare starting from the last character and moving left.
  3. Match check: if all characters match, report the position.
  4. Bad-character rule: shift according to the rightmost position in the pattern of the mismatched text character.
  5. Good-suffix rule: shift according to whether the matched suffix occurs elsewhere in the pattern.

Red numbers give the comparison order: only 6 comparisons on a 12-character text.

Shift = max(bad-character shift, good-suffix shift). Both are "safe": no skipped alignment can contain a match.

Boyer-Moore

The Bad-Character Rule

  • Let p[j] ≠ t[s + j]; c = t[s + j] is the bad character.
  • If c occurs in the pattern left of j: shift so that the rightmost c lines up under t[s + j].
  • If c does not occur in the pattern (last = −1): shift the pattern entirely past c (j + 1).
  • Formula: s += max(1, j − last[c]). If c last occurs right of j, then j − last[c] ≤ 0; hence the minimum of 1.
int[] lastOccurrence(String p) {
  int[] last = new int[256];
  Arrays.fill(last, -1);
  for (int i = 0; i < p.length(); i++)
    last[p.charAt(i)] = i;
  return last;
}

Boyer-Moore

The Good-Suffix Rule

  • The suffix u = P[j+1..m−1] matched the text before the mismatch: the "good suffix".
  • Case 1: if u occurs elsewhere in the pattern (preceded by a different character), shift so that this occurrence lines up under u in the text.
  • Case 2: otherwise, align the longest prefix of P that equals a suffix of u.
  • Case 3: if neither exists, shift the pattern by m.
  • The table is precomputed in O(m) time (similar to KMP's LPS idea, but for suffixes).

"AB" matched, t[2] = 'A' ≠ p[2] = 'B'. Bad character: last[A] = 3 > j → only 1. Good suffix: "AB" also occurs at p[1..2] (preceded by 'C' ≠ 'B') → shift 2.

int horspool(String t, String p) {
  int n = t.length(), m = p.length();
  int[] shift = new int[256];
  Arrays.fill(shift, m);
  for (int i = 0; i < m - 1; i++)
    shift[p.charAt(i)] = m - 1 - i;
  int s = 0;
  while (s <= n - m) {
    int j = m - 1;
    while (j >= 0 &&
      p.charAt(j) == t.charAt(s + j))
      j--;
    if (j < 0) return s;
    s += shift[t.charAt(s + m - 1)];
  }
  return -1;
}

int boyerMoore(String t, String p) {
  int n = t.length(), m = p.length();
  int[] last = lastOccurrence(p);
  int s = 0;
  while (s <= n - m) {
    int j = m - 1;
    while (j >= 0 &&
      p.charAt(j) == t.charAt(s + j))
      j--;
    if (j < 0) return s;
    s += Math.max(1,
      j - last[t.charAt(s + j)]);
  }
  return -1;
}

Boyer-Moore

Boyer-Moore: Analysis and Example

  • Best: text characters do not occur in the pattern → 1 comparison per alignment, skip m: ≈ n/m comparisons.
  • Worst (bad character only): T = aaaa…a, P = baaa…a → m comparisons per alignment, shift 1: O(n · m).
  • With a large alphabet and frequent mismatches, longer patterns give longer shifts (best ≈ n/m).
  • With a small alphabet (DNA, binary data) the bad-character rule is weak; the good-suffix rule matters more.

Rabin-Karp

The Rabin-Karp Algorithm

  • Finds occurrences of a pattern in a text; developed by Michael O. Rabin and Richard M. Karp in 1987.
  • Instead of comparing characters one by one, it compares the hash of the pattern with the hash of each length-m window of the text.
  • Rolling hash: when the window slides one step right, the new hash is computed from the old one in O(1).
  • Equal hashes do not guarantee a match: a spurious hit is possible → verify character by character.
Complexity

Best: hashes rarely collide → O(n + m)

Average: O(n + m) in practice

Worst: a collision (spurious hit) at every window, constant verification → O(n · m)

Rabin-Karp

Rabin-Karp: How It Works and the Rolling Hash

  1. Hash: compute the hash of the pattern and of the first text window.
  2. Match check: substrings whose hash matches are candidates.
  3. Verification: compare a candidate window with the pattern character by character.
  4. Slide and rehash: if there is no match, slide the window one step right and update the hash.
  5. Repeat: continue across the whole text.
Polynomial hash (base B, prime modulus Q):
h(t[s..s+m−1]) = (t[s]·Bm−1 + t[s+1]·Bm−2 + … + t[s+m−1]) mod Q
Slide: hs+1 = (B · (hs − t[s] · Bm−1) + t[s+m]) mod Q — subtract the outgoing character, shift the rest one digit left, add the incoming character.

Rabin-Karp

A Simple Example: Sum Hash and Spurious Hits

Toy hash: the sum of the letter values. Searching for "TS" in "VUATS".

Window "VU": 5 + 1 = 6 ≠ 5 → hashes differ, no character comparison.

Window "UA": 1 + 4 = 5 = 5 → equal hashes, but "UA" ≠ "TS": a spurious hit; the verification is wasted.

Window "AT": 4 + 2 = 6 ≠ 5 → skip. New hash = old − outgoing (U=1) + incoming (T=2): O(1).

Window "TS": 2 + 3 = 5 → equal hashes, and the characters agree too: match (s = 3).

The sum hash is weak (it ignores letter order: "ST" also gives 5). That is why a position-weighted polynomial hash with a large prime Q is used.

Rabin-Karp · Step through the code

rabinKarp("abracadabra", "cad")

n = 11, m = 3, B = 256, Q = 101. h = 256² mod 101 = 88 (weight of the outgoing character).

ph = (99·256² + 97·256 + 100) mod 101 = 11; for the first window "abr", th = 4.

Window "abr": th = 4 ≠ 11 → characters not checked. Slide: 'a' out, 'a' in → new th = 30.

Window "bra": th = 30 ≠ 11 → characters not checked. Slide: 'b' out, 'c' in → new th = 17.

Window "rac": th = 17 ≠ 11 → characters not checked. Slide: 'r' out, 'a' in → new th = 41.

Window "aca": th = 41 ≠ 11 → characters not checked. Slide: 'a' out, 'd' in → new th = 11.

th = 11 = ph → character check with matchAt: "cad" = "cad" → return s = 4.

int rabinKarp(String t, String p) {
  int n = t.length(), m = p.length();
  int B = 256, Q = 101, h = 1;
  for (int i = 0; i < m - 1; i++)
    h = (h * B) % Q;  // B^(m-1) mod Q
  int ph = 0, th = 0;
  for (int i = 0; i < m; i++) {
    ph = (B * ph + p.charAt(i)) % Q;
    th = (B * th + t.charAt(i)) % Q;
  }
  for (int s = 0; s <= n - m; s++) {
    if (ph == th && matchAt(t, p, s))
      return s;
    if (s < n - m) {
      th = (B * (th - t.charAt(s) * h)
            + t.charAt(s + m)) % Q;
      if (th < 0) th += Q;
    }
  }
  return -1;
}

Rabin-Karp

The Sliding Window and Analysis

n − m + 1 = 7 windows; each computed from the previous one in O(1).

  • Hashing cost: O(m) + (n − m) · O(1).
  • With a large prime Q, a spurious hit has probability ≈ 1/Q → expected time O(n + m).
  • Bad Q or adversarial input: every window is a candidate → O(n · m).
  • Strength: many patterns of the same length can be searched in one pass (put their hashes in a set): plagiarism detection, document similarity.
  • It also generalizes to 2D pattern search (a block within an image).

Compression

String Compression Algorithms

  • Goal: store or transmit text (or data) using fewer bits.
  • Lossless compression: decompression gives back the original data exactly. RLE and LZW are lossless (text, programs, PNG/GIF).
  • Lossy compression: perceptually unimportant detail is discarded (JPEG, MP3); not suitable for text.
  • Compression ratio = compressed size / original size (smaller is better).
RLEConsecutive repeats of the same value are stored as one value + a count.
LZWRepeated patterns become short codes in a dictionary that grows on the fly.

RLE

Run-Length Encoding (RLE)

  • Run-length encoding replaces each sequence of repeated characters (a run) with a count + character pair.
  • Steps: scan the text left to right → count consecutive repeats → combine count and character → store the result as the compressed text.
  • The text is scanned once, so the time is O(n).
  • Simple and effective, but useless or even harmful when there is little repetition: "ABCD" → "1A1B1C1D" (twice the size!).
  • Used in: fax (black-and-white lines), BMP/PCX/TIFF, simple icons.
Example

Text: AAAAABBBCCCCDDD (15 characters)

Compressed: 5A3B4C3D (8 characters)

Ratio: 8/15 ≈ 0.53

RLE · Step through the code

rleCompress("AAAAABBBCCCCDDD")

n = 15, result is empty.

New run: c = 'A', count = 1 (i = 0).

The while loop ran 4 times: count = 5, i = 4. Append "5A" to result.

New run: c = 'B', count = 1 (i = 5).

The while loop ran 2 times: count = 3, i = 7. Append "3B" to result.

New run: c = 'C', count = 1 (i = 8).

The while loop ran 3 times: count = 4, i = 11. Append "4C" to result.

New run: c = 'D', count = 1 (i = 12).

The while loop ran 2 times: count = 3, i = 14. Append "3D" to result.

Result: "5A3B4C3D" — 8 characters instead of 15.

String rleCompress(String s) {
  StringBuilder result = new StringBuilder();
  int n = s.length();
  for (int i = 0; i < n; i++) {
    char c = s.charAt(i);
    int count = 1;
    while (i + 1 < n &&
      s.charAt(i + 1) == c) {
      count++;
      i++;
    }
    result.append(count).append(c);
  }
  return result.toString();
}

RLE

RLE on a Binary (Black-and-White) Image

  • Each row is scanned left to right: W = white, B = black, followed by the run length.
  • 42 pixels → 18 runs (each row is encoded separately). With only two colors, the color need not be written at all: runs simply alternate white/black (the fax standard uses this idea).
  • Very effective for images with large flat areas (drawings, scanned text); useless for photographs.

LZW

Lempel-Ziv-Welch (LZW) Compression

  • Dictionary-based lossless compression: Terry Welch (1984) refined Lempel and Ziv's LZ78 method (1978).
  • Identifies repeated strings and represents them by short codes (indices) into a dictionary.
  • The dictionary is dynamic: it grows during compression and is never transmitted; the decompressor rebuilds the same dictionary on its own.
  • Used in formats such as GIF, TIFF, PDF and Unix compress.
  • As the dictionary grows, code width (bits) and memory grow and performance drops: in practice the dictionary is capped (GIF: 4096 codes = 12 bits) and reset when full.
Example

Text: ABABCABABCA

Initial dictionary: A = 0, B = 1, C = 2

Compressed: 0 1 3 2 3 5 0

7 codes instead of 11 symbols.

LZW · Step through the code

lzw("ABABCABABCA")

The dictionary starts with the characters of the text: A = 0, B = 1, C = 2. w = "".

"A" is in dict (0) → w = "A"; look for a longer match.

"AB" not in dict → output code of w = "A": 0; add "AB" = 3 to dict; w = "B".

"BA" not in dict → output code of w = "B": 1; add "BA" = 4 to dict; w = "A".

"AB" is in dict (3) → w = "AB"; look for a longer match.

"ABC" not in dict → output code of w = "AB": 3; add "ABC" = 5 to dict; w = "C".

"CA" not in dict → output code of w = "C": 2; add "CA" = 6 to dict; w = "A".

"AB" is in dict (3) → w = "AB"; look for a longer match.

"ABA" not in dict → output code of w = "AB": 3; add "ABA" = 7 to dict; w = "A".

"AB" is in dict (3) → w = "AB"; look for a longer match.

"ABC" is in dict (5) → w = "ABC"; look for a longer match.

"ABCA" not in dict → output code of w = "ABC": 5; add "ABCA" = 8 to dict; w = "A".

Loop done: output the code of the leftover w = "A", 0. Output: 0 1 3 2 3 5 0.

List<Integer> lzw(String s) {
  Map<String, Integer> dict =
      initDict(s);  // A=0, B=1, C=2
  String w = "";
  List<Integer> codes = new ArrayList<>();
  for (char c : s.toCharArray()) {
    String wc = w + c;
    if (dict.containsKey(wc)) {
      w = wc;
    } else {
      codes.add(dict.get(w));
      dict.put(wc, dict.size());
      w = "" + c;
    }
  }
  if (!w.isEmpty())
    codes.add(dict.get(w));
  return codes;
}

LZW

LZW Decompression

  • The decompressor knows only the initial dictionary; it builds the rest itself, in the same order as the compressor.
  • For each new code k: write e = dict[k]; add w + e[0] to the dictionary; set w = e.
  • The decompressor lags one step behind. If k is not yet defined (k = the next code), e must be w + w[0] (the cScSc case).
  • Output: A·B·AB·C·AB·ABC·A = ABABCABABCA ✓

LZW

LZW with an ASCII Dictionary and the Special Case

  • In practice the initial dictionary holds the 256 single-byte values (0–255; the first 128 are ASCII; a = 97, b = 98, c = 99); new strings are numbered from 256.
  • Text: aabaacababacb (13 characters) → 9 codes: 97 97 98 256 99 257 261 99 98.
  • "aba" = 261 is added while "ab" (257) is written and is used right in the next code.
  • When the decompressor reads 261, its dictionary only goes up to 260 → special case: e = w + w[0] = "ab" + "a" = "aba".

LZW · Step through the code

lzwDecode([97 97 98 256 99 257 261 99 98])

The decompressor knows only the 256 single-byte values. The first code, 97, is always a single character: w = "a", output "a". Nothing from 256 up exists yet.

k = 97 (ASCII) → write e = "a"; add w + e[0] = "a" + "a" = 256 = "aa" to dict.

k = 98 (ASCII) → write e = "b"; add w + e[0] = "a" + "b" = 257 = "ab" to dict.

k = 256 (in dict: 256 = "aa") → write e = "aa"; add w + e[0] = "b" + "a" = 258 = "ba" to dict.

k = 99 (ASCII) → write e = "c"; add w + e[0] = "aa" + "c" = 259 = "aac" to dict.

k = 257 (in dict: 257 = "ab") → write e = "ab"; add w + e[0] = "c" + "a" = 260 = "ca" to dict.

k = 261, but the largest code in the dictionary is 260: special case. e = w + w[0] = "ab" + "a" = "aba"; 261 = "aba" is added too. The compressor used this code the moment it added it.

k = 99 (ASCII) → write e = "c"; add w + e[0] = "aba" + "c" = 262 = "abac" to dict.

k = 98 (ASCII) → write e = "b"; add w + e[0] = "c" + "b" = 263 = "cb" to dict.

The 9 codes turned back into the 13-character text aabaacababacb; the decompressor's entries 256–263 match the compressor's.

String lzwDecode(List<Integer> codes) {
  List<String> dict =
      initDict();      // 0..255: byte values
  String w = dict.get(codes.get(0));
  StringBuilder s = new StringBuilder(w);
  for (int i = 1; i < codes.size(); i++) {
    int k = codes.get(i);
    String e = k < dict.size()
        ? dict.get(k)
        : w + w.charAt(0); // special case
    s.append(e);
    dict.add(w + e.charAt(0));
    w = e;
  }
  return s.toString();
}

LZW

LZ78: The Ancestor of LZW

  • LZ78 starts with an empty dictionary; its output is (index, character) pairs: the index of the longest dictionary match (0 if none) + the character that follows it.
  • Text: aabaacabcabcb → (0,a) (1,b) (1,a) (0,c) (2,c) (5,b).
  • Welch's change (LZW): start the dictionary with every single character → the output consists of codes only; no characters need to be written.
  • The LZ77 (sliding window) family underlies gzip/ZIP (DEFLATE) and PNG.

LZW · Step through the code

lz78("aabaacabcabcb")

The LZ78 dictionary starts empty (unlike LZW). w holds the longest piece found in the dictionary so far; for now it is empty.

w is empty and 'a' is not in dict → (0, a) (0 = empty prefix); add 1 = "a".

w + c = "a" is in dict → w = "a"; no output yet, try a longer piece with the next character.

"ab" not in dict → write w = "a" (index 1) and c = 'b': (1, b); add 2 = "ab", reset w.

w + c = "a" is in dict → w = "a"; no output yet, try a longer piece with the next character.

"aa" not in dict → write w = "a" (index 1) and c = 'a': (1, a); add 3 = "aa", reset w.

w is empty and 'c' is not in dict → (0, c) (0 = empty prefix); add 4 = "c".

w + c = "a" is in dict → w = "a"; no output yet, try a longer piece with the next character.

w + c = "ab" is in dict → w = "ab"; no output yet, try a longer piece with the next character.

"abc" not in dict → write w = "ab" (index 2) and c = 'c': (2, c); add 5 = "abc", reset w.

w + c = "a" is in dict → w = "a"; no output yet, try a longer piece with the next character.

w + c = "ab" is in dict → w = "ab"; no output yet, try a longer piece with the next character.

w + c = "abc" is in dict → w = "abc"; no output yet, try a longer piece with the next character.

"abcb" not in dict → write w = "abc" (index 5) and c = 'b': (5, b); add 6 = "abcb", reset w. End of text: 6 pairs.

List<String> lz78(String s) {
  Map<String, Integer> dict =
      new HashMap<>();
  List<String> out = new ArrayList<>();
  String w = "";
  for (char c : s.toCharArray()) {
    if (dict.containsKey(w + c)) {
      w = w + c;               // extend
    } else {
      int k = w.isEmpty() ? 0
                          : dict.get(w);
      out.add("(" + k + ", " + c + ")");
      dict.put(w + c, dict.size() + 1);
      w = "";
    }
  }
  if (!w.isEmpty())        // last piece
    out.add("(" + dict.get(w) + ")");
  return out;
}

Summary

Common Mistakes

Loop boundWriting i < n − m in brute force skips the last shift (s = n − m); it should be i <= n − m.
Misdefining LPSThe pattern itself does not count: lps("aaaa") = [0, 1, 2, 3], not [1, 2, 3, 4]. On a KMP mismatch use lps[q − 1], not lps[q].
Negative shiftIn Boyer-Moore, j − last[c] can be negative (c right of j). Forget the max(1, …) and the pattern moves back or loops forever.
Trusting equal hashesIn Rabin-Karp, equal hashes do not mean a match: always verify. In Java, % can return a negative value: if (th < 0) th += Q.
Multi-digit counts in RLEDecoding "12A" by reading the count as one digit is wrong (one '2'?). Bound the count or store it as a byte.
LZW's final w and special caseForgetting to output the code of the leftover w after the loop; not handling a not-yet-defined code (w + w[0]) when decompressing.
