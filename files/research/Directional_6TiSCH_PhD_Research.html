Directional and Steerable Antennas in TSCH / 6TiSCH Networks

These notes reconstruct, in a form that a newcomer can follow and reproduce, a doctoral study carried out between 2017 and 2022. The study extended a 6TiSCH protocol stack (4eMAC on Contiki) and the Cooja network simulator so that a sensor node can carry two or three sector antennas or a single electronically steerable antenna, and it exploited antenna direction both in distributed medium access and in a centralised scheduler. The notes first introduce Time-Slotted Channel Hopping, the 6TiSCH stack and the antenna models, then prepare the toolchain. Seven laboratory units rebuild the system layer by layer: the multi-radio driver and hardware platforms, the MSP430 emulator, the antenna and propagation model of the simulator, the antenna-aware MAC layer, the native simulation target, the direction-aware TASA scheduler and the end-to-end experiment. The final chapters explain how scenarios were designed and measured, summarise the results and list known defects. An appendix indexes all 199 source files that were changed.

1Preface and how to use these notes

These notes reconstruct, in a form that a newcomer can follow and reproduce, a body of work that extended a 6TiSCH protocol stack and the Cooja network simulator with support for nodes carrying several sector antennas or a single electronically steerable antenna, and that exploited antenna direction both in distributed MAC operation and in a centralised scheduler.

The material is organised as a course. Sections 2–4 introduce the concepts and prepare the toolchain. Sections 5–11 consist of seven laboratory units (L1–L7), each of which re-implements one layer of the system: the radio driver and hardware platform, the instruction-level emulator, the propagation model of the simulator, the medium access control (MAC) layer, the fast native simulation target, the centralised scheduler and, finally, the end-to-end experiment that connects them. Sections 12–15 explain how scenarios were designed, which metrics were collected and what results were obtained, and Section 16 offers self-check questions. Appendix A lists every one of the 199 source files that differ from the baseline, grouped by purpose.

1.1Prerequisites

  • Working knowledge of C (pointers, bit masks, preprocessor conditionals) and Java (classes, interfaces, the Observer pattern).
  • Basic Linux command-line usage, make and Apache ant.
  • Introductory wireless networking: path loss, received signal strength (RSSI), interference, duty cycling.
  • No prior exposure to Contiki, TSCH or Cooja is assumed; Section 2 supplies the necessary background.

2Background: TSCH, 6TiSCH and antennas

Objectives

  • Name the components of the 6TiSCH stack used in this work (minimal configuration, 6P, SF0, RPL) and the two schedulers used for comparison (6TiSCH minimal/SF0 and Orchestra).
  • Distinguish omnidirectional, sectored multi-radio and electronically steerable antennas, and state why each could improve a TSCH network.

2.1Time-Slotted Channel Hopping

IEEE 802.15.4e-2012 introduced Time-Slotted Channel Hopping (TSCH) as a MAC mode for low-power industrial networks. Time is divided into timeslots of fixed length (10 ms by default; 15 ms throughout this work), counted network-wide by the Absolute Slot Number (ASN). Timeslots are grouped into a repeating slotframe of L slots. A cell is a pair (slot offset, channel offset) inside the slotframe and is either dedicated to one transmitter–receiver pair or shared by contention. The physical channel used by a cell in a given slot is

channel = HoppingSequence[(ASN + channelOffset) mod |HoppingSequence|] (1.1)

so that successive uses of the same cell hop across frequencies and escape narrow-band interference. Nodes join the network by listening for Enhanced Beacons (EB), which carry the ASN and the timeslot template, and stay synchronised by timing corrections exchanged in acknowledgements and keep-alive frames.

2.2The 6TiSCH stack and 4eMAC

6TiSCH places IPv6 (6LoWPAN) and the RPL routing protocol on top of TSCH. Three IETF components matter here:

  • Minimal configuration (RFC 8180): a small number of shared cells sufficient for bootstrapping, EB and routing traffic.
  • 6top Protocol, 6P (RFC 8480): a two-way transaction with which neighbours add, delete, list or relocate dedicated cells between them.
  • Scheduling Function Zero, SF0 (IETF draft): a distributed policy that decides how many cells to request from 6P, based on measured traffic and a hysteresis threshold.

4eMAC is the Contiki implementation of this stack on which the study builds. Its main files are core/net/mac/4emac/4emac.c (MAC driver), 4erdc.c (slot operation, the equivalent of a radio duty-cycling layer), 4emac-buf.c (per-neighbour queues and cell tables), 4emac-timesynch.c (joining, EB, synchronisation) and the 6top-pce/ directory (6P and scheduling functions). A node's MAC keeps one destination_t record per neighbour; dedicated cells hang from that record as a list of slot_t.

Orchestra (Duquennoy et al., 2015) is an alternative, fully autonomous scheduler for Contiki's own TSCH implementation: every node derives its cells from a hash of node addresses, so no negotiation is required. Orchestra and 6TiSCH-minimal/SF0 serve as the comparison baselines of the 2018 experiments.

2.3Why antennas matter for TSCH

Low-power motes normally carry a single omnidirectional antenna, so every transmission illuminates all neighbours. In a dense TSCH network this has three consequences: the same cell cannot be reused by nearby links (low spatial reuse), shared cells suffer collisions, and receivers spend energy on frames that are not addressed to them. Directional radiation can reduce all three, at the cost of making neighbour discovery harder, because two nodes only hear each other when their beams point at each other. The study examined three antenna models.

2.4Research questions addressed

  1. Can sectored antennas reduce collisions and energy in 6TiSCH-minimal/SF0 and in Orchestra, and by how much (2018 conference study)?
  2. How should a node with a single steerable antenna discover neighbours, learn the best direction to each of them and still join the network in reasonable time (2019)?
  3. How do network formation time and control overhead scale with node count (25, 49, 81) and density (20, 30, 40 m spacing) for omnidirectional versus steerable nodes (2020)?
  4. Can a centralised scheduler exploit antenna direction to let interfering links share a channel and thereby shorten the schedule (2020–2022)?

3System architecture

The system spans four software components, each of which had to be modified consistently: the node firmware (Contiki and 4eMAC), the MSP430 emulator (MSPSim), the network simulator (Cooja) and an external scheduler process on the host.

Two simulation paths exist. In the emulated path (2017–2019) each node runs the real MSP430 binary inside MSPSim, so pin-level details of the second and third CC2420 must be emulated; this is precise but slow and limits experiments to about 35 nodes. In the native path (2020 onward) Contiki is compiled for the host CPU as a shared library and loaded by Cooja through JNI; radio state is exchanged through C variables, which permits 81-node networks and batch runs.

The information flow for directional operation is the same on both paths. The MAC chooses a radio or an orientation for every slot and passes it down through the radio API. The driver (or the native radio stub) records the choice in a register or variable. The simulator reads it, updates the node's Direction object, and the radio medium recomputes which receivers can hear the transmission using the antenna gains of both ends. On reception the driver tags the frame with the receiving radio index or orientation, which the MAC uses to learn the best direction per neighbour.

5.1Extend the radio driver interface

Contiki's struct radio_driver assumes one transceiver. The first step is to add a radio_index argument to every function that touches the hardware, and to define the bit masks that name the radios. The receive path of the RDC layer gets the same argument so that a frame can be answered through the radio that received it.

#define RADIO_ALL       7

/* ... in struct radio_driver ... */

  int (* transmit)(unsigned short transmit_len, unsigned short radio_index);
  int (* send)(const void *payload, unsigned short payload_len, unsigned short radio_index);
  int (* channel_clear)(unsigned short radio_index);

Every caller must then be adapted. In core/net/mac/rdc.h the input hook becomes input(unsigned short radio_index); nullradio.c, nullrdc.c, nullrdc-noframer.c, contikimac.c and the Linux radio driver cpu/native/net/linuxradio-drv.c receive mechanical signature changes. Where no antenna choice exists, use RADIO_PRIMARY for transmission and RADIO_ALL for on(). Two packet-buffer attributes carry antenna information between the layers:

// core/net/packetbuf.h — Δ +2 / −0
  PACKETBUF_ATTR_ANTENNA,              /* radio (mask bit) that received or must send the frame */

Finally, extend Energest with one listen and one transmit counter for each additional radio (ENERGEST_TYPE_LISTEN2, LISTEN3, TRANSMIT2, TRANSMIT3 in core/sys/energest.h) so that energy can be reported per antenna.

5.3Make the CC2420 driver address several chips

The driver change is the largest single edit of the study (dev/cc2420/cc2420.c, Δ +953 / −223). The pattern is uniform: every low-level SPI primitive takes the mask and repeats the bus transaction for each selected chip.

// dev/cc2420/cc2420.c — strobe(), the pattern used by getreg, setreg, write_fifo_buf, …
static void
strobe(enum cc2420_register regname, int index)
{
  if(index & RADIO_PRIMARY) {
    CC2420_SPI_ENABLE();
    SPI_WRITE(regname);
    CC2420_SPI_DISABLE();
  }
#ifdef EXP5438_HAS_2_ANTENNA
  if(index & RADIO_SECONDARY) {
    CC2420S_SPI_ENABLE();
    SPI_WRITE(regname);
    CC2420S_SPI_DISABLE();
  }
#endif
#ifdef EXP5438_HAS_3_ANTENNA
  if(index & RADIO_TERTIARY) {
    CC2420T_SPI_ENABLE();
    SPI_WRITE(regname);
    CC2420T_SPI_DISABLE();
  }
#endif
}

On top of these primitives:

  • on, prepare, transmit, send, cca, get_value and set_value forward the mask; channel, PAN identifier and address are configured with RADIO_ALL.
  • cc2420_interrupt(int index) records which radio raised FIFOP; cc2420_read reads the corresponding FIFO (alternating between radios when several are pending) and stores the index in PACKETBUF_ATTR_ANTENNA.
  • Energest uses LISTEN2/3 and TRANSMIT2/3 for the extra radios.

5.4A virtual orientation register for the steerable antenna

Real steerable antennas are controlled by switching lines or a phase network that the CC2420 does not have. The study therefore defines two unused CC2420 register addresses as virtual registers, which the emulator interprets (Lab 2): CC2420_ORIENTATION = 0x31 and CC2420_BEAMWIDTH = 0x32 in dev/cc2420/cc2420_const.h. At initialisation the driver writes orientation 0 and beam width 180°.

// dev/cc2420/cc2420.c — steerable antenna
#ifdef EXP5438_HAS_STEERABLE_ANTENNA
void
cc2420_set_orientation(int ori)          /* ori = 0..23 */
{
  if(ori >= 0 && ori < 24)
  {
    setreg(CC2420_ORIENTATION, ori * 15, RADIO_PRIMARY);   /* degrees */
    cc2420_last_orientation = ori;
  }
}
#endif
/* set_value(): case RADIO_PARAM_ORIENTATION: cc2420_set_orientation(value); */

When a frame is received the driver attaches cc2420_last_orientation as PACKETBUF_ATTR_ANTENNA_ORIENTATION, which lets the MAC learn which direction worked (Lab 4).

7.2The Direction interface

// interfaces/Direction.java — sector layout

{
  this.radioCount = radioCount;
  if(radioCount == 1) {                 /* omni or steerable */
    omni = true;
    beamwidthDegrees = 360.0;
    orientationDegrees = 0.0;
  }

    beamwidthDegrees = 180.0;

  }
}

A single-radio mote is omnidirectional unless its antenna type is set to directional (setAntennaType(1), or <omni>0</omni> in a native scenario), in which case it is steerable.

Gain pattern

Let θ be the bearing from the antenna to the other node, measured in degrees with atan2, and θ0 the antenna orientation. The gain in dBi returned by getGain(θ) is

Gsteer(θ) = 10 · (1 + cos(θ − θ0)) − 15 (L3.1)
Gsector(θ) = +5 if θ0 ≤ θ < θ0 + beam width, otherwise −15 (L3.2)
Gomni(θ) = 0 (L3.3)

The steerable pattern is a cardioid that yields +5 dBi on boresight, −5 dBi at ±90° and −15 dBi behind the antenna. Note that a sector spans from its orientation, not symmetrically around it: the 0° sector of a 2-radio node covers bearings 0°–180°.

Link budget

The received power combines log-distance path loss with exponent 2.5, both antenna gains and Gaussian fading with variance 0.5 dB²:

Prx(d) = −52 − 25 · log10 d + Gtx(θ) + Grx(θ + 180°) + 𝒩(0, 0.5)  [dBm] (L3.4)
// interfaces/Direction.java — link budget
public double getSignalStrength(double distance, double gain1, double gain2)
{
  Random rand = new Random();
  return -52 - 25 * Math.log10(distance) + gain1 + gain2
         + rand.nextGaussian() * Math.sqrt(0.5);
}

public double getMaxRange(double gain1, double gain2)
{
  return Math.pow(10.0, (42.5 + (gain1 + gain2)/2) / 25.0);
}

7.3Angle-dependent connectivity in UDGM

UDGM normally connects a receiver if it lies within a fixed transmission radius. The modified medium instead compares Prx with two thresholds: a frame is receivable above −95 dBm and causes interference above −102 dBm. Both gains are evaluated, the receiver's at the reverse bearing.

8.5Autonomous cells for control traffic

Even after joining, broadcast control frames sent in a shared slot reach only the neighbours that happen to face the sender. The solution adopted from 2020 onward gives every neighbour pair a pair of autonomous unicast cells in a second, long slotframe (251 slots), computed by both ends from their identifiers without negotiation, in the spirit of Orchestra and ALICE:

stx(a→b) = ((a + 1)·7 + (b + 1)·13) mod 251,   srx(a←b) = ((a + 1)·13 + (b + 1)·7) mod 251 (L4.1)

so that node a's transmit cell towards b equals b's receive cell from a. The cells are installed when the neighbour first enters the virtual neighbour table:

Objectives
  • Turn an offline TSCH scheduling library into a live scheduler that receives topology reports over UDP and returns schedules.
  • Modify the TASA channel-allocation (colouring) step so that conflicting transmitters that point in sufficiently different directions may share a channel.
  • Avoid the autonomous cells of Lab 4 and give precedence to freshly received packets.

10.1Starting point: TASA

The Traffic-Aware Scheduling Algorithm (TASA; Palattella et al.) builds a convergecast schedule on a routing tree. Each slot is filled in two phases. A matching phase selects a set of tree links that can transmit simultaneously without half-duplex conflicts, favouring nodes with the largest queue Q. A colouring phase assigns channel offsets so that links which interfere receive different channels; links that exceed the number of channels are deferred to the next slot. The original library (a public TSCH scheduling library, 2017) also contains MCC, MODESA and FHSS and reads link-quality files from the Tutornet testbed. All of these except TASA were removed; matrices were reduced to a single channel dimension.

10.3Building the network model

main.c listens on an IPv6 UDP socket. For each T report it calls parseMessage(srcid, msg), which records the parent in parentMatrix, creates links with a fixed ETX, stores each orientation in degreeMatrix[src][nbr], and marks the autonomous cells of (L4.1) of the reporting node, its parent and its children as occupied in schedule[][]. When every node (exactly MAX_NODES) is attached to the tree, the scheduler builds the connectivity matrix, an interference matrix (nodes within two hops), a conflict matrix and the degree matrix, runs TASA and sends ts … to every node whose schedule changed, 30 ms apart.

10.4Direction-aware colouring

The decisive change is a single condition in tasa/coloring.c. In the original algorithm a link must take a new colour (channel) whenever a conflicting link already uses the current one. In the modified algorithm the colour is advanced only if the two transmitters point within ±8 orientation steps (±120°) of each other; otherwise their main lobes are assumed to be separated enough for both to use the same channel in the same slot.

// tasa/coloring.c — Δ +20 / −5
if (confMatrix[nodeToColor->id][n->id])            /* the two links conflict */
{
  if (ListFind(&n->channels, (void *)color))       /* and n already uses this colour */
  {
    /* 24 * 15 = 360 degree */
    if(nodeToColor->antenna_direction - n->antenna_direction <= 8 &&
       nodeToColor->antenna_direction - n->antenna_direction >= -8)
    {
      color++;                                      /* beams overlap: next channel */
      break;
    }
  }
}

The transmitter's direction is taken from the report of the transmitting node: tx->antenna_direction = degreeMatrix[n1][n2] in tasa.c. With a single channel (NUM_CHANNELS 1), every link whose colour exceeds 0 is deferred, so the rule directly converts angular separation into shorter schedules.

Common pitfall

The difference is not wrapped around 360°: orientations 23 and 1 differ by 22 steps in the code, yet only by 2 steps (30°) in reality, so two nearly parallel beams are treated as separated. A correct test is d = abs(a − b) % 24; if (min(d, 24 − d) <= 8) color++;. Only the transmitter's direction is used; the receiver's is commented out.

10.5Autonomous-cell avoidance and pipelining

  • tasa/matching.c receives schedule[][] and admits a link in slot k only if schedule[k][tx] and schedule[k][rx] are free, so dedicated cells never collide with the autonomous cells of Lab 4.
  • After a link is scheduled, its receiver gets recently_added = 100; matching and colouring order nodes by Q + recently_added, so a packet that has just arrived is forwarded in the next slots (pipelining towards the sink).
  • graphs.h: MAX_NODES (= NODE_COUNT), NUM_CHANNELS 1, AUTONOMOUS_SLOTFRAME_LENGTH 251; Node_t gains antenna_direction, received_message, recently_added; Link_t gains degree.
  • util/files.c accepts a new line type d<i>=… carrying link directions when topologies are read from files; util/print.c prints the degree matrix in degrees (×15).

16Self-check questions

Try to answer each question before opening the solution. All answers follow from the chapters above.

  1. Why must the radio API carry a radio_index mask rather than a single radio number?

    Answer

    Some operations must address several radios at once (switching all receivers on, broadcasting an EB on every sector, configuring the channel), while unicast must use exactly one. A bit mask expresses both cases with one argument (RADIO_ALL = 7 versus RADIO_SECONDARY = 2).

  2. How does the firmware tell the simulator where a steerable antenna points, given that the CC2420 has no such feature?

    Answer

    Through a virtual register: the driver writes 15·k to address 0x31; MSPSim stores it and notifies an OrientationListener, which rotates the Direction object in Cooja. On native motes the same value travels through the C variable simRadioOrientation.

  3. Using (L3.5), what is the communication range between a steerable antenna pointing at an omnidirectional receiver, and what does the scenario file use?

    Answer

    With Gtx + Grx = 5 dB and T = −95 dBm, d = 1048/25 ≈ 83 m. The 2020 steerable scenarios set a 79 m transmission range.

  4. Why can a steerable node fail to join a network even though a neighbour sends Enhanced Beacons regularly?

    Answer

    EBs are sent in shared cells while the joining node points in some random direction; both beams must face each other in the same slot. Fake beacons reverse the roles: the unsynchronised node transmits, and any synchronised neighbour that hears it records the node and its direction.

  5. Show that the autonomous cells of (L4.1) are consistent at both ends of a link.

    Answer

    Node a transmits to b in ((a+1)·7 + (b+1)·13) mod 251. Node b receives from a in ((b+1)·13 + (a+1)·7) mod 251, which is the same number because addition is commutative.

  6. In the direction-aware colouring rule, when may two conflicting links share a channel, and what is wrong with the implemented test?

    Answer

    When the transmitters' orientation indices differ by more than 8 steps (120°). The code compares the plain difference, so indices 23 and 1 appear 22 steps apart although they are only 2 steps (30°) apart; the circular difference min(d, 24 − d) must be used.

  7. Why did the study move from MSPSim to native Cooja motes in 2020?

    Answer

    Instruction-level emulation of MSP430 nodes with several CC2420 chips was too slow for networks beyond roughly 35 nodes. Native motes run Contiki on the host CPU and allowed 49- and 81-node scenarios and batch runs.

  8. Why does the scheduler never run if MAX_NODES is larger than the number of simulated nodes?

    Answer

    TASA is started only after every node, counted up to MAX_NODES, has reported and attached to the tree. Missing nodes keep the condition false indefinitely.

BGlossary

Table B.1: Terms used in these notes.
ASNAbsolute Slot Number; the network-wide count of timeslots since the start of the network.
Autonomous cellA cell that both neighbours compute from their identifiers without negotiation (here: equation (L4.1) in a 251-slot slotframe).
Beam widthAngular extent of a sector (180° or 120°) or nominal width of a steerable lobe.
CellA (slot offset, channel offset) pair in a slotframe.
ColouringThe TASA step that assigns channel offsets so that conflicting links use different channels.
CoojaThe Java network simulator of Contiki; simulates radio media and hosts emulated or native motes.
EBEnhanced Beacon; the IEEE 802.15.4e frame that advertises a TSCH network.
EnergestContiki's energy accounting module, which accumulates time spent in CPU, LPM, listen and transmit states.
FBFake beacon; a short frame sent by unsynchronised steerable nodes so that synchronised neighbours can discover them.
4eMACThe 6TiSCH/TSCH MAC implementation for Contiki on which this work is based.
MSPSimInstruction-level emulator for the TI MSP430, used by Cooja for “emulated” motes.
Native moteA Cooja mote whose Contiki code is compiled for the host and loaded through JNI.
Orientation indexInteger 0–23 encoding a steerable antenna direction in 15° steps.
OrchestraAutonomous TSCH scheduler for Contiki in which cells are derived from node addresses.
PRRPacket reception ratio; delivered over sent application packets.
RDCRadio duty-cycling layer of Contiki; in 4eMAC, the slot operation in 4erdc.c.
RPLIPv6 Routing Protocol for Low-Power and Lossy Networks; builds the routing tree (DODAG) using DIO, DIS and DAO messages.
Sector antennaFixed directional antenna covering an angular sector; here realised as one CC2420 per sector.
SF0Scheduling Function Zero; the default distributed 6TiSCH scheduling function.
6P6top Protocol; transactions for adding, deleting, listing and relocating cells between neighbours.
SlotframeA repeating sequence of timeslots; this work uses a 31-slot primary and a 251-slot secondary slotframe.
Steerable antennaA single antenna whose main lobe can be rotated electronically.
TASATraffic-Aware Scheduling Algorithm; centralised convergecast scheduler based on matching and colouring.
TSCHTime-Slotted Channel Hopping, the MAC mode of IEEE 802.15.4e.
tunslip6Contiki tool that bridges a SLIP serial link to a Linux tun interface.
UDGMUnit Disk Graph Medium; Cooja radio medium, modified here to use antenna gains.
