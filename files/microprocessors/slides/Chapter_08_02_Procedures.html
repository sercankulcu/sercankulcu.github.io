Introduction

What Is a Procedure?

  • A procedure is a piece of code that performs one specific task (a function or subroutine in high-level languages).
  • The program calls it with CALL.
  • When the task is done, RET returns right after the point of the call.
  • The code is written once and called from many places.
  • Procedures make a program more structured and easier to follow.
ReuseLess duplicated code and less memory.
ReadabilityThe program is split into small, named tasks.
MaintenanceA bug is fixed in one place; each part is tested on its own.

Definition

Defining a Procedure

name PROC      ; start (NEAR by default)
    ; procedure body goes here
    RET
name ENDP      ; end
  • name: the procedure's name; it must be the same at both ends.
  • The name follows the rules for labels (it cannot start with a digit).
  • A procedure must contain at least one RET.

Where does a procedure go?

ORG 100h
    CALL p1
    RET          ; main program ends
p1 PROC          ; after the RET:
    ; ...          ; never fallen into
    RET
p1 ENDP
END

Placed after the main program's RET, procedures cannot be executed by accidentally "falling into" them. If one comes first, jump over it with JMP.

Definition

Directives and Instructions

ItemKindRole
PROC / ENDPAssembler directiveTells the assembler where the procedure starts and its type (NEAR/FAR). Not translated into machine code; takes no memory.
CALLCPU instructionPushes the return address and jumps to the procedure.
RETCPU instructionPops the return address and jumps there. Used to return both from a procedure and from a .COM program.
ENDAssembler directiveMarks the end of the source file.
CALL and RET are not assembler directives but instructions the CPU executes (CALL near: E8, RET: C3). Only PROC, ENDP and END are directives.
Why does RET return to the OS? When DOS starts a .COM program it pushes 0000h. The program's last RET loads it into IP; at CS:0000h (start of the PSP) sits an INT 20h, which ends the program.

Definition

Modular Programming

; main.asm
EXTRN show:NEAR   ; in another file
  ...
  CALL show

; tools.asm
PUBLIC show       ; exported
show PROC NEAR
  ...
  RET
show ENDP
  • Large programs are split into procedures, and procedures into separate source files (modules).
  • PUBLIC makes a procedure name visible to other modules; EXTRN declares that a name is defined in another module, along with its type (NEAR/FAR).
  • Each module is assembled separately into an object file (.OBJ); the linker joins them and fills in the addresses in CALL instructions.
  • Frequently used object files are collected in a library (.LIB); the linker pulls in only the procedures the program needs.
  • In emu8086, shared code is usually added with INCLUDE: the file's text is inserted into the source and assembled as one piece (emu8086.inc).

CALL and RET

CALL and RET Step by Step

Start: IP = 0100h, SP = FFFEh. Next instruction: CALL m1 (3 bytes: E8 04 00).

CALL first pushes the return address (the next instruction, 0103h): SP = FFFCh, [FFFCh] = 0103h.

Then IP ← 0103h + 0004h = 0107h: the first instruction of the procedure.

MOV BX, 5 executed, IP = 010Ah. The stack is unchanged.

RET: IP ← [SP] = 0103h, SP = FFFEh. Execution continues right after the CALL.

MOV AX, 2 → IP = 0106h. The RET here pops 0000h and ends the program.

With name PROC NEAR (the default) or name PROC FAR, the assembler encodes each RET inside the procedure accordingly (C3 / CB). In single-segment .COM examples, procedures are NEAR.

CALL and RET

Far Procedure: Stack Layout

  • A FAR procedure lives in another code segment; reaching it requires changing both CS and IP.
  • CALL FAR pushes CS first, then IP: 4 bytes on the stack. RETF pops IP first, then CS.
  • A near CALL pushes only IP (2 bytes), and RET pops only IP.
  • The procedure type and the return instruction must match: with PROC FAR, the assembler encodes the RET inside as RETF (CB).
  • A .COM program runs in a single segment, so near calls are enough; .EXE programs with several code segments need far calls.
The stack order matches the order RETF pops them: IP, pushed last, is on top and is popped first.

Menu with a Jump Table

MOV  AH, 1
INT  21h          ; AL = '1'..'3'
SUB  AL, '1'      ; 0..2

  • The key becomes a table index: '1' → 0, '2' → 1, '3' → 2. Addresses are 2 bytes, so the index is doubled (SHL BX, 1).
  • JA is unsigned: key '0' gives 0 − 1 = FFh, which is above 2 and rejected too. One check covers both ends.
  • Without the check, a bad key would call whatever bytes lie past the table.

Code Trace: A Simple Procedure

The program starts at 0100h. ORG, PROC, ENDP, END produce no bytes.

CALL m1: 0103h is pushed, IP = 0107h.

BX = 0005h.

RET: 0103h is popped → IP = 0103h, SP = FFFEh.

AX = 0002h.

RET: 0000h is popped → IP = 0000h, SP = FFFEh + 2 = 0000h. The INT 20h in the PSP ends the program. Result: AX = 2, BX = 5.

ORG    100h
CALL   m1         ; 0100h: E8 04 00
MOV    AX, 2      ; 0103h: B8 02 00
RET               ; 0106h: C3 → DOS
m1 PROC
MOV    BX, 5      ; 0107h: BB 05 00
RET               ; 010Ah: C3 → caller
m1 ENDP
END

CALL and RET

Machine Code in Memory

  • The example program takes only 11 bytes of memory: E8 04 00 B8 02 00 C3 BB 05 00 C3.
  • CALL m1 stores the target not as an absolute address but as a displacement from the next instruction (rel16). That is why the code still works when moved elsewhere in memory.
  • 16-bit values are stored little-endian: low byte first (04), then high byte (00).
  • The procedure name (m1) exists only for the assembler; the machine code keeps just the address 0107h.

Call overhead

  • Overhead, beyond its actual work, of a procedure that saves two registers: 19 + 8 + 2 × (11 + 8) = 65 clocks.
  • On a 5 MHz 8086 a clock is 200 ns: 65 × 200 ns = 13 µs.
  • Called 1000 times, the overhead is 13 ms.
  • A macro has no such overhead, but copies its body at every use.
Short, very frequent jobs (printing one character) suit a macro; long or rarely called jobs suit a procedure. The table is for register and direct forms; memory-operand forms add the effective-address time.

Parameters

Ways to Pass Parameters

1. In registersThe easiest and fastest way. E.g. AL and BL as two parameters, the result in AX. Registers are limited.
2. In memory variablesThe procedure reads/writes shared variables such as number1, result. Easy, but it ties the procedure to those variables.
3. By address (pointer)The address of an array is sent in SI/DI/BX; long data is processed without copying (print_me).
4. On the stackParameters are pushed with PUSH, read through BP and removed with RET n. The method of high-level languages.
Whichever way you choose, document the inputs, outputs and clobbered registers in a comment at the top of the procedure.

Parameters

By Value or by Reference?

Pass by value

The procedure gets a copy of the data (AX = 5). Even if it changes the copy, the variable in memory stays the same. Fast and safe for small data such as a single number.

Pass by reference

The procedure gets the data's address (SI = OFFSET a). Through [SI] it reads and can change the variable itself. For arrays, strings and variables the procedure must update.

MOV  AX, a        ; value: AX holds a copy of a
CALL twice       ; AX doubles, a stays the same
LEA  SI, a        ; address: SI = OFFSET a
CALL twice_m     ; [SI] doubles, a changes
LEA SI, a and MOV SI, OFFSET a give the same result: the address of a. MOV SI, a instead loads the value stored in a, not its address; a common mix-up when passing by reference.

Code Trace: Swap by Reference

SI and DI carry the addresses of a and b (0113h, 0115h): the procedure gets locations, not values.

CALL swap: return address 0109h pushed, SP = FFFCh.

swap will use AX, so it saves it first (SP = FFFAh).

MOV AX, [SI]: reads the value of a (1234h).

XCHG AX, [DI]: AX and b trade places in one instruction: b = 1234h, AX = 00FFh.

MOV [SI], AX: a = 00FFh. The swap is done in memory.

POP AX and RET: AX gets its old value (0000h) back, SP = FFFEh; a and b stay swapped.

ORG  100h
LEA  SI, a
LEA  DI, b
CALL swap
RET
swap PROC         ; In: SI, DI (addrs)
PUSH AX
MOV  AX, [SI]
XCHG AX, [DI]
MOV  [SI], AX
POP  AX
RET
swap ENDP
a    DW 1234h
b    DW 00FFh

Parameters in Registers

  • In the example, the AL and BL registers hold the two parameters.
  • The m2 procedure multiplies AL by BL and leaves the result in AX.
  • CALL m2 calls the procedure; RET returns to the caller.
  • m2 is called twice: in the second call AL carries the result of the first, because MUL changes AX (and so AL).
MUL sourceOperationResult
8-bitAL × sourceAX
16-bitAX × sourceDX:AX

MUL multiplies unsigned; if the upper half of the result (AH or DX) is not 0, CF = OF = 1. The source cannot be an immediate: MUL 2 is invalid.

Parameters · Step through the code

Code Trace: Parameters in Registers

AL = 1 (MOV AL, 1 = B0 01, 2 bytes).

BL = 2.

1st call: return address 0107h pushed, IP = 010Bh.

MUL BL: AX = 1 × 2 = 0002h. AH = 0 → CF = OF = 0.

RET → IP = 0107h: the second CALL.

2nd call: this time the return address 010Ah is pushed. Same procedure, different return point.

MUL BL: AL is now 2 → AX = 2 × 2 = 0004h.

RET → IP = 010Ah.

RET: back to DOS. Result AX = 0004h.

ORG    100h
MOV    AL, 1       ; 1st parameter
MOV    BL, 2       ; 2nd parameter
CALL   m2          ; 0104h: E8 04 00
CALL   m2          ; 0107h: E8 01 00
RET                ; 010Ah: to DOS
m2 PROC            ; 010Bh
MUL    BL          ; AX = AL * BL
RET                ; to caller
m2 ENDP
END

Code Trace: Returning the Result in CF

The digit procedure converts the character in AL to a number and reports success in CF (as DOS services do). AL = '7' = 37h.

CALL digit; SUB AL, '0': 37h − 30h = 7.

CMP AL, 10: 7 − 10 needs a borrow → CF = 1 (value in 0…9).

CMC: CF = 0 → “a digit”.

RET; the caller can test CF (JC/JNC). BL = 7 saved.

AL = 'x' = 78h; second call: 78h − 30h = 48h (72).

CMP AL, 10: 72 ≥ 10, no borrow → CF = 0.

CMC: CF = 1 → “not a digit”. AL is now garbage (48h) and must not be used.

RET: the result is in the flag. The caller can branch with JC error.

MOV  AL, '7'
CALL digit       ; CF = 0 → AL = value
MOV  BL, AL
MOV  AL, 'x'
CALL digit       ; CF = 1 → not a digit
RET
digit PROC       ; In: AL, Out: CF
SUB  AL, '0'
CMP  AL, 10      ; 0..9 → borrow, CF = 1
CMC              ; digit: CF = 0
RET
digit ENDP

divmod PROC     ; In: AX, BL (divisor)

divmod ENDP
  • Register pair: a 32-bit result in DX:AX (like 16-bit MUL), quotient and remainder in AL and AH.
  • Flag + register: CF reports success, the register holds the value; the caller tests JC first.
  • Memory: results are written to an area whose address is given; any number of them.

Preserving Registers

Problem

If a procedure quietly changes a register the caller relies on (e.g. the loop counter CX), the caller breaks.

Documentation

; m2: computes AL * BL
; In     : AL, BL (unsigned)
; Out    : AX = AL * BL
; Clobber: CF, OF

Solution: PUSH / POP

show PROC
    PUSH AX       ; save what
    PUSH SI       ; you use
    ; ... AX and SI are used
    POP  SI       ; in REVERSE
    POP  AX       ; order
    RET
show ENDP

The register that returns the result (e.g. AX) is not preserved; otherwise the result would be lost.

Parameters · Step through the code

Code Trace: Saving the Counter with PUSH CX

The main loop prints 2 rows: counter CX = 2. The stars procedure also uses CX in its inner loop.

CALL stars: return address 0106h pushed, SP = FFFCh.

PUSH CX: the caller's counter (2) is saved on the stack.

Inner counter CX = 3; AX = 0E23h (AH = 0Eh teletype, AL = '#').

The inner loop runs INT 10h three times: ###. After LOOP, CX = 0.

POP CX: the caller's counter is back, CX = 2.

RET: returns to 0106h, SP = FFFEh.

Main LOOP row: CX = 1 → call again for the second row.

The second call works the same way: ### is printed, CX = 1 restored.

LOOP: CX = 0 → the loop ends. 6 characters on screen. Without PUSH/POP, CX would be 0 on return, and LOOP would make it FFFFh and loop almost forever.

MOV  CX, 2       ; main loop: 2 rows
row: CALL stars
LOOP row
RET
stars PROC
PUSH CX          ; caller's counter
MOV  CX, 3       ; inner counter
MOV  AX, 0E23h   ; AH = 0Eh, AL = '#'
inner:  INT 10h
LOOP inner
POP  CX          ; counter back
RET
stars ENDP

CriterionCallee saves (PUSH/POP in the procedure)Caller saves (around the CALL)
Where is the code?once, in the procedureat every call site
Needless savingsaved even if the caller doesn't use itonly the registers really needed
Risk of forgettinglow: written in one placehigh: needed again at every call
Best forlibrary procedureswhen the old value of an output register is needed
again: PUSH CX         ; caller: counter
       CALL read_num   ; result in CX
       ADD  total, CX
       POP  CX         ; counter back
       LOOP again
The rule in practice: a procedure preserves the registers it uses but not its output registers. If the old value of an output register is needed, the caller saves it.

Code Trace: Single Exit Point

The find procedure searches the array at SI, CX elements long, for AL (7); it returns the result in CF and BX.

CALL find: return address 010Bh pushed.

The procedure will change CX and SI, so it saves both; SP = FFF8h. BX = 0 (index).

arr[0] = 3 ≠ 7: SI and BX advance, LOOP brings CX down to 4.

arr[1] = 9 ≠ 7: BX = 2, CX = 3.

arr[2] = 7: ZF = 1, JE found jumps. The loop ends early, but two saved values are still on the stack.

STC: CF = 1 → “found”. If not found, CLC and JMP done would arrive at the same place.

Both paths meet at the done label: the POPs always run, and SI and CX get their old values back.

RET returns to the right address (010Bh): CF = 1, BX = 2. Had JE been replaced by a direct RET, the SI value on top (011Fh) would have been taken as the return address.

ORG  100h
LEA  SI, arr
MOV  CX, 5
MOV  AL, 7
CALL find        ; CF = 1: found
RET
find PROC        ; In: SI, CX, AL
PUSH CX
PUSH SI
XOR  BX, BX      ; Out: BX = index
scan: CMP [SI], AL
JE   found
INC  SI
INC  BX
LOOP scan
CLC              ; not found
JMP  done
found: STC
done: POP SI     ; single exit point
POP  CX
RET
find ENDP
arr DB 3, 9, 7, 1, 4

Passing Parameters on the Stack (with BP)

The caller puts the parameters on the stack; the procedure reads them through BP.

AX = 7.

1st parameter on the stack: [FFFCh] = 0007h.

AX = 3.

2nd parameter: [FFFAh] = 0003h.

CALL: return address 010Bh → [FFF8h]. IP = 010Fh.

The old BP is saved: [FFF6h] = 0000h.

MOV BP, SP: BP = FFF6h becomes a fixed frame pointer.

[BP+6] = [FFFCh] = 0007h → AX = 7.

[BP+4] = [FFFAh] = 0003h → AX = 000Ah.

BP gets its old value back; SP = FFF8h (return address on top).

RET: IP = 010Bh, SP = FFFAh.

ADD SP, 4: both parameters are discarded, SP = FFFEh. The stack is balanced.

The program ends.

ORG  100h
MOV  AX, 7
PUSH AX          ; 1st parameter
MOV  AX, 3
PUSH AX          ; 2nd parameter
CALL SUM2
ADD  SP, 4       ; drop parameters
RET
SUM2 PROC
PUSH BP
MOV  BP, SP
MOV  AX, [BP+6]  ; 1st parameter
ADD  AX, [BP+4]  ; 2nd parameter
POP  BP
RET
SUM2 ENDP

[BP+0] = old BP, [BP+2] = return address, [BP+4] = the last parameter pushed. Instead of ADD SP, 4, the procedure could also end with RET 4.

Parameters

Stack Frame and Local Variables

PUSH BP
MOV  BP, SP
SUB  SP, 4        ; local space
MOV  [BP-2], AX   ; local 1
...
MOV  SP, BP       ; drop locals
POP  BP
RET  4            ; drop 2 params
  • SUB SP, 4 opens two words of local space on the stack: [BP−2], [BP−4].
  • MOV SP, BP releases the local space in one instruction.
  • Parameters sit at positive BP offsets, locals at negative ones.

Code Trace: A Local Variable on the Stack

Parameter x = 9 is in AX. The procedure will keep x in a local variable and compute x·x + x.

CALL: return address 0106h → [FFFCh].

PUSH BP: the caller's BP (0000h) is saved.

MOV BP, SP: BP = FFFAh, the fixed point of the frame.

SUB SP, 2: one word of local space; [BP−2] = FFF8h.

MOV [BP−2], AX: local = 9. [BP...] addresses use the SS segment by default.

MUL AX: AX = 81 (DX = 0). AX changed, but x is still in the local.

ADD AX, [BP−2]: 81 + 9 = 90 = 005Ah.

MOV SP, BP: the local space is released in one instruction, SP = FFFAh.

POP BP, RET: BP = 0, SP = FFFEh, back in the caller. Result AX = 90.

MOV  AX, 9
CALL sq_plus     ; AX = x·x + x
RET
sq_plus PROC
PUSH BP
MOV  BP, SP
SUB  SP, 2       ; local [BP-2]
MOV  [BP-2], AX  ; local = x
MUL  AX          ; AX = x·x
ADD  AX, [BP-2]  ; + x
MOV  SP, BP      ; drop local
POP  BP
RET
sq_plus ENDP

Code Trace: print_me

SI points to the first character of the string ('H').

CALL print_me: the return address (the RET on line 4) is pushed.

[SI] = 'H' (48h) ≠ 0 → ZF = 0, JE does not jump.

AL = 48h, AH = 0Eh, INT 10h → H.

CALL calc         ; result = a × b + c

calc PROC         ; In: BX = block address
PUSH AX
PUSH DX           ; MUL writes DX too
MOV  AX, [BX]     ; a
MUL  WORD PTR [BX+2] ; × b
ADD  AX, [BX+4]   ; + c
MOV  [BX+6], AX   ; result
POP  DX
POP  AX
RET
calc ENDP
block DW 12, 7, 5, ?
  • A single register (BX) carries any number of parameters: the block is read at fixed offsets ([BX+2], [BX+4]).
  • The result goes into the block too: 12 × 7 + 5 = 89 (0059h).
  • The same procedure is called with another block just by changing BX.
  • Document the block layout (what sits at which offset) in the procedure's header comment.

Testing a Procedure

Try a procedure not only with “normal” input but also with edge cases. Results for the find procedure (array: 3, 9, 7, 1, 4):

CaseALCXCFBXVerdict
first element3510correct
last element4514correct
not in the array8505correct; BX is meaningless, look only at CF
one-element search9101correct: 9 is the 2nd element, outside the range searched
empty array7012wrong: with CX = 0, LOOP runs 65,536 times
Cause of the bug

LOOP decrements CX first and then tests for zero: 0 − 1 = FFFFh. The search runs 65,536 iterations and “finds” the 7 in memory (BX = 2); with a truly empty array it would read past the end.

Fix

Handle the empty array with JCXZ before the loop: if CX = 0, do CLC and go straight to the done label. Also check in every test that CX and SI are preserved.

Nested Calls

main is about to call A. SP = FFFEh.

CALL A: 0103h pushed, SP = FFFCh.

CALL B from inside A: 0115h pushed, SP = FFFAh. Two return addresses are on the stack.

B's RET pops 0115h from the top: back to A (LIFO).

A's RET pops 0103h: back to main. Last called, first to return.

How Much Stack?

  • A program's stack requirement is the total of the bytes accumulated along the deepest path in its call tree.
  • Each near CALL adds a 2-byte return address, each PUSH 2 bytes.
PathCalculationBytes
main → A → B2 + 4 + 2 + 210
main → C2 + 68
  • In a program that starts with SP = FFFEh, SP goes no lower than FFF4h.
  • A and C are never on the stack at the same time: by the time C is called, A's bytes have already been popped.
Interrupts use the stack too (6 bytes for flags, CS and IP): an interrupt may arrive at the stack's deepest moment, so leave a margin above the computed value.

Recursion

Recursion

  • Recursion: a procedure calling itself (directly or through another procedure).
  • Each call pushes a new return address and its own saved values: the values of each level stay separate.
  • A base case (stopping condition) is essential; without it every call eats 2 more bytes and the stack overflows.
  • The problem shrinks at each step into a smaller copy of itself: printing 472 = printing 47 + printing '2'.
  • Printing numbers, factorial, walking a tree or a directory are typical examples of recursion.

Recursion · Step through the code

Code Trace: Printing a Number Recursively

AX = 472 (01D8h); CALL show: return address 0106h pushed.

472 / 10: AX = 47 (2Fh), DX = 2. The last digit (2) is pushed.

AX ≠ 0: show calls itself; return address 0116h (the done label) pushed.

Second level: 47 / 10 → AX = 4, digit 7 pushed; CALL again.

Third level: 4 / 10 → AX = 0, digit 4 pushed. AX = 0: the base case, JZ done. SP at its deepest: FFF2h.

POP AX = 4 → '4' is printed. The digit pushed last comes out first.

RET goes to 0116h, the done line of the second level: POP AX = 7 → '7'.

First level: POP AX = 2 → '2'. The screen shows 472.

The last RET returns to 0106h; SP = FFFEh. Each level kept its digit on the stack, so no extra variable was needed.

ORG  100h
MOV  AX, 472
CALL show
RET
show PROC        ; In: AX (unsigned)
XOR  DX, DX
MOV  BX, 10
DIV  BX          ; AX = quot., DX = digit
PUSH DX
OR   AX, AX      ; more digits?
JZ   done
CALL show        ; upper digits first
done: POP AX
ADD  AL, '0'
MOV  AH, 0Eh
INT  10h
RET
show ENDP

Depth

For show, the number of levels = the number of digits. 65,535 → 5 levels: 5 × 2 (return) + 5 × 2 (digit) = 20 bytes; SP goes no lower than FFEAh.

Where the base case goes

The test must come before the CALL. For AX = 0 one digit (0) is still printed: the number 0 comes out as '0' with no extra code.

Code Trace: Unbalanced PUSH / POP

AX = 1234h.

CALL: return address 0106h pushed.

PUSH AX: 1234h is pushed on top of the return address.

RET pops whatever is on top: IP = 1234h! The CPU jumps to a random address; the program crashes or behaves unpredictably.

CALL bad           ; 0103h: ret = 0106h
RET                ; 0106h
bad PROC
PUSH AX            ; AX saved...
; ... work ...
RET                ; forgot POP AX!
bad ENDP

Code Trace: Near CALL, Far Return

AX = 5. The farp procedure ends with RETF, but the call is near.

A near CALL pushes only IP (0106h): 2 bytes on the stack.

SHL AX, 1: AX = 000Ah.

RETF pops two words: IP = 0106h and, as CS, whatever it finds on the stack, here the 0000h DOS pushed for the .COM program. SP = 0000h.

The CPU jumps to 0000:0106h: that is the interrupt vector table, not program code. The program crashes; ADD AX, 1 never runs.

ORG  100h
MOV  AX, 5
CALL farp        ; near CALL: IP only
ADD  AX, 1
RET
farp PROC
SHL  AX, 1
RETF             ; pops IP and CS!
farp ENDP

Common Bugs

Common Bugs

Forgetting RETThe CPU never sees ENDP; whatever code or data follows the procedure is executed.
Unbalanced PUSH / POPRET loads the wrong value into IP. Every PUSH needs a POP, in reverse order.
"Falling into" a procedureA procedure placed in the middle of the main code and not jumped over runs without a CALL; its RET ends the program.
JMP instead of CALLJMP pushes no return address; the procedure's RET returns to some unrelated value on the stack.
Name mismatchp1 PROC … p2 ENDP → assembler error.
Infinite recursionWithout a stopping condition, every call to a self-calling procedure eats 2 bytes until the stack overflows.

Common Bugs

More Procedure Bugs

Early RETA conditional RET after a PUSH takes the saved value for the return address. All paths go to a single exit label where the POPs are.
MOV instead of LEAMOV SI, arr loads the array's first word, not its address; the procedure reads from an unrelated address.
DX silently clobbered16-bit MUL and DIV also write DX. A procedure whose header lacks “Clobbers: DX” wipes out the caller's DX.
Type mismatchNear CALL + RETF, or CALL FAR + RET: the stack is off by 2 bytes and the return goes to the wrong address.
Clobbering the flagIn a procedure that returns its result in CF, an instruction such as ADD or CMP after STC/CLC changes CF. POP and RET leave the flags alone.
Testing the base case too lateIf a recursive procedure tests its stopping condition after the CALL, the calls never stop and the stack overflows.

PROC / ENDPDirectives; no machine code. CALL and RET are CPU instructions.
