What a Macro Is

Macros

  • Macros resemble procedures: they give a name to a repeated piece of code.
  • But they are not called at run time; they are placeholders replaced by real instructions at assembly time.
  • Macros that are never used are ignored: they add no bytes to the machine code.
  • Unlike procedures, macros must be defined above the code that uses them; the assembler cannot expand a call to a macro it does not yet know.

What a Macro Is

Defining a Macro

name    MACRO  [parametreler,...]
        <instructions>
        ENDM
nameThe macro's name; you write it like an instruction to use it.
parametersComma-separated formal names (optional). The values in the call replace them as text.
ENDMEnds the macro body. Unlike a procedure, the name is not repeated.
Parameters may be registers, memory or immediates: the assembler only substitutes text; whether the resulting instruction is valid is checked after expansion.

Pitfall: Parameters Are Text

The call MyMacro BX, AX, 0 is thought to do AX ← BX, BX ← AX (a swap).

AX = 1111h.

BX = 2222h.

Line 1 of the macro: MOV AX, p1 → MOV AX, BX → AX = 2222h.

Line 2: MOV BX, AX. The programmer expected the “old AX” (1111h), but AX changed on the line before → BX = 2222h.

CX = 0.

Result: AX = BX = 2222h. 1111h is lost.

ORG 100h
MOV  AX, 1111h
MOV  BX, 2222h
MOV  AX, BX  ; MyMacro BX,AX,0
MOV  BX, AX  ; p2 = AX (bad!)
MOV  CX, 0
RET

A macro parameter is not a variable but replacement text: its value is read on the line where it is used. Do not pass registers that the macro body changes as parameters.

  • A parameter may be a register, a variable, an immediate or an expression; what is accepted is decided not by the macro but by the instruction produced by the expansion.
  • The error is reported on the line that uses the macro, but its cause is a line in the body: think of the expansion to make sense of the message.
  • A missing parameter is replaced by empty text. In MASM, z:REQ makes a parameter required and y:=<1> gives it a default value.

Code Trace: Two Expansions of ADD3

org 100h
mov ax, a      ; ADD3 a, b, c
add ax, b
mov c, ax
mov ax, c      ; ADD3 c, 5, d
add ax, 5
mov d, ax
ret
a dw 1200h
b dw 0345h
c dw ?
d dw ?

1st expansion ADD3 a, b, c: x was replaced by a → AX = 1200h.

ADD AX, b: 1200h + 0345h = 1545h.

MOV c, AX: c = 1545h. There is no memory-to-memory add, so the macro uses AX as a go-between.

2nd expansion ADD3 c, 5, d: the same body, different text. x = c → AX = 1545h.

This time y = 5 is an immediate: ADD AX, 5 → AX = 154Ah.

MOV d, AX: d = 154Ah. The two expansions produced 6 instructions; the macro clobbered AX, and the caller must know it.

RET. Code (3 + 4 + 3) + (3 + 3 + 3) = 19 bytes + RET = 20 bytes; ADD AX, 5 is 3 bytes in the short AX form. Every use of ADD3 writes the body again.

Macro: ADD3 MACRO x, y, z / MOV AX, x / ADD AX, y / MOV z, AX / ENDM. The code is the expanded form of the two calls.

What a Macro Is

Parameter Expressions and Operator Precedence

AREA MACRO wd, ht
  MOV AX, wd*ht
ENDM

DIFF MACRO p, q
  MOV CX, p-q
ENDM
  • A parameter is text, not a value: operator precedence is applied again on the line where the expression is substituted.
  • AREA 2+3, 4: the multiplication is done first, so AX = 14; 20 was expected.
  • Fix: put the parameters in parentheses in the body: (wd)*(ht), (p)-(q).
CallExpansionResult
AREA 2+3, 4MOV AX, 2+3*4AX = 000Eh (14)
fixed AREA 2+3, 4MOV AX, (2+3)*(4)AX = 0014h (20)
DIFF 10, 4+1MOV CX, 10-4+1CX = 0007h
AREA BX, 2MOV AX, BX*2error: * with constants only

The expression is evaluated at assembly time; an expression with a register cannot be multiplied at run time. Multiplying a register needs MUL or SHL.

Macros vs Procedures


Procedure Features




    

  • A procedure is called with the CALL instruction.
    • 

  • A procedure exists as a single copy at a specific address in memory.
    • 

  • When it is called, the CPU transfers control there; RET returns control to the main program.
    • 

  • The stack holds the return address.
    • 

  • Calling the same procedure 100 times barely grows the file: a near CALL takes only 3 bytes.
    • 

  • Parameters are passed on the stack or in registers.
    • 

  • A procedure ends with its name and the ENDP directive.
    • 



PRINT_A PROC
      PUSH AX
      MOV  AL, 'A'
      MOV  AH, 0Eh
      INT  10h
      POP  AX
      RET
PRINT_A ENDP

      CALL PRINT_A  ; 3 bytes
      CALL PRINT_A  ; 3 bytes









Macros vs Procedures


Macro Features




    

  • A macro is used just by writing its name (no CALL).
    • 

  • Macros are expanded in place in the program code.
    • 

  • Use the same macro 100 times and the assembler expands it 100 times; the executable keeps growing.
    • 

  • Parameters are written after the macro name.
    • 

  • The ENDM directive alone ends a macro.
    • 

  • If a macro definition contains labels and the macro is used more than once, you can get a Duplicate declaration error; use the LOCAL directive for variable, label and procedure names.
    • 



PUTC MACRO char
     PUSH AX
     MOV  AL, char
     MOV  AH, 0Eh
     INT  10h
     POP  AX
ENDM

     PUTC 'A'  ; 8 bytes
     PUTC 'B'  ; 8 bytes

Rule: short, frequently used, speed-critical code → macro; long code used in many places → procedure. The two can be combined: a macro can put its parameters in registers and call a procedure.






Macros vs Procedures


Code Size: 1, 10 and 100 Uses




1 use: macro 8 bytes; procedure 8 bytes of body + 1 byte RET + 3 bytes CALL = 12 bytes. Here the macro is smaller.


10 uses: macro 80 bytes; procedure 9 + 30 = 39 bytes.


100 uses: macro 800 bytes; procedure 9 + 300 = 309 bytes. The gap grows with the number of uses.


For speed it is the other way round: each CALL + RET pair adds about 19 + 8 = 27 clocks and two stack accesses on the 8086. A macro has no such cost.






Macros vs Procedures


Decision Exercise: Macro or Procedure?




Five cases: in each, weigh code size (how many copies?) against speed (the CALL/RET cost).


1. Print one character, in 200 places → a short body (8 bytes) but 200 copies = 1600 bytes. A procedure: 9 + 600 = 609 bytes. If size matters, procedure; if speed matters, macro.


2. A one-line job swapping two registers → XCHG is already one instruction; a macro is enough for readability, a procedure is needless overhead (macro).


3. A 300-byte sorting algorithm, in 3 places → macro 900 bytes, procedure 300 + 9 bytes: clearly a procedure.


4. A 2-instruction job done on every pass of a tight loop → the CALL/RET cost exceeds the job itself: macro.


5. Put the parameters in registers and call shared code → both together: macro SHOW_NUM x → MOV AX, x + CALL print_num (emu8086.inc works this way too).

Macro Sets the Parameter, Procedure Does the Work

  


org 100h
mov  al, 4       ; PUT_DIGIT 4
call print_digit
mov  al, 7       ; PUT_DIGIT 7

ret

add  al, '0'     ; digit → ASCII

Macro PUT_DIGIT d expanded at assembly time into mov al, d + call print_digit. The work is in the procedure, a single copy. First copy: AL = 04h.


CALL pushes the return address (the instruction after the CALL, 0105h): SP = FFFCh. IP ← print_digit.


Procedure body: AL + 30h = 34h ('4'), AH = 0Eh, INT 10h prints 4.


RET pops 0105h: SP = FFFEh; execution resumes after the macro's first copy.


The macro's second copy: AL = 07h. Each copy is only 5 bytes (2-byte MOV + 3-byte CALL).


CALL again: this time the return address is 010Ah. Same procedure, different return address.


The same single procedure copy runs: AL = 37h ('7'). The screen shows 47.


RET → 010Ah. The stack is empty again; the caller's SP was preserved.


The program ends. The macro loaded the parameter; the shared code is in the procedure, just like emu8086.inc's DEFINE_... + macro pairs.



      

    

  

  
Macro: PUT_DIGIT MACRO d / mov al, d / call print_digit / ENDM. 10 uses: 10 × 5 + 7 = 57 bytes; with the whole body in the macro, 10 × 8 = 80 bytes.

Labels and LOCAL


Macros with Labels: The Problem




If a macro whose body contains a label is used twice, the expansion defines the same label twice:


DELAY MACRO
lp:  DEC CX
      JNZ lp
ENDM

MOV CX, 5
DELAY
MOV CX, 9
DELAY


What the assembler sees:


MOV CX, 5
lp:   DEC CX    ; copy 1
      JNZ lp
MOV CX, 9
lp:   DEC CX    ; copy 2 !
      JNZ lp


emu8086: a Duplicate declaration error. Which lp: to jump to is ambiguous.









Labels and LOCAL


Fix: The LOCAL Directive




MyMacro2 MACRO
    LOCAL label1, label2
    CMP  AX, 2
    JE   label1
    CMP  AX, 3
    JE   label2
label1:
    INC  AX
label2:
    ADD  AX, 2
ENDM




    

  • LOCAL must be the first line of the macro body (right after the MACRO line).
    • 

  • The listed names are replaced by the assembler with unique names at each expansion (??0000, ??0001, … in MASM).
    • 

  • It works for labels, variables and procedure names inside the macro.
    • 





Usagelabel1label2

2nd MyMacro2??0002??0003

Running MyMacro2 (AX = 2)






The code after LOCAL has turned the labels into unique names.


AX = 2.


CMP AX, 2: 2 − 2 = 0 → ZF = 1.


JE: ZF = 1, so it jumps to ??0000 (label1).


INC AX → AX = 3.

The program ends.

With AX = 3 it would jump to label2 and AX = 5. With AX = 7 there is no jump and it falls into label1: INC + ADD → AX = 10.

LOCAL: Two Copies, Two Separate Labels

  


org 100h
mov cx, 3
??0000: dec cx   ; DELAY (copy 1)
jnz ??0000
mov cx, 2
??0001: dec cx   ; DELAY (copy 2)
jnz ??0001
ret

    




The macro has LOCAL lp. At each expansion the assembler put a new name in place of lp: ??0000 (0103h) in copy 1, ??0001 (0109h) in copy 2. CX = 3.


Pass 1: DEC CX → CX = 2, ZF = 0; JNZ goes back to ??0000 (0103h).


Pass 2: CX = 1, ZF = 0 → again 0103h.


Pass 3: CX = 0 → ZF = 1; JNZ does not jump, copy 1 is done.


CX = 2: the counter for the macro's second use.


Copy 2: DEC CX → CX = 1; JNZ goes back to ??0001 (0109h), not to copy 1's label.


CX = 0, ZF = 1: the loop ends. No label name is defined twice, so there is no Duplicate declaration error.


RET: the program ends. 3 + 2 = 5 DECs ran in total.



      

    

  

  
Macro: DELAY MACRO / LOCAL lp / lp: DEC CX / JNZ lp / ENDM; main program mov cx, 3 / DELAY / mov cx, 2 / DELAY.

1st expansion MAX2 x, y, m1: AX = x = 7.


CMP AX, y: 7 − (−3) = 10 → SF = 0, OF = 0.


JGE compares signed: SF = OF → jumps to the ??0000 label. LOCAL turned this copy's ok label into ??0000.


m1 = 7.


2nd expansion MAX2 y, 4, m2: AX = y = −3 (FFFDh); CMP AX, 4: −3 − 4 = −7 → SF = 1, OF = 0.

m2 = 4; RET. With JAE, −3 (FFFDh) would count as the unsigned 65533, and m2 would be −3.



      

    

  

  
Macro: MAX2 MACRO p, q, r / LOCAL ok / MOV AX, p / CMP AX, q / JGE ok / MOV AX, q / ok: MOV r, AX / ENDM. In the first call the parameters are variables; in the second, one is an immediate.






The PUTC Macro


PUTC: Printing a Character




; prints a char, moves the cursor
PUTC  MACRO  char
      push  ax
      mov   al, char
      mov   ah, 0eh
      int   10h
      pop   ax
ENDM

ORG  100h
START:
      PUTC  'A'
      PUTC  'B'
      RET


    

  • The macro prints the character in its char parameter and moves the cursor one place right.
    • 

  • INT 10h, AH = 0Eh: BIOS teletype output. The character in AL is written at the cursor; control characters such as 0Dh, 0Ah, 07h, 08h are interpreted.
    • 

  • push ax / pop ax: the macro uses AX, so it preserves the caller's AX. No “invisible” side effect remains.
    • 

  • This macro is identical to the PUTC macro in the emu8086.inc library.
    • 



The RET after PUTC 'B' ends the program; without it the CPU would go on executing the random bytes after the program.








The PUTC Macro · Step through the code


PUTC 'A' and PUTC 'B' at Run Time






After loading, CX = 0011h: 2 copies × 8 bytes + RET = 17 bytes. The screen is empty.


AX (0000h) is saved on the stack; SP = FFFCh.


AL = 41h ('A').


AH = 0Eh → AX = 0E41h.


INT 10h: A is printed and the cursor advances.


AX gets its old value (0000h) back; SP = FFFEh.


Second copy: AX is saved again.


AL = 42h ('B').


AX = 0E42h.


INT 10h: the screen shows AB.


AX = 0000h; the macro did not clobber the caller's AX.


RET: the program ends.

mov  al, 'A'
mov  ah, 0eh
int  10h
pop  ax

mov  al, 'B'

Output in the emu8086 screen window (80×25): AB. Each PUTC copy is 8 bytes: 50 B0 41 B4 0E CD 10 58.






  
The PUTC Macro

  
Register-Saving Macros




SAVE MACRO
  PUSH AX
  PUSH BX
  PUSH CX
  PUSH DX
ENDM

RESTORE MACRO
  POP DX
  POP CX
  POP BX
  POP AX
ENDM


    

  • PUTC's push ax / pop ax pattern grows to four registers in larger macros; the pattern itself can be a macro.
    • 

  • RESTORE pops the registers in the reverse of the order SAVE pushed them: the stack is last in, first out. In the same order, AX and DX, BX and CX would swap.
    • 

  • Each SAVE + RESTORE pair adds 8 bytes and 8 stack accesses: 4 × 11 (PUSH) + 4 × 8 (POP) = 76 clocks on the 8086.
    • 

  • Use the two macros together in one body; a conditional exit in between leaves the stack unbalanced.
    • 





On the 80186 and later, single-instruction PUSHA / POPA save all general-purpose registers; the 8086 lacks them, so a macro does the job.






The POWER Macro


Exponentiation: The POWER Macro




POWER macro b, e, r
    mov ax, 1        ; result so far = 1
    mov cx, e        ; exponent → CX
    mov bx, b        ; base → BX
powerloop:
    mul bx           ; DX:AX = AX * BX
    loop powerloop   ; repeat e times
    mov r, ax        ; store result
endm


ORG 100h
start:
    POWER base, exponent, result
    ret
base     dw 2     ; base
exponent dw 3     ; exponent
result   dw ?     ; result


    

  • Result r = be: start AX at 1 and multiply by the base e times.
    • 

  • MUL BX: DX:AX ← AX × BX (unsigned). DX changes too!
    • 

  • LOOP: decrements CX and jumps to the label if CX ≠ 0.
    • 









The POWER Macro · Step through the code


POWER 2, 3 Step by Step






The data comes right after the code: base = 0113h, exponent = 0115h, result = 0117h (code is 19 bytes).


AX = 1 (result so far).


CX ← [0115h] = 3 (exponent).


BX ← [0113h] = 2 (base).


Pass 1: DX:AX = 1 × 2 = 0002h.


LOOP: CX = 2 ≠ 0 → powerloop.


Pass 2: AX = 2 × 2 = 0004h.


LOOP: CX = 1 → powerloop.


Pass 3: AX = 4 × 2 = 0008h.


LOOP: CX = 0 → exit the loop.


result ← AX: [0117h] = 0008h = 23.


RET: the program ends.




ORG 100h
mov ax, 1        ; POWER expansion
mov cx, exponent
mov bx, base
powerloop:
mul bx
loop powerloop
mov result, ax
ret
base     dw 2    ; 0113h
exponent dw 3    ; 0115h
result   dw ?    ; 0117h




After MUL, DX = 0, so CF = OF = 0. Had the result exceeded 16 bits (e.g. 216), DX ≠ 0 and CF = 1; since the macro stores only AX, the result would be wrong.






The POWER Macro


Pitfalls of the POWER Macro






1. Exponent = 0With CX = 0, LOOP decrements CX first: FFFFh → the loop runs 65,536 times; b0 should be 1. Fix: JCXZ.


2. Labelpowerloop is not LOCAL: a Duplicate declaration on the second use.


3. Clobbered registersAX, BX, CX and (because of MUL) DX change.


4. OverflowIf the result exceeds 65,535, the high part stays in DX and is not stored.




Fixed version:


POWER MACRO b, e, r
      LOCAL p_loop, p_end
      PUSH BX
      PUSH CX
      PUSH DX
      MOV  AX, 1
      MOV  CX, e
      MOV  BX, b
      JCXZ p_end   ; e = 0 → 1
p_loop: MUL BX
      LOOP p_loop
p_end: MOV r, AX
      POP  DX
      POP  CX
      POP  BX
ENDM

The caller's registers are BX = 0AAAh, CX = 0BBBh, DX = 0CCCh. The fixed macro first saves all three on the stack: SP = FFF8h.


AX = 1, CX ← expn = 2, BX ← base = 7. The registers now belong to the macro.


JCXZ: CX = 2 ≠ 0, no jump. Had expn been 0, it would go straight to ??0001 and the result would be 1 (no 65,536-pass LOOP trap).


1st MUL: DX:AX = 1 × 7 = 0007h. MUL writes DX too (DX = 0).


LOOP: CX = 1 ≠ 0 → ??0000.


2. MUL: DX:AX = 7 × 7 = 0031h = 49.


LOOP: CX = 0 → exit the loop.


res ← AX: [011Fh] = 0031h = 7². LOCAL renamed the labels ??0000 / ??0001.


Three POPs, in the reverse order of the PUSHes: DX = 0CCCh, CX = 0BBBh, BX = 0AAAh are back; SP = FFFEh. The macro changed only AX.


RET: the program ends.



      

    

  

  
The code is the expansion POWER base, expn, res of the fixed macro; LOCAL names are shown as the assembler generates them.

Macro Libraries · Step through the code

  
emu8086.inc: Expanding PRINT 'OK'

  


org 100h
push ax          ; PRINT 'OK'
push si
jmp  ??0003      ; skip the data
??0001 db 'OK', 0
??0003: lea si, ??0001
??0000: mov al, cs:[si]
cmp  al, 0
jz   ??0002
inc  si
mov  ah, 0Eh
int  10h
jmp  ??0000
??0002: pop si
pop  ax
ret

    




PRINT 'OK' is expanded. The macro will use AX and SI, so it saves both on the stack first.


The string is embedded between instructions inside the macro (0104h: 'O', 'K', 0). The JMP jumps over these bytes so the CPU does not take them for instructions.


SI ← the string address 0104h. LOCAL names (??0000…) are new for each PRINT.


AL ← CS:[SI] = 4Fh ('O'). The string is in the code segment, so the CS: prefix is used. Not 0 → continue.


SI advances by one, INT 10h/0Eh prints O, JMP goes back to the top of the loop.


AL = 4Bh ('K'); not the terminator.


The screen shows OK.


AL = 00h: CMP → ZF = 1, JZ jumps to the exit.


SI and AX are popped back: the macro did not clobber the caller's registers.


RET: the program ends. The one-line PRINT 'OK' produced 26 bytes of code + data.



      

    

  

  
Expansion of the PRINT macro from emu8086.inc (LOCAL names as the assembler generates them). PRINTN does the same and appends CR LF.

Macro Operators: &, <>, !, %, ;;


OperatorRoleExample and expansion


&joins a parameter to adjacent textCLEAR MACRO r · XOR r&X, r&X → CLEAR B: XOR BX, BX


< >makes text containing commas or spaces a single parameterEMIT <'A', 'B'> → one parameter: 'A', 'B'


!makes the next character an ordinary character<5 !> 3> → text: 5 > 3


%evaluates an expression and substitutes the result as textSHOW %(4*8) → parameter 32


;;macro comment; not copied into the expansion;; visible only in the definition




    

  • These operators are defined in MASM and TASM; they are used to split and join text when writing a macro definition.
    • 

  • Without &, rX counts as a single name and is not substituted.
    • 

  • A comment written with a single ; is repeated in every expansion; ;; keeps the listing short.
    • 







  
Advanced Macro Features

  
Repeat Blocks: REPT, IRP, IRPC




REPT n
REPT 3
  SHL AX, 1
ENDM
expansion: SHL AX, 1 three times (AX × 8)


IRP p, <list>
IRP r, <AX,BX,CX>
  PUSH r
ENDM
expansion: PUSH AX · PUSH BX · PUSH CX


IRPC p, text
IRPC c, OK
  PUTC '&c'
ENDM
expansion: PUTC 'O' · PUTC 'K'




    

  • Repeat blocks are nameless macros expanded right where they are defined; they end with ENDM.
    • 

  • REPT writes the body n times, IRP once for each item in the list, IRPC once for each character of the text. In MASM 6, IRP and IRPC can also be written as FOR and FORC.
    • 

  • No loop counter is needed, but the code grows: REPT 100 copies the body 100 times. A counted LOOP works with a single copy.
    • 

  • The most common use is generating tables at assembly time: number tables, masks, squares or sine values.
    • 







  
Advanced Macro Features · Step through the code

  
Code Trace: A Table of Squares Generated by REPT

  


org 100h
lea  bx, sq
mov  al, 5
xlat           ; AL = sq[5]
mov  dl, al
mov  al, 7
xlat           ; AL = sq[7]
add  al, dl
ret
sq db 0, 1, 4, 9, 16, 25, 36, 49

    




REPT generated the table at assembly time; memory holds just 8 bytes. LEA BX, sq: BX = 010Eh.


AL = 5: the number to square, which is also the table index.


XLAT: AL ← [BX + AL] = sq+5 = 25 (19h). No multiplication, just a table read.


DL = 19h: the first result is saved.


AL = 7, XLAT → sq+7 = 49 (31h).


ADD AL, DL: 49 + 25 = 74 (4Ah) = 5² + 7².


RET. XLAT takes 11 clocks; an 8-bit MUL on the 8086 takes 70–77.



      

    

  

  
Source of the table: n = 0 / sq LABEL BYTE / REPT 8 / DB n*n / n = n + 1 / ENDM. The code ran in the expanded form of this block. An EQU constant cannot change; a symbol defined with = takes a new value on each pass.

Conditional Assembly: IF, IFB, IFIDN




SHIFTN MACRO r, n
  IFB <n>          ;; n not given?
    SHL r, 1
  ELSE
    MOV CL, n
    SHL r, CL
  ENDIF
ENDM

DEBUG = 1
IF DEBUG
  PUTC '*'         ; debug build only
ENDIF


DirectiveCondition


IF exprexpr ≠ 0


IFE exprexpr = 0


IFB <p>parameter blank


IFNB <p>parameter not blank


IFIDN <a>,<b>two texts identical


IFDIF <a>,<b>two texts different






    

  • The condition is evaluated at assembly time: the branch not chosen never enters the machine code; there is no flag or jump at run time.
    • 

  • EXITM ends the expansion at that point; IFIDN <r>, <CX> can catch a register the body clobbers being passed as a parameter.
    • 







  
Advanced Macro Features · Step through the code

  
Code Trace: SHIFTN AX and SHIFTN BX, 3

  


org 100h
mov ax, 5
mov bx, 3
shl ax, 1      ; SHIFTN AX
mov cl, 3      ; SHIFTN BX, 3
shl bx, cl
ret

    




AX = 5, BX = 3: the values to shift.


SHIFTN AX: n is blank, the IFB branch is chosen → a single SHL AX, 1. AX = 000Ah (5 × 2).


SHIFTN BX, 3: n = 3, ELSE branch → MOV CL, 3. On the 8086 a shift count above 1 goes in CL.


SHL BX, CL: 3 × 2³ = 0018h (24). The same macro produced code of two different lengths: 2 bytes and 4 bytes.


RET. The SHIFTN AX expansion did not touch CL; only the second expansion changed it.



      

    

  

  
The code is the expanded form of two SHIFTN calls. The assembler chose which branch to emit; no comparison happened at run time.

Debugging and Listing Macros




Seeing the expansionThe instruction list in emu8086's emulator window shows the expanded instructions, not macro names; single-stepping moves through these instructions.


Listing fileIn MASM, .LISTMACROALL lists every line of the expansion, .LISTMACRO only the lines that generate code, and .NOLISTMACRO hides the expansion.


Error lineAn error in the body is reported separately at every line that uses the macro. If the same error shows up several times, the cause is usually in the body.


Expand by hand firstDevelop a new macro by writing and testing its body as plain code first; once it works, turn it into a parameterized macro.




Because LOCAL gives macro labels names like ??0000, jump targets in the emulator don't show the source names; these numbers tell you which copy is running.

Common Macro Mistakes




Defining after useThe assembler cannot expand a call to a macro it does not know; put definitions at the top of the file or in an INCLUDE file.


Forgetting ENDMThe rest of the file is taken as the macro body; the error shows up much further down.


Labels not made LOCALDuplicate declaration on the second use.


RET in the bodyA macro is not entered with CALL; RET takes the caller's return address.


Passing a clobbered registerIn a call such as ADD3 BX, AX, CX, the body may change a parameter before reading it.


Unparenthesized expressions(wd)*(ht) instead of wd*ht; otherwise precedence changes.


Mistaking a macro for a loopREPT 1000 produces 1000 copies; repeating at run time needs LOOP.


Using a long body many timesCode size grows with the number of uses; move long work into a procedure.
