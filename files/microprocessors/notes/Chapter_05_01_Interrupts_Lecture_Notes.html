Chapter 5.1: Interrupts

A processor that only ran its own program would know nothing of the outside world. A key is pressed, a timer produces a pulse, a disk drive has data ready; the processor must respond to these events in time. An interrupt lets the processor drop what it is doing at an instruction boundary, run a routine that belongs to the event, and then resume where it left off. These notes begin with what an interrupt is and how it differs from polling. They then cover the 8086 interrupt vector table and the effect of INT and IRET on the stack, followed by exceptions generated by the processor itself, hardware interrupts on the INTR and NMI pins, the 8259A interrupt controller, and interrupt latency. The last part writes an interrupt service routine from scratch, installs its vector, and restores the old vector when the program ends. Every piece of code is traced step by step together with the registers, flags, vector table and stack.

5.1.1The interrupt concept

5.1.1.1What is an interrupt?

While a program runs, the processor fetches, decodes and executes instructions in order. After each instruction IP points to the next one, and apart from jumps and calls this order is never disturbed. Yet events that have nothing to do with the program happen all around the computer. A user presses a key, the timer chip produces pulses at fixed intervals, a character arrives on the serial port. The processor must not miss these events and must respond to them quickly.

Definition 5.1.1

An interrupt is an event that makes the processor temporarily set aside its current work and run a special routine. This routine is called an interrupt service routine (ISR). When the ISR finishes, the processor resumes the program with the instruction after the one that was interrupted.

The last sentence of the definition is the important one. The interrupted program does not notice that it was interrupted. Its registers, flags and memory continue with the values they would have had without the interrupt. Guaranteeing this is the job of both the processor and the programmer who writes the ISR. The processor saves the return address and the flags on its own. The ISR saves the registers it uses and restores them on exit.

An everyday analogy captures the steps of an interrupt. You are reading a book when the phone rings. You first mark your page, then answer the phone and talk. When the call ends, you return to the marked page and carry on reading. Marking the page is saving the return address; the phone call is the ISR; returning to the marked page is the IRET instruction. If you forget to mark the page, you will not know where to continue. The processor would be in the same position if it entered an ISR without pushing the return address on the stack.

Figure 5.1.1 shows this flow on a time axis. The main program stops at some point, control passes to the ISR, and the last instruction of the ISR, IRET, hands control back to the main program. An interrupt can be started in two ways: the program executes an INT instruction, or a request arrives from outside the processor. In both cases what the processor does afterwards is the same.

Interrupts have a second, more everyday use. On an 8086-based PC there are ready-made routines for writing a character to the screen, reading a key from the keyboard, accessing the disk, or ending a program. These are the routines of the BIOS, which sits in ROM on the motherboard, and of the operating system, DOS. A program calls them with an INT instruction, without knowing their addresses. To write a character to the screen, for example, it does not need dozens of instructions that drive the video hardware; INT 10h does the job. For this reason software interrupts are also seen as ready-made services that make programming easier. The details of the interrupt functions that work with hardware such as the screen, the keyboard, the disk drive and memory management are the subject of the notes of Chapter 5.2, Interrupt Functions. These notes cover the interrupt mechanism itself: how the processor accepts an interrupt and how it returns.

5.1.1.2Polling or interrupts?

A processor can learn the state of a device in two ways. The first is to keep asking the device, "Is the data ready?" This method is called polling. In a loop the processor reads the device's status port, checks the ready bit, and reads again if it is not set. The second is for the device to announce itself. When its data is ready, the device drives a pin of the processor; the processor finishes the current instruction and switches to the ISR. This is the interrupt method.

Figure 5.1.2 compares the two methods on the same time axis. The cost of polling can be seen in a single number. The shortest polling loop that asks for the keyboard's state has three instructions: an IN that reads the port, a TEST that checks the ready bit, and a conditional jump that goes back to the start if the device is not ready.

; polling loop (port number and bit are examples)
poll:  IN   AL, 64h      ; read the status port (10 clocks)
       TEST AL, 01h      ; data-ready bit (4 clocks)
       JZ   poll         ; not ready: ask again (16 clocks)

According to Intel's 8086 manual, an IN with a fixed port takes 10 clock cycles, a TEST of a register with an immediate takes 4, and a taken JZ takes 16. One pass of the loop is 30 clock cycles; on a 5 MHz 8086 a clock cycle is 200 ns, so the loop turns once every 6 µs. The processor asks the device about 166,000 times per second. A fast typist presses ten keys per second. Of those 166,000 queries only ten get a "yes" and the rest are wasted. Worse, the processor can do nothing else in the meantime.

Polling less often saves processor time, but then the event is noticed late. If the program asks every 10 ms, the response to a key press can be delayed by up to 10 ms. The longer the interval, the greater the risk of losing data. For example, characters arriving on a serial port at 9600 bit/s are about 1 ms apart. If the device has a one-character buffer, a character that is not read within 1 ms is overwritten by the next.

With interrupts this dilemma disappears. The processor runs the main program as long as there is no event; the moment an event occurs, at the latest when the current instruction finishes, it switches to the ISR. The price is the machinery. A routine must be written for each event, its address placed in a table, the stack used for the return address, and the hardware needs lines that carry the request to the processor. Polling is not always bad. If a small microcontroller circuit is only waiting for one button, polling is the simplest solution. If a very fast device produces data every few microseconds, a tight polling loop can be faster than bearing the overhead of the interrupt machinery for every item. A general-purpose computer, on the other hand, has independent events at unpredictable times: keyboard, timer, disk and serial port. Polling all of them in one loop both keeps the processor busy and slows the response. This is why the PC architecture is built on interrupts.

Common mistake

Generalizing "with an interrupt the processor never waits for the device" to "an interrupt is always faster than polling." The interrupt mechanism itself takes time: on the 8086, accepting a hardware interrupt takes 61 clock cycles and IRET takes 24. For an event that arrives thousands of times per second, this overhead can exceed the cost of polling. The advantage of interrupts is that for rare events the processor does not wait in vain.

5.1.1.3Interrupt kinds and type numbers

The 8086 distinguishes up to 256 different interrupts. Each interrupt has a type number between 0 and 255 (00h–FFh). When the processor accepts an interrupt, the first thing it does is determine this number; it then reads from a table which routine to go to for that number. Interrupts fall into three groups, according to where the type number comes from and what starts the interrupt.

Definition 5.1.2

A software interrupt is one called deliberately by an INT n instruction in the program; the type number n is inside the instruction. A hardware interrupt is one started when an external device drives the processor's INTR or NMI pin. An internal interrupt, or exception, is one the processor generates itself while executing an instruction; division by zero is the best-known example.

Software interrupts. BIOS and DOS services are used this way: INT 10h is the screen, INT 16h the keyboard, INT 21h the DOS services. Two more special instructions belong to this group. INT 3 is the breakpoint instruction used by debuggers and is encoded in a single byte. INTO calls INT 4 when the overflow flag OF = 1 and does nothing when OF = 0. Because they serve debugging and error trapping, these two instructions are often mentioned together with exceptions.

Hardware interrupts. The 8086 has two input pins for interrupt requests. INTR (interrupt request) is the maskable input: while IF = 0 the processor ignores this pin. Requests from the keyboard, timer, disk and serial port arrive on it. NMI (non-maskable interrupt) is the non-maskable input; it is accepted whatever IF is. It is reserved for urgent events that a program cannot switch off and ignore, such as a memory parity error or loss of power.

Internal interrupts. The processor turns some conditions into interrupts by itself. When DIV or IDIV divides by zero, or the quotient does not fit in the destination register, INT 0 is generated. While the trap flag TF = 1, INT 1 is generated after every instruction; this lets debuggers run a program one step at a time.

Table 5.1.2 gives the role of the first five type numbers. The 8086 itself uses these five types; their numbers are fixed and a programmer must not use them for anything else.

Intel stated explicitly in its documentation that it was reserving the range 05h–1Fh for its future processors. The designers of the IBM PC did not heed this warning and placed BIOS services in the range 05h and 08h–1Fh. For example, the BIOS routine that prints the screen on the printer uses type 05h. With the 80186 and 80286, type 05h became the bound-range-exceeded interrupt of the BOUND instruction. The same number thus acquired two different meanings, and PC software wrestled with this collision for years. The story is a good illustration of why reserved numbers must stay reserved.

5.1.1.4Comparing the three sources

At first glance the three kinds of interrupt look very different: one is an instruction, one is a pin, one is an error condition. They differ in only two respects: where the type number comes from and when the interrupt occurs. Table 5.1.3 puts these differences side by side.

Table 5.1.3: Comparison of software, hardware and internal interrupts.

The words synchronous and asynchronous are used here with respect to the program flow. A software interrupt occurs at the same point of the program, in the same way, on every run. An exception is the same: the same DIV instruction with the same data gives the same error every time. A hardware interrupt, on the other hand, is an event whose instruction in the program cannot be known in advance. The user presses a key once at the start of a loop and once in the middle. For this reason the ISR of a hardware interrupt must be written as if it could run at any point of the program. This is where the obligation of ISRs to save registers comes from.

There is an important common point under the table. Once the type number is determined, all three kinds follow the same steps: FLAGS, CS and IP are pushed, IF and TF are cleared, and CS:IP is loaded from the vector table. In other words there is a single interrupt mechanism inside the processor; the sources only determine with which number and at what moment that mechanism is entered.

Common mistake

Assuming that the CLI instruction turns off all interrupts. CLI only clears IF and affects only the INTR input. Software interrupts such as INT 21h, exceptions such as division by zero, and NMI still run while IF = 0. When CLI is used to "protect a critical piece of code from interrupts", remember that NMI can still arrive.

5.1.2The interrupt vector table

5.1.2.1Structure of the table

After the processor learns the type number of an interrupt, it must find where the ISR for that interrupt is. On the 8086 this information is kept in a table at the very beginning of memory. The location of the table is fixed; on every interrupt the hardware looks at the same address.

Definition 5.1.3

An interrupt vector is the 4-byte far address of the service routine of an interrupt type: 2 bytes of IP (offset) and 2 bytes of CS (segment). The interrupt vector table (IVT) is the 1 KB table that holds the vectors of the 256 interrupt types in order and occupies physical addresses 00000h–003FFh.

The size of the table is easy to compute: 256 types × 4 bytes = 1024 bytes = 1 KB. The vector of type 0 starts at 00000h, that of type 1 at 00004h, that of type 2 at 00008h, and so on. The vector of the last type, FFh, is in bytes 003FCh–003FFh. The address at which the vector of type n starts is therefore a simple multiplication:

vector address = n × 4    (within segment 0000h)

The layout of the four bytes of a vector is also fixed. Figure 5.1.3 shows the table. The word at the lower address (n × 4 and n × 4 + 1) holds the IP value. The word at the higher address (n × 4 + 2 and n × 4 + 3) is the CS value. Both words are stored in little-endian order, like all words on the 8086: low byte first, then high byte.

The answer to why the table is at the very beginning of memory lies in the design of the 8086. The hardware does not have to look at any register to find the table; the address is produced from the type number alone. The operation n × 4 is a two-bit shift in the circuit. The 8 bits of the type number are placed on address lines A2–A9; A0, A1 and A10–A19 are zero. Reading a vector therefore needs no extra adder or register. The price is that the first 1 KB of memory must always be RAM. Programs have to be able to change the table; if it were in ROM, no program could install its own ISR.

The table is an ordinary region of memory with no special protection. Any program that sets a segment register to 0000h can read and write any byte of the table. This flexibility lets programs install their own ISRs; it also means that a faulty program can corrupt the table and crash the whole system. Later processors with protected mode solve this problem by moving the table into a protected structure. In the real mode of the 8086, the safety of the table is left entirely to the programmer.

Common mistake

Thinking of the four bytes of a vector in the order "CS first, then IP". The notation CS:IP writes the segment first and so invites this error. In memory the order is reversed: at address n × 4 is the low byte of IP, and at n × 4 + 2 is the low byte of CS.

5.1.2.2The vector address step by step

It helps to follow the rule in action on an example. Suppose the program is executing INT 10h. The processor finds the vector and switches to the ISR in four steps.

Example 5.1.1

Let us find the vector address for INT 10h, the ISR's CS:IP, and its physical address. Suppose the four bytes of the table starting at address 0000:0040h are, in order, 65 F0 00 F0.

  1. Type number. The second byte of the instruction is the type number: n = 10h = 16.
  2. Vector address. n × 4 = 10h × 4 = 40h (decimal: 16 × 4 = 64). The vector is in bytes 0000:0040h–0000:0043h. In binary, shifting 0001 0000b left by two bits gives 0100 0000b = 40h.
  3. Reading the bytes. At 0040h there is 65h and at 0041h F0h; the low word is IP = F065h. At 0042h there is 00h and at 0043h F0h; the high word is CS = F000h.
  4. Physical address. CS × 16 + IP = F0000h + F065h = FF065h. The ISR starts inside the BIOS ROM in the topmost 64 KB of memory.

The bytes read in the example are shown in Figure 5.1.4. The processor fetches these two words with two separate memory reads. The 8086 reads a word at an even address in a single bus cycle. Because both n × 4 and n × 4 + 2 are even, each word arrives in one cycle. The 4-byte alignment of the vector table is also convenient in this respect.

The physical address calculation in the fourth step is the segmentation rule the 8086 uses for all memory accesses: the 16-bit segment value is shifted left by four bits (multiplied by 16) and the offset is added. The segment CS = F000h starts at F0000h. IP = F065h is a position inside this segment. The result is the 20-bit address FF065h.

There is an important detail about the order here. Before the processor reads the vector and loads CS:IP, it writes the return information to the stack. So while the first instruction of the ISR is fetched from FF065h, the old CS, IP and FLAGS are already on the stack. If this order were broken, that is, if CS:IP were loaded first, the return address would be lost. The exact order of the steps is in Table 5.1.5.

5.1.2.3From table to routine and back

Two-way calculations are done on the vector table. In the first direction one goes from a type number to the address of the vector; this is the multiplication n × 4. In the second direction one finds, from an address in the table, which type's vector it is; this is a division of the address by 4. The second direction is needed when looking at a byte sequence in a memory dump and working out what it is.

Example 5.1.2

In a memory dump the bytes 2E E8 00 F0 are seen starting at address 0000:0058h. a) Which interrupt's vector is it? b) What are the ISR's CS:IP and physical address? c) At which addresses is the vector of type 1Ch in the same table?

  1. a) 58h / 4 = 16h. Because the address is a multiple of 4, it is the start of a vector: type 16h, that is, the BIOS keyboard service INT 16h.
  2. b) Low word: 2Eh, E8h → IP = E82Eh. High word: 00h, F0h → CS = F000h. Physical address F0000h + E82Eh = FE82Eh.
  3. c) 1Ch × 4 = 70h. IP is in bytes 00070h–00071h and CS in bytes 00072h–00073h.

If the address were not exactly divisible by 4, for example 005Ah, it would not be the start of a vector but the CS half of the vector of type 16h (5Ah = 4 × 16h + 2).

The calculation is the same for all types: IP is at n × 4 and n × 4 + 1, CS at n × 4 + 2 and n × 4 + 3. For type 00h the address comes out as 0000h, for type FFh as 03FCh; all addresses in between are multiples of 4.

Common mistake

Mistaking the type number for the address directly (INT 21h → 00021h) or multiplying by 2 instead of 4 (INT 21h → 00042h). The correct value is 21h × 4 = 84h. To avoid slips in hexadecimal multiplication, one way is to convert to decimal first: 21h = 33, 33 × 4 = 132 = 84h.

5.1.3INT and IRET

5.1.3.1The steps of INT n

The INT n instruction is two bytes: the opcode CDh and the type number n. For example INT 21h sits in memory as CD 21. While executing it the processor does a series of things the programmer cannot see. They resemble a procedure call but include more. Table 5.1.5 gives the steps in order.

Table 5.1.5: The steps of the INT n instruction and the effect of each on the stack, registers and bus.
StepOperationEffectBus cycle
1FLAGS is pushed on the stackSP ← SP − 2, [SS:SP] ← FLAGSmemory write
2IF and TF are clearedIF = 0, TF = 0—
3CS is pushed on the stackSP ← SP − 2, [SS:SP] ← CSmemory write
4IP is pushed on the stack (the address of the instruction after INT)SP ← SP − 2, [SS:SP] ← IPmemory write
5vector is readIP ← [0000:n×4], CS ← [0000:n×4+2]two memory reads
6the ISR runs and ends with IRETIP, CS, FLAGS are popped from the stack in that orderthree memory reads

Every row of the table has a reason. Step 1 saves the flags. The result of the interrupted program's last comparison, for example ZF, may change during the ISR. If the program is interrupted between a CMP and a JE and the flags are not saved, JE jumps the wrong way. Saving the flags automatically is therefore essential. The CALL instruction does not save the flags, because the program knows when a procedure will be called.

Step 2 clears IF and TF. IF = 0 prevents the ISR from being interrupted by another maskable interrupt at its very first instruction. TF = 0 prevents the ISR from being stopped step by step by the single-step interrupt. It matters that this clearing is done after FLAGS has been pushed. The copy on the stack carries the old IF and TF values. When IRET restores that copy, IF and TF return to their values from before the interrupt.

Steps 3 and 4 save the return address. Because the ISR may be in another segment, IP alone is not enough; CS is saved too. The IP written to the stack is not the address of the INT instruction itself but the address of the instruction after INT. The processor has already advanced IP by two bytes when fetching INT.

Step 5 reads the vector and loads it into CS:IP. From this moment the first instruction the processor fetches is the first instruction of the ISR. The BIU's prefetch queue is also flushed; the bytes in the queue belonged to the instructions after INT and are now invalid.

A total of 6 bytes, that is 3 words, is written to the stack. The whole of INT n takes 51 clock cycles on the 8086. A significant part of these cycles is spent on five memory accesses: three writes to the stack and two reads from the vector table. Flushing the queue and refetching the first bytes of the ISR also take time.

Definition 5.1.4

IRET (interrupt return) is the return instruction from an interrupt service routine. It pops IP, CS and FLAGS from the stack in that order; SP increases by 2 on each pop. It is a single byte (CFh) and takes 24 clock cycles on the 8086.

IRET reads back in reverse order what INT wrote to the stack. This is natural because the stack works last in, first out: the IP pushed last is popped first, and the FLAGS pushed first are popped last. When FLAGS comes back, IF and TF take their old values too. A program that had IF = 1 before the interrupt therefore continues with IF = 1 after IRET.

Example 5.1.3

Common mistake

Taking the IP pushed on the stack to be the address of the INT instruction itself (0104h in this example). The value pushed is the address of the next instruction (0106h). Otherwise IRET would take the processor back to the INT and the program would enter an infinite loop.

The similarity between INT and a procedure call is obvious: both write the return address to the stack and jump elsewhere. The differences show why ISRs need a separate return instruction. Table 5.1.8 compares the two pairs.

The target address row also gives an important flexibility. The assembler writes the target of a CALL into the instruction, and this value does not change. The new routine does its own work and then jumps to the old vector, so that the old routine runs too.

In the instruction length row, INT being 2 bytes is also an advantage. A far CALL is 5 bytes; calling a BIOS routine with a far CALL means both longer code and a fixed address that depends on the BIOS version. INT 10h, by contrast, is the same two bytes on every BIOS.

5.1.3.4An ISR that ends with RET: code trace

To see the practical consequence of the difference in Table 5.1.8, we trace a deliberately faulty program. The program installs its own ISR on type 61h and calls it with INT 61h, but ends the ISR with a near RET instead of IRET.

org 100h

When the program reaches hlt, there are two problems at once (Figure 5.1.7). First, interrupts are off. HLT stops the processor until an interrupt arrives. Because IF = 0, no request from INTR can wake the processor; only NMI or RESET can. In this small program the processor waits forever. Second, the stack is out of step. If there were a ret instead of HLT, it would take the 0700h at the top of the stack for the return address and jump to 0700:0700. There is no meaningful code to execute there.

Trying to fix the problem with RETF is not enough either. The far return instruction pops IP and CS and increases SP by 4. The 2 bytes of FLAGS still remain on the stack and IF does not return to its old state. The rule is therefore absolute: ISRs always end with IRET.

Common mistake

Writing an ISR inside PROC/ENDP and putting RET at the end out of habit. The assembler does not object, because RET is a valid instruction. The error shows up only at run time, often long after the ISR, as a wrong return address or as interrupts that never come again. The symptom being far from the cause makes this bug hard to find.

5.1.4Exceptions

Exceptions are the way the processor reports to the program the special situations it meets while executing an instruction. The 8086 has two true exceptions: divide error (INT 0) and single step (INT 1). The breakpoint (INT 3) and overflow interrupt (INT 4 via INTO) are really software interrupts called by an instruction. But because both are used for debugging and error trapping, they are treated together with exceptions. Intel's 8086 manual groups these four interrupts, together with INT n, under the heading "internal interrupts".

5.1.4.1Divide error (INT 0)

The DIV and IDIV instructions write the quotient to a fixed-size register. In an 8-bit division the dividend is in AX, the quotient is written to AL and the remainder to AH. In a 16-bit division the dividend is in DX:AX, the quotient goes to AX and the remainder to DX. If the quotient does not fit in the destination register, there is no way to produce a correct result. In this case the processor does not write the result and raises the type 0 interrupt.

Definition 5.1.5

A divide error is the type 0 interrupt that the processor raises when, in a DIV or IDIV instruction, the divisor is zero or the quotient does not fit in the destination register. The destination is AL in an 8-bit division and AX in a 16-bit division.

The second condition in the definition is often overlooked. A divide error can occur even without division by zero.

Example 5.1.4

DIV BL runs with AX = 1000 (03E8h) and BL = 2. What happens? How can the same division be done without an error?

  1. 8-bit division: AX / BL = 1000 / 2 = 500. The quotient is to be written to AL.
  2. AL can hold at most 255. Since 500 > 255, the quotient does not fit. Although the divisor is not zero, the processor raises INT 0.
  3. The solution is a 16-bit division: DX = 0, AX = 1000, BX = 2 and DIV BX. The dividend DX:AX = 0000:03E8h = 1000. The quotient 500 = 01F4h is written to AX and the remainder 0 to DX. AX can hold at most 65,535, and 500 fits easily.

A smaller borderline example: AX = 01FEh (510) / 2 = 255 = FFh fits; AX = 0200h (512) / 2 = 256 does not fit and raises INT 0. These values were verified by running them in emu8086.

The rule can be put briefly: in an 8-bit DIV, if AH ≥ BL, that is, if the high half of the dividend is not smaller than the divisor, the quotient exceeds 255 and the error occurs. In the example AH = 03h and BL = 02h, and since 03h ≥ 02h the error is unavoidable. For a 16-bit DIV the condition is DX ≥ divisor. This check can be made before the division with a CMP.

In the signed division IDIV the limits are the signed range. On the 8086 the quotient of an 8-bit IDIV must lie between −127 and +127; for a 16-bit IDIV the range is −32,767 to +32,767. This limit leaves out the smallest value possible in two's complement (−128 or −32,768). For example, with AX = −128 (FF80h) and BL = 1, IDIV BL finds the quotient −128 and on the 8086 still raises INT 0. Later processors accept this smallest value.

Return address. The IP that the 8086 pushes on a divide error is the address of the instruction after DIV. So IRET resumes the program by skipping the division. Execution continues as if the division had never been done; the destination registers keep their old values. On the 80286 and later processors this behavior was changed, and the address of the faulting instruction itself is pushed. The error routine can then remove the cause and retry the instruction. An error routine written for the 8086 does not have this option; it can only report to the program in some way that the result is invalid.

What does DOS do? When a program starts, the vector of INT 0 points to DOS's own routine. This routine prints "Divide overflow" on the screen and terminates the program. A program can change this behavior by installing its own routine. The simplest form of this is seen in the trace below.

Common mistake

Thinking of a divide error only as "division by zero" and checking only whether the divisor is zero. When the dividend is large and the divisor small, the quotient does not fit in the destination and the same interrupt occurs. Checking before the division both that the divisor is nonzero and that the quotient will fit (AH < divisor for 8 bits, DX < divisor for 16 bits) prevents INT 0 in the first place.

5.1.4.3INTO and the overflow interrupt (INT 4)

In signed addition and subtraction, OF = 1 if the result does not fit in the signed range. The processor does not raise an interrupt by itself in this case; testing OF is the program's job. INTO (interrupt on overflow) makes this test in a single byte.

Definition 5.1.6

INTO is a one-byte (CEh) instruction that calls the type 4 interrupt if OF = 1 and does nothing if OF = 0. It is written immediately after a signed addition or subtraction.

Example 5.1.5

ADD AL, BL followed by INTO runs with AL = 64h and BL = 32h. Then the same operation is repeated with BL = F6h. In each case, what are AL, OF and CF, and is INT 4 called?

  1. 64h + 32h = 96h. In the unsigned reading, 100 + 50 = 150 ≤ 255; there is no carry, CF = 0. In the signed reading, the sum of two positive numbers is +150, which exceeds +127. The top bit of 96h is 1; the result looks like −106. OF = 1 and INTO calls INT 4. AL stays 96h; INTO does not correct the result.
  2. 64h + F6h = 15Ah; AL = 5Ah and CF = 1. In the signed reading +100 + (−10) = +90 is correct; the sum of two numbers of different signs cannot overflow: OF = 0. INTO does nothing. CF = 1 does not affect INTO.

Running the two cases in emu8086 gives the same result: in the first the INT 4 routine runs, in the second it does not.

The cost of INTO is small: with OF = 0 it takes only 4 clock cycles. A program that does signed arithmetic can therefore put an INTO after every important operation and catch overflows in a central routine. In practice, though, DOS does not install a meaningful routine for INT 4. The default vector often points to an empty routine consisting only of IRET. A program that is going to use INTO must install its own INT 4 routine.

Common mistake

Assuming that INTO looks at CF. INTO looks only at OF; an unsigned overflow (CF = 1) does not trigger INTO. A program that works with unsigned numbers catches overflow with JC, not with INTO.

5.1.4.4Single step (INT 1)

The most effective way to find a bug in a program is to execute it instruction by instruction and look at the registers after each one. The 8086 supports this in hardware. While the trap flag TF, bit 8 of the FLAGS register, is 1, the processor raises the type 1 interrupt after every instruction. The INT 1 routine, which is part of the debugger, prints the registers on the screen and waits for the user to press a key. It then returns to the program with IRET, the program executes one more instruction, and the cycle repeats.

There is no instruction that changes TF directly. CLC/STC, CLD/STD and CLI/STI have no counterpart for TF. TF is changed through the stack: FLAGS is pushed, popped into a register, bit 8 is set, and the value is loaded back into FLAGS.

PUSHF
POP  AX
OR   AH, 01h      ; bit 8 = TF
PUSH AX
POPF              ; TF = 1

If FLAGS = F202h at the start, then after PUSHF and POP AX AX = F202h. Bit 0 of AH is bit 8 of FLAGS; OR AH, 01h makes AX F302h. POPF loads this value into FLAGS and TF = 1. To clear TF, the same sequence is written with AND AH, 0FEh.

There is a subtle but important point here. The INT 1 routine is also a sequence of instructions. If every instruction of this routine also raised INT 1 while TF = 1, the routine would interrupt itself forever. What prevents this is the second of the INT n steps: on entering an interrupt, the processor pushes FLAGS on the stack and clears TF. The INT 1 routine runs with TF = 0, so its own instructions are not single-stepped. When the routine returns with IRET, the copy of FLAGS on the stack restores TF = 1 and tracing continues.

The single-step interrupt has the lowest priority of all interrupts (Table 5.1.12). If another request is also waiting at the same instruction boundary, that one is serviced first.

5.1.4.5Breakpoint (INT 3)

Single stepping is too slow for stopping at every instruction of a long program. Often you want the program to run at full speed up to a certain point and stop there. This point is called a breakpoint. On the 8086 breakpoints are set with INT 3.

INT 3 has a special one-byte encoding: CCh. Written in the general INT n form it would be the two-byte CD 03. A debugger sets and removes a breakpoint in four steps:

  1. It saves the first byte of the instruction to stop at and writes CCh in its place.
  2. The program runs at full speed. When that address is reached, CCh, that is INT 3, executes. FLAGS, CS and the address after INT 3 are pushed on the stack; the debugger's INT 3 routine shows the registers.
  3. The debugger writes the saved byte back and decreases the return IP on the stack by 1. The return address then becomes the address where CCh was, that is, where the original instruction starts.
  4. With IRET the original instruction is executed from the beginning, undamaged.

The reason for the one-byte encoding lies in the first step. The shortest instructions of the 8086 are a single byte: INC AX, PUSH BX, CLC and so on. If the two-byte CD 03 were written in place of such an instruction, the second byte would corrupt the first byte of the next instruction. If the program reached that next instruction by a jump, a corrupted instruction would now be executed. CCh, on the other hand, fits in place of the first byte of any instruction and affects only that instruction. Decreasing the return IP by 1 also depends on INT 3 being a single byte.

The "single step" button of emu8086 does the same job inside the emulator. On a real 8086 system, DOS's DEBUG program and similar tools work by installing their own routines on the INT 1 and INT 3 vectors.

Common mistake

Taking the CCh bytes for the program's own instructions when the code of a program running under a debugger is dumped from memory. At addresses where a breakpoint is set, CCh temporarily sits in memory. If the program reads its own code or computes a checksum, it may find a different result under the debugger.

5.1.5Hardware interrupts

5.1.5.1The INTR and NMI pins

External devices send interrupt requests to the 8086 over two pins. The two pins differ in how they are triggered and in how the type number is determined.

INTR (pin 18) is the maskable interrupt request input. It is level-triggered: the processor samples the pin during the last clock cycle of each instruction and sees the request if the pin is 1 at that moment. If IF = 0 the request is ignored; if the pin stays at 1 it is seen as soon as IF = 1. The type number is not fixed inside the processor. When the processor accepts the request, it produces two pulses on the INTA' output (pin 24, interrupt acknowledge) and reads the type number from the data bus. This arrangement makes it possible to connect many devices behind a single INTR pin; each device can be given a different type number.

NMI (pin 17) is the non-maskable interrupt input. It is rising-edge triggered: the 0-to-1 transition of the pin is recorded in a latch inside the processor, so the request is not lost. IF is not consulted; it cannot be turned off with CLI. The type number is always 2, so no INTA cycle is needed and the vector is read directly from 00008h. On the IBM PC, NMI is used to report memory parity errors. Circuits that sense loss of power also use NMI to give the processor a few milliseconds to save important data before the supply fails completely.

Thinking that the vector of NMI is also read with INTA. The INTA cycle is only for INTR. The type of NMI is fixed (2) and the processor does not ask outside for it. In the same way, the types of INT 0, INT 1, INT 3 and INT 4 are fixed and have nothing to do with external hardware.

5.1.5.2The INTR acknowledge sequence

Let us follow step by step the chain of events from the moment a key is pressed to the execution of the first instruction of the keyboard ISR. On the PC the keyboard controller is connected to input IRQ1 of the 8259A.

  1. The keyboard controller activates the IRQ1 line. The 8259A records the request and, if the mask allows, drives the INTR pin to 1.
  2. The 8086 finishes the instruction it is executing. Interrupts are not accepted in the middle of an instruction; the processor samples INTR only at instruction boundaries.
  3. If IF = 0 the request is held off and INTR stays at 1. If IF = 1 the request is accepted.
  4. The processor produces two INTA' pulses. The first tells the 8259A to "get ready". On the second pulse the 8259A puts the type number on data bus lines D0–D7; on the PC this is 09h for the keyboard.
  5. From here on it is the same as INT n: FLAGS, CS, IP are pushed on the stack; IF = TF = 0; CS:IP ← [n × 4], that is, [0000:0024h].
  6. When the ISR has read the key and finished its work, it sends the 8259A an EOI (end of interrupt) and returns with IRET.

The fourth step in Figure 5.1.9 is the only step that separates a hardware interrupt from a software interrupt. The INTA cycle resembles a read bus cycle: the processor puts no meaningful address on the address bus, activates INTA' instead of RD', and takes the byte on the data bus. Between the two pulses, in maximum mode, the LOCK' signal is also held active so that no other bus master can take the bus in the meantime. Once the type number is received, the processor behaves as if there were an INT 09h instruction in the program.

The rule in the second step, that an interrupt is accepted only at an instruction boundary, is the foundation of ISR design. An instruction is never left half done. For example, while ADD [BX], AX reads and writes memory, no interrupt comes in between; the ISR always sees memory either as it was before the instruction or as it is after it. A task done by two separate instructions, however, can be interrupted between the two. This must be kept in mind for data shared by the ISR and the main program.

5.1.5.4The 8259A interrupt controller

The 8086 has a single INTR pin, while the PC has at least six interrupt sources. The chip that gathers these sources onto one pin, sets a priority order among them and gives the processor the right type number is the 8259A.

Definition 5.1.7

The programmable interrupt controller (8259A) is a chip that puts eight interrupt request inputs (IRQ0–IRQ7) into a priority order, masks them, and places the corresponding type number on the data bus during the processor's INTA cycle. On the PC it is at ports 20h and 21h.

Inside the 8259A are three registers, each eight bits wide with each bit corresponding to one IRQ (Figure 5.1.10).

  • IRR (interrupt request register): holds requests that have arrived but have not yet been serviced. When an IRQ line becomes active, the corresponding bit becomes 1.
  • IMR (interrupt mask register): holds one mask bit for each IRQ. If the bit is 1, the request on that line is not passed on to the processor. While IF shuts off the whole INTR input, the IMR shuts off lines one by one. On the PC it is read and written at port 21h.
  • ISR (in-service register): marks the IRQ currently being serviced. During INTA the bit of the selected request moves from the IRR to the ISR. Until the EOI arrives this bit stays 1, and the same or lower-priority IRQs are held off.

The third register's name, ISR, is the same as the abbreviation of interrupt service routine. To avoid confusion, these notes say "ISR register" when speaking of the register.

EOI. The bit in the ISR register does not clear by itself. When the service routine has finished its work, it must tell the 8259A so. This notification is called end of interrupt (EOI). On the PC it is done with two instructions:

MOV AL, 20h     ; non-specific EOI command
OUT 20h, AL     ; to the 8259A's command port

This command clears the highest-priority 1 bit in the ISR register. That the port number and the command value are both 20h is a coincidence. If the EOI is forgotten, the 8259A thinks that IRQ is still in service. The same and lower-priority IRQs never reach the processor again. For example, if the EOI is forgotten in the timer ISR, then because IRQ0 has the highest priority, the keyboard, disk and serial port interrupts all stop. The system appears frozen.

Cascading. Eight inputs are sometimes not enough. 8259As can be cascaded: if a slave 8259A is connected to each input of a master 8259A, the count rises to 8 × 8 = 64 IRQs. The IBM PC/AT connects a second 8259A to input IRQ2 of the master chip. The inputs of the second chip are called IRQ8–IRQ15 and map to types 70h–77h. On the AT, IRQ8 is the real-time clock and IRQ14 is the interrupt of the hard disk.

Common mistake

Reading a 1 bit in the IMR as "interrupt allowed". The IMR is a mask register: 1 blocks, 0 allows. For IF the situation is the opposite: IF = 1 allows. To avoid mixing up the two rules, it helps to read a 1 in the IMR as "masked" and a 1 in IF as "open".

5.1.5.5Masking with the IMR: code trace

Sometimes a program needs to block the interrupt of just one device for a short time. For example, a piece of code that changes the keyboard buffer directly does not want the keyboard ISR to run in the meantime, but wants the timer to keep counting. CLI is too crude here, because it shuts off the whole INTR input. The right tool is the IMR.

org 100h
in  al, 21h        ; read IMR
or  al, 00000010b  ; mask IRQ1
out 21h, al
mov cx, 3          ; critical work
in  al, 21h
and al, 11111101b  ; unmask IRQ1
out 21h, al
ret

The program applies the read–modify–write pattern twice. Only one bit of the IMR is to be changed; the other seven bits are the settings of other programs, the BIOS or the operating system. So the IMR is read first, the wanted bit is set with OR or cleared with AND, and the result is written back. Writing MOV AL, 02h / OUT 21h, AL directly would mask IRQ1, but it would unmask all the other IRQs.

In the trace the initial value of the IMR is taken, as an example, to be B8h: 1011 1000b. In this value IRQ3, 4, 5 and 7 are masked; IRQ0 (timer), IRQ1 (keyboard), IRQ2 and IRQ6 (floppy disk) are enabled.

The difference between the IMR and CLI is plain in this trace. CLI holds off all maskable interrupts; the timer's pulses wait too, and the clock may fall behind. The IMR holds off only the selected device. The price is that access to the IMR takes two IN/OUT instructions and, because it writes to an I/O port, is slower than CLI.

Common mistake

Writing to the IMR without reading it first: MOV AL, 02h and OUT 21h, AL. These two lines mask IRQ1 but unmask IRQ3, 4, 5 and 7. If a device with no ISR installed is connected to those lines, the first request that arrives sends the processor to a meaningless vector.

5.1.5.6When an interrupt is held off

The 8086 accepts an interrupt only at instruction boundaries. In some cases this boundary is deliberately moved forward by one instruction. Table 5.1.15 collects these cases.

After SS is loaded. Moving the stack takes two instructions: MOV SS, AX and MOV SP, 0FFFEh. If an interrupt arrived between the two, the processor would push FLAGS, CS and IP at the address given by the new SS and the old SP. This address is most likely on top of some other data. For this reason the 8086 postpones interrupts by one instruction after every instruction that writes a segment register. For this to work safely, MOV SP must be written immediately after MOV SS.

After STI. STI enables interrupts not immediately but after the instruction following it has finished. This small delay makes two common patterns safe. The first is the STI / IRET sequence at the end of an ISR: a new interrupt cannot arrive before IRET finishes and the stack is emptied. The second is the STI / HLT sequence. The program wants to say "enable interrupts and wait until an interrupt arrives". If an interrupt slipped in between STI and HLT, the ISR would run and return, and HLT would wait needlessly until the next interrupt.

String instructions with REP. A copy of 60,000 bytes with REP MOVSB takes about a million clock cycles. Interrupts cannot be allowed to wait for all that time. The 8086 therefore can interrupt a REP instruction between iterations. The return address pushed on the stack is the address of the REP prefix; SI, DI and CX hold the progress so far. After IRET the instruction restarts and runs for the remaining CX iterations. This scheme has a flaw specific to the 8086: on return from an interrupt the processor remembers only one prefix. If an instruction with two prefixes such as REP ES: MOVSB is interrupted, the segment prefix is lost on return and the copy continues from the wrong segment. For this reason such a line is put between CLI and STI, or written so that no segment prefix is needed.

HLT and WAIT. HLT halts the processor. INTR (with IF = 1) or NMI wakes the processor; the ISR runs and IRET returns to the instruction after HLT. This is the most economical way of writing a main program as "sleep until something happens". WAIT waits for the 8087 coprocessor to finish its work; an interrupt that arrives during this wait is also accepted.

Common mistake

Loading SP first and then SS when moving the stack, or putting another instruction between the two. The postponement protects only the one instruction after the one that writes a segment register. The correct order is MOV SS, AX followed immediately by MOV SP, …; the safest approach is to put these two lines between CLI and STI as well.

5.1.5.7Interrupt latency

When a device requests an interrupt, the ISR is expected to start running at once. In reality this time is not zero and for some devices it is bounded.

Definition 5.1.8

Interrupt latency is the time between the arrival of an interrupt request and the start of the first instruction of the ISR.

Latency has two parts. The first is waiting for the instruction that is running when the request arrives to finish. The second is the acceptance process itself: the INTA cycles, three stack writes, two vector reads and refilling the queue. Table 5.1.16 gives the relevant times.

Example 5.1.6

On a 5 MHz 8086 an INTR arrives just after a 16-bit IDIV has started. What is the worst-case interrupt latency in clock cycles and in µs? What would it be if the processor ran at 8 MHz?

  1. In the worst case the running instruction must finish: IDIV takes at most 184 cycles.
  2. Then the acceptance process: 61 cycles. The total is 184 + 61 = 245 cycles.
  3. At 5 MHz a clock cycle is 1 / 5 MHz = 200 ns. 245 × 200 ns = 49 µs.
  4. At 8 MHz a cycle is 125 ns: 245 × 125 ns ≈ 30.6 µs.

If the program had turned interrupts off with CLI at that moment, the time spent with them off adds directly to this latency. A 100 µs CLI–STI interval raises the worst-case latency to about 149 µs at 5 MHz.

What these numbers mean depends on the device. For the timer interrupt, which arrives 18.2 times per second, 49 µs is negligible; there are 55 ms between two interrupts. A serial port is different. Characters arriving at 9600 bit/s are about 1.04 ms apart, and at 115,200 bit/s about 87 µs apart. With a serial port controller that has a one-character buffer, the ISR must read the previous character before the next one arrives. If the latency plus the ISR's running time exceeds this interval, a character is lost.

This calculation gives directly the two basic rules of ISR writing. First, the CLI–STI interval must be kept short, because this time adds to the latency of all devices. Second, the ISR itself must be kept short. While an ISR runs, IF = 0 and the same or lower-priority IRQs wait until the EOI. A long ISR has the same effect on all the other devices as a long CLI.

The share of the processor an ISR takes can also be computed. Suppose the timer ISR takes 200 clock cycles. Running 18.2 times per second, it spends 200 × 18.2 = 3640 cycles. That is only 0.07% of the 5,000,000 cycles per second of a 5 MHz processor. The advantage of interrupts over polling is clear in this figure.

5.1.6Writing our own interrupt service routine

5.1.6.1Installing a vector: INT 90h

Installing an interrupt service routine takes three jobs: writing the routine, choosing an unused type, and writing the routine's address into that type's vector. The following program does these three jobs in the simplest form and calls its own interrupt once.

org 100h
mov ax, 0
mov es, ax                         ; ES = 0: IVT segment
cli                               ; interrupts off
mov word ptr es:[90h*4], offset isr ; IP
mov word ptr es:[90h*4+2], cs        ; CS
sti                               ; interrupts on
int 90h                           ; our interrupt
ret
isr:
mov ah, 0Eh
mov al, '*'
int 10h
iret                              ; not RET!

Every decision in the program has a reason.

  • Choice of type. 90h is a type that neither the BIOS nor DOS uses on the PC. Its vector is at address 90h × 4 = 240h; IP is at 0000:0240h–0241h and CS at 0000:0242h–0243h.
  • ES = 0. The vector table is in segment 0000h. Since DS points to the program's own data, the table is accessed through ES, with the es: prefix. Because an immediate value cannot be loaded into a segment register, 0 is put into AX first.
  • CLI / STI. The vector is written as two words with two separate MOVs. After the first MOV, the IP half of the vector is new and the CS half is old. If an interrupt of this type arrived at that moment, the processor would jump to a meaningless address. CLI holds off maskable interrupts during this short interval. Since only the program itself calls type 90h, there is no danger in this example; but for hardware types the same pattern is mandatory, and applying it every time a vector is written is a good habit.
  • The end of the ISR. The ISR writes an asterisk to the screen with the BIOS INT 10h teletype service and returns with IRET. Another software interrupt can be called from inside an ISR; with nested interrupts, 6 more bytes are added to the stack for each level.

When the program runs, * is printed on the screen and the program returns to DOS. This short example does not save and restore the old vector. After the program ends, the vector of type 90h keeps pointing to memory into which another program will now be loaded. If another program calls INT 90h, the random bytes there are executed as instructions. The correct form, which saves and restores the old vector, is traced separately below.

Under DOS, instead of writing vectors directly in memory, two DOS services can be used: INT 21h with AH = 25h sets a vector and AH = 35h reads one. These services manage interrupts themselves while a vector is written and make the operating system aware of the vectors. That makes this the safer way. The register layout of the services is given in the notes of Chapter 5.2, Interrupt Functions; here the direct-write method is used to show how the vector table works.

5.1.6.3Save, replace and restore a vector: code trace

What the previous two programs lack is that they change the table and leave it that way. A correct program first saves the old vector and restores it when done. The following program does this for type 3 and also shows how the ISR protects the main program's registers.

The new element in the program is the XCHG instruction. xchg ax, es:[3*4] swaps AX with the word in memory in a single instruction: while the new IP is written to memory, the old IP comes into AX. If the read and the write were done with two separate MOVs, a gap of two instructions would remain between them. With XCHG it is impossible for the new value to be written without the old one being read, or for the old value to be lost before it is read. The old vector is saved in a two-word variable named old_vec. xor ax, ax zeroes AX; it is one byte shorter than MOV but changes the flags: ZF = 1 and PF = 1. That is why FLAGS is F246h in this program.

The type 3 vector before the program is F000:1003h: emu8086 sets the default vector for each type n to F000:(1000h + n) (F000:1000h for type 0). On a real PC this value varies with the BIOS and any debugger that is loaded; the correctness of the program does not depend on it. Common mistake

Forgetting to restore the vector on every exit path of the program. If the program restores only at its normal end, but returns early to DOS in an error case, the vector points to code that is no longer loaded. The next INT 3 or hardware interrupt crashes the system. The restoration code must be placed at a single point through which all the program's exits pass.

5.1.6.4Rules for writing an ISR

The previous traces brought out the rules of ISR writing one by one. Table 5.1.19 collects these rules and the symptoms that appear when they are not followed.

Protecting registers. A hardware ISR can run after any instruction of the program. It cannot be known which register the program is using at that moment. For this reason the ISR pushes every register it uses on entry and pops them in reverse order on exit. There is no need to save the flags; INT and IRET do that themselves. Segment registers must not be forgotten either. If the ISR changes DS to reach its own data, it must save DS too.

A short ISR and a flag variable. Work that takes long is not done inside the ISR. The ISR does only the urgent part: it reads the data from the device, puts it in a buffer and sets a variable to 1. The main program looks at this variable in its loop and does the long work with interrupts enabled. This pattern looks like polling, but what is polled is a variable in memory rather than a slow device, and the ISR has removed the risk of losing data.

Definition 5.1.9

A reentrant routine is one that works correctly even when it is called again before an earlier call has finished, for example because of an interrupt. To achieve this, the routine keeps its persistent state not in fixed memory cells but on the stack or in registers.

Not calling DOS. While running, DOS keeps its internal variables and its own stack in fixed memory areas. If a hardware interrupt arrives while the program is in the middle of an INT 21h call and the ISR calls INT 21h again, the second call overwrites the variables and the stack of the first. When the first call is resumed, the data are corrupted. Because DOS is not reentrant, hardware ISRs do not use DOS services. BIOS services such as INT 10h are often safer in this respect; the example ISRs above use INT 10h for this reason and are called by a software interrupt.

STI inside an ISR. An ISR starts with IF = 0. A long ISR can allow higher-priority hardware interrupts at the start of its work with STI; the 8259A already holds off the same and lower-priority IRQs until the EOI. In this case the ISR itself must also be written to be reentrant, because the interrupt of another device can run another routine in the middle of the ISR and touch the variables the ISR shares.

The skeleton of a typical hardware ISR that applies these rules is as follows. The code is written to show the order of the rules; the lines in the middle change with the device.

isr_irq:
    push ax              ; save the registers used
    push ds
    mov  ax, seg data    ; the ISR's own data segment
    mov  ds, ax
    in   al, 60h          ; get data from the device (example port)
    mov  last_code, al    ; put in the buffer / variable
    mov  ready, 1         ; flag for the main program
    mov  al, 20h          ; EOI
    out  20h, al
    pop  ds               ; restore in reverse order
    pop  ax
    iret                  ; not RET
Common mistake

Putting an EOI in an ISR called by a software interrupt. EOI is only for hardware interrupts coming from the 8259A. If the ISR of a software interrupt such as INT 60h sends an EOI, the 8259A clears the bit of some other IRQ that is in service at that moment, and the interrupt scheme of that device is disrupted.

5.1.7Exercises and solutions

The six exercises in the slides are solved here with their intermediate steps.

1. At which physical addresses is the INT 13h vector located?

13h × 4 = 4Ch (decimal: 19 × 4 = 76). The vector is in bytes 0004Ch–0004Fh. IP is at 0004Ch–0004Dh and CS at 0004Eh–0004Fh.

2. If SP = FFFEh before INT 21h runs, what is SP inside the ISR? What is on the stack?

INT pushes three words, 6 bytes: FFFEh − 6 = FFF8h. At the top of the stack, at [FFF8h], is the return IP; at [FFFAh], CS; at [FFFCh], FLAGS. The copy of FLAGS on the stack carries IF = 1; the FLAGS in the register has IF = TF = 0.

3. With IMR = B8h, write the instructions that also mask IRQ0 (the timer) without changing the other bits. What does the IMR become?

The read–modify–write pattern is used: IN AL, 21h · OR AL, 01h · OUT 21h, AL. 1011 1000 OR 0000 0001 = 1011 1001 = B9h. IRQ3, 4, 5 and 7 stay masked, and IRQ0 is masked too. As long as the timer stays masked the time of day does not advance; for this reason such a mask is kept very short.

4. The vector of type 61h is to be made 0700:0120h. Which bytes are written to which physical addresses?

61h × 4 = 184h. IP is written first, then CS; both are written in little-endian order. 00184h ← 20h, 00185h ← 01h, 00186h ← 00h, 00187h ← 07h. The physical address of this ISR is 07000h + 0120h = 07120h.

5. On a 5 MHz 8086, an INTR arrives just after MUL BX (at most 133 cycles) has started. What is the maximum interrupt latency?

The MUL must finish first: 133 cycles. Then acceptance: 61 cycles. The total is 194 cycles. 194 × 200 ns = 38.8 µs ≈ 39 µs.

6. What problems does an ISR cause by ending with RET instead of IRET?

A near RET pops only IP. CS and FLAGS stay on the stack and SP is off by 4 bytes. Because FLAGS is not restored, IF stays 0 and maskable interrupts are never accepted again. If the ISR is in another segment, CS is also left wrong and the program continues in the wrong segment. The first RET or POP afterwards takes the CS left on the stack for data or a return address. All of these cases are seen in the trace of the ISR that ends with RET.

5.1.8Summary

  • An interrupt makes the processor drop its current work at an instruction boundary, run an interrupt service routine (ISR), and return to where it left off with IRET. The interrupted program does not notice that it was interrupted.
  • In polling the processor keeps asking the device and wastes most of its time; with an interrupt the device alerts the processor when it is ready. The price of interrupts is the vector table, stack and ISR machinery.
  • Interrupts come from three sources: software (INT n, INT 3, INTO), hardware (INTR, NMI) and internal (divide error INT 0, single step INT 1). Once the type number is determined, all three follow the same steps.
  • The interrupt vector table is at 00000h–003FFh: 256 types × 4 bytes. The vector of type n is at address n × 4; the low word is IP, the high word is CS, and both are stored little-endian.
  • INT n: FLAGS is pushed, IF = TF = 0, CS and IP are pushed (SP − 6), CS:IP ← vector. The IP pushed is the address of the instruction after INT. IRET pops IP, CS and FLAGS; IF and TF return to their old values.
  • Ending an ISR with RET shifts the stack by 4 bytes and leaves IF off; RETF does not pop FLAGS either. ISRs always end with IRET.
  • A divide error occurs both when the divisor is zero and when the quotient does not fit in the destination. The 8086 pushes the address of the instruction after DIV. INTO calls INT 4 only when OF = 1. While TF = 1, INT 1 is raised after every instruction; TF is changed through the stack. INT 3 is a single byte (CCh) and is used for breakpoints.
  • INTR is level-triggered, accepted only when IF = 1 and at an instruction boundary; the type number is read from the 8259A on the second INTA pulse. NMI is rising-edge triggered, non-maskable, and always type 2.
  • Priority: divide error / INT n / INTO, then NMI, then INTR, and last single step. On the PC the type of IRQ n is 08h + n; timer 08h, keyboard 09h.
  • In the 8259A, the IRR holds pending requests, the IMR holds the masks (port 21h, bit 1 = blocked), and the ISR register holds the IRQ in service. A hardware ISR sends an EOI at its end: MOV AL, 20h · OUT 20h, AL. The IMR is changed with the read–modify–write pattern.
  • After a load of SS and after STI, an interrupt is postponed by one instruction; string instructions with REP can be interrupted between iterations.
  • Interrupt latency = the remaining time of the running instruction + the acceptance time (61 cycles for INTR). Time spent with interrupts off by CLI adds to latency; the CLI–STI interval and the ISR are kept short.
  • To install your own ISR, an unused type is chosen and the vector is written between CLI/STI (or with INT 21h, AH = 25h). The old vector is saved and restored on exit. The ISR protects the registers it uses and ends with IRET.

5.1.10Test Yourself

  1. In a memory dump the bytes A5 FE 00 F0 are seen starting at address 0000:0020h. Which type's vector is it, and which device does it belong to on the PC? What is the physical address of the ISR?

    Answer

    20h / 4 = 08h: type 08h, that is, the timer interrupt attached to IRQ0. IP = FEA5h, CS = F000h. Physical address F0000h + FEA5h = FFEA5h.

  2. Before the INT 21h at 0700:0200 runs, SP = FFF0h and FLAGS = F246h. At the first instruction of the ISR, what are SP, the three words on the stack, and FLAGS?

    Answer

    SP = FFF0h − 6 = FFEAh. [FFEAh] = 0202h (INT 21h is two bytes), [FFECh] = 0700h, [FFEEh] = F246h. In the FLAGS register IF (bit 9) is cleared: F246h − 0200h = F046h. TF is already 0.

  3. With BL = 2, what does DIV BL give for AX = 01FEh and for AX = 0200h?

    Answer

    510 / 2 = 255 = FFh fits in AL: AL = FFh, AH = 00h. 512 / 2 = 256 does not fit; INT 0 is raised even though the divisor is not zero. A quick check: in the second case AH = 02h ≥ BL = 02h.

  4. With IMR = 00h, what instruction sequence masks the timer and keyboard interrupts together? What is the new IMR? What happens if a key is pressed in the meantime?

    Answer

    IN AL, 21h · OR AL, 03h · OUT 21h, AL; the IMR becomes 03h. The request of the key that was pressed waits in the 8259A's IRR; it is serviced when the mask is lifted.

  5. On an 8 MHz 8086, an INTR arrives just after an IDIV of at most 184 cycles has started. What is the worst-case interrupt latency in µs?

    Answer

    184 + 61 = 245 cycles. At 8 MHz a cycle is 125 ns: 245 × 125 ns ≈ 30.6 µs.

  6. To move the stack, a program writes MOV SP, 0FFFEh first and then MOV SS, AX. Why is this order not safe?

    Answer

    The postponement protects only the instruction after the one that writes a segment register. An interrupt can arrive between the two instructions, that is, after MOV SP. At that moment SP is new and SS is old, and FLAGS, CS and IP are pushed to a wrong place. The correct order is MOV SS first, followed immediately by MOV SP.

  7. A hardware ISR uses BX and DX but pushes and pops only BX. What symptom is seen in the main program?

    Answer

    Because an interrupt can arrive after any instruction of the program, DX changes at moments the main program does not know about. The program usually works correctly, but gives a wrong result in the rare cases when the interrupt arrives exactly while DX is in use. The bug is hard to reproduce and looks random.

  8. A debugger has written CCh in place of a one-byte instruction at address 0150h. Which IP does INT 3 push on the stack? Why does the debugger change this value?

    Answer

    Because INT 3 is a single byte, the IP pushed is 0151h. The debugger writes the saved original byte back to 0150h and decreases the IP on the stack by 1, making it 0150h. After IRET the original instruction is executed from the beginning, undamaged.

  9. A memory parity error occurs while a program has interrupts turned off with CLI. Is the interrupt accepted? From which address is the vector read?

    Answer

    On the PC a parity error is reported through NMI. NMI is non-maskable; it is accepted even when IF = 0. Its type is fixed at 2 and the vector is read from bytes 2 × 4 = 00008h–0000Bh. No INTA cycle is performed.
