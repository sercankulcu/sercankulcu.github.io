Chapter 3.1: Programming Languages

A processor recognizes only bits. Every byte it reads from memory is either part of an instruction or a piece of data, and the flow of the program decides which. A person, on the other hand, thinks “add a and b and store the result in x.” Programming languages were invented to close the gap between these two worlds. These notes climb that gap layer by layer. At the bottom is machine language, which the processor executes directly; we follow, step by step, how a few bytes of 8086 code are fetched and executed from memory. On a small, made-up instruction format we encode and decode instructions by hand. Next come assembly language, the two passes of the assembler, the linker, and the loader. Writing the same “Welcome” program in six different environments shows how strongly assembly code depends on both the processor and the operating system. The last sections divide high-level languages into compiled, interpreted, and hybrid ones. A program that decides whether a number is odd or even is read in fourteen languages and, finally, in 8086 assembly.

3.1.1Software and language levels

3.1.1.1The role of software and its layers

The hardware of a computer does nothing on its own. The processor, memory, and input/output units are ready to work the moment power is applied, but they do not know what to do or in what order. Software supplies that knowledge. Software is the body of instructions and data that makes the hardware work correctly, in coordination, and in the desired way. In an electronic circuit a control unit determines the sequence of signals; in a computer, the program in memory determines that sequence.

The most fundamental piece of software is the operating system. The operating system manages the hardware: it shares memory among programs, arbitrates access to the disk and the screen, and keeps concurrently running programs from corrupting one another. Application programs do not touch the hardware directly; when they want to open a file or write text to the screen, they ask the operating system for a service. Such a request is called a system call, and we will see its details in the “Welcome” programs. The operating system in turn reaches the hardware through drivers, which know the device-specific details.

Figure 3.1.1 shows this arrangement as four layers. The user is at the top and the hardware at the bottom. Each layer uses only the services offered by the layer immediately below it. Applications such as a browser, a compiler, or a game use the operating system, and the operating system uses the processor, memory, and input/output units.

Programming languages are used to write applications, operating systems, and drivers. A programming language is an artificial language, with precisely defined rules, for describing a task step by step. Today there are hundreds of them. Some target operating systems, some numerical computation, some web pages. The history of languages also mirrors the history of computer technology. The first computers were programmed with wires and switches. As memories grew and processors got faster, languages appeared that shifted the programmer's burden onto the machine.

3.1.1.2Three language levels

Programming languages fall into three levels according to how close they are to the hardware. Figure 3.1.2 stacks these levels; as we move up, abstraction increases, that is, the programmer sees fewer of the hardware's details.

Definition 3.1.1

Machine language consists of the binary instructions that the processor executes directly, with no translation. Assembly language writes each machine instruction with a memorable name such as MOV or ADD, that is, a mnemonic. An assembly line usually corresponds to a single machine instruction. A high-level language is written with variables, expressions, loops, and functions, independently of the processor's instructions; one line usually turns into several machine instructions.

High-level languages split further into two groups. In compiled languages (C, Rust, Go) the source code is translated entirely into machine language before the program runs. The resulting file runs directly on the processor. In interpreted languages (Python, Ruby) the source code is read and processed at run time by a program called an interpreter. The examples in the figure show the distinction: the line MOV AL, 5 is assembly language, and its equivalent, the bits 1011 0000 0000 0101, is machine language.

As the level rises, three things change together. The first is readability. Anyone who reads the line x = a + b understands what is being done; decoding the machine code for the same job requires an instruction table. The second is portability. A program written in C can be compiled for x86 as well as for ARM, whereas 8086 machine code runs only on the 8086 family. The third is direct control, and it moves the opposite way. In a high-level language the compiler decides which register holds a variable and which jump instruction builds a loop. The assembly programmer chooses every register, every flag, and every memory access personally. For hardware-near work such as device drivers, interrupt handlers, or bootloaders, this control is necessary.

For an electrical and electronics engineer, these levels can be thought of through a familiar analogy. Machine language is the bit patterns applied to the control inputs of a digital circuit. Assembly language is a symbol list that gives those patterns names. A high-level language resembles describing behavior in a hardware description language and leaving the details to the synthesis tool. The job is the same at every level; what changes is who fills in the details.

3.1.1.3The same operation at three levels

The best way to see the difference between the levels is to write the same job at all three. The job is simple: add the variables a and b and store the result in the variable x. All three variables are 16-bit integers.

In C this job is a single line:

x = a + b;

This line does not say where the variables live in memory or in which register the addition is performed. Those decisions are left to the compiler. In 8086 assembly language the same job takes three lines:

MOV AX, [a]     ; load a into AX
ADD AX, [b]     ; AX = AX + b
MOV [x], AX     ; store the result in x

Here everything is explicit. The addition is done in the AX register. The square brackets mean the contents of the memory cell at the variable's address. On the 8086, two memory operands cannot be used together in one instruction. For that reason a is first brought into a register, then b is added, and finally the result is written back to memory. Each line is a single machine instruction.

In machine language only bytes remain. Let the variables' addresses be a = 0200h, b = 0202h, and x = 0204h. The suffix “h” indicates that the number is written in hexadecimal. The assembler translates these three lines into the following bytes:

A1 00 02        ; MOV AX, [0200h]
03 06 02 02     ; ADD AX, [0202h]
A3 04 02        ; MOV [0204h], AX

The first byte of each instruction is the opcode: it tells the processor which operation to perform. A1 means “load the memory word into AX,” and the address follows immediately. A3 is its opposite: “store AX to memory.” These two are short forms specific to AX. 03, by contrast, is a general addition instruction: “add a register or a memory word to a 16-bit register.” Which register and which memory cell is determined by the second byte, called the ModR/M byte. 06 = 00 000 110b; the middle 000 encodes AX, while the outer 00 and 110 encode the case “the address is given directly inside the instruction.”

The order of the address bytes looks reversed at first glance: the address 0200h is written as 00 02. The 8086 stores multi-byte numbers in memory low byte first (little-endian). The low byte of 0200h is 00h and the high byte is 02h; 00h comes first, then 02h. The same rule applies to data: if a = 0015h, then address 0200h holds 15h and address 0201h holds 00h.

Common mistake

A common mistake is to read the address bytes in machine code in the order they are written. The address in the instruction A1 00 02 is 0200h, not 0002h. On the 8086, every 16-bit number inside an instruction, whether an address or a constant, is written low byte first. When you read a word in a memory dump, the second byte is likewise the high byte.

3.1.1.4Code trace: x = a + b in memory

To trace how these three instructions run in memory, let us put them into a small COM program. A COM program is the simplest executable file type, used by emu8086 and DOS. Code, data, and stack live in the same 64 KB segment; the program starts at offset 0100h of the segment.

org 100h
mov ax, [0200h]   ; A1 00 02
add ax, [0202h]   ; 03 06 02 02
mov [0204h], ax   ; A3 04 02
ret               ; C3

org 100h is a directive: it generates no machine code and only tells the assembler that the first byte will be placed at address 0100h. The code is the 11 bytes in the range 0100h–010Ah: the three instructions take 3 + 4 + 3 = 10 bytes, and ret takes 1 byte. Let a = 0015h (21) and b = 0027h (39) initially; the value of x is unknown.

The processor handles each instruction in two phases. In the fetch phase the instruction bytes are read from the address IP points to, and IP advances by the instruction length. In the execute phase the opcode is decoded and the work is done. On the 8086 these two phases are divided between two separate units. The bus interface unit (BIU) reads instruction bytes from memory and fills a six-byte instruction queue. The execution unit (EU) takes bytes from this queue, decodes them, and executes them. If the bus is idle while the execution unit is working, the BIU prefetches the next bytes. The trace table shows the two phases on separate rows, but in a real processor the execution of one instruction and the fetching of the next can overlap in time.

In step 1, IP = 0100h. When the processor reads the byte A1, it learns that the instruction is three bytes long; the following bytes 00 02 form the address. The address is read little-endian: 0200h. IP advances to 0103h. In step 2 the execution unit asks for a word at address 0200h of the data segment. The BIU reads the 15h at 0200h and the 00h at 0201h; AX becomes 0015h. This read is a real bus cycle. The 8086's data bus is 16 bits wide and 0200h is an even address. The two bytes of the word therefore arrive in a single bus cycle, that is, in at least four clock periods. Had the word been at an odd address, two separate cycles would have been needed.

In step 3 the four-byte 03 06 02 02 is fetched. 03 carries the addition operation, 06 the information “destination AX, source direct address,” and 02 02 the address 0202h. In step 4, 0027h is read from 0202h and added to AX in the arithmetic logic unit: 0015h + 0027h = 003Ch, which is 21 + 39 = 60 in decimal. The addition also updates the flags: since the result is nonzero, ZF = 0; since the most significant bit is 0, SF = 0; and since there is no carry out, CF stays 0.

In step 5, A3 04 02 is fetched, and in step 6 AX is written to memory. The write is also done low byte first: 3Ch goes to address 0204h and 00h to address 0205h. Now x = 003Ch = 60. The byte C3 in step 7 is the RET instruction; the COM program hands control back to the system that ran it. Figure 3.1.3 shows three moments of this trace.

This trace shows what a single line of C turns into in hardware. The line has become three instructions and ten bytes of machine code. To these are added three data accesses and the bus cycles that fetch the instruction bytes. The timing table in the 8086 user's manual also gives the durations of these instructions. Loading memory into AX takes 10 clock periods. Adding a memory word to a register with direct addressing takes 9 + 6 = 15, and writing AX to memory again takes 10. Since one clock period is 200 ns on a 5 MHz 8086, these three instructions take about 35 × 200 ns = 7 µs. Periods spent waiting for fetches when the instruction queue runs empty may be added to these times.

Example 3.1.1

What happens to x and the flags if the same program is run with a = 7FFFh and b = 0001h?

The addition gives 7FFFh + 0001h = 8000h. Memory receives 0204h ← 00h and 0205h ← 80h. The result is not zero (ZF = 0). Because the most significant bit is 1, SF = 1. In unsigned addition there is no carry out of 16 bits (CF = 0). Viewed as signed numbers, however, the sum of two positives appears negative: +32767 + 1 yields −32768. This is a signed overflow and OF = 1. The processor merely records the overflow in the OF flag and carries on. C does not report signed overflow by itself either; the language standard treats this case as undefined behavior. Checking for overflow is the programmer's job.

3.1.2Machine language

3.1.2.1The only language the processor understands

Machine language is the lowest-level language, made of 0s and 1s. The processor's control unit decodes the bit pattern it reads from memory and drives the registers, the arithmetic logic unit, and the data bus accordingly. This decoding is done by decoder circuits: a given opcode activates given control lines. Machine language is therefore entirely dependent on the processor and the hardware. Machine code written for one processor family is meaningless to the decoder of another family, or does something completely different.

ENIAC (1945), one of the first general-purpose electronic computers, did not work with a program loaded into memory. The program was set up on the hardware by plugging cables between units and setting switches. Rewiring for a new problem could take days. The idea of placing the program in memory like data solved this problem. The instructions in memory were now numbers, and the language of those numbers was machine language.

Today every processor family has its own machine language, in other words its own instruction set. Machine language is impractical to read and write, so programmers do not use it directly. Even so, a microprocessor engineer must be able to decode machine code. Reading a memory dump, making sense of the bytes on a bus with a logic analyzer, or checking what a compiler produced all rest on this skill.

Figure 3.1.4 shows how the job “load 5 into register AL” is encoded in two different machine languages. On the 8086 the job takes two bytes: B0 05. The upper four bits of the first byte, 1011, specify the “load a constant into a register” instruction. The next bit, w = 0, says that the operation is 8 bits wide. The last three bits, 000, select the destination register; among the 8-bit registers, 000 is AL. The second byte is the constant itself: 00000101 = 5. Had the same instruction been written for the 16-bit AX, w would be 1 and the constant would take two bytes: MOV AX, 5 = B8 05 00.

On ARM processors, by contrast, every instruction is 32 bits long. The instruction MOV r0, #5 is translated into the word E3A00005. The top four bits of this word, 1110, are the “always execute” condition. The following fields encode that the instruction is a data-processing instruction, that the operation is MOV, that the destination register is r0, and the lowest eight bits hold the constant 5. For the same job the 8086 uses two bytes and ARM four. The position and meaning of the fields are completely different as well. This difference explains with a single example why 8086 code does not run on an ARM processor.

This dependence of machine language is softened by assembly languages. Assembly language is also tied to the processor, but it spares the programmer from fiddling with bit fields and makes programming friendlier.

3.1.2.2A sample instruction format

The instruction set of a real processor contains hundreds of instructions and dozens of formats. To see the main idea of machine language, it suffices to design a much smaller, made-up processor. Let this processor have four registers (R0–R3) and let every instruction be 8 bits. Figure 3.1.5 shows the fields of the instruction.

Definition 3.1.2

The instruction format is the layout that specifies into which fields the bits of a machine instruction are divided and what each field encodes. The opcode field specifies the operation to perform, and the operand fields specify which register, memory cell, or constant the operation acts on.

In the sample processor the meaning of an instruction always follows one pattern: destination ← destination operation source. The result is written to the destination register; the source register does not change. Registers are encoded with two bits: R0 = 00, R1 = 01, R2 = 10, R3 = 11. Two bits are exactly enough to tell four registers apart. The opcodes are given in Table 3.1.2.

Table 3.1.2: Opcodes of the sample processor.

0001ADDdest ← dest + src
0010SUBdest ← dest − src
0011ANDdest ← dest AND src (bitwise)
0100ORdest ← dest OR src (bitwise)

Because the opcode field is 4 bits, at most 24 = 16 different operations can be defined. This design uses only five; the remaining eleven codes are free for instructions added later. The width of a field determines how many things it can select: a field of k bits selects one of 2k things. Conversely, selecting one of n things takes at least ⌈log2 n⌉ bits.

An example instruction: 0001 10 11. The first four bits 0001 = ADD, the next two bits 10 = R2 (destination), and the last two bits 11 = R3 (source). The instruction is ADD R2, R3 and performs R2 ← R2 + R3. In hexadecimal this byte is 1Bh. The convenience of hexadecimal shows here: the first hex digit is directly the opcode, and the second digit carries the destination and source fields together.

3.1.2.3Encoding and decoding instructions

Translating an assembly line into machine code is called encoding, and recovering an assembly line from a byte is called decoding. The assembler does the first; the disassembler and the processor's decoder do the second. The way to decode is to split the bits into their fields. Table 3.1.3 splits a four-instruction program into its fields.

Example 3.1.2

Let us encode SUB R2, R0 and decode the byte 4Dh.

The opcode of SUB is 0010, R2 = 10, R0 = 00. Written side by side, the fields give 0010 1000, which is 28h in hexadecimal. If R2 = 12 and R0 = 5, the instruction performs R2 ← 12 − 5 = 7, and R0 is unchanged.

4Dh = 0100 1101. The opcode 0100 = OR. The remaining four bits are 11 01: destination R3, source R1. The byte is the instruction OR R3, R1 and performs R3 ← R3 OR R1. If R3 = 1010 and R1 = 0011, the result is 1011 = 11.

This small processor also carries the basic working cycle of the 8086: fetch, advance PC, decode, execute, write the result.

3.1.2.5Pros and cons of machine language

The pros of machine language come from its closeness to the hardware. No translation is needed; the processor runs the code as it is. The programmer has full control over the hardware: which byte is written where and which instruction comes in what order are all their decisions. Written well, this is also how the smallest and fastest code is obtained.

The cons are heavy. Machine code is unreadable, and it is very hard to write and debug. A single wrong bit turns an instruction into another one; if 0011 0001 is written instead of 0001 0001 (ADD R0, R1), the addition becomes an AND. The code is not portable either. The program has to be rewritten from scratch for every processor.

Perhaps the most annoying problem is computing addresses by hand. Jump instructions carry the address of the target. When an instruction is inserted in the middle of the program, the addresses of all the following instructions shift, but the addresses inside the jump instructions stay as they were. Figure 3.1.6 shows this situation.

The programmer must then find and fix all the jump addresses again. In a large program this takes a long time and is error-prone. To solve these problems, assembly languages (1950s) were developed first, followed by high-level languages such as FORTRAN (1957). In assembly language a jump target is written as a label; the assembler recomputes its address every time.

Common mistake

A common mistake is to mix up the order of the fields in the instruction format. In the sample processor the destination field comes before the source: 0010 11 00 is SUB R3, R0 and performs R3 ← R3 − R0. If the fields are read in reverse, SUB R0, R3 results; because subtraction is not commutative, the result is written to a different register with a different value.

3.1.3Assembly languages and the assembler

3.1.3.1Mnemonics

The first gain of assembly language is names. The programmer writes MOV AL, 5 instead of 10110000 00000101. MOV is a mnemonic: as an abbreviation of the word “move,” it reminds you what the instruction does. AL is the name of a register, and 5 is a constant written in decimal. The program that translates this line into machine code is called an assembler. Figure 3.1.7 shows what the translation does for a single line.

Assembly language is designed separately for each processor architecture and instruction set. Intel x86, Motorola 68000, ARM, PIC, and AVR processors each have their own assembly language. The register names and instructions valid in one are absent in another. Within a processor family, however, compatibility is preserved. An assembly program written for the 8086 can, with small differences, also be assembled and run on the 80286, 80386, and today's x86 processors. Assembly languages specific to microcontrollers are still widely used in embedded systems and electronics applications.

Assembly language remains important today, when high-level languages are widespread, for three reasons. First, some code can be written only in assembly. The bootloader that runs first when a computer powers on, interrupt handlers, the hardware-touching parts of device drivers, and the context-switching parts of an operating system kernel are of this kind. Second, the way to understand how a processor really works runs through assembly. Why a program crashed, what the code shown by a debugger does, or examining software by reverse engineering all require reading assembly. Third, performance. Special instructions that the compiler cannot generate by itself, such as SIMD or cryptographic instructions, and time-critical loops are still written by hand.

3.1.3.2From source code to a running program

The text file the programmer writes is called source code. Three tools take part on the way from source code to a running program. Figure 3.1.8 shows this toolchain.

Assembler
Reads the source file (prog.asm) and translates each line into machine code. Its output is an object file (prog.obj or prog.o). The object file contains machine code but is not yet complete. The addresses of functions defined in other files are left blank, and these blanks are recorded in a list. MASM, NASM, TASM, and GNU as are tools that do this job.
Linker
The linker combines one or more object files and libraries (.lib, .obj). It fills in the blank addresses and produces an executable file (prog.exe) in a form the operating system understands. Microsoft's LINK and GNU's ld are common linkers.
Loader
The loader is a part of the operating system. It copies the executable file from disk into memory, sets up the segment registers and the stack, adjusts addresses to where the program was loaded if necessary, and hands control to the program's first instruction.

The assembler has one more output: the listing. The listing writes, next to each source line, that line's address and the machine code it produced. The listing of a small DOS program that prints “Welcome!” on the screen is as follows:

The db (define byte) directive on the last line produces data, not an instruction: the ASCII codes of the characters “Welcome!$” sit one after another in memory. The listing is used both to check what the assembler produced and to match addresses with source lines in a debugger. emu8086 performs all of these steps with a single key and produces the COM or EXE file directly.

3.1.3.3The assembler's two passes

There is an interesting situation in the listing above. The line mov dx, offset msg is the second line, but the label msg is defined at the very end. When the assembler reaches this line, it does not yet know the address of msg. Referring to a label before its definition is called a forward reference. Assemblers solve this problem by reading the source code twice.

Definition 3.1.3

A two-pass assembler reads the source code from start to end twice. In the first pass it computes how many bytes each line takes and advances the location counter (LC). It also writes each label into the symbol table with the current LC value. In the second pass it produces the machine code using the addresses in the symbol table.

The location counter holds the address in memory where the next byte will be placed. In the source it can be read with the $ sign. There is an important condition for the first pass: the length of every instruction must be computable without knowing the value of the operand. That mov dx, offset msg is 3 bytes is known whatever the value of msg turns out to be. The program being traced is this:

The two-pass structure also solves the address-shifting problem of machine language by itself. If the programmer inserts an instruction, the assembler recomputes the addresses of all labels at the next assembly and writes the new addresses into the jump instructions.

Common mistake

A common mistake is to take directives for instructions. org, db, equ, and offset are not processor instructions; they are information given to the assembler. org 100h produces no bytes and only sets the location counter. db produces data, not an instruction. If the processor reaches the bytes of a db line as if they were instructions, it tries to decode them as instructions too; this is why data is placed after the code.

There is more than one assembler for the same x86 processor, and they do not all follow the same rules. The rules that govern how an assembly line is written are called syntax. Two main syntaxes are used for x86: Intel and AT&T. Table 3.1.6 summarizes the common assemblers.

The most important difference between the two syntaxes is the order of the operands. In Intel syntax the destination is written first and then the source. In AT&T syntax the order is reversed: source first, then destination. The same two instructions look like this in the two syntaxes:

; Intel:  destination, source
mov eax, 5
add eax, [ebx+4]

# AT&T:  source, destination

In AT&T syntax, register names are prefixed with % and constants with $. The operand size is indicated by the letter at the end of the instruction: b means 8, w 16, and l 32 bits. A memory operand is written as offset(base) instead of with square brackets: 4(%ebx) is the same address as [ebx+4] in Intel syntax. The comment character differs too: assemblers with Intel syntax use ;, while GNU as uses # on x86. Both notations give the processor the same bytes. The difference is only in the text a human reads.

Common mistake

A common mistake is to read AT&T code produced by a compiler with Intel conventions. The instruction subl %ebx, %eax does not subtract EAX from EBX; it performs EAX ← EAX − EBX, that is, Intel's sub eax, ebx. By default gcc and clang produce AT&T syntax; the -masm=intel option switches the output to Intel syntax.

3.1.4“Welcome” in different environments

A program that prints a short text on the screen is the smallest complete example of a language or an environment. In this section the same job is done in six environments: 32-bit Linux, DOS, Windows, the Motorola 68000-based Amiga, ARM, and PowerPC. All the programs follow the same three steps: define the text in memory, ask the operating system for the service “write this many bytes at this address to the screen,” and terminate the program. The differences lie in how each environment expresses these three steps.

3.1.4.1Linux, x86 (32-bit)

The first program runs on a 32-bit x86 processor under the Linux operating system and is assembled with NASM. The 16-bit registers AX, BX, CX, and DX of the 8086 were widened to 32 bits starting with the 80386; their 32-bit names are EAX, EBX, ECX, and EDX. AX is the lower half of EAX.

section .data
hello  db 'Welcome, Linux!', 10
len    equ $ - hello     ; = 16 bytes
section .text
global _start
_start:
  mov eax, 4     ; sys_write
  mov ebx, 1     ; stdout
  mov ecx, hello ; string address
  mov edx, len   ; byte count
  int 0x80       ; call the kernel
  mov eax, 1     ; sys_exit
  xor ebx, ebx   ; exit code 0
  int 0x80

The program consists of two sections. section .data opens the section where data lives, and section .text the section where code lives. The label hello marks the start address of the text; db places the bytes of the text and, at the end, 10, the newline character. The line len equ $ - hello occupies no memory. equ gives a name a constant value; $ is the current location counter. Subtracting the start address of the text from the location counter gives the length of the text. “Welcome, Linux!” is 15 bytes; with the newline it is 16 bytes. Having the assembler compute the length instead of counting by hand prevents an error when the text changes.

Common mistake

A common mistake is to write the length by hand and then change the text. Had len been written as 15, the newline would not be printed and the next output would be appended to the same line. Had the text been shortened and the length left at 16, the memory bytes after the text would also be printed to the screen. $ - hello prevents both errors. Non-ASCII characters need extra care: in UTF-8, letters such as “ü” take 2 bytes; “Dünya” is 5 characters but 6 bytes.

3.1.4.2The system call

The Linux program did not write to the screen itself; it asked the kernel to do so. In modern operating systems, application programs cannot access the hardware directly. The processor's protection mechanism defines two operating modes. A program running in user mode cannot use input/output instructions and some control instructions. Kernel mode is privileged and open only to the operating system. When an application needs a hardware service, it crosses into the kernel through a controlled gate.

Definition 3.1.4

A system call is the special call by which a program requests a service from the operating system. The program puts the service number and the parameters in specific registers, then hands control to the kernel with a software interrupt or a special instruction. The kernel performs the service, places the result in a register, and returns control to the program.

Figure 3.1.10 shows this path. int 0x80 is a software interrupt. The processor saves the flags and the return address, jumps to the address stored in entry number 80h of the interrupt table, and switches to kernel mode at the same moment. The entry routine in the kernel looks at EAX and calls the corresponding function from the service table. When the service finishes, a special return instruction both returns to the saved address and switches back to user mode.

The 8086 has no protection mechanism and no user/kernel mode distinction; every program can access everything. The interrupt mechanism is nevertheless the same. When executing INT n, the 8086 pushes the flags register, CS, and IP onto the stack and clears the IF and TF flags. It reads the new CS:IP from the interrupt vector table at the very beginning of memory. Each entry is 4 bytes; for INT 21h the entry is at address 21h × 4 = 84h. DOS writes the address of its own service routine into this entry. Table 3.1.8 compares the call paths in different environments.

3.1.4.3DOS, 8086 (COM program)

The third program is in the environment of this course: a COM program running under DOS, assembled with emu8086.

org 100h          ; COM program
mov ah, 09h       ; DOS 09h: print string
lea dx, msg       ; DS:DX = address
int 21h           ; call DOS
mov ax, 4C00h     ; DOS 4Ch: exit
int 21h
msg db 'Welcome, DOS!$'

org 100h declares that the COM program will be loaded at offset 100h of the segment. When loading the program, DOS places a structure called the program segment prefix (PSP) in the first 256 bytes of the segment (0000h–00FFh). The program starts right after this structure. In a COM program all four segment registers point to the same segment: CS = DS = ES = SS. Code, data, and stack are within the same 64 KB.

mov ah, 09h selects DOS service number 09h: “print the string starting at DS:DX and ending with $ to the screen.” lea dx, msg loads the relative position of the label msg into DX (load effective address). Since DS already points to the program's segment, DS:DX is the full address of the string. int 21h calls DOS. DOS prints characters to the screen until it sees $; the $ itself is not printed. mov ax, 4C00h loads 4Ch into AH, that is, the “terminate the program” service, and the exit code 00h into AL. The last int 21h hands control back to DOS.

The letters that follow would also turn into random instructions, and the program would behave unpredictably.

Common mistake

A common mistake is to forget the $ at the end of the string in service 09h. DOS has no other way to know where the string ends. Without $, it prints whatever lies after the code and data in memory until it hits the first 24h byte. You will see meaningless characters, beeps, and cursor jumps on the screen.

3.1.4.4Windows, Win32 API

Windows programs do not make system calls directly. The operating system's services are offered as functions in DLL (dynamic-link library) files. The program calls these functions with the call instruction like an ordinary subroutine. The following program opens a message box on the screen and then terminates the process.

extern MessageBoxA    ; user32.dll
extern ExitProcess    ; kernel32.dll

section .data
msg db 'Welcome, Windows!', 0

section .text
global _start
_start:
    push 0          ; uType = MB_OK
    push msg        ; lpCaption (title)
    push msg        ; lpText (text)
    push 0          ; hWnd = NULL
    call MessageBoxA
    push 0          ; uExitCode = 0
    call ExitProcess

The extern lines say that the names MessageBoxA and ExitProcess are defined elsewhere. The assembler does not know the addresses of these names; it leaves a note in the object file: “let the linker fill this in.” Using the import information of the libraries user32.dll and kernel32.dll, the linker directs the calls to these functions. This time the string ends not with $ but with 0. The Windows API was designed with the C language in mind, and C strings end with a zero byte.

Parameters are passed not in registers but on the stack. In C the call has the form MessageBoxA(hWnd, lpText, lpCaption, uType). In assembly the parameters are pushed from right to left: uType first, hWnd last. That way the first parameter lands at the top of the stack, just above the return address, and the function always finds it in the same place regardless of the number of parameters. This program uses the same string for the title and the text; the two push msg instructions push the same address. 3.1.4.5Motorola 68000, Amiga

Amiga computers use the Motorola 68000 processor. The 68000 is a processor of the same period (1979) as the 8086, but its architecture is different. It has eight data registers (d0–d7) and eight address registers (a0–a7); all are 32 bits. Memory is not divided into segments; addresses are linear.

    move.l  4.w,a6         ; a6 = ExecBase
    lea     dosname(pc),a1 ; library name
    moveq   #0,d0          ; any version
    jsr     -552(a6)       ; OpenLibrary()
    tst.l   d0
    beq.s   quit           ; failed → quit
    move.l  d0,a6          ; a6 = DOSBase
    jsr     -60(a6)        ; Output() → d0
    move.l  d0,d1          ; file handle
    move.l  #msg,d2        ; string address
    moveq   #16,d3         ; byte count
    jsr     -48(a6)        ; Write(d1,d2,d3)
    move.l  a6,a1
    move.l  4.w,a6
    jsr     -414(a6)       ; CloseLibrary()
quit moveq  #0,d0          ; return code 0
    rts
dosname dc.b 'dos.library',0
msg     dc.b 'Welcome, Amiga!',10

In AmigaOS, system services are offered as libraries, and each library has a base address. Functions are called through a jump table that sits at negative offsets from this base. At memory address 4 is the base address of exec.library, the core library of the whole system. The first line loads this address into a6. lea dosname(pc),a1 puts the address of the library name into a1. moveq #0,d0 means “any version will do.” jsr -552(a6) jumps to the entry 552 bytes below a6; this entry is OpenLibrary.

On return, d0 holds the base of the opened dos.library. tst.l d0 and beq.s quit leave the program if the library could not be opened (d0 = 0). If it opened, the base is moved into a6. jsr -60(a6) is the Output() function and returns the handle of standard output in d0. The parameters of the Write(d1, d2, d3) call are passed in registers: the handle goes into d1, the address of the text into d2, and the length, 16, into d3. “Welcome, Amiga!” is 15 bytes; with the newline it is 16. jsr -48(a6) does the writing. Finally the library is closed with CloseLibrary (offset -414) and rts is executed with return code d0 = 0.

In 68000 syntax the operand order is like AT&T: source first, then destination. The size is indicated by the suffix .b, .w, or .l at the end of the instruction. Constants are written with #. The library is first opened, used, and then closed. The operating system's resources are managed in this pattern.

3.1.4.6ARM

ARM processors are used today in smartphones, embedded systems, and many laptops. ARM is a RISC (reduced instruction set computer) architecture: its instructions are few, simple, and of fixed length.

    .data
msg:    .ascii "Welcome, ARM!\n"
len = . - msg          @ 14 bytes

    .text
    .global _start
_start:
    mov  r7, #4        @ sys_write
    mov  r0, #1        @ stdout
    ldr  r1, =msg      @ string address
    mov  r2, #len      @ byte count
    svc  #0            @ call the kernel
    mov  r7, #1        @ sys_exit
    mov  r0, #0        @ exit code
    svc  #0

The program is assembled with GNU as. In GNU as, data is defined not with db but with the .ascii directive; \n is the newline. The dot in the line len = . - msg is the location counter, the counterpart of $ in NASM. “Welcome, ARM!” is 13 bytes; with the newline it is 14. The comment character for ARM in GNU as is @.

On 32-bit ARM Linux the service number goes into r7 and the parameters into r0, r1, and r2. The write service is again 4 and exit is 1; although the numbers are the same as on 32-bit x86 Linux, the registers differ. ldr r1, =msg is a special notation. Since ARM instructions are 32 bits, a 32-bit address does not fit inside a single instruction. The assembler stores the address in a literal pool near the code and generates the ldr instruction so that it reads it from there. svc #0 (formerly named swi) hands control to the kernel. On ARM only the ldr (load) and str (store) instructions work with memory. Operations such as addition are performed only on registers. ARM has no instruction that adds directly from memory like add ax, [0202h] on the 8086.

3.1.4.7PowerPC

PowerPC is a RISC architecture developed jointly by IBM, Motorola, and Apple. It has been used in older Macintosh computers, game consoles, and automotive controllers.

    .data
msg:    .ascii "Welcome, PowerPC!\n"
len = . - msg           # 18 bytes

    .text
    .globl _start
_start:
    li   0, 4           # r0 = sys_write
    li   3, 1           # r3 = stdout
    lis  4, msg@ha      # r4 = addr (high)
    addi 4, 4, msg@l    #    + low half
    li   5, len         # r5 = byte count
    sc                  # call the kernel
    li   0, 1           # r0 = sys_exit
    li   3, 0           # r3 = exit code
    sc

PowerPC has 32 general-purpose registers. In GNU as these registers are written as plain numbers: the 3 in the instruction li 3, 1 is register r3. li (load immediate) loads a constant into a register. The service number goes into r0 and the parameters into r3, r4, and r5; the switch into the kernel is made with the sc instruction. The comment character is #. “Welcome, PowerPC!” is 17 bytes; with the newline it is 18.

Loading an address is again a two-step affair. PowerPC instructions are also 32 bits and the constant field is 16 bits. A 32-bit address is split into two 16-bit parts. lis 4, msg@ha loads the upper half into the upper 16 bits of the register; addi 4, 4, msg@l adds the lower half. @ha means “high adjusted.” Because addi adds the lower half as a signed number, if the top bit of the lower half is 1, the upper half is increased by 1 beforehand. This detail is left to the assembler.

3.1.5High-level languages

3.1.5.1Compiled, interpreted, hybrid

A program written in a high-level language must also end up running in the processor's machine language. Languages differ in who does this translation and when.

Definition 3.1.5

A compiler is a program that examines high-level source code as a whole and translates it into machine code before the program runs. An interpreter is a program that reads and executes the source code statement by statement at run time; it produces no separate executable file. Just-in-time (JIT) compilation translates parts of a program into machine code during execution, as they are needed.

In compiled languages the source code is translated into machine language in advance. Because the compiler sees the whole source, most type and syntax errors are caught at compile time. Since there is no translation overhead at run time, the program runs fast. Compilation has two stages: the compiler translates each source file into an object file, and the linker combines the object files with libraries. The output is specific to a particular processor and a particular operating system. An x86 program compiled for Windows does not run on Linux or on an ARM processor.

In interpreted languages the source code itself is distributed and processed by the interpreter at run time. Since there is no compilation step, a change can be tried immediately; working line by line in an interactive shell is possible. The source code is platform-independent: the same file runs on any computer that has the interpreter. The price is twofold. Some errors surface only when the relevant line runs. In addition, analyzing every statement as it runs takes time, so the program is usually slower.

Between the two models there is also a hybrid model (Figure 3.1.12). Java and C# programs are first compiled to a processor-independent intermediate code. In Java this code is called bytecode, in C# it is called IL (intermediate language). A virtual machine runs the intermediate code: the JVM for Java, the CLR for C#. The virtual machine first interprets the intermediate code; it translates frequently executed parts to real machine code with JIT and caches them. This yields both portability and high speed. Today the Python and JavaScript engines also use bytecode and JIT internally; the boundaries are not sharp.

3.1.5.2The compilation process

A program written in C becomes an executable file in five stages. Take as an example the program oddeven.c, which prints whether a number is odd or even. The gcc compiler runs all the stages with a single command, but it also offers an option to stop at each stage.

  1. Preprocessor: replaces the #include lines with the contents of the corresponding header files and expands the names defined with #define. The output is still C code: oddeven.i (gcc -E). The 15-line program grows to thousands of lines once stdio.h is included; with the clang-based compiler used while preparing these notes it came to 1,543 lines.
  2. Compiler: passes the C code through syntax and type checking, then translates it into assembly language: oddeven.s (gcc -S). Most errors are reported at this stage.
  3. Assembler: translates the assembly code into machine code and produces an object file: oddeven.o (gcc -c). In this file the addresses of the printf and scanf calls are still blank.
  4. Linker: combines the object file with code such as printf and scanf from the C library and produces the executable file: oddeven on Linux, oddeven.exe on Windows.
  5. Loader: when the program is run, the operating system loads the file into memory, prepares the stack and the startup environment, and finally jumps to the main function.

The whole job is done with one command: gcc oddeven.c -o oddeven. To see the intermediate assembly code the compiler produces, in Intel syntax, use gcc -S -masm=intel oddeven.c. Reading this output is the most direct way to see which instructions a high-level line turns into. For example, when the loop of the odd/even program is compiled for x86-64 with optimization (-O2), the comparison i % 2 == 0 becomes not a division instruction but test bl, 1. The compiler tests the lowest bit instead of dividing, because the division instruction is much slower. The same trick can be written by hand in 8086 assembly: test cl, 1.

Common mistake

A common mistake is to confuse a compile error with a link error. Misspelling the name printf may cause only a warning in the compiler. The real error shows up in the linker as an “undefined reference,” because no library contains a function with that name. Looking at which tool an error message came from shows at which stage the problem lies.

3.1.5.3Code trace: a loop generated by the compiler

To see how a compiler translates a loop, take a small piece of C:

sum = 0;
i = 10;
while (i > 0) {
    sum += i;
    i -= 3;
}

One equivalent of this fragment that could be generated for the 8086 is as follows:

org 100h
mov bx, 0         ; sum = 0
mov cx, 10        ; i = 10
cond: cmp cx, 0   ; i > 0 ?
jle done
add bx, cx        ; sum += i
sub cx, 3         ; i -= 3
jmp cond
done: mov sum, bx
ret
sum dw ?

The compiler has placed the variables in registers: sum lives in BX and i in CX. At the end of the loop the sum is written to the memory variable sum. The while condition is tested at the top of the loop. There is an important transformation here. The condition in C says “if i > 0, enter the body.” In assembly the condition is inverted: “if i ≤ 0, leave the loop.” The instruction cmp cx, 0 performs the subtraction CX − 0 but does not store the result; it only sets the flags. jle done (jump if less or equal) jumps if the signed comparison says less or equal. This condition holds when ZF = 1 or SF ≠ OF. After the body, jmp cond returns unconditionally to the top.

In this example it matters that the condition is tested with a signed jump. i is an int and can be negative. Had the compiler chosen an unsigned jump, for example jbe, it would have read FFFEh as 65534 and found it greater than 0; the loop would have continued at the wrong place. The variable type in C decides which conditional jump is chosen in assembly. A single C loop has turned into three kinds of instructions: comparison, conditional jump, and unconditional jump. When the same C fragment is compiled and run on a computer, sum also comes out as 22, and the intermediate values (10, 7), (17, 4), (21, 1), (22, −2) are the same.

Common mistake

A common mistake is to forget to invert the loop condition when translating it to assembly. If the C while (i > 0) is written directly as jg body, then in the case where the body is not entered, the flow falls through to the instruction just below the body. The correct pattern is an inverted jump that leaps to the end of the loop when the condition is false, plus a jmp at the end of the body that returns to the top.

3.1.6.1The common task and C

To see the differences between languages fairly, all of them are given the same task. The program reads a number from the user and prints whether each number from 1 up to that number is odd or even. 3.1.7Interpreted languages

3.1.7.1How an interpreter works

An interpreted language has no separate compilation step. The programmer gives the source file directly to the interpreter: python oddeven.py. The interpreter is also an ordinary program running on the processor; it is mostly written in C. Its job is to read the statements in the source code in order and do the work each one asks for. This approach allows rapid development and experimentation. In the interactive shell (REPL, read–eval–print loop) of languages such as Python and Ruby, you type a line and see its result immediately.

The loop in Figure 3.1.14 is the software counterpart of the processor's fetch–decode–execute cycle. The difference is that each step is done by a program instead of hardware. An addition takes a single instruction on the processor but dozens, sometimes hundreds, in an interpreter. The interpreter must first look at the types of the operands, then choose the appropriate addition routine, and then create the result as a new object. This is where the slowness of interpreted languages comes from. Real interpreters do not parse the source code as text each time; they first translate it to bytecode and interpret the bytecode. CPython stores the bytecode it produced in .pyc files, so on the next run it skips the translation too.

Each of the common interpreted languages stands out in a particular area. Python is general-purpose; it is widely used for data science, artificial intelligence, and automation. JavaScript is the language of the web; it runs in the browser and, with Node.js, on the server. Ruby is known for its ease of use and flexibility, especially through the Ruby on Rails web framework.

Python (1991, Guido van Rossum) puts readability first. Blocks are determined not by braces but by indentation. Wrong indentation either gives a syntax error or changes the meaning of the program.

input always returns text. Even if the user types 3, the returned value is the string "3"; int(...) converts it to an integer. range(1, number + 1) produces a sequence of numbers starting at 1, but does not include the upper bound. That is why 1 is added to number. f"{i} is …" is a formatted string (f-string): the value of the expression inside the braces is placed into the text. The program is run with python oddeven.py.

Python is dynamically typed: the type of a variable is determined at run time by the value assigned to it. number is not declared beforehand; the assignment creates it. The job that takes 15 lines in the C version is 6 lines of code here. This is the expressive power of high-level languages. The price is speed: CPython runs the same loop dozens of times slower than compiled C, because on every i % 2 it checks the types and creates new integer objects.

“After warm-up” describes a property of JIT. When the program starts, the virtual machine interprets the code and counts which parts run often. Definition 3.1.6

Being “compiled” or “interpreted” is a property not of a language but of its implementation. Both a compiler and an interpreter can be written for the same language.

C is usually compiled, but C interpreters exist. Python is usually interpreted by CPython, but Cython translates Python-like code to C and compiles it, and PyPy runs it with JIT. Instead of saying “Python is a slow language,” it is more accurate to say “the CPython interpreter is slow.” The language itself is a definition; its speed is determined by the tool that runs it.

3.1.8.2Intermediate code and the stack machine

Intermediate code is the machine language of an imaginary processor that belongs to no real processor. Virtual machines such as the JVM and the CLR define this imaginary processor as a stack machine. In a stack machine, instructions have no operand fields. The operands sit on an operand stack. An instruction takes the top items off the stack, performs the operation, and pushes the result back. Because the number of registers varies from processor to processor, a design without registers makes the intermediate code portable. Mapping this code onto the registers of a real processor is the JIT's job.

For the expression x = (a + b) * c, the intermediate code produced by the compiler is as follows:

// x = (a + b) * c;
iload a      // push a
iload b      // push b
iadd         // add the top two
iload c
imul         // multiply the top two
istore x     // pop into x
return

The parenthesized expression has become an order of operations in the intermediate code: the addition is done before the multiplication because it is written first. Real Java bytecode has the same structure. Only, local variables are referred to not by name but by index. When the following Java method is compiled with JDK 21 and disassembled with javap -c, this code appears:

Both virtual machines are stack machines.

This intermediate code is tied to no processor. The virtual machine either interprets each instruction or translates it with JIT into the machine code of a real processor such as the 8086, x86-64, or ARM. On the 8086 this expression takes a few instructions using registers instead of an operand stack: mov ax, a, add ax, b, imul c, mov x, ax. The “push onto the stack” and “pop from the stack” operations of the stack machine turn into loads into registers and stores from registers on a real processor.

3.1.9The same task in 8086 assembly

3.1.9.1Program and memory layout

Finally, the odd/even task is written in 8086 assembly. The program is assembled in emu8086 as a COM file. Two simplifications keep the task short. n = 3 is written into the code as a constant; it is not read from the keyboard. The numbers are single-digit, so printing a number means printing a single ASCII character.

org 100h
       mov  cx, 1       ; i = 1
again: cmp  cx, 3       ; compare i with n
       ja   done        ; done if i > n
       mov  dl, cl
       add  dl, '0'     ; digit → ASCII
       mov  ah, 02h
       int  21h         ; print DL
       test cl, 1       ; lowest bit
       jnz  odd         ; 1 means odd
       lea  dx, even_m
       jmp  print
odd:   lea  dx, odd_m
print: mov  ah, 09h
       int  21h         ; print string
       inc  cx          ; i++
       jmp  again
done:  ret
odd_m  db ' is odd.',0Dh,0Ah,'$'
even_m db ' is even.',0Dh,0Ah,'$'

The CX register is the loop counter and stands in for i in C. The cmp cx, 3 and ja done at the label again are the inverted form of the C condition i <= n: leave the loop if i > n. ja (jump if above) jumps on “greater” in an unsigned comparison; the jump is taken when CF = 0 and ZF = 0. Since the counter is never negative, an unsigned jump is correct here.

The first four lines of the body print the number. mov dl, cl copies the low byte of the counter into DL. add dl, '0' adds to it the ASCII code of the character '0', that is, 30h. In the ASCII table the digits run in order from 30h to 39h; 1 + 30h = 31h is the character '1'. mov ah, 02h and int 21h are DOS's “print the character in DL” service.

The next two lines are the counterpart of the C test i % 2 == 0. The remainder of division by 2 is the lowest bit of the number. test cl, 1 performs a bitwise AND of CL and 1, does not store the result, and only sets the flags. If the lowest bit is 1, the result is 1 and ZF = 0; if the bit is 0, the result is 0 and ZF = 1. jnz odd (jump if not zero) jumps when ZF = 0. The division instruction (div) can take more than 80 clock periods on the 8086; test takes only a few. Compilers choose the same route.

For an even number the flow continues without jumping: lea dx, even_m loads the address of the even message into DX, and jmp print goes to the common printing code. For an odd number the jump goes to the label odd and the address of the odd message is loaded into DX. The two paths merge at the label print: service 09h prints from the address in DX up to $. The 0Dh, 0Ah at the end of the messages are the carriage return and line feed characters; in DOS both are needed to move to a new line. inc cx increments the counter, and jmp again returns to the condition. ret returns the COM program to DOS.

3.1.10Common mistakes

Common mistake

Confusing an address with its contents. Every service that prints a string asks for the address of the string: DX in DOS, ECX in Linux, r1 on ARM, a value pushed on the stack in Windows. In assembly, the notation mov dx, msg in some assemblers loads not the address but the word at that address. For the address, use lea dx, msg or mov dx, offset msg. Forgetting the & in the C call scanf("%d", &number) is the high-level form of the same mistake.

Common mistake

Not choosing the string-end rule for the environment. DOS service 09h expects $; the Windows API and the C library expect a 0 byte; Linux's write call looks at no terminator and takes the length as a parameter. If $ is put at the end of the string in a Linux program, this character is printed to the screen; in a DOS program, a string ending in 0 runs on until a $ is found.

Common mistake

Putting the data before the code. A COM program starts running at its first byte. If a db line is put right after org 100h, the processor decodes the bytes of the string as instructions. Data is either put after the code, or a jmp at the start of the code jumps over the data.

Common mistake

Mixing up signed and unsigned jumps. After the same cmp instruction, ja/jb make an unsigned comparison and jg/jl a signed one. If ja is used with a counter that can be negative, −1 (FFFFh) is seen as the largest unsigned number and the loop continues on the wrong branch.

Common mistake

Thinking “an interpreted language has no errors.” In an interpreted language the program starts to run, but a syntax or type error in a branch that never runs shows up only when that branch runs. During testing, inputs that run every branch at least once must be chosen.

Common mistake

Not following the calling convention. If, after calling a stdcall function, the caller also cleans the stack with add esp, 16, the stack is cleaned twice. ESP moves up by an extra 16 bytes and the next ret takes the wrong return address. Which convention applies must be read from the function's documentation.

3.1.11Exercises and solutions

The exercises in the slides are solved here with their intermediate steps. The first three exercises use the sample instruction format of Figure 3.1.5: 4-bit opcode, 2-bit destination, 2-bit source; HALT = 0000, ADD = 0001, SUB = 0010, AND = 0011, OR = 0100; R0 = 00, R1 = 01, R2 = 10, R3 = 11.

1. What are the binary and hexadecimal codes of the instructions SUB R3, R0 and OR R0, R2?

The code of SUB is 0010. The destination is R3 = 11 and the source is R0 = 00. Written in order, the fields give 0010 1100. The four-bit groups convert to hexadecimal digits: 0010 = 2, 1100 = C. The result is 2Ch. The code of OR is 0100; the destination is R0 = 00 and the source is R2 = 10. The instruction is 0100 0010 = 42h.

2. Which instruction is 0010 0111? What is the result if R1 = 9 and R3 = 4?

The first four bits 0010 = SUB. The remaining four bits are 01 11: destination R1, source R3. The instruction is SUB R1, R3 and performs R1 ← R1 − R3. R1 = 9 − 4 = 5; R3 stays 4. Binary check: 1001 − 0100 = 0101.

3. How many different opcodes can be defined in this design? How must the instruction format change to raise the number of registers to 8?

The opcode field is 4 bits: 24 = 16 opcodes. Selecting one of eight registers takes log2 8 = 3 bits. The destination and source fields grow to 3 bits each, and the instruction becomes 4 + 3 + 3 = 10 bits. If the instruction is to stay at 8 bits, the register fields take 6 bits and 2 bits remain for the opcode. With 2 bits only 22 = 4 operations can be defined; the five operations of the design would not fit. This is the basic trade-off among instruction length, number of registers, and number of instructions.

4. What happens in a DOS program if the '$' at the end of the string is forgotten?

Service 09h prints every byte starting at DS:DX and stops when it sees a byte with the value 24h. If there is no terminator, the memory bytes after the string are printed too. These bytes may be the program's own code, other data, or random values. Among them, a 07h byte produces a beep, and 0Dh and 0Ah produce cursor movement. Printing continues until the first $ character in memory is met.

5. What would appear on the screen if len were written by hand as 15 in the Linux example?

sys_write writes exactly as many bytes as EDX. The first 15 bytes of the string are the text “Welcome, Linux!”; the 16th byte is the newline. If EDX = 15, the text is printed but the newline is not. The terminal's prompt line comes right after the text, on the same line. On return EAX = 15.

6. Why are the parameters pushed in reverse order in the Windows example? What is ESP right after the call?

In C calling conventions the first parameter must be at the top of the stack, just above the return address. Because the stack grows downward, the value pushed last stays on top; that is why the parameters are pushed from last to first. The function always finds the first parameter at [ESP + 4] and the second at [ESP + 8]. Four push instructions and the return address pushed by call take 5 × 4 = 20 bytes. ESP = 0012FF80h − 14h = 0012FF6Ch.

7. Why can Java not be classified in a single word as “compiled” or “interpreted”?

Java source code is compiled with javac, but the output is bytecode, not machine code. This bytecode is first interpreted in the JVM; its frequently running parts are compiled to machine code with JIT at run time. The program is both compiled in advance and interpreted and recompiled while running. That is why Java is an example of the hybrid model. Moreover, the compiled/interpreted distinction is a property of the implementation, not of the language: there are also tools that compile Java ahead of time directly to machine code.

3.1.12Summary

  • Software manages the hardware. The operating system is the fundamental software; applications reach the hardware through its system calls. Programming languages are used to develop software.
  • Languages are at three levels: machine language, assembly language, and high-level languages. As the level rises, readability and portability increase and direct control over the hardware decreases.
  • Machine language is the only language the processor understands: binary instructions made of opcode and operand fields. It depends entirely on the hardware; B0 05 on the 8086 and E3A00005 on ARM do the same job. The 8086 stores multi-byte numbers low byte first.
  • In an instruction format, a field of k bits encodes one of 2k alternatives. Decoding an instruction means splitting the bits into their fields and reading each field from a table.
  • Assembly language writes machine instructions with mnemonics. The assembler translates source code into an object file, the linker turns object files and libraries into an executable file, and the loader places the program in memory. A two-pass assembler fills the symbol table in the first pass and produces the bytes in the second.
  • Assembly code depends on both the processor and the operating system: int 0x80, int 21h, a DLL call, jsr, svc, sc. Service numbers, parameter registers, and string-end rules change with the environment.
  • Compiled languages (C, C++, Go, Rust, Fortran, Ada) are translated to machine code in advance: they are fast, but the output is platform-specific. Interpreted languages (Python, Ruby, PHP, Perl, MATLAB) are processed while running: they give fast development and portable source, but run more slowly. Java and C# sit between the two with intermediate code + JIT; JavaScript engines use JIT too.
  • Intermediate code is the language of a stack machine that uses no registers; operands are taken from the stack and results are put on the stack.
  • High-level while, for, and if constructs are realized in assembly as compare + conditional jump; the condition is usually inverted. Whether a variable is signed or unsigned determines which jump instruction is chosen.

3.1.14Test Yourself

  1. In the sample instruction format, addresses 0, 1, and 2 hold the bytes 13h, 2Ch, and 00h in that order. Initially R0 = 2, R1 = 0, R2 = 5, R3 = 9. What are the registers at HALT?

    Answer

    13h = 0001 00 11: ADD R0, R3 → R0 = 2 + 9 = 11. 2Ch = 0010 11 00: SUB R3, R0 → R3 = 9 − 11 = −2; in an 8-bit register, in two's complement, 1111 1110 = FEh. 00h: HALT. Result: R0 = 11, R1 = 0, R2 = 5, R3 = FEh (−2). The second instruction uses the value of R0 left by the first.

  2. On the 8086 the instruction mov ax, [0300h] is encoded as A1 00 03. If address 0300h holds 34 and address 0301h holds 12, what is AX? What would change on the data bus if the instruction read a word from address 0301h?

    Answer

    Because the low byte is stored first, AX = 1234h. 0301h is an odd address. The 8086's 16-bit data bus can read in one cycle only a word that starts at an even address. A word at an odd address arrives with two separate byte reads, that is, two bus cycles. The result is the same, but the access takes at least 4 clock periods longer.

  3. Why does the first pass of a two-pass assembler not produce the bytes of the instructions? If all labels were defined before they were used, would a single pass be enough?

    Answer

    In the first pass the addresses of forward references are not yet known; an operand such as offset msg cannot be encoded. This pass only adds up the lengths and fills the symbol table. If all labels were defined before use, every address would be known when needed and a single pass would be enough. But most jump instructions go forward, for example to the end of a loop; this restriction cannot be applied in practice.

  4. In a DOS COM program the line msg db 'Hello$' starts at address 0110h. What is the machine code of the instruction lea dx, msg? How many characters does service 09h print?

    Answer

    emu8086 encodes a direct-address lea dx, … like mov dx, offset …: BA and the little-endian address, that is, BA 10 01 (3 bytes). In MASM the same instruction would be 8D 16 10 01. Service 09h prints the 5 characters of the word “Hello”; the $ is not printed.

  5. What does the sequence mov eax, 1 / mov ebx, 7 / int 0x80 do on 32-bit Linux? With which registers and which instruction is the same job done on 64-bit Linux?

    Answer

    EAX = 1 is sys_exit; the process terminates with exit code 7. On 64-bit Linux the number of the exit service is 60 and it goes in RAX, the exit code in RDI; the switch into the kernel is made with the syscall instruction.

  6. Before a function with two parameters is called under the stdcall convention, ESP = 0012FF40h. What is ESP at the moment of entering the function, and what does [ESP + 8] hold? With which instruction must the function return?

    Answer

    Two push instructions and the return address take 12 bytes: ESP = 0012FF40h − 0Ch = 0012FF34h. [ESP] is the return address, [ESP + 4] the first parameter, and [ESP + 8] the second parameter. To discard the 8 bytes of parameters itself, the function returns with ret 8; on return ESP is 0012FF40h again.

  7. What is the intermediate code of the expression a * (b − c) on a stack machine? For a = 4, b = 10, c = 3, what is the maximum depth of the stack?

    Answer

    iload a, iload b, iload c, isub, imul, istore x. The stack goes through [4], [4, 10], [4, 10, 3], [4, 7], [28], [ ]. The maximum depth is 3; the result is x = 28.

  8. In the 8086 odd/even program, cmp cx, 5 is written instead of cmp cx, 3 and jae is mistakenly used instead of ja. Which numbers does the program print?

    Answer

    jae jumps when CF = 0, that is, when CX ≥ 5. For CX = 1, 2, 3, 4, CF = 1 and the body runs; at CX = 5, 5 − 5 = 0 and CF = 0, and the loop is left. The program prints 1 through 4; 5 is missing. The correct choice is ja: the body must also run on equality.

  9. When a Python program is written with for i in range(1, n):, over which values does it iterate for n = 4? What happens if the same loop is written in Ruby as 1..n and as 1...n?

    Answer

    Python iterates over 1, 2, 3; the upper bound is not included. In Ruby, 1..4 iterates over 1, 2, 3, 4 and 1...4 over 1, 2, 3. Two dots include the upper bound; three dots leave it out.
