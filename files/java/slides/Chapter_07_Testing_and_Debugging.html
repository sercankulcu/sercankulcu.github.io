“Testing is not about finding bugs; it is about making sure the system works as expected.”

Michael Bolton (software testing expert)

“The best way to predict the future is to create it.”

Often attributed to Abraham Lincoln; also to Peter Drucker and Alan Kay

“A bug is just an undocumented feature.”

Anonymous

Testing checks systematically that a program shows the expected behavior. No test suite proves a program correct; it only raises confidence.

Test Levels

Levels of Testing in Software Development

Unit Testing

  • Focuses on individual, independent components (a class, a method).
  • Makes sure each component works correctly on its own.
  • Example: does BankAccount.withdraw() throw an exception when funds are insufficient?

Unit tests: the smallest parts, the most tests, the fastest to run.

Module Testing

  • Tests a module made of related components.
  • Checks the integration and behavior of the components inside it.
  • Example: do the Account, Transaction and Receipt classes transfer money correctly together?

Module tests: related components together.

Sub-System Testing

  • Tests for interface mismatches between sub-systems.
  • Checks communication and data flow between components.
  • Example: do the account and database sub-systems use the same date format?

Sub-system tests: the interfaces where sub-systems meet.

System Testing

  • Tests the interactions between sub-systems as a whole.
  • Checks that functional (what it does) and non-functional (speed, security, usability) requirements are met.
  • Example: with 1000 concurrent users, does a transfer finish in under 2 seconds?

System tests: the whole system, functional and non-functional requirements.

Acceptance Testing

  • Tests the system with real data instead of simulated data.
  • Confirms its real-world usability and performance.
  • Done together with users: alpha testing at the developer's site, beta testing in the user's own environment.

Acceptance tests: can the customer say “I accept this system”?

First: Testing by Hand

Class under test

public class Calculator {
  public int add(int a, int b) {
    return a + b;
  }

  public int multiply(int a, int b) {
    return a * b;
  }

Manual test program

public class ManualTest {
  public static void main(String[] args) {
    Calculator calc = new Calculator();
    System.out.println("2 + 3 = " + calc.add(2, 3));
    System.out.println("2 * -3 = " + calc.multiply(2, -3));
    // Correct? We look at the screen and decide.
  }

Console

Problems with this approach

  • A human eye judges whether the result is right; it gets tired and makes mistakes.
  • When the code changes, everything must be retried by hand.
  • The test code sits in main and is later deleted: the effort is lost.
  • Who will read 100 output lines for 100 methods?
The fix: write the expected value into the code and let the computer compare: automated unit testing.

Unit Testing and JUnit

JUnit

  • JUnit is the most widely used unit testing framework for Java. Tests are ordinary Java methods; JUnit finds them, runs them and reports the results.
  • In Java a unit usually means a class; its tests check the class's methods one by one.
  • JUnit was designed for unit testing but is quite flexible; it is also used for:
    • Module testing: scenarios that involve several classes.
    • System testing: system-level interactions.
  • IntelliJ IDEA, Eclipse, NetBeans, VS Code and Maven / Gradle run JUnit tests directly.

@Test

Tells JUnit the method is a test. It is void with no parameters; no main is needed, and it need not be public.

Expected value first, then the actual result. If they differ, the test fails (✘). import static saves writing the class name.

Unit Testing and JUnit

The Class Under Test: BankAccount

public class BankAccount {
  private double balance;
  public BankAccount(double balance) {
    this.balance = balance;
  }
  public void deposit(double amount) {
    if (amount <= 0) {
      throw new IllegalArgumentException("Invalid amount");
    }
    balance += amount;
  }
  public void withdraw(double amount) {
    if (amount > balance) {
      throw new IllegalStateException("Insufficient funds");
    }
    balance -= amount;
  }
  public double getBalance() {
    return balance;
  }
}

Unit Testing and JUnit

Shared Setup: @BeforeEach

BankAccountTest

class BankAccountTest {
  private BankAccount acct;

  @BeforeEach
  void setUp() {
    acct = new BankAccount(100);
  }

  @Test
  void depositIncreasesBalance() {
    acct.deposit(50);
    assertEquals(150.0, acct.getBalance(), 0.001);
  }

  @Test
  void overdraftThrows() {
    assertThrows(IllegalStateException.class,
      () -> acct.withdraw(500));
    assertEquals(100.0, acct.getBalance(), 0.001);
  }
}
  • The @BeforeEach method runs before every test: each test starts with a fresh account (balance 100).
  • JUnit creates a new instance of the test class for every test method; one test's changes to acct do not affect another.
  • assertThrows runs the code in its second argument and expects an exception of that type. () -> acct.withdraw(500) is a lambda expression: “a piece of code to run”.
  • We also check that the balance is unchanged after the exception.
Test Results
  • ✔ overdraftThrows()
  • ✔ depositIncreasesBalance()
2 tests · 2 passed

Unit Testing and JUnit · Step by step

How Does JUnit Run Tests?

JUnit finds the @Test methods and creates a new test object for the first test. The field acct is still null.

@BeforeEach runs before the test: a new account, balance 100.

JUnit picks the order: overdraftThrows runs first. assertThrows calls the lambda: withdraw(500) throws.

The exception has the expected type: assertThrows passes. The balance is still 100, so the second assertion passes too.

A brand-new test object (#2) for the second test. The old object and its account are no longer used.

@BeforeEach runs again: this test also starts at balance 100.

Act: deposit(50); the balance becomes 150.

Assert: 150.0 = 150.0 (difference ≤ 0.001). Both tests passed, and they ran independently.

ArrayUtils (fixed)

public class ArrayUtils {
  public static int max(int[] arr) {
    int best = arr[0];               // first element
    for (int i = 1; i < arr.length; i++) {
      if (arr[i] > best) {
        best = arr[i];
      }
    }
    return best;
  }
}
Test Results
  • ✔ positiveArray()
  • ✔ allNegativeArray()
2 tests · 2 passed

The maximum now starts from the first element. The test stays for good: if the bug returns, it is caught at once.

Green: after the fix the same tests were run again, and both passed.

Unit Testing and JUnit

Which Values to Test? Boundary Values

public class Grade {
  public static String letterGrade(int score) {
    if (score < 0 || score > 100) {
      throw new IllegalArgumentException("Invalid score: " + score);
    }
    if (score >= 90) return "AA";
    if (score >= 80) return "BA";
    if (score >= 70) return "BB";
    if (score >= 60) return "CB";
    if (score >= 50) return "CC";
    return "FF";
  }
}
  • Bugs cluster at boundaries: > instead of >=, < 100 instead of <= 100…
  • Boundary value analysis: pick both ends of each range (49 / 50, 89 / 90) and the first invalid values (−1, 101).
  • Equivalence classes: 61, 65 and 68 lie in the same range and give the same result; one of them is enough.

A Parameterized Test, Step by Step

class GradeTest {
  @ParameterizedTest

        "60, CB", "89, BA", "90, AA", "100, AA"})

JUnit reads the 8 strings in @CsvSource; each becomes a separate test call.

Row 1: "0, FF" is split at the comma; "0" is converted to an int for score, and "FF" goes to expected.

49: the upper end of FF. Had we written > 48 instead of >= 50, it would fail here.

50: the lower end of CC; with 49 it tests the boundary from both sides.

59: the upper end of CC.

60: the lower end of CB.

89: the upper end of BA.

90: the lower end of AA.

100: the last valid value; if the score > 100 check is right, it returns AA.

Unit Testing and JUnit

What Makes a Good Unit Test: FIRST

F · Fast

Finishes in milliseconds, so thousands can run after every change. No files, network or database.

I · Independent

Does not depend on another test, on test order, or on state left by an earlier test.

R · Repeatable

Gives the same result on every machine, every time: randomness and the clock are under control.

S · Self-validating

The result is ✔ or ✘; no human needs to read the output.

T · Timely

Written with the code (or even before it), not months later.

And readable

A descriptive name, the AAA pattern, one behavior per test. A test documents how the code is meant to be used.

Regression and Automation

Regression Testing

  • Checks that everything that worked before still works after a change. A regression is a step backward: something that worked breaks again.
  • Method: rerun all existing tests after every change.
Tests must be deterministic

Under the same conditions a test must give the same result every time. A test that sometimes passes and sometimes fails (“flaky”) destroys trust.

Tests must be repeatable

Design tests so they can be repeated at different times, on different machines and in different states.

Regression and Automation

Automated Tests

  • Write automated tests instead of testing code by hand.
  • The effort is about the same, but you end up with an automated test.
  • That test can be rerun whenever you like (every build, every change).
  • It is wrong to think that software that worked once needs no more testing: code changes, libraries change, environments change.
  • Continuous integration (CI, e.g. GitHub Actions, Jenkins) runs all tests on a server after every git push; a red test blocks the merge.

Regression and Automation

Test-Driven Development (TDD)

  • Test-Driven Development: write the test before the code.
  • Red: write a test for behavior that does not exist yet; it fails (or does not compile).
  • Green: write the simplest code that makes it pass.
  • Refactor: clean up the code; as long as the tests stay green, the behavior is preserved.
  • Example: first write assertEquals("CC", Grade.letterGrade(50)), then the letterGrade method. Each new grade range is one more cycle.
The payoff: every line of code is born with a test, and regression tests pile up on their own.

Debugging

The Debugger

A debugger lets you inspect the state of a running program. With a debugger you can:

  • Run the program one statement (one line) at a time
  • See the source code with the current line marked
  • View variable values and change them if needed
  • Set breakpoints in the program
  • Run the program up to a given breakpoint
  • Inspect a crashed or stopped program through a dump file (a core file in C; in Java a .hprof heap dump and a thread dump)
IDE debuggers

IntelliJ IDEA, Eclipse, NetBeans, VS Code: click next to a line number to set a breakpoint, then start with Debug.

println debugging

Quick, but it clutters the code, needs recompiling and is easy to forget to remove. A debugger leaves the code alone.

Debugging · Step by step

Finding the Defect with a Debugger

A breakpoint is set on line 5 (if). The program was started with Debug.

Step Into: we step into the call to max.

A new frame: arr refers to the same array. best is not assigned yet.

At the breakpoint: best = 0, arr[0] = -5. The watched expression is false.

Resume: i = 1, -2 > 0 is false again; best is unchanged.

i = 2, -8 > 0 is false. Suspicious: best never changes!

The loop ends and 0 is returned. Defect found: the initial value 0 is wrong when all elements are negative. It should be best = arr[0].

The failure on screen: Max: 0. After the fix, this case is added as a unit test.

public class FindMax {
  public static int max(int[] arr) {
    int best = 0;
    for (int i = 0; i < arr.length; i++) {
      if (arr[i] > best) {
        best = arr[i];
      }
    }
    return best;
  }

  public static void main(String[] args) {
    int[] temps = {-5, -2, -8};
    int result = max(temps);
    System.out.println("Max: " + result);
  }
}

    int sq1 = square(a);
    int sq2 = square(b);
    return sq1 + sq2;
  }

  public static void main(String[] args) {
    int s = sumSquares(3, 4);
    System.out.println("s = " + s);
  }
}

Debugging

Systematic Debugging

1
Reproduce Find the smallest input that triggers the failure every time (e.g. {-5, -2, -8}).

A bug you cannot reproduce, you cannot debug.

2
Write it as a test Write a unit test that fails on this input: the red test is proof of the bug.

The test will also show that the fix works.

3
Narrow it down Start at the first line of the stack trace; watch variables at a breakpoint and halve the suspect region.

Look for the line where a value first goes wrong. assert statements in the code (enabled with -ea) catch the problem where it starts.

4
Form and test a hypothesis Propose an explanation such as “best starts at 0, so it never updates”, then confirm it in the debugger.

Changing code on a hunch breeds new bugs.

5
Fix, then run all tests The new test must turn green and the old ones stay green (no regression).

The test stays in the suite for good.

Profilers

  • A profiler shows where a program spends its time: which method was called how often, how long it took, how much memory it allocated.
  • It can show the call graph (who called whom) in several forms: a flat list, a tree, a flame graph.

  • Rule: measure first, then optimize. Most of the time goes into a small “hot spot”; optimizing on a hunch usually hits the wrong place.

Measuring the Hot Spot

public class Profile {
  static String concatPlus(int n) {
    String s = "";
    for (int i = 0; i < n; i++) {
      s += i;  // new String each pass
    }
    return s;
  }

  static String concatBuilder(int n) {
    StringBuilder sb = new StringBuilder();
    for (int i = 0; i < n; i++) {
      sb.append(i);
    }
    return sb.toString();
  }
  // main: see the next box
}
  • s += i builds a new String each pass and copies the old one: total work grows as n².
  • StringBuilder appends to one buffer: work grows as n. Hundreds of times faster.
public static void main(String[] args) {
  long t0 = System.nanoTime();
  String a = concatPlus(50_000);
  long t1 = System.nanoTime();
  String b = concatBuilder(50_000);
  long t2 = System.nanoTime();
  long ms1 = (t1 - t0) / 1_000_000;
  long ms2 = (t2 - t1) / 1_000_000;
  System.out.println("+= : " + ms1 + " ms");
  System.out.println("SB : " + ms2 + " ms");
  System.out.println(a.equals(b));
}

Code Coverage Tools

  • Shows which parts of the code ran during a test run.
  • Reveals code that never runs or is never used.
  • Helps find untested regions of code.
  • Coverage is a key tool for making software more reliable.

QuickCheck: Property-Based Testing

  • QuickCheck generates tests automatically: the tool, not the programmer, picks random inputs.
  • Instead of single examples, the programmer writes a property: “this must hold for every input”.
  • If an input breaks the property, it is reported as a counterexample (shrunk when possible).
  • The original is for Haskell; there are versions for many languages; in Java: jqwik and junit-quickcheck.

The test on the right applies the idea in plain JUnit: 1000 random strings.

import java.util.ArrayList;
import java.util.List;

The garbage collector (GC) frees only unreachable objects; a leak means unneeded objects still have a reference. -Xmx256m: heap at most 256 MB.

Analysis Tools

Eclipse Memory Analyzer (MAT)

  • Finds memory leaks by analyzing the Java heap.
  • Used for memory optimization: which objects take how much space, and who holds them?
  • Input: a heap dump (.hprof): a snapshot of every object at one moment.
  • Key reports: Leak Suspects, Dominator Tree (who holds the most memory), Histogram (object count per class).

Taking a heap dump

// on OutOfMemoryError
java -XX:+HeapDumpOnOutOfMemoryError Leak

jps

What does the example show?

The Leak Suspects report shows that the Leak.cache list and its byte[] arrays hold almost the whole heap. Fix: remove data once it is done, or use a size-bounded cache.

Common Mistakes

Swapping expected and actual

assertEquals(calc.add(2, 3), 5) also works, but on failure the message reads backwards: expected shows the actual result.

Forgetting the delta for doubles

assertEquals(0.3, 0.1 + 0.2) fails: expected: <0.3> but was: <0.30000000000000004>.

Missing import static

assertEquals(5, x) → compile error: cannot find symbol: method assertEquals(int,int).

Mixing JUnit 4 and 5

org.junit.Test and org.junit.jupiter.api.Test differ; the wrong import can stop tests from running at all.

@BeforeAll method not static

JUnit 5 will not run the tests: @BeforeAll method '…' must be static unless the test class is annotated with @TestInstance(Lifecycle.PER_CLASS).

Tests that depend on each other

Relying on an object left by another test: when the order changes, tests fail at random. Each test sets up its own data.

Tests with no assertions

Calling a method without any assert: the test is always ✔ and proves nothing.

Testing only the “happy path”

Boundaries (0, empty array, negatives), invalid input and exceptions get forgotten; that is exactly where bugs live.
