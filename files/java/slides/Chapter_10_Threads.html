Basic Concepts

Threads

  • A thread is the basic unit of execution in a Java program: an independent flow that runs instructions in order.
  • Each thread is represented by an object of the Thread class.
  • Threads are used for multithreading and concurrent programming.
  • Every Java program starts with at least one thread: the main thread, which runs main().
Analogy: a beehive

Each bee does its own job (a thread), but they all share the same hive and honeycomb (shared memory). If two bees try to fill the same cell at once, trouble follows: this chapter is about managing those “collisions”.

Why?

Do background work without freezing the GUI, use a multicore CPU, keep working while waiting for the network or a file.

Basic Concepts

Concurrency and Parallelism

Concurrency

Several tasks make progress in the same time span. Possible even on one core: the OS runs threads in tiny alternating slices, so they seem to run at once.

Parallelism

Tasks run truly at the same time on different cores. Requires more than one core; speeds up computation.

The scheduler of the JVM and the OS decides which thread runs when and on which core; the programmer cannot know this order.

Basic Concepts

Context Switching

  • With more threads than cores, the OS runs them in turn using time slices.
  • On each switch the running thread's state (program counter, registers, stack pointer) is saved and the next one's is loaded: this is a context switch.
Cost

Each switch takes a few microseconds and invalidates part of the cache. Starting thousands of threads can slow the program down.

Rule of thumb

For CPU-bound work, threads ≈ cores (Runtime.getRuntime().availableProcessors()). For I/O-bound work (network, files) more can help; use a pool for that.

Basic Concepts

The Java Virtual Machine (JVM)

The JVM is a virtual environment that manages threads as independent units of execution.

When a thread is created, the JVM gives it its own stack, PC register and native method stack; the method area and the heap exist once.

Creating and Starting

The Runnable Interface

  • Every thread has a Runnable object that it runs.
  • The Runnable interface has just one method, run().
  • A class that implements it defines run(): the thread's work.
  • Since it is a functional interface (a single abstract method), Java 8+ also lets you write a lambda.

Definition in the JDK

package java.lang;

public interface Runnable {
    void run();
}

An implementing class

public class MyRunnable implements Runnable {
    @Override
    public void run() {
        // The thread's tasks
    }
}

Java 8+: a lambda

Runnable r = () -> System.out.println("hello");

Creating and Starting

Starting a Thread

public class Worker implements Runnable {
    // The thread's work goes here
    public void run() {
        String name = Thread.currentThread().getName();
        System.out.println("Worker running: " + name);
    }
    public static void main(String[] args) {
        // Start the thread
        Worker w = new Worker();
        Thread t = new Thread(w);
        t.start();
        System.out.println("main goes on");
    }
}
  • The Runnable object is passed to the Thread constructor.
  • Calling start() starts the thread.
  • Don't call run() directly: the code would then run on the caller's thread.
Output (a real run)

Worker running: Thread-0

The order of the lines may change from run to run: main carries on as soon as start() returns; the scheduler decides when the new thread runs.

start(): Two Stacks, Two Flows

main is running; a Worker object is created on the heap. There is still only one thread.

The Thread object exists (NEW) but has no separate flow or stack yet.

start(): the JVM creates a new stack and starts run() on it. start() returns at once.

One possible order: main moves first and prints.

main() has ended but the program hasn't: the JVM waits until all non-daemon threads finish.

Thread-0 runs on its own stack; name is its local variable.

Thread-0 prints.

public class StartVsRun {

Creating and Starting

The Single Inheritance Problem

  • Java lets a class inherit from only one class.
  • If the runnable class already extends another class (Base), it cannot extend Thread: extends Base, Thread won't compile.
  • The fix: the class implements Runnable and keeps a field of type Thread.
  • There is no limit on interfaces, which is why Runnable is usually preferred.

Creating and Starting

Single Inheritance: The Fix in Code

class Base {
    public void greet() {
        System.out.println("Hello from Base");
    }
}
class Worker extends Base implements Runnable {
    private Thread thread;   // Thread as a field
    public void run() {
        String name = Thread.currentThread().getName();
        System.out.println("run(): " + name);
    }
    public void start() {
        thread = new Thread(this);
        thread.start();
    }
}
public class SingleInheritance {
    public static void main(String[] args) {
        Worker w = new Worker();
        w.greet();   // inherited from Base
        w.start();   // our own start()
    }
}
Output
Hello from Base
run(): Thread-0
  • Worker inherits Base's methods and can also run on a thread.
  • Our own start() hands itself to a Thread with new Thread(this).
  • this is a Runnable, which the Thread constructor accepts.

Two Threads: One Possible Order

main starts A. A is now RUNNABLE; when it will run is unknown.

main starts B.

a.join(): main is WAITING until A ends. Now A and B run.

The scheduler runs A: A executes task() on its own stack.

A context switch: now B is running. B's i is a separate local variable.

A again.

B again. Then both end (TERMINATED).

a.join() returns; b.join() returns at once since B is already done; main prints.

public class TwoThreads {
    static void task() {
        String name = Thread.currentThread().getName();
        for (int i = 1; i <= 2; i++) {
            System.out.println(name + ": step " + i);
        }
    }
    public static void main(String[] args)
            throws InterruptedException {
        Thread a = new Thread(() -> task(), "A");
        Thread b = new Thread(() -> task(), "B");
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println("main: done");
    }
}

One of the possible orders. A real run gave B1 · B2 · A1 · A2. What is certain: “main: done” comes last.

Managing and Stopping

Managing Threads: sleep, join, yield

sleep(ms)

Puts the current thread to sleep for a while (TIMED_WAITING). It keeps any lock it holds.

join()

The calling thread waits until the target thread ends. join(ms): at most ms.

yield()

A hint to let another thread run for now; the scheduler may ignore it.

public class JoinDemo {
    static long result = 0;
    public static void main(String[] args)
            throws InterruptedException {
        Thread calc = new Thread(() -> {
            long sum = 0;
            for (int i = 1; i <= 1_000_000; i++) {
                sum += i;
            }
            result = sum;
        });
        calc.start();
        System.out.println("before join: " + result);
        calc.join();   // wait for calc to end
        System.out.println("after join : " + result);
    }
}
Output

after join : 500000500000

Without join(), main reads result before calc finishes and sees 0. After join(), calc has definitely finished and the value it wrote is visible.

Managing and Stopping

Stopping a Thread

  • A thread stops when its run() method completes.
  • The JVM exits when System.exit() (internally Runtime.exit()) is called or when all non-daemon threads have ended.
  • The right way to stop a thread from outside is cooperation: the thread periodically checks a flag.
  • The flag is declared volatile so other threads can see the change.
  • Alternative: an interrupt request with interrupt().
Don't use Thread.stop()

The deprecated stop() kills a thread mid-task; its locks are released and objects may be left half-updated. Since Java 20 it no longer works:

Synchronization

Executing Operations in the Right Order

Unknown speed

Each thread's speed and frequency vary. Operating systems may ignore priorities; you can't rely on priorities for ordering.

Stale values

After one thread reads a variable, another may update it; the first carries on with an out-of-date value.

Reordering

The compiler, the JIT and the CPU may reorder instructions for speed; unnoticeable in one thread, surprising with several.

When several threads access shared, mutable data, access must be synchronized. Otherwise the result depends on the order in which the threads run: this is a race condition.

Synchronization

Race Conditions

public class RaceCondition {
    static int counter = 0;   // shared data
    public static void main(String[] args)
            throws InterruptedException {
        Runnable inc = () -> {
            for (int i = 0; i < 100_000; i++) {
                counter++;   // read, add 1, write: NOT atomic
            }
        };
        Thread t1 = new Thread(inc);
        Thread t2 = new Thread(inc);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Expected: 200000");
        System.out.println("Actual  : " + counter);
    }
}

Synchronization · One possible order

Why Does counter++ Get Lost?

At first counter = 0. Both threads will do counter++; the right result is 2.

t1 reads: its register gets 0.

Context switch! t2 reads too: it also sees 0.

t1 adds 1 in its register.

t1 writes: counter = 1.

t2 adds 1 to its own (stale) value: 1.

t2 writes: counter = 1. Two increments ran, but the result is 1: t1's increment is lost.

// counter++ is three CPU steps:
int reg = counter;     // 1) read
reg = reg + 1;          // 2) add 1
counter = reg;          // 3) write

This is just one possible order; without an interleaving the result is right. That is why the bug looks random and is hard to test. The call stack box shows the thread running at that moment.

Synchronization

Synchronization Options

join()

Wait for a thread to finish.

synchronized

Mutual exclusion with an object's monitor lock.

ReentrantLock, ReadWriteLock: explicit locking.

Synchronization · synchronized

synchronized and Monitors

  • Every object has a monitor (intrinsic lock) that can be locked and unlocked.
  • Only one thread can own a monitor at a time.
  • If t2 wants it while t1 owns it, t2 waits (BLOCKED).
  • When the monitor is released, the waiting threads compete and only one gets it.
  • The monitor is taken with synchronized and released automatically when the block ends (even via an exception).
  • This gives mutual exclusion and protects data integrity.

Syntax

synchronized (o) {
    // we hold o's monitor here
}
Runnable r = () -> {
    for (int i = 0; i < 50_000; i++) {
        synchronized (o) {   // take o's monitor
            shared++;
        }                    // monitor released
    }
};
Output (2 × 50000, every time)
100000

Synchronization

Monitors Step by Step

// t1 and t2 run the same code
synchronized (o) {
    shared++;     // critical section
}

A critical section is code that accesses shared data and must be run by only one thread at a time.

t1 and t2 reach the synchronized (o) line at the same time; the monitor is free.

t1 wins and takes the monitor. t2 waits in the entry set, BLOCKED.

t1 leaves the block: the monitor is released automatically. The waiting threads compete.

t2 takes the monitor and enters the critical section.

t2 leaves too. shared++ ran twice without interfering.

Synchronization

Declaring Synchronized Methods

synchronized method

class C {
    synchronized void p() { ... }
    static synchronized void q() { ... }
    //...
}

Equivalent: a synchronized block

class C {
    void p() { synchronized (this) { ... } }
    static void q() { synchronized (C.class) { ... } }
    //...
}
  • Declaring a method synchronized is the same as wrapping its body in a synchronized block.
  • Instance method → the monitor of this.
  • static method → the monitor of the class object C.class (there is no instance).
  • So a static synchronized method and an instance synchronized method don't block each other: different locks.
  • The block form lets you lock only the lines that really need it.

With real bodies in place of ... (say n++, s++), both forms compile and behave the same.

The Java Memory Model: happens-before

The Java Memory Model (JMM) defines when a value written by one thread becomes visible to another. Programmers reason not with CPU barriers but with happens-before relations: if A happens-before B, whatever A wrote is guaranteed to be visible in B.

RuleA happens-before B
Locksreleasing a monitor/lock → the next acquisition of the same lock
volatilea write to a volatile field → the next read of that field
Starteverything before t.start() → the actions inside t
Terminationall of t's actions → the thread returning from t.join()
Library structuresBlockingQueue.put → the take that gets that element; a Future's task → get()
False sharing: if independent variables of different threads sit on the same cache line (usually 64 bytes) and are updated often, the cores keep pulling the line from each other. The result isn't wrong, but the program slows down: a performance problem, not a correctness one.

Livelock and Starvation

Livelock

The threads aren't blocked; they keep changing state by “giving way” to each other, but none finishes. Example: two threads that release everything when tryLock fails and retry at the same moment, colliding every time.

Starvation

A thread gets the resource late or never: others keep grabbing the lock, or long critical sections keep it waiting. Priority values (setPriority) are not reliable for fixing this.

Lock lock = new ReentrantLock(true);  // fair
if (lock.tryLock(50, TimeUnit.MILLISECONDS)) {
    try { /* work */ }
    finally { lock.unlock(); }
} else {
    Thread.sleep(rnd.nextInt(20)); // random
}
  • A fair lock gives the turn to the longest waiter (a bit slower).
  • Waiting a random time before retrying breaks the symmetry and prevents livelock.
  • Short critical sections give everyone a turn.

Condition Synchronization

Condition Synchronization

  • Gives safe access to a shared resource only when a certain condition holds.
  • Example: a consumer should take an item only when the queue is not empty; a producer should add only when it is not full.
  • Controlled updates need the object's lock, plus a way to wait until the condition holds.
  • But you can't wait while holding the lock: the thread that would change the condition can't get the lock, and everyone gets stuck.

1) Object.wait() and Object.notify() / notifyAll()
2) The Condition interface (with Lock)

Condition Synchronization

Object.wait() and Object.notify()

  • Every object has a wait set.
  • The thread holding the lock calls wait(): it enters the set, releases the lock and blocks.
  • notify() wakes one thread, notifyAll() wakes them all; wait(ms) also returns when time is up.
  • The woken thread continues where it left off once it reacquires the lock.
  • Rule 1: call them only inside synchronized; otherwise IllegalMonitorStateException: current thread is not owner.
  • Rule 2: check the condition with while, not if: on waking it may be false again (or the wakeup may be spurious).

BlockingQueue with wait() and notifyAll()

class BlockingQueue {
    private Object[] data;
    private int head = 0;
    private int tail = 0;
    private int count = 0;
    public BlockingQueue(int capacity) {
        if (capacity <= 0)
            throw new IllegalArgumentException(
                    "capacity must be > 0");
        data = new Object[capacity];
    }
    public synchronized int getSize() {
        return count;
    }
    public synchronized void add(Object item)
            throws InterruptedException {
        while (count == data.length) {
            wait();
        }
        data[tail] = item;
        tail = (tail + 1) % data.length;
        count++;
        notifyAll();
    }
    public synchronized Object remove()
            throws InterruptedException {
        while (count == 0) {
            wait();
        }
        Object item = data[head];
        data[head] = null;
        head = (head + 1) % data.length;
        count--;
        notifyAll();
        return item;
    }
}
  • A circular array: head is where to remove, tail where to add; % data.length wraps around.
  • add waits while full, remove while empty; after each change notifyAll() wakes the waiters.

CountDownLatch

Synchronizes threads that wait for a number of events. count: the starting count, here 3.

Three threads are started; when they will run is unknown.

public static void main(String[] args)
        throws Exception {
    int count = 3;
    CountDownLatch latch = new CountDownLatch(count);
    for (int i = 0; i < count; i++) {
        int no = i + 1;   // copy for the lambda
        new Thread(() -> {
            System.out.println(no + ": event happened");
            // count down when the event happens
            latch.countDown();
        }).start();
    }
    // wait for the threads to finish
    latch.await();
    System.out.println("All events done!");
}

Data 2 owner got: Data 1
  • Used by two threads to exchange data; more a communication object than a lock.
  • exchange(data) waits until the other side also calls exchange: the “Data 2” owner waited 1 s.
  • When they meet, each gets the other's data.

Synchronizers · A real run

Semaphore

A semaphore limits concurrent access: here at most 3 threads at a time. new Semaphore(n, true): fair distribution.

Five threads start. acquire() waits if no permit is left; release() gives the permit back.

1 takes a permit and enters.

3 enters.

2 enters. No permits left.

4 and 5 wait in acquire().

After 2 s, 2 leaves and releases its permit.

1 leaves too.

The waiting 4 and 5 take the permits and enter.

3, 4 and 5 leave too; all 3 permits are back.

public static void main(String[] args) {
    int permits = 3;
    Semaphore semaphore = new Semaphore(permits);
    for (int i = 0; i < 5; i++) {
        int no = i + 1;
        new Thread(() -> {
            try {
                semaphore.acquire();   // take a permit
                System.out.println(no + " in");
                Thread.sleep(2000);
                System.out.println(no + " out");
                semaphore.release();   // give it back
            } catch (InterruptedException e) {
                e.printStackTrace();
            }
        }).start();
    }
}

public class AtomicCounter {

  • AtomicInteger, AtomicLong, AtomicBoolean…: safe access without locks.
  • incrementAndGet() = an atomic ++x; it can't be interrupted halfway.
  • An atomic object ≈ a volatile field + an atomic compareAndSet.

Lock-Free Increment with compareAndSet

AtomicInteger counter = new AtomicInteger(5);

int inc() {                    // how incrementAndGet works
    while (true) {
        int old = counter.get();
        int next = old + 1;
        if (counter.compareAndSet(old, next))
            return next;
        // failed: someone got in first; retry
    }
}

Two threads will increment the same counter object. It starts at 5.

T1 reads the current value: old = 5.

Before T1 goes on, T2 reads too and also sees 5. There's no lock, so both keep running.

Both compute next = 6 locally. With a plain counter++, both would write 6 and one increment would be lost.

T1: compareAndSet(5, 6). The value is still 5 → 6 is written and true returned. Check and write are one atomic operation.

T2: compareAndSet(5, 6). The value is now 6, not the expected 5 → nothing is written; false.

The loop repeats: T2 rereads the current value.

next = 7.

This time the CAS succeeds: counter = 7. Both increments counted; nobody waited for a lock, T2 just went around once more.

Interrupting, Step by Step

Thread worker = new Thread(() -> {
    try {
        while (!Thread.interrupted()) {
            System.out.println("working...");
            Thread.sleep(400);
        }
    } catch (InterruptedException e) {
        System.out.println("cancelled!");
    }
});
worker.start();
Thread.sleep(1000);
worker.interrupt();   // worker is in sleep()
worker.join();
System.out.println("main: done");

start() sets worker running. The interrupt flag is false.

The flag is clear: it enters the loop, prints and sleeps 400 ms.

main sleeps 1000 ms too; the two threads proceed independently.

worker wakes up; Thread.interrupted() is still false: one more lap.

Third lap: it prints and sleeps again (it would have slept until 1200 ms).

main wakes up and calls interrupt(): worker's interrupt flag becomes true.

worker is in sleep, so the sleep is cut short at once: an InterruptedException is thrown and the flag is cleared again.

main waits for worker with join(); worker ends after the catch.

The program ends cleanly. An interrupt is a request: the thread itself handles the flag or the exception and exits.

Thread Pools

  • A structure that creates threads up front and manages them: tasks are submitted to the pool.
  • Creating threads is expensive; a pool reuses them and caps their number.
  • The ExecutorService interface controls the pool's work; Executors.newFixedThreadPool(n) gives a ready-made pool.

public class PoolDemo {
    static void task(int no) {

        System.out.println("Task " + no + " -> " + name);

    }
}

The Pool and Future, Step by Step

static int job(int ms, int d) throws Exception {
    Thread.sleep(ms);   // stands in for slow work
    return d;
}
// inside main:
ExecutorService pool = Executors.newFixedThreadPool(2);
Future<Integer> f1 = pool.submit(() -> job(300, 10));
Future<Integer> f2 = pool.submit(() -> job(100, 20));
Future<Integer> f3 = pool.submit(() -> job(100, 30));
System.out.println(f1.isDone() + " " + f3.isDone());
int sum = f1.get() + f2.get() + f3.get();
System.out.println("sum = " + sum);
System.out.println(f2.isDone() + " " + f3.isDone());
pool.shutdown();

A fixed pool of 2 threads. Workers run tasks as they come and take a new one when done.

submit hands the task to the pool and returns a Future at once. f1 starts on worker 1.

f2 goes to the idle worker 2.

Both workers are busy: f3 waits in the queue. No new thread is created.

No task is done yet; isDone() answers without waiting.

f1.get() blocks main until the result is ready. Meanwhile f2 ends and worker 2 takes f3 from the queue.

f3 ends too; main is still waiting for f1.

t ≈ 300 ms: f1 is ready. f2 and f3 are already done, so their get()s return at once. Total time ≈ 300 ms, not 500.

The result and states are printed.

shutdown() stops accepting tasks; the workers end. Forget it and the program never exits.

Times are approximate (ignoring thread start-up delay); which worker gets which task may vary from run to run.

CompletableFuture, Concurrent Collections, ForkJoinPool

  • CompletableFuture: rather than blocking on get(), chain steps; each runs in the background after the previous one.

Thread Safety

A class is thread-safe if it behaves correctly even when used from several threads at once.

Immutable objects

Objects that never change after construction (String, classes with final fields, Java 16+ records) can be shared without synchronization.

Don't share

Local variables live on each thread's stack; ThreadLocal gives copies too. Unshared data can't race.

Synchronization

Every access to shared mutable data is guarded by the same lock: synchronized, Lock.

Ready-made structures

AtomicInteger, ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue; ArrayList and HashMap are not safe.
