Basics

What Is an Exception?

  • An exception is an unexpected event that occurs while a program runs and disrupts its normal flow.
  • Examples: a file that cannot be found, division by zero, an index outside an array, using a null reference.
  • Exceptions are created automatically by the Java runtime (the JVM) or explicitly by the programmer (throw).
  • In Java an exception is an object: it carries its type, a message and where it happened.
  • The exception mechanism lets you deal with abnormal situations in an orderly way.
When Java hits an exception, it roughly says: “I give up. I don't know what to do now. Somebody else handle this!”
Analogy

A waiter learns in the kitchen that a dish has run out. He can't fix it, so he tells the manager. The manager either solves it (suggests another dish) or passes it further up.

Basics

Runtime Errors: Exception and Error

Compile errors stop a program from running at all; logic errors give no signal. A problem that arises while the program runs is thrown by the JVM as a Throwable object, which has two main branches.

BranchWhat it meansWhat the program can doExample
Exception
(Exception)		An unusual condition the program can anticipateCatch it and recover10 / 0, arr[5] (on a 3-element array), a missing file
Error
(Error)		A serious JVM- or system-level problemUsually not caught; the program endsStackOverflowError, OutOfMemoryError

Exceptions and stack traces are among the most powerful tools for finding and fixing the cause of runtime errors (debugging).

Basics

Two Ways to Deal with an Exception

1) Handle it

The method puts the risky code in try and resolves the problem itself in catch.

Example: if the file is missing (FileNotFoundException), a file-reading method shows a message and goes on with default settings.

2) Make it the caller's problem (declare)

The method does not handle the exception; it declares it with throws in its signature. The exception becomes the caller's problem.

The caller faces the same choice: handle it or pass it up.

Which one? The code that can meaningfully resolve the exception should handle it. Code that got the file name from the user can ask again when the file is missing; a low-level read method cannot know that.

Basics

Exceptions Instead of Return Codes

public static int find(String[] names, String name) {
  for (int i = 0; i < names.length; i++) {
    if (names[i].equals(name)) {
      return i;
    }
  }
  throw new IllegalArgumentException("Not found: " + name);
}
// in main
try {
  System.out.println(find(names, "Ece"));
} catch (IllegalArgumentException e) {
  System.out.println("Error: " + e.getMessage());
}
Output
Error: Not found: Ece
  • As a rule, avoid special return codes like -1; prefer Java's exception mechanism.
  • Exceptions handle error cases clearly and effectively.

Why exceptions help

  • Clear, consistent error handling; errors never mix with normal results
  • More readable code, easier debugging
  • More reliable code

try and catch

try and catch Statements

try {
  // Code that may fail
  int result = 10 / 0; // ArithmeticException
} catch (ArithmeticException e) {
  // Handle the error
  System.out.println("Error: " + e.getMessage());
}
Output
Error: / by zero
  • The basic structure of error handling.
  • try block: code that may fail.
  • catch block: runs if an exception of the given type occurs inside try, and handles it.
  • catch (ArithmeticException e): e refers to the thrown exception object (like a parameter).
  • If an exception occurs, the rest of try is skipped; if none occurs, catch never runs.
  • After catch, the program continues its normal flow.

try and catch

Multiple catch Blocks

try {
  // Code that may fail
} catch (ArithmeticException e) {
  // Handle ArithmeticException
} catch (NullPointerException e) {
  // Handle NullPointerException
} catch (Exception e) {
  // All other exceptions
}
  • A block of code can throw more than one type of exception.
  • Add a separate catch block per type; each holds the response specific to that type.
  • When an exception is thrown, the catch blocks are tried top to bottom; the first match runs and the rest are skipped.
  • “Match” means the thrown object is the catch type itself or a subclass (the instanceof rule).
  • The final catch (Exception e) is the general case that catches everything else.

try and catch

Chained catch Blocks: Order Matters

✗ General type first

try {
  int result = 10 / 0;
} catch (Exception e) {
  System.out.println("General error");
} catch (ArithmeticException e) {
  System.out.println("Arithmetic error");
}
OrderError.java:7: error: exception ArithmeticException
    has already been caught
  • If the catch types are related by inheritance, order matters: subclasses must come before superclasses.
  • ArithmeticException is an Exception; the first block already catches it, so the second can never run. The compiler rejects this.
  • For unrelated types (ArithmeticException, NullPointerException) order does not matter.

✓ Specific to general

} catch (ArithmeticException e) {
  System.out.println("Arithmetic error");
} catch (Exception e) {
  System.out.println("General error");
}

try and catch · Step by step

Which catch Runs?

1st call: parseInt("abc") → NumberFormatException. The division line is skipped.

The first catch matches and runs; the other catches are not checked.

Then finally.

2nd call: 10 / 0 → ArithmeticException.

The 1st catch doesn't match (✗), the 2nd does (✓).

3rd call: the array has one element; input[1] → ArrayIndexOutOfBoundsException.

The first two catches don't match, the third does; then finally.

static void divide(String[] input) {
  try {
    int x = Integer.parseInt(input[0]);
    int y = Integer.parseInt(input[1]);
    System.out.println("Result: " + (x / y));
  } catch (NumberFormatException e) {
    System.out.println("Not a number: " + e.getMessage());
  } catch (ArithmeticException e) {
    System.out.println("Zero: " + e.getMessage());
  } catch (ArrayIndexOutOfBoundsException e) {
    System.out.println("Missing: " + e.getMessage());
  } finally {
    System.out.println("finally ran");
  }
}
// in main
divide(new String[] {"10", "abc"});
divide(new String[] {"10", "0"});
divide(new String[] {"10"});

finally

The finally Block

try {
  // Code that may fail
} catch (Exception e) {
  // All other exceptions
} finally {
  // Always runs
}
  • Comes after the try and catch blocks.
  • Runs in every case: whether or not an exception occurs, and whether or not it is caught.
  • Even if try or catch contains a return, it runs before the method exits.
  • Guarantees that certain steps run: resource management and cleanup, such as closing files, network and database connections.
  • try must be followed by at least one catch or a finally; try { } finally { } is valid.
  • The one exception: System.exit() stops the JVM at once; finally does not run.

finally · Step by step

finally and return: Step by Step

Before println runs, its argument must be evaluated: divide(10, 2) is called.

The try block starts.

The division succeeds: s = 5.

return s: the return value 5 is ready, but the method doesn't end yet…

…first finally runs. catch was skipped (no exception).

Now 5 is returned and printed.

Second call: divide(10, 0).

try starts.

10 / 0 → exception! The rest of try (“try ended”, return s) is skipped.

catch matches and prints the message.

return -1: the value is ready, but again finally runs first.

finally runs this time too.

-1 is returned. So finally ran in both cases.

static int divide(int a, int b) {
  try {
    System.out.println("try started");
    int s = a / b;
    System.out.println("try ended");
    return s;
  } catch (ArithmeticException e) {
    System.out.println("catch: " + e.getMessage());
    return -1;
  } finally {
    System.out.println("finally");
  }
}
public static void main(String[] args) {
  System.out.println("Result = " + divide(10, 2));
  System.out.println("Result = " + divide(10, 0));
}

try-with-resources (Java 7+)

class Resource implements AutoCloseable {
  private String name;
  Resource(String name) {
    this.name = name;
    System.out.println(name + " opened");
  }
  void use(int x) {
    System.out.println(name + " in use");
    int s = 10 / x;
  }
  @Override
  public void close() {
    System.out.println(name + " closed");
  }
}
try (Resource r = new Resource("file")) {
  r.use(0);
} catch (ArithmeticException e) {
  System.out.println("Error: " + e.getMessage());
}
Output
file opened
file in use
file closed
Error: / by zero
  • A resource opened in try (...) is closed automatically (close()) when the block ends, even after an exception.
  • The resource is closed before catch runs. Its class must implement AutoCloseable, as streams, Scanner, NIO channels and database connections do; no finally or null check is needed.
  • This is the modern, safe way to do what finally did for closing resources.

finally · Step by step

Two Resources: Opening and Closing Order

Resource: its constructor prints “… opened”, use prints “… in use”, close() prints “… closed”.

The first resource is created: file opened.

The second resource is created. Resources are separated by semicolons and opened in the order written.

b.use(0): first “net in use” is printed, then 10 / 0.

Exception thrown: the rest of try (“try end”) is skipped. But the resources are closed before catch.

Closing happens in reverse order: b, opened last, closes first (close()).

Then a closes. Both resources were closed despite the exception.

Now catch runs: the exception is caught.

finally runs last. Order: open → use → close (reversed) → catch → finally.

try (Resource a = new Resource("file");
     Resource b = new Resource("net")) {
  b.use(0);
  System.out.println("try end");
} catch (ArithmeticException e) {
  System.out.println("Error: " + e.getMessage());
} finally {
  System.out.println("finally");
}

finally

Nested try Blocks

try {
  // Outer try block
  try {
    // Inner try block
    // Code that may fail
  } catch (Exception e) {
    // Inner catch block
  } finally {
    // Inner finally block
  }
} catch (Exception e) {
  // Outer catch block
} finally {
  // Outer finally block
}

A try block can contain another try block. If an exception occurs in the inner try:

  1. If one of the inner try's catches matches, it runs.
  2. Otherwise the exception moves outward; the first matching catch is found and runs.
  3. If no catch matches, the exception leaves the method; if nobody catches it, the JVM's default handler ends the program.
  4. In every case, the finally (if any) at each level the exception passes through runs.

finally · Step by step

Nested try: The Exception Moves Outward

The outer try starts.

The inner try starts; s = null.

Calling a method on null → NullPointerException.

The inner catch only catches ArithmeticException: no match.

Before the exception leaves, the inner finally runs.

The exception reached the outer level; “Outer try cont.” was skipped. The outer catch matches.

The outer finally runs.

The exception was handled; the program continues normally.

public static void main(String[] args) {
  try {
    System.out.println("Outer try");
    try {
      System.out.println("Inner try");
      String s = null;
      System.out.println(s.length());
    } catch (ArithmeticException e) {
      System.out.println("Inner catch");
    } finally {
      System.out.println("Inner finally");
    }
    System.out.println("Outer try cont.");
  } catch (NullPointerException e) {
    System.out.println("Outer catch: NPE");
  } finally {
    System.out.println("Outer finally");
  }
  System.out.println("Program goes on");
}

Hierarchy

The Exception Hierarchy

  • Java's exception classes form a class hierarchy.
  • Throwable is the root of everything that can be thrown: only objects of Throwable and its subclasses can be thrown with throw and caught with catch.
  • Throwable has two direct subclasses: Error and Exception.
  • A catch block catches the named type and all its subclasses (a natural result of inheritance).
  • Java lets you define your own custom exception classes: classes for application-specific situations join this hierarchy.
Why a hierarchy?

Exceptions of one family can be caught with a single supertype: catch (IOException e) catches FileNotFoundException and other I/O errors alike.

Hierarchy

Error and Exception

Error

  • Signals that the program has hit a serious problem it cannot recover from.
  • Such situations usually cannot be handled and typically end the program.
  • Examples: extreme cases such as running out of memory (OutOfMemoryError), a call stack overflow, or a disk drive “vanishing”.
  • Catching them in application code is not recommended.

Exception

  • Conditions the program can anticipate and often recover from.
  • A missing file, a dropped network connection, invalid input, a null reference…
  • The type you are expected to handle with try-catch.
  • Its subclass RuntimeException mostly represents programmer errors.

Both derive from Throwable, so both can be thrown. But the family that “should be handled” is Exception.

Kinds of Exceptions

Kinds of Exceptions

Checked exceptions

Checked by the compiler at compile time; the programmer must handle or declare them. They cover situations known in advance to be possible.

Unchecked exceptions

Not checked at compile time; they show up at run time. RuntimeException, Error and their subclasses.

Kinds of Exceptions

Checked Exceptions

  • Must be handled or declared by the code: the “catch or declare” rule.
  • Either list it with throws in the method header or handle it in a try-catch.
  • Derives from Exception but not from RuntimeException.
  • The rule is enforced at compile time: break it and the program won't compile.
  • Example: reading a file that doesn't exist. However correct the program is, the file may have been deleted, so the compiler demands a plan.

✗ Neither handled nor declared

public void readFile() {
  FileReader reader = new FileReader("data.txt");
}
error: unreported exception FileNotFoundException;
  must be caught or declared to be thrown

✓ Declared with throws

public void readFile() throws FileNotFoundException {
  // Read the file
  FileReader reader = new FileReader("data.txt");
}

Kinds of Exceptions

Handling a Checked Exception

public static void readFile2() {
  try {
    FileReader reader = new FileReader("data.txt");
    // Read the file
  } catch (FileNotFoundException e) {
    // Checked exception handled here
    System.err.println("File not found: " + e.getMessage());
    // Rethrow if needed:
    // throw e;
  }
}
Output (Windows; on Linux: No such file or directory)
File not found: data.txt (The system cannot find the file specified)
  • Here the method catches the exception itself; there is no throws in its signature. The caller doesn't have to do anything.
  • System.err: the error output stream. Most IDEs show it in red.
  • The message comes from the operating system, so it differs on Windows and Linux.
  • throw e;: a caught exception can be rethrown if needed (say, after logging it). The method must then declare throws FileNotFoundException again.

Kinds of Exceptions

Unchecked Exceptions

  • Exceptions you are not required to handle or declare.
  • They usually come from logic errors or programmer errors: dividing by zero, using null, going past an array's bounds.
  • No throws clause or try-catch is required; the compiler stays silent.
  • They derive from RuntimeException or Error.
  • The right fix is usually not to catch them but to prevent them: check the divisor before dividing and null before use.
public void divide(int num, int den) {
  // Unchecked: ArithmeticException
  int result = num / den;
}

Compiles; no throws needed. If den == 0, an exception occurs at run time.

public void divide(int num, int den) {
  if (den == 0) {   // prevention
    System.out.println("Divisor cannot be 0");
    return;
  }
  int result = num / den;
}

Throwing

Throwing an Exception

  • When the Java runtime hits an unexpected situation, it creates an exception object and throws it to notify higher-level code.
  • The programmer can do the same with the throw keyword.
  • An exception changes the normal flow: the lines after throw don't run; control jumps to a matching catch.
  • Many types can be thrown: IOException, NullPointerException, IllegalArgumentException, your own custom classes…
  • The caller can catch a thrown exception with try-catch. If it is never handled, the JVM ends the program and reports what went wrong and where.

Syntax

throw new Exception("This is an exception!");

new creates the exception object (the message goes to the constructor); throw throws it.

try {
  throw new Exception("This is an exception!");
} catch (Exception e) {
  System.out.println(e);
}
Output
java.lang.Exception: This is an exception!

Throwing

The Exception Type That Best Fits

class CustomException extends Exception {
  public CustomException(String message) {
    super(message);
  }
}
public static void check(int value)
    throws CustomException {
  if (value < 0) {
    // Check a condition and throw
    throw new CustomException("Value cannot be negative!");
  }
  // Value is OK: carry on
  System.out.println("Value OK: " + value);
}
// in main
try {
  check(5);
  check(-3);
  check(8);
} catch (CustomException e) {
  System.out.println("Caught: " + e.getMessage());
}
Output
Value OK: 5
Caught: Value cannot be negative!
  • Choose the exception class that best represents the situation.
  • For special scenarios you can create custom exception classes.
  • CustomException is a subclass of Exception, so it is checked. That is why the method signature needs throws CustomException.
  • Once check(-3) throws, the rest of try is skipped: check(8) is never called.

Throwing · Step by step

throw: An Exception Skips the Rest of try

main calls check(5) inside try; a new frame is pushed on the stack.

5 < 0 is false: the throw line is skipped.

“Value OK: 5” is printed; the method returns normally.

Next call: check(-3).

-3 < 0 is true.

new creates the exception object and throw throws it. Line 5 doesn't run; the method has no catch, so its frame is discarded.

The exception reached main; the rest of try (check(8)) is skipped and a matching catch is found.

getMessage() returns the message given to the constructor.

catch is done; the program continues its normal flow. check(8) was never called.

static void check(int value) throws CustomException {
  if (value < 0) {
    throw new CustomException("Value cannot be negative!");
  }
  System.out.println("Value OK: " + value);
}

  check(-3);
  check(8);

Throwing

Calling Methods That Throw

A file-reading method

public void readFile() throws FileNotFoundException {
  // Read the file
}

1) The caller handles it (preferred)

try {
  readFile();
} catch (FileNotFoundException e) {
  // Handle the missing file
  System.err.println("File not found: " + e.getMessage());
}

2) The caller declares it too (passes it on)

public void makeReport() throws FileNotFoundException {
  readFile();
}
  • When calling a method, consider the exceptions declared in its signature and pick a suitable strategy.
  • Put the call inside a suitable try-catch block.
  • Or have the caller declare the same type with throws; the problem moves up a level. This only postpones the problem, so it is less preferred than catching.
  • Even main can declare throws; an uncaught exception then ends the program.

Throwing · Step by step

Propagation: The Exception Unwinds the Call Stack

main calls compute(10) inside try.

A compute frame is pushed on the stack.

compute calls divide(10, 0).

divide is now on top of the stack.

10 / 0: the exception is born in divide. divide has no try → the rest of divide doesn't run and its frame is discarded.

The exception passes to the caller, compute. No try here either → “compute ended” is skipped and the frame is discarded.

The exception reaches main. The call is inside a try, so a matching catch is sought. The “Result” line is skipped.

catch matches: the exception is caught and propagation stops.

The program ends normally. Had nobody caught it, the JVM would have ended the program.

static int divide(int a, int b) {
  System.out.println("divide started");
  int s = a / b;
  System.out.println("divide ended");
  return s;
}
static int compute(int x) {
  System.out.println("compute started");
  int r = divide(x, 0);
  System.out.println("compute ended");
  return r;
}
public static void main(String[] args) {
  try {
    int result = compute(10);
    System.out.println("Result: " + result);
  } catch (ArithmeticException e) {
    System.out.println("main: " + e.getMessage());
  }
  System.out.println("Program ended");
}

Throwing

How Does the JVM Handle an Exception?

  1. The JVM (or throw) creates an exception object holding its type, its message and a stack trace of where it occurred.
  2. In the method where it occurred, the JVM looks for an enclosing try with a compatible catch.
  3. If none is found, the method ends at once (its finally runs, if any) and the exception passes to the calling method. The search continues down the call stack.
  4. If a matching catch is found, it runs; the program continues after the catch.
  5. If main doesn't catch it either, the JVM's default handler prints the stack trace and ends the program (that thread).
This search is called stack unwinding. Once the catch block ends, the caught exception object is no longer used and is cleaned up by the garbage collector.

ArithmeticException

  • Represents an error during a mathematical operation; the best-known case is integer division by zero (/ and %).

Safe Number Parsing

static int safeParse(String text, int fallback) {
  try {
    return Integer.parseInt(text.trim());
  } catch (NumberFormatException e) {
    return fallback;
  }
}
// in main
System.out.println(safeParse(" 42 ", 0));
System.out.println(safeParse("forty", 0));
System.out.println(safeParse("10.5", -1));

0

  • trim() removes leading and trailing spaces: parseInt(" 42 ") alone would throw.
  • "10.5" is not an int; for decimals use Double.parseDouble.
  • Pick a default that can't be confused with a valid result; if it can, passing the exception to the caller is the better choice.

Where Does a Stack Trace Come From?

main calls show("Ali") at line 9.

show calls len(name) at line 6. Each frame remembers its current line.

"Ali".length() = 3 is returned; the frame is removed.

“Ali: 3” is printed and show ends.

main calls show(null) at line 10.

null is passed as an argument; no problem yet.

null.length(): an NPE is thrown. The stack now holds three frames: len:3, show:6, main:10.

When the exception object is born, it records the stack: each frame becomes an at line, the top one first.

Nobody caught it: all three frames were discarded; the JVM printed the stack trace and ended the program. “Done” is never printed.

Best Practices for Exception Handling

Catch specific types

Where possible, catch the expected type instead of catch (Exception e), and respond to each kind appropriately.

Don't swallow exceptions

An empty catch { } hides the error. At least log it or tell the user.

Close resources

Close files, connections and other resources with try-with-resources or finally.

Prevent what you can

Check for null, bounds and zero; fix the code instead of catching RuntimeException.

Not for control flow

Don't use exceptions for ordinary tasks such as leaving a loop; exceptions are for exceptional situations.

Meaningful messages

State the bad value and what was expected: "Grade must be 0-100: 120".

Handle in the right place

Catch an exception where it can be resolved; otherwise pass it on with throws.

Log them

Logging exceptions to a file makes it easier to trace errors later.

Common Mistakes

Forgetting a checked exception

new FileReader(name) with no try/throws: unreported exception FileNotFoundException; must be caught or declared to be thrown.

General catch first

catch (Exception e), then catch (ArithmeticException e): exception ArithmeticException has already been caught.

Catching what is never thrown

catch (FileNotFoundException e) on a try with no file operation: exception FileNotFoundException is never thrown in body of corresponding try statement.

A lone try

A try with no catch or finally: 'try' without 'catch', 'finally' or resource declarations.

Code after throw

A line right after throw in the same block: unreachable statement.

Using a try variable outside

Printing result, declared inside try, after the block: cannot find symbol. Declare it before the try.

Swallowing the exception

catch (Exception e) { } compiles, but the error vanishes without a trace.

Throwing a string

throw "error"; → incompatible types: String cannot be converted to Throwable.

What happens if the two catch blocks in Problem 2 swap places?

Show answers

static void a() {

static void b() {

The exception is born in b(); neither b() nor a() has a try. Which prints run and which are skipped? When does finally run?

Show answer

a1 b1 caught! end

The exception travels b → a → main: “a2” and “m” are skipped. The catch in main catches it, then finally prints “ end” and ends the line.

Problem 6: What is the output?

try {
  throw new RuntimeException("X");

  System.out.println("F");

Show answers
  1. 1109: 12/4 = 3, 12/0 → +100, 12/2 = 6, d[3] → +1000. Each pass has its own try, so the loop keeps going.

Exercises (1)

  1. Write int readAge(String text): if the text isn't a number, let NumberFormatException occur; if negative, throw IllegalArgumentException. Use two catches to print messages for "20", "-3", "twenty".
  2. Write a checked exception InvalidGradeException and setGrade(int grade), which throws it for grades outside 0–100.
  3. In Exercise 1, what if the catch order is IllegalArgumentException, then NumberFormatException?
Answers / hints
  1. int age = Integer.parseInt(text); if (age < 0) throw new IllegalArgumentException("Negative age: " + age); return age; · Output: Age: 20, Negative age: -3, Not a number: twenty. The NFE catch must come first.
  2. class InvalidGradeException extends Exception { … super(msg); } · void setGrade(int grade) throws InvalidGradeException { if (grade < 0 || grade > 100) throw new InvalidGradeException("Grade must be 0-100: " + grade); … } · setGrade(120) → Grade must be 0-100: 120.
  3. Compile error: exception NumberFormatException has already been caught (NFE is a subclass of IAE).

Exercises (2)

  1. Classify as checked or unchecked: IOException, NumberFormatException, SQLException, NullPointerException, FileNotFoundException, ClassCastException, StackOverflowError.
  2. Rewrite code that closes a BufferedReader in finally using try-with-resources.
