The Idea of Inheritance

What Is Inheritance?

  • Inheritance: building a new class from an existing one by taking over its fields and methods and adding new or modified behavior.
  • The existing class: the superclass.
  • The new class: the subclass.
  • A subclass can add fields and methods; inherited fields are not redeclared.
Analogy: “Every rectangle is a shape.” A rectangle has everything a shape has, plus its own width, height and area().

The Idea of Inheritance

Subclassing with extends

// base class (superclass)
public class Shape {
    // fields and methods of the base class
    // ...
}

// new class (subclass), derived from Shape
public class Rectangle extends Shape {
    // fields and methods of the new class
    // ...
}
  • Syntax: class Sub extends Super. extends means “builds on”.
  • extends names exactly one class.
  • The subclass uses the superclass’s public and protected members as if they were its own.
  • Redeclaring a superclass field with the same name in the subclass hides it: you get two separate variables and a lot of confusion. Don’t do it.
  • A class without extends implicitly extends Object.

The Idea of Inheritance

Subclass and Superclass

  • A subclass behaves like its superclass and adds behavior of its own.
  • This is why inheritance is also called specialization: the subclass represents a more specific group.
  • Every cat is an animal, but not every animal is a cat.
  • The Java class hierarchy starts with the Object class in package java.lang.
  • Every class inherits from Object, directly or indirectly.

The Idea of Inheritance

Kinds of Inheritance

  • Single: one subclass, one superclass. Cat extends Animal.
  • Multilevel: a chain. Cat gets the members of LivingThing through Animal; each level carries everything of the one above.
  • Hierarchical: many subclasses of one superclass. Common code is written once; each subclass adds only its differences.
  • Multiple: a class with several superclasses. Java does not allow this for classes; interfaces cover the same need.
In Java the class hierarchy is a tree: its root is Object, and every class except Object has exactly one direct superclass. Chains can be arbitrarily deep, but deep chains are hard to read and change.

The Idea of Inheritance

Inside a Subclass Object

  • new Cat(...) creates one object; there is no separate object for the superclass.
  • The object also has room for the fields inherited from the superclass. They are there even when private; only Cat’s code cannot name them.
  • super is not a separate object: it is a way to reach the superclass part of the same object through the superclass’s code.

Proof: getClass() in the constructor

class Animal {
    Animal() {
        System.out.println("In Animal(): "
            + getClass().getSimpleName());
    }
}
class Cat extends Animal { }
// in main:
new Cat();
new Animal();
In Animal(): Cat
In Animal(): Animal

Even while the Animal constructor runs, the object’s real class is Cat: the constructor chain builds the parts of the same object in turn.

The Idea of Inheritance

Moving Common Code Up

Generalization: finding fields and methods repeated in several classes and moving them into a common superclass. It is the reverse of specialization.

Before: the same code in two places

class Student {
    private String name;
    private int age;
    private double gpa;
    String info() { return name + " (" + age + ")"; }
}
class Teacher {
    private String name;
    private int age;
    private String subject;
    String info() { return name + " (" + age + ")"; }
}

If the age format changes, both classes must be fixed; forget one and the output is inconsistent.

After: the common part lives in Person

class Person {
    private String name;
    private int age;
    Person(String n, int a) { name = n; age = a; }
    String info() { return name + " (" + age + ")"; }
}
class Student extends Person {
    private double gpa;
    Student(String name, int age, double gpa) {
        super(name, age);
        this.gpa = gpa;
    }
    @Override String info() {
        return super.info() + ", gpa " + gpa;
    }
}   // Teacher likewise: adds subject
Ece (20), gpa 3.4
Murat (41), Physics

Ask before moving: “Is every student a person?” If yes, generalization is right; if the two classes merely share a few fields, composition fits better.

Animal Example

The Animal Class Hierarchy

Common fields and methods are written once, in Animal. Each subclass overrides speak() in its own way and adds a method of its own. In UML, inheritance is drawn as an arrow with a hollow triangle pointing to the superclass.

Animal Example

The Animal and Dog Classes

public class Animal {
    private String name;     // common fields
    private int age;
    private double health;

    public Animal(String name, int age) {
        this.name = name;
        this.age = age;
        this.health = 100.0;

    public String getName() { return name; }   // access to private name
    public void speak() {

    }
    public void sleep() {
        health += 5;

Superclass Animal: the fields and behavior shared by all animals.

public class Dog extends Animal {
    public Dog(String name, int age) {

Benefits of Inheritance

Reuse

Superclass methods and fields are used in the subclass without being rewritten.

Extension

An existing class gains new features without changing its code.

Modification

Superclass methods can be changed in the subclass by overriding them.

public class AdvancedCalculator
        extends Calculator {

Constructors and super

The super Keyword

  • super(...): called inside a subclass constructor, it runs the superclass constructor, which initializes the superclass fields.
  • super(...) must be the first statement of the constructor (before Java 25; Java 25 allows statements that do not touch the object before it).
  • If omitted, the compiler silently inserts super(); (no arguments).
  • super.method(): reaches a superclass method with a dot; used to call the superclass version from inside an overriding method.
  • Principle: each class manages only its own data. Cat does not assign Animal’s name field itself; it leaves that to super(name).
class Cat extends Animal {
    private boolean indoor;

    Cat(String name, boolean indoor) {
        super(name);         // Animal(String)
        this.indoor = indoor;  // its own data
    }

    @Override
    public String toString() {
        return super.toString()   // Animal's
               + ", Indoor: " + indoor;
    }
}
// in main
System.out.println(new Cat("Mavi", true));

Output

Name: Mavi, Health: 100.0, Indoor: true

Animal’s toString() returns the name and health; Cat appends only its own field.

this(...) and super(...): Code Trace

new first allocates the object; all three fields hold default values. Then Manager(String) is called.

The first line, this(name, 5000.0), passes control to the two-argument constructor of the same class. Manager(String) waits before running its body.

super(name): the one-argument constructor of the superclass Employee. Building the Manager part waits until the Employee part is done.

Employee also delegates with this(...). That constructor’s first line is neither this nor super, so the compiler inserts an implicit super(): Object() runs and returns.

The first body runs here: name and salary are set and the first line is printed. The calls went bottom-up; the bodies complete starting from the topmost class.

The two-argument constructor returned; Employee(String) prints its line.

super(name) is done. Only now does the subclass set its own field: bonus = 5000.0.

Finally the first one called, Manager(String), finishes. Four constructors ran, but only one object was built.

The object’s address is stored in y. income() adds the inherited getSalary() to its own bonus: 25000.0.

Initialization Order with Inheritance: Code Trace

For the first new Child(), the JVM must initialize class Child. The superclass goes first: Parent’s static block runs.

Then Child’s static block. Class initialization happens once per program run.

The object is allocated (a and b are 0). Child() first calls an implicit super(); Parent’s field initializers run before the Parent() body: a = value(...).

Then the Parent() body. At this point b is still 0: the Child part has not been initialized at all.

After super() returns, the subclass field initializers run: b = value("Child field").

Last comes the Child() body. Order: superclass fields → superclass constructor → subclass fields → subclass constructor.

Second new Child(): the classes are already initialized, so the static blocks do not run again. The four per-object steps repeat in the same order.

class Parent {
    static { System.out.println("Parent static"); }
    int a = value("Parent field");
    Parent() { System.out.print("Parent(), "); }
    static int value(String s) {
        System.out.print(s + ", ");
        return 1;
    }
}
class Child extends Parent {
    static { System.out.println("Child static"); }
    int b = value("Child field");
    Child() { System.out.println("Child()"); }
}
// in main:
new Child();
new Child();

Overriding

Overriding a Method

Overriding: a subclass rewrites an inherited method with the same signature to give it its own behavior.

  • Name and parameter list must be identical.
  • The return type must be the same (or a subtype).
  • Access cannot be narrowed: a public method stays public.
  • final, static and private methods cannot be overridden.
class Shape {
    public void draw() {
        System.out.println("Drawing a shape.");
    }
}
class Rectangle extends Shape {
    @Override
    public void draw() {
        System.out.println("Drawing a rectangle.");
    }
}
// in main
new Shape().draw();
new Rectangle().draw();
Drawing a shape.
Drawing a rectangle.
// in subclass: void draw()

  draw() in Shape
  attempting to assign weaker access
  privileges; was public
// in subclass: public int draw()
error: draw() in Rectangle cannot override
  draw() in Shape
  return type int is not compatible
  with void

Overriding

The @Override Annotation

  • @Override is an annotation: it states that the method overrides an inherited method.
  • It tells the compiler to check this: if the superclass has no such method, compilation fails.
  • It makes the code easier to read; other developers see at once that the method comes from the superclass.
  • It is optional, but you should always write it: it catches typos immediately.
public class Rectangle extends Shape {
    // override the inherited method
    @Override
    public void draw() {
        System.out.println("Drawing a rectangle.");
    }
}

Typo: Draw (capital D)

    @Override
    public void Draw() { ... }
error: method does not override or implement
  a method from a supertype

Without @Override, Draw() would silently become a new method, and calls to draw() would still run Shape’s version.

Overriding

Covariant Return Types

class Animal {
    Animal reproduce() { return new Animal(); }
    public String toString() { return "Animal"; }
}
class Cat extends Animal {
    @Override
    Cat reproduce() { return new Cat(); }  // subtype
    void meow() { System.out.println("meow"); }
    public String toString() { return "Cat"; }
}
// in main:
Cat k = new Cat();
k.reproduce().meow();   // no cast needed
Animal h = k;
System.out.println(h.reproduce());
meow
Cat
  • An overriding method may return a subtype of the superclass method’s return type: a covariant return type.
  • A caller holding a Cat reference gets a Cat directly; no (Cat) cast is needed.
  • A caller holding an Animal reference loses nothing: a Cat is also an Animal.
  • This works only for reference types; you cannot return long instead of int.

Unrelated type: String reproduce()

Overriding

private Methods Are Not Overridden

class Parent {
    private void greet() { System.out.println("Parent.greet"); }
    void call() { greet(); }
}
class Child extends Parent {
    void greet() { System.out.println("Child.greet"); } // new
}
// in main:
Child a = new Child();
a.call();
a.greet();
Parent.greet
Child.greet

If @Override is added to the method in Child

error: method does not override or implement
  a method from a supertype
  • A private method is invisible to subclasses; a same-named subclass method is an unrelated new one.
  • In Parent.call(), greet() is bound at compile time to Parent’s private method, so Parent.greet is printed even for a Child.
  • Using @Override catches this at compile time.
Likewise for static methods: a subclass static method with the same signature does not override the parent’s, it only hides it.

Overriding

Example: A Product Hierarchy

class Product {
    private String name;
    private double price;
    Product(String name, double price) {
        this.name = name; this.price = price;
    }
    double taxRate() { return 0.20; }
    double salePrice() { return price * (1 + taxRate()); }
    @Override public String toString() {
        double f = Math.round(salePrice() * 100) / 100.0;
        return name + ": " + f + " TL";
    }
}
class Food extends Product {
    Food(String name, double price) { super(name, price); }
    @Override double taxRate() { return 0.01; }
}
class SaleProduct extends Product {
    private double discount;
    SaleProduct(String name, double price, double discount) {
        super(name, price);
        this.discount = discount;
    }
    @Override double salePrice() {
        return super.salePrice() * (1 - discount);
    }
    @Override public String toString() {
        return super.toString()
            + " (" + (int) (discount * 100) + "% off)";
    }
}
Product[] cart = {new Product("Pen", 50),
    new Food("Bread", 10),
    new SaleProduct("Headphones", 1000, 0.25)};
for (Product u : cart) System.out.println(u);
Pen: 60.0 TL
Bread: 10.1 TL
Headphones: 900.0 TL (25% off)
  • Food changes only taxRate(); salePrice() and toString() are not written there, yet they use 1%, because the call inside Product is chosen by the object’s class.
  • SaleProduct does not replace the superclass computation, it extends it: it applies the discount to super.salePrice(). 1000 × 1.20 × 0.75 = 900.

Access and Restriction

The protected Access Level

ModifierSame classSame packageSubclass
(other package)		Everywhere
private✓✗✗✗

  • public: the members are accessible from everywhere. private: only from inside the class.
  • protected sits between the two: the class itself, its subclasses and other classes in the same package can access it.
  • A subclass can reach the private fields of its superclass only through inherited public or protected methods.

Good practice: keep fields private; expose the operations subclasses need as protected methods.

Access and Restriction

A Subtle protected Rule

package animals;
public class Animal {
    protected String name;
    public Animal(String name) {
        this.name = name;
    }
}
package indoor;
import animals.Animal;
public class Cat extends Animal {
    public Cat(String name) { super(name); }
    void compare(Cat k, Animal h) {
        System.out.println(name);    // own field
        System.out.println(k.name);  // via Cat
        System.out.println(h.name);  // via Animal
    }
}
indoor/Cat.java:8: error: name has protected access in Animal
        System.out.println(h.name);
  • A subclass in another package can reach a protected member only through a reference of its own type (or its subtypes): name and k.name are fine.
  • h, however, may point to any Animal, a Dog for example. Cat is not allowed to touch the internals of another subclass.
  • Classes in the same package have no such restriction: there, protected includes package access.

Access and Restriction

Restricting Inheritance with final

  • The final keyword can be used to restrict inheritance.
  • A final method cannot be overridden in any subclass.
  • No class can extend a final class. Examples: String, Math, Integer.
class Animal {
    public final void breathe() { ... }
}
class Cat extends Animal {
    public void breathe() { ... }
}
error: breathe() in Cat cannot override
  breathe() in Animal
  overridden method is final
final class Fixed { ... }
class Test extends Fixed { }
error: cannot inherit from final Fixed
Why? Security and consistency: String must stay immutable, and no subclass should be able to break that promise.

On variables, final means something else: the value is assigned once (a constant).

Access and Restriction

Restricting an Object’s View

  • An object can be assigned to a variable of a superclass type (upcasting): every Tire is a Part.
  • Only the methods of the superclass are then exposed.
  • Whatever the object’s real class, the variable’s type decides what we can call.
Part p = new Tire("Petlas", "XYZ-123", "225/45R17", true);
System.out.println(p.serialNumber());   // allowed → XYZ-123
// p.isWinter()                         // not allowed
error: cannot find symbol
  symbol:   method isWinter()
  location: variable p of type Part

To reach a Tire-only method you need a type check (instanceof) followed by a downcast.

Relationships Between Classes

is-a and has-a Relationships

Is-a (inheritance)

  • One class is derived from another; the subclass is a kind of the superclass.
  • A subclass object can also be used as a superclass object.

Has-a (composition)

  • A class has a field whose type is another class.
  • The object holds references to other objects.
// is-a relationship (inheritance)
public class Car extends Vehicle {
    // has-a relationship (composition)
    private Engine engine;

    public Car(int horsepower) {
        engine = new Engine(horsepower);
    }
    public void drive() {
        engine.start();   // delegate
        accelerate(50);         // inherited
        System.out.println("Speed: " + speed
                           + " km/h");
    }
}
// Engine: field horsepower and start():
//   "Engine started: " + horsepower + " hp"

new Car(110).drive();

Engine started: 110 hp
Speed: 50 km/h

is-a and has-a: Code Trace

new Car(90): one object, holding speed from the superclass Vehicle and its own engine field (is-a).

The constructor creates a second object: a car is not an engine, it has one (has-a). The link is a reference.

drive() runs on the Car object.

engine.start(): Car does not do the work itself; it follows the reference and delegates to the Engine object.

accelerate(50) is not written in Car; it is inherited from Vehicle and sets the same object’s speed to 50.

Inheritance (speed, accelerate) and composition (engine) worked together in one class.

class Engine {
    private int hp;
    Engine(int hp) { this.hp = hp; }
    void start() {
        System.out.println("Engine: " + hp + " hp");
    }
}
class Car extends Vehicle {        // is-a
    private Engine engine;           // has-a
    Car(int hp) { engine = new Engine(hp); }
    void drive() {
        engine.start();  accelerate(50);
        System.out.println("Speed: " + speed);
    }
}
new Car(90).drive();   // main

Design Principles for Inheritance

The “is-a” test

If “every X is a Y” is false, do not use inheritance. A Car is not an Engine; it has one → composition.

Each class manages its own data

Superclass fields get their values through super(...) and superclass methods; fields stay private.

Override the general methods

Every meaningful class should override toString and equals (and, with it, hashCode).

Common concepts go into abstract classes

Concepts shared by subclasses should be modeled with abstract classes, if “Animal” on its own should never be an object.

Fragile Base Class: Code Trace

CountingList extends MyList to count the items added. Both add methods are overridden.

The subclass’s addAll adds the array length to the counter: 3. Then it hands the work to the superclass.

MyList.addAll calls add(s), i.e. this.add(s), for each item. That is an implementation detail of the superclass.

The object is a CountingList, so the call goes to the subclass’s add. The same item is counted a second time: 4.

super.add(s) stores the item in the array: size = 1.

"b" and "c" take the same path: each is counted once more. When the loop ends the counter is 6 and size is 3.

Wrong result: 6 3. The subclass depended on how the superclass uses its own methods. If a new version of the superclass changed the loop, the result would change again: the fragile base class problem.

class MyList {
    private String[] items = new String[10];
    private int size;
    void add(String s) { items[size++] = s; }
    void addAll(String[] arr) {
        for (String s : arr) add(s);
    }
    int size() { return size; }
}
class CountingList extends MyList {
    int addCount = 0;
    @Override void add(String s) {
        addCount++;
        super.add(s);
    }
    @Override void addAll(String[] arr) {
        addCount += arr.length;
        super.addAll(arr);
    }
}
CountingList l = new CountingList();   // main
l.addAll(new String[] {"a", "b", "c"});
System.out.println(l.addCount + " " + l.size());

Relationships Between Classes

The Composition Fix: Forwarding

class CountingList2 {
    private final MyList list = new MyList(); // has-a
    private int addCount = 0;
    void add(String s) {
        addCount++;
        list.add(s);            // forwards
    }
    void addAll(String[] arr) {
        addCount += arr.length;
        list.addAll(arr);  // forwards
    }
    int getAddCount() { return addCount; }
    int size() { return list.size(); }
}
CountingList2 l2 = new CountingList2();
l2.addAll(new String[] {"a", "b", "c"});
System.out.println(l2.getAddCount()
    + " " + l2.size());
3 3
  • The new class does not extend MyList; it has a MyList. Each method does its own work first, then forwards the call to the inner object.
  • The add calls inside list.addAll(...) run on a plain MyList object; they never come back to CountingList2. The count is right: 3.
  • Even if MyList’s internals change, the result does not: the dependency is only on public methods.
  • The price: a CountingList2 cannot be passed where a MyList is expected. If needed, both implement a common interface.

The Liskov Substitution Principle (LSP)

class Rectangle {
    protected int width, height;
    void setWidth(int w) { width = w; }
    void setHeight(int h) { height = h; }
    int area() { return width * height; }
}
class Square extends Rectangle {
    @Override void setWidth(int k) { width = height = k; }
    @Override void setHeight(int k) { width = height = k; }
}
static void resize(Rectangle d) {
    d.setWidth(5);
    d.setHeight(4);
    System.out.println("Expected 20, got "
        + d.area());
}
// in main:
resize(new Rectangle());
resize(new Square());
Expected 20, got 20
Expected 20, got 16
  • Liskov substitution principle: code written against a superclass type must also work correctly with a subclass object. Compiling is not enough.
  • In mathematics every square is a rectangle. But this Rectangle class promises that “width and height change independently”; Square cannot keep that promise.
  • resize is not at fault; the fault lies in the subclass that breaks the promise.
  • Fixes: do not derive Square from Rectangle (both extend Shape), or make the classes immutable.
Apply the is-a test to the class’s behavior, not to the real world: “Can a Square answer every Rectangle method the way a Rectangle does?”

== or equals?

new creates an object; k1 holds its address (reference).

Second new: same contents, but a separate object. k2 points to it.

k3 = k1 copies no object, only the address. k1 and k3 point to the same object.

== compares references: k1 and k2 point to different objects → false.

k1 and k3 point to the same object → true.

Since Person overrides equals, it compares the contents (name, age) → true. Without the override it would be false.

Person k1 = new Person("Ali", 25);
Person k2 = new Person("Ali", 25);
Person k3 = k1;
System.out.println(k1 == k2);
System.out.println(k1 == k3);
System.out.println(k1.equals(k2));

The Object Class

The equals Method

  • public boolean equals(Object other): tells whether two objects are equivalent.
  • By default it compares only references: unless overridden it behaves like the == operator.
  • Overriding changes this: the method should compare the two objects’ state (their fields) and return true if they are equal.
  • The parameter has type Object, so do a type check first to rule out bad cases.

The equals contract

Reflexivex.equals(x) → true
Symmetricx.equals(y) ⇔ y.equals(x)
Transitiveif x = y and y = z, then x = z
ConsistentThe result stays the same while the fields do not change
nullx.equals(null) → false
The same rule applies to String: compare with s1.equals(s2), not s1 == s2.

The Object Class

equals with getClass()

public class Person {
    private String name;
    private int age;
    // ... constructor ...

    @Override
    public boolean equals(Object obj) {
        // same reference: equal
        if (this == obj) return true;
        // null or other class: not equal
        if (obj == null
                || getClass() != obj.getClass())
            return false;
        // compare the fields
        Person p = (Person) obj;
        return age == p.age
               && name.equals(p.name);
    }
}
  • this == obj: the same object returns true at once (fast path).
  • getClass() gives the object’s actual class; both sides must have exactly the same class.
  • Compare primitive fields (int age) with == and object fields (String name) with equals.
Type checkCan a subclass object count as equal?
instanceofYes (a Cat object is an Animal)
getClass()No (the classes must match exactly)

equals(): Code Trace

There are three separate objects. k1 and k2 have the same contents; k3 differs only in age.

k1.equals(k2): in the new frame this = #1 and obj = #2. The type of obj is Object.

this == obj compares addresses: #1 ≠ #2, so the fast path does not apply.

obj is not null and getClass() is Person on both sides. The condition is false, so return false is skipped.

k1.equals(k3): a new call with obj = #3. Different object, same class: on to the fields.

20 == 21 is false; && short-circuits and name.equals is never called. The result is false.

obj == null is true, so || skips its right side. Had obj.getClass() run, it would throw a NullPointerException.

The Object Class

equals and hashCode

Rule: if you override equals, override hashCode too. Equal objects must have the same hashCode.
import java.util.Objects;
public class Point {
    private int x, y;
    public Point(int x, int y) {
        this.x = x; this.y = y;
    }
    @Override public boolean equals(Object o) {
        return (o instanceof Point n)
               && x == n.x && y == n.y;
    }
    @Override public int hashCode() {
        return Objects.hash(x, y);
    }
    @Override public String toString() {
        return "Point[x=" + x + ", y=" + y + "]";
    }
}

Why? HashSet and HashMap first pick a “bucket” by hashCode, then call equals. If the hashCodes differ, equal objects are never compared.

HashSet<Point> set = new HashSet<>();
set.add(new Point(3, 4));
set.add(new Point(3, 4));
System.out.println(set.size() + " "
    + set.contains(new Point(3, 4)));

only equals2 false ✗
equals + hashCode1 true ✓

The pattern o instanceof Point n requires Java 16+; the classic form is if (o instanceof Point) { Point n = (Point) o; … }.

equals and hashCode Inside a HashSet: Code Trace

An empty HashSet: each element goes into one of 16 buckets, chosen by hashCode().

hashCode() = 31·(31+3)+4 = 1058; 1058 % 16 = 2. The bucket is empty: the object is added.

Same numbers, other order: hash 1088, bucket 0. Again an empty bucket, so it is added.

A new Point(3, 4) object: hash 1058 again, the same bucket 2. The bucket is occupied, so equals is asked against its contents.

equals is true: the set does not take the same element twice, and add returns false.

The set holds two elements: 2.

contains also finds the bucket first, then asks equals: true. Without hashCode, equal objects would land in different buckets.

Common Mistakes

Not calling super(...)

If the superclass has no no-arg constructor: constructor Animal in class Animal cannot be applied to given types.

Accessing a private field directly

health += 5; in the subclass: health has private access in Animal. Fix: a getter or a protected method.

Writing equals(Point)

If the parameter is not Object, it is an overload; with @Override: method does not override or implement a method from a supertype.

Comparing objects with ==

For two objects with the same contents == → false. Compare contents with equals, String included.

equals without hashCode

No compile error, but HashSet/HashMap misbehave: the same point is added twice.

Extending two classes

class D extends B, C → '{' expected. Fix: composition or an interface.

Narrowing access

If public void draw() becomes void draw() in the subclass: attempting to assign weaker access privileges.

Unchecked downcast

(Tire) p when p is not a Tire: ClassCastException. Check with instanceof first.

Summary

Common Mistakes (2)

this(...) and super(...) together

Both must be the first statement: call to super must be first statement in constructor. The constructor at the end of the chain calls super(...).

Changing the return type

String reproduce(): return type String is not compatible with Animal. Only a subtype (covariant) is allowed.

Thinking a private method is overridden

No error, but the superclass code still calls its own private version. @Override catches this mistake.

Reaching a protected member via a supertype reference

h.name in a subclass in another package: name has protected access in Animal. Access must go through the subclass’s own type.

Widening the exception list

void f() throws Exception when the superclass method has no throws: overridden method does not throw Exception.

Getting field order wrong

Subclass field initializers run after the superclass constructor finishes; while it runs, they still hold defaults.

Inheritance just to share code

If is-a does not hold, the subclass also gets unwanted public methods: Stack extends ArrayList allows inserting in the middle. Fix: composition.

Overriding a self-calling method

Other superclass methods may call the subclass version too: the counter goes up twice. Fix: read the superclass documentation, or use composition.

class A {
    A() { System.out.println("A"); }
    void print() { System.out.println("A.print"); }
}
class B extends A {
    B() { System.out.println("B"); }
    @Override void print() { System.out.println("B.print"); }
}
class C extends B {
    C() { super(); System.out.println("C"); }
    @Override void print() {
        super.print();
        System.out.println("C.print");
    }
}
  1. What does C c = new C(); print?
  2. What does c.print(); print next?
  3. What does A a = new B(); a.print(); print?
  4. What is c instanceof A?
  5. In a Student class that does not override equals, what is o1.equals(o2) for two objects with the same name?
Show answers
  1. A B C: constructors complete top-down (B’s implicit super() runs A first).
  2. B.print, then C.print: super.print() calls B’s version.
  3. A B, then B.print: the variable has type A, but the object is a B, so B’s version runs.
  4. true: C extends A through B.
  5. false: Object’s equals compares references.
