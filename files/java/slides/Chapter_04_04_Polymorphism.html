The Idea of Polymorphism

Polymorphism

  • Greek poly (many) + morph (form): the same expression leads to different behavior on different objects.
  • A reference can refer to an object of its own type or of any subclass.
  • animal.makeSound() prints Woof woof! for a dog and Meow! for a cat.
  • We write the code once, against the superclass; each object answers the call with its own version.
The four pillars of object-oriented programming: encapsulation, inheritance, polymorphism and abstraction. Polymorphism is built on inheritance.
Remote controlThe same "on" button turns on the TV, the air conditioner and the projector; each device does it in its own way.
Driver's licenseOne license lets you drive any make of car: the driver uses the "car" interface; the engine details belong to the maker.
ZooThe keeper says "everyone, make a sound"; each animal makes its own.

Example Class Hierarchy

class Animal {
  public void makeSound() { System.out.println("Animal sound"); }
  public void run()       { System.out.println("Animal runs"); }
  public void sleep()     { System.out.println("Animal sleeps"); }
}
class Dog extends Animal {
  @Override public void makeSound() { System.out.println("Woof woof!"); }
  @Override public void run() { System.out.println("Dog runs"); }
  public void bark() { System.out.println("Dog barks"); }
}
class Cat extends Animal {
  @Override public void makeSound() { System.out.println("Meow!"); }
  public void scratch() { System.out.println("Cat scratches"); }
}
  • Dog overrides makeSound() and run() and adds bark(); Cat overrides only makeSound() and adds scratch().
  • Dog and Cat are both Animals (is-a); either can be stored in a variable of type Animal.

References and Type Compatibility

The Reference Rule

  • An object of a subclass can be assigned to a reference of the superclass type.
  • But a superclass object cannot be assigned to a reference of the subclass type.

Legal

// Dog is a subtype of Animal
Animal animal = new Dog();
Object obj = new Cat();

Every dog is an animal: a dog can do everything expected of an animal.

Illegal

// Animal is Dog's superclass
Dog dog = new Animal();
error: incompatible types:
  Animal cannot be converted to Dog

An animal may not know bark(); the compiler won't allow it.

Animal h = new Dog(); Dog k = h; gives the same error. The compiler sees the h reference's declared type (Animal), not the object it points to; the fix is an explicit cast.

Type Conversion

Downcasting

  • A superclass reference can be explicitly converted to a subclass type: (Subclass) reference.
  • Only through such a cast can a superclass reference be assigned to a subclass variable.
  • Purpose: to call methods that are not in the superclass (that belong only to the subclass).
  • A cast does not change the object; it only tells the compiler "treat this reference as a Dog".
Animal h2 = new Dog();
Dog k = (Dog) h2;
k.bark();
((Dog) h2).bark(); // in one line
Dog barks
Dog barks

Precedence trap

The dot (.) binds tighter than a cast. Without parentheses, (Dog) is applied to the result of bark():

(Dog) h2.bark();   // wrong
error: not a statement
String s = (Dog) h2.name();
// h2.name() first → not in Animal
error: cannot find symbol
  symbol:   method name()
  location: variable h2 of type Animal

Correct: ((Dog) h2).bark();

Type Conversion

Bad Downcast: ClassCastException

Animal h4 = new Cat();
Dog k4 = (Dog) h4; // compiles!
k4.bark();
Exception in thread "main" java.lang.ClassCastException:
class Cat cannot be cast to class Dog
Dog k5 = (Dog) new Animal(); // compiles!
java.lang.ClassCastException:
class Animal cannot be cast to class Dog
  • The compiler allows it: a reference of type Animal may well point to a Dog.
  • The JVM checks the object's actual class at the cast: if it is a Cat or a plain Animal, the program stops with an exception.
  • So a superclass object can never be assigned to a subclass reference; a cast only succeeds if the object really is of that subclass.
B objB = (B) objA; compiles, but runs only if objA really points to a B object. If unsure, test it first with instanceof.

Casts between unrelated types are rejected outright: (Cat) dog → incompatible types: Dog cannot be converted to Cat.

Long instanceof chains are usually a design smell: it is better to move the behavior into a method overridden in the subclasses (Exercise 5).

Arrays and ArrayStoreException

Dog[] dogs = new Dog[2];

animals[0] = new Dog();
System.out.println("first ok");
animals[1] = new Cat();    // compiles, but...
System.out.println("never reached");

Same idea with a generic list

List<Animal> l = new ArrayList<Dog>();
error: incompatible types: ArrayList<Dog>
  cannot be converted to List<Animal>
  • Arrays are covariant: a Dog is an Animal, so a Dog[] also counts as an Animal[] and the upcast compiles.
  • But the array object is really a Dog[]. Storing a Cat in it through the Animal[] reference looks fine to the compiler; the JVM checks the element type on every store and throws ArrayStoreException.
  • Generic collections close this hole at compile time: a List<Dog> is not a List<Animal>.
  • Covariance is safe for reading (every element is an Animal); the problem only arises when writing.

Dynamic Binding

Dynamic Binding

  • If the reference points to a subclass object, the subclass's method is called.
  • The version called depends not on the variable's declared type but on the object's actual class.
  • The choice is made not at compile time but at run time, hence dynamic (late) binding.
Animal h = new Dog();
h.run();       // Dog's method
h.makeSound(); // Dog's method
h.sleep();     // not in Dog → Animal's
Dog runs
Woof woof!
Animal sleeps

h.run() is resolved in two steps

1. Compile timeThe compiler looks at h's type (Animal): does it have run()? Yes → the call compiles. Otherwise, a compile error.
2. Run timeThe JVM looks at the object: its actual class is Dog → Dog.run() runs.
Rule: the compiler asks "is there one?"; the JVM asks "which one?".

Dynamic Binding

Method Lookup Starts at the Bottom of the Hierarchy

Animal h = new Dog();
h.run();
h.sleep();
System.out.println(h.toString());
// h.bark(); → compile error

The object is a Dog: lookups always start at the bottom, at the actual class.

Dog has run() → lookup ends, the Dog version runs.

Dog has no sleep() → go up one level: found in Animal.

toString() is found at the top, in Object: class name + @ + hex hash code (varies between runs).

h.bark() does not compile: the compiler searches up from the reference type Animal and finds nothing.

Polymorphic Array: Step-by-Step Trace

Animal[] animals = new Animal[3];
animals[0] = new Dog();
animals[1] = new Cat();
animals[2] = new Animal();
for (int i = 0; i < animals.length; i++) {
    animals[i].makeSound();
}

Animal array of 3: the elements are references, initially null.

Element 0 points to a Dog (upcast, automatic).

Element 1 points to a Cat.

Element 2 is a plain Animal object. The array now holds three different forms.

i = 0, 0 < 3 true → loop body.

Same line, different object: the JVM checks the object's class → Dog.makeSound().

i = 1, 1 < 3 true → loop body.

Same line, different object: the JVM checks the object's class → Cat.makeSound().

i = 2, 2 < 3 true → loop body.

Same line, different object: the JVM checks the object's class → Animal.makeSound().

i = 3, 3 < 3 false → the loop ends. One line of code, three behaviors.

Dynamic Binding

Behind the Scenes: The Method Table

  • JVMs usually implement dynamic binding with a per-class method table (virtual method table): each overridable method has a fixed index (slot).
  • A subclass's table starts as a copy of its superclass's; overridden slots are replaced with the new body, and new methods are appended.
  • Every object knows its class. For h.run() the JVM goes object → class → the table's run slot → body. The lookup is one array access; no walking up the hierarchy.

javap -c Main output

47: invokevirtual #15  // Method Animal.run:()V
52: invokevirtual #18  // Method Animal.makeSound:()V

The compiler writes only Animal.run into the bytecode; invokevirtual picks the body from the object's table. Constructors and super.m() use invokespecial, static methods use invokestatic: no table lookup. private methods use invokevirtual since Java 11, but have only one candidate.

Dynamic Binding

Calling an Overridable Method from a Constructor

  • Dynamic binding works even while the object is being constructed: the object is a Label, so the draw() call in the superclass constructor runs Label.draw().
  • But at that moment the subclass field initializers have not run yet: text is still null. The subclass method runs on a half-built object.
  • Had the method used the field rather than just printing it, the program would have crashed.
  • Rule: call only private, final or static methods from a constructor; they cannot be overridden.

If draw() used text.length()

The stack trace tells the story: Label constructor → Component constructor → back to Label's method. <init> is the constructor's name in bytecode.

Overloading: Most Specific Version and Ambiguity

static void show(Object o) { System.out.println("show(Object)"); }
static void show(Animal h) { System.out.println("show(Animal)"); }
static void show(String s) { System.out.println("show(String)"); }
// in main:

Object o = "a";
show(o);
show((Animal) null);
show(Animal)
show(String)
show(Object)
show(Animal)

show(null);

error: reference to show is ambiguous
  both method show(Animal) in Main and
  method show(String) in Main match
  • If several versions apply, the compiler picks the most specific one: Cat fits both Animal and Object; Animal is more specific.
  • null fits every reference type. Animal and String are not related by inheritance, so neither is more specific: an ambiguous call, a compile error.
  • If the applicable versions lie on one chain (Object, Animal, Cat) there is no ambiguity: show(null) picks the lowest, show(Cat).
  • The fix is to set the declared type with an explicit cast: show((Animal) null).

Overloading

The Three Phases of Overload Resolution

1. No boxing

Only exact matches, primitive widening (int → long) and reference widening (String → Object) are tried.

2. Boxing

If phase 1 finds no candidate, boxing and unboxing are tried too: double → Double → Object.

3. Varargs

If there is still no candidate, variable-arity versions such as int... come into play.

  • Once a phase finds at least one candidate, later phases are skipped; the most specific candidate of that phase wins.
  • Result: given f(long) and f(Integer), the call f(5) picks f(long). Widening comes before boxing because boxing arrived in Java 5, and old programs had to keep their behavior.
  • Narrowing (long → int) is never tried; if no phase finds a candidate: no suitable method found for print(boolean).
  • This order is applied at compile time; the chosen signature goes into the bytecode. Which class's body runs for that signature is decided at run time.

Overloading · Step-by-step code trace

Inheritance and Polymorphism

Inheritance and Polymorphism

  • Inheritance is needed to build class hierarchies.
  • Polymorphism requires inheritance: we need a class hierarchy.
  • Inheritance does not require polymorphism: we can inherit just to reuse code.
  • If B is a subclass of A, a B object can act as an A object (not the reverse).
  • Assigning an A reference to a B reference needs a narrowing conversion (cast), written with parentheses.
A objA = new B(); // B acts as an A
B objB = (B) objA; // legal, but
                   // use with care
The last line compiles; at run time, if objA does not point to a B object, a ClassCastException is thrown.

Interfaces also provide polymorphism in Java: any class that implements an interface can be assigned to a reference of that interface type.

Inheritance and Polymorphism

Example: Shape Hierarchy

abstract class Shape {
    private String name;

    public Shape(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public abstract double area();

    public abstract double perimeter();

    public void draw() {
        System.out.println(name + " drawn.");
    }
}

abstract: a method with no body; every subclass must implement it, and new Shape(…) is not allowed.

Inheritance and Polymorphism

Subclasses Override the Methods

class Square extends Shape {
    private double side;
    public Square(double side) {
        super("Square");
        this.side = side;
    }
    @Override
    public double area() {
        return side * side;
    }
    @Override
    public double perimeter() {
        return 4 * side;
    }
    @Override
    public void draw() {
        System.out.println("Square drawn: side " + side);
    }
}

Square: the constructor passes the name up with super("Square"); it overrides all three methods.

class Rectangle extends Shape {
    private double width;
    private double height;
    public Rectangle(double width, double height) {
        super("Rectangle");
        this.width = width;
        this.height = height;
    }
    @Override
    public double area() {
        return width * height;
    }
    @Override
    public double perimeter() {
        return 2 * (width + height);
    }
    // no draw() → Shape's is used
}

Rectangle: overrides area and perimeter but not draw() → Shape.draw() is used.

class Circle extends Shape {
    private double radius;
    public Circle(double radius) {
        super("Circle");
        this.radius = radius;
    }
    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
    @Override
    public double perimeter() {
        return 2 * Math.PI * radius;
    }
    @Override
    public void draw() {
        System.out.println("Circle drawn: radius " + radius);
    }
}

Circle: computes with Math.PI; overrides draw() with its own info.

Why Polymorphism?

With type tests

static double badArea(Shape s) {
    double area;
    if (s instanceof Square) {
        area = ((Square) s).area();
    } else if (s instanceof Rectangle) {
        area = ((Rectangle) s).area();
    } else if (s instanceof Circle) {
        area = ((Circle) s).area();
    } else {
        area = 0; // new type forgotten!
    }
    return area;
}

Every new shape means changing this method; forget it and badArea(new RightTriangle(3, 4)) silently returns 0.0.

Polymorphic

static double totalArea(Shape[] arr) {
    double total = 0;
    for (Shape shape : arr) {
        // each object knows its area
        total += shape.area();
    }
    return total;
}
  • Just add a new RightTriangle extends Shape class; this code never changes.
  • { Square(5), Rectangle(4, 6), RightTriangle(3, 4) } → 55.0
  • Shorter code, and no ClassCastException risk.

Principle: open for extension, closed for modification (open/closed principle).

Inheritance and Polymorphism

Polymorphic Parameters and Return Values

class Vet {
    void examine(Animal h) {     // any subclass
        System.out.print("Exam: ");
        h.makeSound();
    }
    static Animal adopt(String kind) { // hidden
        if (kind.equals("cat")) return new Cat();
        return new Dog();
    }
}
// in main:
Vet v = new Vet();
v.examine(new Cat());
Animal h = Vet.adopt("dog");
v.examine(h);
System.out.println(h.getClass().getSimpleName());
Exam: Meow!
Exam: Woof woof!
Dog
  • Parameter of superclass type: the method accepts objects of every subclass, existing or yet to be written. examine needs no change for a new Bird class.
  • Return type of superclass type: the method hides which subclass it creates. The caller relies only on the Animal contract; if adopt starts returning another subclass, client code is unaffected.
  • Methods that create objects like this are called factory methods.
  • General rule: choose the most general type for parameters and variables that still does the job.

Inheritance and Polymorphism

equals and Inheritance: The Symmetry Trap

Object methods are dynamically bound too: Object o = k1; System.out.println(o); runs the object's own toString, and o.equals(x) its own equals.

class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }
    @Override public boolean equals(Object o) {
        if (!(o instanceof Point)) return false;
        Point n = (Point) o;
        return x == n.x && y == n.y;
    }
    @Override public int hashCode() { return 31 * x + y; }
}
class ColoredPoint extends Point {
    final String color;
    ColoredPoint(int x, int y, String color) {
        super(x, y);
        this.color = color;
    }
    @Override public boolean equals(Object o) {
        if (!(o instanceof ColoredPoint)) return false;
        ColoredPoint r = (ColoredPoint) o;
        return super.equals(r) && color.equals(r.color);
    }
}
Point p = new Point(1, 2);
ColoredPoint k =
    new ColoredPoint(1, 2, "red");
System.out.println(p.equals(k)
    + " " + k.equals(p));
true false
  • The receiver object decides which equals runs: p.equals(k) runs Point's, k.equals(p) runs ColoredPoint's.
  • The results differ: symmetry is broken. A HashSet or contains may answer differently depending on the order of elements.
  • Fixes: compare getClass() in both classes; or use composition instead of inheritance (ColoredPoint holds a Point field).

Common Mistakes (2): Run Time and Logic

Unchecked downcast

Writing (Dog) h and forgetting that h may point to a Cat → ClassCastException. Test with instanceof first.

Thinking "a cast changes the object"

(Animal) dog does not turn the dog into an animal; makeSound() still prints "Woof woof!".

Thinking fields are overridden too

h.kind is read by the reference type ("animal"). Fix: make fields private and override a getter instead.

Confusing overloading with overriding

Writing equals(Person p) in a subclass does not override equals(Object), it overloads it; collections never call this method. @Override catches this mistake.

== to compare objects

== compares references; for content, use the overridden equals.

instanceof chains everywhere

They break as subclasses are added. Move the behavior into an overridden method.

Summary

Common Mistakes (3)

Calling an overridable method from a constructor

The subclass method runs on an object whose fields are not yet set: null output or NullPointerException.

Relying on array covariance

Animal[] d = new Dog[2]; d[1] = new Cat(); compiles, but at run time: ArrayStoreException: Cat.

Ambiguous call with null

show(null), with two unrelated overloads: reference to show is ambiguous. Resolve it with an explicit cast.

Thinking boxing comes first

With f(long) and f(Integer), f(5) → f(long): widening is in phase 1.

Extending equals one-way in a subclass

p.equals(k) true, k.equals(p) false: symmetry breaks, collections behave inconsistently.

Treating a generic list like an array

List<Animal> l = new ArrayList<Dog>(); → incompatible types. Generics are not covariant.

class A {

}

// in main:

a.call();

call() is defined only in A and calls print(). B overrides only print(). What does the program print?

Answer 
B.print
A.print
  • a.call(): B has no call → A.call() runs.

Sample Problem 3: Overloading + Overriding

class Parent {
    void f(Object o) {
        System.out.println("Parent.f(Object)");
    }

    void f(String s) {
        System.out.println("Parent.f(String)");
    }
}

class Child extends Parent {
    @Override
    void f(Object o) {
        System.out.println("Child.f(Object)");
    }
}

// in main:
Parent u = new Child();
Object o = "hello";
u.f(o);
u.f("hello");

Parent has two overloaded f methods; Child overrides only f(Object). What do the two calls print?

Answer 
Child.f(Object)
Parent.f(String)
  1. The compiler picks the version: o's declared type is Object → f(Object). At run time the object is a Child → overridden version: Child.f(Object).
  2. Argument String → best version f(String). Child doesn't override it, so Parent.f(String).

Overloading first (compile time, declared type), then overriding (run time, object type).

Sample Problem 4: Construction, Phases, Arrays

class Parent {
    Parent() { show(); }
    void show() { System.out.println("Parent"); }
}
class Child extends Parent {
    private int[] arr = {1, 2, 3};
    @Override void show() {
        System.out.println(arr == null
            ? "no arr" : "length " + arr.length);
    }
}
  1. new Child(); and then new Child().show(); print what?
  2. Given f(long), f(Integer), f(Object) and f(int...), which versions do short s = 3; f(s);, f('A'); and f(Long.valueOf(4)); choose?
  3. Object[] d = new String[1]; d[0] = 1;: compiles? runs?
Show answers
  1. no arr, then no arr and length 3: during every new Child(), Parent() calls Child.show() before arr is assigned; after construction arr is ready.
  2. f(long), f(long), f(Object): short and char widen to long. For Long, f(long) needs unboxing; the only phase-1 candidate is Object.
  3. Compiles, but at run time ArrayStoreException: java.lang.Integer: 1 is boxed to Integer and cannot be stored in an array that is really a String[].
