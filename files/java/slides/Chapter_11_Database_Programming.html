Database Concepts

Why Do Databases Matter?

  • A program's variables and objects live in RAM: they are lost when the program exits.
  • Persistent storage keeps data for the long term, after the program has exited. Student grades, bank accounts and game scores must all persist.
  • A database is an organized collection of data that is easy to query. The software that manages it is a database management system (DBMS).
  • Analogy: a database is like a library's cataloged archive; you find a book without walking every shelf.

Database Concepts

Files or a Database?

Plain files can be enough for some applications (a settings file, a log, a short list). As data grows and gets complex, you need a database: it offers key features for processing data efficiently.

FeatureFlat file (txt, csv)Database
SearchThe file is read start to endFast with an index; a one-line SQL query
UpdateOften the whole file is rewrittenOnly the affected row changes
Concurrent accessTwo programs writing at once can corrupt dataSafe with locking and transactions
ConsistencyFormat checking is entirely up to the programmerData types and constraints (NOT NULL, UNIQUE, CHECK)
SecurityFile permissions: all or nothingRights per user, table and field (server DBMSs; file permissions in SQLite)
After a crashA half-done write can corrupt the fileA half-done transaction is rolled back

Database Concepts

Key Features

Fast data access

Indexes find a record among millions of rows in no time.

Field-level security

Rights can be granted per table or even per column: only accounting sees the salary column (in server DBMSs, e.g. PostgreSQL/MySQL GRANT; SQLite has no users or rights, access depends on file permissions).

Portable, standard APIs

SQL is a standard; in Java, JDBC reaches different databases through one interface.

Independence from file layout

The program doesn't know how data is stored. It says what it wants in SQL; the DBMS decides how.

On top of these, databases offer integrity constraints and transaction support.

Database Concepts

The Relational Model: Tables, Rows, Columns

  • A relational database stores data in tables.
  • Column: one attribute of the data, with a name and a data type (name TEXT).
  • Row: all the information about one entity (one user).
  • Primary key: identifies each row uniquely; no two rows share an id.
  • Java analogy: table ≈ class, column ≈ field, row ≈ object.

Database Concepts

Kinds of Databases

Relational

Tables and SQL. Oracle, SQL Server, MySQL, PostgreSQL. About 77% of usage.

NoSQL / search

Table-less models such as documents, key–value stores and search indexes, used in specific scenarios: MongoDB, Elasticsearch (about 23%).

Embedded relational

SQLite: a relational database that runs inside the program; common where little data is shared.

The examples use SQLite, the easiest to set up. SQL and JDBC code is almost the same for other relational databases.

SQLite

What Is SQLite?

  • An embedded relational database: it runs as a library inside the program.
  • Serverless: no separate program, installation or administrator.
  • Self-contained: all tables are stored in a single disk file (e.g. sample.db).
  • Cross-platform: the same file opens on Windows, Linux, macOS and Android.
  • Easy to install and use; open source and free.
  • The most widely used embedded relational database in the world.

Common uses

  • Mobile apps
  • Embedded systems
  • Small-scale applications
  • Desktop programs such as browsers and e-mail clients

Not a good fit for

  • Large systems where many users write at once over a network

SELECT: Filtering, Sorting, Limiting

QueryResult
SELECT player, score FROM scores
WHERE score < 90 ORDER BY score DESC		naz 81, ada 72, ece 58

ORDER BY score DESC, player LIMIT 3		can 95, efe 95, naz 81

SQL Basics · Step-by-step trace

How Does a SELECT Query Run?

String sql = "SELECT player, score FROM scores "
           + "WHERE score > 70 "
           + "ORDER BY player DESC LIMIT 2";
try (Statement st = conn.createStatement();
     ResultSet rs = st.executeQuery(sql)) {
  while (rs.next()) {
    System.out.println(rs.getString("player") + " "
                       + rs.getInt("score"));
  }
}

The query is a single string. The scores table has 5 rows.

executeQuery sends the query. The database starts with FROM: every row of the table.

WHERE score > 70: ece fails the condition and is dropped; 4 rows remain.

ORDER BY player DESC: names are sorted in reverse alphabetical order (not by score).

LIMIT 2: the first two rows of the sorted list form the result set.

The cursor starts before the first row; next() moves it to row 1.

The columns are read by name and printed.

The cursor moves to row 2.

efe 95 is printed.

No more rows: next() returns false and the loop ends. When the try ends, rs and st are closed.

Relations and Grouping

Avoiding Repetition: Normalization

  • In one table, the same fact (Ali's phone) is repeated in every order: wasted space and a risk of inconsistency.
  • Update anomaly: when the phone changes, every row must be fixed; miss one and Ali has two different phones.
  • Insert anomaly: a customer with no orders yet can't be recorded.
  • Delete anomaly: deleting Ece's only order loses Ece's details too.
  • Normalization: split the tables so each fact is kept in one place. The tables are linked by a key (customer_id).
  • First normal form: one value per cell. A list like '555-11, 555-33' moves to separate rows or a separate table.

Relations and Grouping

Foreign Keys and Relationships

CREATE TABLE depts (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL);
CREATE TABLE students (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  dept_id INTEGER REFERENCES depts(id));
  • A foreign key is a column that points to another table's primary key. A dept can have many students: a one-to-many relationship.
  • Adding a student to a missing dept (dept_id = 9) or deleting a dept that has students is rejected: FOREIGN KEY constraint failed.
  • SQLite doesn't check this by default: every connection needs stmt.execute("PRAGMA foreign_keys = ON"). With it off, dept_id = 9 is silently accepted.
  • A many-to-many relationship (student–course) needs a third, linking table: enrollments(student_id, course_id).
  • Java analogy: a Dept reference inside a Student object.

Relations and Grouping

Combining Tables with JOIN

SELECT s.name AS student, d.name AS dept
FROM students s JOIN depts d
  ON s.dept_id = d.id
ORDER BY s.id
studentJOIN (INNER)LEFT JOIN
AdaCSCS
BoraEEEE
CemCSCS
Denizno rowNULL
  • A JOIN matches the rows of two tables by the ON condition and produces one result table.
  • s and d are table aliases. Both tables have a name column, so we write s.name and d.name; a bare name gives ambiguous column name: name.
  • AS renames a result column: Java reads it with rs.getString("dept").
  • INNER JOIN (plain JOIN): only rows that have a match. Deniz, whose dept is NULL, is missing from the result.
  • LEFT JOIN: every row of the left table; with no match the right side is NULL, null in Java.
  • Forget ON (FROM students, depts) and every row pairs with every row: a 12-row Cartesian product, 4 × 3.

A JOIN Query, Step by Step

String sql = "SELECT s.name AS student, d.name AS dept "
    + "FROM students s JOIN depts d "
    + "ON s.dept_id = d.id ORDER BY s.id";
try (ResultSet rs = stmt.executeQuery(sql)) {
  while (rs.next()) {
    System.out.println(rs.getString("student") + " - "
        + rs.getString("dept"));
  }
}

The query refers to the two tables by aliases: s = students, d = depts.

executeQuery: Ada's dept_id is 1; id = 1 is found in depts → (Ada, CS).

Bora → 2 → EE.

Cem → 1: the same dept row is used a second time.

Deniz's dept_id is NULL: it equals no id, so the row doesn't make it into the result.

next() moves to the first row; the columns are read by the names given with AS.

The second row is printed.

The third row is printed.

No more rows; the loop ends. With LEFT JOIN, a fourth row Deniz - null would appear.

Relations and Grouping

Grouping: GROUP BY and HAVING

  • GROUP BY collects rows with the same value into a group; aggregate functions (COUNT, SUM, AVG, MIN, MAX) are computed per group.
  • WHERE filters rows before grouping, HAVING filters groups after it. WHERE SUM(amount) >= 150 is an error: misuse of aggregate: SUM().
  • Logical order of evaluation: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
Query (SELECT customer, COUNT(*), SUM(amount) FROM orders …)Result
GROUP BY customerAli (3, 200) · Can (1, 200) · Ece (2, 120)
WHERE amount >= 50 GROUP BY customerAli (2, 170) · Can (1, 200) · Ece (1, 80)
GROUP BY customer HAVING SUM(amount) >= 150Ali (3, 200) · Can (1, 200)

With a JOIN: SELECT d.name, COUNT(s.id) FROM depts d LEFT JOIN students s ON s.dept_id = d.id GROUP BY d.id → CS 2 · EE 1 · ME 0. COUNT(s.id) skips NULLs; with COUNT(*), ME, which has no students, would get 1.

Relations and Grouping · Step-by-step trace

A GROUP BY Query, Step by Step

String sql = "SELECT customer, COUNT(*) AS num, "
    + "SUM(amount) AS total FROM orders "
    + "GROUP BY customer HAVING SUM(amount) >= 150 "
    + "ORDER BY total DESC, customer";
try (ResultSet rs = stmt.executeQuery(sql)) {
  while (rs.next()) {
    System.out.println(rs.getString("customer") + ": "
        + rs.getInt("num") + " orders, "
        + rs.getInt("total") + " TL");
  }
}

The orders table has 6 rows; the query is a single string.

FROM and GROUP BY customer: the rows are split into three groups by customer name.

For each group, COUNT(*) and SUM(amount): Ali 120 + 50 + 30 = 200, Can 200, Ece 80 + 40 = 120.

HAVING SUM(amount) >= 150: Ece's group is dropped (120).

ORDER BY total DESC, customer: Ali and Can tie at 200; the second key is the name, so Ali comes first.

next() moves to the first row; the aliases (num, total) are read as column names.

The second row is printed.

The loop ends. The result has one row per group; individual orders don't appear.

Relations and Grouping

NULL: The Absence of a Value

  • NULL means “unknown / missing”; it is not 0 or empty text ('').
  • Any comparison with NULL gives an unknown result: WHERE dept_id = NULL selects no rows. Use IS NULL or IS NOT NULL.
  • WHERE dept_id <> 1 doesn't select Deniz either: we don't even know that NULL differs from 1.
  • NULL + 1 is NULL. COALESCE(dept_id, 0) puts 0 in place of NULL.
  • COUNT(*) counts rows, COUNT(dept_id) non-NULL values: 4 and 3. With no matching rows, AVG and SUM return NULL.
String sql = "SELECT name, dept_id FROM students "
    + "WHERE id >= 3";
try (ResultSet rs = stmt.executeQuery(sql)) {
  while (rs.next()) {
    int d = rs.getInt("dept_id");
    boolean none = rs.wasNull();
    System.out.println(rs.getString("name") + " " + d
        + (none ? " (NULL)" : ""));
  }
}
Output
Cem 1
Deniz 0 (NULL)
  • getInt returns 0 for NULL; to tell 0 from NULL, call wasNull() right after.
  • wasNull() looks at the last column read: called after getString("name"), it would ask about the name and (NULL) would never print.
  • getString and getObject return null for NULL.

Relations and Grouping

Indexes: Faster Searches

CREATE INDEX idx_stu_name ON students(name);
EXPLAIN QUERY PLAN
  SELECT * FROM students WHERE name = 'Cem';
  • An index is an extra structure (a B-tree) that keeps a column's values sorted, like the index at the back of a book. A search goes to the right row instead of scanning the whole table.
  • Primary keys and UNIQUE columns get an index automatically.
  • The cost: every INSERT, UPDATE, DELETE updates the index too, and the index takes disk space. Put indexes on columns searched often and used in WHERE, JOIN and ORDER BY.
  • EXPLAIN QUERY PLAN (SQLite) shows how a query will be executed.
CaseEXPLAIN QUERY PLAN output
No indexSCAN students
With the indexSEARCH students USING INDEX idx_stu_name (name=?)
WHERE id = 3SEARCH … USING INTEGER PRIMARY KEY (rowid=?)
WHERE name LIKE '%em'SCAN students (a leading wildcard can't use the index)

JDBC

JDBC (Java Database Connectivity)

  • JDBC (Java Database Connectivity) is Java's standard API for connecting to databases; it lives in java.sql and ships with the JDK.
  • The program uses only the JDBC interfaces; each database vendor supplies a driver that implements them.
  • Switching databases usually changes only the driver jar and the connection URL.
  • Polymorphism at work: Connection is an interface; in SQLite the real object's class is org.sqlite.jdbc4.JDBC4Connection.

JDBC

All of them are in java.sql: put import java.sql.*; at the top of the file. Connection, Statement and ResultSet are resources that must be closed (AutoCloseable).

JDBC

The Steps of a JDBC Program

try (Connection conn = DriverManager.getConnection(url); // 1
     Statement stmt = conn.createStatement();             // 2
     ResultSet rs = stmt.executeQuery(sql)) {             // 3
  while (rs.next()) {                                     // 4
    System.out.println(rs.getInt(1));
  }
} // 5: rs, stmt, conn auto-closed in reverse
  • Resources are opened in the try-with-resources parentheses; when the block ends (even on an error) they close in reverse order: first rs, then stmt, finally conn.
  • Unclosed connections can leave the file locked and leak memory.
  • getInt(1): column numbers start at 1.

Basic Operations

Connecting to SQLite

// Path to the database file (connection URL)
String url = "jdbc:sqlite:sample.db";
try (Connection conn = DriverManager.getConnection(url)) {
  // Print a message if connected.
  if (conn != null) {
    System.out.println("Connected!");
  }
} catch (SQLException e) {
  // Print the error message on failure.
  System.out.println(e.getMessage());
}
Output
Connected!
  • getConnection creates the file if it doesn't exist (an empty database).
  • If it can't connect, it doesn't return null; it throws SQLException. if (conn != null) is just an extra safeguard.
  • SQLException is a checked exception: catch it or declare it with throws.

Basic Operations

Creating a Table

String url = "jdbc:sqlite:sample.db";
String sql = "CREATE TABLE IF NOT EXISTS users "
           + "(id INTEGER PRIMARY KEY, name TEXT, email TEXT)";
try (Connection conn = DriverManager.getConnection(url);
     Statement stmt = conn.createStatement()) {
  // Create the table.
  stmt.execute(sql);
  System.out.println("Table created!");
} catch (SQLException e) {
  System.out.println(e.getMessage());
}
Output
Table created!
  • execute(sql) runs any SQL; it returns true if it produced a result set, false for CREATE.
  • Thanks to IF NOT EXISTS, running the program again is no error. Without it: table users already exists.
  • Several resources go in one try (…; …), separated by ;.

Reading Data

String url = "jdbc:sqlite:sample.db";
String sql = "SELECT * FROM users";

ID: 1, Name: Ahmet Yılmaz, Email: ahmet@example.com

  • rs.next() moves the cursor to the next row; it returns true if there is one, false otherwise.
  • getInt("id"), getString("name"): read the current row's columns by name.

Basic Operations · Step-by-step trace

What Does executeUpdate Return?

String[] names = {"stapler", "scissors", "tape"};
int[] stock = {40, 0, 15};
PreparedStatement ins = conn.prepareStatement(
    "INSERT INTO supplies(name, stock) VALUES(?, ?)");
for (int i = 0; i < names.length; i++) {
  ins.setString(1, names[i]);
  ins.setInt(2, stock[i]);
  ins.executeUpdate();
}
int u = stmt.executeUpdate(
    "UPDATE supplies SET stock = stock + 10 WHERE stock < 20");
int d = stmt.executeUpdate("DELETE FROM supplies WHERE stock > 100");
System.out.println(u + " updated, " + d + " deleted");

The insert statement is prepared once; in the loop only the values change.

On the first pass the placeholders are filled.

executeUpdate returns 1; SQLite assigns id = 1.

The same prepared statement runs again with new values.

The third item is inserted; when i = 3 the loop ends.

WHERE stock < 20 picks scissors (0) and tape (15); 10 is added to both. The return value is the number of rows affected: 2.

No item has more than 100 in stock: no error, just 0.

From these counts the program can give accurate messages such as "record not found".

SQL Injection

String input = "x' OR '1'='1";   // the "name" the user typed

// DANGEROUS: input pasted into the SQL text
String sql = "SELECT name FROM people WHERE name = '"

PreparedStatement

PreparedStatement and Placeholders

static void add(Connection conn, String name, String surname,
                 int age) throws SQLException {
  String sql = "INSERT INTO people(name, surname, age) "
             + "VALUES(?, ?, ?)";
  try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, name);      // 1st question mark
    ps.setString(2, surname);   // 2nd question mark
    ps.setInt(3, age);          // 3rd question mark
    ps.executeUpdate();
  }
}

Why?

  • Safe: prevents SQL injection.
  • No quoting trouble: "O'Brien" is stored without a hitch.
  • The same statement is reused with different values.

setXxx(index, value) fills each ?; the index starts at 1. Then call executeUpdate() with no arguments.

From Rows to Objects: The DAO Pattern

class Student {
  private final int id;
  private final String name;
  Student(int id, String name) {
    this.id = id;
    this.name = name;
  }
  public String toString() {
    return "#" + id + " " + name;
  }
}
StudentDao methodSQLReturns
add(name, dept)INSERTthe new id
find(id)SELECT … WHERE id = ?a Student or null
inDept(dept)SELECT … WHERE dept_id = ?List<Student>
delete(id)DELETEdeleted? (boolean)
  • In an object-oriented program, each row becomes an object: table ≈ class, row ≈ object.
  • A DAO (Data Access Object) gathers all of a table's SQL in one class. The rest of the program never sees SQL.
  • If the database changes, only the DAO changes. The DAO gets its connection through the constructor.
  • ORM (object-relational mapping) libraries such as JPA and Hibernate do this mapping automatically.

From Rows to Objects, Step by Step

static List<Student> inDept(Connection conn,
    int dept) throws SQLException {
  List<Student> list = new ArrayList<>();
  String sql = "SELECT id, name FROM students "
      + "WHERE dept_id = ? ORDER BY id";
  try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setInt(1, dept);
    try (ResultSet rs = ps.executeQuery()) {
      while (rs.next()) {
        list.add(new Student(rs.getInt("id"),
                             rs.getString("name")));
      }
    }
  }
  return list;
}
// inside main:
List<Student> list = inDept(conn, 1);
for (Student s : list) System.out.println(s);

main calls the method with dept = 1. The connection is open in main.

An empty list is created; the query is prepared with ?.

? = 1 is bound and the query runs: dept 1 has Ada and Cem.

First row: id = 1, name = Ada are read; new Student(1, "Ada") is added to the list.

The second row gives a second object: Student #3 Cem.

next() is false: the try blocks end and rs and ps close. The connection is closed by main, which opened it.

The method returns a List<Student> (2 items); its frame leaves the stack.

Each object is printed via toString(). main knows nothing about SQL.

Transactions

Transactions and ACID

  • A transfer: add 300 TL to Ece's account and take 300 TL from Ali's. If one of the two UPDATEs happens and the other doesn't, money is created from nothing or lost.
  • A transaction is one or more SQL statements run as a single unit of work: all or nothing.
  • JDBC's default is auto-commit: every statement is permanent at once.
  • conn.setAutoCommit(false) → statements → conn.commit() (make permanent) or conn.rollback() (undo).
Atomicity

The transaction is applied entirely or not at all.

Consistency

After the transaction, all constraints hold (e.g. balance ≥ 0).

Isolation

Concurrent transactions don't see each other's half-done state.

Durability

Committed data survives even a power cut.

Transactions

A Transfer: Setup and Result

static final String DEPOSIT =
    "UPDATE accounts SET balance = balance + ? WHERE id = ?";
static final String WITHDRAW =
    "UPDATE accounts SET balance = balance - ? WHERE id = ?";

public static void main(String[] args) throws SQLException {
  String url = "jdbc:sqlite::memory:";  // in memory, temporary
  try (Connection conn = DriverManager.getConnection(url);
       Statement st = conn.createStatement()) {
    st.execute("CREATE TABLE accounts (id INTEGER PRIMARY KEY, "
        + "owner TEXT, balance INTEGER CHECK (balance >= 0))");
    st.execute("INSERT INTO accounts(owner, balance) "
        + "VALUES ('Ali', 1000), ('Ece', 500)");
    transfer(conn, 1, 2, 300);    // Ali → Ece 300 TL
    transfer(conn, 1, 2, 5000);   // Ali can't afford it
    printAll(conn);
  }
}
Output
300 TL transferred.
Rolled back: 5000 TL
Ali: 700
Ece: 800
  • CHECK (balance >= 0): a statement that drives a balance negative throws SQLException.
  • In the second transfer, 5000 TL had already been deposited to Ece; rollback undid that too.
  • printAll is a SELECT loop, like list.

Transactions

commit and rollback, Step by Step

Auto-commit is turned off: from now on, changes are tentative until commit.

300 TL is deposited to Ece: 500 → 800.

300 TL is withdrawn from Ali: 1000 → 700. The constraint holds.

commit(): both changes become permanent together.

finally: auto-commit is turned back on; the method ends.

Second call: 5000 TL is deposited to Ece (tentatively): 800 → 5800.

700 − 5000 would be < 0: the CHECK fails and SQLException is thrown.

rollback(): the tentative deposit is undone too. No money was lost or created.

static void transfer(Connection conn, int from, int to,
                     int amount) throws SQLException {
  conn.setAutoCommit(false);         // transaction starts
  try (PreparedStatement p1 = conn.prepareStatement(DEPOSIT);
       PreparedStatement p2 = conn.prepareStatement(WITHDRAW)) {
    p1.setInt(1, amount);  p1.setInt(2, to);
    p1.executeUpdate();              // deposit to receiver
    p2.setInt(1, amount);  p2.setInt(2, from);
    p2.executeUpdate();              // withdraw from sender
    conn.commit();                   // make permanent
    System.out.println(amount + " TL transferred.");
  } catch (SQLException e) {
    conn.rollback();                 // undo
    System.out.println("Rolled back: " + amount + " TL");
  } finally {
    conn.setAutoCommit(true);
  }
}

Batching: addBatch and executeBatch

conn.setAutoCommit(false);
try (PreparedStatement ps = conn.prepareStatement(
        "INSERT INTO readings(value) VALUES(?)")) {
  for (int i = 1; i <= 1000; i++) {
    ps.setInt(1, i);
    ps.addBatch();
  }
  int[] result = ps.executeBatch();
  conn.commit();
  System.out.println(result.length + " statements, "
      + "the first affected " + result[0] + " row");
} catch (SQLException e) {
  conn.rollback();
  throw e;
} finally {
  conn.setAutoCommit(true);
}
Output
1000 statements, the first affected 1 row
  • addBatch() adds the filled-in statement to a queue; executeBatch() sends the whole queue and returns each statement's affected row count as an int[].
  • With auto-commit on, every INSERT is its own transaction and is written to disk separately. In one test with a .db file on disk, 1000 rows took about 2.6 s one by one and about 0.01 s batched in one transaction (varies by machine).
  • It is all one transaction, so if one fails, rollback() undoes the whole queue's effect: all or nothing.
  • For very large loads, send the queue in pieces (e.g. an executeBatch every 500 addBatches) so memory doesn't balloon.
