Encapsulation and Information Hiding

Encapsulation

  • Encapsulation: bundling an object's data (fields) and the methods that work on it into one unit, the class.
  • The data is hidden (private); outside code can call only the methods the class offers.
  • Analogy: a medicine capsule. You never see the powder inside; you just swallow the capsule. Likewise, a class is the guardian of its own data: an invalid value (e.g. second 75) cannot get in.

Encapsulation is one of the four pillars of object-oriented programming (the others: inheritance, polymorphism, abstraction).

Encapsulation and Information Hiding

Information Hiding

  • Information hiding is also called abstraction. A design should separate what is done from how it is done.
  • A method should be usable without knowing its internals: knowing what it does should be enough.
  • In a car we see and use the brake, the gas pedal and the steering wheel; we don't know their inner mechanics.

The same idea applies in code: we use System.out.println all the time without knowing how printing to the screen works.

Preconditions and Postconditions

Preconditions and Postconditions

Precondition

A condition assumed true before the method is called. Ensuring it is the caller's responsibility.

public class DataService {
    // Precondition: data != null
    public void addData(String data) {
        // check whether data is null
        // ...
    }
}

Postcondition

If the precondition held, the state guaranteed to be true after the method finishes. Ensuring it is the method's responsibility.

public class DataService {
    // Postcondition: returns true if data was added
    public boolean addData(String data) {
        // check whether the data was added
        // ...
        return true;
    }
}
Together they form the method's contract: “Give me non-empty data, and I will add it and return true.” The user knows only the contract, not the body.

Preconditions and Postconditions

Contract: A Complete Example

public class DataService {
  private int count = 0;

  /**
   * Adds a record to the database.
   * Precondition: data is not null or empty.
   * Postcondition: returns true if added,
   *   and count grows by 1.
   */
  public boolean addData(String data) {
    if (data == null || data.isEmpty()) {
      return false;   // precondition broken
    }
    // ... add data to the database ...
    count++;
    return true;      // postcondition met
  }

  public int getCount() {
    return count;
  }
}
// in main:
DataService service = new DataService();
System.out.println(service.addData("Ali"));
System.out.println(service.addData(""));
System.out.println(service.addData(null));
System.out.println(service.getCount());

false
false
1
  • /** ... */ is a Javadoc comment: it explains how to use the method.
  • If the precondition is broken, the method adds nothing and returns false.

Preconditions and Postconditions

Writing the Contract with Javadoc

/**
 * Withdraws money from the account.
 * @param amount sum to withdraw; {@code 0 < amount <= balance}
 * @return the balance after the call (old balance - amount)
 * @throws IllegalArgumentException if amount is out of range
 */
public double withdraw(double amount) {
    if (amount <= 0 || amount > balance)
        throw new IllegalArgumentException("Invalid amount: " + amount);
    balance -= amount;
    return balance;
}
Tags

@param: each parameter and its precondition. @return: the return value, i.e. the postcondition. @throws: what happens when the contract is broken.

Generating docs

Write what the method does and how to use it. How it does it stays out: that is the hidden implementation, and it may change.

For whom?

For the user, who never sees the body. A class's interface is its signatures plus these comments.

Access Modifiers

Access Modifiers

  • Access modifier: a keyword that sets who can access a class, field or method.
  • public: other classes can access it directly.
  • private: accessible only from within the class; the compiler blocks outside access.
  • Classes are usually public.
  • Fields are usually private.
  • Fields are read and changed through public methods.
public class Student {      // public class
    private String name;      // hidden field
    private int grade;        // hidden field

    public int getGrade() {   // public method
        return grade;
    }
}

Rule: fields hidden, behavior public.

Access Modifiers

  • With no modifier, package access (package-private, “default”) applies: only classes in the same package have access.
  • protected is for subclasses: a subclass in another package also has access.
  • As a rule, prefer the most restrictive level: start with private, and open up only when truly needed.
  • A top-level class can only be public or package-private.

Access Modifiers

Trying to Access a private Field

public class Test {
    public static void main(String[] args) {
        DigitalClock s = new DigitalClock();
        s.second = 75;
    }
}
Test.java:4: error: second has private access in DigitalClock
        s.second = 75;
         ^
1 error
  • second is declared private in DigitalClock.
  • Writing s.second from another class is a compile error: the program never runs.
  • If the field were public, s.second = 75; would be silently accepted and the clock would fall into an invalid state.
  • The fix: let the class's own method make the change: s.setSecond(75); The method rejects the invalid value.

Access Modifiers

private Is Per Class

class Ratio {
    private int num, den;
    Ratio(int num, int den) {
        this.num = num;
        this.den = den;
    }
    Ratio times(Ratio other) {
        // other's private fields: allowed
        return new Ratio(num * other.num,
                         den * other.den);
    }
    @Override public String toString() {
        return num + "/" + den;
    }
}
// in main:
Ratio k = new Ratio(2, 3).times(new Ratio(3, 4));
System.out.println(k);
6/12
  • Access control works per class, not per object: Ratio's code can read every Ratio object's private fields.
  • times, equals, compareTo: methods that work on two objects need no getters for this reason.
  • In another class, the same line does not compile:
error: num has private access in Ratio
Encapsulation's boundary is the class's source code. The inside is one author's responsibility; it is the outside users who are kept out.

The DigitalClock Class

public class DigitalClock {

  • Setter (mutator): checks the new value first, and assigns it if valid.

Why Not a public Field?

public field

public class Clock {
    public int second;
}
// in another class:
s.second = -5;   // accepted!
  • Any code can write any value.
  • The rule (0–59) is left to every user; one slip and the object is broken.
  • If the field's name or type changes, every class that uses it must change.

private field + method

public class Clock {
    private int second;
    public void setSecond(int s) {
        if (s >= 0 && s < 60) second = s;
    }
}
  • The rule is checked in one place, inside the class.
  • Read-only fields are possible: write only a getter.
  • The internals may change while method signatures stay the same.

Java 16+: for immutable classes that only carry data, you can write record Point(int x, int y) { }; the fields automatically become private final, and the accessors are named x() and y().

Example: Bank Account

BankAccount: Deposit and Withdraw

  // ...
  // deposit
  public void deposit(double amount) {
    if (amount > 0) {
      balance += amount;
      System.out.println(amount
          + " TL deposited. New balance: " + balance);
    } else {
      System.out.println("Invalid deposit amount.");
    }
  }

  // withdraw
  public void withdraw(double amount) {
    if (amount <= balance && amount > 0) {
      balance -= amount;
      System.out.println(amount
          + " TL withdrawn. New balance: " + balance);
    } else if (amount > balance) {
      System.out.println("Insufficient balance.");
    } else {
      System.out.println("Invalid withdrawal amount.");
    }
  }
  • Each operation first checks its precondition: amount > 0, and for withdrawals also amount ≤ balance.
  • If the condition fails, the balance stays the same; only a message is printed.
  • The balance can never go negative: this is the class's invariant.

Example: Bank Account

The Constructor Must Validate Too

  • Setters and transaction methods protect the balance, but the constructor in the example assigns its input without checking.
  • new BankAccount(1, -500.0, "Checking") creates an account with a negative balance; write "savings" (lowercase) and the account never earns interest, with no one noticing.
  • The class invariant must hold from the moment the object is born: the constructor is a precondition checker too.
  • If the constructor throws, the new expression yields no reference: the invalid object never reaches the user.
public BankAccount(int accountNumber,
        double balance, String accountType) {
    if (balance < 0)
        throw new IllegalArgumentException(
            "Initial balance cannot be negative");
    if (!accountType.equals("Savings")
            && !accountType.equals("Checking"))
        throw new IllegalArgumentException(
            "Unknown account type: " + accountType);
    this.accountNumber = accountNumber;
    this.balance = balance;
    this.accountType = accountType;
}

The constructor is the only door into the object: if the rules are enforced there once, the class's other methods can trust that every object is valid.

Class Design

Class Design

  • A class definition has two parts: interface and implementation.
  • The interface states what the class does and how to use it: the names, parameters, return types and comments of the public methods.
  • The implementation holds the class's internal mechanics and private fields, which matter only inside the class.
  • The implementation may change while the interface stays the same; private fields are hidden from outside the class.
  • Three parts: specification (constructor and method signatures), representation (the private fields that hold the data), and implementation (constructor and method bodies). Users know only the specification; their code survives changes to the representation and implementation.

Class Design

Interface

public interface Car {
    // Interface: WHAT is done?
    public void drive();

    public void stop();
}
  • In Java, an interface is a contract that says what a class will do: the methods have only signatures, no bodies.
  • Whoever uses the car knows only the drive() and stop() methods.

Class Design

Class Implementation

public class SportsCar implements Car {
  // Implementation: HOW is it done?
  private String brand;
  private int speed;

  public SportsCar(String brand) {
    this.brand = brand;
  }

  public void drive() {
    speed = 100;
    System.out.println(brand + " is moving: "
        + speed + " km/h");
  }

  public void stop() {
    speed = 0;
    System.out.println(brand + " stopped.");
  }
}
// in main:
Car car = new SportsCar("Rüzgar");
car.drive();
car.stop();
Output
Rüzgar is moving: 100 km/h
Rüzgar stopped.
  • implements Car: the class must write every method of the interface.
  • An interface and a class in the same package cannot share a name (duplicate class: Car); that is why the class is named SportsCar.
  • Main declares the variable as type Car: it depends only on the interface.

public class DigitalClock {
  // seconds since midnight
  private int totalSeconds = 0;
  public int getMinute() {
    return totalSeconds / 60 % 60;
  }
  public int getSecond() {
    return totalSeconds % 60;
  }
  public void setMinute(int minute) {
    if (minute >= 0 && minute < 60) {
      int diff = minute - getMinute();
      totalSeconds += diff * 60;
    }
  }
  public void setSecond(int second) {
    if (second >= 0 && second < 60) {
      totalSeconds += second - getSecond();
    }
  }
}
Client code is unchanged: after setMinute(12); setSecond(45); setSecond(75);, both versions give 12:45.

setSecond(45): the value is in range, the condition is true.

First, getSecond() = 720 % 60 = 0; the difference 45 is added: 765. From outside it reads 12:45.

The difference can be negative: 9 − 45 = −36, total 729. The minute is still 12.

Output 12:9; the old version would give the same. The internal representation changed, yet not one character of main changed.

Class Design

Guidelines

  1. All variables (fields) in a class should be private.
  2. Provide only as many public accessor methods as needed (you don't need an automatic setter for every field).
  3. Add comments saying how to use each method: what it does and its pre- and postconditions.
  4. Internal-only helper methods should be private.
public class Student {
    private int grade;
    private boolean isValid(int value) {
        return value >= 0 && value <= 100;
    }
    public void setGrade(int grade) {
        if (isValid(grade)) this.grade = grade;
    }
}

If another class calls o.isValid(50):

error: isValid(int) has private access in Student

Class Design

Tell, Don't Ask

Writing a getter and a setter for every field is not encapsulation: if the rules are still enforced outside the class, the data has only moved one step away.

Asking: the rule lives in client code

// same check at every withdrawal
if (h.getBalance() >= 300) {
    h.setBalance(h.getBalance() - 300);
}
// ...and wherever points are added
o.setGrade(Math.min(100, o.getGrade() + 5));
  • The rule repeats at every call site; one slip and the object is broken.
  • setBalance: once it exists, anyone can set the balance to anything.

Telling: the rule lives in the object

h.withdraw(300);   // rule in BankAccount
o.addBonus(5);     // 100 cap in Student
  • Instead of asking the object for its data and deciding for it, you tell it what you want; the object holding the data makes the decision.
  • Write a setter only when the field can truly change freely. BankAccount therefore has no setBalance.

Test question: “Who has the data needed to make this decision?” If the answer is the object itself, the decision belongs in its method.

Class Design

Benefits of Encapsulation

Abstraction

Simplifies the relation between an object and its user: the user knows only the methods.

Protection

Protects the object from unwanted, faulty access by users.

Modifiability

Without changing the interface, the class's internals can change; client code is unaffected.

Valid state (invariant)

The object's state always obeys the rules (class invariant):

  • only points with positive coordinates,
  • seconds and minutes between 0 and 59,
  • hours never negative.
In this chapter's examples: setSecond(75) is rejected, withdraw never takes the balance below zero, BankAccount's internals may change, yet code calling deposit stays the same.

Class Design

Observations

  • Interfaces change much less often than implementations: this keeps the code stable.
  • When the implementation changes, code that depends on it directly must change too.
  • Hiding the implementation reduces other classes' dependence on it: changes stay inside the class (loose coupling).

Immutable Classes

A Leaking Reference

public class ReportCard {
    private final int[] grades;
    public ReportCard(int[] grades) {
        this.grades = grades; // same array
    }
    public int[] getGrades() {
        return grades;        // inner array
    }
    public double average() {
        int t = 0;
        for (int n : grades) t += n;
        return (double) t / grades.length;
    }
}
int[] arr = {70, 80, 90};
ReportCard k = new ReportCard(arr);
arr[0] = 0;                // outside array
k.getGrades()[1] = -100;    // from the getter
System.out.println(k.average());
-3.3333333333333335
  • The field is private final, with no setter; yet the grades changed from outside, and even an invalid grade like −100 got in.
  • The reason: an array is an object. The constructor and getter shared only the reference; the object is reachable from three places.
  • final only stops the reference from pointing to another array; it does not protect the array's contents.

Immutable Classes · Step-by-step code trace

A Leaking Reference: Code Trace

An array is an object on the heap; the arr variable holds only its reference.

The constructor writes the reference from its parameter into the field. Now ReportCard's private field and main's arr variable point to the same array.

arr[0] = 0 goes through none of ReportCard's methods, yet the grade ReportCard sees has changed.

getGrades() returns the inner array itself; −100 is written through the returned reference. An invalid grade got into the object without passing any check.

Average (0 − 100 + 90) / 3 ≈ −3.33. private alone was not enough: the reference to the inner object leaked out.

Immutable Classes

Defensive Copying

public class ReportCard {
    private final int[] grades;
    public ReportCard(int[] grades) {
        this.grades = grades.clone(); // on entry
    }
    public int[] getGrades() {
        return grades.clone();        // on exit
    }
    // average() unchanged
}

With the same main 

80.0
  • Defensive copy: a mutable object is copied when it enters and leaves the class. The only reference to the inner array stays the class's own field.
  • The constructor's copy guards against the caller later changing its array; the getter's copy guards against changes to the returned array.
  • For lists, use new ArrayList<>(list) or the read-only view Collections.unmodifiableList(list).
  • String, Integer and other immutable objects are not copied: sharing them is harmless.

Copying has a cost; for large data, a read-only view or an immutable type from the start is cheaper.

Immutable Classes

Designing an Immutable Class

public final class Money {        // no subclasses
    private final long cents;     // assigned once
    private final String unit;
    public Money(long cents, String unit) {
        this.cents = cents;
        this.unit = unit;
    }
    public Money plus(Money other) {   // instead of a setter
        if (!unit.equals(other.unit))
            throw new IllegalArgumentException("Units differ");
        return new Money(cents + other.cents, unit);
    }
    @Override public String toString() {
        return cents / 100 + "."
            + String.format("%02d", cents % 100) + " " + unit;
    }
}

Rules

  1. No setters; the state is set only in the constructor.
  2. Fields are private final.
  3. The class is final: no mutable subclass can be written.
  4. “Modifying” methods return a new object.
  5. Mutable fields get defensive copies.

Payoff

  • The invariant is checked only in the constructor; after that it can never break.
  • The object can be shared without copying, can be a HashMap key, and is thread-safe.
  • String and record are ready-made examples of these rules.

Immutable Classes · Step-by-step code trace

Immutable Money: Code Trace

The first object is built. Its fields are final: from now on no method can change them.

plus leaves a unchanged; it builds and returns a new object (#3) holding the sum.

The returned value was not assigned to a variable: #3 is lost. This is the most common mistake with immutable objects; a is unchanged.

This time the result is assigned to b: 1250 + 375 = 1625 cents. #4, built as the argument, is no longer used either.

a kept its initial value. String's toUpperCase() and concat() methods work the same way.

Packages

Packages

  • Package: a group of classes collected in one folder. The folder's name is the package's name.
  • Each public class is defined in its own file, named after the class.
  • The file's first line declares its package: package packagename;
  • The compiler and JVM look for packages starting from the class path roots; the package name gives the folder path from there. The default class path is the current directory (.).
  • For nested folders, use a dot instead of / or \: school/admin → school.admin.
  • Package names are lowercase; Java's own packages: java.lang, java.util, java.io…
project/
├── src/
│   ├── bank/
│   │   ├── Account.java      // package bank;
│   │   └── Helper.java   // package bank;
│   └── app/
│       └── Main.java        // package app;
└── out/                    // compiler output
    ├── bank/
    │   ├── Account.class
    │   └── Helper.class
    └── app/
        └── Main.class

A class's full name includes its package: bank.Account, app.Main.

  • -cp out: the class path; when running, give the class's full name.

Packages

Importing Classes

  • To use a class from another package by its short name: import packagename.ClassName; The whole package: import java.util.*; (not subpackages).
  • Without import, you can also use the full name: java.util.Random.
  • java.lang (String, Math, System) and classes in the same package are visible automatically.
  • Order: first package, then imports, then the class. import static lets you use a static member without the class name.
import java.util.Scanner;
import static java.lang.Math.sqrt;

public class ImportDemo {
  public static void main(String[] args) {
    Scanner sc = new Scanner(System.in);
    int n = sc.nextInt();
    java.util.Random rnd =
        new java.util.Random(42);
    System.out.println(sqrt(n) + " "
        + Math.max(n, 10) + " "
        + rnd.nextInt(100));
  }
}
Output (input: 49)
7.0 49 30
  • Scanner: short name via import.
  • java.util.Random: full name, no import.
  • sqrt: import static; Math.max: java.lang.

  • A package is also a level of encapsulation: its classes are closed to the outside, and only the public ones form the package's interface.

Packages

Package Naming and Subpackages

  • To avoid name clashes, organizations start package names with their reversed domain name: giresun.edu.tr → tr.edu.giresun.bank.
  • Dotted names map to folders: tr/edu/giresun/bank/.
  • A subpackage is a separate package. tr.edu.giresun.bank.report cannot see the package-private members of bank; similar names grant no access rights.
  • import tr.edu.giresun.bank.*; does not import subpackages: import java.util.*; likewise skips the classes in java.util.function.
// tr/edu/giresun/bank/Helper.java
package tr.edu.giresun.bank;
class Helper {                  // package-private
    static double vat(double t) { return t * 0.20; }
}
// tr/edu/giresun/bank/report/Report.java
package tr.edu.giresun.bank.report;
import tr.edu.giresun.bank.Helper;
public class Report {
    double compute() { return Helper.vat(100); }
}
error: Helper is not public in tr.edu.giresun.bank; cannot be accessed from outside package

If the package name and folder path don't match exactly, the compiler cannot find the class; that is why IDEs create folders from the package name.

Common Mistakes (1)

Accessing a private field from outsideerror: second has private access in DigitalClock

s.second = 75; is wrong; write s.setSecond(75); instead.

Forgetting this in a setterwidth = width; // compiles, field unchanged

The parameter shadows the field; getWidth() returns 0. Correct: this.width = width;

Declaring a getter voiderror: incompatible types: unexpected return value

public void getWidth() cannot return a value; the return type must be int.

Setter without validationpublic void setSecond(int s) { second = s; }

This is no better than a public field; the setter must enforce the validity rule.

Forgetting importerror: cannot find symbol symbol: class Scanner

Add import java.util.Scanner; at the top of the file.

public class ≠ file nameerror: class Account is public, should be declared in a file named Account.java

The file name must exactly match the public class's name.

Using a package-private class from outsideerror: Helper is not public in bank; cannot be accessed from outside package

Either make the class public, or use it only from the same package.

Summary

Common Mistakes (3)

Exposing an inner object via a getter

return grades; exposes a mutable array or list. Return a copy or a read-only view.

Thinking a final field is immutable

private final int[] grades: the reference is fixed, not the array elements.

Forgetting to assign the new object

a.plus(p); or s.toUpperCase(); alone changes nothing: a = a.plus(p);

Not validating in the constructor

Even if setters check, new BankAccount(1, -500.0, ...) builds an invalid object. The constructor must enforce the rule too.

Checking arguments with assert

-ea off means the check never runs. public method arguments call for IllegalArgumentException.

Assuming subpackages are imported

import java.util.*; does not cover Function: cannot find symbol. java.util.function must be imported separately.

A setter for every field

The rule drifts into client code. Design behavior first (withdraw, addBonus); you may not need a setter.

Silently swallowing errors

Ignoring an invalid value without a trace hides the bug; either document it in the contract or throw an exception.
