Chapter 8: Input and Output

A program's variables live in memory and vanish when the program ends. Everything that has to last, such as measurement logs, configuration files, images, and student lists, is kept somewhere outside the program: on a disk, across a network, or on a device. A program's exchange of data with this outside world is called input and output (I/O). Java builds all of it on a single idea: data is a stream that flows in order from a source to a destination. These notes first introduce the stream concept and the standard streams of the keyboard and the screen. They then go down to the bytes inside files: the difference between text and binary files, character encodings, and how many bytes a number occupies in a file. The following sections cover the File class, the classes for reading and writing text, buffering, the other byte streams, and the ways of copying a file. The last sections treat random access, object serialization, and NIO, Java's library built on buffers and channels.

8.1Streams

A program takes data from the outside, processes it, and hands the result back. The outside can be a different place each time: the keyboard, the screen, a file on disk, a server on the network, or an array in memory. Learning a separate way of reading for each of these sources would be hard and unnecessary. Java treats them all through one abstraction: the stream.

8.1.1What is a stream?

Definition 8.1

A stream is a structure that carries data from a source to a destination in order, piece by piece. A stream through which data enters the program is an input stream, and a stream through which data leaves the program is an output stream. The pieces carried can be characters, numbers, or raw bytes.

A water pipe is a fitting analogy. Water that enters at one end of the pipe comes out at the other end in the same order, and whoever drinks the water does not care whether the far end is a tap or a tank. A stream works the same way. The program sees only its own end of the stream. The other end may be a keyboard, a file, or a network connection, and in every case the program calls the same read() and write() methods. The power of Java's I/O (input/output) library comes from this common interface. Figure 8.1 shows the structure.

Two properties of streams matter throughout this chapter. The first is order: data read from a stream arrives in the order it was written, and an item cannot be skipped to reach the next one. For this reason a stream cannot jump straight to a record in the middle of a file; that requires random access. The second is direction: a stream is either an input stream or an output stream, never both. A program that wants to both read and write the same file opens two separate streams.

8.1.2Standard streams

The keyboard and the screen are the simplest I/O devices. Data handled through them is transient: what is typed at the keyboard and written to the screen is not stored, and it disappears when the program ends. It is also immediate: input arrives as the user types, and output appears on the screen as the program writes it. When a Java program starts, it receives three ready-made streams from the operating system. They are called the standard streams (Table 8.1).

System.out and System.err both write to the screen. So why are there two streams? The difference shows when output is redirected. If you type java Application > result.txt on the command line, the > sign redirects only standard output to the file result.txt. Whatever is written to System.err stays on the screen. This way error messages neither pollute the output file nor go unnoticed. A program's actual result goes to System.out; warnings and error messages go to System.err.

The type of System.in is InputStream, so it delivers raw bytes. When a user types 42 at the keyboard and presses Enter, three bytes enter the stream: '4', '2', and the line terminator. Converting these bytes into an int is left to the programmer. The class java.util.Scanner does that job.

8.1.3A first example: reading and writing

The following program uses all three standard streams. It reads a number from the keyboard, writes two lines to standard output, and writes one line to standard error.

import java.util.Scanner;
public class StreamDemo {
  public static void main(String[] args) {
    // Read from the input stream
    Scanner scanner = new Scanner(System.in);
    int userInput = scanner.nextInt();
    // Write to the output stream
    System.out.println("Hello, World!");
    System.out.println("You entered: " + userInput);
    System.err.println("This line went to stderr.");
  }
}

If the user types 42, the console shows the following lines (the first line is the input the user typed):

42
Hello, World!
You entered: 42
This line went to stderr.

The program runs line by line as follows:

  • new Scanner(System.in) creates a scanner that reads the keyboard stream. Scanner is in the java.util package, which is why the import line at the top of the file is required.
  • scanner.nextInt() waits until the user types a number and presses Enter. This waiting is called blocking: the program stops at that line and continues once input arrives.
  • System.out.println writes a line to the output stream and ends the line.
  • System.err.println writes to the error stream. Most development environments show this line in red.

If the user types abc instead of a number, nextInt() cannot convert the text to a number and throws java.util.InputMismatchException. The program ends with an uncaught exception:

8.1.4Code trace: reading from the keyboard

The following program asks for the user's name and age and computes the age next year. It uses nextLine() to read the name and nextInt() to read the age. The two methods treat the line terminator differently, which causes one of the most common mistakes in this chapter; the trace makes the difference visible.

import java.util.Scanner;
public class ConsoleInput {
  public static void main(String[] args) {
    Scanner keyboard = new Scanner(System.in);
    System.out.print("Name: ");
    String name = keyboard.nextLine();
    System.out.print("Age: ");
    int age = keyboard.nextInt();
    int nextYear = age + 1;
    System.out.println("Hello " + name + "!");
    System.out.println("Next year you'll be " + nextYear + ".");
    keyboard.close();
  }
}

In the first step the Scanner object is attached to the System.in stream. Nothing has been read yet, and the keyboard buffer is empty. In the second step print (not println) writes the prompt Name: . Because print does not end the line, the user's answer is typed right next to the prompt.

The third step is the important one. The user types Ayşe Yılmaz and presses Enter. The keyboard buffer now holds Ayşe Yılmaz⏎. nextLine() takes everything up to the line terminator, spaces included, and also discards the terminator from the buffer. The variable name is assigned "Ayşe Yılmaz"; the line terminator is not part of this text.

In the fifth step the user types 19 and presses Enter. nextInt() skips leading whitespace, reads the digits, and converts them to the int value 19. It does not touch the line terminator: ⏎ stays in the buffer. This causes no trouble here, because no further read follows. In the later steps age is an ordinary int: 19 + 1 = 20. The output lines are built by string concatenation: "Next year you'll be " + 20 + ".".

The keyboard.close() on the last line closes not just the scanner but also the System.in stream it wraps. A closed standard input cannot be reopened. Even if the program later creates a new Scanner(System.in), it cannot read from the keyboard. The small experiment below shows this: after the first scanner is closed, the second one throws NoSuchElementException even though a line is waiting in the input.

read: one
java.util.NoSuchElementException: No line found

For this reason, the scanner that reads the keyboard is created once in a program and, if at all, closed only at the very end. Scanners that read files, on the other hand, should be closed as soon as the work is done; the file sections return to this difference.

8.1.5nextLine after nextInt

The effect of the leftover line terminator shows up when the order is reversed. Suppose the age is read first and the name second:

import java.util.Scanner;
public class LineAfterInt {
  public static void main(String[] args) {
    Scanner keyboard = new Scanner(System.in);
    System.out.print("Age: ");
    int age = keyboard.nextInt();
    System.out.print("Name: ");
    String name = keyboard.nextLine();
    System.out.println("[" + name + "] " + age);
  }
}

The user types 19 and presses Enter. nextInt() reads 19 and leaves the line terminator in the buffer. Then nextLine() is called. This method asks for the text up to the next line terminator. A line terminator is already waiting in the buffer, and the text in front of it is empty. nextLine() returns the empty string without waiting at all. The program ends before the user gets a chance to type a name:

Age: Name: [] 19
Common mistake

Reading text with nextLine() right after a call to nextInt(), nextDouble(), or next(). The first nextLine() reads the line terminator left over from the previous line and returns an empty string. There are two fixes: insert an extra keyboard.nextLine(); that discards the terminator, or read the number as a line too and convert it: int age = Integer.parseInt(keyboard.nextLine());.

The second fix is usually cleaner. Because every read consumes a whole line, nothing is left in the buffer. If the user types extra spaces next to the number, parseInt fails; in that case use keyboard.nextLine().trim().

8.2Files and encodings

Exchange through the keyboard and the screen is transient. Lasting data needs a file. This section explains what a file really is, how text files differ from binary files, and how characters are converted into bytes. This knowledge decides which stream class to choose in the later sections.

8.2.1A file: a sequence of bytes on disk

A file stores data permanently on disk. The data stays in place even when the program ends or the computer restarts. Variables in RAM, by contrast, vanish with the program. The data in every file ultimately consists of 0s and 1s, that is, of a sequence of bytes. What distinguishes one file from another is how these bytes are interpreted.

Definition 8.2

In a text file, bytes are converted into letters according to a character encoding; a person can read the file with a text editor. In a binary file, the bytes are data such as numbers, pixels, audio samples, or machine instructions; only a program that knows the format of the file can make sense of them.

To see the bytes of a file, you use a hexadecimal (hex) editor. This tool shows each byte as two hexadecimal digits. A file file.txt containing Merhaba, dünya! looks like this in a hex editor:

0000  4D 65 72 68 61 62 61 2C  Merhaba,
0008  20 64 C3 BC 6E 79 61 21   d..nya!

The left column is the position of the first byte on each line: 0000 and 0008. The middle holds the hexadecimal value of each byte, and the right the ASCII equivalent. The first byte is 4D: 4 · 16 + 13 = 77, which is the capital letter M in ASCII. The text has 15 characters, but the file takes 16 bytes. The difference comes from the letter ü: in UTF-8, ü is two bytes, C3 BC. The two dots in the right column show that these two bytes have no ASCII equivalent. 8.2.2The file-processing cycle

Whatever language is used, working with a file goes through the same steps. Figure 8.4 shows the steps, and Table 8.3 gives the Java counterpart of each.

Table 8.3: The file-processing steps and their counterparts in Java.

The last step is the one most often forgotten. A file that is not closed causes two problems. The first is data loss: some of the bytes written wait in a buffer in memory and may never reach the disk unless the file is closed. The second is a resource leak: the operating system allocates a file handle for every open file, and the number of files a process can keep open at once is limited. A long-running program that never closes its files eventually cannot open new ones. On Windows, a file left open also cannot be deleted or moved.

8.2.3A first file program

The following program writes one sentence to a text file and a single byte to a binary file. It then reads the byte back from the binary file and prints the size of the text file.

import java.io.*;

public class FirstFile {
  public static void main(String[] args) throws IOException {
    // Write to a text file
    FileWriter writer = new FileWriter("file.txt");
    writer.write("Merhaba, dünya!");
    writer.close();
    // Write one byte to a binary file
    FileOutputStream out = new FileOutputStream("data.dat");
    out.write(127);
    out.close();
    // Read from the binary file
    FileInputStream stream = new FileInputStream("data.dat");
    int b = stream.read();
    stream.close();
    System.out.println("Byte read: " + b);
    File text = new File("file.txt");
    System.out.println("file.txt: " + text.length() + " bytes");
  }
}
Byte read: 127
file.txt: 16 bytes

After the program has run, the contents of file.txt are:

Merhaba, dünya!

The program uses three different stream classes:

  • FileWriter writes text. It converts the characters it is given into bytes with a character encoding and sends them to the file. Since Java 18 the default encoding is UTF-8; that is why ü becomes two bytes and the 15-character text takes 16 bytes.
  • FileOutputStream writes raw bytes. The call write(127) puts a single byte in the file: 7F in hexadecimal, 0111 1111 in binary. No character conversion takes place.
  • FileInputStream reads raw bytes. read() returns a byte as an int between 0 and 255. If there is no byte left to read, it returns −1; this detail matters in the section on copying.

The throws IOException in the header of main declares that file operations can throw a checked exception. The file may not exist, the disk may be full, or permission may be missing. The compiler requires these cases to be handled: either caught with try-catch or declared with throws in the method header. These short examples choose the second way. In real programs it is better to catch the exception so that the error message can be given to the user in an understandable form.

8.2.4Text files and character encodings

Text files contain printable characters: letters, digits, punctuation marks, spaces, and line terminators. They can be opened and edited with text editors such as Notepad or VS Code. Source code (.java, .c), .txt, .csv, and .html files are text files.

A computer cannot store letters, only numbers. So every character is assigned a number. The rule of this mapping is called a character encoding.

Definition 8.3

A character encoding, also called a character set, is the rule that determines with which number, that is, with which byte or bytes, each character is stored. The programs that write and read a text file must use the same encoding.

Many encodings have appeared over the course of history. The four met in this course are summarized in Table 8.4.

8.2.5Binary files

Binary files store bytes not as characters but in a format chosen by the program: numbers, pixels, audio samples, machine code. These bytes are meaningful only to a program that knows the format; a person cannot read them directly. Executable files (.exe, Java's .class files), images (.png, .jpg), music (.mp3), video (.mp4), and data files (.dat) are binary files. The advantages of binary files are that they are smaller and faster to process: a number does not have to be converted to text and back.

The first 32 bytes of FirstFile.class, produced by compiling the previous program, look like this in a hex editor:

0000  CA FE BA BE 00 00 00 41  .......A
0008  00 5C 0A 00 02 00 03 07  .\......
0010  00 04 0C 00 05 00 06 01  ........

Every .class file begins with the bytes CA FE BA BE. These four bytes are called the magic number; the JVM recognizes from it that the file really is a class file. The next four bytes are version information. 00 41 = 65 is the class-file version of Java 21; this number was also read from a file compiled with JDK 21, using Java itself (major = 65 in the earlier output). The constant pool follows. Some readable pieces are visible as well: class names such as java/lang/Object are stored in the file as text. Opening a binary file in a text editor and saving it can corrupt it: the editor may change some bytes or convert the line terminators.

8.2.6Extended ASCII and Turkish characters

ASCII is 7 bits and covers 128 characters. A byte, however, is 8 bits. The one remaining bit makes room for 128 new characters.

Definition 8.4

Extended ASCII is the general name for encodings that use all 8 bits to represent 28 = 256 characters. Codes 0–127 are the standard ASCII characters and are the same in every table. Codes 128–255 are reserved for special characters, symbols, and national letters.

There is no single "extended ASCII". Which characters the upper half holds varies with the code page. Two code pages are used for Turkish: ISO-8859-9 (Latin-5) and Windows-1254. They use the same bytes for the Turkish letters. Table 8.5 shows the meaning of the same bytes in Latin-1 and Latin-5 side by side.

The lasting solution to this problem is Unicode, which collects all languages in a single table, and its byte encoding UTF-8. In UTF-8 each character has exactly one byte sequence; the reader does not have to guess which code page to choose. UTF-8 is the choice for every text file written today.

8.2.7Writing 127 to a file

How a number is stored in a file depends on its data type, its purpose, and the file format. The number 127 can be written in two fundamentally different ways.

  • Written as text, the number is first converted into characters: "127". Each digit takes one ASCII byte. A point that is often confused matters here: the code of the character '1' is not 1 but 49. '2' is 50 and '7' is 55. The file holds the bytes 31 32 37.
  • Written as binary, the binary value of the number, 0111 1111, is written directly into as many bytes as the type is wide: 1 byte for byte, 2 for short, and 4 for int. For numeric data this way is more efficient.

The following program really writes these five representations to files and measures the file sizes. It uses OutputStreamWriter to write text and DataOutputStream to write binary. For brevity, the lines import java.io.*; and import java.nio.charset.*; are not shown.

public class Number127 {
  static void writeText(String name, Charset cs) throws IOException {
    Writer w = new OutputStreamWriter(new FileOutputStream(name), cs);
    w.write(String.valueOf(127));            // "127": 3 chars
    w.close();
  }
  static void writeBinary(String name, int size) throws IOException {
    FileOutputStream fos = new FileOutputStream(name);
    DataOutputStream d = new DataOutputStream(fos);
    if (size == 1) d.writeByte(127);        // 01111111
    else if (size == 2) d.writeShort(127);  // 00000000 01111111
    else d.writeInt(127);                    // 4 bytes
    d.close();
  }
  public static void main(String[] args) throws IOException {
    writeText("text.txt", StandardCharsets.US_ASCII);
    writeText("text16.txt", StandardCharsets.UTF_16BE);
    writeBinary("b.dat", 1);  writeBinary("s.dat", 2);  writeBinary("i.dat", 4);
    String[] names = {"text.txt", "text16.txt",
             "b.dat", "s.dat", "i.dat"};
    for (String name : names)
      System.out.println(name + ": " + new File(name).length());
  }
}

The BE (big-endian) in the name of this encoding fixes the byte order, so no byte order mark (BOM) is written at the start of the file. Had the UTF_16 encoding with a byte order mark been used, two bytes FE FF would have been added at the start and the file would have taken 8 bytes.

The choice depends on the purpose:

  • Text is for data that people will read. It opens in every editor, moves easily between platforms, and can be repaired by eye when it is damaged. Log files, configuration files, and CSV tables are text.

8.3The file system: the File class

Before reading the contents of a file, you often ask questions about the file itself. Does the file exist? Is it a file or a directory? How large is it? Is it readable? The java.io.File class answers these questions.

8.3.1A File is a path

Definition 8.5

A File object represents a path on disk: the name and location of a file or directory. File does not read or write the contents of a file; that is the job of streams. 8.4Reading and writing text

Most file work is done with text files. This section explains the ways of reading and writing text, the class structure behind them, and how to close resources safely.

8.4.1Reading a file with Scanner

Scanner can read not only the keyboard but also a file or a String. To change the source, a File object is passed to the constructor instead of System.in. The reading methods are the same. The following program reads a file line by line and prints it to the screen. The required imports are java.io.File, java.io.FileNotFoundException, and java.util.Scanner.

public class ScannerFile {
  public static void main(String[] args) {
    Scanner scanner = null;
    try {
      scanner = new Scanner(new File("sample.txt"));
      // Read the file and print it
      while (scanner.hasNextLine()) {
        String line = scanner.nextLine();
        System.out.println(line);
      }
    } catch (FileNotFoundException e) {
      System.err.println("File not found: " + e.getMessage());
    } finally {
      if (scanner != null)
        scanner.close();
    }
  }
}

  • A checked exception. new Scanner(File) throws FileNotFoundException if the file does not exist. This is a checked exception: it is either caught or declared in the method header. The program catches it and writes a message to the error stream.
  • The loop. hasNextLine() asks whether there is a line to read, and nextLine() takes the line. At the end of the file hasNextLine() returns false and the loop ends.
  • finally and the null check. If the file cannot be opened, the variable scanner stays null. The finally block runs in every case; without the check, close() would be called through a null reference.

The streams in java.io fall into two large families. The distinction is made by the unit the stream carries.

8.4.5Class hierarchies

Each of the two families consists of classes derived from an abstract superclass. Figure 8.9 shows the byte streams and Figure 8.10 the character streams.

InputStream and OutputStream at the top of the hierarchy are abstract classes, so no objects are created from them directly. The subclasses take on two kinds of work. Some connect to a data source: FileInputStream connects to a file, ByteArrayInputStream to an array in memory, and PipedInputStream to a pipe. The others derive from FilterInputStream and FilterOutputStream. These do not connect to a source on their own; they wrap another stream and add a new capability to it. BufferedInputStream adds a buffer, and DataInputStream adds the ability to read primitive types.

Character streams follow the same pattern. The relationship that stands out here is the position of FileReader. A FileReader is really an InputStreamReader: inside, it opens a FileInputStream and converts the bytes coming from it into characters with the chosen encoding. FileWriter likewise derives from OutputStreamWriter. So underneath every character stream there is, in the end, a byte stream. A disk only knows bytes.

8.4.6Wrapper streams

Every class in Java's I/O library does one job well. FileReader reads characters from a file but does not recognize lines. BufferedReader reads lines but cannot connect to a file. The capabilities you need are combined by nesting streams inside one another.

Definition 8.8

A wrapper stream (also called a decorator) is a stream that takes another stream in its constructor and adds a new capability to it, such as buffering, line reading, or reading of primitive types. The wrapper's methods do part of the work themselves and pass the rest on to the inner stream. This arrangement is known as the Decorator design pattern.

BufferedReader reader = new BufferedReader(new FileReader("sample.txt"));
PrintWriter writer = new PrintWriter(new BufferedWriter(new FileWriter("file2.txt")));

The first line has two layers: FileReader opens the file and converts bytes to characters; BufferedReader wraps it and adds a buffer and readLine(). The second line has three layers: FileWriter converts characters to bytes and writes them to the file, BufferedWriter adds a buffer, and PrintWriter adds convenient writing methods such as print, println, and printf (Figure 8.11).

You can think of a garden hose: first a filter and then a spray nozzle are attached to the end of the hose. The water, which is the data, passes through all of them in turn. Each part does its own job, and the parts can be combined in any order you like. To add a capability, you do not need to write a new class; you combine the existing wrappers.

Wrapping has two rules. The first: closing the outermost stream closes all the inner ones. writer.close() first flushes its own buffer, then the buffer of the BufferedWriter, and finally closes the FileWriter and the file. The inner streams do not have to be closed separately. The second: a wrapper interprets the data but does not validate it. If a text file is wrapped in a DataInputStream and readInt() is called, the first four bytes, the codes of the letters J, a, v, a, are read as the integer 1,247,901,281. The stream raises no error; the wrong wrapper produces a wrong but valid-looking result.

8.5Buffering

The basic methods of streams work with small pieces. read() reads a byte or a byte array, and write() writes a byte or a byte array. If the program goes to the disk separately for every byte, the application slows down badly. This section explains the cause of the problem and its solution.

8.5.1Why buffer?

A disk is thousands of times slower than memory. Moreover, a disk access is not just transfer time. The program makes a system call, the operating system runs the device driver, and the result returns to the program. This fixed cost is roughly the same whether one byte or eight thousand bytes are read. Reading a thousand bytes with a thousand separate calls is therefore far more expensive than reading them with one call.

Definition 8.9

A buffer is an area in which data is temporarily collected in memory. Buffering is the technique of reducing the number of physical disk accesses by doing reads and writes in bulk through this area. When reading, the buffer is filled with a large piece at a time, and the program's small reads are served from the buffer. When writing, small writes accumulate in the buffer, and when the buffer is full it is sent to the disk in one go.

An everyday analogy explains the difference. To buy ten items at the market, you do not make a separate trip for each item; you put them all in one basket and carry them at once. The trip itself, the fixed cost, is paid once. Figure 8.13 compares unbuffered and buffered writing.

Not closing a buffered writer. If you write bw.write("data"); and never close the stream, the data stays in the buffer. 8.5.5How much does buffering help?

The following program creates a 2 MB file and reads it twice byte by byte: first unbuffered, then buffered. The time is measured in milliseconds with System.nanoTime().

public class BufferTiming {
  static long time(InputStream in) throws IOException {
    long start = System.nanoTime();
    while (in.read() != -1) { }          // 1 byte at a time
    in.close();
    return (System.nanoTime() - start) / 1_000_000;
  }
  public static void main(String[] args) throws IOException {
    File f = new File("big.dat");
    try (FileOutputStream fos = new FileOutputStream(f)) {
      fos.write(new byte[2 * 1024 * 1024]);   // 2 MB
    }
    long t1 = time(new FileInputStream(f));
    long t2 = time(new BufferedInputStream(new FileInputStream(f)));
    System.out.println("Unbuffered: " + t1 + " ms");
    System.out.println("Buffered  : " + t2 + " ms");
    f.delete();
  }
}

While these notes were being prepared, the same program was run three more times. The times were 3194/58, 3241/62, and 3250/63 milliseconds. The times vary with the machine, the disk, and the operating system's cache; the ratio stays similar. On this machine buffered reading is more than fifty times faster.

The reason for the difference is the number of calls. The file is 2 MB, that is, 2 · 1024 · 1024 = 2,097,152 bytes. In the unbuffered stream every read() is a system call: 2,097,152 calls, plus one more that reports the end of the file. In the buffered stream there is one system call per 8192 bytes: 2,097,152 / 8192 = 256 calls that carry data and one call for the end of the file. The number of the program's own read() calls is the same in both cases; but in the buffered case these are ordinary method calls that read from an array in memory. The number of system calls drops by a factor of about 8000. The time drops only by a factor of about fifty, because a method call is still made for every byte. Reading block by block removes this cost as well.

8.6Other byte streams

The InputStream and OutputStream family has classes besides the file streams. They use an array in memory, another thread, or several streams as the source of data. Since they all carry the same read() and write() methods, they can be used wherever a file stream is expected.

8.6.1FileInputStream and reading in chunks

FileInputStream derives from InputStream and reads bytes directly from a file. It is a low-level class, suited to non-text data such as images and sound. It has two read methods:

  • read() reads a single byte and returns an int between 0 and 255. At the end of the file it returns −1.
  • read(byte[] b) reads at most b.length bytes into the array and returns the number of bytes it read. At the end of the file it returns −1. The returned number may be smaller than the length of the array.
public class ChunkRead {
  public static void main(String[] args) throws IOException {
    try (FileInputStream fis = new FileInputStream("file.txt")) {
      byte[] buf = new byte[4];
      int n;
      while ((n = fis.read(buf)) != -1) {
        System.out.println(n + ": " + new String(buf, 0, n));
      }
    }
  }
}

Suppose file.txt contains Hello, Java!: 12 bytes. Because the array holds 4 bytes, the file is read in three chunks:

4: Hell
4: o, J
4: ava!

The second line, o, J, contains a comma and a space. new String(buf, 0, n) converts only the part of the array that was read, that is, n bytes starting at 0. In this example the file is an exact multiple of 4, so every chunk is full. Had the file been 13 bytes, the fourth read would have returned 1, and the last three cells of the array would still hold bytes left over from the previous chunk. Had new String(buf) been written, these stale bytes would have become part of the text.

Using FileInputStream for text is difficult. Multibyte characters such as Turkish letters can be split at a chunk boundary. If the word Gündüz is read in 2-byte chunks and each chunk is decoded separately as UTF-8, the two bytes of ü land in two different chunks:

[G�][�n][d�][�z]

Each half-finished byte is an invalid UTF-8 sequence and turns into the � sign. For text files, character-based classes such as FileReader are more suitable; they keep a half character at a chunk boundary for the next read.

8.6.2In-memory streams

ByteArrayInputStream also derives from InputStream, but it reads not from a file but from a byte array in memory. It is fast because it touches no physical resource. It can only be read; to write to memory, its counterpart ByteArrayOutputStream is used. ByteArrayOutputStream collects the bytes written in a growing array; toByteArray() returns this array and toString() its text equivalent.

public class ByteArrayRead {
  public static void main(String[] args) throws IOException {
    byte[] arr = {74, 97, 118, 97};           // "Java"
    ByteArrayInputStream bais = new ByteArrayInputStream(arr);
    int b;
    while ((b = bais.read()) != -1) {
      System.out.print(b + "=" + (char) b + " ");
    }
    System.out.println();
    // Writing to memory: ByteArrayOutputStream
    ByteArrayOutputStream baos = new ByteArrayOutputStream();
    baos.write(arr);
    baos.write('!');
    byte[] result = baos.toByteArray();
    System.out.println(result.length + " bytes: " + baos);
  }

8.6.4Pipes

PipedInputStream and PipedOutputStream provide safe communication of data between two threads. A thread is an independently progressing flow of execution inside the same program. One thread writes data with PipedOutputStream, and the other reads it with PipedInputStream. The two ends are connected with new PipedOutputStream(pis) (Figure 8.15).

A pipe has four properties:

  • Reading and writing are synchronized: if the pipe is empty the reader waits, and if it is full the writer waits.
  • Data flows in one direction. Two-way communication needs two pipes.
  • The buffer of a pipe is 1024 bytes by default.
  • Using both ends in the same thread can cause a deadlock. When the buffer is full, the writer waits for the reader; but the reader is the same thread and never gets to run.

The following program creates a reader thread and a writer thread. The bodies of the threads are written as lambda expressions.

PipedInputStream pis = new PipedInputStream();
PipedOutputStream pos = new PipedOutputStream(pis);
// Reader thread
Thread reader = new Thread(() -> {
  try {
    int b;
    while ((b = pis.read()) != -1)
      System.out.print((char) b);
    System.out.println();
    pis.close();
  } catch (IOException e) {
    e.printStackTrace();
  }
});
// Writer thread
Thread writer = new Thread(() -> {
  try {
    pos.write("Hello, pipe!".getBytes());
    pos.close();
  } catch (IOException e) {
    e.printStackTrace();
  }
});
reader.start();
writer.start();
writer.join();
reader.join();
Hello, pipe!

start() starts a thread; join() waits for it to finish. The two threads run at the same time, and which of them makes progress first can change from run to run. If the reader starts first, it waits in pis.read() because the pipe is empty. The writer writes the 12 bytes into the pipe and calls pos.close(). The reader's waiting read() call picks up the bytes in order. When the pipe has been emptied and the writer end is closed, read() returns −1 and the loop ends. The output is the same in every run, because a pipe preserves the order of the bytes. The program was run twice for these notes and printed the same line both times.

8.7Copying files

Copying a file is a good exercise for learning streams: everything read from an input stream is written to an output stream. The same job can be done with different units: byte by byte, block by block, or line by line. This section compares the ways and shows the pitfalls of each.

8.7.1Copying byte by byte

The simplest copy writes every byte read from the source file to the destination file. Because byte streams do not care about the meaning of the bytes, this method copies every kind of file, whether text, an image, or an .exe, without corrupting it. To speed up reading and writing, the two streams are wrapped in buffered streams (Figure 8.17).

import java.io.*;

public class ByteCopy {
  public static void main(String[] args) throws IOException {
    File src = new File("file.txt");
    File dst = new File("file2.txt");
    FileInputStream fis = new FileInputStream(src);
    FileOutputStream fos = new FileOutputStream(dst);
    BufferedInputStream bis = new BufferedInputStream(fis);
    BufferedOutputStream bos = new BufferedOutputStream(fos);
    int b;
    // Read a byte; -1 at end of file.
    while ((b = bis.read()) != -1)
      bos.write(b);    // write it out
    bos.close();
    bis.close();
    System.out.println(dst.length() + " bytes copied");
  }
}

The copy loop is a single line: while ((b = bis.read()) != -1) bos.write(b);. bis.read() reads a byte and returns −1 at the end of the file. bos.write(b) writes the byte just read to the output stream. The value read must be kept in an int variable. The reason is to tell −1 apart from a byte with the value 255. read() can return every value in the range 0–255 as a valid byte; since −1 lies outside this range, it reports the end of the file without ambiguity.

Common mistake

Storing the result of read() in a byte: byte b; while ((b = (byte) in.read()) != -1). In Java, byte is signed and takes values between −128 and 127. A byte with the value 255, that is FF, becomes −1 through the (byte) cast. The loop mistakes this byte for the end of the file and stops; the rest of the file is not copied. The correct type is int.

The effect of the mistake can be seen in a small experiment. If the three-byte array {10, (byte) 255, 20} is read with this loop, only the first byte is processed:

processed: 1

Because the FF byte rarely occurs in text files, this mistake goes unnoticed in experiments with text files. In images or compressed files, FF is common, and the copy is cut off halfway.

8.7.3Copying block by block

Buffered streams reduce disk access, but the program itself still calls read() and write() once per byte. The faster way is to read the data in blocks into the program's own array. read(byte[] buf) tries to fill the array and returns the number of bytes it read. write(buf, 0, size) writes only the first size bytes of the array.

public class BlockCopy {
  public static void main(String[] args) throws IOException {
    // Data is read in 16K chunks
    byte[] buf = new byte[1024 * 16];
    File src = new File("file.txt");
    File dst = new File("file2.txt");
    FileInputStream fis = new FileInputStream(src);
    FileOutputStream fos = new FileOutputStream(dst);
    BufferedInputStream bis = new BufferedInputStream(fis);
    BufferedOutputStream bos = new BufferedOutputStream(fos);
    int size;
    // Read up to 16K; -1 at end of file.
    while ((size = bis.read(buf)) > -1)
      bos.write(buf, 0, size);   // write the chunk
    bos.close();
    bis.close();
    System.out.println(dst.length() + " bytes copied");
  }
}

For a 40,000-byte file the output is:

40000 bytes copied

new byte[1024 * 16] creates a 16 KB array. The data is processed in chunks of this size, so the program's memory use stays constant no matter how large the file is. A 40,000-byte file arrives in three reads: 16,384, 16,384, and 7,232 bytes. The last chunk does not fill the whole array. An experiment with a 40,000-byte file of random bytes, run for these notes, confirms the chunk sizes and that the copy is identical to the source:

chunks read: 16384 16384 7232
identical: true

The loop condition has the form > -1; it means the same as != -1, because read never returns a value smaller than −1. A return value of 0 from read(byte[]) is possible only when the array has length 0.

Common mistake

Writing out.write(buf); in a block copy. In the last block the array is not completely filled; the stale data at the end of the array also goes into the copy, and the copy becomes larger than the source. The correct call is always write(buf, 0, size), where size is the value read returned last. The same rule applies when converting to text: new String(buf, 0, size).

8.7.5Copying line by line

Text files can also be copied line by line. This way works with character streams and is useful when the lines have to be processed while being copied: filtering, numbering, or modifying them, for example.

public class LineCopy {
  public static void main(String[] args) throws IOException {
    File src = new File("file.txt");
    File dst = new File("file2.txt");
    FileReader fr = new FileReader(src);
    BufferedReader br = new BufferedReader(fr);
    FileWriter fw = new FileWriter(dst);
    BufferedWriter bw = new BufferedWriter(fw);
    PrintWriter pw = new PrintWriter(bw);
    String line;
    // read a line until end of file
    while ((line = br.readLine()) != null)
      pw.println(line);    // write the line
    pw.close();
    br.close();
    System.out.println("Copied: " + dst.getName());
  }
}
Copied: file2.txt

On the reading side there is FileReader and BufferedReader, and on the writing side the chain FileWriter, BufferedWriter, and PrintWriter. The loop takes each line with readLine() and writes it with println. pw.close() closes the whole chain, including bw and fw.

This method has two limits. First, it is suitable only for text files. If a binary file goes through a character stream, the encoding conversion corrupts the bytes. Second, the copy may not be byte-for-byte identical. readLine() discards the line terminator, while println adds the system's line terminator: \r\n on Windows and \n on Linux. If the last line of the source has no terminator, the copy has one extra. The experiment below was run on Windows with a 41-byte file whose last line ends without a line terminator; the copy takes 43 bytes:

Copied: file2.txt
41 -> 43 bytes; line.separator length 2

If the line terminators of the source were in Linux form (\n), each line of the copy made on Windows would be one byte longer. So whenever a byte-for-byte identical copy is needed, byte streams are always used.

8.7.6Downloading a web page

The source of a copy loop does not have to be a file. The following program downloads a web page and saves it to disk. This time the source is the network: url.openStream() returns an InputStream. The rest of the loop is the same as in file copying.

}

8.7.7Shortcuts and a comparison

There is no need to rewrite the copy loop every time. 8.8Random access

Streams are all sequential: they read or write data from beginning to end. Some tasks, however, require going directly to a record in the middle of a file. To read the grade of the thousandth student in a student file, reading the previous 999 records is an unnecessary burden.

8.8.1Sequential and random access

Definition 8.10

In sequential access, each read or write continues from where the previous one ended; going back needs special support (for example mark/reset, within a limited buffer), and you cannot jump freely to a position. In random access, the program jumps to a desired position in the file and reads or writes from there. The position is the number of bytes from the start of the file, counting from 0.

Sequential access is like a cassette tape: to reach a song, the earlier ones have to be wound past. Random access is like a vinyl record: the needle is placed wherever you want (Figure 8.21). Streams (FileInputStream, BufferedReader, and so on) are all sequential. Sequential access is used when the structure of the file is unknown or when the whole file is being processed; copying is the typical example.

Random access can be used when the size and position of the records are known. If all records have the same size, the position of record number k is found by multiplication: position = k · record size (numbering starts at 0). This way is very convenient for reading or modifying a particular record in place. The fixed-size requirement is important. In a text file whose lines have different lengths, the start of the kth line cannot be computed.

8.8.2RandomAccessFile

In Java, random access is done with the class java.io.RandomAccessFile. This class differs from streams: a single object both reads and writes, and it is not part of the InputStream/OutputStream hierarchy. Inside the object there is a file pointer. Every read and write takes place at the position the pointer indicates and advances the pointer by the number of bytes read or written. Table 8.18 lists the main members of the class.

Example 8.1

In a student file, let each record consist, in order, of an int student number, a double average, and an int credit count. Records are numbered from 0. How is the average of record 37 read?

The record size is 4 + 8 + 4 = 16 bytes. Record 37 starts at byte 37 · 16 = 592. Within the record, the average comes after the student number, 4 bytes past the start of the record. Write f.seek(37 * 16 + 4); double avg = f.readDouble();. After the read, the pointer is at 592 + 4 + 8 = 604, which is the start of the credit field of the same record. If one of the records had been written with float instead of double, all the position calculations would break. Random access requires the file format to be known exactly.

8.9Serialization

So far numbers and text have been written to files. In an object-oriented program, however, what we want to store is often an object: the state of a game, a student record, a settings object. Writing and reading back every field of an object one by one is tedious. Java offers a mechanism that does this in a single call.

8.9.1What is serialization?

Definition 8.11

Serialization is converting the state of an object, that is, the values of its fields, into a sequence of bytes. This byte sequence can be written to a file or carried to another environment over a network. Rebuilding an object from a byte sequence is called deserialization.

For the objects of a class to be serializable, the class must implement the java.io.Serializable interface. This interface has no methods at all. Such interfaces are called marker interfaces; their only job is to mark the class as "serializable". The serialization mechanism looks for this mark before writing the object.

Serialization involves three flows (Figure 8.24). An object sits in memory. ObjectOutputStream.writeObject converts it to bytes; the file begins with the magic number AC ED. ObjectInputStream.readObject builds a new object from these bytes. The new object has the same values but is a different object.

Serialization is used in game saves, in caches, and in sending objects over a network to another JVM. Its format is specific to Java and tightly bound to the structure of the class. For this reason, text formats such as JSON are generally preferred for data that will be stored for a long time or shared with other languages. Moreover, deserializing data that comes from an untrusted source can create a security hole, because during deserialization the program's classes are instantiated with unknown data.

8.9.2A serializable class

import java.io.Serializable;

class Student implements Serializable {
  private static final long serialVersionUID = 1L;
  private String name;
  private int age;

  public Student(String name, int age) {
    this.name = name;
    this.age = age;
  }

  public String toString() {
    return "Student [name=" + name + ", age=" + age + "]";
  }
}

Three details in the class are related to serialization:

  • implements Serializable makes the class serializable. No method has to be written.
  • serialVersionUID is the version identifier of the class. This number is also written into the serialized bytes. When reading, the number in the file is compared with the number of the class in the program; if they differ, InvalidClassException is thrown. Writing the number by hand is recommended. If it is not written, the serialization mechanism computes it from the structure of the class; when a field or method is added to the class, the computed number changes and old files can no longer be read.
  • The fields must be serializable too. String and int are serializable. If the type of a field is not Serializable, NotSerializableException is thrown during writing.

The version check really works. When a file written with serialVersionUID = 1L is read with version 2L of the same class, this exception results:

java.io.InvalidClassException: Student; local class incompatible: stream classdesc serialVersionUID = 1, local class serialVersionUID = 2

8.9.4transient and static fields

Not every field of an object should be stored. A password should not be stored. A temporary cache or an open file connection cannot even be stored. Such fields are marked with the keyword transient.

Definition 8.12

A field marked transient is skipped during serialization. When the object is read back, this field gets the default value of its type: null for references, 0 for numbers, and false for boolean. static fields are never serialized, because they belong to the class, not to the object.

class Account implements Serializable {
  private static final long serialVersionUID = 1L;
  static int count;
  private String name;
  private transient String password;   // not written

  Account(String name, String password) {
    this.name = name;
    this.password = password;
  }

  public String toString() {
    return "Account [name=" + name + ", password=" + password + "]";
  }
}

8.10NIO

Java NIO (New I/O) arrived with Java 1.4 in the java.nio package. It offers higher performance and flexibility than the classic java.io streams. NIO.2 (java.nio.file), which came with Java 7, added the Path and Files classes for file operations.

8.10.1The building blocks of NIO

NIO is built on four basic concepts:

  • Buffer (Buffer): memory areas that hold data temporarily.
  • Channel (Channel): connection objects that manage input and output operations and can be bidirectional.
  • Selector (Selector): an object that monitors multiple channels with a single thread and reports which are ready.
  • Path (Path): the NIO.2 class that represents file and directory paths.

8.10.2Stream or channel?

In classic I/O the program works with a stream, and data flows in one direction, byte by byte or character by character. In NIO the program writes to a buffer or reads from a buffer, and a channel moves whole buffers of data between the buffer and the source or destination (Figure 8.26).

Table 8.21: Classic I/O compared with NIO.

The non-blocking mode is the most important difference of NIO. With a classic stream, read() waits until data arrives, and the thread cannot do anything else in the meantime. A server with a thousand clients has to start a thousand threads. A non-blocking channel, by contrast, returns immediately if there is no data. A single thread can therefore poll many channels in turn.

8.10.3Buffers and their properties

Definition 8.13

An NIO buffer is a fixed-size block of memory that holds data temporarily: an array plus position information over it. It has four properties. The capacity is the maximum number of elements it can hold and never changes. The position is the index at which the next read or write takes place. The limit is the first index that cannot be read or written. The mark is a position saved with mark(); reset() returns to it. Always 0 ≤ mark ≤ position ≤ limit ≤ capacity.

There is a buffer class for each primitive type: ByteBuffer, CharBuffer, ShortBuffer, IntBuffer, LongBuffer, FloatBuffer, and DoubleBuffer. Because channels carry bytes, ByteBuffer is used most. A buffer is created either with ByteBuffer.allocate(1024) or by wrapping an existing array with ByteBuffer.wrap(array).

A buffer has two modes. In write mode the position points to the next empty cell and the limit to the capacity. In read mode the position points to the next cell to read and the limit to the end of the data written. The modes are switched with flip(). The buffer does not know which mode it is in; the programmer has to keep track of it.

8.10.4ByteBuffer examples

8.10.6Channels

Definition 8.14

A channel is a connection that exchanges data with a file, a network socket, or another I/O device. Data from a channel is always read into a buffer (read(buffer)) and written from a buffer (write(buffer)).

There are four basic channel types: FileChannel reads and writes files, SocketChannel transmits data over a TCP network socket, ServerSocketChannel accepts incoming TCP connections, and DatagramChannel transmits data over a UDP socket. Channels are opened with factory methods such as FileChannel.open(path, options…) and SocketChannel.open(). When the work is done, they are closed with close() or with try-with-resources.

public class ChannelOpenClose {
  public static void main(String[] args) throws IOException {
    // Create a FileChannel
    FileChannel fileChannel = FileChannel.open(
        Paths.get("file.txt"), StandardOpenOption.READ);
    // Create a SocketChannel
    SocketChannel socketChannel = SocketChannel.open();
    socketChannel.connect(new InetSocketAddress("example.com", 80));
    System.out.println("Connected: " + socketChannel.isConnected());
    // Close the channels
    fileChannel.close();
    socketChannel.close();

}

This program opens two channels: a file channel and a network channel connected to port 80 of example.com. In blocking mode, connect waits until the connection is established. The program was actually run for these notes, and the connection succeeded. Two close() calls keep the channels from being left open; if an exception occurs, these lines are never reached. That is why try-with-resources is safer.

Reading with a file channel follows the typical pattern of buffer use:

8.10.8The selector

Definition 8.15

A selector is an NIO object that watches several channels from a single thread. Channels are put into non-blocking mode and registered with the selector. select() waits until at least one channel is ready and returns the number of ready channels.

A selector is created with Selector.open(). A channel is put into non-blocking mode with configureBlocking(false) and registered with channel.register(selector, events). Which events the channel waits for is specified with SelectionKey constants (Table 8.25).

Table 8.25: The SelectionKey event constants.

The following skeleton is the selector loop of a server. The loop is infinite; this program was therefore checked only by compiling it.

public class SelectorDemo {
  public static void main(String[] args) throws IOException {
    ServerSocketChannel server = ServerSocketChannel.open();
    Selector selector = Selector.open();
    server.bind(new InetSocketAddress(8080));
    server.configureBlocking(false);
    server.register(selector, SelectionKey.OP_ACCEPT);
    while (true) {
      int ready = selector.select();
      if (ready > 0) {
        Set<SelectionKey> keys = selector.selectedKeys();
        for (SelectionKey key : keys) {
          if (key.isAcceptable()) {
            // accept a connection
          } else if (key.isReadable()) {
            // read data
          }
        }
        keys.clear(); // drop handled keys
      }
    }
  }
}

The server channel is bound to port 8080, put into non-blocking mode, and registered for OP_ACCEPT. In the loop, select() gives the number of ready channels and selectedKeys() gives the ready keys. If the handled keys are not removed with clear(), they come back in the next round. In a real server, the accepted client channel is also registered with OP_READ and its data is read. Two rules are checked at registration. A blocking channel cannot be registered, and a server channel supports only the OP_ACCEPT event:

registering a blocking channel: IllegalBlockingModeException
OP_READ on a server channel: IllegalArgumentException
validOps == OP_ACCEPT: true

8.10.9Pros and cons of NIO

The advantages of NIO fall under three headings. Performance: data is transferred in blocks, which is more efficient than classic I/O for large files. Flexibility: buffers and channels allow flexible data handling; channels are two-way, and files and the network are processed in the same way. Many connections: with a selector, many channels are watched from a single thread, and only the active channels are processed.

The drawback is complexity. The code is longer and harder than with classic I/O. The buffer state and error cases such as a partial read or a dropped connection have to be managed by hand. Learning the selector also takes time, because the state of many channels has to be tracked correctly. As a rule, BufferedReader or Files is enough for reading a single file line by line. Channels come into their own for very large files and for large numbers of network connections.

}

The file has four records: 10, 20, 30, 40; each is 4 bytes, 16 bytes in all. seek(4) is the start of the second record, so a = 20. length() - 4 = 12 is the start of the last record; b = 40. After the read the pointer is at 16, that is, at the end of the file. The output is 20 40 16.

The solutions of the four exercises in the slides were also verified by running them with JDK 21. The first counts the lines, words, and characters of text.txt, whose content is "Java and files / read and write / (blank line) / very easy":

int lineCount = 0, wordCount = 0, charCount = 0;
try (BufferedReader br = new BufferedReader(new FileReader("text.txt"))) {
  String line;
  while ((line = br.readLine()) != null) {
    lineCount++;
    charCount += line.length();
    String trimmed = line.trim();
    if (!trimmed.isEmpty()) wordCount += trimmed.split("\\s+").length;
  }
} catch (IOException e) {
  System.err.println("Error: " + e.getMessage());
}
System.out.println(lineCount + " lines, " + wordCount + " words, "
    + charCount + " characters");
4 lines, 8 words, 37 characters

The trim() and isEmpty() check is needed for the blank line. "".split("\\s+") returns an array of length 1; without the check, the blank line would count as one word. The characters are 14 + 14 + 0 + 9 = 37; readLine discards the line terminators, so they are not counted.

The second exercise reads n from the keyboard, writes the numbers from 1 to n and their squares to squares.txt, then reads the file and finds the sum of the squares:

Scanner keyboard = new Scanner(System.in);
try (PrintWriter pw = new PrintWriter(new FileWriter("squares.txt"))) {
  int n = keyboard.nextInt();
  for (int i = 1; i <= n; i++) {
    pw.println(i + " " + i * i);
  }
}
int sum = 0;
try (Scanner in = new Scanner(new File("squares.txt"))) {
  while (in.hasNextInt()) {
    in.nextInt();               // i
    sum += in.nextInt();      // i * i
  }
}
System.out.println("Sum of squares: " + sum);
Sum of squares: 55

Reading starts after the writing block has closed; otherwise the data would remain in the buffer and the file would be read as empty. For n = 5: 1 + 4 + 9 + 16 + 25 = 55. The third exercise serializes an int array and reads it back. Arrays are serializable:

int[] arr = {3, 1, 4, 1, 5};
try (ObjectOutputStream c = new ObjectOutputStream(new FileOutputStream("arr.ser"))) {
  c.writeObject(arr);
}
try (ObjectInputStream g = new ObjectInputStream(new FileInputStream("arr.ser"))) {
  int[] copy = (int[]) g.readObject();
  int sum = 0;
  for (int x : copy) sum += x;
  System.out.println(copy.length + " elements, sum " + sum);
}
5 elements, sum 14

In the fourth exercise, five grades are written as int values with RandomAccessFile, and the grade at a given sequence number is found without reading the whole file: f.seek((pos - 1) * 4); int grade = f.readInt();. The position of the third grade is 8. The same approach works for the last record of a log file with 10,000 lines, but only if the records have a fixed size: seek((n - 1) * size). If the lines differ in length, the position cannot be computed. Either the file is read sequentially from the start, or a \n is searched for backwards from the end.

8.12Common mistakes

The mistakes mentioned here and there in the chapter are collected below, together with the real messages of the compiler or the JVM.

Not handling a checked exception. new FileReader("a.txt") can throw FileNotFoundException, and readLine() can throw IOException. The code must be inside try-catch, or the method must say throws IOException:

Main.java:5: error: unreported exception FileNotFoundException; must be caught or declared to be thrown
    BufferedReader r = new BufferedReader(new FileReader("a.txt"));
                                          ^
Main.java:6: error: unreported exception IOException; must be caught or declared to be thrown
    String s = r.readLine();
                         ^
2 errors

Forgetting the import. Scanner is in java.util, and the I/O classes are in java.io. If no import is written, the compiler cannot find the class:

Main.java:3: error: cannot find symbol
    Scanner sc = new Scanner(System.in);
    ^
  symbol:   class Scanner
  location: class Main
Main.java:3: error: cannot find symbol
    Scanner sc = new Scanner(System.in);
                     ^
  symbol:   class Scanner
  location: class Main
2 errors

Each of the other mistakes was shown with its real output in the relevant section: writing a single backslash in a Windows path, not checking for null in finally, using nextLine after nextInt, not closing a buffered writer, forgetting flip() or Serializable, keeping the result of read() in a byte, and writing write(chunk) in a block copy. In most of these the program compiles and runs but gives a wrong result. For this reason, after writing I/O code, always check the size of the copy, the values read, and the actual contents of the file.

8.13Summary

  • A stream is a structure that carries data from a source to a destination in order. Every Java program has three standard streams: System.in, System.out, and System.err. When output is redirected, System.err stays on the screen.
  • Scanner reads the keyboard, files, and strings. nextInt() leaves the line terminator in the buffer; a following nextLine() returns an empty string.
  • Every file is a sequence of bytes. In a text file the bytes are converted to letters with a character encoding; in a binary file they are interpreted as numbers, pixels, or instructions.
  • ASCII is 7 bits, and ISO-8859-9 is 8 bits for Turkish; UTF-8 writes a character with 1–4 bytes and has been the default since Java 18. A file must be read with the encoding it was written in.
  • 127 is 3 bytes as text and 4 bytes as an int. The binary size depends on the type, the text size on the number of digits. Binary data is read back in the order and with the type in which it was written.
  • File is only a path; it does not read the contents. Most of its methods report errors by returning false.
  • Byte streams (InputStream/OutputStream) are for any kind of data, and character streams (Reader/Writer) are for text. Wrapper streams add capabilities; closing the outermost one closes them all.
  • readLine() returns null at the end of the file, and read() returns −1. The result of read() is kept in an int.
  • FileWriter(name, true) appends; the form without the parameter resets the file. PrintWriter does not throw exceptions; errors are seen with checkError().
  • Buffering batches disk accesses. Data written may wait in memory until flush() or close().
  • try-with-resources closes resources in the reverse of the opening order and before catch.
  • In a block copy, only the n bytes actually read are written: write(chunk, 0, n). The shortcuts are transferTo and Files.copy.
  • RandomAccessFile jumps to any position with seek; with fixed-size records, the position of record k is k · record size.
  • Serialization converts an object to bytes. The class implements Serializable; static and transient fields are not written; the constructor is not called on reading back.
  • NIO works with buffers, channels, and selectors. After writing to a buffer, call flip() before reading and clear() or compact() before writing again.

8.15Test Yourself

  1. How many bytes does the word "Ilık" take in UTF-8 and in ISO-8859-9?

    Answer

    In UTF-8, I, l, and k take one byte each and ı takes two: 5. In ISO-8859-9 every letter is one byte: 4.

  2. With a PrintWriter, print(5L), print('A'), and print(1.5f) are called; with a DataOutputStream, writeLong(5), writeChar('A'), and writeFloat(1.5f). How many bytes is each of the two files?

    Answer

    The text file contains 5A1.5: 5 bytes. In the binary file, long is 8, char 2, and float 4 bytes: 14 bytes. print(1.5f) is independent of the locale and writes a dot.

  3. A file of 10,000 bytes is read by calling read(array) with a 4096-byte array. What values do the calls return? If write(array) had been used in the copy, how many bytes would the copy have?

    Answer

    4096, 4096, 1808, and −1 at the end of the file. write(array) writes the whole array in every round: 3 · 4096 = 12,288 bytes. In the last round, 2288 stale bytes are written in addition.

  4. ByteBuffer t = ByteBuffer.allocate(5); then 1, 2, 3 are written with put; then flip(), two get() calls, compact(), put((byte) 9), and flip() again. What are the position, the limit, the remaining count, and cells 0 and 1?

    Answer

    After the two get calls, the only unread element is 3. compact moves it to the front: position 1, limit 5. put(9) writes to cell 1 and the position becomes 2. flip sets the limit to 2 and the position to 0. Result: position 0, limit 2, remaining 2, cells 3 and 9.

  5. Into an empty file, 7, 8, 9 are written as int values with RandomAccessFile. Then seek(4); writeInt(100); seek(length()); writeShort(1); is done. What is the length of the file, and what does readShort() return after seek(0)?

    Answer

    Three int values are 12 bytes; writeInt(100) is written in place of the 8, and the length does not change. writeShort appends 2 bytes at the end: 14. readShort() reads the first two bytes. Since the bytes of 7 are 00 00 00 07, the result is 0.

  6. An object is created of a serializable class whose constructor prints "constructed" and which has the fields transient String note = "temporary"; and int n = 5;; n is set to 8, and the object is written and read back. How many times is "constructed" printed, and what are note and n in the object read?

    Answer

    Once; readObject does not call the constructor. note is null, because a transient field is not written and its field initializer does not run either. n is 8.

  7. The block try (R a = new R("A"); R b = new R("B"); R c = new R("C")) { … } finishes without an exception; R prints a message when it is opened and when it is closed. What is the order of the messages?

    Answer

    A opened, B opened, C opened, the body, C closed, B closed, A closed. Resources are opened from left to right and closed in the reverse order.

  8. A 3 MB file is read byte by byte through a default BufferedInputStream. How many reads are made on the underlying FileInputStream?

    Answer

    3 · 1,048,576 / 8192 = 384 reads that carry data, plus one read for the end of the file: 385.
