Chapter 11: Database Programming

A program's variables and objects live in memory and disappear when the program ends. Student grades, bank accounts, and sensor readings, however, must be kept for years, found quickly, and changed safely by many programs at the same time. Databases do this job. The chapter begins with the idea of a database, how it differs from a file, and the relational model. It then turns to SQLite, an embedded database, and to SQL, the common language of relational databases. The SQL part shows how to create tables, insert, query, update, and delete records, and how to join and group tables. The following sections cover JDBC, Java's database interface, and the safe way to use user input. The last sections show how to turn rows into objects and how transactions run several statements as a single unit of work. All code was run with JDK 21 and the SQLite JDBC driver.

11.1The idea of a database

This section explains what a database is, which problem it solves, and how it organizes data. There is no code here; the concepts defined below underlie all of the JDBC code that follows.

11.1.1Why do we need a database?

When a Java program executes int total = 87;, the value 87 is placed somewhere in RAM, the main memory. Objects live in the heap. This memory is fast but not persistent. When the program ends, the operating system reclaims its memory, and the variables and objects are gone. If the power fails, the contents of memory are erased as well.

Yet much data must outlive the program. A student's midterm grade is needed throughout the semester, a bank balance for years, a game's high score every time the game starts. Storing data this way is called persistent storage. Persistent storage lives on a medium such as a disk, which keeps its contents when the power is off.

Definition 11.1

A database is an organized collection of data that can be queried easily. The software that creates, protects, queries, and updates a database is called a database management system (DBMS).

In everyday speech the two are often confused: people say "the MySQL database", but MySQL is really a DBMS. The database is the set of tables and the records in them that the system manages. Figure 11.1 shows the difference between the two kinds of storage. While running, a program works on data in memory and writes whatever must last to the database (INSERT, UPDATE). When the program starts again, the data is read back from disk (SELECT).

An analogy helps. A database is like a library's catalogued archive. Without a catalog, finding a book would mean walking past every shelf. With one, the book's location is found in a few steps. A database likewise finds the record you want among millions without reading all the data from beginning to end.

11.1.2File or database?

A database is not the only way to store data persistently. A program can also write data to a text file or to a CSV (comma-separated values) file. For a settings file, a log, or a short list, a file is enough and simpler. As data grows and becomes more complex, and as several programs begin to use the same data, the limits of files appear. Table 11.1 compares the two approaches on six points.

Table 11.1: Flat file versus database.
FeatureFlat file (txt, csv)Database
SearchThe file is read from start to endFast with an index; a one-line SQL query
UpdateOften the whole file is rewrittenOnly the affected row changes
Concurrent accessData can be corrupted if two programs write at onceSafe, thanks to locking and transactions
ConsistencyFormat checking is left entirely to the programmerData types and constraints (NOT NULL, UNIQUE, CHECK)

Each difference in the table corresponds to a concrete problem. If a school's student list is in a CSV file, finding one student among 20,000 rows means reading the file line by line. Changing one student's phone number usually means reading the whole file, changing it in memory, and writing it out again, because if a line in the middle of a text file grows longer, every byte after it shifts.

The most serious problem is concurrent access. If two teachers enter grades at the same time, both read the file, make their own changes, and write it back. The second one to write overwrites the first one's change without noticing it. A DBMS manages this situation with locks and transactions. If the power fails during a write, the file may be left half-written; a database rolls back the unfinished transaction at startup.

The difference in consistency is also large. Nothing stops someone from typing "twenty" instead of an age into a cell of a CSV file; every program that reads the file must check for this error itself. In a database the rules are part of the table definition, and a record that violates them is rejected up front. Figure 11.2 summarizes the structural difference: with a file, the program accesses the file directly; with a database, a DBMS sits in between.

11.1.3Core features

Four core features make databases superior to files.

Fast access to data. A database keeps extra structures called indexes for frequently searched columns. With an index, a record among millions is found quickly without looking at every row.

Column-level security. With a file, permissions usually apply to the whole file: whoever can read the file can read everything in it. A DBMS can grant permissions per table or even per column (field). In a company database, for example, only the accounting department may see the salary column, while other departments can read the name and phone columns of the same table. These permissions are granted in server DBMSs (for example with GRANT in PostgreSQL or MySQL); SQLite has no users or permissions, and access depends on file permissions.

Platform-independent, standard interfaces. SQL is a standard; its core statements are the same in all relational databases. On the Java side there is likewise a single set of interfaces, JDBC. The same Java code reaches different databases when the driver is swapped.

Independence from the file structure. The program does not know in which file, in what order, or in what format the data is stored on disk. Its job is to say what it wants in SQL; the DBMS decides how to find the data (Figure 11.3). Because of this separation, when the DBMS adds an index or changes how the data is laid out, the program code does not change.

Two more features come on top of these four. The first is integrity constraints: rules such as "this column cannot be empty", "this value cannot repeat", or "age cannot be negative" are written into the table, and the DBMS rejects any record that violates them. The second is transaction support: several changes are either all applied or none is.

11.1.4The relational model

The most common kind of database today is the relational database. Its name comes from the fact that data is kept in tables based on the mathematical notion of a relation.

Definition 11.2

The relational model keeps data in tables made of rows and columns. A column is one attribute of the data; it has a name and a data type. A row (record) holds all the information about one entity. A primary key is a column that identifies each row of the table uniquely; no two rows can have the same primary key.

Figure 11.4 shows the users table used throughout the chapter. The table has three columns. The type of the name column is text (TEXT), and the type of the id column is integer (INTEGER). The highlighted second row holds everything about the user named Ayşe Demir: her ID is 2 and her e-mail is ayse@example.com.

Why is a primary key needed? Two users can have the same name; if two "Ahmet Yılmaz" records cannot be told apart, it is unclear which one to update. Even first and last name together are not unique. That is why each row is given a number that identifies it and nothing else. The number never changes and is never given to another row. The primary key is also used by other tables to point to this row.

An analogy with Java is useful. A table corresponds to a class, a column to a field, and a row to an object. The users table resembles a User class with the fields int id, String name, and String email; each row is an object of that class. The analogy is not exact: a table holds only data and has no methods. But this mapping is used directly when rows are converted to objects.

Common mistake

Confusing rows with columns. A column is an attribute found in every record (email). A row is one record and carries all of its attributes (Ayşe Demir's ID, name, and e-mail). "Adding a new student to the table" means adding a new row; "adding a birth date for students" means adding a new column.

11.1.5Kinds of databases

Databases are grouped by the way they organize data. Three groups matter for this course.

Relational databases keep data in tables and are queried with SQL. Oracle, SQL Server, MySQL, and PostgreSQL belong to this group. These systems run as a server; many clients connect to the same database over the network. Most usage, about 77 percent, is in this group.

NoSQL and search systems do not use tables. They keep data as documents (JSON-like records), key-value pairs, or a search index. MongoDB is a document database and Elasticsearch is a search engine. They are used in particular scenarios, for example for data whose structure changes often or whose volume is very large. Their share of usage is about 23 percent (Figure 11.5).

Embedded relational databases run not as a separate server but as a library inside the program. The best known is SQLite. They are common where little data is shared and a single program stores its own data: phone apps, browsers, embedded devices.

The examples in this chapter use SQLite, which is the easiest to set up. There is no server to install, no user to define, and no network to configure. The SQL statements and the JDBC code are almost the same in other relational databases. What you learn with SQLite carries over directly to MySQL or PostgreSQL; only the connection URL and the driver change.

11.2SQLite

11.2.1What is SQLite?

SQLite is an open-source, free relational database written in C. The following features set it apart from other relational systems.

  • It is embedded: it runs as a library inside the program. When a Java program calls SQLite, no separate process starts; the database code runs in the program's own process.
  • It is serverless: no separate server program, installation, or database administrator is needed.
  • It is self-contained: all tables, indexes, and the schema are stored in a single disk file, for example sample.db. Backing up the database or moving it to another machine means copying this file.
  • It is cross-platform: the same .db file opens on Windows, Linux, macOS, and Android.

SQLite is the most widely used embedded relational database in the world. It is found in every Android phone, every major browser, and many desktop programs. Common uses are mobile apps, embedded systems, small-scale applications, and desktop programs such as browsers and e-mail clients. For electrical and electronics engineering, embedded systems are especially important: a measuring device can store the values it reads in a SQLite file and query them later.

There is also a clear case where SQLite is not suitable: large systems in which many users write at the same time over a network. SQLite allows only one writer at a time. For the thousands of concurrent orders of an e-commerce site, a server-based system such as MySQL or PostgreSQL is needed.

11.2.2Server-based and embedded databases

Figure 11.6 shows the difference between the two architectures. A server-based database involves two processes: the Java program and the database server. The program connects to the server over the network; MySQL's default port is 3306. A user name and password are supplied when connecting. The server writes the data to files on disk; the program never sees these files.

An embedded database involves a single process. The SQLite library lives inside the Java program and reads and writes the .db file directly. There is no network, user name, or password. Table 11.2 summarizes the differences.

11.2.3The driver, DB Browser, and running the code

For Java to talk to SQLite, a JDBC driver is needed. The common driver for SQLite is Xerial's sqlite-jdbc library (github.com/xerial/sqlite-jdbc). The driver is a single jar file, for example sqlite-jdbc-3.40.0.0.jar. This jar contains both the Java classes and SQLite's native library compiled for each operating system, so SQLite does not need to be installed separately.

To look inside the database file you can use DB Browser for SQLite (sqlitebrowser.org). This program opens a .db file, shows the tables and rows visually, and runs SQL statements. It is very useful for checking what a Java program has changed. After the program inserts a row, you refresh the table in DB Browser and see that the row was really added.

In Eclipse, the driver is added to the project as follows. Put the jar file in a lib folder in the project. Right-click the project and choose Build Path → Configure Build Path…. In the Libraries tab select Classpath, add the jar with Add JARs…, and close with Apply and Close. From the command line, compiling and running look like this:

javac Connect.java
java -cp ".;sqlite-jdbc-3.40.0.0.jar" Connect

The first line compiles the program. The driver is not needed for compiling, because the java.sql package that the program uses ships with the JDK. The second line runs the program. The -cp option gives the classpath: the dot is for Connect.class in the working folder, and the jar is for the driver. On Windows, classpath entries are separated by a semicolon (;); on Linux and macOS, by a colon (:). The driver is needed only at run time; if the jar is not on the classpath, the program compiles but fails when it tries to connect. The message in that case has the form "No suitable driver found …".

11.3SQL basics

Before connecting to a database from Java, you need to know the database's language. A Java program sends SQL statements to the database as text; the database parses and runs them. The statements in this section work the same in DB Browser for SQLite and inside a Java program.

11.3.1Common SQL statements

Definition 11.3

SQL (Structured Query Language) is the common language of relational databases. An SQL statement that asks the database for data is called a query.

Unlike Java, SQL is a declarative language. To search an array in Java you write a loop: you say step by step which element to look at and in what order. In SQL you describe only the result you want: "get the players whose score is above 70." The DBMS decides how to produce the result. Table 11.3 lists the five most commonly used statements.

Table 11.3: Common SQL statements and CRUD operations.
StatementPurposeExampleCRUD
CREATE TABLECreates a new tableCREATE TABLE users (id INTEGER, name TEXT)—
INSERT INTOInserts a new recordINSERT INTO users(name) VALUES('Ali')Create
SELECTQueries a tableSELECT * FROM usersRead
UPDATEUpdates existing recordsUPDATE users SET name = 'Efe' WHERE id = 1Update
DELETEDeletes recordsDELETE FROM users WHERE id = 1Delete

The four basic operations on persistent data are known as CRUD. The name comes from the initials of the operations: create, read, update, and delete. Almost every database application is a combination of these four operations. Figure 11.7 shows which SQL statement corresponds to each letter. CREATE TABLE is not part of CRUD; it creates the structure of the table, not data.

The syntax rules are short. SQL keywords are case-insensitive: select and SELECT are the same. For readability, keywords are written in upper case and table and column names in lower case. Text values go inside single quotes: 'Ali'. Double quotes in SQL are used for names, not values; that is why SQL inside a Java string writes text values with single quotes, and the two languages do not get mixed up. The asterisk in SELECT * means "all columns". WHERE selects the rows to which the statement applies.

11.3.2CREATE TABLE, data types, and constraints

A table is defined by its name and its columns. Each column has a name, a type, and optional constraints. The following statement creates a table of members:

CREATE TABLE IF NOT EXISTS members (
  id    INTEGER PRIMARY KEY,   -- unique
  name  TEXT NOT NULL,         -- required
  email TEXT UNIQUE,           -- no repeats
  age   INTEGER CHECK (age >= 0)
)

Each part of the statement has a job. IF NOT EXISTS prevents an error when the table already exists. The program can run this statement every time it starts: the first time the table is created, and later the statement does nothing. Parts that start with -- are comments that run to the end of the line in SQL, like // in Java.

INTEGER PRIMARY KEY has a special meaning in SQLite. This column is the row's internal number (rowid). If no value is given on insert, SQLite assigns one more than the largest id in the table, or 1 if the table is empty. The program therefore does not need to generate numbers.

Constraints are rules written into the table. NOT NULL says the column cannot be left empty, UNIQUE says a value cannot repeat in two rows, and CHECK says the given condition must hold in every row. If a constraint is violated, the statement is rejected and the table does not change. The following experiment sends nine inserts to this table and prints the message JDBC gives for each rejected insert:

accepted: INSERT INTO members(name, email, age) VALUES ('Ada', 'ada@x', 20)

Each message corresponds to one constraint. The row without a name is rejected with NOT NULL constraint failed: members.name, and the row with age −3 with CHECK constraint failed: age >= 0. The row that reuses Ada's e-mail runs into the UNIQUE constraint, and the second row with id 1 runs into the primary key. The [SQLITE_CONSTRAINT_…] part at the start of the message is an error code added by the driver; the actual message in parentheses comes from SQLite itself.

The last lines of the output show how INTEGER PRIMARY KEY behaves. Naz gets number 2. When Ece is given 10 by hand, the next row (Nur) gets 11: the largest id + 1. Numbers 3 to 9 stay unused; this is not a problem, because a primary key does not have to be consecutive, only unique.

The last row reveals a subtlety specific to SQLite: the text 'twenty' could be stored in an INTEGER column. SQLite is flexibly typed; a column's type is only a suggestion (type affinity). If a value can be converted to a number it is stored as a number, and otherwise as text. CHECK (age >= 0) did not stop this row either, because in SQLite comparisons any text value counts as greater than any number. MySQL and PostgreSQL reject such a value. So on the Java side the value must be given with the right type, and numbers should be sent with typed methods such as setInt. Table 11.4 lists the Java counterparts of the SQLite types.

11.3.3SQL statements step by step

How the five basic statements change a table can be followed by running them in order on an empty database. The first statement creates the table:

CREATE TABLE users (id INTEGER PRIMARY KEY,
                    name TEXT, email TEXT)

After this statement the table has three columns but no rows. Two inserts follow:

INSERT INTO users(name, email)
  VALUES('Ahmet Yılmaz', 'ahmet@example.com')
INSERT INTO users(name, email)
  VALUES('Ayşe Demir', 'ayse@example.com')

The inserts do not give an id; only the name and email columns are named, and their values are given in the same order inside VALUES. SQLite assigns 1 to the first row and the largest id + 1 = 2 to the second. Each insert affects one row. Then the first row is updated and deleted, and finally the table is read:

UPDATE users SET name = 'Mehmet Akdeniz'
  WHERE id = 1
DELETE FROM users WHERE id = 1
SELECT * FROM users

If the statements are run one by one from a Java program and the table is printed after each, the result is Table 11.5. The "Rows affected" column is the count that JDBC reports for each statement.

An update changes only the column named in SET; email stays the same (Figure 11.8). WHERE id = 1 selects only the first row. The delete uses the same condition and removes only the first row. The final SELECT does not change the table; it only reads and returns one row. The deleted number 1 is not passed to Ayşe: her id stays 2. A primary key does not change once it has been assigned.

Common mistake

Forgetting WHERE in UPDATE or DELETE. UPDATE users SET name = 'X' raises no error; it changes the name of every row in the table. DELETE FROM users deletes all rows but leaves the table itself. On a table with three rows, both statements return 3. The database does not treat this as an error; the only ways to undo it are to work inside a transaction or to restore a backup.

11.3.4SELECT: filtering, sorting, limiting

SELECT is the most used and richest statement in SQL. The examples in this section work with a score table of five rows (Figure 11.9).

A query consists of at most seven clauses; five of them are used here. SELECT says which columns to return, and FROM says which table to read. WHERE filters rows by a condition. The condition can use comparisons such as =, <> (not equal), <, and >=, and the connectives AND and OR. LIKE 'e%' means "starts with e": % stands for any number of characters and _ for exactly one. ORDER BY sorts the result; DESC means descending, and the default ASC means ascending. LIMIT n takes the first n rows. Table 11.6 gives four queries and their results.

Table 11.6: Four queries on the scores table (results obtained by running them).
QueryResult
SELECT player, score FROM scores WHERE score < 90 ORDER BY score DESCnaz 81, ada 72, ece 58
SELECT player, score FROM scores ORDER BY score DESC, player LIMIT 3can 95, efe 95, naz 81
SELECT player, score FROM scores WHERE player LIKE 'e%'ece 58, efe 95
SELECT COUNT(*), AVG(score), MAX(score) FROM scores WHERE score >= 604 · 85.75 · 95

The first query selects scores below 90; can and efe (95) are dropped. The remaining three rows are sorted by score in descending order. The second query has no filter. Its sort has two keys: score descending first, and player name ascending when scores tie. can and efe tie at 95; can comes first alphabetically. LIMIT 3 takes the first three rows. Without the second key, the order of tied scores would be undefined, and the result would depend on how the DBMS happened to lay out the data.

The third query returns the two names that start with e. In SQLite, LIKE is case-insensitive for ASCII letters; LIKE 'E%' gives the same two rows. The fourth query returns a single row, because COUNT, AVG, and MAX are aggregate functions: each produces one value from a set of rows. There are four scores of 60 or more: 72, 95, 95, and 81. Their sum is 343 and their average is 343 / 4 = 85.75. The maximum is 95. SUM and MIN belong to the same family.

Keep in mind how these functions behave on an empty set. With WHERE score > 100, where no row is selected, COUNT(*) returns 0, while AVG(score) and SUM(score) return NULL. The query still returns a single row; its values are empty.

11.3.5Code trace: a SELECT query

An SQL statement does not run in the order it is written. The following Java code sends a query to the database and prints the result row by row. What matters here is not the JDBC types but the stages the query goes through.

String sql = "SELECT player, score FROM scores "
           + "WHERE score > 70 "
           + "ORDER BY player DESC LIMIT 2";
try (Statement st = conn.createStatement();
     ResultSet rs = st.executeQuery(sql)) {
  while (rs.next()) {
    System.out.println(rs.getString("player") + " "
                       + rs.getInt("score"));
  }
}
naz 81
efe 95

The database processes FROM first: it takes the five rows of the table. Then it applies the condition WHERE score > 70 to each row and drops ece (58); four rows remain. Next, ORDER BY player DESC sorts the rows in reverse alphabetical order by name: naz, efe, can, ada. The sort is by name, not by score. Finally LIMIT 2 takes the first two rows. The result set has two rows: (naz, 81) and (efe, 95). Figure 11.10 shows these stages.

The result reaches Java as a ResultSet object. This object has a cursor, which starts out before the first row. 11.4Relationships and grouping

In a real application the data does not fit in a single table. Students, departments, courses, and orders live in separate tables and are linked to one another. This section explains why tables are split, how they are linked, and how linked tables are combined in a single query.

11.4.1Normalization

Suppose a shop keeps its orders in a single table: each row holds the customer's name, phone, and the product ordered. If Ali places three orders, his name and phone are repeated in three rows (Figure 11.11, top). This repetition is not just wasted space; the real problem is the risk of inconsistency.

Repetition leads to three kinds of corruption, called anomalies. Update anomaly: when Ali's phone changes, every row must be corrected separately; if one is forgotten, Ali has two different phones and there is no way to know which is right. Insert anomaly: a customer who has no orders yet cannot be recorded, because every row is an order. Delete anomaly: when Ece's only order is deleted, Ece's phone is lost too.

Definition 11.4

Normalization is splitting data into tables so that each fact is stored in exactly one place, in order to avoid repetition. The split tables are linked to one another by a key.

In the lower part of the figure, the customer's information is stored once in the customers table. The orders table holds not the customer's name and phone but only the customer's number (customer_id). When Ali's phone changes, a single cell is updated. A customer with no orders can be added to customers. Even if Ece's order is deleted, Ece's record remains. All three anomalies disappear at once.

The first rule of normalization is called first normal form: each cell holds a single value. A customer's two phones are not written as a list in one cell such as '555-11, 555-33'. In such a cell, searching for "the customer whose phone is 555-33" becomes hard, and removing one number turns into text processing. The phones are moved either to separate rows or to a separate phones(customer_id, number) table. Higher normal forms exist as well; for this course the first rule and the principle "each fact in one place" are enough.

11.4.2Foreign keys

The column that links split tables has a special name.

Definition 11.5

A foreign key is a column that points to another table's primary key. The value of a foreign key either equals the key of a row in that table or is NULL.

The chapter's relationship examples use two tables: depts and students. Every student has a department, and the link is made through the dept_id column:

CREATE TABLE depts (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL);
CREATE TABLE students (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  dept_id INTEGER REFERENCES depts(id));

REFERENCES depts(id) declares that dept_id is a foreign key. The following rows are inserted into the tables; Deniz's department is not yet known:

INSERT INTO depts(name) VALUES ('CS'), ('EE'), ('ME');
INSERT INTO students(name, dept_id)
  VALUES ('Ada', 1), ('Bora', 2), ('Cem', 1), ('Deniz', NULL);

Figure 11.12 shows the relationship. Ada and Cem both have dept_id 1; both are in the CS department. A department can have several students, but a student has only one department. This structure is called a one-to-many relationship. In Java the counterpart is that each Student object holds a Dept reference. In the table, a key value stands in place of the object reference.

The main benefit of a foreign key is integrity checking. Adding a student to the nonexistent department 9, or deleting a department that still has students, breaks the link: the student carries a number that points nowhere. A DBMS rejects both operations. SQLite, however, does not perform this check by default, for backward compatibility. The check must be enabled separately on every connection:

PRAGMA foreign_keys = ON;
INSERT INTO students(name, dept_id) VALUES ('Efe', 9);   -- rejected
DELETE FROM depts WHERE id = 2;                        -- rejected: Bora is linked
DELETE FROM depts WHERE id = 3;                        -- accepted: ME is empty

Another kind of relationship besides one-to-many is also common: many-to-many. A student is enrolled in many courses, and a course has many students. This relationship cannot be built with columns of the two tables alone; a third, linking table is needed:

CREATE TABLE enrollments (
  student_id INTEGER REFERENCES students(id),
  course_id  INTEGER REFERENCES courses(id),
  PRIMARY KEY (student_id, course_id));

Each row of the enrollments table says "this student is enrolled in this course". Each of the two columns is a foreign key to a different table. The primary key is the combination of the two columns, so the same student cannot be enrolled in the same course twice.

11.4.3Combining tables with JOIN

Normalization has a price: the answer to "Which department is Ada in?" is now spread over two tables. students holds only the number 1, and depts says that 1 is "CS". To bring the two pieces of information together in one result, the tables are joined.

Definition 11.6

A join (JOIN) is an SQL operation that matches the rows of two tables according to an ON condition and produces a single result table. A plain JOIN (or INNER JOIN) returns only the rows that have a match; a LEFT JOIN returns all rows of the left table.

SELECT s.name AS student, d.name AS dept
FROM students s JOIN depts d
  ON s.dept_id = d.id
ORDER BY s.id

In the query, s and d are table aliases: FROM students s says that s can be written in place of students in the rest of the query. Aliases are required here, because both tables have a column called name. s.name is the student's name and d.name is the department's name. AS gives a result column a new name; on the Java side the column is read by that name: rs.getString("dept"). ON s.dept_id = d.id is the matching condition: a student row is matched with the department row whose id equals its own dept_id.

Written with LEFT JOIN on the same tables, the query becomes:

SELECT s.name AS student, d.name AS dept
FROM students s LEFT JOIN depts d
  ON s.dept_id = d.id
ORDER BY s.id

The results of the two queries are side by side in Table 11.8. The only difference is Deniz. Because Deniz's dept_id is NULL, he matches no department. JOIN leaves a row without a match out of the result. LEFT JOIN keeps every row of the left table (students); if there is no match, it fills the right table's columns with NULL. In Java, reading this value with getString gives null.

11.4.5GROUP BY and HAVING

Aggregate functions give a single value when applied to a whole table. Often, though, you want a separate value for each group: the number of orders per customer, the number of students per department. The examples in this section use an order table of six rows:

INSERT INTO orders(customer, amount) VALUES
  ('Ali', 120), ('Ece', 80), ('Ali', 50),
  ('Can', 200), ('Ali', 30), ('Ece', 40);

GROUP BY customer gathers the rows that have the same customer value into one group. Aggregate functions are computed separately for each group, and each group becomes a single row in the result (Figure 11.14). Ali has three orders: 120 + 50 + 30 = 200. Can has a single order of 200, and Ece has two orders: 80 + 40 = 120.

Filtering can happen before or after grouping. WHERE filters rows before grouping. HAVING filters groups after grouping. That is why a condition containing an aggregate function cannot go in WHERE: when WHERE runs there are no groups yet, and therefore no SUM(amount). If you write WHERE SUM(amount) >= 150, SQLite rejects it with the message misuse of aggregate: SUM(). Table 11.10 compares three cases.

Table 11.10: Three forms of the query SELECT customer, COUNT(*), SUM(amount) FROM orders ….

GROUP BY customerAli (3, 200) · Can (1, 200) · Ece (2, 120)

In the second row, WHERE amount >= 50 first filters the individual orders: Ali's order of 30 and Ece's order of 40 are dropped. The groups are built from the remaining orders. Ali's count falls to 2 and his total to 170. In the third row, all orders are grouped first, and then Ece's group, whose total is below 150, is dropped. The two queries look alike but answer different questions: one says "count the orders of 50 TL or more by customer", the other "find the customers whose total is 150 or more".

The clauses of a query run logically in this order:

FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT

This order explains many rules. WHERE cannot use aggregate functions, because it comes before grouping. ORDER BY can use aliases defined in SELECT, because it comes after it.

Grouping is also used together with joins. The number of students in each department is found like this:

SELECT d.name, COUNT(s.id)
FROM depts d LEFT JOIN students s
  ON s.dept_id = d.id
GROUP BY d.id

The result is CS 2 · EE 1 · ME 0. Two details matter here. Thanks to LEFT JOIN, ME, which has no students, also appears in the result; a plain JOIN would have hidden it. The second detail is COUNT(s.id). COUNT(column) counts only values that are not NULL. In ME's single joined row, s.id is NULL and is not counted; the result is 0. COUNT(*), on the other hand, counts rows. Had it been used, it would have given ME a 1; this was verified by running it.

There is one more trap in grouping. In the query SELECT customer, amount FROM orders GROUP BY customer, amount is neither grouped nor inside an aggregate function. Ali's group has three different amounts; which one should be shown? SQLite raises no error and returns the value from one of the rows in the group. In a test, Ali came out as 120, Can as 200, and Ece as 80. Many databases, such as PostgreSQL and SQL Server, reject this query. The rule is simple: every column in SELECT either appears in GROUP BY or is inside an aggregate function.

11.4.7NULL: the absence of a value

Deniz's department is unknown. This is shown in the table as NULL.

Definition 11.7

In SQL, NULL is a special marker that means a value is unknown or absent. NULL is neither 0 nor the empty string (''). Every comparison involving NULL gives the result "unknown".

SQL uses a three-valued logic: true, false, and unknown. The comparison dept_id = NULL is not true even for Deniz; it is unknown. Whether an unknown value equals another unknown value is unknown as well. WHERE selects only the rows whose condition is true; that is why the first query below returns no rows:

SELECT name FROM students WHERE dept_id = NULL;      -- 0 rows
SELECT name FROM students WHERE dept_id IS NULL;     -- Deniz
SELECT name FROM students WHERE dept_id <> 1;        -- only Bora
SELECT name, COALESCE(dept_id, 0) FROM students;     -- Deniz 0
SELECT COUNT(*), COUNT(dept_id) FROM students;     -- 4 and 3

The correct forms are IS NULL and IS NOT NULL. The result of the third line is more surprising. dept_id <> 1 does not select Deniz either, because it is not even known whether NULL differs from 1. If you want "the students outside CS", write WHERE dept_id <> 1 OR dept_id IS NULL.

NULL also propagates through arithmetic: the result of NULL + 1 is NULL. COALESCE(dept_id, 0) returns the second argument if the first is NULL; this puts 0 in place of NULL. Aggregate functions skip NULLs. COUNT(*) counts rows and gives 4; COUNT(dept_id) counts the values that are not NULL and gives 3. If no rows match, AVG and SUM return NULL and COUNT returns 0. All of these lines were verified by running them in a Java program.

11.4.8Indexes

The secret of a database's fast search is the index.

Definition 11.8

A database index is an additional structure that keeps the values of a column in sorted order and points to the row where each value is found. SQLite stores an index as a B-tree.

An index is like the index at the back of a book. The pages where the word "inheritance" appears can be found from the index without reading the book from cover to cover. Without an index, the query WHERE name = 'Cem' looks at every row of the table; this is called a scan. With an index, a search similar to binary search is made in the sorted structure, and the database goes directly to Cem's row (Figure 11.16). In a table of n rows, a scan needs n comparisons, while a search in the B-tree takes about log n steps. For a million rows, that is the difference between a million and about twenty.

An index is created with CREATE INDEX. SQLite's EXPLAIN QUERY PLAN statement shows how a query will be executed, that is, whether the table will be scanned or an index will be used:

CREATE INDEX idx_stu_name ON students(name);
EXPLAIN QUERY PLAN
  SELECT * FROM students WHERE name = 'Cem';

SCAN shows that the table will be scanned, and SEARCH that an index will be used for the search. No separate index is needed for a primary key; INTEGER PRIMARY KEY is already the table's own ordering key. The index of a UNIQUE column is created automatically too, because the DBMS needs it to check for duplicates.

The last row shows the limit of an index. LIKE '%em' means "ends with em". An index keeps names sorted from the beginning; names that end in "em" are scattered throughout the sequence. A leading wildcard therefore cannot use the index. In the test, LIKE 'C%' also produced a SCAN. In SQLite LIKE is case-insensitive, while an ordinary index is case-sensitive, so even a prefix search did not use the index with default settings.

An index has a cost. Every INSERT, UPDATE, and DELETE updates not only the table but also the index, and the index takes up disk space. That is why not every column gets an index. An index goes on columns that are searched often and used in WHERE, JOIN, or ORDER BY. To see how large the effect is, 200 searches by the name column were run on a table of 200,000 rows. Without an index the searches took 633 ms; after the index was created, the same searches took 1 ms. The times vary with the machine and the run; the ratio is hundreds of times each time.

11.5JDBC

SQL statements are the database's language; the Java program must pass these statements to the database and get the results back. JDBC builds this bridge.

11.5.1What is JDBC?

Definition 11.9

JDBC (Java Database Connectivity) is the standard API (application programming interface) that Java offers for connecting to databases. It lives in the java.sql package and ships with the JDK. The code that talks to a particular database is supplied by that database's JDBC driver.

The structure of JDBC is a fine application of the interface concept from object-oriented programming. Connection, Statement, and ResultSet in the java.sql package are interfaces; they only say which methods will exist. The driver of each database vendor implements these interfaces with its own classes. The SQLite driver knows how to talk to a SQLite file, and the MySQL driver knows how to talk to a MySQL server (Figure 11.17).

Because the program knows only the interfaces, switching databases often means changing only the driver jar and the connection URL. Polymorphism is at work here. The type of the variable in the program is Connection. At run time, the class of the actual object the variable refers to is org.sqlite.jdbc4.JDBC4Connection in the SQLite driver. This name was verified by printing conn.getClass().getName(). When the program calls conn.createStatement(), the JVM runs this class's implementation of the Connection interface. The same line runs the MySQL driver's implementation with MySQL.

An object of an interface cannot be created directly. If you write new Connection(), the compiler rejects it:

    Connection conn = new Connection();
                      ^

It is possible to build the connection object with new from the driver's class, but that would be wrong, because the program would become dependent on one driver. A connection is always obtained with DriverManager.getConnection; the driver decides which class's object is returned.

Connection, Statement, and ResultSet hold resources in the database: an open file, locks, memory. All three implement the AutoCloseable interface and must be closed when you are done with them. The safest way is try-with-resources.

11.5.3The connection URL

DriverManager learns which database to connect to from a text address. This address is called the JDBC URL (Figure 11.18).

The format of the URL is jdbc:<subprotocol>:<database file or address>. The first part is always jdbc. The second part determines the driver: sqlite, mysql, postgresql. DriverManager asks the registered drivers in turn whether they accept the URL. The first driver that accepts it opens the connection. The format of the third part is specific to the driver. For example, the URL jdbc:sqlit:school.db gives this message even when the driver is loaded, because no driver recognizes the subprotocol sqlit. The second line is the ClassNotFoundException received when the old method looks up the driver class.

11.5.4The steps of a JDBC program

Every JDBC program follows the same five steps (Figure 11.19): open a connection, create a statement object, run the SQL, process the result, and close the resources.

try (Connection conn = DriverManager.getConnection(url); // 1
     Statement stmt = conn.createStatement();             // 2
     ResultSet rs = stmt.executeQuery(sql)) {             // 3
  while (rs.next()) {                                     // 4
    System.out.println(rs.getInt(1));
  }
} // 5: rs, stmt, conn auto-closed in reverse

The structure of the code matches the steps one to one. Steps one, two, and three happen in order in the try-with-resources parentheses: the connection is opened, a Statement is taken from it, and the Statement runs the query and returns a ResultSet. Step four is the while (rs.next()) loop. No code is written for step five: when the block ends, even after an error, the resources are closed in the reverse order of opening. First rs, then stmt, and last conn.

The reverse order is not arbitrary. A ResultSet depends on its Statement, and the Statement depends on its Connection. If the connection were closed first, the others would be left dangling. To verify the closing, the resources were copied into variables outside the block and queried with isClosed() after the block ended:

Connections that are not closed can leave the SQLite file locked. Another program, or even another connection of the same program, cannot write to the file. In long-running programs, objects that are not closed also cause memory leaks.

The code has one more detail: rs.getInt(1). Columns can be read by name or by position. In JDBC, column numbers start at 1. For a programmer used to Java arrays starting at 0, this is a frequent source of errors.

Common mistake

Trying to use a try-with-resources resource outside the block. The scope of a variable declared in the parentheses is the block only; when the block ends, the resource is both closed and out of sight. The compiler rejects the use outside:

11.6Basic operations

The six small programs in this section run in sequence on the same file, sample.db: connecting, creating a table, inserting, reading, updating, and deleting. The programs are independent; each opens and closes its own connection. The data stays persistently in the file between programs. Each program was run in full inside public static void main with import java.sql.*;; the chapter shows only the body of main.

11.6.1Connecting to SQLite

// Path to the database file (connection URL)

The program keeps the connection URL in a variable and opens the connection with getConnection. 11.6.2Creating a table

String url = "jdbc:sqlite:sample.db";

           + "(id INTEGER PRIMARY KEY, name TEXT, email TEXT)";

     Statement stmt = conn.createStatement()) {

Table created!

This time there are two resources in the try-with-resources parentheses: the connection and a Statement. CREATE TABLE produces no result set; execute returns false. For SELECT it would return true. The program does not use the return value; both cases were verified by printing them in a separate experiment.

11.6.4Reading data

String url = "jdbc:sqlite:sample.db";
String sql = "SELECT * FROM users";

     Statement stmt = conn.createStatement();
     ResultSet rs = stmt.executeQuery(sql)) {
  // Read and print the rows one by one.
  while (rs.next()) {
    System.out.println("ID: " + rs.getInt("id")

} catch (SQLException e) {
  System.out.println(e.getMessage());
}
ID: 1, Name: Ahmet Yılmaz, Email: ahmet@example.com

Reading is done with executeQuery, which returns a ResultSet. This time the result set is also a resource, so it joins the try-with-resources parentheses as the third resource. rs.next() moves the cursor to the next row; it returns true if there is a row and false if not. getInt("id") and getString("name") read the columns of the current row by name. Since the table has a single row, the loop runs once.

Reading by column name is safer than reading by position. SELECT * returns the columns in the order of the table definition; if a new column is added to the table later, the numbers may shift, while the names do not change. In the SQLite driver, column names are case-insensitive: getString("NAME") works too. A column name that does not exist throws a SQLException: trying getString("title") gave the message no such column: 'title'.

11.7PreparedStatement

The SQL texts so far were fixed. In real programs, the values come from the user: the name to search for, the grade to insert, the number of the record to delete. There is a wrong way and a right way to put these values into the SQL text.

11.7.1SQL injection

The easiest-looking way is to paste the value the user typed into the SQL text by string concatenation. On a search screen the user types the name to look for, and the program builds this text: "SELECT name FROM people WHERE name = '" + input + "'". As long as the input is Ali, all is well. But if the input contains a quotation mark, the structure of the SQL text changes.

Definition 11.10

SQL injection is an attack in which user input gets mixed into an SQL statement and changes its meaning. The input is interpreted not as a value but as part of the SQL.

String input = "x' OR '1'='1";   // the "name" the user typed

// DANGEROUS: the input is pasted into the SQL text
String sql = "SELECT name FROM people WHERE name = '"
           + input + "'";
System.out.println(sql);
ResultSet rs1 = stmt.executeQuery(sql);

// SAFE: the input is sent only as a value
PreparedStatement ps = conn.prepareStatement(
    "SELECT name FROM people WHERE name = ?");
ps.setString(1, input);
ResultSet rs2 = ps.executeQuery();

The first half of the code is the dangerous way and the second half is the safe way. With three people named Ali, Ayşe, and Can in the people table, the rows of the two result sets were counted:

The first line of the output is the SQL text that went to the database. The user typed x' OR '1'='1 in place of a name. In the concatenation, the first quotation mark in the input closes the quotation mark the program opened. The name value ends as 'x'. The OR '1'='1' that follows is no longer a value but part of the SQL. The quotation mark the program appended at the very end closes '1, and the text becomes syntactically perfect. The condition is name = 'x' OR '1'='1'; because '1'='1' is true in every row, the condition eliminates no row. Three rows come back.

On a login screen this means signing in without a password. Worse is possible too: the input could be a piece of SQL that deletes data or reads passwords from other tables. SQL injection has for years been among the most common security holes in web applications.

In the second half, the PreparedStatement returns 0 rows with the same input. Here the SQL text is fixed and the place of the input is marked with ?. The input is sent separately with setString(1, input) and used only as a value. The database looks for "the person whose name is exactly x' OR '1'='1". This 12-character text is nobody's name.

The last lines of the output show two more side results. When a text with an apostrophe, such as Ali's, is inserted by concatenation, the SQL breaks and the message near "s": syntax error is received. Even an ordinary user with no intent to attack can break the program. With PreparedStatement the same text is inserted and read back without trouble. Doubling the quote by hand ('') is another way, but it is error-prone; a single forgotten spot leaves the whole program vulnerable. The SQLite driver's executeQuery did not run a second statement appended with a semicolon (after the DROP TABLE attempt the table was still there). This does not count as protection: an attack that stays inside a single statement, like the one above, still works.

11.7.3Placeholders

Definition 11.11

A prepared statement (PreparedStatement) is an SQL statement that contains ? placeholders in place of values and takes the values separately. It is created with the connection's prepareStatement(sql) method; the placeholders are filled with setXxx(index, value) methods.

The following method inserts a person into the people table:

static void add(Connection conn, String name, String surname,
                 int age) throws SQLException {
  String sql = "INSERT INTO people(name, surname, age) "
             + "VALUES(?, ?, ?)";
  try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, name);      // 1st question mark
    ps.setString(2, surname);   // 2nd question mark
    ps.setInt(3, age);          // 3rd question mark
    ps.executeUpdate();
  }
}

There are three ? in the SQL text. The first argument of the setXxx methods is the index of the placeholder; the index starts at 1 and follows the left-to-right order in the SQL text (Figure 11.23). The method name says the Java type of the value: setString for text, setInt for an integer, setDouble for a floating-point number. After all placeholders are filled, executeUpdate() is called without parameters, because the SQL text was given when the statement was prepared.

PreparedStatement has three benefits. The first is security: it prevents SQL injection. The second is that there is no quoting problem: "Ali's" is saved without trouble. The third is reuse: the same statement is prepared once and run again and again with different values. The DBMS does not parse the statement anew each time; the difference is noticeable when thousands of inserts are made in a loop.

Placeholders can stand in only for values. A table or column name cannot be given with ?: preparing SELECT * FROM ? gave the message near "?": syntax error. A '?' inside quotes is not a placeholder but a question-mark character; in the query WHERE name = '?', a setString(1, …) call fails. A placeholder that is not filled counts as NULL. When the insert with three placeholders was run with only two values given, the message NOT NULL constraint failed: people.age was received. One more detail: a value that has been set stays in place until a new setXxx call. When, after an insert, only setString(1, "Bora") was changed and the statement was run again, the second row took the previous row's surname and age.

Common mistake

Starting the placeholder index at 0: ps.setInt(0, 5). The standard expects a SQLException in this case. The SQLite driver 3.40.0.0, however, threw an unchecked ArrayIndexOutOfBoundsException (Index -1 out of bounds for length 3). This exception is not caught by catch (SQLException e) and stops the program. The index always starts at 1 and does not exceed the number of ?.

11.7.4The people program

The insert method, together with methods for updating, deleting, and listing, makes up a small but complete program. The update and delete methods are as follows:

static void update(Connection conn, String name, String surname,
                   int age) throws SQLException {
  String sql = "UPDATE people SET surname = ?, age = ? "
             + "WHERE name = ?";
  try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, surname);
    ps.setInt(2, age);
    ps.setString(3, name);
    ps.executeUpdate();
  }
}

static void delete(Connection conn, String name) throws SQLException {
  String sql = "DELETE FROM people WHERE name = ?";
  try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, name);
    ps.executeUpdate();
  }
}

Each method takes the Connection as a parameter. The connection is opened once in main and used for many jobs. Opening a new connection for every operation is both slow and unnecessary. A PreparedStatement, on the other hand, is opened in each method's own try-with-resources block and closed when the method ends; the connection stays open.

In the update method, pay attention to the order of the ? marks. The SQL text is SET surname = ?, age = ? WHERE name = ?. Although the method's parameter order is (name, surname, age), in the SQL the name is the third placeholder. That is why setString(3, name) is written. The numbers follow the SQL text, not the Java parameters.

The methods pass errors to the caller with throws SQLException. Because main also declares throws SQLException, if an error occurs the program stops with a stack trace. For a small example program this is acceptable. In a real program the error is caught in main and the user is given an understandable message. The listing method is as follows:

static void list(Connection conn) throws SQLException {
  String sql = "SELECT id, name, surname, age FROM people";

          + " " + rs.getString("surname") + " " + rs.getInt("age"));

}

This query has no variable value; a plain Statement is enough. Since there is no user input, there is no injection risk either. Each call to list reads the table as it is at that moment and prints --- at the end. Finally, main calls the methods in order:

11.8.2From rows to objects: the DAO pattern

The programs so far scattered SQL and row reading throughout main. In an object-oriented program, each row is instead converted to an object, and the SQL is collected in one place. A simple class is enough for student rows:

class Student {
  private final int id;
  private final String name;
  Student(int id, String name) {
    this.id = id;
    this.name = name;
  }
  public String toString() {
    return "#" + id + " " + name;
  }
}

The fields of the Student class are final; the object does not change after it is created. toString writes the object in the form #1 Ada. This class knows nothing about the database: it contains neither SQL nor JDBC.

11.9Transactions

So far, each SQL statement has run on its own and become permanent immediately. Some jobs, however, consist of several statements that make sense only together. This section explains how to run such jobs safely.

11.9.1Transactions and ACID

Consider a money transfer: Ali sends 300 TL to Ece. The job is two UPDATE statements: 300 TL is added to Ece's account, and 300 TL is subtracted from Ali's. What happens if the power fails after the first statement has run, or if the second statement does not run because of an error? Ece's money has increased and Ali's has not decreased: money has appeared out of nothing. Had the order of the statements been reversed, money would have vanished. It is unacceptable for one of the two statements to happen and the other not.

Definition 11.13

A transaction is one or more SQL statements run as a single unit of work. Either all the statements of the transaction become permanent together, or none does. Making them permanent is called commit, and undoing them is called rollback.

In JDBC, the default setting of a connection is auto-commit: each statement is a transaction on its own and becomes permanent as soon as it runs. This setting was queried on a SQLite connection with conn.getAutoCommit() and came out true. The pattern for grouping several statements into one transaction is fixed. conn.setAutoCommit(false) starts a transaction, and then the statements run. If all goes well, conn.commit() makes the changes permanent; if an error occurs, conn.rollback() undoes them (Figure 11.27).

A reliable transaction has four properties, known by their initials as ACID.

  • Atomicity: either the whole transaction is applied or none of it. Only one of the transfer's two statements cannot become permanent.
  • Consistency: all constraints hold at the end of the transaction. If there is a CHECK (balance >= 0), no transaction can end by pushing a balance below zero.
  • Isolation: concurrent transactions do not see each other's half-done work. If another program reads Ece's balance while the transfer is under way, it sees either the value before the transfer or the value after it, never the one in between.
  • Durability: committed data is not lost even if the power fails right afterward. The DBMS completes the commit only after the change has been safely written to disk.

Isolation can be seen in an experiment. Two separate connections were opened to the same bank.db file. The first connection turned off auto-commit and raised Ece's balance from 500 to 800, without committing yet. Meanwhile, both connections read the same row:

a sees: 800
b sees: 500
after commit b sees: 800

The connection that made the change sees its own temporary value (800). The second connection does not see the uncommitted change and reads 500. After the commit, the second connection also sees 800.

11.9.2A money transfer

The transfer program has two parts. main sets up an in-memory database, inserts two accounts, and tries two transfers:

static final String DEPOSIT =
    "UPDATE accounts SET balance = balance + ? WHERE id = ?";
static final String WITHDRAW =
    "UPDATE accounts SET balance = balance - ? WHERE id = ?";

public static void main(String[] args) throws SQLException {
  String url = "jdbc:sqlite::memory:";  // in memory, temporary
  try (Connection conn = DriverManager.getConnection(url);
       Statement st = conn.createStatement()) {
    st.execute("CREATE TABLE accounts (id INTEGER PRIMARY KEY, "
        + "owner TEXT, balance INTEGER CHECK (balance >= 0))");
    st.execute("INSERT INTO accounts(owner, balance) "
        + "VALUES ('Ali', 1000), ('Ece', 500)");
    transfer(conn, 1, 2, 300);    // Ali → Ece 300 TL
    transfer(conn, 1, 2, 5000);   // Ali can't afford it
    printAll(conn);
  }
}

The balance column of the accounts table has the constraint CHECK (balance >= 0). Any statement that pushes a balance below zero throws a SQLException. In the second transfer, Ali's 700 TL is not enough for a 5000 TL transfer. The transfer method is as follows:

static void transfer(Connection conn, int from, int to,
                     int amount) throws SQLException {
  conn.setAutoCommit(false);         // transaction starts
  try (PreparedStatement p1 = conn.prepareStatement(DEPOSIT);
       PreparedStatement p2 = conn.prepareStatement(WITHDRAW)) {
    p1.setInt(1, amount);  p1.setInt(2, to);
    p1.executeUpdate();              // deposit to receiver
    p2.setInt(1, amount);  p2.setInt(2, from);
    p2.executeUpdate();              // withdraw from sender
    conn.commit();                   // make permanent
    System.out.println(amount + " TL transferred.");
  } catch (SQLException e) {
    conn.rollback();                 // undo
    System.out.println("Rolled back: " + amount + " TL");
  } finally {
    conn.setAutoCommit(true);
  }
}

The method first turns off auto-commit; the transaction begins. With two PreparedStatements it first deposits to the receiver and then withdraws from the sender. If both statements succeed, commit() makes both permanent together. If either statement throws a SQLException, control passes to catch, and rollback() undoes all the changes in the transaction. The finally block turns auto-commit back on no matter which path was taken; the connection returns to its default state for later users. The printAll method is a SELECT loop like list and prints each account's owner and balance. When run, the program gives this output:

300 TL transferred.
Rolled back: 5000 TL
Ali: 700
Ece: 800

Common mistake

11.9.4Batch processing

Writing 1000 values from a measuring device into a table takes 1000 INSERTs. These statements can be sent one by one, or collected in a queue and sent together.

Definition 11.14

A batch update collects many statements in a queue with addBatch() and sends them together with executeBatch(). executeBatch() returns the number of rows each statement affected, as an int[] array.

conn.setAutoCommit(false);
try (PreparedStatement ps = conn.prepareStatement(
        "INSERT INTO readings(value) VALUES(?)")) {
  for (int i = 1; i <= 1000; i++) {
    ps.setInt(1, i);
    ps.addBatch();
  }
  int[] result = ps.executeBatch();
  conn.commit();
  System.out.println(result.length + " statements, "
      + "the first affected " + result[0] + " row");
} catch (SQLException e) {
  conn.rollback();
  throw e;
} finally {
  conn.setAutoCommit(true);
}

In each round of the loop the placeholder is filled and addBatch() adds the filled statement to the queue. When the loop ends, the queue holds 1000 statements. executeBatch() sends them all and returns an array of 1000 elements; each element is 1, because each insert affected one row. The second line of the output was added as a check. The table has 1000 rows; the sum of the values is 1 + 2 + … + 1000 = 1000 · 1001 / 2 = 500,500.

At the end of each transaction, SQLite has the data written to disk to guarantee durability and waits for the write to finish. Three measurements were made with a .db file on disk (Table 11.24).

Even if the statements are sent one by one, they are as fast as batched sending when they are inside a single transaction. The reason is that SQLite runs inside the program; sending a statement is just a method call. On a server such as MySQL, each statement needs a network round trip, and addBatch also reduces the number of round trips.

Because the whole queue is a single transaction, if one statement fails, rollback() undoes the effect of the whole queue. To see this, the constraint CHECK (value <> 500) was added to the table and the same code was run:

SQLiteException: [SQLITE_CONSTRAINT_CHECK] A CHECK constraint failed (CHECK constraint failed: value <> 500)

The 500th statement was rejected, the catch block called rollback(), and the table stayed empty: all or nothing. After the rollback, the exception is rethrown with throw e;; the error is not silently swallowed, and the caller learns that the operation failed. The finally block turns auto-commit back on, on success and on failure alike. The standard specifies that a failure in a batch is reported with BatchUpdateException, a subclass of SQLException. The SQLite driver threw its own SQLiteException here. Because both are SQLExceptions, catch (SQLException e) catches both cases.

For very large loads, the queue is sent in pieces. For example, executeBatch is called after every 500 addBatch calls. This way a million statements do not pile up in memory, and memory does not balloon; the transaction can still end with a single commit.

Example 11.2

If the table had been defined with AUTOINCREMENT, Ece would have got 3.

Example 11.3

The people program is run a second time with people.db. What are the first block of the output (up to the first ---) and the last block?

The file is persistent. Ayşe (id 2) was left from the first run, and CREATE TABLE IF NOT EXISTS does not drop the table. The new records get numbers 3 (Ahmet) and 4 (Ayşe) by the largest-id-plus-1 rule. update makes Ahmet Akdeniz 35. First block: 2 Ayşe Demir 40, 3 Ahmet Akdeniz 35, 4 Ayşe Demir 40. delete deletes Ahmet. Last block: 2 Ayşe Demir 40, 4 Ayşe Demir 40. The same person is now recorded twice. The second run of the program really gave this output:

2 Ayşe Demir 40
3 Ahmet Akdeniz 35
4 Ayşe Demir 40
---
2 Ayşe Demir 40
4 Ayşe Demir 40
---

This result shows a design gap. If the same person should not be added twice, add a constraint such as UNIQUE(name, surname) to the table, or have the program check whether the person exists before inserting.

Example 11.4

A login screen is checked with the following code. The table has three people. If the user types ahmet as the name and ' OR '1'='1 as the password, what SQL is produced, how many rows come back, and does the login succeed?

String sql = "SELECT * FROM people WHERE name = '" + name
           + "' AND password = '" + password + "'";
ResultSet rs = stmt.executeQuery(sql);
boolean loggedIn = rs.next();

The concatenation produces this text: SELECT * FROM people WHERE name = 'ahmet' AND password = '' OR '1'='1'. In SQL, AND is applied before OR. The condition reads (name = 'ahmet' AND password = '') OR '1'='1'. The right side is true in every row; 3 rows come back. rs.next() returns true and the login succeeds without the password. The fix is to use a PreparedStatement with WHERE name = ? AND password = ?; with the same input, 0 rows come back. All three were verified by running them:

SELECT * FROM people WHERE name = 'ahmet' AND password = '' OR '1'='1'
login: true, rows: 3
PreparedStatement login: false
correct password: true
SELECT * FROM people WHERE name = 'ahmet' --' AND password = 'wrong'
login with comment: true

The last two lines of the output show another form of attack. If ahmet' -- is typed in the name field, -- starts an SQL comment and the password condition is never read; the login succeeds even with a wrong password. In real systems, passwords are not stored as plain text anyway but as hashes.

Example 11.5

If the lines setAutoCommit(false), commit(), and rollback() were removed from the transfer method, what would Ali's and Ece's balances be at the end of the program?

The first transfer succeeds in the same way: Ali 700, Ece 800. In the second transfer, the deposit becomes permanent immediately and Ece rises to 5800. The withdrawal fails because of the CHECK, and there is no transaction to roll back. The result: Ali 700, Ece 5800. 5000 TL has appeared out of nothing, and the program still prints "Rolled back". The program was run in this form to verify this.

The solutions to the four exercises in the slides were also tried with JDK 21 and the SQLite driver. The first exercise fixes the delete program so that it prints a message according to the return value of executeUpdate:

int n = stmt.executeUpdate(sql);
if (n > 0) System.out.println("Data deleted!");
else System.out.println("Record not found.");

When the program tried to delete the same row twice, it printed "Data deleted!" first and then "Record not found." In the second exercise, Ada (60, 70), Bora (30, 50), and Cem (80, 40) are inserted into the students(id, name, midterm, final) table in a loop with a PreparedStatement. Those whose average (midterm 40 percent, final 60 percent) is 50 or above are listed in descending order:

SELECT name, midterm * 0.4 + final * 0.6 AS avg FROM students
WHERE midterm * 0.4 + final * 0.6 >= 50 ORDER BY avg DESC

Ada's average is 60 · 0.4 + 70 · 0.6 = 24 + 42 = 66. Bora's is 12 + 30 = 42, and Cem's is 32 + 24 = 56. Bora is dropped; the output is Ada 66.0 and Cem 56.0. The value is read with getDouble("avg"). The expression is repeated in WHERE because in the logical order WHERE comes before SELECT, and the alias avg is not yet defined. ORDER BY, however, can use the alias. Because the coefficients are written as decimals such as 0.4, the result is REAL. An integer expression such as (midterm * 4 + final * 6) / 10, on the other hand, does integer division in SQLite and drops the fractional part.

The third exercise is a menu-driven program: 1-Add, 2-Update, 3-Delete, 4-List. The menu is built with Scanner and switch. Because nextInt() leaves the end of the line in the buffer, a nextLine() is called after it; otherwise the next name read returns an empty string. Update is done with UPDATE … WHERE id = ? and delete with DELETE … WHERE id = ?. If the number returned by executeUpdate is 0, there is no user with that id, and "User not found." is printed. The fourth exercise saves game scores in a scores(player, score) table with INSERT INTO scores(player, score) VALUES(?, ?). The top 10 scores are listed with SELECT player, score FROM scores ORDER BY score DESC LIMIT ? and ps.setInt(1, 10). The value of LIMIT can also be given with a placeholder; on a table with 12 scores, the query returned 10 rows in descending order.

11.12Summary

  • A database is a persistent, organized, queryable collection of data; a DBMS manages it. Compared with a file, it offers fast search, safe concurrent access, consistency through constraints, column-level permissions (in server DBMSs, for example GRANT in PostgreSQL or MySQL; in SQLite, access depends on file permissions), and recovery after a failure.
  • The relational model keeps data in tables: a column is an attribute and a row is a record; a primary key identifies each row uniquely. A table resembles a class, a column a field, and a row an object.
  • SQLite is an embedded, serverless, single-file relational database. To use it from Java, the driver jar must be on the classpath; the URL has the form jdbc:sqlite:sample.db.
  • The basic SQL statements cover the CRUD operations: INSERT, SELECT, UPDATE, DELETE. WHERE filters rows, ORDER BY sorts, and LIMIT limits. UPDATE and DELETE without WHERE affect all rows.
  • If no value is given for INTEGER PRIMARY KEY, SQLite assigns the largest id + 1; AUTOINCREMENT never hands out a number that has been used.
  • Normalization keeps each fact in one place and prevents update, insert, and delete anomalies. Tables are linked with foreign keys; in SQLite, checking is turned on with PRAGMA foreign_keys = ON.
  • JOIN … ON returns only matching rows, and LEFT JOIN returns all rows of the left table. If ON is forgotten, a Cartesian product results.
  • GROUP BY groups rows; WHERE filters rows before grouping, and HAVING filters groups after grouping. Logical order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT.
  • NULL is an unknown value; it is checked with IS NULL. getInt returns 0 for NULL; to tell the difference, call wasNull() right afterward.
  • An index turns a scan into a B-tree search; the cost is that the index must be updated on every write as well.
  • The JDBC chain: DriverManager → Connection → Statement/PreparedStatement → ResultSet. These are interfaces; the driver implements them.
  • execute returns a boolean and is used for table operations, executeUpdate returns the number of rows affected, and executeQuery returns a ResultSet. The result is read with while (rs.next()); column numbers start at 1.
  • User input is never concatenated into the SQL text; it is always passed with ? and setXxx. Otherwise SQL injection results.
  • A DAO collects a table's SQL in a single class and returns rows as objects.
  • Transaction: setAutoCommit(false), commit(), and on error rollback(); all or nothing (ACID). Bulk inserts are done in a single transaction.
  • Resources are opened with try-with-resources and closed in the order rs, stmt, conn. SQLException is a checked exception.

11.14Test Yourself

The questions use the chapter's three tables: students (Ada 1, Bora 2, Cem 1, Deniz NULL), depts (CS, EE, ME), and orders (Ali 120, Ece 80, Ali 50, Can 200, Ali 30, Ece 40). The answers were verified by running them with JDK 21 and SQLite JDBC.

  1. What does SELECT COUNT(*) FROM students WHERE dept_id <> 2 return?

    Answer

    2. Ada and Cem (1) satisfy the condition; Bora (2) does not. Deniz's dept_id is NULL, and NULL <> 2 is not true but unknown; Deniz is not counted.

  2. Three rows (1, 2, 3) are inserted into a table with the column id INTEGER PRIMARY KEY, the row with number 2 is deleted, and a new row is inserted. What are the numbers in the table?

    Answer

    1, 3, 4. The new row gets the largest id + 1 = 4. The gap in the middle is not filled; only if the largest number had been deleted would that number have been reused.

  3. What does SELECT customer, SUM(amount) FROM orders WHERE amount < 100 GROUP BY customer HAVING COUNT(*) >= 2 return?

    Answer

    WHERE first drops the orders of 120 and 200. Ali's 50 and 30 and Ece's 80 and 40 remain; Can has no orders left. Both groups have a count of 2. The result: Ali 80 and Ece 120.

  4. What does SELECT COUNT(*) FROM depts d LEFT JOIN students s ON s.dept_id = d.id return? What if LEFT is removed?

    Answer

    CS matches two students and EE one; ME matches none, but LEFT JOIN keeps it with one row: 4. With a plain JOIN, ME drops out: 3. Deniz is in neither query, because the preserved side is the departments.

  5. A name search is done with "SELECT name FROM people WHERE name = '" + input + "'". If the user types ' OR 1=1 --, how many rows come back on a table of three people?

    Answer

    The SQL text becomes SELECT name FROM people WHERE name = '' OR 1=1 --'. -- turns the final quotation mark into a comment; the condition is true in every row. 3 rows come back. With a PreparedStatement, 0 rows would come back.

  6. The supplies table has stapler 40, scissors 10, and tape 25. The statements INSERT … ('pen', 5), UPDATE supplies SET stock = stock + 10 WHERE stock < 20, and DELETE FROM supplies WHERE stock > 100 are added to a Statement in that order with addBatch, and then executeBatch() is called. What is the returned array?

    Answer

    [1, 2, 0]. The insert affects one row. In the update, the rows with stock below 20 are scissors (10) and the newly inserted pen (5); they become 20 and 15. There is no row to delete. The addBatch(String) form of Statement can also queue different SQL texts.

  7. The students table is read in id order; for each row, total += rs.getInt("dept_id") is executed, and none++ if rs.wasNull() is true. At the end, what are total and none?

    Answer

    getInt gives 0 for Deniz: 1 + 2 + 1 + 0 = 4. wasNull() is true only for Deniz: none = 1.

  8. The table members(id INTEGER PRIMARY KEY, email TEXT UNIQUE) is empty. setAutoCommit(false) is called, a@x and b@x are inserted, then rollback(), then c@x is inserted, then commit(). Which rows are in the table?

    Answer

    A single row: (1, c@x). rollback() undoes the first two inserts; undone inserts do not use up numbers either. c@x is inserted into the empty table and gets 1.
