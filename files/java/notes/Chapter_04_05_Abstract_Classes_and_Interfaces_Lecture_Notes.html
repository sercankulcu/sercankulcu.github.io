Chapter 4.5: Abstract Classes and Interfaces

Inheritance gathers shared code in the superclass, and polymorphism makes the same call run the method of each object's own class. These two tools leave one gap: a superclass sometimes cannot write the body of a method. The area of a general “shape” cannot be computed; only a square, a circle or a triangle knows the formula. Java offers two tools for this situation: the abstract class and the interface. Both say “what to do” and leave “how to do it” to the subtypes. These notes first cover the abstract class and the abstract method, then the interface, the methods with bodies in interfaces, and sealed types. Lambda expressions, the short notation for interfaces with a single method, generic classes with type parameters, and annotations that add metadata to code are among the topics too. The last section explains five design patterns, most of them built on interfaces (Singleton, Factory, Observer, Strategy and MVC), with small console programs. All programs were compiled and run with JDK 21; the outputs, the final values in the trace tables and the compiler messages come from these runs.

4.5.1Abstraction

Someone who drives a car knows the steering wheel, the gear stick and the pedals. They do not have to know how the fuel burns inside the engine or how the gearbox changes its gears. The face the car presents to the driver is simple; the complex detail stays behind that face. Moreover, the same face is the same on different cars. Someone who can drive a gasoline car can drive an electric car too, because both obey the contract of steering wheel and pedals.

Definition 4.5.1

Abstraction is hiding complex details and showing only the essential features. In programming, abstraction separates “what” a job does from “how” it does it.

The same separation is useful in a program. Suppose a drawing program wants to compute the total area of the shapes on the screen. Every shape has an area; this is the essential property of the concept “shape”. But the area of a general shape cannot be computed. The formula is a · a for a square, π · r² for a circle, b · h / 2 for a triangle. Only the concrete shape knows the formula. Figure 4.5.1 draws this situation: the common concept is at the top, the detail at the bottom.

The code that computes the total area should rely only on the knowledge that “every shape has an area() method”. It does not ask whether a shape is a square or a circle; it asks each shape for its area. If a hexagon is added to the program tomorrow, the summing code does not change; only the new class is written. This is the gain of abstraction: the code that uses a type depends on the concept, not on the detail.

Java has two tools for abstraction: abstract classes (abstract class) and interfaces (interface). Both say what is to be done and leave how to do it to the subclasses. The difference between them in brief is this. An abstract class is the common ancestor of closely related classes; it can have fields, a constructor and ready-made methods. An interface is a contract that gives a common ability to classes that are not related to each other.

4.5.2Abstract classes

In inheritance, the superclass carries the shared fields and methods of the subclasses. Class Shape can write the shared name field and the move method of all shapes. It gets stuck at the area() method. What should the body be? Writing return 0; is wrong. No shape's area is really 0. If a subclass forgets to override the method, the program silently produces a wrong result. The right solution is not to write the body at all and to tell the compiler so explicitly.

4.5.2.1Defining an abstract class

Definition 4.5.2

An abstract class is a class declared with the abstract keyword from which no object can be created. An abstract class can contain both abstract methods (without a body) and concrete methods (with a body). A subclass that writes all the abstract methods is called a concrete class; objects can be created only from such a class.

public abstract class Shape {
    // concrete (non-abstract) method
    void move(int x, int y) {
        System.out.println("Moved to (" + x + ", " + y + ")");
    }
    // abstract method (subclasses must implement)
    abstract void draw();
}

This Shape class has two methods. move is concrete: its body is ready. Subclasses inherit it as it is, or override it if they wish. Since moving a shape to a point requires the same work for every shape, writing the body once in the superclass is right. draw is abstract: it has only a signature. Drawing a square and drawing a circle are different jobs; so every concrete subclass must write its own draw() body.

An abstract class is like an unfinished plan. Some rooms are finished, for others only the place is fixed. The architect who takes over the plan fills the empty places without touching the finished rooms. The small program below completes the class with a Square and calls both methods:

abstract class Shape {
    // concrete (non-abstract) method
    void move(int x, int y) {
        System.out.println("Moved to (" + x + ", " + y + ")");
    }
    // abstract method (subclasses must implement)
    abstract void draw();
}
class Square extends Shape {
    void draw() { System.out.println("Drawing a square"); }
}
public class D03 {
    public static void main(String[] args) {
        Shape s = new Square();
        s.move(3, 4);
        s.draw();
    }
}

Square has written only draw(); it gets move from Shape. The type of the variable is the abstract Shape, but the object it points to is a Square. In the call s.draw(), which body runs is chosen at run time by the class of the object, as in polymorphism. This decision is called dynamic binding.

The other properties of an abstract class are the same as those of an ordinary class. It can have fields, constructors and static members. Other classes extend it with extends. Figure 4.5.2 draws a Shape class with four methods and the three concrete classes that extend it. The drawing is in UML (Unified Modeling Language) notation.

The gain of the design in the figure is that the shared state (the fields) and behavior are gathered in a single place. The name field and the getName() that reads it are not written separately in three classes. The subclasses fill in the abstract methods according to their needs. That is why abstract classes often sit at the top of an inheritance hierarchy.

4.5.2.2No object can be created from an abstract class

The most striking rule about an abstract class is that no object can be created from it with new. Of the three lines below, the first does not compile and the other two do:

Shape s1 = new Shape("?");     // ERROR
Shape s2 = new Square(3);        // OK: the variable type may be abstract
Shape[] arr = new Shape[3];   // OK: the array holds only references
AbstractNew.java:8: error: Shape is abstract; cannot be instantiated
        Shape s1 = new Shape("?");
                   ^
1 error

The ban is not arbitrary. The area() method of Shape has no body. If new Shape("?") were allowed, there would be no code to run in the call s1.area(). The compiler prevents this up front: an object with a missing body is never created.

The name of an abstract class, however, can be used freely as a reference type. A variable, a parameter, an array element and a return type can be Shape. The Shape s2 = new Square(3); on the second line is exactly the notation abstraction wants: the type of the variable is the concept, the class of the object is the detail. The third line often surprises students. new Shape[3] does not create a Shape object; it creates an array with three slots, and each slot starts as null. The array object holds references, not objects of the abstract class. This is clearly seen when the lines are run:

abstract class Shape {
    private String name;
    Shape(String name) { this.name = name; }
    abstract double area();
}
class Square extends Shape {
    private double side;
    Square(double side) { super("Square"); this.side = side; }
    double area() { return side * side; }
}
public class D05 {
    public static void main(String[] args) {
        Shape s2 = new Square(3);        // OK: the variable type may be abstract

        System.out.println(arr.length + " " + arr[0]);

4.5.2.3Abstract methods and their rules

Definition 4.5.3

An abstract method is a method defined without a body, with only its signature. It contains no braces and ends with a semicolon. Every concrete subclass must implement it, that is, write its body.

public abstract void draw();

A class that has an abstract method must itself be abstract. In the two files below, Shape declares the abstract method draw() and Circle implements it:

public abstract class Shape {
    // abstract method
    public abstract void draw();
}

// in a separate file:
public class Circle extends Shape {
    // must implement draw
    public void draw() {
        System.out.println("Drawing a circle");
    }
}
Drawing a circle

The call new Circle().draw(); runs the body that Circle wrote. Implementing an abstract method follows the same rules as overriding an ordinary method. The signature (name and parameter list) must be exactly the same, and access must not be narrowed. Since the method in the superclass is public, the one in Circle is public too.

Common mistake

Writing the signature of an abstract method wrongly. If the abstract method in Shape is double area() and the subclass writes double Area() or double area(int x), it is a new method. The abstract area() is still missing and the compiler rejects the class:

The message shows not the place of the mistake but its consequence; the typo may go unnoticed. If @Override is written above the method, the compiler states the real error directly: method does not override or implement a method from a supertype.

4.5.2.4The constructor of an abstract class

If no object can be created from an abstract class, what is its constructor for? The answer lies in how a subclass object is built. When a Square object is created, the part of the object that comes from Shape must be built too: the name field must be given a value. The constructor of Shape does this job and the subclass calls it with super(...). In the program below the Shape constructor also prints a message, so the output shows when the call is made.

abstract class Shape {
    private String name;
    Shape(String name) {
        this.name = name;
        System.out.println(name + " created");
    }
    abstract double area();
}
class Square extends Shape {
    private double side;
    Square(double side) {
        super("Square");
        this.side = side;
    }
    double area() { return side * side; }
}
// in main:
Shape s = new Square(3);
System.out.println(s.area());

In the first step, new Square(3) reserves space for a Square object on the heap. The object has two fields: name from Shape and side, which belongs to Square. Both get their default values: null and 0.0. In the second step the constructor of Square starts to run. The argument is the int 3 and the parameter is a double; the value is widened automatically to 3.0.

In the third step the first line of the Square constructor, super("Square"), runs and the superclass constructor is called. In the fourth step a Shape("Square") frame is added to the stack. There is a very important detail here: a separate Shape object is not created. There is still a single object on the heap. The Shape constructor builds the part of the same object that comes from Shape. In the fifth step this.name = name sets the field of this part to "Square", in the sixth step the message is printed and the frame of Shape leaves the stack.

In the seventh step control returns to the constructor of Square and this.side = side runs. The object is now completely built. In the eighth step the reference that is the value of the new expression is assigned to s. The type of the variable is the abstract Shape, and the object it points to is a Square. The drawing on the right of Figure 4.5.3 shows this moment.

The ninth step does the real work of abstraction. When s.area() is compiled, the compiler looks only at Shape: Shape has a method called area() that returns double, so the call is valid. At run time the JVM looks at the actual class of the object and runs Square.area(): 3.0 · 3.0 = 9.0. In the tenth step this value is printed.

The order of the constructor chain is the same as in inheritance: first the superclass constructor, then the subclass's. The abstract class does not change this order; it only forbids creating an object directly from the top link of the chain. Since Shape has no no-argument constructor, the constructor of Square must write super("Square"). Had it not, the compiler would insert super() itself and report an error because it cannot find the no-argument constructor.

4.5.2.5The template method

A concrete method of an abstract class can call an abstract method of the same class. At first hearing this seems contradictory: how can a method without a body be called? The call compiles, because the signature of the method is known. At run time this always points to an object of a concrete subclass, and in that object's class the method has a body. The Beverage class below fixes the order in which a beverage is prepared:

abstract class Beverage {
    final void prepare() {
        boilWater();
        brew();
        System.out.println("Served");
    }
    void boilWater() {
        System.out.println("Water boiled");
    }
    abstract void brew();
}
class Tea extends Beverage {
    void brew() {
        System.out.println("Tea brewed");
    }
}
// in main:

Brewing differs by beverage; brew() is abstract and Tea fills it in with its own body. prepare() is final: subclasses cannot override it, that is, they cannot disturb the order of preparation.

Definition 4.5.4

The template method is a design that defines the skeleton of an algorithm in the superclass and leaves the varying steps to the subclasses. The method that builds the skeleton is usually final; the varying steps are abstract methods.

The strength of the template method shows when a new beverage is added. A Coffee class writes only brew(); it takes the water-boiling and serving steps, together with their order, ready-made:

Trying to override a final template method in a subclass. The template method is written final to protect the skeleton. If a subclass wants to rewrite it, the compiler rejects it:

4.5.3Interfaces

An abstract class works well as the common ancestor of related classes. A square and a circle are both shapes. But some things in common do not come from kinship. A bird, an airplane and a drone can fly; the three have no common ancestor, and should not have one. A duck both flies and swims; since it has a single superclass, it cannot derive from two separate abstract classes at the same time. Java offers a second tool of abstraction for this need: the interface.

4.5.3.1An interface is a contract

Definition 4.5.5

An interface is a type that specifies the methods classes must implement. It is defined with the interface keyword. A class implements an interface with implements, that is, it writes the bodies of the abstract methods in the interface.

An interface is a contract. It guarantees that every class implementing it will offer certain methods. It is the meeting point between two pieces of software: the using side knows only the interface and does not know the class behind the contract. Figure 4.5.5 draws this relationship.

An everyday analogy describes the interface well: the socket and the plug. The socket is a contract. Whatever device is plugged in, it gives the same voltage. Both an iron and a computer obey the standard of the socket. The grid does not know the inside of the device, and the device does not know how the grid is built. Making a new device does not require changing the grid; following the standard is enough.

The rules of an interface differ from those of a class:

  • Methods in an interface are public, whether or not public is written.
  • A method that is not static, default or private is abstract by itself.
  • Only public static final constants can be fields. There are no instance fields and no constructors.

The difference between an abstract class and an interface can be summed up with two relationship names. An abstract class establishes an “is-a” relationship: a square is a shape. An interface defines a “can-do” ability: a duck can fly, a duck can swim.

4.5.3.2Defining an interface

Below, first comes the interface the programmer wrote, then how the compiler sees it. The compiler adds the modifiers that were not written:

public interface GeometricShape {
    // abstract method (public abstract)
    void draw();
    // constant (public static final)
    int SIDES = 4;
}
public interface GeometricShape {
    public abstract void draw();
    public static final int SIDES = 4;
}

The line void draw(); is read as public abstract void draw();. The line int SIDES = 4; is a public static final constant. Constants are reached with the interface name: GeometricShape.SIDES gives 4. Constant names are traditionally written in UPPER_CASE. These implicit modifiers have three consequences, and the compiler checks all three.

First, giving a value to a constant in an interface is mandatory. A final field without a value cannot get one later either, because an interface has no constructor:

interface GeometricShape {
    int value;
}
public class FinalNoValue { }

4.5.3.4One class, several interfaces

4.5.4Lambda expressions

Most interfaces like PaymentMethod have a single abstract method. To implement such an interface one has to write a separate class, give it a name and place the body inside that class. If the class will be used only once, in one place, this ceremony is needlessly long. Lambda expressions, which came with Java 8, let you write a one-method behavior directly where it will be used.

4.5.4.1An anonymous function and its syntax

Definition 4.5.6

A lambda expression is an anonymous function made of a parameter list, an arrow (->) and a body: (ParameterList) -> Expression. An anonymous function represents the code itself directly, instead of a name.

The expression (int x, int y) -> x + y in Figure 4.5.10 takes two integers and returns their sum. The ordinary method that does the same job is:

static int add(int x, int y) {
    return x + y;
}

The differences between the two notations explain the short form of the lambda. A lambda has no name; the return type is not written, it is inferred from the type of the expression; in a single-expression body neither return nor braces are written. The syntax has a few forms:

  • Parameter types are often not written; the compiler infers them from the context: (x, y) -> x + y.
  • With a single parameter the parentheses are not needed either: s -> s * 2.
  • A lambda with no parameters is written with empty parentheses: () -> 4.
  • If the body consists of several statements, braces and return are needed: (a, b) -> { int s = a + b; return s; }.

The program below tries all of these forms with the same sum. Each lambda is assigned to a variable of an interface type. The type of a lambda is always such an interface.

import java.util.function.IntBinaryOperator;
public class Main {
    static int add(int x, int y) {
        return x + y;
    }
    public static void main(String[] args) {
        IntBinaryOperator t1 = (int x, int y) -> x + y;
        IntBinaryOperator t2 = (x, y) -> x + y;
        IntBinaryOperator t3 = (a, b) -> { int s = a + b; return s; };
        java.util.function.IntUnaryOperator twice = s -> s * 2;
        System.out.println(add(5, 3) + " " + t1.applyAsInt(5, 3) + " " + t2.applyAsInt(5, 3) + " "
                + t3.applyAsInt(5, 3) + " " + twice.applyAsInt(21));
    }
}
8 8 8 8 42

All four sums give 8; the one-parameter lambda twice doubles 21 to 42. The behavior is the same even though the notation changes.

4.5.4.2The functional interface

In Java every value has a type. What is the type of a lambda expression? Java answers this question without adding a new kind of type: a lambda is an object of an interface that has a single abstract method.

Definition 4.5.7

A functional interface is an interface with a single abstract method. A lambda expression can be assigned only to such a type. The lambda writes the body of that one method; the parameter and return types are inferred from the signature of the method.

@FunctionalInterface
interface Greeting {
    void greet(String name);
}

Greeting s = name -> System.out.println("Hello " + name);
s.greet("Ayşe");
Hello Ayşe

The only abstract method of the Greeting interface is greet(String name). The lambda name -> System.out.println("Hello " + name) is the body of this method. The compiler infers the type of name as String from the method's parameter. The return type is void; the println call produces no value either. Figure 4.5.11 shows the match.

The @FunctionalInterface annotation is optional. If written, the compiler checks that the interface really is functional and does not allow a second abstract method to be added. Even without the annotation, every interface with a single abstract method can be a target for a lambda. The annotation is a safeguard against the programmer who changes the interface later. If someone accidentally adds a second method, all lambdas that use the interface break. The annotation catches this mistake in the interface itself.

The most important rule about lambdas is when they run. A lambda does not run when it is defined. The definition only creates an interface object and assigns it to the variable. The body runs when the method of the interface is called, that is on the line s.greet(...). To see this, let us add numbered messages to the program:

@FunctionalInterface
interface Greeting {
    void greet(String name);
}
public class Main {

        Greeting s = name -> System.out.println("3: Hello " + name);
        System.out.println("2: not called yet");
        s.greet("Ayşe");
        s.greet("Ali");

4.5.4.5Filtering and transforming with streams

The place where lambdas are used most is processing collections. The stream interface that came with Java 8 lets you pass a list through a series of operations, and each operation takes a lambda. The code below runs inside a main with import java.util.*;, java.util.function.IntBinaryOperator and java.util.stream.Collectors imported:

The first two lines assign the sum lambda to the type IntBinaryOperator and call it with applyAsInt(5, 3): 8. The brevity of the lambda has a price; three limits must be known. First, a lambda can be assigned only to a functional interface type. An anonymous class can also implement an interface with several methods or extend a class.

Second, the local variables a lambda uses must be final or effectively final. Effectively final means a variable not written final but never assigned a value after its initial value. The lambda below reads the local variable tax and adds 20% VAT to a price of 150 TL: 150 + 150 · 20 / 100 = 180.

The reason for the rule is that a lambda can run later. A lambda can be called long after the method where it was defined, even after that method has ended. So it carries not the local variable itself but a copy of its value. Had the variable changed later, the value the lambda sees and the value the method sees would diverge. Java forbids this ambiguity up front. Fields do not fall under this rule; a lambda can read and change a field. This is why the counter in the counter example was written as a static field.

Third, the keyword this means something different. The this inside a lambda refers to the enclosing object, that is the object of the method that wrote the lambda. The this in an anonymous class refers to the anonymous object itself:

4.5.4.7Uses

Lambda expressions shorten code markedly in three kinds of work:

  • Collection operations. Filtering, sorting, mapping a list and doing something for each element (filter, sort, map, forEach).
  • Thread management. Giving briefly the body of a job to be run in parallel.
  • Readable code. Instead of defining a separate method or class for a small operation used in one place, writing the operation where it is used.
List<String> names = new ArrayList<>(List.of("Zeynep", "Ali", "Mehmet"));

The call names.sort(...) takes the sorting criterion as a lambda. (a, b) -> a.length() - b.length() returns the difference in length of two names. If the difference is negative, a comes first; if positive, b comes first; if zero, the two count as equal. “Ali” goes first because it has three letters. “Zeynep” and “Mehmet” have six letters each; Java's list sort keeps the original order of equal elements, so “Zeynep” stays before “Mehmet”. Such a sort is called a stable sort.

forEach calls the given lambda for every element of the list and prints three greetings. The last two lines create a thread. The constructor of Thread expects a Runnable; () -> ... is a lambda with no parameters and becomes the body of run(). t.start() starts this body in a separate thread. The line t.join() was added to the program that was run; it makes main wait for the thread to finish. In this program the last message is printed last anyway, because there is no other work before it.

Changing the sorting criterion means only changing the lambda. The program below sorts the same list by three criteria. Comparator.comparing(String::length) is the ready-made way of saying “by length”; the notation String::length is a shorthand (a method reference) for the lambda s -> s.length(), which only calls one method.

import java.util.*;
public class Main {
    public static void main(String[] args) {
        List<String> names = new ArrayList<>(List.of("Zeynep", "Ali", "Mehmet"));
        names.sort(Comparator.comparing(String::length));
        System.out.println(names);
        names.sort((a, b) -> b.length() - a.length());
        System.out.println(names);
        names.sort(Comparator.comparing(String::length).thenComparing(Comparator.naturalOrder()));
        System.out.println(names);
    }
}

[Ali, Mehmet, Zeynep]

The first line sorts from short to long, the second from long to short; in the second too, elements of equal length keep their original order. The third line looks at alphabetical order when lengths are equal and puts “Mehmet” before “Zeynep”.

4.5.5Methods with bodies in interfaces

Until Java 8 an interface could contain only abstract methods and constants. This rigidity caused a big problem. New methods that work with lambdas (forEach, removeIf, stream) were to be added to Java's own Collection and List interfaces. Adding a new abstract method to an interface breaks all classes that implement it: every list class in the world would suddenly stop compiling. The solution was to allow methods with bodies in interfaces. Today an interface can contain three kinds of method with a body: default (default), static and private.

4.5.5.1Default methods

Definition 4.5.8

A default method is a method written in an interface with the default keyword and a body (Java 8+). A class implementing the interface inherits it ready-made; it overrides it if it wishes.

The Collection interface below has three abstract methods and one default method. This Collection is a small interface we wrote ourselves; it should not be confused with java.util.Collection.

interface Collection {

    void remove(Object o);

4.5.6Sealed types

When a class or interface is written, by default anyone can extend or implement it. This openness is often useful, but sometimes it does not reflect the truth of the design. A traffic light can only be red, yellow or green; a payment can only be by card, transfer or cash. In such a hierarchy, adding a new subtype unnoticed leaves all the code that handles it incomplete. Sealing, which came with Java 17, makes it possible to close the list of subtypes.

Definition 4.5.9

A sealed class or interface is a type declared with the sealed keyword (Java 17+). Only the subtypes named in its permits list can extend or implement this type.

Every permitted subtype must choose how the hierarchy continues after it. There are three options:

  • final: the hierarchy ends here; no class can be derived from this type.
  • sealed: the type is restricted again; it gives its own permits list.
  • non-sealed: the restriction is lifted; anyone can extend this type.

The real benefit of sealing is that the compiler knows all the subtypes. Such a hierarchy is called a closed hierarchy. In the example below the Animal interface permits only Cat and Dog:

public sealed interface Animal permits Cat, Dog {
    void move();
}
final class Cat implements Animal {
    public void move() {
        System.out.println("Cat walks silently");
    }
}
non-sealed class Dog implements Animal {
    public void move() {
        System.out.println("Dog runs");
    }
}
class Kangal extends Dog {   // open
    public void move() {
        System.out.println("Kangal guards the flock");
    }
}

Since Cat is final, that branch of the hierarchy is closed. Dog is non-sealed; so Kangal extends Dog without any permission (Figure 4.5.16). Kangal is indirectly an Animal, but not a direct subtype of Animal; so it need not be in the permits list.

What a sealed type gives the compiler shows when it is used with switch. In Java 21 a switch can branch on the type of an object, and the compiler checks whether all subtypes are handled:

An abstract class is appropriate when:

  • The subclasses are close relatives: Square and Circle are both a Shape.
  • Common fields and a constructor are needed (like name).
  • Part of the common code is ready-made (like a template method).

An interface is appropriate when:

  • The same ability is to be given to unrelated classes: Bird, Airplane and Drone are all Flyable.
  • Several abilities are to be given to one class.
  • A contract is to be established between the using code and the implementing code. Such a contract is called an API (application programming interface).

Often the two are used together:

abstract class Animal implements Noisy { … }
class Duck extends Animal implements Flyable, Swimmable { … }

In this notation the abstract class Animal carries kinship and common state; the interfaces Noisy, Flyable and Swimmable add abilities. A Duck is an Animal, and can both fly and swim.

The reason Java does not allow multiple inheritance of classes is that, when two superclasses define the same field or method differently, it becomes unclear which one applies. This problem is called the diamond problem because of the shape of the drawing in which two superclasses come from a common ancestor. Since interfaces carry no state, most of the problem disappears. The only remaining ambiguity is the conflict of two default methods, and the compiler makes the class resolve that too.

4.5.8Generics

Interfaces and abstract classes let code work with different classes. Generics take the same idea one step further: they let a class or a method work with different types, without losing type safety. The angle brackets in List<String> and Function<String, Integer> are the syntax of generics.

4.5.8.1Why generics?

Suppose we want to write a box class that can store a value of any type. Without generics, the only way that comes to mind is to use Object, the superclass of everything:

class ObjBox {
    private Object content;
    void put(Object o) { content = o; }
    Object get() { return content; }
}
ObjBox k = new ObjBox();
k.put("Hello");
String s = (String) k.get(); // cast required
k.put(42);                  // no complaint
String t = (String) k.get(); // runtime error
Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')
	at Main.main(Main.java:12)

This design has two flaws. First, reading a value from the box needs an explicit cast every time: (String) k.get(). The compiler does not know what is inside the box; it trusts the programmer's word. Second, when a value of the wrong type is put in, nobody objects. k.put(42) compiles, because 42 is boxed into an Integer object and every object is an Object. The error shows only while the program runs, on the line that tries to cast 42 to String: ClassCastException. The place where the mistake was made is far from the place where it is noticed.

    private T content;
    void put(T x) { content = x; }
    T get() { return content; }
}

In the generic version the type of the box is a parameter: Box<T>. When Box<String> is written, String takes the place of T. put now accepts only String and get returns String. No cast is needed when reading. The wrong-typed k.put(42) is rejected at compile time, before the program runs.

The two gains of generics can be summed up this way. Type safety: a value of the wrong type is caught at compile time, not at run time. Reuse: a single implementation works for every type and no explicit cast is needed when reading.

About a plain T the compiler knows nothing; on a value of type T only the methods of Object can be called. If we want to write a generic method that computes twice a number, we have to say that T is a number.

Definition 4.5.11

Definition 4.5.12

Invariance: even if A is a subtype of B, List<A> is not a subtype of List<B>. Generic types do not automatically inherit the subtype relationship between their type arguments.

The reason for the rule is writing. If a List<Integer> could be assigned to a List<Number> variable, 2.5 could be added to the list through that variable, because 2.5 is a Number. But the list is really a list of integers and a Double would have got into it. Code that reads from the list and expects Integer would crash at run time. Java closes this door at compile time (Figure 4.5.18).

Invariance is safe but reduces flexibility. If a method that sums the values in a list of numbers takes a List<Number> parameter, a List<Integer> cannot be given to it. Wildcards solve this problem:

  • ?: any unknown type.
  • ? extends T: T or a subtype of it. Such a list produces values; it is read as T.
  • ? super T: T or a supertype of it. Such a list consumes values; T is written into it.
static double sum(List<? extends Number> list) {
    double t = 0;
    for (Number n : list) t += n.doubleValue();  // read
    return t;
}
static void fill(List<? super Integer> list) {
    list.add(1);                                 // write
    list.add(2);
}
// in main:

Whatever list arrives can take an Integer. 1 and 2 are added to the List<Number> given to it; the program itself adds 2.5 and the list becomes [1, 2, 2.5]. 4.5.10Design patterns

Interfaces, abstract classes and lambdas are language tools. How to put these tools together for a given problem is a separate kind of knowledge. Experienced programmers have met the same design problems again and again and have given names to the solutions that work. All five patterns below are explained with small console programs; three of them rely directly on an interface.

4.5.10.1What is a pattern?

Definition 4.5.16

A design pattern is a tried and reusable solution template for a frequently met design problem. A pattern is not ready-made code to be copied; it is a shared vocabulary that names the problem, the solution and the trade-offs of the solution.

The common aim of patterns is to separate responsibilities and reduce dependencies between classes. A part with few dependencies can be changed without touching the others and can be tested on its own. Patterns are traditionally divided into three groups (Figure 4.5.20). Creational patterns deal with how objects are created, structural patterns with how objects are combined. Behavioral patterns arrange the cooperation of objects.

A pattern is useful only if it solves a real problem. A pattern added needlessly complicates the program. Patterns are concrete applications of more general design principles such as “few dependencies between components” and “composition over inheritance”. Composition means a class, instead of inheriting behavior, holding another object as a field and having it do the work.

4.5.10.2Singleton

Some classes should have a single object in the program. If the settings of the application, a log file or a hardware driver are kept in two copies, the copies may drift apart. The Singleton pattern ensures that the class has only one object and that this object is reached from a single place.

public final class Settings {
  private static final Settings INSTANCE = new Settings();
  private Settings() {
    System.out.println("Settings created");
  }
  public static Settings getInstance() { return INSTANCE; }
}
// main:
System.out.println("main started");

Second, the single object is kept in a private static final field inside the class. Third, this object is reached through a public static method (getInstance()). Since both calls return the same object, a == b gives true.

The order of the output is instructive too: the message “main started” is printed before “Settings created”. The JVM initializes the INSTANCE field once, when the class Settings is first used, that is at the first getInstance() call. Since the JVM does class initialization only once, this method is safe with several threads too.

The Singleton pattern has a serious drawback: it behaves like a hidden global variable. Every class that calls Settings.getInstance() from inside becomes invisibly tied to that single object. When testing these classes it becomes hard to put another object in place of the real settings. Often a better way is to pass the object as a parameter to the constructor of the class that needs it. Giving a dependency from outside is called dependency injection.

4.5.10.3Factory

Suppose a drawing program creates the shape the user chooses from a menu. The choice arrives as a string: “square”, “circle” … Deciding which class to create with an if chain everywhere scatters the creation code over the program. The Factory pattern gathers object creation in one place.

interface Shape { double area(); }
class Square implements Shape { … }   // area: a * a
class Circle implements Shape { … }  // area: π r²

class ShapeFactory {
  static Shape create(String kind, double size) {
    switch (kind.toLowerCase(Locale.ROOT)) {
      case "square":  return new Square(size);
      case "circle": return new Circle(size);
      default:      return null;  // unknown kind
    }
  }
}
Shape s = ShapeFactory.create("Square", 3);
System.out.println(s.area());   // 9.0
Definition 4.5.17

A factory method is a method that produces an object and returns it as a superclass or interface type. The calling code does not know which concrete class was created.

The method ShapeFactory.create takes the kind and the size, creates the suitable object and returns it as the interface type Shape. The calling code knows not Square but only Shape. The class bodies abbreviated with … in the code are completed in the program that was run:

4.5.10.4Observer

A weather station measures the temperature. When a new measurement arrives, a display should show it, an alert module should warn when the temperature exceeds 30 degrees, and a logger should store the measurement. If the station calls these three parts directly, every new part changes the code of the station. The Observer pattern reverses this dependency.

Definition 4.5.18

The observer pattern establishes a one-to-many relationship between a subject object and the observers registered with it. When the state of the subject changes, all registered observers are notified. The subject does not know the concrete class of the observers; it only calls the common interface.

interface Observer { void update(int degrees); }

class Station {
  private final List<Observer> list = new ArrayList<>();
  void add(Observer g) { list.add(g); }
  void setTemp(int d) {
    for (Observer g : list) g.update(d);
  }
}

Observer is an interface with a single method. Station keeps the observers in a list. add registers a new observer, and setTemp walks through the list and calls the update method of every observer. 4.5.10.5Strategy

The checkout of a store computes the amount to pay. A 10% discount is applied to students, and in the campaign period 50 TL is deducted above 200 TL; tomorrow another rule may come. If the checkout knows these rules itself with an if chain, every new rule changes the code of the checkout.

Definition 4.5.19

The strategy pattern puts interchangeable algorithms behind a common interface. The object that uses the algorithm delegates the job to the strategy object given to it; when the strategy changes, its behavior changes without its code changing.

interface Discount { double apply(double amount); }

class StudentDiscount implements Discount {
  public double apply(double amount) { return amount * 0.90; }
}
class Checkout {
  private final Discount strategy;
  Checkout(Discount strategy) { this.strategy = strategy; }
  double due(double amount) {
    return strategy.apply(amount);
  }
}
Checkout k = new Checkout(new StudentDiscount());

4.5.10.6MVC

In programs that interact with the user, three different jobs tend to get mixed up: the data itself and its rules, showing the data on the screen, and reacting to the user's input. Putting these three jobs in one class means a small change made on the screen can break the data rules.

Definition 4.5.20

MVC (Model–View–Controller) is an architectural pattern that divides the program into three responsibilities. The model holds the data and the rules, the view only displays, the controller takes the input and manages the model and the view.

Let us take the responsibilities one by one. The model (Student, getName()) contains the data and the rules. It knows nothing of the screen; it can be tested without a screen. The view (StudentView) only displays; its show(name) method writes to the console. The controller (StudentController) takes the input and manages both sides; update() reads the model and gives the result to the view.

Student m = new Student("Ayşe");
StudentView g = new StudentView();
StudentController d =
    new StudentController(m, g);
d.update();  // g.show(m.getName())

The full form of the three classes used in this short excerpt is in the program below:

class Student {
  private final String name;
  Student(String name) { this.name = name; }
  String getName() { return name; }
}
class StudentView {
  void show(String name) { System.out.println("Student: " + name); }
}
class StudentController {
  private final Student model;
  private final StudentView view;
  StudentController(Student model, StudentView view) {
    this.model = model;
    this.view = view;
  }
  void update() { view.show(model.getName()); }
}
public class Main {
  public static void main(String[] args) {
    Student m = new Student("Ayşe");
    StudentView g = new StudentView();
    StudentController d =
        new StudentController(m, g);
    d.update();  // g.show(m.getName())
  }
}
Student: Ayşe

The controller receives the model and view objects in its constructor. This too is dependency injection: the controller does not create the model and view it will work with; it receives them from outside. Changing the view, for example writing the name to a file instead of the console, affects only StudentView; the model does not change at all. Application frameworks implement MVC in different ways. There is no single “right” class structure; what they share is the separation of the three responsibilities.

4.5.10.7When a pattern is not used

A side effect of learning patterns is the wish to use them where they are not needed. There are four common mistakes:

  • Making Singleton a global variable. State that can be reached and changed from everywhere ties the parts of the program together invisibly.
  • A needless factory. Writing a separate class for a creation as simple as new Point(3, 4).
  • A needless observer. Building an event system when a single direct method call is enough; the flow of the program becomes harder to follow.
  • Using a pattern for its name's sake. The problem comes first, then the pattern. Before adding a pattern, two questions are asked: “Which change does it make easier? Which dependency does it reduce?”

Strategy and dependency injection make it possible to put a simple fake object in place of a real part. Attaching a constant strategy to the checkout and giving a fake payment object to the payment method are examples. Looked at the other way round, a class that is hard to test on its own often shows that its design should be reviewed.

4.5.12Common mistakes

The compiler catches almost all mistakes with abstract classes and interfaces. The messages are in English and formulaic; once recognized, the place of the error is found at once. The boxes below give the most frequent ones with their messages.

Common mistake

Creating an object from an abstract class. new Shape("?") → Shape is abstract; cannot be instantiated. The object is created from a concrete subclass; the type of the variable can stay abstract: Shape s = new Square(3);. The same message comes when an object is created from an interface.

Common mistake

Forgetting to write an abstract method. Circle is not abstract and does not override abstract method draw() in Shape. Either the method is written or the class is made abstract. When implementing an interface the message is the same; only the last word is the name of the interface.

Common mistake

Writing a body for an abstract method, or not making the class abstract. abstract void draw() { } → abstract methods cannot have a body. A method is either abstract or has a body. class Shape { abstract void draw(); } → Shape is not abstract and does not override abstract method draw() in Shape.

Common mistake

Contradictory modifiers. abstract final, private abstract, static abstract → illegal combination of modifiers. All three modifiers prevent overriding; an abstract method and an abstract class exist for subclasses.

Common mistake

Deriving from two classes. class C extends A, B → '{' expected. A class can have a single extends and many implements. That the message does not explain the error makes it harder to recognize.

Common mistake

Calling a method that is not in the type of the reference. Flyable u = new Duck(); u.swim(); → cannot find symbol. Which methods can be called is decided not by the object but by the type of the reference. The method is called through a reference of a type that knows it (Swimmable or Duck).

Common mistake

Not resolving conflicting default methods. class Clerk inherits unrelated defaults for greet() from types Greeter and Welcomer. The method is overridden in the class; the version of the wanted interface can be called with InterfaceName.super.greet().

Common mistake

Forgetting the sealing rules. A subtype that is not permitted: class is not allowed to extend sealed class: Animal. A permitted subtype with no modifier: sealed, non-sealed or final modifiers expected.

Common mistake

Changing a local variable that a lambda uses. local variables referenced from a lambda expression must be final or effectively final. A lambda carries a copy of the value of the local variable; the variable cannot be changed afterwards. A value that has to change is kept in a field.

Common mistake

Thinking generic types inherit the subtype relationship. List<Number> x = ints; (ints is a List<Integer>) → incompatible types: List<Integer> cannot be converted to List<Number>. A method that reads declares its parameter as List<? extends Number>, a method that writes as List<? super Integer>.

4.5.13Summary

  • Abstraction is hiding the detail and defining “what is done”, leaving “how” to the subtypes. Java has two tools for it: the abstract class and the interface.
  • An abstract class is defined with abstract class; no object can be created from it. It can contain fields, constructors, abstract and concrete methods. Its constructor builds the part of a subclass object that comes from it and is called with super(...).
  • An abstract method has no body and ends with ;. A concrete subclass must implement it. It cannot be written together with private, static and final.
  • The template method defines the skeleton of an algorithm in the superclass (in a final method); the varying steps are abstract methods written in the subclasses.
  • An interface is a contract. Its methods are implicitly public abstract, its fields public static final; it has no instance fields and no constructor. A class can write a single extends and many implements; the implementing method must be public.
  • The type of the reference decides which methods can be called, and the class of the object decides which body runs. Programming to an interface type gives loose coupling.
  • A lambda expression is an anonymous function written in the form (parameters) -> expression and is assigned to a functional interface (an interface with a single abstract method) (Java 8+). It runs not when it is defined but when the interface's method is called. The local variables it uses must be effectively final.
  • Methods with bodies in interfaces: default (Java 8, inherited), static (Java 8, called only with the interface name) and private (Java 9, only inside the interface). Conflicting default methods are overridden by the class; a method in the superclass beats a default method.
  • A sealed type (sealed, Java 17+) limits its subtypes with permits; each subtype is final, sealed or non-sealed. In a closed hierarchy a switch can cover every case without a default branch.
  • An abstract class groups closely related classes with common state and code (“is a”); an interface gives abilities to unrelated classes (“can do”). Often the two are used together.
  • Generics write classes and methods with type parameters (Box<T>, <T extends Parent>). Type errors are caught at compile time. Generic types are invariant; flexibility comes from wildcards (? extends, ? super). Type information is erased after compilation.
  • Annotations are metadata like @Override; RUNTIME annotations are read by reflection.
  • Design patterns are tried solution templates: Singleton (one object), Factory (gathering creation), Observer (notifying registered objects of changes), Strategy (an interchangeable algorithm) and MVC (separating data, display and control). A pattern is used only if it solves a real problem.

  2. The interface Counter has an abstract int count() and default int twice() { return 2 * count(); }; the interface Meter has default int twice() { return 100; }. The class Both implements Counter, Meter returns 7 in count() and writes twice() as Counter.super.twice() + Meter.super.twice(). What is new Both().twice()? What would happen if Both did not write twice()?

    Answer

    The default body of Counter calls this.count() and finds 2 · 7 = 14; that of Meter returns 100. The result is 114. If the method were not written, the class would not compile, because the two interfaces bring two default bodies with the same signature: inherits unrelated defaults for twice().

  3. After the definitions Function<Integer, Integer> f = x -> x + 1; and Function<Integer, Integer> g = x -> x * 3;, what are f.apply(g.apply(4)) and g.apply(f.apply(4))? When the definition lines run, does either of the lambdas run?

    Answer

    The inner call runs first. g.apply(4) = 12, f.apply(12) = 13. f.apply(4) = 5, g.apply(5) = 15. The result is 13 15. The definition lines only create two interface objects; the bodies run only when apply is called.

  4. l.removeIf(s -> s.length() == 4); is applied to the list List<String> l = new ArrayList<>(List.of("plum", "pear", "kiwi", "fig", "apricot"));. What becomes of the list? Which functional interface is the parameter of removeIf?

    Answer

    The four-letter “plum”, “pear” and “kiwi” are removed; the remaining list is [fig, apricot] and the order of the rest is preserved. removeIf takes a Predicate: the test method that returns boolean for each element. removeIf was added to the Collection interface as a default method in Java 8.

  5. The generic method max of this chapter is called with Integer[] d = {3, 9, 4} and String[] a = {"Olive", "apricot", "Apple"}. What are the results? Why is the second result surprising at first sight?

    Answer

    For the numbers 9 is found. For the strings compareTo compares character codes, and the codes of capital letters (O = 79, A = 65) are smaller than those of lowercase letters (a = 97). So the string that comes last in dictionary order, the “largest”, is apricot. The result is 9 apricot.

  6. The sealed interface Animal permits only Cat and Dog, and the switch in the method kind has two branches and no default branch. One day Bird is added to the permits list and final class Bird implements Animal is written. What happens? What would have happened if the switch had a default branch from the start?

    Answer

    The method kind stops compiling: the switch expression does not cover all possible input values. The compiler points to every place where the new type is not handled. With a default branch the program would compile and Bird would silently fall into default; the missing branch would be noticed only at run time, perhaps never.

  7. In class Machine, public void work() prints “Machine is working”. In the interface Printer, default void work() prints “Printing”. For class Photocopy extends Machine implements Printer { }, what does Printer y = new Photocopy(); y.work(); print? Why does the class compile?

    Answer

    “Machine is working” is printed. If a class receives a method with the same signature both from its superclass and from the default body of an interface, the method in the class hierarchy wins. In this case there is no conflict, so the class compiles. That the reference has type Printer does not change the result.

  8. Predicate<Integer> p = x -> { counter.add(x); return x > 2; }; is defined (counter is an empty ArrayList<Integer>). A loop over List.of(1, 5, 2, 8) increases n if p.test(x) is true. After the loop what are n and counter? What would happen if counter were an int local variable and the lambda increased it with counter++?

    Answer

    The lambda runs once per test call and adds the number it sees to the list. 5 and 8 satisfy the condition: n = 2, counter = [1, 5, 2, 8]. Adding an element to the list is not assigning a new value to the variable counter; the variable always points to the same list and stays effectively final. Increasing an int local variable with counter++, however, is assigning it a new value and does not compile: local variables referenced from a lambda expression must be final or effectively final.
