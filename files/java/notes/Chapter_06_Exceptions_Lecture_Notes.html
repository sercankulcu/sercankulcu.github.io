Chapter 6: Exceptions

Even a correctly written program runs into surprises from the outside world. A file it needs to read may have been deleted, a user may type letters where a number is expected, a network connection may drop. Programs also contain faults of their own: division by zero, indexing past the end of an array, using a null reference. Java handles all of these through a single mechanism, the exception. This chapter first shows what an exception is and what happens to a program that does not catch one. It then traces the try, catch and finally blocks, automatic resource closing, and nested blocks step by step. The class hierarchy of exceptions, checked and unchecked exceptions, and the throw and throws keywords form the core of the chapter. The common exception classes are illustrated one by one. The chapter ends with writing custom exception classes, reading a stack trace, and good practices.

6.1The idea of an exception

Programming errors fall into three groups. A compile-time error is code that breaks the rules of the language: a semicolon is missing or a variable is undeclared. The compiler finds it and the program never runs. A logic error is silent: the program runs but produces a wrong result, for example when an average is computed by dividing the sum by the wrong number. The third group consists of problems that appear while the program is running. The code compiles, but at a particular moment, with a particular value, it cannot be executed. This chapter is about that third group.

6.1.1What is an exception?

Definition 6.1

An exception is an unexpected event that occurs while a program is running and disrupts its normal flow. In Java an exception is an object. It carries the type of the event, a descriptive message, and the place where the problem occurred.

Everyday examples come to mind at once. A file that is to be opened cannot be found. An integer is divided by zero. Code tries to reach the fifth element of a three-element array. A method is called through a null reference. None of these is something the compiler can foresee. Whether the file exists or whether the denominator is zero becomes known only while the program runs.

Two parties can create an exception. The first is the Java Virtual Machine (JVM). Situations such as division by zero or an array index out of range are noticed by the JVM itself, which creates the exception object on its own. The second is the programmer. When the programmer sees an invalid argument, for instance, the throw keyword deliberately creates an exception. In both cases the outcome is the same: there is an exception object and the normal flow has stopped.

The exception mechanism gives the programmer an orderly way to deal with unusual situations. Roughly speaking, when Java meets an exception it says: “I give up, I do not know what to do right now. Someone else handle this!” The code that resolves the problem does not have to be where the problem occurred.

Think of a restaurant. A waiter goes to the kitchen and learns that the requested dish has run out. The waiter cannot fix this alone and reports it to the manager. The manager either solves the problem by suggesting another dish to the customer, or passes it on to a higher level. An exception travels between methods in the same way. If the method that notices a problem cannot solve it, it reports it to the method that called it. This chain continues until the problem reaches a method that can solve it.

6.1.2Runtime errors: Exception and Error

When a problem arises while the program is running, the JVM throws it as a Throwable object. The name of this class means “something that can be thrown”. Throwable has two main branches, and they describe very different situations.

Table 6.1: The two main branches of runtime problems.
BranchWhat it describesWhat the program can doExample
Exception (Exception)An unusual situation that the program can anticipateCan catch it and recover10 / 0, arr[5] on a three-element array, a missing file
Error (Error)A serious problem at the JVM or system levelUsually not caught; the program terminatesStackOverflowError, OutOfMemoryError

The criterion behind the distinction in the table is the question “can the program recover from this situation?” If a file is not found, the program can ask the user for another file name. If the user types letters instead of a number, the program can warn and ask again. These are exceptions. If memory is exhausted or the call stack has overflowed, the program has no resources left with which to repair anything. These belong to the Error class.

The exception mechanism, together with the stack trace an exception leaves behind, is among the most powerful tools for finding and fixing the causes of runtime errors, that is, for debugging. The compiler reports compile-time errors, and a logic error leaves no trace. With a runtime error, however, the JVM prints the type of the problem, its message, and its exact location.

6.1.3An uncaught exception

Let us first see what happens when no precaution is taken. The following program divides an integer by zero.

public class Crash {
  public static void main(String[] args) {
    int num = 10, den = 0;
    System.out.println("Start");
    int result = num / den;
    System.out.println("Result: " + result);
    System.out.println("Done");
  }
}
Start
Exception in thread "main" java.lang.ArithmeticException: / by zero
    at Crash.main(Crash.java:5)

The program first prints Start. While line 5 evaluates num / den, the denominator is zero. Integer division by zero has no result. The JVM creates an ArithmeticException object and throws it. There is no code at this line to catch the exception. The caller of main is the JVM itself, so the exception reaches the JVM and the program terminates. The Result and Done lines are never printed.

The message printed by the JVM carries three pieces of information. The Exception in thread "main" part says that the exception was not caught in the main thread. Next comes the fully qualified class name of the exception: java.lang.ArithmeticException. The / by zero after the colon is the message of the exception. The last line gives the location of the problem: the main method of the Crash class, line 5 of the file Crash.java. Lines beginning with at are called the stack trace.

Common mistake

Taking the “crash” of a program for a compile-time error. This program compiles without trouble. The compiler cannot know what value the variable den will have at run time. The problem appears only when the program is run. The phrase Exception in thread in the message shows that it is a runtime problem.

6.1.4Handle or declare

If an exception can occur in a method, the method has two options.

The first way is to handle the exception. The method places the code that may cause the exception in a try block and resolves the situation itself in a catch block. Consider a method that reads a settings file. If the file is not found (FileNotFoundException), the method shows the user a message and continues with default settings.

The second way is to make the exception the caller's problem. The method does not handle the exception; it declares in its signature, with the throws keyword, that it may throw this exception. The exception thereby becomes the problem of the code that calls the method. The calling code faces the same choice: it either handles the exception or passes it on to the method above it.

The question that decides which way to choose is: where is the place that can resolve the exception in a meaningful way? Code that takes the file name from the user can ask again in the “file missing” case. A low-level method that reads the file line by line does not talk to the user, and it does not know where the file name came from. For that method the right choice is to declare the exception; for user-interface code the right choice is to handle it.

6.1.5Exceptions instead of return codes

Exceptions are how a program reports that “something went wrong”. But “going wrong” is subjective. Is failing to find a name in an array an error, or an ordinary outcome? Before the exception mechanism became widespread, such situations were reported with a special return value. The following method returns -1 if it cannot find the name it is looking for.

public static int indexOf(String[] names, String name) {
  for (int i = 0; i < names.length; i++) {
    if (names[i].equals(name)) {
      return i;
    }
  }
  return -1;
}
// in main
String[] names = {"Ali", "Ayşe", "Can"};
System.out.println(indexOf(names, "Can"));
int k = indexOf(names, "Ece");   // k = -1
System.out.println(names[k]);
2
Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index -1 out of bounds for length 3
    at ReturnCode.main(ReturnCode.java:14)

The first call finds "Can" at index 2 and 2 is printed. In the second call "Ece" is not in the array and the method returns -1. The calling code has forgotten to check this value. The access names[-1] throws an ArrayIndexOutOfBoundsException. The real problem arose in the search, but the error shows up somewhere else, at the array access. A fault whose source and symptom are in different places is harder to debug.

A return code has another problem: the error value can be confused with ordinary results. Here -1 works because it is an invalid index. For a method that measures temperature, however, -1 is a valid value, and the same method is left with no spare value to report an error.

The same method is written like this with an exception.

public static int find(String[] names, String name) {
  for (int i = 0; i < names.length; i++) {
    if (names[i].equals(name)) {
      return i;
    }
  }
  throw new IllegalArgumentException("Not found: " + name);
}
// in main
try {
  System.out.println(find(names, "Ece"));
} catch (IllegalArgumentException e) {
  System.out.println("Error: " + e.getMessage());
}
Error: Not found: Ece

If no match is found, the method throws an IllegalArgumentException. The message includes the name that was searched for: Not found: Ece. The caller can no longer forget to check. If the exception is not caught, the program stops at that point and clearly shows where the problem is. The error is not confused with a normal result: whenever the find method returns a number, that number is always a valid index.

For this reason special return codes such as -1 are generally avoided and Java's exception mechanism is preferred. The benefits of exceptions can be summed up in three points:

  • Error handling is explicit and consistent; the error value is not confused with a normal result.
  • The code is more readable and debugging is easier: the error is visible where it occurs.
  • Code is more reliable: exceptions, unlike unchecked return codes, do not slip by silently.
Common mistake

Turning every negative outcome into an exception. The result “not found” of a search method may be part of the program's ordinary flow. This is why String.indexOf in the Java library still returns -1. Exceptions are for situations that the caller does not expect and that cannot be described by an ordinary value. The decision is made according to the method's contract and is documented.

6.2try and catch

6.2.1The try and catch statements

The basic structure of error handling in Java is the try-catch statement. Code that may cause an error is written in the try block. What to do if an error occurs is written in the catch block.

Definition 6.2

The try block contains the statements that may cause an exception. The catch block runs and handles an exception of the specified type when one occurs in the try block; this is called catching the exception. The (ArithmeticException e) in the parentheses of catch is a parameter declaration: e is a reference to the thrown exception object.

try {
  // Code that may fail
  int result = 10 / 0; // ArithmeticException
} catch (ArithmeticException e) {
  // Handle the error
  System.out.println("Error: " + e.getMessage());
}
Error: / by zero

The expression 10 / 0 throws an ArithmeticException. The type of the thrown object matches the type written in catch. The JVM binds this object to the parameter e and runs the catch block. e.getMessage() returns the message of the object, the text / by zero.

The flow of this structure is summarized by two rules:

  • If an exception occurs, the remaining lines of the try block are skipped and control passes to the matching catch block.
  • If no exception occurs, the catch block never runs.

In both cases the program continues its normal flow after the catch block. Because the exception was caught, the program does not crash.

The code used here is an artificial example written to demonstrate an exception. With the literal expression 10 / 0 the compiler can see the problem too, but it issues the warning (division by zero) only when compiling with -Xlint. In real programs the denominator is usually a variable whose value becomes known only at run time.

Using a variable declared inside try outside the block. In the program above, int result is declared in the try block; its scope ends at the closing brace of the block. If System.out.println(result) is written after the try, the compiler reports cannot find symbol. If the variable is needed outside, it is declared before the try and given an initial value.

The catch parameter is an ordinary reference. The exception object is also an ordinary object, and it inherits its methods from the Throwable class. The following code shows what these methods return.

try {

  System.out.println(e.getMessage());
  System.out.println(e);

The first line of the output comes from getMessage(): Index 5 out of bounds for length 3. The second line is written by println(e). println calls the object's toString() method, which joins the full class name with the message. The third line is just the short name of the class. getCause() is for chained exceptions. A method can convert an exception it caught at a lower level into one of its own types and rethrow it. In doing so it attaches the old exception to the new object as its “cause”: new RuntimeException("Could not read settings", e). Code at the higher level can then reach the original source of the problem with getCause(). In this example the exception has no cause and the method returns null.

Common mistake

Assuming that getMessage() is always non-empty in a message shown to the user. For exceptions created without a message, such as new Exception(), getMessage() returns null. When logging, e.toString() or println(e) is safer: at least the class name is always printed.

6.2.4Multiple catch blocks and their order

More than one type of exception can occur in a block of code. Consider a program that divides two numbers taken from the user. The input may not be a number, the denominator may be zero, the input may be missing. A separate catch block is written for each kind of error, and each block contains the reaction specific to that type.

try {
  // Code that may fail
} catch (ArithmeticException e) {
  // Handle ArithmeticException
} catch (NullPointerException e) {
  // Handle NullPointerException
} catch (Exception e) {
  // All other exceptions
}

When an exception is thrown, the catch blocks are tried in order from top to bottom. The first matching block runs and the others are skipped. Here “matching” means that the thrown object is of the type in the catch or one of its subclasses. This is the logic of the instanceof operator. The final catch (Exception e) is the general case that catches all remaining exceptions.

Order matters when there is an inheritance relationship among the catch types. In the following code the general type is written before the specific type.

try {
  int result = 10 / 0;
} catch (Exception e) {
  System.out.println("General error");
} catch (ArithmeticException e) {
  System.out.println("Arithmetic error");
}
OrderError.java:7: error: exception ArithmeticException has already been caught
    } catch (ArithmeticException e) {

ArithmeticException is an Exception. The first block already catches every ArithmeticException that is thrown, so the second block can never run. The Java compiler does not allow an unreachable catch block and reports an error. The rule is simple: subclasses come before superclasses. The correct order is as follows.

} catch (ArithmeticException e) {
  System.out.println("Arithmetic error");
} catch (Exception e) {
  System.out.println("General error");
}

For types with no inheritance relationship the order does not matter. ArithmeticException and NullPointerException are not subclasses of each other. An object cannot be both at once, so at most one of the two blocks matches, whichever order they are written in.

Example 6.1

NumberFormatException is a subclass of IllegalArgumentException. What happens if catch (IllegalArgumentException e) is written first and catch (NumberFormatException e) second?

A compile-time error occurs: exception NumberFormatException has already been caught. Since every NumberFormatException is an IllegalArgumentException, the first block already catches it. If the two blocks are swapped, the code compiles. The specific case (“not a number”) is handled first, then the general case (“invalid argument”).

6.2.6One catch, several types

Sometimes different exceptions get the same reaction. Writing a separate, identical catch for each leads to code duplication. Since Java 7, types can be combined in a single catch with the | sign. This construct is called multi-catch.

try {
  Object o = "Hello";
  Integer i = (Integer) o;
} catch (ClassCastException
    | NullPointerException e) {
  System.out.println("Type or null error: "
    + e.getClass().getSimpleName());
}
Type or null error: ClassCastException

"Hello" is a String object; it cannot be cast to Integer. The thrown ClassCastException fits one of the two types in the block, and the block runs. e.getClass().getSimpleName() shows which exception was actually caught.

Multi-catch has two rules. First, in this block e is implicitly final; a new value cannot be assigned to it. If e = null; is written, the compiler reports multi-catch parameter e may not be assigned. The same assignment is not forbidden in a single-type catch, but it is not good practice either.

The second rule is that the alternatives cannot be subclasses of one another.

} catch (FileNotFoundException
    | IOException e) {
Main.java:9: error: Alternatives in a multi-catch statement cannot be related by subclassing
    | IOException e) {
  Alternative FileNotFoundException is a subclass of alternative IOException

FileNotFoundException is a subclass of IOException. Writing IOException already covers the subtype, so writing both together is meaningless. The fix is to write only the supertype: catch (IOException e).

6.3finally and resource management

6.3.1The finally block

A program opens a file, reads data, and closes the file. What happens if an exception occurs during reading? The rest of the try block is skipped; if the closing line is also inside the try, it never runs. The file stays open. The operating system limits the number of files a program can have open at the same time. Files, network connections and database connections that are never closed pile up, and eventually the program cannot open any new resource. This problem is called a resource leak.

Definition 6.3

The finally block is the block written after the try and catch blocks that runs in every case. Whether or not an exception occurs, and whether or not it is caught, finally runs.

try {
  // Code that may fail
} catch (Exception e) {
  // All other exceptions
} finally {
  // Always runs
}

That finally runs “in every case” covers four situations:

  • There is no exception: try ends, then finally runs.
  • There is an exception and a catch catches it: the catch ends, then finally runs.
  • There is an exception but no catch matches: finally runs, and then the exception leaves the method.
  • There is a return inside try or catch: finally runs just before the method exits.

This guarantee ensures that certain steps are certain to run. The typical use is cleanup: closing files and network and database connections, releasing locks, deleting temporary files.

A try must be followed by at least one catch or a finally. Writing only try { } finally { } is valid. In that form the exception is not caught, but cleanup is still done. A lone try is a compile-time error: 'try' without 'catch', 'finally' or resource declarations.

The real exception to the rule is the call to System.exit(). This call stops the JVM immediately. If System.exit(0) runs inside try, finally does not run. A crash of the JVM itself or a shutdown of the computer also prevents finally, of course.

6.3.3try-with-resources

Closing a resource with finally is correct, but the code gets long. The resource variable is declared as null before the try, finally checks whether it is null, and then calls close(). Since close() can also throw an exception, another try-catch is often needed. Java 7 introduced a construct that shortens this work.

Definition 6.4

try-with-resources is a try statement that opens a resource in the parentheses after the try keyword. A resource opened in the parentheses is closed automatically when the block ends: the JVM calls the resource's close() method. Closing happens even if the block ends with an exception. The resource class must implement the AutoCloseable interface.

The example in the slides uses a small resource class that prints its opening and closing.

class Resource implements AutoCloseable {
  private String name;
  Resource(String name) {
    this.name = name;
    System.out.println(name + " opened");

  void use(int x) {
    System.out.println(name + " in use");
    int s = 10 / x;
  }
  @Override
  public void close() {
    System.out.println(name + " closed");
  }
}

  r.use(0);
} catch (ArithmeticException e) {
  System.out.println("Error: " + e.getMessage());

6.3.5Nested try blocks

A try block can contain another try block. This structure is used to take a precaution specific to one part of a task while taking a general precaution for the whole task.

try {
  // Outer try block
  try {
    // Inner try block
    // Code that may fail
  } catch (Exception e) {
    // Inner catch block
  } finally {
    // Inner finally block
  }
} catch (Exception e) {
  // Outer catch block
} finally {
  // Outer finally block
}

If an exception occurs in the inner try, the JVM proceeds in this order:

  1. The catch blocks of the inner try are tried. If there is a suitable catch, it runs.
  2. If there is no suitable catch, the exception moves outward. The catch blocks of the outer try are tried and the first suitable one runs.
  3. If no catch matches, the exception leaves the method. If nobody finally catches it, the JVM's default handler terminates the program.

In every case, the finally block at each level the exception passes through runs.

6.4The exception hierarchy

6.4.1The Throwable tree

In Java the exception classes form a class hierarchy. At the root of the tree is the class Throwable. Throwable is the ancestor of everything that can be thrown. Only objects of Throwable and its subclasses can be thrown with throw and caught with catch. A line such as throw "error"; therefore does not compile: incompatible types: String cannot be converted to Throwable.

Throwable has two direct subclasses: Error and Exception. RuntimeException, one of the subclasses of Exception, forms a family of its own. Figure 6.9 shows this structure.

The hierarchy has a practical consequence: a catch block catches the type written in it and all of its subclasses. This is a natural consequence of inheritance. Every FileNotFoundException is also an IOException. So catch (IOException e) catches both FileNotFoundException and other input/output errors. Exceptions of the same family can be caught with a single supertype.

A few relationships in the tree are worth noting separately. NumberFormatException is a subclass of IllegalArgumentException. ArrayIndexOutOfBoundsException and StringIndexOutOfBoundsException are subclasses of IndexOutOfBoundsException. StackOverflowError and OutOfMemoryError derive not directly from Error but from its subclass VirtualMachineError. The figure omits this intermediate level for simplicity.

Java also supports writing new exception classes. An application-specific situation, for example “insufficient balance”, is added to this hierarchy with a class of its own. Such classes are attached to a branch of the tree and obey the same rules.

Example 6.4

new FileReader("missing.txt") throws a FileNotFoundException. Which of the types RuntimeException, Error, SQLException and IOException catches this exception?

Only IOException. The superclass chain of the exception is FileNotFoundException → IOException → Exception → Throwable. RuntimeException and SQLException are separate branches of Exception. Error is not in the Exception family at all. catch (Exception e) or catch (Throwable t) would also catch it, but they are not among the options.

6.4.2Error and Exception

The two big branches of the tree answer different questions.

Definition 6.5

Error indicates that the program has met a serious problem from which it cannot recover. Coping with these situations is mostly impossible and the program usually terminates. Exception represents situations that the program can anticipate and can often recover from; this is the type that is expected to be handled with try-catch.

Examples of Error are extreme situations: the program running out of memory (OutOfMemoryError), the call stack overflowing (StackOverflowError), a disk drive “disappearing”. These situations arise less from a line of the program than from the state of the environment. Catching Error in application code is not recommended. If memory is exhausted, the catch block itself may have no memory left to run.

Examples of Exception, on the other hand, are everyday problems: the file is missing, the network dropped, the input is invalid, the reference is null. Some of these come from outside the program; some are the programmer's mistake. RuntimeException, a subclass of Exception, mostly represents programmer errors. The distinction between checked and unchecked exceptions is based on this difference.

Error and Exception both derive from Throwable; so both can be thrown and, technically, both can be caught. But the one that “should be handled” is the Exception family.

Common mistake

Believing that “catch (Exception e) catches everything”. Exception does not include the Error family. A StackOverflowError caused by infinite recursion is not caught by this block and the program terminates with a stack trace. The type that catches everything is Throwable; but catching it is not recommended either, because it hides Errors.

6.5Checked and unchecked exceptions

6.5.1Two kinds of exceptions

Java exceptions fall into two groups according to the compiler's attitude.

Definition 6.6

A checked exception is an exception that the compiler verifies at compile time. The programmer must either handle or declare this exception. Classes that derive from Exception but not from RuntimeException are in this group. An unchecked exception, on the other hand, is not verified at compile time and arises at run time. RuntimeException, Error and their subclasses are in this group.

Checked exceptions describe situations known in advance to be possible. Every program that reads a file must face the possibility that the file is not found. The compiler asks for a plan for this possibility. Unchecked exceptions, on the other hand, are mostly the symptom of a programming error. If the compiler demanded a plan at every division, every array access and every method call, the code would become unreadable.

6.5.2Checked exceptions: catch or declare

Java's rule for checked exceptions is the “catch or declare” rule. Code that may throw an exception is either handled inside a try-catch or declared in the method's signature with throws. This rule is verified at compile time; if it is not obeyed, the program does not compile.

The rationale is simple. However correctly a program that tries to read a file is written, the file may have been deleted in the meantime. This is not a programmer's mistake; it is a fact of the outside world. The compiler makes sure the programmer does not forget this possibility.

public void readFile() {
  FileReader reader = new FileReader("data.txt");
}
Main.java:5: error: unreported exception FileNotFoundException; must be caught or declared to be thrown
  FileReader reader = new FileReader("data.txt");

The constructor of FileReader declares throws FileNotFoundException in its signature. The method readFile neither catches nor declares this exception. The compiler gives the two ways to fix the error in the message itself: must be caught or declared to be thrown. The fix by declaring is as follows:

public void readFile() throws FileNotFoundException {
  // Read the file
  FileReader reader = new FileReader("data.txt");
}

Now the method compiles. But the problem has not disappeared; it has passed to the code that calls the method. Every piece of code that calls readFile() must obey the same rule.

6.5.3Handling a checked exception

The second solution is to catch the exception inside the method.

public static void readFile2() {
  try {
    FileReader reader = new FileReader("data.txt");
    // Read the file
  } catch (FileNotFoundException e) {
    // Checked exception handled here
    System.err.println("File not found: " + e.getMessage());
    // Rethrow if needed:
    // throw e;
  }
}
File not found: data.txt (The system cannot find the file specified)

In this version the method catches the exception itself; it has no throws in its signature. The calling code needs to do nothing. The message is written to System.err, the error output stream. The second part of the message comes from the operating system. The output above was obtained on Windows: (The system cannot find the file specified). On Linux the same situation prints (No such file or directory).

The throw e; in the comment shows another possibility. The caught exception can be rethrown, for example after logging it. Then the exception again leaves the method, and the method signature must again declare throws FileNotFoundException.

Common mistake

Trying to catch a checked exception that is never thrown. If catch (FileNotFoundException e) is written for a try that contains no file operation, the compiler reports exception FileNotFoundException is never thrown in body of corresponding try statement. The compiler knows where checked exceptions can come from. catch (Exception e) does not produce this error, because Exception also covers the unchecked RuntimeExceptions.

6.5.4Unchecked exceptions

Unchecked exceptions need not be handled or declared. They are usually the result of logic errors or programmer mistakes: division by zero, use of null, exceeding an array bound. They do not have to be listed with throws or wrapped in try-catch; the compiler stays silent.

public void divide(int num, int den) {
  // Unchecked: ArithmeticException
  int result = num / den;
}

This method compiles and does not need throws. If den is zero, an ArithmeticException occurs at run time. The right fix for such an error is often not to catch it but to prevent it. The denominator is checked before dividing, and null is checked before use.

public void divide(int num, int den) {
  if (den == 0) {   // prevention
    System.out.println("Divisor cannot be 0");
    return;
  }
  int result = num / den;
}

In the prevention version the exception never occurs. The check catches the problem at its source and lets the programmer decide how to handle the situation. Here the method prints a message and returns early. In a real program it is often more correct to throw an IllegalArgumentException with a meaningful message, because that clearly tells the caller that it made a mistake.

6.6Throwing exceptions

6.6.1The throw statement

When the Java runtime meets an unexpected situation, it creates an exception object and throws it. The aim is to report the situation to the code at a higher level. The programmer can do the same with the throw keyword.

Definition 6.7

The throw statement throws an exception object: throw expression;. The value of the expression must be a Throwable object. The object is usually created on the same line with new, and a message is given to its constructor.

throw new Exception("This is an exception!");

An exception changes the normal flow of the program. The lines after throw do not run; control passes to a suitable catch. The thrown exception can be caught in the calling code with a try-catch. If it is handled nowhere, the JVM terminates the program and reports what went wrong and where.

try {
  throw new Exception("This is an exception!");
} catch (Exception e) {
  System.out.println(e);
}
java.lang.Exception: This is an exception!

There are many types that can be thrown: IOException, NullPointerException, IllegalArgumentException and custom classes written by the programmer. In the example above, println(e) prints the result of the object's toString(): the full name of the class and the message given to the constructor.

Common mistake

Writing code after throw in the same block. If throw runs unconditionally, the line after it can never be reached. The compiler notices this and reports unreachable statement. throw is usually inside an if; in that case the following lines run when the condition is false.

6.6.2The type that best describes the situation

When choosing an exception type, choose the class that best represents the situation. IllegalArgumentException suits an invalid argument, and IllegalStateException suits an operation that cannot be done in the object's current state. If none of the existing classes fits, a program-specific exception class is written.

Believing that “throw can be used only in a catch block”. throw is a valid statement anywhere in a body: inside an if, in a loop, in a catch, even on the first line of a method. When used inside a catch it rethrows the caught exception.

6.6.5Calling methods that throw exceptions

When a method is called, the exceptions declared in its signature are taken into account and a suitable strategy is chosen. The file-reading method in the slides declares a checked exception.

public void readFile() throws FileNotFoundException {
  // Read the file
}

The first strategy is for the caller to handle the exception. The call is written inside a suitable try-catch block. This is the preferred way in most cases.

try {
  readFile();
} catch (FileNotFoundException e) {
  // Handle the missing file
  System.err.println("File not found: " + e.getMessage());
}

The second strategy is for the caller to declare the exception too. The calling method declares the same type with throws in its signature, and the problem passes to a higher level.

public void makeReport() throws FileNotFoundException {
  readFile();
}

The second way is less preferred than catching because it merely postpones the problem. Still, it is sometimes the right choice: if makeReport does not talk to the user, it cannot decide what to do when the file is not found either. The type in the declaration can be the thrown type itself or one of its superclasses. Writing throws IOException also compiles, because every FileNotFoundException is an IOException. If no strategy is chosen, the compiler reports unreported exception FileNotFoundException for the line readFile();.

Even the main method can write throws: public static void main(String[] args) throws IOException. Then the exception is passed all the way to the JVM, and the uncaught exception terminates the program. This is a practical shortcut in small experimental programs; in real applications it is more correct to give the user an understandable message.

6.6.7How does the JVM handle an exception?

The process seen in the propagation trace works through the same steps for every exception:

  1. The JVM or a throw statement creates an exception object. The object contains the type, the message, and the stack trace of where it was created.
  2. In the method where the exception occurred, an enclosing try and a compatible catch are looked for.
  3. If none is found, the method ends at that moment; its finally block runs, if there is one. The exception passes to the calling method and the search continues there.
  4. If a suitable catch is found, it runs; the program continues from the line after the catch.
  5. If main does not catch it either, the JVM's default handler prints the stack trace and terminates the program, or more precisely that thread.
Definition 6.9

The process that moves down the call stack to find a suitable catch, discarding the frames on the way, is called stack unwinding.

A caught exception object is an ordinary object. After the catch block ends, if no other reference to it is held, the object is no longer used. The garbage collector cleans it from memory after a while.

6.7.2NullPointerException

A null reference points to no object. Calling a method through this reference, accessing a field, or reading the length of an array leads to a NullPointerException (NPE for short). This exception is among the most common sources of bugs.

String str = null;
int length = str.length();
Exception in thread "main" java.lang.NullPointerException:
  Cannot invoke "String.length()" because "str" is null

Before Java 14 this message was just java.lang.NullPointerException and did not say which reference was null. If several references were used on the same line (a.b().c()) it was hard to find the culprit. Since Java 14 the helpful message says which operation could not be performed and why. The variable name appears only if the class was compiled with debugging information (javac -g; IDEs do this by default). The same program compiled with plain javac cannot know the name and prints this:

Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because "<local1>" is null

There are several ways to prevent an NPE:

  • An explicit check with if (str != null).
  • Objects.requireNonNull(x, message): if x is null, it immediately throws an NPE with a meaningful message.
  • Objects.requireNonNullElse(x, fallback) (Java 9+): returns the fallback value if x is null.
  • The Optional class (Java 8+): represents the “there may be no value” case explicitly with a type.
  • Libraries: for example, the StringUtils class of Apache Commons Lang offers null-safe string operations.

The following code shows these ways together.

Common mistake

Catching an NPE with catch (NullPointerException e) and moving on. An NPE is almost always a programming error: a variable was never assigned a value, or a method unexpectedly returned null. The right fix is to find where the null came from and correct it there. Catching only hides the symptom.

6.7.4ArithmeticException

ArithmeticException represents an error that occurs during a mathematical operation. The best-known example is dividing an integer by zero; both the / and % operators throw this exception. It has other sources too:

  • The “exact” methods of the Math class throw on overflow: addExact, multiplyExact, toIntExact …
  • BigDecimal provides high-precision arithmetic. It throws on division by zero and on a division whose result cannot be represented exactly (1/3).

Some operations, contrary to expectation, do not throw an exception:

  • double operations do not throw: 10.0 / 0 → Infinity, Math.sqrt(-1) → NaN.

6.7.7ClassCastException and instanceof

If an explicit cast is made when an object is not of the type it is being cast to, a ClassCastException occurs. What matters is not the type of the variable but the actual type of the object. After the line Object obj = "Hello"; the type of obj is Object, but the object it refers to is a String.

Raw-typed collections, that is, ArrayList, Map and Set written without a type parameter, accept objects of any kind. When an element of the wrong type is taken and cast, the cast fails. 6.8.2FileNotFoundException and IOException

FileNotFoundException occurs when a file is to be opened and cannot be found. The same exception is thrown if the given path is a directory or if there is no permission to read the file.

try {
  FileReader fileReader = new FileReader("file.txt");

  // Handle the missing file
  System.out.println(e);

java.io.FileNotFoundException: file.txt

The typical reaction to this exception is to tell the user and ask for a new name, or to continue with default values.

The message the same exception gives for a directory was also tried: new FileReader(".") on Windows gives java.io.FileNotFoundException: . (Access is denied). Although the name of the class says “file not found”, the exception is used to mean “file could not be opened”.

IOException represents a general error in input/output operations and has many subclasses, such as FileNotFoundException. The following code reads a text file line by line.

    new BufferedReader(new FileReader(path));

  // Handle the I/O error
  e.printStackTrace();

The code works, but it has a flaw. If readLine() throws an exception, control passes directly to the catch and the line reader.close() never runs. The file stays open: this is a resource leak. The fix is try-with-resources:

    new BufferedReader(new FileReader(path))) {
  String line;
  while ((line = reader.readLine()) != null) {
    System.out.println(line);
  }

  System.out.println(e.getMessage());
}

In this version the reader is closed however the block ends. If the file does not exist, new FileReader(path) throws an exception; in that case no resource has been created to close, and the catch runs directly. catch (IOException e) catches both the opening error (FileNotFoundException) and read errors. Tried with the nonexistent missing.txt, the block prints the message missing.txt (The system cannot find the file specified).

6.8.4ParseException and ClassNotFoundException

ParseException (in the java.text package) is thrown when a string does not match the format being used to parse it.

try {
  SimpleDateFormat form =
    new SimpleDateFormat("dd/MM/yy");
  Date date = form.parse("01-01-2022");

  // Handle the parse error
  System.out.println(e);
}
java.text.ParseException: Unparseable date: "01-01-2022"

The format is dd/MM/yy; a / is expected between day and month. The text has a - instead. The parser reads the first two characters as the day and gets stuck at the third character. e.getErrorOffset() gives this position: 2, that is, the third character.

ClassNotFoundException is thrown when a class is to be loaded by its name (Class.forName) and cannot be found.

try {
  Class.forName("java.util.Scanner");
  System.out.println("Scanner loaded");
  // Try to load a missing class
  Class.forName("com.example.NonExistentClass");
} catch (ClassNotFoundException e) {
  System.out.println(e);
}
Scanner loaded
java.lang.ClassNotFoundException:
  com.example.NonExistentClass

java.util.Scanner is in the standard library and loads without trouble. com.example.NonExistentClass, on the other hand, is not on the classpath. Loading a class by name is used when working with classes not known at compile time, such as database drivers. Because the name is a string, the compiler cannot check it; whether the class will be found becomes known only at run time.

This exception should not be confused with NoClassDefFoundError from the Error family. With ClassNotFoundException the program itself asks for a class by name. With NoClassDefFoundError, a class that existed at compile time could not be found while the program was running; this is a deployment problem.

6.8.5NotSerializableException

Definition 6.10

Serialization is the conversion of an object into a stream of bytes. This stream can be written to a file or sent over a network. Later the stream is converted back into an object.

In Java, for the objects of a class to be serializable, the class must implement the Serializable interface. This interface has no methods; it is only a permission marker. If an object of a class that does not implement the interface is to be written, a NotSerializableException occurs.

class Point {               // not Serializable
  int x = 3, y = 4;
}
// in main
try (ObjectOutputStream outputStream =
    new ObjectOutputStream(new ByteArrayOutputStream())) {
  // Try to serialize the object
  Point notSerializableObj = new Point();
  outputStream.writeObject(notSerializableObj);
} catch (NotSerializableException e) {
  System.out.println(e);
} catch (IOException e) {
  System.out.println("Other I/O error: " + e);
}
java.io.NotSerializableException: Point

NotSerializableException is an indirect subclass of IOException. For this reason its catch is written before that of IOException. If the order were reversed, the compiler would report has already been caught. The fix is to add the interface to the class:

class Point implements Serializable {
  int x = 3, y = 4;
}

With this fix the object can be written and read back. The test program wrote the object to a byte array and read it again, getting back the values x = 3, y = 4.

6.9Error classes

Error classes represent system-level problems that fundamentally affect the normal running of the program. They are unchecked types. They generally arise not from a line of application code but from the state of the JVM and the runtime environment. The JVM itself throws them. Handling or declaring these errors is not recommended; letting the program terminate cleanly is a more suitable approach. Still, because they are Throwables, they can technically be caught.

6.10Custom exceptions

6.10.1Writing a custom exception class

The exceptions in the Java library describe general situations. For the “insufficient balance” case in a banking program, or the “grade out of range” case in a grading system, the library has no special class. A developer can write custom exception classes to manage such situations that may arise in their own program.

Definition 6.11

A custom exception class is an exception class derived from Exception or RuntimeException that describes an application-specific situation.

public class MyException extends Exception {
  // Constructor
  public MyException(String message) {
    super(message);
  }
}

The constructor passes the message it receives up to the superclass with super(message). The message is stored inside Throwable; so getMessage() and toString() show the message automatically. If the super call is forgotten, getMessage() returns null.

Table 6.21: Choosing the superclass of a custom exception.
SuperclassResult
extends ExceptionChecked: the caller must handle it; recoverable business-rule violations
extends RuntimeExceptionUnchecked: incorrect use, programmer error

An object of any class that extends Throwable can be thrown. In practice, however, Exception or RuntimeException is extended. Error is reserved for JVM problems. Extending Throwable directly leaves the class outside both families; code that writes catch (Exception e) cannot catch it.

A few rules are followed when writing a custom exception. The name of the class describes the situation and ends with Exception (or Error): InsufficientBalanceException, InvalidGradeException. An exception is an ordinary class; it can contain extra fields and methods. Information such as the missing amount, the faulty value or the name of the faulty field can be added as fields. If the compiler is run with -Xlint, it also reports that the serialVersionUID field is missing; Throwable is a serializable class. This is a warning, not an error.

6.10.2Throwing and catching a custom exception

public class MyExceptionTest {
  public static void main(String[] args) {
    try {
      doWork();
    } catch (MyException e) {
      System.out.println("Caught: " + e.getMessage());
    }
  }
  public static void doWork() throws MyException {
    if (true) {
      throw new MyException("Custom error occurred.");
    }
  }

MyException is a checked exception because it derives from Exception. throws MyException is mandatory in the signature of doWork(). main uses the “handle” option by wrapping the call in a try.

The if (true) in the code is for demonstration only. Since throw is the last statement of the method here, writing it unconditionally would also compile. But if any code came after an unconditional throw, the compiler would report unreachable statement. In real programs the condition checks a business rule: is the balance sufficient, is the grade between 0 and 100, is the username empty?

6.10.3An exception that carries information: a bank account

The real power of a custom exception is that it can carry information describing the situation. The following class stores the missing amount as well as the message.

class LowBalanceException extends Exception {
  private double deficit;

  public LowBalanceException(String msg, double deficit) {
    super(msg);            // kept in Throwable
    this.deficit = deficit;
  }

  public double getDeficit() {
    return deficit;
  }
}

6.11Stack trace and good practices

6.11.1What is a stack trace?

Definition 6.12

A stack trace is a report that shows which methods were on the call stack at the moment the exception occurred and where the exception occurred. The first line gives the type and message of the exception. Each following at line gives the class, method, file and line number of one call.

For an uncaught exception the JVM prints the stack trace to the error stream (System.err). It can also be printed at any time with e.printStackTrace(). The stack trace is the most important clue that helps the programmer understand and fix the error.

Exception in thread "main" java.lang.NullPointerException
    at com.example.MyClass.myMethod(MyClass.java:10)
    at com.example.MyClass.main(MyClass.java:6)

In this listing the main method called myMethod at line 6. The exception occurred at line 10 of myMethod. com.example is the name of the package and MyClass the name of the class. The list is read from top to bottom, from “most recently called” to “first called”.

Let us look at the method of reading on a more detailed example.

A stack trace is read in four steps:

  1. The first line gives the type and message. Here the variable text is null and length() could not be called on it.
  2. The first at line is where the exception was born: the method len, line 3.
  3. Downward the call chain is read: main (10) → show (6) → len (3).
  4. Look first at the program's own lines. Lines of library classes (those starting with java.) are mostly not the source of the problem.

The real cause is often further down the list. The exception was born at line 3, but there is nothing wrong at line 3: the method len correctly computes the length of the text it is given. It was line 10 that sent the null value. The place to fix is often not where the exception was born but where the faulty value was produced.

The name "text" in the message appears when the class is compiled with debugging information (javac -g). The same program compiled with plain javac cannot know the name and prints this:

Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.length()" because "<parameter1>" is null

Line numbers, however, are printed in both cases, because javac puts line information into the class file by default.

6.11.3Good practices in exception handling

Using the exception mechanism correctly is as important as knowing it. The following eight rules gather the lessons seen in the examples.

Catch a specific type
If possible, catch the expected type instead of catch (Exception e) and give a reaction suited to each kind. The general type also silently swallows unexpected errors.
Do not swallow exceptions
An empty catch { } hides the error. At the very least the exception is logged or reported to the user.
Close resources
Resources such as files and connections are closed with try-with-resources or finally.
Prevent what can be prevented
Do null, bounds and zero checks. Instead of catching a RuntimeException, fix the code.
Do not use them for flow control
Ordinary tasks such as leaving a loop are not done with exceptions. Exceptions are for exceptional situations; also, creating an exception object and recording the stack is much more expensive than an ordinary if.
A meaningful message
The message states the faulty value and the expectation: "Grade must be 0-100: 120".
Handle in the right place
The exception is caught where it can be resolved; if it cannot be resolved, it is passed on with throws.
Keep a log
Logging exceptions to a file makes it easier to trace the error afterwards. A message that vanishes from the user's screen stays in the log file.
Common mistake

Swallowing the exception: catch (Exception e) { }. This code compiles and runs, but the error disappears without a trace. The program keeps running in a wrong state and the problem shows up much later in an unrelated place. By then the stack trace of the real cause is long gone.

6.11.4final, finally and finalize

The three names are spelled alike, but their jobs are entirely different.

Table 6.24: final, finally and finalize().
What?Purpose
finalKeywordVariable: cannot be reassigned · method: cannot be overridden · class: cannot be subclassed

finalize()A method of the Object classThe garbage collector used to be able to call it before deleting an object. When it will be called is undefined; it has been deprecated since Java 9.

The problem with finalize() is that it is unreliable. It is not clear when the garbage collector will delete an object, or even whether it will. It may never have run by the time the program ends. In the calling code, catch (NumberFormatException e) (“Not a number”) is written first, then catch (IllegalArgumentException e). The output: Age: 20, Negative age: -3, Not a number: twenty.

If the order is reversed, the NumberFormatException block can never be reached, because an NFE is an IllegalArgumentException. The compiler reports this error: exception NumberFormatException has already been caught.

Example 6.18 (Exercise: resources and the empty array)

How is code that closes a BufferedReader with finally written with try-with-resources? What should the method double average(int[] grades) do for an empty array?

Solution. The reader is opened in the parentheses: try (BufferedReader r = new BufferedReader(new FileReader(path))) { … } catch (IOException e) { … }. close() is called automatically; no finally, null check or nested try is needed.

The average of an empty array is undefined. Returning 0 is wrong, because 0 can be confused with a valid average; this is exactly the problem of the -1 return code. An empty array is an invalid argument: throw new IllegalArgumentException("Empty array");. An unchecked type is chosen, because passing an empty array is the caller's mistake. In the test program, average(new int[0]) gave this exception, while the array {70, 80, 90} returned 80.0.

6.14Summary

  • An exception is an event that disrupts the normal flow while a program is running. In Java an exception is an object; it carries its type, its message and where it occurred. The JVM or the programmer (throw) can create it.
  • Runtime problems have two branches: Exception if the program can recover, Error if there is a serious problem at the JVM or system level.
  • A method in which an exception can occur either handles it (try-catch) or declares it to the caller (throws). The right place is where the exception can be resolved in a meaningful way.
  • Special return codes (-1) mix the error with the normal result and slip by silently if unchecked. Exceptions solve these problems.
  • If an exception occurs in try, the rest of the block is skipped and the first matching catch runs. After the catch, the program continues its normal flow. If there is no exception, the catch does not run.
  • catch blocks are tried from top to bottom. A block catches the type written and all its subclasses. A subclass is written before its superclass; the reverse is the compile-time error has already been caught.
  • Since Java 7, catch (A | B e) collects the same reaction in a single block. The alternatives cannot be subclasses of one another; e is implicitly final.
  • finally runs in every case, even before a return inside try or catch. The return value is computed and stored first. System.exit() or a crash of the JVM prevents finally.
  • try-with-resources closes the AutoCloseable resources opened in the parentheses automatically. Resources are opened in the order written and closed in reverse order, before the catch.
  • In a nested try, an exception not caught at the inner level moves outward. The finally of every level it passes through runs.
  • The root of the hierarchy is Throwable; its two subclasses are Error and Exception. RuntimeException is a subclass of Exception.
  • For checked exceptions (those that derive from Exception but not from RuntimeException) the compiler enforces the “catch or declare” rule. The RuntimeException and Error families are not checked.
  • throw throws an object in the body; throws declares in the signature the types that may be thrown.
  • An uncaught exception propagates down the call stack toward the caller; the methods on the way end at that moment. This process is called stack unwinding. If main does not catch it either, the JVM prints the stack trace and terminates the program.
  • Commonly seen runtime exceptions: NullPointerException, ArrayIndexOutOfBoundsException, ArithmeticException, IllegalArgumentException, NumberFormatException, ClassCastException. These are mostly not caught but prevented.
  • double operations do not throw exceptions (Infinity, NaN); an int addition that overflows silently wraps around. Math.addExact is used to check for overflow.
  • Commonly seen checked exceptions: IOException and its subclass FileNotFoundException, SQLException, ParseException, ClassNotFoundException, InterruptedException.
  • Errors (OutOfMemoryError, StackOverflowError, AssertionError) are not caught in application code. assert is turned on only with -ea.
  • A custom exception class is written by extending Exception (checked) or RuntimeException (unchecked); the message is passed with super(message). An exception can carry extra fields with information describing the situation.
  • The first line of a stack trace is the type and message; the first at line is where the exception was born. The call chain is read downward. The real cause is often on the line that produced the faulty value.
  • Good practices: catch a specific type, do not swallow the exception, close resources, and prevent what can be prevented. Exceptions are not used for flow control; the message is meaningful, the exception is handled in the right place and logged.

6.16Test Yourself

  1. The outer try prints A. The inner try does throw new RuntimeException("x"); the inner catch catches only IllegalStateException and prints B; the inner finally prints C. After the inner block, the outer try prints D. The outer catch (RuntimeException e) prints outer: followed by the message. If all printing is done with print, what is the output?

    Answer

    AC outer:x. RuntimeException is the superclass of IllegalStateException, not a subclass; the inner catch does not match and B is not printed. Before the exception leaves, the inner finally prints C. D is skipped and the outer catch catches.

  2. What does the method static int f() { try { return 1; } finally { return 2; } } return? Why is this style not recommended?

    Answer

    2. The return 1 in the try prepares the value, but before the method exits finally runs and its own return replaces the pending value. The same style would also silently destroy an exception thrown in the try. This is why javac -Xlint gives the warning finally clause cannot complete normally.

  3. What are the results of the calls Integer.parseInt("12 ") and Double.parseDouble(" 12 ")?

    Answer

    The first throws NumberFormatException: For input string: "12 "; parseInt does not accept trailing whitespace and trim() is needed first. The second returns 12.0: Double.parseDouble strips leading and trailing whitespace itself. That two similar methods behave differently is one reason to always clean user input with trim().

  4. The parentheses of a try-with-resources contain K a = new K("A"); K b = new K(null). The constructor of K throws IllegalArgumentException("no name") if the name is null, and otherwise prints … opened; close() prints … closed. The block prints work; the catch prints catch followed by the message. What is the output?

    Answer

    A opened, A closed, catch no name. Because the constructor of the second resource throws an exception, b is never created and the block body does not run. The successfully opened a is still closed. Only resources that could be created are closed.

  5. Does catch (IOException | Exception e) compile? If the methods static void a() throws IOException and static void b() throws RuntimeException are called in main without a try, which call gives an error?

    Answer

    The multi-catch does not compile: IOException is a subclass of Exception, and the alternatives cannot be related by inheritance. The call a() gives the error unreported exception IOException. b() compiles: RuntimeException is unchecked; its declaration serves only as documentation.

  6. What do Integer.MAX_VALUE * 2 and Math.multiplyExact(Integer.MAX_VALUE, 2) give?

    Answer

    The first gives -2 with no exception: the result exceeds the int range and the value wraps around (silent overflow). The second throws ArithmeticException: integer overflow. The exact methods make overflow visible.

  7. For the class class X extends Exception { X(String m) { } }, what does new X("m").getMessage() return?

    Answer

    null. The constructor did not pass the message to the superclass with super(m). The compiler implicitly calls the no-argument super(), and the message field of Throwable stays empty. The correct form is X(String m) { super(m); }.

  8. A stack trace reads: java.lang.ArithmeticException: / by zero, followed by at Account.ratio(Account.java:12), at Account.report(Account.java:8), at Account.main(Account.java:3). Where was the exception born? Which method did main call, and at which line?

    Answer

    The exception was born at the first at line, at line 12 of the ratio method. Reading the list from bottom to top, main called report at line 3, and report called ratio at line 8. The zero denominator was most likely produced in report or in main; to fix it, one looks back from there.
