Chapter 10: Threads

A program can do several things at once. A word processor checks spelling while you type, a browser stays responsive to one tab while it downloads another, and a server handles hundreds of requests together. Java does this with threads, independent flows of execution inside one program. These notes first introduce threads, processes, concurrency, and parallelism. They then cover the Thread class, the thread life cycle, the ways to create and start a thread, and how to stop one safely. The core of the chapter is the protection of shared data: race conditions, synchronized, volatile, explicit locks, deadlock, and waiting for a condition. The last sections introduce the ready-made tools of the java.util.concurrent package, atomic classes, interruption, ThreadLocal, and thread pools. The output of a program with several threads often changes from run to run. Every such output in these notes was measured by running the program many times on JDK 21, and each example states which part of the output may vary.

10.1Basic concepts

10.1.1Threads

Every program written so far ran as a single flow. The first line of main runs, then the second; if a method is called, the flow enters that method and resumes where it left off when the method returns. At any moment, the program's "position" can be described by a single line. That single flow is itself a thread.

Definition 10.1

A thread is an independently progressing flow of execution inside a program. It executes instructions one after another and has its own call stack and its own program counter. In Java, every thread is represented by an object of the class java.lang.Thread.

Every Java program starts with at least one thread. The JVM creates a thread to run main(); it is called the main thread. If the program starts new threads, they run alongside the main thread. Working with several threads is called multithreading. Programming in which several tasks make progress during the same period of time is called concurrent programming.

The slides compare the situation to a beehive. Each bee does its own job; that is a thread. But all the bees use the same hive and the same honeycomb; that is shared memory. If two bees try to put honey into the same cell at the same moment, there is trouble. Most of this chapter is about how to organize such collisions.

Why do we need several threads? Three reasons stand out:

  • A responsive interface. In a program with a graphical interface, a long computation done on the thread that draws the interface freezes the window. If the computation is given to a separate thread, the user can keep pressing buttons.
  • Using multicore processors. Most of today's processors have 4, 8, or more cores. A single-threaded program uses only one of them. If the work is split into pieces, the cores run at the same time and the computation speeds up.
  • Working while waiting. Waiting for data to arrive over the network or for a file to be read from disk is very slow compared with the processor. While the waiting thread sleeps, another thread carries on with its work.

10.1.2Concurrency and parallelism

In everyday speech, "at the same time" describes two different situations. In technical language, the two have different names.

Definition 10.2

Concurrency means that several tasks make progress during the same period of time. It can happen even on a single core: the operating system runs threads in turn for very short time slices. Parallelism means that tasks really run at the same instant on different cores; it requires more than one core.

The left half of Figure 10.2 shows one core. A runs for a slice, then B, then A again. Because the slices last milliseconds, the user believes that both jobs advance at once. This is concurrency but not parallelism: at any given instant, only one thread is on the processor. The right half has two cores, and A and B really run at the same time. Parallelism is a special case of concurrency.

The scheduler of the JVM and the operating system decides which thread runs when and on which core. The programmer cannot know or control this order. The same program may run A first in one execution and B first in another. This nondeterminism is the most distinctive feature of multithreaded programs.

10.1.3Processes and threads

Definition 10.3

A process is a running program that has its own memory space. The operating system gives each process a separate address space. Inside a process, one or more threads run; these threads share the process's memory.

Table 10.1: Comparison of a process and a thread.
ProcessThread
MemoryIts own address spaceShares the process's heap
Stack—Each has its own
CreationExpensiveCheap (lightweight process)
CommunicationFiles, sockets, pipesShared objects
RiskCannot corrupt each otherCan corrupt shared data

A running Java program is a process, and many threads run inside it. Table 10.1 summarizes the difference between the two concepts. The objects on the heap are open to all threads of the process. If two threads hold references to the same object, both can read and modify it. Local variables, on the other hand, live on each thread's own stack and are not shared. Even if two threads run the same method at the same time, the method's local variable i has two separate copies.

This distinction cuts both ways. The good side is that sharing data between threads is very easy: it is enough to write to a shared object. Two processes can send data to each other only through operating-system facilities such as files, sockets, or pipes. The bad side is that two threads that know nothing about each other can modify a shared object at the same time. One process cannot corrupt another's memory; a thread can corrupt anything in its own process.

Creating a thread is much cheaper than creating a process, because no new address space is opened; only a new stack is allocated. That is why a thread is also called a lightweight process.

10.1.4Context switching

A computer usually has many more threads than cores. The operating system runs them in turn in time slices. When a thread's slice ends, its state is saved and the state of the next one is loaded.

Definition 10.4

Context switching is the processor's move from one thread to another. During the switch, the state of the running thread (program counter, registers, stack pointer) is saved and the state of the next thread is loaded.

Context switching has a price. Each switch takes a few microseconds. More importantly, some of the data in the processor's cache is useless to the new thread and has to be read from memory again. For this reason, adding threads does not always speed things up. A program that starts thousands of threads spends a significant part of its time on switches and slows down.

There is a practical rule. For compute-bound work, keep the number of threads at about the number of cores. The core count is available from Runtime.getRuntime().availableProcessors(); the examples in these notes were run on a machine with 12 logical cores. For I/O-bound work (network, files), more threads can help because most of them are asleep much of the time. A thread pool keeps the number under control.

10.1.5The JVM and threads

Java programs do not run directly on the operating system but inside the Java Virtual Machine (JVM). The JVM is a virtual environment that manages threads as independent units of execution. In today's JVMs, every Java thread corresponds to an operating-system thread, and the operating system does the scheduling.

Figure 10.5 shows the memory areas of the JVM. When a thread is created, the JVM gives it three private areas:

  • Stack: holds the frames of method calls, local variables, and parameters.
  • Program counter (PC) register: holds the address of the instruction the thread is currently executing.
  • Native method stack: serves calls to native methods written outside Java, for example in C.

The method area (the code of classes and static fields) and the heap (all objects) exist in a single copy and are shared by all threads. A static field and an object on the heap are therefore shared between two threads; local variables are not.

Common mistake

Believing that local variables are also shared between threads. If two threads run void count() { int i = 0; i++; } at the same time, each increments its own i on its own stack; both get 1 and neither affects the other. Trouble begins when two threads write to a field of the same object or to the same static field.

10.2The Thread class

10.2.1The class and its basic methods

Every thread is an object of the class Thread in the java.lang package. Because the package is java.lang, no import is needed. The Thread object manages the life cycle of the thread: it starts it, makes it wait, and holds its name and state.

One way to write a thread is to write a subclass of Thread. The subclass overrides the run() method and puts the thread's work there. The thread is then started by calling start(). The difference between the two methods is critical: run() is the work itself, and start() is the call that opens the new flow. Table 10.2 summarizes the frequently used methods of the class.

Table 10.2: The basic methods of the Thread class.
MethodPurpose
start()Starts the new thread, which then runs run()
run()The work the thread does
sleep(ms)static: puts the running thread to sleep for a given time
join()Waits for that thread to finish
yield()static: temporarily gives up execution to others
interrupt()Sends an interrupt request
currentThread()static: the thread that is running right now
getName(), getState(), isAlive()Read information

It is significant that sleep, yield, and currentThread are static. They act not on a particular Thread object but on the thread that executes that line. The thread that writes Thread.sleep(100) puts itself to sleep; there is no way to put another thread to sleep.

10.2.2Thread properties

A Thread object carries several properties that describe the thread. They are fields of the object, with get/set methods to read or change them.

Runnable
The object that contains the run() method the thread will execute. The main logic of the thread is defined here.
Name
Such as main, Thread-0, Thread-1. If no name is given, the JVM appends an increasing number to the prefix Thread-. It is used to recognize the thread in log files and while debugging: getName(), setName().
ID
A unique number assigned automatically when the thread is created. Since Java 19 it is read with threadId(); older versions used getId().
Group (ThreadGroup)
The group the thread belongs to. It is used to organize threads.
Daemon
A helper thread that serves other threads. The JVM does not wait for it to finish when shutting down.
Context class loader
The class loader the thread uses when it loads classes at run time.
Priority
An integer between MIN_PRIORITY (1) and MAX_PRIORITY (10); the default is NORM_PRIORITY (5).
State
One of NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED.
Interrupted
A flag showing whether an interrupt request has arrived; it is set by interrupt().

The following fragment runs inside main and prints the properties of the thread that is running at that moment.

Thread t = Thread.currentThread();   // current
System.out.println("Name    : " + t.getName());
// threadId(): Java 19+ (getId() before)
System.out.println("ID      : " + t.threadId());
System.out.println("Priority: " + t.getPriority());
String group = t.getThreadGroup().getName();
System.out.println("Group   : " + group);
System.out.println("Daemon  : " + t.isDaemon());
System.out.println("State   : " + t.getState());
Name    : main

Thread.currentThread() returns the thread that executes that line. Because the code is in main, this is the main thread. Its name is main, its ID is 1, and its priority is the default 5. Its group is also named main. The main thread is not a daemon thread. Its state is RUNNABLE, because the thread calling getState() is running at that moment. Run on JDK 21, the program printed these six lines identically every time.

Priority and the daemon property are inherited from the thread that creates the new thread. A thread created in main has priority 5 and is not a daemon. These values can be changed before start().

Example 10.1

In main, before any other thread has been created, these lines run: Thread a = new Thread(() -> { }, "worker");, Thread b = new Thread(() -> { });, Thread c = new Thread(() -> { });, and c.setPriority(Thread.MAX_PRIORITY);. What are the names of a, b, and c, and the priorities of b and c?

The names are worker, Thread-0, and Thread-1. A thread that is given a name does not use up an automatic number; numbers go in order only to unnamed threads. The priority of b is 5, inherited from the creating thread (main); that of c is 10. None of the three was ever started, so their states are NEW. On JDK 21 the program printed worker Thread-0 Thread-1 and 5 10 false.

10.2.3Thread groups

When the JVM starts, it creates two thread groups. The system group contains the JVM's own threads: Reference Handler, which manages references, the finalizer Finalizer, Signal Dispatcher, which handles signals, and others. The main group is a subgroup of system; the main thread and the threads the program creates belong to it by default.

Thread.getAllStackTraces() returns all live threads and their stacks as a map. Iterating over the key set lists them all:

10.2.4Threads running when the JVM starts

The slides discuss four of the threads that exist when the HotSpot JVM starts:

Main thread
The first thread that runs when the JVM starts. The main() method runs here; the core logic of the application executes here.
Garbage collector
Responsible for memory management. It finds and cleans up objects that no longer have references. In the HotSpot JVM, the garbage collector's threads are internal JVM threads; they do not appear as Java objects, so they are not in the list above.
Signal Dispatcher
Handles signals from the operating system. For example, on a shutdown request that arrives with Ctrl+C, it starts the orderly shutdown of the JVM.
Finalizer
Calls the finalize() method of objects. finalize() was deprecated in Java 9 and marked for removal in Java 18 (JEP 421). If the JVM is started with the --finalization=disabled option, the finalizer thread never starts. Use try-finally or try-with-resources with AutoCloseable instead.

10.3The life cycle

10.3.1The six states

From the moment it is created until it finishes, a thread passes through different states. The getState() method returns the current state as a constant of the Thread.State enumeration. Java defines six states.

Table 10.3: Thread states.
StateMeaningHow it is entered
NEWThe object has been created but not yet startednew Thread(…); exit: start()
RUNNABLERunning, or waiting for its turn on the processorAfter start()
BLOCKEDWaiting for a monitor lock to enter a synchronized block or methodWhile another thread holds the lock
WAITINGWaiting indefinitely; another thread must wake itObject.wait(), Thread.join(), LockSupport.park()
TIMED_WAITINGWaiting for a limited timeThread.sleep(ms), wait(ms), join(ms), parkNanos, parkUntil
TERMINATEDHas completed executionWhen run() returns

Table 10.3 makes one point clear: Java has no separate RUNNING state. The thread that is on the processor right now and a thread waiting for its turn are both RUNNABLE. The scheduler knows which one is really on the processor; the JVM does not expose this distinction to the program.

The three waiting states should not be confused. BLOCKED means only waiting for a monitor lock: the thread wants to enter a synchronized block, but the lock is held by another thread. WAITING is waiting indefinitely for an event: another thread must finish (join) or wake it (notify). TIMED_WAITING is waiting for a limited time; when the time runs out, the thread returns on its own. That is why sleep always produces TIMED_WAITING.

10.3.2The state diagram

Figure 10.7 shows the transitions. The main path is one-way: NEW → RUNNABLE → TERMINATED. There is no way back. A thread that has finished cannot be restarted; to do the same work again, a new Thread object is needed. From each of the three waiting states, on the other hand, the thread returns to RUNNABLE: when the lock is free, when the awaited event happens, or when the time runs out.

10.3.3Code trace: observing the states

The following program puts four threads into different states and prints their states. pause(ms) and waitFor(t) are helper methods that wrap the calls Thread.sleep and t.join() in try-catch. lock is a field of type static final Object.

public static void main(String[] args) {
    Thread sleeper = new Thread(() -> pause(1000));
    System.out.println("1) " + sleeper.getState());
    sleeper.start();
    pause(100);
    System.out.println("2) " + sleeper.getState());
    Thread waiter = new Thread(() -> waitFor(sleeper));
    waiter.start();
    pause(100);
    System.out.println("3) " + waiter.getState());
    Thread blocked = new Thread(() -> {
        synchronized (lock) { }
    });
    synchronized (lock) {
        blocked.start();
        pause(100);
        System.out.println("4) " + blocked.getState());
    }
    waitFor(waiter);
    System.out.println("5) " + sleeper.getState());
}

In steps 1 and 2, the sleeper object is created but not started; its state is NEW. In step 3, start() is called. The new thread immediately enters pause(1000) and sleeps for a second. Meanwhile main also sleeps for 100 ms. When main wakes up, sleeper is still asleep: TIMED_WAITING.

In step 6, waiter is started and calls sleeper.join(). join without a timeout is indefinite; waiter stays in the WAITING state until sleeper finishes. In step 8, main acquires the monitor of lock and then starts blocked. blocked wants to enter a synchronized block on the same lock, but main holds it. While main sleeps for 100 ms inside the block, it prints the state: BLOCKED.

Figure 10.8 shows the situation in step 9: four threads are in four different states. One point deserves attention. While main sleeps inside sleep, it does not release the lock, so blocked cannot get in. When the block ends, the lock is released, blocked enters, leaves immediately, and finishes. main then waits for waiter. sleeper finishes its full second and ends; waiter then finishes too. The last line prints the state of sleeper: TERMINATED.

Although this program is multithreaded, its output is stable. The waiting times determine which state the threads will be in at each observation: 100 ms is enough for a thread to start and enter sleep or join. The program was run 8 times and printed the same five lines each time. Even so, such timing assumptions can break on a heavily loaded machine. The delays are used here only for observation, not for synchronization.

10.4Creating and starting threads

10.4.1The Runnable interface

Every thread runs a Runnable object. The Runnable interface is in the java.lang package and contains a single method:

package java.lang;

public interface Runnable {
    void run();
}

A class that implements this interface writes the run() method. The body of the method is the work the thread will do.

public class MyRunnable implements Runnable {
    @Override
    public void run() {
        // The thread's tasks
    }
}

Because Runnable has a single abstract method, it is a functional interface. Since Java 8, a lambda expression can be written in place of such an interface. A separate class is not needed for short tasks:

Runnable r = () -> System.out.println("hello");

The lambda gives the body of the run() method directly. Its parameter list is empty because run() takes no parameters, and since the return type is void, the lambda returns no value.

10.4.2Starting a thread

A Runnable object is not a thread by itself; it only describes the work to be done. To run the work in a new thread, the object is passed to the Thread constructor and start() is called.

public class Worker implements Runnable {
    // The thread's work goes here
    public void run() {
        String name = Thread.currentThread().getName();
        System.out.println("Worker running: " + name);
    }
    public static void main(String[] args) {
        // Start the thread
        Worker w = new Worker();
        Thread t = new Thread(w);
        t.start();
        System.out.println("main goes on");
    }
}

The slides show the output of one run like this:

main goes on
Worker running: Thread-0

main creates the Worker object and passes it to the constructor to create a Thread. t.start() opens the new thread and returns immediately. From then on there are two threads: main moves on to the next line and prints main goes on, while Thread-0 runs run() and prints its own name. The name was given automatically: the first unnamed thread the program creates is Thread-0.

Which of the two lines is printed first is not determined. As soon as start() returns, main continues; the scheduler decides when the new thread gets the processor. The program was run 40 times on JDK 21, and main goes on came first every time. The reverse order is also valid and can be seen on another machine or under load. The measured distribution varies with the machine and the load; the correctness of a program must never depend on any particular order.

Common mistake

Calling run() instead of start(). t.run() is an ordinary method call: the code runs in the caller's thread, that is, in main, and no new thread is opened. The program raises no error, but nothing runs in parallel. For this reason the mistake often goes unnoticed.

10.4.4Extending Thread

A thread can also be written by extending the Thread class. Thread already implements Runnable; the subclass only overrides run().

public class Worker2 extends Thread {
    // The thread's work goes here
    public void run() {
        String name = getName();   // inherited from Thread
        System.out.println("Worker running: " + name);
    }
    public static void main(String[] args) {
        // Create and start the thread
        Worker2 w = new Worker2();
        w.start();

10.4.5start() or run()?

The difference between start() and run() becomes visible when both are called one after the other on the same object.

public class StartVsRun {
    public static void main(String[] args)
            throws InterruptedException {
        Thread t = new Thread(() -> {
            String name = Thread.currentThread().getName();
            System.out.println("inside run(): " + name);
        });
        t.run();     // WRONG: main runs it
        t.start();   // RIGHT: a new thread
        t.join();
    }
}
inside run(): main
inside run(): Thread-0

The first line comes from t.run(). This call is an ordinary method call inside main; currentThread() returns main. The second line comes from t.start(): now run() runs in the new thread, Thread-0. The order of the output is fixed: execution does not reach the t.start() line until the t.run() call has finished. join() makes main wait until Thread-0 ends.

Example 10.2

A thread named T is created; its job is to print "run: " + Thread.currentThread().getName(). Then these lines run in order: t.run();, System.out.println("A " + t.getState());, t.start();, t.join();, and System.out.println("B " + t.getState());. What does the program print?

The call t.run() runs in main: run: main. The thread has still never been started: A NEW. After start(), run() runs on T's own stack: run: T. join() waits until T ends, so the last line is B TERMINATED. Because join() fixes the order, these four lines are the same in every run; the program was run five times and always gave the same output.

10.4.6The single-inheritance problem

Java allows a class to inherit from only one class. If the class that should run in a thread already extends another class, it cannot extend Thread. Writing class Worker extends Base, Thread is a compile-time error; javac reports '{' expected at the comma.

The solution lies in the Runnable interface. There is no limit on the number of interfaces a class can implement. The class extends Base, implements Runnable, and, if needed, keeps a field of type Thread inside.

class Base {
    public void greet() {
        System.out.println("Hello from Base");
    }
}
class Worker extends Base implements Runnable {
    private Thread thread;   // Thread as a field
    public void run() {
        String name = Thread.currentThread().getName();
        System.out.println("run(): " + name);
    }
    public void start() {
        thread = new Thread(this);
        thread.start();
    }
}
public class SingleInheritance {
    public static void main(String[] args) {
        Worker w = new Worker();
        w.greet();   // inherited from Base
        w.start();   // our own start()
    }
}
Hello from Base
run(): Thread-0

Worker both inherits the methods of Base and can run in a thread. w.greet() is the method that comes from Base, and it runs in main. w.start() is not the start() of Thread but a start() method that Worker defines itself. It hands itself to a Thread with new Thread(this) and starts it. this is of type Runnable, which is why the Thread constructor accepts it. The order of the two output lines is fixed: greet() finishes before the thread is started.

This pattern separates the work from the thread. Worker describes "what to do", and the Thread object describes "how to run it". The same Runnable object can later be handed to a thread pool as well. This is why Runnable is preferred in most cases.

10.5Managing and stopping threads

10.5.1sleep, join, and yield

Three basic methods control the flow of a thread.

sleep(ms)
Puts the running thread to sleep for a given time; during this time the thread is in the TIMED_WAITING state. A sleeping thread does not release the locks it holds.
join()
The calling thread waits until the target thread has finished. The form join(ms) waits at most ms milliseconds; when the time is up it returns even if the target has not finished.
yield()
A hint that the thread is willing to give up execution temporarily to another thread. The scheduler may ignore the hint, so no order is guaranteed with yield().

The following program shows why join() is needed. The calc thread adds the numbers from 1 to 1,000,000 and writes the result into a static field.

public class JoinDemo {
    static long result = 0;
    public static void main(String[] args)
            throws InterruptedException {
        Thread calc = new Thread(() -> {
            long sum = 0;
            for (int i = 1; i <= 1_000_000; i++) {
                sum += i;
            }
            result = sum;
        });
        calc.start();
        System.out.println("before join: " + result);
        calc.join();   // wait for calc to end
        System.out.println("after join : " + result);
    }
}
before join: 0
after join : 500000500000

Right after start(), main reads result. The computation has not yet finished at that point; main sees the initial value, 0. The program was run 30 times, and the first line was 0 every time. This is not a guarantee: a main that was slow to continue, or a very fast computation, could have shown the result on the first line as well. After join(), however, the situation is certain. The computation has finished, and the value it wrote is visible to main: 1 + 2 + … + 1,000,000 = 1,000,000 · 1,000,001 / 2 = 500,000,500,000.

It matters that the result is kept in a long. The total is about 5 · 1011, far above 2,147,483,647, the upper limit of int.

join() gives a second guarantee: everything the target thread wrote is visible to the thread that returns from join(). That is why it is not a problem that result is not volatile.

sleep and join can throw InterruptedException, a checked exception. Wherever they are called, they must therefore be either caught or declared with throws InterruptedException. Most examples in the slides declare main with throws InterruptedException. Inside a lambda, throws cannot be written, because run() declares no checked exceptions; there try-catch is mandatory.

Common mistake

Writing Thread.sleep(100); without try-catch in a method that does not declare throws. The compiler reports unreported exception InterruptedException; must be caught or declared to be thrown. The fix is a try-catch or adding throws InterruptedException to the method signature.

10.5.2Daemon threads

Definition 10.5

A daemon thread is a helper thread that does not prevent the JVM from shutting down. The JVM exits when all threads that are not daemon threads have finished; it does not wait for daemon threads to finish.

public class DaemonDemo {
    public static void main(String[] args)
            throws InterruptedException {
        Thread clock = new Thread(() -> {
            int s = 0;
            while (true) {
                System.out.println("tick " + s++);
                try {
                    Thread.sleep(300);
                } catch (InterruptedException e) {
                    return;
                }
            }
        });
        clock.setDaemon(true);   // BEFORE start()
        clock.start();
        Thread.sleep(1000);
        System.out.println("main done, JVM exiting");
    }
}
tick 0
tick 1
tick 2
tick 3
main done, JVM exiting

clock is in an infinite loop and prints a line every 300 ms. setDaemon(true) makes it a daemon thread. main sleeps for one second, prints its last line, and ends. Only a daemon thread is left, so the JVM exits; the loop of clock is cut off midway.

How many tick lines are printed? clock prints at about 0, 300, 600, and 900 ms; its fourth sleep would end at 1200 ms. main wakes up at 1000 ms. The expected output is therefore four tick lines. The program was run 10 times and printed four tick lines every time. Like any output that depends on timing, this is not guaranteed; the margin between 900 ms and 1000 ms is small.

setDaemon(true) must be called before start(). If it is called after the thread has started, IllegalThreadStateException is thrown; this behavior was tried on JDK 21. Daemon threads are meant for helper work such as logging, cache cleanup, or periodic checks. A job that writes to a file or must not be interrupted is not given to a daemon thread, because when the JVM exits, even finally blocks may be cut off without running.

10.5.3Stopping a thread

A thread stops when its run() method completes. The JVM exits in two cases: when System.exit() (internally Runtime.exit()) is called, or when all threads that are not daemon threads have finished.

The right way to stop a thread from outside is cooperation. The thread to be stopped checks a flag at regular intervals; when the flag is raised, it finishes its work cleanly and leaves run(). The flag is declared volatile so that a change made by another thread becomes visible. A second way is to send an interrupt request with interrupt().

Older versions of Java had a method called Thread.stop(). It killed the thread in the middle of its work. The locks the thread held were suddenly released, and the objects they protected were left half updated. For example, money might have been withdrawn from one account but not yet deposited into the other. The method stayed deprecated for a long time; since Java 20 it no longer works:

Thread t = new Thread(() -> { });
try {
    t.stop();
} catch (UnsupportedOperationException e) {
    System.out.println("stop(): not supported");
}
stop(): not supported

On JDK 21, stop() always throws UnsupportedOperationException. In the same experiment, suspend() and resume() threw the same exception.

class Worker extends Thread {

finish() only raises the flag; it does not stop the thread by force. The worker checks the condition !flag at the start of every iteration. What would happen if the flag were not volatile? The worker could keep the value it first read in a cache or a register and never see the change. In this example, the sleep call in the loop often hides the problem; in an empty loop, the thread could really get stuck.

10.5.5Stopping through a reference

A second form of cooperative stopping is to keep a reference to the thread itself instead of a flag.

class Worker implements Runnable {
    private volatile Thread thread;
    public void start() {
        thread = new Thread(this);
        thread.start();
    }
    public void finish() { thread = null; }
    public void run() {
        Thread me = Thread.currentThread();
        while (thread == me) {   // ... work ...
        }
        System.out.println("run() done");
    }
}
public class ReferenceStop {
    public static void main(String[] args) throws Exception {
        Worker w = new Worker();
        w.start();
        Thread.sleep(200);
        w.finish();
        Thread.sleep(200);
        System.out.println("main: done");
    }
}
run() done
main: done

The class implements Runnable and keeps the running Thread object in a volatile field. The loop continues as long as the field still points to its own thread. The comparison with Thread.currentThread() checks this. finish() sets the field to null; the condition fails and run() ends. main stops the worker after 200 ms, waits another 200 ms, and prints its last line. In ten runs, the output was always these two lines.

One detail: currentThread() is a static method of Thread. In a class that does not extend Thread, it must be written with the Thread. prefix. If the prefix is forgotten, the compiler reports cannot find symbol. Because the body of the loop is empty, the thread keeps one core completely busy for these 200 ms. In a real program, the body does some work or sleeps for a short time.

10.6Synchronization

10.6.1Why the order breaks

When several threads work with the same data, performing operations in the right order is hard for three reasons.

Speed is unpredictable
The speed and frequency at which each thread runs vary. Operating systems may ignore priorities, so priority cannot be trusted for ordering.
Values can go stale
After one thread reads a variable, another can update the value. The first keeps working with an out-of-date value.
Instructions can be reordered
The compiler, the JIT (just-in-time) compiler, and the processor may change the order of instructions for speed. In a single thread this goes unnoticed; with more than one, it causes unexpected behavior.

If several threads access shared, changing data, the access must be synchronized. Otherwise the result depends on the order in which the threads run.

Definition 10.6

A race condition occurs when the result of a program depends on the order in which threads run. Synchronization is the coordination of the threads' access to shared data so that the result no longer depends on that order.

10.6.2Race conditions

The simplest race example is two threads incrementing the same counter. Each thread does counter++ 100,000 times; the expected result is 200,000.

public class RaceCondition {
    static int counter = 0;   // shared data
    public static void main(String[] args)
            throws InterruptedException {
        Runnable inc = () -> {
            for (int i = 0; i < 100_000; i++) {
                counter++;   // read, add 1, write: NOT atomic
            }
        };
        Thread t1 = new Thread(inc);
        Thread t2 = new Thread(inc);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Expected: 200000");
        System.out.println("Actual  : " + counter);
    }
}

In the source code, counter++ looks like a single operation. On the processor it is three steps: read the value from memory, add one, write it back to memory.

Example 10.4

The balance of an account is 500. T1 calls deposit(100) and T2 calls withdraw(30); the methods consist only of the lines balance += m and balance -= m and are not synchronized. Suppose the order is: T1 reads, T2 reads, T2 subtracts and writes, T1 adds and writes. What is the balance in the end, and what should it have been?

The correct result is 500 + 100 − 30 = 570. T1 reads 500. T2 also reads 500, subtracts 30, and writes 470. T1 adds 100 to the stale 500 and writes 600. The result is 600: the withdrawal by T2 is lost. If the last two writes had happened in the opposite order, the result would be 470, and this time the deposit would be lost. The solution is to protect both methods with the lock of the same object (synchronized).

10.6.4Synchronization options

Java offers many tools for coordinating threads. Each of them solves a different problem:

  • join(): waiting for a thread to finish.
  • synchronized: mutual exclusion with an object's monitor lock.
  • Lock objects (ReentrantLock, ReadWriteLock): explicit locking.
  • Barrier, semaphore, exchanger, countdown latch: CyclicBarrier, Semaphore, Exchanger, CountDownLatch.
  • volatile variables: making reads and writes visible to all threads.
  • Atomic objects: indivisible operations such as those of AtomicInteger.

There are also tools that look like synchronization but are not: priorities, putting a thread to sleep with sleep, giving way with yield, and timers. They do not guarantee order. Code written with the thought "I'll wait a bit, the other one will have finished" will one day produce a wrong result at a moment when the other one has not finished.

10.6.5synchronized and monitors

Definition 10.7

A monitor is an internal lock and waiting mechanism attached to every Java object that can be locked and unlocked. Only one thread can hold a monitor at a time. The synchronized keyword acquires the monitor of an object; when the block ends, the monitor is released automatically.

The monitor works like this. While t1 holds an object's monitor, if t2 also wants the same monitor, t2 waits; its state is BLOCKED. When the monitor is released, the waiting threads compete and only one of them gets the monitor. The monitor is released both when the block ends normally and when it is left through an exception. In this way mutual exclusion is achieved and data integrity is preserved.

Definition 10.8

A critical section is a piece of code that accesses shared data and must be executed by only one thread at a time. Mutual exclusion means that only one thread is in the critical section at a time.

The syntax is short. The object whose monitor will be used is written in parentheses:

synchronized (o) {
    // we hold o's monitor here
}

The counter increment in the race example is protected by such a block:

Runnable r = () -> {
    for (int i = 0; i < 50_000; i++) {
        synchronized (o) {   // take o's monitor
            shared++;
        }                    // monitor released
    }
};

When two threads run this task 50,000 times each, the result is 100000 every time. The program was run 10 times and always gave this value. Every shared++ is done while the monitor is held; the other thread cannot enter the block until one thread has finished its read–add–write steps.

The operation of the monitor goes step by step like this:

// t1 and t2 run the same code
synchronized (o) {
    shared++;     // critical section
}
  1. t1 and t2 reach the line synchronized (o) at the same time; the monitor is free.
  2. t1 wins and acquires the monitor. t2 waits in the entry set, BLOCKED.
  3. t1 leaves the block; the monitor is released automatically. The waiting threads compete.
  4. t2 acquires the monitor and enters the critical section.
  5. t2 leaves too. shared++ has been done twice, without interleaving.

Which thread enters first is not determined. What matters is that the critical section is never executed by two threads at the same time. For monitor locking to work correctly, all threads must lock the same object. If each thread takes the monitor of its own object, there is no protection at all.

10.6.6Synchronized methods

synchronized can also be written in front of a method. This is the same as wrapping the whole body of the method in a synchronized block.

class C {
    synchronized void p() { ... }
    static synchronized void q() { ... }
    //...
}

The equivalent of the definition above is:

class C {
    void p() { synchronized (this) { ... } }
    static void q() { synchronized (C.class) { ... } }
    //...
}

Which object is locked depends on the kind of method:

  • Instance method: the monitor of the this object is locked.
  • static method: since there is no instance, the monitor of the class's C.class object is locked.

For this reason, a static synchronized method and an instance synchronized method do not block each other; they use different locks. This behavior was tried on JDK 21: while another thread held the monitor of C.class for 500 ms, x.p() ran without waiting, whereas C.q() waited until the monitor was released. When a body is written in place of ... in the code from the slides (for example n++, s++), both forms compile and behave the same.

The block form has an advantage: only the lines that really need it are locked. If only two lines of a long method touch shared data, locking the whole method makes the other threads wait for nothing.

Example 10.5

The class Counter implements Runnable; it has a static int total field, and its run() method is synchronized. run() increments total 100,000 times. Two threads run two separate objects with new Thread(new Counter()). Why can the total come out smaller than 200,000?

Each thread takes the monitor of its own object (this). Two different locks do not block each other, while the data they are supposed to protect is the shared static total. The program was run ten times, and the totals found ranged from 111,143 to 169,427; none was 200,000. The fix is for everyone to use the same lock: the increment in the loop goes into a synchronized (Counter.class) block. The corrected program gave 200000 in all five runs. AtomicInteger is another solution.

10.6.7Preventing the race

The counter in the race example is fixed by moving it into a class whose methods are synchronized.

class Counter {
    private int value = 0;
    public synchronized void increment() { value++; }
    public synchronized int getValue() { return value; }
}

public class SyncCounter {
    public static void main(String[] args)
            throws InterruptedException {
        Counter counter = new Counter();
        Runnable task = () -> {
            for (int i = 0; i < 100_000; i++) {
                counter.increment();
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Result: " + counter.getValue());
    }
}
Result: 200000

increment() is now synchronized: the read–add–write steps are performed without being split. The program was run 10 times and printed Result: 200000 every time. The reading method getValue() is synchronized too. At first sight this may look unnecessary, because reading an int is a single step anyway. But if the read is not synchronized, there is no guarantee that the reading thread sees the current value. What was written before a lock is released becomes visible to the thread that acquires the same lock afterward.

Synchronization has a cost. Threads enter the critical section one at a time and wait for each other; the program becomes somewhat slower. That is why only shared data is protected. Local variables that only a single thread uses need no lock.

10.6.8Mutual exclusion: a priority queue

Synchronized methods are the shortest way to make a whole data structure thread-safe. The following priority queue returns the smallest element on each call. All methods use the same monitor, this.

class MinQueue {
    private int[] data;
    private int size;
    public MinQueue(int n) { data = new int[n]; }
    public synchronized void add(int o) {
        if (size == data.length)
            throw new HeapFullException();
        data[size++] = o;
    }
    public synchronized int remove() {   // the smallest
        int min = 0;
        for (int i = 1; i < size; i++) {
            if (data[i] < data[min]) min = i;
        }
        int result = data[min];
        data[min] = data[--size];
        return result;
    }
    public synchronized String toString() {
        return Arrays.toString(Arrays.copyOf(data, size));
    }
}

HeapFullException is not defined in the slides; here it was written as a class that extends RuntimeException and carries the message "Queue full". The queue is used from a single thread as follows:

Making toString() synchronized as well prevents printing a half-modified array.

10.7Visibility

10.7.1volatile fields

A race condition arises when two threads write at the same time. There is a subtler problem too: a value written by one thread may never be seen by another. Let us describe it with an intuitive model. For speed, processors keep values in caches close to the core or in registers. A compiler may also read a variable it believes does not change in a loop just once and keep it in a register. In that case, even if a thread on another core writes the new value to main memory, the first thread keeps working with the old value.

Definition 10.9

In a field declared with the volatile keyword, every read sees the last write to that field: a volatile write happens-before every subsequent read of the same field. In the intuitive model, this can be thought of as the value being read from main memory on every read and made visible to all threads immediately on every write. volatile guarantees visibility; it does not make multi-step operations atomic.

By the rules of the Java language, a single read or write of any variable other than long and double is already atomic. A 64-bit long or double value, however, may be written as two 32-bit halves on some JVMs. For volatile long and volatile double fields, this half-write cannot happen; reads and writes become atomic.

For a simple shared flag, volatile is enough; neither synchronized nor a lock is needed. But only a single read or a single write is atomic. Read–modify–write operations such as x++ are not atomic on a volatile field either.

10.7.2The visibility problem

public class VisibilityProblem {
    static boolean stop = false;   // NOT volatile!
    public static void main(String[] args)
            throws InterruptedException {
        Thread t = new Thread(() -> {
            long laps = 0;
            while (!stop) {
                laps++;
            }
            System.out.println("thread stopped");
        });
        t.setDaemon(true);
        t.start();
        Thread.sleep(500);
        stop = true;
        System.out.println("main: stop = true");
        t.join(2000);   // wait at most 2 s
        boolean alive = t.isAlive();
        System.out.println("still running? " + alive);
    }
}

The thread checks stop in an empty loop. After 500 ms, main sets stop to true and waits at most two seconds. Without volatile, the output in the slides is:

main: stop = true
still running? true

The thread never saw the change and is still running after two seconds. The cause is the JIT compiler. After the loop has run a few thousand times, the JIT translates it to machine code. Because nothing inside the loop changes stop, stop is read once and the loop runs like while (true). This transformation is entirely correct for a single-threaded program, and the Java rules allow it for a field that is not volatile.

The program was run 10 times on JDK 21, and the thread failed to see the change every time; the output was like the one in the slides. When the field was declared static volatile boolean stop, the thread stopped in all ten runs:

main: stop = true
thread stopped
still running? false

In one of these runs, the line thread stopped was printed before main: stop = true. This is not a contradiction: main first changes the field and then prints; the thread can see the change between these two steps and print its own line first.

The outcome can vary with the JVM, the processor, and when the JIT kicks in. On one machine the problem may never show up, on another it shows up every time. Correctness is not left to this kind of luck: a flag changed by another thread is always declared volatile. That is also the purpose of the setDaemon(true) call in the example: the stuck thread must not prevent the program from exiting.

10.7.4The Java Memory Model and happens-before

When does one thread see a value written by another? The precise answer to this question is given by the Java Memory Model (JMM). The programmer does not have to think about processor caches and memory barriers; instead, they reason with happens-before relationships.

Definition 10.10

If operation A happens-before operation B, everything A wrote is guaranteed to be visible in B. The happens-before relation is transitive: if A happens-before B and B happens-before C, then A happens-before C.

In the synchronized counter, getValue() being synchronized as well brings the lock rule into play. In the flag example, the volatile rule applies. If none of these relationships is established, there is no visibility guarantee between two threads.

There is also a performance problem that must not be confused with visibility: false sharing. Independent variables of different threads sit on the same cache line (usually 64 bytes), and if they are updated often, the cores keep pulling the line away from each other. The result is not wrong, but the program slows down. This is a performance problem, not a correctness problem.

10.8Explicit locks and deadlock

10.8.1The Lock interface

synchronized is simple and safe, but it is not flexible. A thread cannot give up while waiting for a lock, the wait cannot be limited by a timeout, and a waiting thread cannot be interrupted. For complex synchronization scenarios, the java.util.concurrent.locks package offers explicit locks.

Definition 10.11

An explicit lock is an object that implements the Lock interface. The lock is acquired with lock() and released with unlock(); the programmer calls both. ReentrantLock and ReentrantReadWriteLock are the main implementations of this interface.

Explicit locks do three things that synchronized cannot: try without waiting (tryLock()), wait for a limited time (tryLock(time)), and wait in an interruptible way (lockInterruptibly()). In return, the responsibility is the programmer's: the lock must not be forgotten. To use them, import java.util.concurrent.locks.*.

public class LockDemo {
    private final Lock lock = new ReentrantLock();
    private int counter = 0;
    public void work() {
        lock.lock();
        try {
            // critical section
            counter++;
        } finally {
            lock.unlock();
        }
    }
    public static void main(String[] args)
            throws InterruptedException {
        LockDemo o = new LockDemo();
        Runnable r = () -> {
            for (int i = 0; i < 100_000; i++) o.work();
        };
        Thread a = new Thread(r), b = new Thread(r);
        a.start(); b.start();
        a.join(); b.join();
        System.out.println("Result: " + o.counter);
    }
}
Result: 200000

The program is the race example rewritten with an explicit lock. Every counter++ is done while the lock is held. The program was run 10 times and printed Result: 200000 every time. The lock object is in a final field; all threads use the same lock.

10.8.2Unlocking in a finally block

The correct usage pattern for an explicit lock is always the same:

public void work() {
    Lock lock = ...;
    lock.lock();
    try {
        // access the guarded resource
    } finally {
        lock.unlock();
    }
}

lock() is called right before the try. unlock() is inside the finally. Even if an exception occurs in the critical section, finally runs and the lock is released. There is also a reason why lock() is written before the try and not inside it. If lock() fails, we do not want finally to try to release a lock that was never acquired.

lock.lock();
doWork();       // if this throws...
lock.unlock();  // ...we never get here

In this wrong form, if doWork() throws an exception, the unlock() line is never reached. The lock stays locked, and every thread that wants it waits forever. synchronized has no such problem: even if the block is left through an exception, the monitor is released automatically.

Example 10.6

The method divide(a, b) acquires the lock, prints a / b, and releases the lock; there is no finally. t1 calls divide(10, 0); after t1 finishes, t2 calls divide(10, 2). What is seen on the screen, and in what state does t2 remain?

In t1, 10 / 0 throws ArithmeticException. t1 terminates, but because unlock() is never reached, the lock stays locked. Only the stack trace of t1 appears on the screen; 5 is never printed. t2 waits in lock() forever. The test program was made to finish without hanging by turning t2 into a daemon thread and printing its state after 300 ms; in all three runs the state was WAITING. Because waiting on a Lock is not a monitor wait, the state is WAITING, not BLOCKED. When unlock() was moved into finally, t2 printed 5 and finished.

10.8.3tryLock()

tryLock() tries to acquire the lock without waiting. If the lock is free, it takes it and returns true; if it is held, it returns false without waiting at all. The form tryLock(3, TimeUnit.SECONDS) waits at most three seconds. Because the timed wait can be interrupted, InterruptedException must be declared.

static void work()
        throws InterruptedException {
    if (lock.tryLock()) {
        // got it
        try { System.out.println("1: acquired"); }
        finally { lock.unlock(); }
    } else {
        // didn't get it; do something else
        System.out.println("1: not acquired");
    }
    if (lock.tryLock(3, TimeUnit.SECONDS)) {
        try { System.out.println("2: acquired"); }
        finally { lock.unlock(); }
    } else {
        // not acquired within 3 seconds
        System.out.println("2: not acquired");
    }
}

10.8.4ReentrantLock and reentrancy

The name ReentrantLock means "a lock that allows re-entry". If the thread that holds the lock asks for the same lock once more, it does not wait; only a counter increases. The lock is really released when the counter drops back to 0.

Definition 10.12

A reentrant lock is a lock that lets the thread holding it acquire it again without waiting. The lock stores an owner and a hold count; each lock() increases the count by one, and each unlock() decreases it by one.

Nested critical sections with more than one lock can also be entered:

ReentrantLock lock1 = new ReentrantLock();
// true: a fair lock
ReentrantLock lock2 = new ReentrantLock(true);
// ...
lock1.lock();
try {
    // enter the critical section
    lock2.lock();
    try {
        // enter the nested section
        System.out.println("both locks acquired");
    } finally {  lock2.unlock();  }
} finally {  lock1.unlock();  }
System.out.println("fair? " + lock2.isFair());
both locks acquired
fair? true

new ReentrantLock(true) creates a fair lock: when the lock becomes free, it is given to the thread that has waited longest. The no-argument constructor gives a non-fair lock; lock1.isFair() returns false. A non-fair lock is faster, but it may let a thread keep waiting for a long time. When two locks are acquired in a nested way, the release order is the reverse of the acquisition order: first lock2, then lock1.

synchronized is reentrant too. A synchronized method can call another synchronized method of the same object; the thread does not wait for a monitor it already holds. Without reentrancy, such a call would lock the thread against itself.

10.8.5ReadWriteLock

Many data structures are read often and written rarely: a settings table, a cache, a dictionary. Because reads do not change the data, there is no need for them to block each other. ReadWriteLock handles this situation with two separate locks.

Read lock
More than one thread can read the data at the same time; they do not block each other while reading.
Write lock
While one thread writes, both reading and writing by the others are blocked; the write is safe and atomic.
private final Map<String, String> table =
        new HashMap<>();
private final ReadWriteLock lock =
        new ReentrantReadWriteLock();

public String get(String key) {
    lock.readLock().lock();   // lock for reading
    try {
        return table.get(key);   // read the data
    } finally {
        lock.readLock().unlock();
    }
}
public void put(String key, String value) {
    lock.writeLock().lock();  // lock for writing
    try {
        table.put(key, value);   // write the data
    } finally {
        lock.writeLock().unlock();
    }
}

10.8.8Preventing deadlock

The most effective remedy for deadlock is a single change: all threads acquire locks in the same order.

Thread t1 = new Thread(() -> useBoth(a, b, "T1"));
Thread t2 = new Thread(() -> useBoth(a, b, "T2"));
T1 done
T2 done
TERMINATED TERMINATED
Deadlocked: 0

Everyone acquires a first and then b. T2 waits for a and never holds b; no cycle can form. When T1 finishes, it releases the locks, T2 acquires them, and it finishes too. The program was run 10 times, and the output was these four lines every time.

There are four ways to prevent deadlock:

Fixed lock order
All threads acquire locks in the same order; for example, by the ID number of the objects.
Timed attempt
If tryLock(time) cannot acquire the lock, the thread releases the locks it holds and tries again later.
Short critical sections
Do not ask for another lock while holding one, and do not do long work while holding a lock.
Diagnosis
The JDK's jstack tool or ThreadMXBean.findDeadlockedThreads() shows the deadlocked threads and the locks they hold.
Common mistake

Ignoring deadlock because "it never happens anyway". In a version without the sleep, if T1 takes a then b and T2 takes b then a, in most runs one of them acquires both locks and leaves, and the problem is not visible. For these notes, two threads each ran these two blocks 1,000 times, and the experiment was repeated at most 200 times. In all three separate runs, the deadlock occurred before this limit was reached. When a deadlock shows up varies from run to run; if its probability is not zero, it will happen sooner or later.

10.8.9Livelock and starvation

Deadlock is not the only progress problem. It has two relatives.

Livelock
The threads are not blocked; they keep changing state by constantly "giving way" to each other, but none of them can finish its work. It is like two people meeting in a narrow corridor who step to the same side at the same time. Example: two threads release the lock they hold when tryLock fails, try again at the same moment, and always collide.
Starvation
A thread cannot reach a resource for a long time, or at all: others always grab the lock, or long critical sections keep it waiting. Priority values (setPriority) are not a reliable way to solve this problem.
Lock lock = new ReentrantLock(true);  // fair
if (lock.tryLock(50, TimeUnit.MILLISECONDS)) {
    try { /* work */ }
    finally { lock.unlock(); }
} else {
    Thread.sleep(rnd.nextInt(20)); // random
}

The remedies are short. A fair lock gives the lock to the thread that has waited longest; the price is slightly slower operation. Waiting a random time before retrying breaks the symmetry of the two threads and prevents livelock; in the code, rnd.nextInt(20) does this job. Keeping critical sections short also ensures that everyone gets a turn.

10.9Condition synchronization

10.9.1Waiting for a condition

Mutual exclusion prevents two threads from entering the critical section at the same time. In some cases that is not enough: when a thread enters the critical section, the condition suitable for its work may not yet hold. Consider a shared queue. A consumer takes items from the queue, but if the queue is empty, there is nothing to take. A producer adds items, but if the queue is full, there is no room.

Definition 10.14

Condition synchronization ensures that a shared resource is accessed only when a certain condition holds. A thread waits until the condition holds; the thread that changes the condition wakes the waiting one.

Updating the queue safely requires the object's lock. It is also necessary to wait until the condition holds. But one cannot wait while holding the lock. If a consumer holds the lock while waiting for an item to arrive in the queue, the producer can never acquire the lock and cannot add an item; everyone gets stuck.

The first solution that comes to mind is to check the condition continuously in a loop:

while (queue.isEmpty()) {
    // burns CPU; if the lock is held,
    // the producer can never add
}

This busy waiting is wrong in two ways. The loop keeps one core completely busy for nothing. And if the lock is held, the producer can never add, and the loop goes on forever. Java offers three correct solutions:

  1. Object.wait() and Object.notify() / notifyAll().
  2. The Condition interface, used together with Lock.
  3. Synchronizer objects (CountDownLatch, Semaphore, …) and the ready-made BlockingQueue classes.

10.9.2wait() and notify()

Two sets are attached to the monitor of every object. The entry set holds the threads that want to acquire the monitor. The wait set holds the threads that are waiting for a condition to change.

  • The thread that holds the lock calls wait(): it enters the wait set, releases the lock, and blocks.
  • notify() wakes one thread from the wait set, and notifyAll() wakes all of them. The form wait(ms) also returns when the time is up.
  • The woken thread must first reacquire the lock. Once it has the lock, it returns from wait() and continues where it left off.

There are two rules. First, wait and notify are called only inside a synchronized block or method of the same object. Otherwise JDK 21 throws java.lang.IllegalMonitorStateException: current thread is not owner. Second, the condition is checked with while, not if. By the time the woken thread reacquires the lock, another thread may have invalidated the condition again. Java also allows a thread to wake up without any notify, a spurious wakeup. The while loop rechecks the condition on every wakeup.

Example 10.7

Inside a synchronized block, what is the difference between lock.wait() and Thread.sleep(1000)?

wait() releases the monitor and enters the wait set; when it is woken by notify or notifyAll, it reacquires the lock and continues. sleep() has nothing to do with the lock: it sleeps while holding it, and during that time everyone who wants the lock waits BLOCKED. Holding the lock while waiting for a condition keeps out the thread that would change the condition; that is why wait() is used for waiting on a condition.

10.9.3Blocking queues

The classic example of condition synchronization is the producer–consumer problem. Producer threads put items into a shared buffer, and consumer threads take them. If the buffer is full, the producer waits; if it is empty, the consumer waits. The following BlockingQueue class implements this buffer with a fixed-size array.

class BlockingQueue {
    private Object[] data;
    private int head = 0;
    private int tail = 0;
    private int count = 0;
    public BlockingQueue(int capacity) {
        if (capacity <= 0)
            throw new IllegalArgumentException(
                    "capacity must be > 0");
        data = new Object[capacity];
    }
    public synchronized int getSize() {
        return count;
    }
    public synchronized void add(Object item)
            throws InterruptedException {
        while (count == data.length) {
            wait();
        }
        data[tail] = item;
        tail = (tail + 1) % data.length;
        count++;
        notifyAll();
    }
    public synchronized Object remove()
            throws InterruptedException {
        while (count == 0) {
            wait();
        }
        Object item = data[head];
        data[head] = null;
        head = (head + 1) % data.length;
        count--;
        notifyAll();
        return item;
    }
}

The array is used circularly. head is the position of the element to be removed, and tail is the position where the next element will be added. On every add and remove the position advances by one; % data.length wraps it around at the end. count is the number of elements in the queue. remove sets the slot it read to null; this way the queue no longer holds an object that does not belong to it, and the garbage collector can reclaim it. The constructor rejects a capacity of 0 or less with IllegalArgumentException; in a queue of capacity 0, add would wait forever.

add waits when the queue is full (count == data.length); remove waits when the queue is empty. After every add or remove, notifyAll() wakes the waiting threads. Here notifyAll() is a deliberate choice. Both producers and consumers can be waiting in the same wait set. If notify() woke the wrong kind of thread, that thread would find the condition unsatisfied and wait again, and the right thread might never wake up.

10.9.5The Condition interface

wait and notify belong to the world of monitors. In a class that uses Lock, the Condition interface does the same job.

Definition 10.15

A Condition is a wait set attached to a Lock; it is created with lock.newCondition(). await() releases the lock and suspends the thread; signal() wakes one waiting thread, and signalAll() wakes all of them.

The main advantage of Condition is that several conditions can be attached to one lock. Producers and consumers wait in separate sets; each thread wakes only the relevant one.

class BlockingQueue {
    private final Lock lock = new ReentrantLock();
    private final Condition notFull =
            lock.newCondition();
    private final Condition notEmpty =
            lock.newCondition();
    private Object[] data;
    private int head = 0;
    private int tail = 0;
    private int count = 0;
    public BlockingQueue(int capacity) {
        if (capacity <= 0)
            throw new IllegalArgumentException(
                    "capacity must be > 0");
        data = new Object[capacity];
    }
    // add() and remove()
}
public void add(Object item)
        throws InterruptedException {
    lock.lock();
    try {
        while (count == data.length)
            notFull.await();
        data[tail] = item;
        tail = (tail + 1) % data.length;
        count++;
        notEmpty.signal();
    } finally {
        lock.unlock();
    }
}
public Object remove()
        throws InterruptedException {
    lock.lock();
    try {
        while (count == 0)
            notEmpty.await();
        Object item = data[head];
        data[head] = null;
        head = (head + 1) % data.length;
        count--;
        notFull.signal();
        return item;
    } finally {
        lock.unlock();
    }
}

The thread that adds signals only the notEmpty condition, and the thread that removes signals only notFull. Only consumers wait on notEmpty, and only producers wait on notFull. Because there are no unnecessary wakeups, signal() is enough in place of signalAll(). The lock is released in finally; await, like wait, sits inside a while loop.

10.10Synchronizer objects

10.10.1Four ready-made tools

The java.util.concurrent package offers ready-made classes for common forms of coordination between threads. Each is a solution to a particular scenario.

CountDownLatch
"Wait until N events have happened, then go on." Waiting threads stay put until the counter reaches zero. It is single-use.
CyclicBarrier
"Let all of us reach the meeting point, then continue together." It can be reused.
Exchanger
Two threads meet at a point and swap data.
Semaphore
N permits: at most N threads can enter the resource at the same time.

10.10.2CountDownLatch

A countdown latch coordinates threads that wait for a certain number of events. An initial count is given to the constructor. Each countDown() decreases the counter by one. A thread that calls await() waits until the counter reaches 0.

public static void main(String[] args)
        throws Exception {
    int count = 3;
    CountDownLatch latch = new CountDownLatch(count);
    for (int i = 0; i < count; i++) {
        int no = i + 1;   // copy for the lambda
        new Thread(() -> {
            System.out.println(no + ": event happened");
            // count down when the event happens
            latch.countDown();
        }).start();
    }
    // wait for the threads to finish
    latch.await();
    System.out.println("All events done!");
}

The line int no = i + 1; in the loop is important. A lambda can access only local variables that are final or effectively final (assigned once and never changed). The loop variable i changes in every iteration and cannot be used directly; javac reports this error: local variables referenced from a lambda expression must be final or effectively final. no, which is created anew in every iteration, never changes.

10.11Other tools

10.11.1Atomic classes

Using a lock to protect a single counter is like using a sledgehammer to crack a nut. The java.util.concurrent.atomic package offers lock-free, thread-safe counters.

Definition 10.17

An atomic operation is an operation that completes in a single step, without being split; no other thread can get into the middle of it. Classes such as AtomicInteger, AtomicLong, and AtomicBoolean offer atomic operations on their values.

public class AtomicCounter {
    public static void main(String[] args)
            throws InterruptedException {

        Runnable r = () -> {
            for (int i = 0; i < 100_000; i++) {
                counter.incrementAndGet();   // atomic ++counter

        Thread a = new Thread(r), b = new Thread(r);
        a.start(); b.start();
        a.join(); b.join();

        boolean b1 = counter.compareAndSet(200000, 0);
        System.out.println(b1 + " " + counter.get());
        boolean b2 = counter.compareAndSet(5, 10);
        System.out.println(b2 + " " + counter.get());

Definition 10.18

Compare-and-set (CAS): compareAndSet(expected, new) writes new and returns true if the value is still expected. If the value is different, it leaves it alone and returns false. The comparison and the write are a single atomic operation; the processor does this with one instruction.

Roughly speaking, an atomic object is the combination of a volatile field and an atomic compareAndSet operation. volatile provides visibility, and CAS provides indivisibility.

In steps 2 and 3, T1 and T2 read the current value; both see 5. Because there is no lock, both carry on. In step 4, both compute 6 locally. With an ordinary counter++, both would write 6 and one increment would be lost.

In step 5, T1 calls compareAndSet(5, 6). Because the value is still 5, 6 is written and true is returned. In step 6, T2 also calls compareAndSet(5, 6). The value is now 6, not the expected 5; nothing is written and false is returned. T2 does not lose its increment; it goes back around the loop: in step 7 it rereads the current value, 6, and computes 7. In step 9 the CAS succeeds this time: counter = 7. Both increments are counted. Nobody waited for a lock; only T2 went around the loop once more.

When this method was called 100,000 times by each of two threads, the counter reached 5 + 200,000 = 200,005; the result was the same in all five runs. The advantage of the lock-free method is that threads never sleep. When contention is low, it is faster than a lock; under very heavy contention, threads spin for nothing.

10.11.3Interruption

The second cooperative way to stop a thread is interruption. t.interrupt() sends an interrupt request to t; it does not stop t by force.

Definition 10.19

An interrupt is a request sent to a thread to "drop what you are doing". interrupt() sets the target's interrupt flag. If the target is waiting in sleep, wait, or join, the wait is cut short immediately and InterruptedException is thrown; at that moment the flag is cleared.

There are two ways to read the flag. Thread.interrupted() is a static method; it reads and clears the flag of the running thread. isInterrupted() is an instance method and only reads the flag.

public class InterruptDemo {
    public static void main(String[] args)
            throws InterruptedException {
        Thread worker = new Thread(() -> {
            try {
                while (!Thread.interrupted()) {
                    // the thread's work
                    System.out.println("working...");
                    Thread.sleep(400);

            } catch (InterruptedException e) {
                System.out.println("Thread cancelled!");
            }
        });
        worker.start();
        Thread.sleep(1000);
        worker.interrupt();   // interrupt it in sleep()
        worker.join();
        System.out.println("main: done");
    }
}

Common mistake

Swallowing InterruptedException with an empty catch. When the exception is thrown, the flag has been cleared. If the catch does nothing, the interrupt request is lost and the thread keeps running. The right thing is to leave the loop or to pass the request upward by setting the flag again inside the catch with Thread.currentThread().interrupt().

10.11.4Suspension

In old versions of Java, suspend() froze a thread and resume() continued it. Because suspend() froze the thread together with the locks it held, it was very prone to deadlock; on JDK 21, both methods throw UnsupportedOperationException. The same job is done safely with wait() and notifyAll().

class Task implements Runnable {
    private boolean paused = false;
    public synchronized void pause() {
        paused = true;
    }
    public synchronized void resume() {
        paused = false;
        notifyAll();   // wake the waiter
    }
    public void run() {
        try {
            for (int i = 1; i <= 5; i++) {
                synchronized (this) {
                    while (paused) wait();
                }
                System.out.println("step " + i);
                Thread.sleep(200);
            }
        } catch (InterruptedException e) { }
    }
}

At the start of each step, the task checks the paused flag under the lock. If the flag is raised, it waits with wait(). resume() lowers the flag and wakes the waiting thread with notifyAll(). The flag is protected by the same monitor in both methods; it does not also need to be volatile.

10.11.5ThreadLocal

The surest remedy for a race is not to share. ThreadLocal gives each thread its own copy of the same variable.

static final ThreadLocal<String> value =
        new ThreadLocal<>();
public static void main(String[] args)
        throws InterruptedException {
    Thread thread1 = new Thread(() -> {
        // first thread
        value.set("Value 1");
        System.out.println("thread1: " + value.get());
    });
    Thread thread2 = new Thread(() -> {
        // second thread
        value.set("Value 2");
        System.out.println("thread2: " + value.get());
    });
    thread1.start();
    thread2.start();
    thread1.join();
    thread2.join();
    System.out.println("main: " + value.get());
thread1: Value 1
thread2: Value 2
main: null

Both threads write to the same value object, but each writes to and reads from its own copy. The copies are independent of each other. Because main never called set, its own copy is empty and it sees null. The order of the first two lines varies: in 40 runs, thread1 printed first 20 times and thread2 20 times. The line main: null was always last.

To give each thread a separate initial value, write ThreadLocal.withInitial(() -> 0) (Java 8+) or override the initialValue() method. A typical use is to give each thread its own copy of an object that is not thread-safe, such as a date formatter.

Example 10.11

ThreadLocal<Integer> t = ThreadLocal.withInitial(() -> 0);, then t.set(5) in main. A new thread x does t.set(t.get() + 1) and prints "x: " + t.get(); main waits for x and prints "main: " + t.get(). What is the output?

The 5 in main does not pass to x. On its first get(), x starts with the 0 from withInitial and makes it 1: x: 1. What x wrote does not affect the copy of main either: main: 5.

10.11.6Thread pools

Starting a new thread for every task creates two problems. Creating a thread is not cheap: a stack is allocated and an operating-system record is made. More importantly, the number grows without control: if a thousand requests arrive, a thousand threads are started.

Definition 10.20

A thread pool is a structure that creates the threads to be used in advance and distributes tasks to them. Tasks are submitted to the pool (submit); an idle worker takes a task and, when finished, moves on to the next one. If there is no idle worker, the task waits in the queue.

A pool reuses threads and limits their number. In Java, pools are managed through the ExecutorService interface. Executors.newFixedThreadPool(n) gives a ready-made pool with a fixed n workers. When detailed configuration is needed, the ThreadPoolExecutor class, which creates and manages the pool, is used directly.

public class PoolDemo {
    static void task(int no) {
        String name = Thread.currentThread().getName();
        System.out.println("Task " + no + " -> " + name);
    }
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);
        for (int i = 1; i <= 4; i++) {
            int no = i;
            pool.submit(() -> task(no));
        }
        // Callable: a task that returns a value
        Future<Integer> f = pool.submit(() -> 6 * 7);
        System.out.println("Callable result: " + f.get());
        pool.shutdown();   // accept no new tasks
        pool.awaitTermination(5, TimeUnit.SECONDS);
        System.out.println("Pool shut down");
    }
}

Task 2 -> pool-1-thread-2
Task 3 -> pool-1-thread-2
Task 4 -> pool-1-thread-2

The four tasks are distributed over the two workers. Which worker gets which task and the order of the lines vary; in a second run, the slides give the last two task lines as Task 3 -> pool-1-thread-1 and Task 4 -> pool-1-thread-2. For these notes, 6 different outputs were seen in 40 runs. Some things do not change: the worker names are always pool-1-thread-1 and pool-1-thread-2; the pool never starts a third thread. The last two lines are always the same, too.

Runnable does not return a value. For tasks that return a value there is the Callable interface; the lambda () -> 6 * 7 is a Callable<Integer>. submit returns a Future immediately. A Future represents a result that will be ready in the future. get() waits until the result is ready.

shutdown() asks the pool to stop accepting new tasks; the tasks in the queue are still completed. awaitTermination waits for all tasks to finish, for at most the given time. If shutdown() is forgotten, the program stays open, because the pool's workers are not daemon threads.

Java 21 introduced a new option: Executors.newVirtualThreadPerTaskExecutor() gives each task its own virtual thread. Virtual threads are managed by the JVM, not by the operating system; millions of them can be started. They are suited to large numbers of short, wait-heavy tasks. In one experiment, isVirtual() and isDaemon() both returned true inside such a task.

10.11.8CompletableFuture and concurrent collections

CompletableFuture<Integer> cf = CompletableFuture
    .supplyAsync(() -> 6)
    .thenApply(x -> x * 7)              // 42
    .thenCombine(CompletableFuture
        .supplyAsync(() -> 8), Integer::sum);
System.out.println(cf.get());           // 50

Map<String, Integer> freq =
    new ConcurrentHashMap<>();
String[] w = {"apple", "pear", "apple"};
Arrays.stream(w).parallel()
    .forEach(s -> freq.merge(s, 1, Integer::sum));
System.out.println(freq);  // {apple=2, pear=1}

This code shows two different tools, and in all ten runs it printed 50 and {apple=2, pear=1}.

CompletableFuture
Instead of waiting with get(), it chains operations; each step runs in the background when the previous one finishes. In the code, 6 is produced, multiplied by 7 (42), and added to the 8 produced by a separate task: 50.
ConcurrentHashMap
A thread-safe map. The methods merge and compute are atomic. A parallel stream processes the elements of the array on different threads; merge makes sure that no count is lost.
CopyOnWriteArrayList
Copies the internal array on every write. It suits lists that are read a lot and written rarely.
ForkJoinPool
For divide-and-conquer tasks (RecursiveTask). An idle worker steals work from another worker's queue (work stealing). Parallel streams (parallelStream()) use this pool.

A parallel stream is not always fast. On small data, the cost of coordinating threads exceeds the gain. A parallel stream that writes to a shared mutable variable, on the other hand, corrupts the result. The decision to parallelize is made by measurement.

10.11.9Thread safety

Definition 10.21

A class is thread-safe if it behaves correctly when used from several threads at the same time.

Thread safety is reached in four ways:

Immutable objects
Objects that do not change after they are created (String, classes whose fields are all final, Java 16+ record) can be shared without synchronization. Data that does not change does not race.
Not sharing
Local variables live on each thread's own stack; ThreadLocal also gives each thread a copy.
Synchronization
Every access to shared mutable data is protected by the same lock: synchronized or Lock.
Ready-made structures
AtomicInteger, ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue.

The ordinary classes of the collections framework, ArrayList and HashMap, are not thread-safe. When two threads each added 10,000 elements to the same ArrayList, the size was not 20,000 in any of the ten runs made for these notes; the values found ranged from 10,004 to 14,121. In four runs, one of the threads died with ArrayIndexOutOfBoundsException while the internal array was being grown. These classes are either protected with a lock or replaced by their concurrent counterparts.

10.14Summary

  • A thread is an independently progressing flow of execution inside a process. The threads of one process share the heap and the method area; each has its own stack, PC register, and local variables.
  • Concurrency means that tasks make progress during the same period of time, and it happens even on a single core. Parallelism means that tasks really run at the same instant on different cores.
  • The scheduler decides which thread runs when. The output order of multithreaded programs can therefore vary from run to run.
  • A thread is written by implementing Runnable, by extending Thread, or with a lambda. The work goes into run(); the thread is started with start(). Calling run() directly does not start a new thread.
  • There are six states: NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED. A thread that has finished cannot be restarted.
  • join() waits for a thread to finish and makes what it wrote visible. sleep does not release locks.
  • Daemon threads do not prevent the JVM from exiting; setDaemon(true) is called before start().
  • A thread is stopped cooperatively: with a volatile flag or with interrupt(). stop() has not worked since Java 20.
  • A race condition arises from divisible operations on shared data. counter++ consists of read–add–write steps, and a thread that slips in between makes increments get lost.
  • synchronized provides mutual exclusion by acquiring an object's monitor. An instance method locks this, and a static method locks Class.class. The protection works only if everyone uses the same lock.
  • volatile provides visibility, not atomicity. Happens-before relations (lock, volatile, start, join) determine when what one thread wrote becomes visible to another.
  • Lock is an explicit lock: it offers tryLock, timed and interruptible waiting, fairness, and several Conditions. unlock() always goes in finally. ReentrantLock and synchronized are reentrant.
  • ReadWriteLock lets readers read at the same time and gives the writer exclusive access.
  • Deadlock arises when locks are acquired in different orders. A fixed lock order, timed attempts, and short critical sections prevent it.
  • To wait for a condition, use wait/notifyAll or the await/signal of Condition; check the condition with while. The ready-made ArrayBlockingQueue solves the producer–consumer problem by itself.
  • CountDownLatch counts events, CyclicBarrier makes threads meet, Exchanger swaps data, and Semaphore limits concurrent entry.
  • Atomic classes update safely and without locks using compareAndSet. ThreadLocal gives each thread its own copy.
  • Thread pools reuse threads and limit their number. Callable returns a value, Future.get() waits for the result, and shutdown() must not be forgotten.
  • The ways to thread safety: immutable objects, not sharing, synchronization, and ready-made concurrent structures. ArrayList and HashMap are not thread-safe.

10.16Test Yourself

  1. A static method defines int total = 0;, increments total++ 1,000 times in a loop, and prints the result. If two threads named A and B run this method, what does each print? Is there a race?

    Answer

    Both print 1000. total is a local variable and lives on each thread's own stack; the two copies never see each other. A race happens only when the writes go to a shared field (an object field or a static field).

  2. A class has static synchronized void s() { shared++; } and synchronized void o() { shared++; }; shared is a static int. One thread calls s() 100,000 times, and another calls o() 100,000 times on the same object. Is the result always 200,000?

    Answer

    No. s() locks the class's .class object, and o() locks this. Two different locks do not block each other, and shared++ can run in both threads at the same time. In five trials, the result was below 200,000 every time (between 180,586 and 198,518). The fix is for both methods to use the same lock.

  3. On a ReentrantLock k, main calls lock() twice and unlock() once. Then another thread calls k.tryLock(). What does it return? What is k.getHoldCount() in main?

    Answer

    tryLock() returns false; getHoldCount() is 1. The hold count has dropped from 2 to 1, and the lock is still held by main. The lock is released only by the second unlock().

  4. countDown() is called twice on CountDownLatch m = new CountDownLatch(3);. What does m.await(100, TimeUnit.MILLISECONDS) return? What is m.getCount()?

    Answer

    false and 1. Because the counter has not reached 0, the latch does not open; the timed await waits 100 ms and returns false when the time is up. If the untimed await() had been called, the thread would have waited until the third event arrived.

  5. Three tasks are submitted to a pool created with Executors.newFixedThreadPool(1), each printing its own number and the name of its thread. What are the output order and the thread names?

    Answer

    Because the pool has a single worker, the tasks run one after another in queue order: 1, 2, 3. All three run on pool-1-thread-1; the pool starts no new thread. A single-worker pool therefore preserves the order of tasks. In five trials, the output was always the same.

  6. AtomicInteger a = new AtomicInteger(10); is created, then a.compareAndSet(10, 20), a.compareAndSet(10, 30), and a.getAndIncrement() are called. What do the three calls return, and what is the final value of a?

    Answer

    true, false, 20; the final value is 21. The first CAS finds 10 and writes 20. The second expects 10, but the value is 20, so it does not touch it. getAndIncrement() returns the old value (20) first and then increments.

  7. main first calls Thread.currentThread().interrupt(), then runs Thread.sleep(1000) inside a try-catch. Does sleep last a second? What is isInterrupted() inside the catch?

    Answer

    No. If a thread whose interrupt flag is set enters sleep, InterruptedException is thrown immediately. In the experiment, the exception came in under 100 ms. When the exception is thrown, the flag is cleared; isInterrupted() is false.

  8. Three threads acquire three locks as follows: T1 takes a then b; T2 takes b then c; T3 takes c then a. Can deadlock occur? If it can, which rule prevents it?

    Answer

    It can. If all three acquire their first lock, T1 waits for b, T2 for c, and T3 for a. Each lock being waited for is held by the next thread, and the cycle T1 → T2 → T3 → T1 forms. A fixed order is imposed, for example a < b < c, and every thread acquires its locks in that order. T3 then takes a first and c second, and no cycle can form.

  9. In the blocking-queue example, what problem could arise if notify() were written instead of notifyAll()?

    Answer

    Both producers and consumers can be waiting in the same wait set. notify() chooses a single thread arbitrarily. If a consumer, after taking an item, wakes another consumer, that consumer finds the queue empty and waits again. The waiting producer never wakes up, and the program may hang. notifyAll() wakes everyone; the irrelevant threads find the while condition unsatisfied and wait again. If producers and consumers are given separate sets with Condition, signal() is enough.
