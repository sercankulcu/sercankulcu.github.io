Introduction

Deciding Without the Full Picture

  • Sometimes decisions must be made without all the information.
  • Online algorithms:
    • when information arrives piece by piece,
    • they try to make the best decision with what is known so far.
  • A decision is irrevocable: information that arrives later does not change past decisions.
A chess player moves without knowing the opponent's next move; once made, a move cannot be taken back.

Introduction

Online Algorithms

  • Like walking through a maze:
    • You cannot see the whole maze, only the path ahead.
  • At each step you pick the best path with limited information.
  • They allow fast decisions when information does not arrive all at once.
  • Examples:
    • Which road to take in a traffic jam?
    • What is the next move in a chess game?
    • Adjusting traffic lights to current traffic.

Introduction

Online vs. Offline Problem Model

The input is a request sequence σ = σ1, σ2, …, σn. The difference lies in when the algorithm sees it.

"Online" here does not mean the internet; it means the input is revealed over time. Insertion sort can run online; selection sort cannot.

Introduction

The Online Algorithm Model

  • Data arrives continuously; the algorithm processes each piece as it arrives and outputs immediately.
  • The memory (buffer) cannot hold the whole input: the past survives only as a summary (a sum, a heap, a sample…).
  • So the goal is little work per element (usually O(1) or O(log n)) and little memory.

Introduction

Advantages and Disadvantages

Advantages

  • Work in dynamic environments; no need to wait for the input to end.
  • Make real-time decisions with low latency.
  • Can process very large, even infinite, streams with little memory.
  • The competitive ratio gives a worst-case guarantee.

Disadvantages

  • Wrong decisions in early steps can affect later ones.
  • In chess, one wrong move can lose the game.
  • No guarantee of finding the best global solution.
  • Sensitive to the early input; harder to design and analyze.

Introduction

Design Approaches for Online Algorithms

GreedyHandles each arrival in the way that looks best right now, ignoring global effects. Example: assign each request to the nearest idle server.
SummarizingKeeps a small summary instead of the whole past: a sum, two heaps, a sample. Example: moving average, running median.
AdaptiveLearns from mistakes and changes its behavior over time. Example: LRU, move-to-front (MTF), incremental learning.
DeterministicAlways makes the same decision on the same input; a malicious input sequence (an adversary) can easily trap it.
RandomizedAdds chance to its decisions, so the adversary cannot predict them. Example: reservoir sampling, randomized marking.

Competitive Analysis

Competitive Analysis

  • On every input, the online algorithm ALG is compared with the best offline algorithm OPT, which knows everything in advance.
  • ALG is c-competitive if for every request sequence σ
    ALG(σ) ≤ c · OPT(σ) + α
    holds (α: a constant independent of σ; if α = 0, it is strictly competitive).
  • The smallest such c is the competitive ratio: c = supσ ALG(σ) / OPT(σ).
  • The closer the ratio is to 1, the less the missing knowledge of the future hurts.
Pessimistic viewThe analysis is over the worst input: no averaging and no probabilistic assumptions.
Cost problemsHere cost is minimized (c ≥ 1). For profit problems the ratio is defined as OPT / ALG.

Competitive Analysis

The Adversary Model

To lower-bound the competitive ratio, imagine an adversary playing against the algorithm: it generates the input and runs OPT.

Deterministic ALGThe adversary knows the algorithm's code; at each step it issues the request that hurts ALG the most.
Oblivious adversaryCannot see a randomized algorithm's coin flips; it fixes the sequence in advance. We measure ALG's expected cost.
Adaptive adversarySees ALG's random choices before picking the next request; randomness helps less.
Proof pattern: to show that "no deterministic algorithm can beat c", build for every ALG a sequence σ with ALG(σ) / OPT(σ) ≥ c.

Ski Rental

The Ski Rental Problem

  • Skis can be rented for 1 TL per day or bought for B TL.
  • The number of ski days d is unknown: each morning you learn only whether you ski today.
  • Each day's decision: rent again or buy?
  • OPT knows d: OPT(d) = min(d, B).

B = 10; x-axis: actual days d. Worst ratio at d = B: 19/10 = 2 − 1/B.

Always rentAs d → ∞, cost d vs. OPT = B: ratio unbounded.
Buy on day 1With d = 1, cost B vs. OPT = 1: ratio B.
Break-evenRent B − 1 days, buy on day B: ratio 2 − 1/B.

Same shape: hourly cloud server vs. a yearly plan; keeping a TCP connection open vs. closing it.

Ski Rental

Cost of the Strategies (B = 10)

OPT, knowing the future: if d < 10 it always rents (cost d); if d ≥ 10 it buys on day 1 (cost 10).

Always rent: cost d. As d grows the cost increases without bound while OPT stays at 10 → not competitive.

Buy on day 1: the cost is always 10. But if d = 1, OPT = 1 → ratio 10 = B. Bad.

Break-even: rent for 9 days, buy on day 10. While d < 10 it matches OPT; for d ≥ 10 the cost is 9 + 10 = 19.

Worst case d = 10: ALG = 19, OPT = 10 → ratio 1.9 = 2 − 1/B. No d is worse.

Day 1: 1 < B → rent. cost = 1.

Day 2: 2 < B → rent. cost = 2.

Day 3: 3 < B → rent. cost = 3.

Day 4 = B: rent so far is B − 1 = 3 TL; now buy: cost = 3 + 4 = 7.

break: the skis are ours now; days 5 and 6 are free.

int breakEven(int B, int d) {  // d unknown
  int cost = 0;
  for (int day = 1; day <= d; day++) {
    if (day < B) {
      cost += 1;                // rent
    } else {
      cost += B;                // buy
      break;                    // no more fees
    }
  }
  return cost;
}

Why Nothing Does Better: Lower Bound

Every deterministic strategy is described by a single number: k = the day it buys.

  • Adversary: the weather turns right after the purchase, i.e., d = k.
  • ALG = (k − 1) rent + B, OPT = min(k, B).
  • k < B: ratio (k − 1 + B) / k ≥ (2B − 1) / B.
  • k ≥ B: ratio (k − 1 + B) / B ≥ (2B − 1) / B.
  • Best is k = B: ratio 2 − 1/B.

Paging

The Paging Problem

  • Fast memory (the cache) holds k pages; slow memory is unbounded.
  • If the requested page is in the cache, it is a hit (cost 0); otherwise a page fault (cost 1): the page is loaded.
  • If the cache is full, which page should be evicted? Future requests are unknown: a typical online problem.
  • Goal: minimize the total number of page faults.

int lruFaults(int[] requests, int k) {
  var cache = new LinkedList<Integer>();
  int faults = 0;
  for (int page : requests) {
    if (cache.remove((Integer) page)) {
      cache.addLast(page); // make newest
    } else {
      faults++;
      if (cache.size() == k)
        cache.removeFirst(); // drop oldest
      cache.addLast(page);
    }
  }
  return faults;
}

LRU Cache: O(1) Implementation

class LruCache<K, V>
    extends LinkedHashMap<K, V> {
  private final int k;

  LruCache(int k) {
    super(16, 0.75f, true); // access order
    this.k = k;
  }

  @Override
  protected boolean removeEldestEntry(
      Map.Entry<K, V> eldest) {
    return size() > k;      // evict beyond k
  }
}
  • LinkedHashMap = hash table + doubly linked list.
  • true (accessOrder): every get/put moves the entry to the end of the list.
  • removeEldestEntry: once the size exceeds k, the head (least recently used) is removed.
  • Find, move, remove: all O(1); memory O(k).
For FIFO, build the same class with false (insertion order): accesses do not change the order.

Paging

Theorem: Deterministic Lower Bound k

  • k + 1 distinct pages suffice. At every step the adversary requests the one page not in ALG's cache → ALG faults on every request.
  • When OPT (evict farthest) faults, the page it evicts is not requested for at least k − 1 requests → OPT faults at most once every k requests.
  • Hence ALG / OPT → k (Sleator and Tarjan, 1985).
In the example (k = 3, against LRU): LRU 12 faults, OPT 6; excluding the first 3 compulsory faults, 9 to 3.

Paging

Theorem: LRU (and FIFO) Are k-Competitive

  • Split the sequence into phases: each phase is a maximal block with k distinct pages; the (k + 1)-th distinct page starts a new phase.
  • LRU faults at most k times per phase: a page requested in a phase is not evicted before the phase ends (some page used less recently always exists). Each distinct page faults at most once.
  • OPT faults at least once per two consecutive phases: from the 2nd request of one phase to the 1st request of the next, k + 1 distinct pages are requested; they do not fit in k frames.
  • For m phases, LRU ≤ k · m and OPT ≥ m − 1 → LRU ≤ k · OPT + k.
The example sequence has 4 phases: LRU = 9 ≤ 3 · 4, OPT = 7 ≥ 3. Theory bounds the worst case; on real sequences, locality keeps LRU much closer to OPT.

Paging

Belady's Anomaly: More Memory, More Faults

  • Sequence: 1 2 3 4 1 2 5 1 2 3 4 5.
  • FIFO, k = 3: 9 faults; k = 4: 10 faults. The cache grew, and so did the faults!
  • LRU on the same sequence: k = 3 → 10, k = 4 → 8. LRU and OPT are stack algorithms: the pages in k frames are a subset of those in k + 1 frames → no anomaly.

int fifoFaults(int[] requests, int k) {
  Queue<Integer> queue = new LinkedList<>();
  Set<Integer> cached = new HashSet<>();
  int faults = 0;
  for (int p : requests) {
    if (cached.contains(p)) continue;   // hit
    faults++;
    if (cached.size() == k)
      cached.remove(queue.poll()); // oldest
    queue.offer(p); cached.add(p);
  }
  return faults;
}

Paging

Randomized Paging: The Marking Algorithm

Marking

  1. At the start of a phase, all pages are unmarked.
  2. The requested page is marked (hit or fault).
  3. On a fault, evict a random page among the unmarked ones.
  4. If all pages are marked, a new phase begins (step 1).

Results

  • Expected ratio 2Hk against an oblivious adversary (Fiat et al., 1991).
  • Hk = 1 + 1/2 + … + 1/k ≈ ln k. For k = 8, H8 ≈ 2.72 → ratio ≈ 5.4 (8 for deterministic).
  • No randomized algorithm can beat Hk.
  • LRU is also a marking algorithm (it picks the oldest unmarked page).
Randomness defeats the adversary's strategy of "request the page ALG does not have": it cannot know which page was evicted.

int marking(int[] requests, int k) {
  Set<Integer> cache = new HashSet<>();
  Set<Integer> marked = new HashSet<>();
  int faults = 0;
  for (int p : requests) {
    if (!cache.contains(p)) {
      faults++;
      if (cache.size() == k) {
        if (marked.size() == k) marked.clear(); // new phase
        List<Integer> cand = new ArrayList<>(cache);
        cand.removeAll(marked);       // unmarked ones
        int i = rng.nextInt(cand.size());
        cache.remove(cand.get(i));
      }
      cache.add(p);
    }
    marked.add(p);
  }
  return faults;
}

List Update

The List Update Problem

  • A linked list of n elements; accessing the element at position i costs i (scanned from the head).
  • After an access, the accessed element may be moved toward the front for free.
  • Requests arrive online: which elements will be popular is unknown.
Move-to-front (MTF)The accessed element is moved to the front of the list.
TransposeThe accessed element swaps places with the preceding one.
Frequency countElements are kept in decreasing order of access count.
Applications: self-organizing lists, chains in hash table buckets, data compression with the MTF transform (bzip2).

List Update

Theorem: MTF Is 2-Competitive

  • Sleator and Tarjan (1985): for every request sequence σ, MTF(σ) ≤ 2 · OPT(σ) − m (m: number of requests; OPT's paid swaps count toward its cost).
  • Proof idea: the potential function Φ = the number of inversions between the MTF list and the OPT list. On every access, MTF's actual cost + ΔΦ ≤ 2 · (OPT's cost) − 1. This is amortized analysis.

Transpose is not competitive

  • Request the last two elements alternately: xn, xn−1, xn, … Each access swaps them, but they stay at positions n and n − 1 → ≈ n per request. MTF pays 2 per request after the first two.

Neither is frequency count

  • Request x1 n times, x2 n − 1 times, …, then the same in reverse order. The counter keeps the old order for a long time; the cost can be a factor Θ(n) worse.

Data Streams

Moving Average

  • The average of the last k elements of a stream: smoothing sensor data, a 50-day moving average of a stock.
  • The naive method sums k elements each time: O(k).
  • The smart method: a sliding window. Keep the sum; add the new element as it enters and subtract the oldest as it leaves: O(1).
sum ← sum − xt−k + xt
average = sum / min(t, k)
class MovingAverage {
  private final int k;
  private final Queue<Integer> window
      = new LinkedList<>();
  private int sum = 0;

  MovingAverage(int k) { this.k = k; }

  double next(int value) {
    if (window.size() == k)
      sum -= window.poll();
    window.offer(value);
    sum += value;
    return sum / (double) window.size();
  }
}

6 joins the queue and is added to the sum: sum = 18.

Average = 18 / 3 = 6.

New value 2. The window is full (size 3 = k) → the oldest must go.

The oldest element 4 leaves the queue and is subtracted from the sum: sum = 14.

2 joins the queue and is added to the sum: sum = 16.

Average = 16 / 3 = 5.33.

New value 10. The window is full (size 3 = k) → the oldest must go.

The oldest element 8 leaves the queue and is subtracted from the sum: sum = 8.

10 joins the queue and is added to the sum: sum = 18.

Average = 18 / 3 = 6.

double next(int value) {
  if (window.size() == k)
    sum -= window.poll(); // oldest
  window.offer(value);
  sum += value;
  return sum / (double) window.size();
}

Running Median

  • After each new element we want the median so far.
  • Sorting every time: O(n log n). Inserting into a sorted array: O(n).
  • Two heaps: the smaller half in a max-heap (left), the larger half in a min-heap (right).
  • Invariants: every element of left ≤ every element of right; |left| = |right| or |left| = |right| + 1.
  • The median is read from the heap tops in O(1); insertion takes O(log n).
With an odd count the median is the top of left; with an even count it is the average of the two tops. A max-heap in Java: new PriorityQueue<>((a, b) -> b - a).

void add(int x) {
  if (left.isEmpty() || x <= left.peek())
    left.offer(x);         // smaller half
  else
    right.offer(x);        // larger half
  if (left.size() > right.size() + 1)
    right.offer(left.poll());
  else if (right.size() > left.size())
    left.offer(right.poll());
}
double median() {
  if (left.size() == right.size())
    return (left.peek() + right.peek()) / 2.0;
  return left.peek();
}

Reservoir Sampling

  • Maintain a sample of k elements from a stream of unknown length, with every element equally likely to be chosen.
  • Algorithm R (Vitter, 1985): put the first k elements into the reservoir (if the stream is shorter than k, return them all). Then for the i-th element (0-based, i ≥ k), pick j = random[0, i]; if j < k, set reservoir[j] ← xi.
  • The i-th element enters with probability k / (i + 1); if it does, it replaces an element at a random slot.
Proof (after n elements, each is in the reservoir with probability k / n): xi enters with k/(i+1). At each later step t > i it survives with probability 1 − (k/(t+1)) · (1/k) = t/(t+1). The product:
k/(i+1) · (i+1)/(i+2) · … · (n−1)/n = k / n

Example: k = 2, n = 5, element x2.

The same holds for the first k elements: they enter with probability 1, and the product k/(k+1) · … · (n−1)/n = k/n. Memory O(k), O(1) per element.

List<Integer> reservoir(int[] stream, int k) {
  List<Integer> r = new ArrayList<>();
  for (int i = 0; i < Math.min(k, stream.length); i++)
    r.add(stream[i]);
  for (int i = k; i < stream.length; i++) {
    int j = rng.nextInt(i + 1); // 0..i
    if (j < k)
      r.set(j, stream[i]);
  }
  return r;
}

Pattern Matching in a Stream: Rolling Hash

Pattern "AB", m = 2, B = 101. pow = 101m−1 = 101, hp = 65 · 101 + 66 = 6631. The stream "CABDAB" arrives one character at a time; for each new character hnew = (hold − cout · Bm−1) · B + cin: O(1) instead of O(m) from scratch.

t = 0, c = C (67): the window is not full yet; h = 67.

t = 1: the window is full: "CA". h = 6832 ≠ hp → no match.

t = 2: C leaves (subtract 67 · 101), B enters. h = 6631 = hp and the characters agree → match: 1.

t = 3: A leaves (subtract 65 · 101), D enters. h = 6734 ≠ hp → no match.

t = 4: B leaves (subtract 66 · 101), A enters. h = 6933 ≠ hp → no match.

t = 5: D leaves (subtract 68 · 101), B enters. h = 6631 = hp and the characters agree → match: 4. Equal hashes are not enough: collisions are possible, so the characters are compared too.

void search(String stream, String pattern) {
  int m = pattern.length(), B = 101, h = 0, hp = 0;
  int pow = 1;                          // B^(m-1)
  for (int i = 0; i < m - 1; i++) pow *= B;
  for (int i = 0; i < m; i++)
    hp = hp * B + pattern.charAt(i);
  for (int t = 0; t < stream.length(); t++) {
    char c = stream.charAt(t);
    if (t >= m) h -= stream.charAt(t - m) * pow;
    h = h * B + c;          // add incoming
    if (t >= m - 1 && h == hp
        && stream.startsWith(pattern, t - m + 1))
      System.out.println("match: " + (t - m + 1));
  }
}

Incremental Learning · Step by step

Incremental Learning

At first the model is trained on the original data set: MODEL 1.

New data 1 arrives. Instead of retraining on all the data, the model is updated with the new data only.

MODEL 2 captures the information in both old and new data; the old data is not processed again.

New data 2 arrives; the same update is repeated.

MODEL 3 carries the information of all three data sets. The model is always up to date, and each update costs only as much as the new data.

Incremental Learning

Incremental Updates and Their Challenges

Running mean

The mean is updated with each new element; no need to store the past:

μn = μn−1 + (xn − μn−1) / n

Stream 4, 8, 6: μ = 4 → 4 + (8 − 4)/2 = 6 → 6 + (6 − 6)/3 = 6.

Online gradient descent

w ← w − η · ∇ℓ(w; xt, yt)

Each example is used once; η is the learning rate.

Challenges

  • Catastrophic forgetting: old knowledge is lost while adapting to new data.
  • Concept drift: the data distribution changes over time; old data can mislead.
  • Order effects: the model is shaped by the order in which data arrives.
  • Noise: a single outlier can corrupt the model; a small η and a sliding window help.

Common Mistakes

Thinking "online = internet"An online algorithm works in a model where the input is revealed over time; it has nothing to do with network connections.
Confusing the ratio with the average caseThe competitive ratio refers to the worst input; "usually works well" is not a competitive ratio.
Mixing up FIFO and LRUIn FIFO a hit does not change the order; in LRU a hit makes the page the most recent.
Forgetting compulsory faultsThe first k distinct pages fault under every policy; even OPT cannot achieve 0 faults.
Wrong range in the reservoirj must be random[0, i] (i included, 0-based). Writing nextInt(i) breaks the probabilities.
Forgetting to rebalance the median heapsInserting is not enough; when the size difference exceeds 1, a top must move to the other heap.

Exercises

  1. Implement FIFO paging in O(1) time with a Queue and a HashSet.
  2. Implement OPT (Belady) in Java. What is its time complexity?
  3. Find the ratio of the "buy on day B/2" strategy for ski rental.
  4. Why is adding remove(x) to the running median hard?
  5. Show that with k = 1, each element of a 3-element stream is chosen with probability 1/3.
  6. Find the maximum of the last k elements in amortized O(1) time.
Answers / hints
  1. Hit: cached.contains(p). Fault: if full, cached.remove(queue.poll()); then offer + add.
  2. Scan ahead on every fault: O(n² · k) in total; precomputing next-use indices and keeping them in a heap gives O(n log k).
  3. With d = B/2, ALG = (B/2 − 1) + B and OPT = B/2 → ratio 3 − 2/B. Worse than break-even (2 − 1/B).
  4. A heap cannot delete an arbitrary element quickly; use a TreeMap with counts, or lazy deletion.
  5. 1st element: 1 · (1/2) · (2/3) = 1/3; 2nd element: (1/2) · (2/3) = 1/3; 3rd element: 1/3.
  6. A monotonically decreasing deque: a newcomer pops smaller elements from the back, and elements outside the window leave from the front; the front is the maximum.
