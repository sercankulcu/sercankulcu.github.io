Introduction

Faster Together

  • Some jobs take a very long time: big data analysis, scientific simulation, image processing.
  • Parallel algorithms solve a problem using several processors (cores) at the same time.
  • Complex tasks finish in much less time.
  • Single-core clock speeds have nearly stopped rising; performance gains now come from the number of cores.
Analogy: one teacher grades 1000 exams in 10 hours. If 10 teachers share the exams it takes ≈ 1 hour; but handing out the exams and collecting the grades also takes time.

Introduction

Parallel Algorithms

  • Like a group of people working together.
  • Split a complex problem into smaller pieces.
  • Speed up the work by assigning the pieces to different processors at the same time.
  • When the processors finish, combine the results.
  • The foundation of high-performance computing (HPC).
  • Uses: big data analysis, scientific simulation, machine learning and more.

Introduction

Benefits and Drawbacks

Benefits

  • Finish the same job sooner (speedup)
  • Solve large problems that do not fit on one machine (scalability)
  • Use the hardware (all cores, the GPU) efficiently

Drawbacks

  • Splitting the problem and combining the results takes extra effort
  • Communication and synchronization add overhead
  • Load balancing: every processor should get equal work, and there must be enough processing power
  • Debugging is hard (race conditions, deadlocks)
  • Some problems are inherently sequential
With data dependences (step k waits for the result of step k − 1), that part cannot be parallelized: e.g., the recurrence xₖ = f(xₖ₋₁).

Introduction

Applications

Matrix multiplication

The core operation of scientific computing; every row (even every cell) of the result can be computed independently.

Image processing

Edge detection, filtering, object recognition: the same operation on every pixel or block (data parallelism, GPU).

Computational fluid dynamics

Flow simulation in aircraft, ship and vehicle design: the domain is split into a grid, each region on one processor.

Genetic algorithms

The fitness of individuals in a population is evaluated independently and in parallel (scheduling, routing).

Models and Measures

Memory Architectures

  • Shared memory: all processors see the same address space. Communication is cheap; concurrent access requires synchronization.
  • Java threads, ForkJoinPool, OpenMP.
  • Distributed memory: each node has its own memory; data moves via messages.
  • Scales well, but communication is expensive: MPI, Hadoop MapReduce.

Models and Measures

The PRAM Model

  • PRAM (Parallel Random Access Machine): the theoretical model of parallel algorithms; the parallel counterpart of the sequential RAM model.
  • p processors, a shared memory and a common clock: the processors take steps in lockstep.
  • In each step a processor reads from memory → computes locally → writes to memory. Each takes O(1).
  • Communication and synchronization costs are ignored, so the model measures an algorithm's inherent parallelism.

E = Exclusive (one processor per cell per step), C = Concurrent (several processors). In CRCW, conflicting writes are resolved by a rule (common value, arbitrary one, priority…).

Models and Measures

Speedup, Efficiency, Cost

MeasureDefinition

Example: T₁ = 100 s, p = 8, T₈ = 16 s
S = 100 / 16 = 6.25
E = 6.25 / 8 ≈ 0.78

  • Cost-optimal: C = Θ(T₁).
  • Why S < p: communication, waiting, load imbalance, sequential parts.
  • These bounds hold in the model; in practice cache effects or finding a target early in a search can give S > p (superlinear speedup).

Models and Measures

Amdahl's Law

  • A fraction f of the program can be parallelized; the fraction 1 − f is sequential.
  • S(p) = 1 / ((1 − f) + f / p)
  • As p → ∞, S → 1 / (1 − f): the sequential part limits the speedup.
  • f = 0.9, p = 8: S = 1 / (0.1 + 0.1125) ≈ 4.71; the limit is 10.
Gustafson's law: if the problem size grows with p, S = (1 − f) + f · p. f = 0.9, p = 8 → S = 7.3. Parallelism pays off more on large problems.

Models and Measures

Work and Depth

  • Work W: the total number of operations = T₁ (time on one processor).
  • Depth (span) D: the longest chain of dependences = T∞ (time with unlimited processors).
  • Parallelism = W / D: the largest number of processors that can be used profitably.
  • Lower bounds: Tₚ ≥ W / p and Tₚ ≥ D.
  • Brent's theorem: Tₚ ≤ W / p + D.
  • Work-efficient: W is of the same order as the best sequential algorithm.
Example: summing n numbers with a tree
W = n − 1 additions, D = log₂ n rounds.
n = 1024: W = 1023, D = 10, parallelism ≈ 102.
Brent with p = 32: T₃₂ ≤ 1023/32 + 10 ≈ 42 steps.

Summation on a PRAM

Problem: Parallel Summation

  • Input: n numbers; output: their sum. The sequential algorithm performs n − 1 additions: O(n).
  • In the sequential loop each addition waits for the previous one: a chain of length n − 1, no parallelism.
  • Since addition is associative, we can regroup the parentheses:
    ((2 + 3) + (5 + 1)) + ((7 + 6) + (8 + 4)) → a balanced binary tree.
  • The sums on each level of the tree are independent → done in parallel in the same round.
  • The same idea works for any associative operation: max, min, product, AND, OR (reduction).
Example array: 2, 3, 5, 1, 7, 6, 8, 4 → sum 36. Eight processors p₀ … p₇ hold one number each.

Summation on a PRAM · Step by step

PRAM Summation Step by Step

Start: the 8 numbers are distributed one per processor (p₀ … p₇). Dashed boxes are the cells written in later rounds.

Round 1: 4 processors add adjacent pairs simultaneously: 2+3=5, 5+1=6, 7+6=13, 8+4=12.

Round 2: 2 processors combine partial sums at distance 2: 5+6=11, 13+12=25.

Round 3: p₀ computes 11+25 = 36. The 8 numbers were summed in log₂ 8 = 3 rounds (sequential: 7 steps).

Summation on a PRAM

Parallel Prefix Sums

  • Prefix sum (scan): yᵢ = x₀ + x₁ + … + xᵢ.
  • Sequential: yᵢ = yᵢ₋₁ + xᵢ, O(n) but fully chained.
  • Hillis–Steele: for d = 1, 2, 4, …, every i ≥ d does x[i] += x[i − d] in parallel.
  • D = ⌈log₂ n⌉ rounds, W = O(n log n) → not work-efficient.
  • The Blelloch algorithm (up-sweep/down-sweep) has W = O(n), D = O(log n).
  • Uses: parallel sorting, compaction (filter), Arrays.parallelPrefix in Java.
The summation tree yields only the last cell (the sum); in a prefix sum every cell must learn its own prefix.

Summation on a PRAM · Step by step

Hillis–Steele Prefix Sums Step by Step

Input: 2 3 5 1 7 6 8 4. Goal: x₀ + … + xᵢ for every i (inclusive prefix sum).

d = 1: every processor with i ≥ 1 adds its left neighbor's value (7 additions at once).

d = 2: for i ≥ 2, add the value 2 positions to the left. Each cell now holds the sum of a 4-element window.

d = 4: result 2 5 10 11 18 24 32 36. Done in log₂ 8 = 3 rounds, but with 7+6+4 = 17 additions in total.

Summation on a PRAM · Run the code step by step

Blelloch Prefix Sums: Code Trace

Input 2 3 5 1 7 6 8 4 (n = 8). The array serves as an implicit binary tree: first up (reduction), then down.

d = 1: x[1] += x[0], x[3] += x[2], x[5] += x[4], x[7] += x[6] (in parallel in one round, 4 additions).

d = 2: x[3] += x[1], x[7] += x[5] (in parallel in one round, 2 additions).

d = 4: x[7] += x[3] (in parallel in one round, 1 addition). The root x[7] = 36 is the total.

The total 36 is at the root. The root is set to 0: in the down-sweep every node carries "the sum of everything to its left".

d = 4: in each pair (i − d, i), the left child takes the parent's value and the right child takes parent + the old left value.

d = 2: in each pair (i − d, i), the left child takes the parent's value and the right child takes parent + the old left value.

d = 1: the last round; 4 pairs are updated at once.

Result 0 2 5 10 11 18 24 32: the exclusive prefix sums. 2 · (n − 1) = 14 operations, O(n) work, depth 2 log₂ n = 6 rounds.

// up-sweep; x = 2 3 5 1 7 6 8 4
for (int d = 1; d < n; d *= 2)
  for (int i = 2*d - 1; i < n; i += 2*d)
    x[i] += x[i - d];
x[n - 1] = 0;
// down-sweep (inner loops in parallel)
for (int d = n / 2; d >= 1; d /= 2)
  for (int i = 2*d - 1; i < n; i += 2*d) {
    int t = x[i - d];
    x[i - d] = x[i];
    x[i] += t;
  }
// x: exclusive prefix sums

Pipelining

The Idea of Pipelining

  • A pipeline splits the work into consecutive stages; each stage is a processor.
  • Like a factory assembly line: while one job moves to stage 2, stage 1 starts on the next job.
  • A single job does not get faster, but the number of jobs finished per unit time (throughput) increases.
  • k stages, m jobs: k · m steps sequentially; k + m − 1 steps with a pipeline.
  • Some stages are idle while the pipeline fills at the start and drains at the end.

3 stages, 4 jobs: 3 + 4 − 1 = 6 steps instead of 3 · 4 = 12.

Pipelining

The Pipeline Problem

  • Five processors p₀ … p₄ form a linear chain; each processor can send messages only to its right neighbor.
  • Each pj holds a column of 4 values (rows 0 … 3).
  • Goal: for every row r, the value at pj should become the sum of the values of p₀ … pj in that row (row-wise prefix sums). Then p₄ holds the sum of every row.
  • In one step each processor sends one value; the receiver adds it to its own.
  • Naive method: first move row 0 along the chain (4 steps), then row 1… → 4 · 4 = 16 steps.
  • Pipeline: pj sends row r at time t = r + j; the rows flow through the chain one after another.

Pipelined Tree

Reduction on a Tree

  • The processors are connected as a tree; each node sends its value to its parent, which adds it to its own. The result accumulates at the root.
  • If the tree has depth h, reducing a single value takes h rounds (h = 3 in our example).
  • Now each processor holds not one number but a vector with k components (k = 3 here: green, blue, red). Each component is summed separately.
  • Naive method: reduce the components one after another → k · h = 9 rounds.
  • Pipelined tree: while one component moves up, the next one sets out from the leaves.
  • Rule: a node can receive at most one message per round (and may also send one in the same round).

Kinds of Parallel Algorithms

Kinds of Parallel Algorithms

Divide and conquer

The problem is split into independent subproblems that are solved simultaneously on different cores, and the results are combined. Parallel merge sort, quicksort, matrix multiplication.

MapReduce

Big data is processed on distributed nodes: the map step emits intermediate key–value pairs, and the reduce step combines them. Hadoop, Spark; counting, indexing, log analysis.

Data parallel

The same computation is applied to different parts of the data at the same time (SIMD instructions, GPU). Scientific simulation, image processing, numerical computing.

Kinds of Parallel Algorithms

Parallel Merge Sort

class SortTask extends RecursiveTask<int[]> {
  private final int[] arr;
  SortTask(int[] arr) { this.arr = arr; }

  protected int[] compute() {
    if (arr.length <= 1) return arr;
    int mid = arr.length / 2;
    var left = new SortTask(
        Arrays.copyOfRange(arr, 0, mid));
    var right = new SortTask(
        Arrays.copyOfRange(arr, mid, arr.length));
    left.fork();              // start in parallel
    right.fork();
    return merge(left.join(), right.join());
  }
}
// usage:
int[] s = new ForkJoinPool().invoke(
    new SortTask(arr));
  • RecursiveTask: a Fork/Join task that returns a result.
  • fork(): submits the subtask to the pool (asynchronously).
  • join(): waits for the subtask to finish and gets its result.
  • merge: the usual sequential merge, O(n).
  • ForkJoinPool uses work stealing to hand work to idle cores.

Kinds of Parallel Algorithms · Step by step

Parallel Merge Sort: 2 3 5 1 7 6 8 4

Task: sort the 8-element array. SortTask is the root task.

The task splits the array in two and submits both subtasks to the pool with fork(); the halves can be processed at the same time.

Each subtask splits again: now 4 tasks can run in parallel.

Base case: one-element arrays are already sorted (8 leaf tasks).

join(): each parent waits for its two children's results and merges them: [2 3] [1 5] [6 7] [4 8].

One level up, two merges run in parallel: [1 2 3 5] and [4 6 7 8].

The root task does the final merge alone: [1 2 3 4 5 6 7 8]. This sequential merge makes the depth (span) Θ(n).

Kinds of Parallel Algorithms

MapReduce

  • Map: each chunk is processed independently and emits intermediate key–value pairs (word → count).
  • Shuffle: equal keys are gathered at the same reducer.
  • Reduce: the values of each key are combined (summed).
  • In the example: 13 words, 4 threads → chunk size ⌊13/4⌋ = 3; the last chunk has 4 words.

Data Parallelism: Matrix Multiplication

// each row is a separate task
class RowTask extends RecursiveAction {
  protected void compute() {
    for (int j = 0; j < n; j++) {

Row Task: Code Trace

This task computes only row 1 of C: row 1 of A (4, 5, 6) times each column of B. The other rows are in other tasks.

j = 0: C[1][0] starts at 0.

k = 0: C[1][0] += A[1][0] · B[0][0] = 4 · 9 → 36.

k = 1: C[1][0] += A[1][1] · B[1][0] = 5 · 6 → 66.

Kinds of Parallel Algorithms

Race Conditions

Two threads increment the shared counter at the same time. counter++ is really three steps: read → increment → write.

timeThread 1Thread 2counter
1read (0)0
2read (0)0
3write 0 + 11
4write 0 + 11

Expected 2, got 1: a lost update.

  • Race condition: the result depends on the timing of the threads; the bug may not show up on every run.
  • Fixes: a synchronized block / lock, AtomicInteger.incrementAndGet(), concurrent collections (ConcurrentHashMap).
  • Best of all is to avoid shared state: each task produces its own partial result, and the results are combined afterward (reduction, MapReduce).
  • Locks are not free either: they create sequential regions (Amdahl) and risk deadlock.

Kinds of Parallel Algorithms

Concurrent Graph Traversal

  • Idea: fork() a new traversal task for each unvisited neighbor; subtrees are traversed in parallel.
  • The tasks share the visited set. If it is an ordinary HashSet, concurrent access is not safe.
  • Moreover, contains + add are two separate steps: two tasks may visit the same node together.
Set<Node> visited = ConcurrentHashMap.newKeySet();
if (!visited.add(neighbor)) continue; // atomic check+add

Level-synchronous BFS: all nodes of a level are expanded in parallel, with a barrier at the end of each level. D = O(diameter) on an ideal PRAM with enough processors; the number of levels does not exceed the diameter of the part reachable from the source (O(diameter · log n) in a realistic model).

Summary

Common Mistakes

Thinking p processors = p times fasterThe sequential part (Amdahl), communication and waiting make S < p. 10% sequential code caps the speedup at 10.
A shared HashSet / counterConcurrent writes lead to race conditions. Use ConcurrentHashMap, AtomicInteger, or local results + combining.
Overly fine-grained tasksCalling fork() for every element inflates task-creation overhead. Parts below a threshold are processed sequentially.
Forgetting synchronization between roundsIn PRAM summation, if round t + 1 starts before all writes of round t finish, stale values are read.
Looking only at depthHillis–Steele finishes in O(log n) rounds but does O(n log n) work; with few processors it can be slower than a sequential scan.
Miscounting pipeline stepsThe fill time is forgotten: for m rows and p processors it takes m + p − 2 steps, not m.

Sample Problems

  1. n = 16 numbers are summed with a PRAM tree. How many rounds does it take, how many processors work in the first round, and how many additions are made in total?
  2. How many steps does a pipeline with p = 5 processors and m = 100 rows need? Compare with the naive method.
  3. In the chapter's pipelined tree example (7 processors, h = 3), how many rounds would be needed if each processor held a vector with k = 10 components?
  4. 80% of a program is parallel. What is the Amdahl speedup for p = 4, and what is the upper limit?
  5. T₁ = 120 s, T₆ = 30 s. Find the speedup, efficiency and cost.
  6. Write the Hillis–Steele prefix sums of [1, 2, 3, 4] round by round; how many additions are made?
Show answers
  1. log₂ 16 = 4 rounds; 8 processors in the first round; 8 + 4 + 2 + 1 = 15 additions (= n − 1).
  2. m + p − 2 = 103 steps; naive m(p − 1) = 400 steps (≈ 3.9 times as many).
  3. 3 + (10 − 1) · 2 = 21 rounds (naive 10 · 3 = 30).
  4. S = 1 / (0.2 + 0.8/4) = 1 / 0.4 = 2.5; limit 1 / 0.2 = 5.
  5. S = 4, E = 4/6 ≈ 0.67, C = 6 · 30 = 180 s.
  6. d = 1: [1, 3, 5, 7]; d = 2: [1, 3, 6, 10]. 3 + 2 = 5 additions (sequential: 3).

Exercises

  1. Modify PRAM tree summation to find the maximum element. What are its time and work?
  2. How many additions does Hillis–Steele make for n = 8? Compare with the sequential algorithm.
  3. Make the visited set of the parallel traversal thread-safe.
  4. Add a threshold to parallel merge sort; why is it better to compute() one of the two subtasks directly instead of calling fork()?
  5. On p = 32 processors, what minimum parallel fraction gives a speedup of S = 16 (Amdahl)?
  6. Express the number of steps and the efficiency of a pipeline with m rows and p processors in general.
Answers / hints
  1. a[i] = Math.max(a[i], a[i + step]); D = log₂ n, W = n − 1.
  2. d = 1: 7, d = 2: 6, d = 4: 4 → 17 additions; sequential 7. In general: n log₂ n − (n − 1).
  3. Use ConcurrentHashMap.newKeySet(); visited.add(neighbor) checks and inserts in one atomic step.
  4. If size < threshold, use Arrays.sort. left.fork(); x = right.compute(); y = left.join();: the thread does not sit idle, and the number of tasks halves.
  5. 1 / ((1 − f) + f/32) = 16 → 1 − (31/32) f = 1/16 → f = 30/31 ≈ 96.8%.
  6. Steps: m + p − 2; efficiency: m / (m + p − 2).
