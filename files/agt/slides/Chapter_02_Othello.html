How to play

  1. You play Black and move first; the computer plays White.
  2. Place a disc on an empty square so that one or more white discs lie in a straight line (horizontal, vertical, or diagonal) between the new disc and another black disc. All those discs turn black.
  3. Valid moves are marked with a gold ring. A player with no valid move must pass; when neither side can move the game ends and the player with more discs wins.
  4. The small red dot marks the computer's last move.
  5. The letters (columns) and digits (rows) around the board name the squares; the top-left square is a1. The reasoning panel writes moves with these names.

Move scores

With Move scores on, each ring shows how good that move looks for you (higher is better; the best move's ring is white):

  • Simple: the number of discs flipped, with bonuses for corners (+15) and edges (+5) and a penalty for squares next to a corner (−15).
  • Smart: a short minimax lookahead using the same evaluation as the Smart computer (your move, then two more plies), measured relative to your worst move.

Computer opponents

  • Simple picks the move with the best one-move heuristic score.
  • Smart searches five plies deep with minimax and alpha-beta pruning. Details of both are in the How the AI decides tab.

The Show move reasoning box shows, in the side panel, what the computer computed before each move.

Why the disc count can mislead

Having many discs early in the game is not always an advantage: many discs form a wide frontier that gives the opponent extra valid moves. Corners can never be flipped and anchor stable edges. Position and mobility (the Moves counter: the valid moves of the player to move) usually matter more than the current disc count; near the end of the game the exact disc count decides.

Link to game theory

Othello is a two-player, zero-sum game of perfect information. In 2023 it was shown by computation that the 8×8 version ends in a draw with perfect play. Comparing the two opponents shows how deeper search and a better evaluation function change decision quality.

Simple mode: a one-move score

For every valid move one number is computed (heuristicScore): the number of discs flipped plus a bonus or penalty (corner +15, edge +5, square next to a corner −15). The move with the largest score is played; on a tie the first move found while scanning the board (row by row, left to right) stays. There is no randomness: the same position always gets the same move. This mode does not look ahead; it never considers your reply.

Smart mode: what is searched?

Smart mode runs minimax with alpha-beta pruning from the Minimax and Alpha-Beta Pruning lecture.

  • Depth. 5 plies (DEPTH = 5): White's move, then 4 more plies.
  • Max and min. Values are written from White's (the computer's) side: White's turn is a max node, yours (Black) is a min node.
  • A narrowed window at the root. Each root move is searched with the best value found so far (α = bestVal). If a move cannot beat the best one, the search cuts it off at once and only an upper bound is known: “≤ v” in the panel. The value of a move that beats the best is exact.
  • Ordering and ties. There is no move ordering; moves are tried in scan order and on equal values the first one found stays. There is no randomness.
  • Passes and the end of the game. If a side has no move it passes (this uses up one ply). If neither side can move, the game is over and the value is (White − Black discs) × 1000: the real result always dominates the heuristic score. With five plies left in the game the computer really sees the result.

Why not search to the end of the game?

In the middlegame of Othello a position has roughly 8–10 valid moves and a game lasts at most 60 moves: the number of possible games is roughly 1058. A five-ply tree has about 105 leaves (fewer with pruning), which is fast for one move in a browser. Searching to the end is impossible: it took a huge computation in 2023 to show that the 8×8 game ends in a draw. So the search stops at the fifth ply and an evaluation function estimates the value of that position.

What does the evaluation function count?

The function (evaluateBoard) counts five terms for each player and takes the difference (White − Black):

value = disc difference + 100·corners + 15·edges + 8·mobility − 50·corner neighbors

  • Discs: 1 point per disc.
  • Corners: 100 points per disc in a corner; corners can never be flipped.
  • Edges: 15 points per disc on the 24 edge squares that are not corners.
  • Mobility: the player's number of valid moves × 8. The move lists of both sides are computed.
  • Corner neighbors: −50 per disc on the 12 squares next to a corner (applied even when the corner is taken).

So early in the game the evaluation hardly looks at the disc count: one corner equals 100 discs, and one more valid move equals 8 discs.

A small example (with real values)

Let Black play d3 on the first move. White's valid moves are c3, e3 and c5. The evaluation of the position after each move:

The corner, edge and corner-neighbor terms are 0 in these positions. The real search uses such numbers as leaf values and goes 4 plies deeper; but in this position the result is still c3.

What does the panel show?

With Show move reasoning on, after each move the computer lists the following in the panel. In Smart mode: the depth, the number of positions searched, the value of every candidate move (column letter + row number), largest first (“≤ v” for moves that were cut off), the chosen move (yellow) and the five terms of the position after the move. In Simple mode: for every move the number of flips, the bonus or penalty and the total score.

Decision code (JavaScript)

// Constants: the terms other than the disc count look at these squares
var DEPTH = 5;                                   // 5 plies
var CORNERS = [[0, 0], [0, 7], [7, 0], [7, 7]];
var NEIGHBORS = [[0, 1], [1, 0], [1, 1], [0, 6], [1, 7], [1, 6],
                 [7, 1], [6, 0], [6, 1], [7, 6], [6, 7], [6, 6]];   // the 12 squares next to a corner

// Smart mode, root: try every move and compute its value
function bestMinimaxMove(b, depth, player) {
  var bestVal = -Infinity, bestMove = null;
  var rows = [];                                 // record for the reasoning panel
  nodeCount = 0;                                 // counter of searched positions
  getValidMoves(b, player).forEach(function (m) {
    var nb = cloneBoard(b);
    makeMove(nb, m[0], m[1], player);            // play the move on a copy
    // window (bestVal, +infinity): the best value found so far becomes alpha
    var v = minimax(nb, depth - 1, false, bestVal, Infinity, opposite(player));
    var improved = v > bestVal || !bestMove;
    rows.push({ move: m, value: v, exact: improved });
    if (improved) { bestVal = v; bestMove = m; }
  });
  lastWhy = { mode: 'smart', depth: depth, nodes: nodeCount, rows: rows, chosen: bestMove };
  return bestMove;
}

// Minimax with alpha-beta pruning; values are from White's (the AI's) side, maximizing = White to move
function minimax(b, depth, maximizing, alpha, beta, player) {
  nodeCount++;
  var moves = getValidMoves(b, player);
  if (!moves.length) {
    if (!hasValidMove(b, opposite(player))) {    // neither side can move: game over
      var n = countPieces(b);
      return (n.white - n.black) * 1000;         // the real result, dominates the heuristic
    }
    if (depth === 0) return evaluateBoard(b);
    return minimax(b, depth - 1, !maximizing, alpha, beta, opposite(player));   // pass
  }
  if (depth === 0) return evaluateBoard(b);
  var best = maximizing ? -Infinity : Infinity;
  for (var i = 0; i < moves.length; i++) {
    var nb = cloneBoard(b);
    makeMove(nb, moves[i][0], moves[i][1], player);
    var v = minimax(nb, depth - 1, !maximizing, alpha, beta, opposite(player));
    if (maximizing) { best = Math.max(best, v); alpha = Math.max(alpha, v); }
    else { best = Math.min(best, v); beta = Math.min(beta, v); }
    if (beta <= alpha) break;                    // pruning
  }
  return best;
}

// Evaluation: White - Black
function evaluateBoard(b) {
  var n = countPieces(b);
  return n.white - n.black +                                    // disc difference
    cornerBonus(b, 'white') - cornerBonus(b, 'black') +         // corners: 100
    edgeBonus(b, 'white') - edgeBonus(b, 'black') +             // edges: 15
    getValidMoves(b, 'white').length * 8 -                      // mobility: 8
    getValidMoves(b, 'black').length * 8 -
    cornerNeighborPenalty(b, 'white') + cornerNeighborPenalty(b, 'black');   // corner neighbors: 50
}

function cornerBonus(b, player) {
  return CORNERS.reduce(function (s, p) { return s + (b[p[0]][p[1]] === player ? 100 : 0); }, 0);
}

function edgeBonus(b, player) {                  // the 24 edge squares that are not corners
  var score = 0;
  for (var k = 1; k < 7; k++) {
    if (b[0][k] === player) score += 15;
    if (b[7][k] === player) score += 15;
    if (b[k][0] === player) score += 15;
    if (b[k][7] === player) score += 15;
  }
  return score;
}

function cornerNeighborPenalty(b, player) {      // applies even when the corner is taken
  return NEIGHBORS.reduce(function (s, p) { return s + (b[p[0]][p[1]] === player ? 50 : 0); }, 0);
}

// Simple mode: a one-move score that does not look ahead
function heuristicScore(b, r, c, player) {
  var score = countFlips(b, r, c, player);       // number of discs flipped
  if (isCornerNeighbor(r, c)) score -= 15;
  else if ((r === 0 || r === 7) && (c === 0 || c === 7)) score += 15;
  else if (r === 0 || r === 7 || c === 0 || c === 7) score += 5;
  return score;
}

function bestHeuristicMove(b, player) {
  var best = null, bestScore = -Infinity, rows = [];
  getValidMoves(b, player).forEach(function (m) {
    var s = heuristicScore(b, m[0], m[1], player);
    rows.push({ move: m, value: s, flips: countFlips(b, m[0], m[1], player) });
    if (s > bestScore) { bestScore = s; best = m; }          // on a tie the first move stays
  });
  lastWhy = { mode: 'simple', rows: rows, chosen: best };
  return best;
}

The same idea in Python

The same pattern as the course's Python examples (alphabeta, maxi, pruning with break). Helpers such as moves, play and discs supply the Othello rules.

from math import inf

def evaluate(t):                             # value from White's (the AI's) side
  def score(p):                              # position score of one player
    return (100 * corners(t, p) + 15 * edges(t, p)
            + 8 * len(moves(t, p)) - 50 * neighbours(t, p))
  return discs(t, 'W') - discs(t, 'B') + score('W') - score('B')

def alphabeta(t, depth, a, b, maxi, player):
  mv = moves(t, player)
  if not mv:
    if not moves(t, opponent(player)):       # neither side can move: game over
      return (discs(t, 'W') - discs(t, 'B')) * 1000
    if depth == 0:
      return evaluate(t)
    return alphabeta(t, depth - 1, a, b, not maxi, opponent(player))   # pass
  if depth == 0:
    return evaluate(t)
  best = -inf if maxi else inf
  for m in mv:
    v = alphabeta(play(t, m, player), depth - 1, a, b, not maxi, opponent(player))
    if maxi:
      best = max(best, v); a = max(a, best)
    else:
      best = min(best, v); b = min(b, best)
    if b <= a:
      break                                  # pruning
  return best

def best_move(t, depth, player):             # root: alpha = best value so far
  best, chosen = -inf, None
  for m in moves(t, player):
    v = alphabeta(play(t, m, player), depth - 1, best, inf, False, opponent(player))
    if v > best or chosen is None:
      best, chosen = v, m
  return chosen

Try it yourself

  1. Predict first, then look. Set the computer to Smart and tick Show move reasoning. After each of your moves, guess which square you would choose in the computer's place before it plays. Then compare with the chosen move in the panel. Are there rows marked “≤”? Explain from the How the AI decides tab why these are upper bounds and not exact values.
  2. Recompute a value by hand. In Smart mode make a move and look at the “mobility” term below the panel. The term is the computer's number of valid moves minus yours, times 8. The Moves counter in the left panel shows your number of valid moves: can you work out the computer's number? Check the edge and corner-neighbor terms on the same line by counting the discs on the board.
  3. Compare Simple and Smart. First play a game in Simple mode. The panel shows each move's flips and bonus: does the computer always pick the move that flips the most discs, or does the bonus sometimes decide? Can you find a moment when it plays next to a corner (the row says −15)? Then watch similar situations in Smart mode: why is the corner-neighbor penalty (50) so much larger?
  4. Watch the endgame. In Smart mode play until about four empty squares are left. Write down when the values in the panel turn into multiples of 1000 (for example +24000, +18000). What do these numbers show? What does the computer see at that point that makes mobility or corner weights unnecessary?

Discussion questions

  • Why does the evaluation reward mobility and not the disc count?
    Answer

    In Othello having many discs is often bad: the side with many discs gives the opponent a wide frontier and many valid moves; the opponent reaches good squares such as corners while it is forced to play on bad ones. A player with few moves left has to make forced moves. Mobility is the number of options for the future; the disc count does not measure that. In short, what looks good now (many discs) can be bad at the end.

  • Why does narrowing the window at the root (α = best so far) not change the result?
    Answer

    At the root you do not need to know a move's exact value, only whether it beats the best found so far. As soon as a min node finds one reply whose value is at most α, it has proved that the move cannot beat the best; the remaining replies need not be looked at. So the chosen move is the same as with a full search; only the values of the losing moves stay inexact, shown as “≤ v”. (In the chess page the root window is (−∞, +∞), so all values are exact, but it is slower.)

  • The weights 100, 15, 8 and 50 are fixed. What would change if they depended on the phase of the game? How could the weights be found?
    Answer

    Early in the game mobility and avoiding corner traps weigh most; at the end the exact disc count decides. Fixed weights cannot capture this change: the weight of the “discs” term should grow as the game goes on. Instead of choosing weights by hand, they can be learned from real game results (self-play, hill climbing, genetic algorithms or temporal-difference learning; Chapter 13). Strong Othello programs do the evaluation with pattern tables learned from many positions.

  • Othello is a solved game (a draw with perfect play). So why do we still search with a heuristic evaluation?
    Answer

    Knowing the value of the game does not mean knowing the best move in every position. The solution came from a huge computation and is not available as a strategy table covering every position; a program running in a browser cannot repeat that computation. Zermelo's theorem says “a value exists”; it does not say what it costs to find it. So in practice the program works with limited depth and a heuristic evaluation, and computes the exact result when the end of the game is near.
