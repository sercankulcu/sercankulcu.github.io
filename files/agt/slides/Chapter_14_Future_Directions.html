Infinite Horizon: The Rubinstein Solution

  • No last round, so backward induction cannot start; use stationary strategies: A always keeps x* when proposing, B always leaves y* to A.
  • B is indifferent: 1 − x* = δB·(1 − y*); so is A: y* = δA·x*.
  • Substituting: 1 − x* = δB·(1 − δA·x*) ⇒ x*·(1 − δAδB) = 1 − δB:
x* = (1 − δB) / (1 − δAδB)

Equal patience δ: x* = 1/(1 + δ); δ = 0.9 gives 100/1.9 ≈ 52.6. Accepted in round 1: no delay, no loss.

AI Agents

Can Pricing Algorithms Collude?

  • Two firms sell the same product; at the monopoly price total profit is 100 (50 each). If one undercuts, profit drops to zero (Bertrand competition: the cheaper firm takes the whole market).
  • The grim trigger strategy: "Price high until the rival undercuts; if it does, compete forever."
  • The structure is the repeated Prisoner's Dilemma: a deviator gets 100 for one period, then 0; a complier gets 50 every period. The trigger condition 50/(1 − δ) ≥ 100 ⟺ δ ≥ 1/2.

Simulations show that pricing agents using reinforcement learning can learn supracompetitive prices without communicating (Calvano et al., 2020).

The regulatory question: without an explicit agreement, is there algorithmic collusion? Competition law has traditionally rested on "agreements between people"; algorithms that learn high prices without communicating strain this framework.

Code Trace: Does Deviating Pay Under a Trigger?

Two paths: cooperate at 50 each period, or deviate at t = 2 for 100, then 0 under the trigger. δ = 0.6, 6 periods.

t = 0: both paths earn 50 (δ⁰ = 1).

t = 1: +0.6·50 = 30; still equal: 80.

t = 2: A deviates and takes the market: +0.36·100 = 36 vs. +18. Deviation 18 ahead.

t = 3: the trigger fires; deviation gets 0, cooperation +10.8.

t = 4: cooperation +6.48 = 115.28; gap 0.72.

t = 5: +3.89, cooperation pulls ahead: 119.17 > 116. The gain of 18 is repaid in lost future profit.

Printed. With an infinite horizon: 50/(1 − 0.6) = 125 vs. 116.

δ = 0.4: deviation 86 vs. 82.99 (83.3 at infinity): collusion collapses. Threshold δ = 1/2.

def compare(delta, s, T):
    coop, dev = 0.0, 0.0         # cooperate / deviate
    for t in range(T):
        coop += delta**t * 50
        if t < s:
            dev += delta**t * 50
        elif t == s:
            dev += delta**t * 100  # A undercuts
        # t > s: trigger fired, profit 0
    return round(coop, 2), round(dev, 2)
print(compare(0.6, 2, 6))
print(compare(0.4, 2, 6))

(100/n)/(1 − δ) ≥ 100 ⟺ δ ≥ 1 − 1/n. With more firms, each one's cooperative share shrinks and deviating becomes more tempting.

Frequent price updates

If prices update every minute, the future is worth almost as much as today (δ ≈ 1); a deviator's gain lasts only a few minutes.

Transparent prices

If rival prices are visible instantly, a deviation is noticed at once and punishment is immediate.

Price-matching guarantees

"If a rival is cheaper, we refund the difference" wipes out the gain from undercutting and protects collusion.

Policy proposals

Test algorithms in simulated markets; open decision logs to audit.

Learned Mechanisms

Automated Mechanism Design

The classical route
  • A person proposes a rule (Vickrey, VCG, Myerson).
  • IC and optimality are proved by hand.
  • Works for structured problems (one item); with many items and buyers the optimum is often unknown.
The automated route
  • The mechanism solves an optimization problem: objective (revenue, welfare) + constraints IC (truth is best) and IR (participating does no harm).
  • Linear programs over randomized mechanisms for finite types (Conitzer and Sandholm, 2002).
  • Neural-network auctions: IC becomes a "regret" penalty, the extra utility a bidder could gain by lying (Dütting et al., 2019).
Approximate IC

A learned rule may keep a small regret.

Generalization

If the distribution shifts, the rule may fail.

Explainability

"Why this price?" cannot be answered with network weights.

Learned Mechanisms

Code Trace: Automated Design for a Two-Type Buyer

One buyer, one item. Type L (value 1) with probability qL, type H (value 3). xL = 0: L never buys, H buys at 3. Revenue 0.5·3 = 1.5. General rule: L's price is the most L will pay: pL = xL·1. If H acts like L, H gains 3·xL − pL; the highest price that keeps H truthful is pH = pL + 3·(1 − xL).

xL = 0.5: selling to L with probability one half for an expected payment of 0.5 (price 1 when sold) gives H an option to lie (claiming L yields 3·0.5 − 0.5 = 1). H's price drops to 2. Revenue 0.25 + 1 = 1.25.

xL = 1: everyone buys at 1; H pays the same price even if it lies. Revenue 1.

qL = 0.5: best is xL = 0, i.e. sell only to H, at 3.

qL = 0.75: type L is now the majority. Selling only to H earns little: 0.25·3 = 0.75.

xL = 0.5: 0.75·0.5 + 0.25·2 = 0.875.

xL = 1: sell to everyone at 1: 1.

qL = 0.75: best: sell to everyone at 1. Revenue is linear in xL, so at least one optimum is at an endpoint (a vertex of the linear program; at qL = 2/3 every xL gives the same revenue): both solutions are posted prices.

def revenue(xL, qL, vL=1, vH=3):
    pL = xL * vL                 # L's IR binds
    pH = pL + vH * (1 - xL)      # H's IC binds
    return qL * pL + (1 - qL) * pH
for qL in [0.5, 0.75]:
    G = [revenue(x, qL) for x in [0, 0.5, 1]]
    print(qL, G)

def best_price(samples):
  v = sorted(samples, reverse=True)
  n = len(v)
  price, revenue = 0, 0
  for k in range(1, n + 1):
    p = v[k - 1]        # k-th highest
    g = p * k / n       # k buyers buy
    if g > revenue:
      price, revenue = p, g
  return price, revenue

Learned Mechanisms

How Far Does the Empirical Revenue Curve Stray from the Truth?

  • The empirical curve p · #{vi ≥ p}/n is piecewise linear: it rises between sample values and drops at them; its maximum is always at a sample value (here 0.47).
  • The chosen price's performance on the sample (0.294) overstates its true performance (0.249): because the same data is used to choose and to measure, there is an optimistic bias. The gap to the true best of 0.25 is small, but it grows as samples get scarce.

Lesson: with scarce data, a learned mechanism overstates its success. Separate training and evaluation data, as in machine learning.

Learned Mechanisms

Differential Privacy: One Person's Data Should Barely Matter

  • Differential privacy: adding or removing a single person's data changes the probability of any outcome only slightly. Here ε measures privacy: a smaller ε means more privacy (a change by a factor of at most eε).
  • The exponential mechanism (McSherry and Talwar, 2007): instead of picking the best price outright, it runs a lottery; good prices get exponentially higher probability, bad prices a small but nonzero probability.
  • The game theory link: since one person's report barely affects the outcome, lying gains little too (at most eε − 1 if utilities are in [0, 1]) → approximate incentive compatibility, with privacy on top.

Reserve price example, ε = 2: removing one buyer changes the probabilities by a factor of at most 1.44 (the bound is e² ≈ 7.39).

import math
def exp_mech(v, prices, eps):
    R = [p * sum(x >= p for x in v) for p in prices]
    w = [math.exp(eps * r / 2) for r in R]   # Δ = 1
    W = sum(w)
    return [x / W for x in w]
v = [0.62, 0.15, 0.91, 0.47, 0.33, 0.78, 0.55, 0.08]
P = [0.2, 0.4, 0.6, 0.8]
q = exp_mech(v, P, 2)
print([round(x, 3) for x in q])
q = exp_mech(v[1:], P, 2)       # 0.62 removed
print([round(x, 3) for x in q])

Blockchain Mechanisms

Blockchains and Smart Contracts

  • Smart contract: a program whose code is public and runs automatically on-chain → a self-enforcing mechanism.
  • Mechanism design's assumption that "the designer is bound by the rules" (commitment) is enforced by code; but pending transactions are visible to everyone too.
  • The block producer decides which transactions enter the block and in what order: a scarce resource → an auction.
  • Transaction fee auction: Scarce block space is allocated to bidders.
  • Decentralized exchange: An automated market maker (AMM): the price is set by a formula.
  • On-chain governance: Token-weighted voting; the problems of voting rules apply here too.

Blockchain Mechanisms

Transaction Fee Auctions

First price (the original design)
  • Each transaction bids a fee; the producer takes the highest bids and everyone pays their own bid.
  • Values 9, 7, 6, 4, 2 and capacity 3: truthful bids pay 9 + 7 + 6 = 22.
  • But truthful bidding is not optimal: everyone shades, and "how much should I bid?" burdens the user.
Base fee + tip (EIP-1559 style)
  • The protocol sets a base fee r (here 5); r is burned, i.e. paid to no one and removed from circulation. Only the tip (1) goes to the producer.
  • Transactions with value ≥ r + tip get in: 3 transactions, 15 burned, 3 in tips.
  • If demand does not exceed capacity, the best strategy is simple: pay "r + a small tip"; no price guessing needed.
Design goals (Roughgarden, 2021): simple bidding for users, honest behavior for producers, resistance to collusion. A rule that fully achieves all of them is hard to find.

Blockchain Mechanisms

Step by Step: The Base Fee Tracks Demand

The general principle: the fee rises when usage is above target and falls when below. With EIP-1559's launch parameters: rt+1 = rt·(1 + ⅛·(gt − gtarget)/gtarget), with gtarget half the block capacity. Initially r = 100.

Block 1 is 100% full → change +12.5% → r = 112.5.

Block 2 is 100% full → change +12.5% → r = 126.6.

Block 3 is 100% full → change +12.5% → r = 142.4.

Block 4 is 100% full → change +12.5% → r = 160.2. A demand spike: the fee rises by at most 12.5% per block.

Block 5 is 50% full → change ±0% → r = 160.2. Exactly on target, the fee stays put.

Block 6 is 25% full → change −6.25% → r = 150.2.

Block 7 is 0% full → change −12.5% → r = 131.4.

Block 8 is 0% full → change −12.5% → r = 115. Empty blocks lower the fee; when demand falls, the price comes back down.

The base fee works like a "posted price" that tracks demand; when blocks are full it reverts to a tip-based auction.

Blockchain Mechanisms

Why Burn? Properties of a Good Fee Mechanism

User incentive compatibility

If demand does not exceed capacity, base fee + a small tip is the best bid; the user need not think "how much should I shade?".

Producer incentive compatibility

The producer earns the most by following the rule: adding fake transactions or withholding transactions does not pay.

Collusion resistance

The producer and users cannot raise their joint gain through off-chain agreements.

  • If the base fee went to the producer, fake transactions would be free (the producer pays itself) and it could inflate the fee at will.
  • With burning, every fake transaction is a real loss of r: 5 fake transactions burn 5r.
  • Not free, but not unlimited either: in a full block the tip race (first price) comes back.

These three properties were formalized by Roughgarden (2021); when block space is scarce, the three cannot all hold together (Chung and Shi, 2023, with the side-contract definition; Chung, Roughgarden and Shi, 2024, with Roughgarden's definition).

Code Trace: The Sandwich Attack and the Slippage Limit

The user will sell 100 A and wants at least 82 B (slippage tolerance). The attacker tries three front-run sizes a.

a = 20: the attacker first sells 20 A and gets 19.61 B. B fell → the price rose.

The user gets 87.54 B (≥ 82, the trade goes through; alone it would get 90.91).

The attacker sells the 19.61 B back for 24.07 A: profit = 24.07 − 20 = 4.07 A.

The result is printed.

a = 50: the attacker first sells 50 A and gets 47.62 B. B fell → the price rose.

The user gets 82.82 B (≥ 82, the trade goes through; alone it would get 90.91).

The attacker sells the 47.62 B back for 59.71 A: profit = 59.71 − 50 = 9.71 A.

The result is printed.

a = 80: the attacker first sells 80 A and gets 74.07 B. B fell → the price rose.

The user would get only 78.47 B < 82 → the trade is reverted and the attack fails (None).

A bigger front-run brings more profit, but the user's slippage limit cuts it off: the attacker's best a pushes the limit exactly. A tight tolerance is a simple defense against MEV.

swap = lambda x, y, dx: y - x * y / (x + dx)  # xy=k
def sandwich(x, y, a, u, min_out):
    b1 = swap(x, y, a)           # front-run: sell a A
    x, y = x + a, y - b1
    b2 = swap(x, y, u)           # user: sell u A
    if b2 < min_out:
        return None              # tx reverted
    x, y = x + u, y - b2
    a2 = swap(y, x, b1)          # back-run: sell b1 B
    return round(a2 - a, 2)
for a in [20, 50, 80]:
    print(a, sandwich(1000, 1000, a, 100, 82))

Scale and Open Questions

Computation and Scale

  • Finding equilibria in large games can be hard (PPAD) → approximate equilibria and learning dynamics.
  • Superhuman results in multiplayer poker came from regret minimization and search (Brown and Sandholm, 2019).
  • Winner determination in combinatorial auctions is NP-hard; bidding languages and approximation algorithms are needed.
  • Latency, data access and energy cost matter as much as theoretical guarantees.

Scale and Open Questions

Winner Determination in Combinatorial Auctions

  • Each bid is a bundle and a value: (Si, vi). Choosing non-overlapping bids that maximize total value is the winner determination problem.
  • It is weighted set packing: NP-hard and, in general, hard to approximate well.
  • Brute force tries 2n subsets for n bids; in practice, solvers prune this search cleverly.
  • VCG payments require solving the problem n + 1 times (removing each bidder once). Solving it approximately can break VCG's truthfulness guarantee.

Code Trace: Greedy Winner Determination

Sorted by value: t1 (10), t2 (4), t3 (4), t4 (3). Total 0, no items used.

t1 = {a, b, c}: no item used yet → taken. Total 10; all three items are now used.

t2 = {a}: a is already used → nonempty intersection, skipped.

t3 and t4 overlap too. Because the big bundle was taken early, all the small bids were left out.

Result 10; the optimum was 11. Greedy by value is fooled by big bundles.

Value per item: t2 and t3 (4), t1 (10/3 ≈ 3.33), t4 (3). On ties, sorted keeps the original order.

t2 = {a} is taken: total 4.

t3 = {b} is taken: total 8.

t1 = {a, b, c}: a and b are used → skipped (even though it is worth 10).

t4 = {c} is free → taken: total 11.

Result 11 = the optimum. But this key can fail too: with ({a, b}, 10) and ({a}, 6) it takes 6 first. Sorting by value/√|S| guarantees a factor of √m in the worst case (Lehmann et al., 2002).

def greedy(bids, key):
    ranked = sorted(bids, key=key, reverse=True)
    total, used = 0, set()
    for S, v in ranked:
        if not (S & used):        # no overlap
            total += v
            used |= S
    return total
T = [({'a','b','c'}, 10), ({'a'}, 4), ({'b'}, 4), ({'c'}, 3)]
print(greedy(T, lambda t: t[1]))
print(greedy(T, lambda t: t[1] / len(t[0])))

Common Mistakes

Forgetting the number of firms

Patience that suffices for two firms does not suffice in a crowded market: the threshold is δ ≥ 1 − 1/n, 0.80 for n = 5.

Confusing finite and infinite horizons

With a finite horizon the last proposer is strong (A gets 18.1 at T = 4); with an infinite horizon the first proposer is slightly ahead (52.6).

Mistaking empirical revenue for true revenue

A price chosen and measured on the same data looks better than it is; separate validation data are needed.

Linear proportions in the exponential mechanism

Probability is proportional to exp(ε·R/2Δ), not to revenue; revenue gaps show up exponentially in probability ratios.

Updating the base fee additively

The change is multiplicative: two full blocks give 100 → 112.5 → 126.6 (not 125). The base fee is burned, not paid to the producer.

Thinking a loose slippage tolerance is safe

It raises the chance that the trade goes through but leaves the attacker more room to front-run.

Appendix

Agent Tournament: A Reproducible Experiment Protocol

Language-model agents are stochastic: the same pairing can score differently on each run. A result is trustworthy if someone else can repeat the experiment and get the same result (reproducibility).

What is recorded
  • A fixed random seed
  • The full text of the prompt
  • Model version and temperature
  • Opponent order and number of rounds: kept fixed and stated in the report
What is reported
  • Each pairing is repeated at least N times (e.g. N = 30)
  • Mean and spread: standard deviation or a 95% confidence interval
  • Code and game logs are shared in a public repository
Example: over 30 repetitions the mean score is 2.6 with standard deviation 0.4. The approximate 95% confidence interval is 2.6 ± 1.96 · 0.4 / √30 ≈ 2.6 ± 0.14, i.e. [2.46, 2.74].

An End-to-End Example: Pizza Voting

Banusausagemushroomolive

  • The model: 3 players; strategy = the reported ranking; payoff = 2, 1, 0 by the true ranking.
  • Plurality: each candidate gets one first place, a 1–1–1 tie.
  • Borda (2, 1, 0): mushroom 3, sausage 4, olive 2 → sausage. Sausage wins both pairwise comparisons 2–1: the Condorcet winner.
Analysis: strategic voting

If Ali buries sausage and reports "mushroom, olive, sausage", the Borda scores become 3–3–3. With alphabetical tie-breaking, mushroom wins: by lying, Ali gets his favorite.

Try it yourself

Console version: read the rankings and tally plurality, two-round runoff, Borda, Condorcet and approval voting side by side. Web version: let the user change one player's report and watch the winner shift. Changing the tie-breaking rule also changes the winner.

Burying in Borda (putting the strongest rival last) is a small instance of the Gibbard–Satterthwaite theorem.
