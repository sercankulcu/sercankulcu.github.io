Foundations

The System Life Cycle

Software goes through a process with the following phases:

Requirements: A project starts by specifying its purpose: which inputs are given, which outputs must be produced?

Analysis: The problem is broken into pieces. There are two approaches: bottom-up or top-down.

Design: Define the data objects (→ ADTs) and operations (→ algorithms); both are language-independent. More time spent on design means fewer errors.

Refinement and coding: Algorithms are coded on the chosen data structures. The data representation determines how efficient the algorithm is.

Verification: Correctness proofs, testing on varied data, and debugging. Each is a research area in its own right.

Horowitz–Sahni, Chapter 1

Foundations

Analysis: Bottom-Up or Top-Down?

Bottom-up

  • Split the problem into pieces and focus on each one separately.
  • Modules are visible right away; the problem is solved module by module.
  • Preferred when we are experienced in the domain.

Top-down

  • Start with a master plan: “What is the goal?”, “What is the final product?”
  • Divide the problem into subproblems; this takes more time.
  • Less backtracking and fewer errors; preferred when we lack experience.
In the design phase we decide which fields a student record has, but we can defer whether to implement it with an array, a linked list or a tree. Deferring lets us pick a more efficient implementation later.

Foundations

Coding and Verification

Correctness proofs

Mathematical techniques prove a program correct; proving a large project end to end is nearly impossible. Using proven algorithms reduces errors.

Testing

Needs working code and test data covering all scenarios. A program that runs without syntax errors is not necessarily correct.

Error removal

When proofs or tests reveal errors, debugging retraces design and coding decisions.

Running time

A correct but slow program is of little value: correctness and efficiency are separate questions.

Foundations

What Is an Algorithm?

An algorithm is a finite sequence of instructions that accomplishes a particular task. Every algorithm must satisfy these criteria:

CriterionMeaning
InputZero or more quantities are supplied externally.
OutputAt least one quantity is produced.
DefinitenessEach instruction is clear and unambiguous: no “add 6 or 7 to x”.
FinitenessIn every case, it terminates after a finite number of steps.
EffectivenessEach instruction is basic enough to be carried out with pencil and paper.
A program that never terminates (e.g. an operating system) is not an algorithm but a computational procedure. We can describe an algorithm in natural language, as a flowchart or in C; we will use C.

Horowitz–Sahni, Chapter 1

Foundations

Abstract Data Types

Data type = objects + operations. An ADT is a data type whose specification of objects and operations is separated from their representation and implementation.

Specification: WHAT?

Operation names, argument types, result type and what each operation does. This is all the user knows.

Implementation: HOW?

How the data is laid out in memory (struct, array…) and the code for the operations. Hidden from the user.

ADT Fraction
  objects: num/den, den ≠ 0
  operations:
    create(p, q)   → Fraction /* constructor */
    add(a, b)      → Fraction /* transformer */
    equal(a, b)    → Boolean  /* observer */
    print(a)                  /* reporter */
    destroy(a)
A constructor creates a new instance, a transformer builds a new value from existing ones, an observer/reporter returns information. The same ADT can be implemented with different data structures.

Horowitz–Sahni, Section 1.3

Abstraction in C: Header File + struct

/* fraction.h : interface (WHAT?) */
#ifndef FRACTION_H
#define FRACTION_H
typedef struct fraction Fraction; /* opaque */

Fraction *fraction_create(int num, int den);
Fraction *fraction_add(const Fraction *a,
                       const Fraction *b);
int  fraction_equal(const Fraction *a,
                    const Fraction *b);
void fraction_print(const Fraction *f);
void fraction_free(Fraction *f);
#endif
/* fraction.c : implementation (HOW?) */
#include <stdio.h>
#include <stdlib.h>
#include "fraction.h"

struct fraction { int num, den; };

Fraction *fraction_create(int num, int den) {
  Fraction *f;
  if (den == 0) return NULL;
  f = malloc(sizeof *f);
  if (f == NULL) return NULL;
  f->num = num;
  f->den = den;
  return f;
}
typedef struct fraction Fraction; declares an incomplete (opaque) type: a file that includes fraction.h cannot see the fields and only holds a Fraction *. The fields stay hidden in fraction.c → C’s counterpart of an ADT.

Foundations

The Rest of the Implementation, and Its Use

Fraction *fraction_add(const Fraction *a,
                       const Fraction *b) {
  return fraction_create(
      a->num * b->den
        + b->num * a->den,
      a->den * b->den);
}
int fraction_equal(const Fraction *a,
                   const Fraction *b) {
  return a->num * b->den
      == b->num * a->den;
}
void fraction_print(const Fraction *f) {
  printf("%d/%d\n", f->num, f->den);
}
void fraction_free(Fraction *f) { free(f); }
/* main.c : knows only the interface */
#include "fraction.h"
#include <stddef.h> /* NULL */
int main(void) {
  Fraction *a = fraction_create(1, 2);
  Fraction *b = fraction_create(1, 3);
  Fraction *s = NULL;
  if (a && b) s = fraction_add(a, b);
  if (s) fraction_print(s);  /* 5/6 */
  fraction_free(a); fraction_free(b);
  fraction_free(s);  /* free(NULL) is safe */
  return 0;
}
Contract

fraction_create returns NULL if the denominator is 0 or memory runs out; the caller checks.

Ownership

Every result of create/add belongs to the caller and is released with fraction_free.

Selection Sort

Selection Sort

We want to sort an array into ascending order. Each pass finds the smallest of the remaining elements and moves it to the front (position i):

for (i = 0; i < n; i++) {
    examine list[i] to list[n-1];
    let list[min] be the smallest integer;
    interchange list[i] and list[min];
}
Instructor“Aim for the level where you can find fault with published algorithms and offer better ones.”

Selection Sort in C

#include <stdlib.h>

#define SWAP(x, y, t) ((t) = (x), (x) = (y), (y) = (t))

int main(void) {
  int i, n, list[MAX_SIZE];
  printf("Enter the array size: ");
  if (scanf("%d", &n) != 1 || n < 1 || n > MAX_SIZE) {
    printf("Invalid value of n!\n");
    return 1;
  }
  for (i = 0; i < n; i++) list[i] = rand() % 100;
  sort(list, n);
  for (i = 0; i < n; i++) printf("%d ", list[i]);
  return 0;
}
void sort(int list[], int n) {
  int i, j, min, temp;
  for (i = 0; i < n - 1; i++) {
    min = i;
    for (j = i + 1; j < n; j++)
      if (list[j] < list[min])
        min = j;
    SWAP(list[i], list[min], temp);
  }
}
Comparisons: (n−1) + (n−2) + … + 1 = n(n−1)/2 → O(n²). At most n−1 swaps.

Selection Sort

SWAP: Macro or Function?

Macro

#define SWAP(x, y, t) \
        ((t) = (x), (x) = (y), (y) = (t))

int temp;
SWAP(list[i], list[min], temp);
  • No call overhead: the preprocessor substitutes the text.
  • The temporary t is supplied by the caller.

Function

void swap(int *x, int *y) {
  int temp = *x;
  *x = *y;
  *y = temp;
}

swap(&list[i], &list[min]);
  • Type-checked; temp is local.
  • We must pass the addresses of the variables.
A macro may evaluate its arguments more than once: SWAP(a[i++], a[j], t) increments i twice! A function named SWAP would clash with the macro, so the function is called swap.

Selection Sort · Run the code step by step

Code Trace: swap(&a, &b)

In main’s frame, a = 3 and b = 8.

The call copies addresses, not values. x → a, y → b.

temp = *x: read the value x points to (3).

*x = *y: the 8 that y points to is written where x points, i.e. into a.

*y = temp: 3 goes into b. The swap happened in main’s variables.

swap’s frame is gone (x, y, temp), but its effect remains.

void swap(int *x, int *y) {
  int temp = *x;
  *x = *y;
  *y = temp;
}

int main(void) {
  int a = 3, b = 8;
  swap(&a, &b);
  printf("%d %d\n", a, b);
}

Performance Analysis

How Do We Judge a Program?

  1. Does it meet the specification?
  2. Does it work correctly?
  3. Is it documented (with comments) so others can use it?
  4. Does it use functions effectively to produce logical units?
  5. Is the code readable?
  6. Does it use primary and secondary memory efficiently?
  7. Is its running time acceptable?
1 · Performance analysis

Machine-independent: estimates of time and space (complexity).

2 · Performance measurement

Machine-dependent: the actual running time is measured.

The last two questions are the subject of performance evaluation; the first five matter at least as much.

Performance Analysis

Space Complexity

The amount of memory a program needs to run to completion: S(P) = c + SP(I)

Fixed part c

Independent of input/output size: the code itself, simple variables, constants.

Variable part SP(I)

Depends on characteristics of input I (usually its size). This is what we analyze.

float abc(float a, float b, float c) {
  return a + b + b * c
         + (a + b - c) / (a + b) + 4.00;
}
/* fixed space only: S_abc(I) = 0 */
Instructor“Write code as if every resource were scarce. Plenty of memory is no excuse for wasting it.”

Performance Analysis

sum and rsum: Variable Space

float sum(float list[], int n) {
  float tempsum = 0;
  int i;
  for (i = 0; i < n; i++)
    tempsum += list[i];
  return tempsum;
}

float rsum(float list[], int n) {
  if (n)
    return rsum(list, n - 1) + list[n - 1];
  return 0;
}
  • sum receives the address of the first element → Ssum(n) = 0. If the elements were copied by value, Ssum(n) would be n.
  • rsum(list, n) is called n+1 times in all; each call pushes a stack frame → Srsum(n) ∝ n.

Performance Analysis

Time Complexity

T(P) = compile time + run time. A program is compiled once; we care about the run time tP.

tP(n) = ca·ADD(n) + cs·SUB(n) + cl·LDA(n) + cst·STA(n)
Constants c

The time of each operation depends on the compiler and the machine; hard to know in advance.

Step count

Instead we count program steps: a meaningful, machine-independent unit.

Instructor“Why does performance matter so much? Suppose you are programming a fighter jet’s bombing system. If yours releases in 3 s and the enemy’s in 2 s, the battle is lost before it starts.”

rsum (2n+2) seems to take “fewer steps” than sum (2n+3), yet each recursive call (frame setup, return) costs more than one loop iteration.

Asymptotic Notation

Big-O Notation

Definition: f(n) = O(g(n)) if there exist constants c > 0 and n0 such that f(n) ≤ c·g(n) for all n ≥ n0: “the algorithm has complexity of order g(n)”.

  • Tsum(n) = 2n + 3 = O(n)
  • Trsum(n) = 2n + 2 = O(n)
  • Tadd = 2·rows·cols + 2·rows + 1 = O(rows·cols) → O(n²)
Instructor“Time matters more than memory!”

O is an upper bound; here “=” means “is a member of” and reads one way only.

Asymptotic Notation

Example: f(n) = 3n³ + 6n² + 7n = O(n³)

Bound the lower-order term 7n by n²: 7n ≤ n² whenever n ≥ 7.

6n² + n² = 7n².

Same trick once more: 7n² ≤ n³ for n ≥ 7.

We found c = 4 and n₀ = 7: the definition holds.

1 · Upper bound

The running time never exceeds 4n³ steps (n ≥ 7).

2 · Cubic growth

If sorting 100 numbers takes 2 s, sorting 300 takes at most 2·3³ = 54 s (not 6 s!).

A First Look at Amortized Analysis

Some operations are occasionally expensive but usually cheap. Amortized analysis divides the total cost of a sequence of n operations by n. Example: an array whose capacity doubles when full (realloc); we trace it and count its copies in Chapter 2.

Over n insertions the copies are 1 + 2 + 4 + … < 2n → total < 3n. A single insertion may take O(n), but the amortized cost per insertion is O(1). (Growing the capacity by a constant amount would give O(n).)

Magic Square

The Magic Square Problem

Every row, column and diagonal: 65

Place the numbers 1 to n² in an n×n square so that every row, every column and both main diagonals have the same sum: n(n²+1)/2 (65 for 5×5).

Coxeter’s rule (n odd; also known as the Siamese or de la Loubère method): put 1 in the middle of the first row. Always move diagonally up and to the left; if that square is taken, move down from the current square instead. Moves off the square wrap around to the opposite edge. It finishes in n² steps → O(n²).

Brute force: (n²)! arrangements. 25! ≈ 1.55·10²⁵ possibilities; at 10⁹ tries per second that is ≈ 1.55·10¹⁶ s ≈ 4.9 million centuries.

Magic Square

“Computers Are Fast, It’ll Solve It Instantly!”?

A common objection: a new 10 GHz computer will solve this right away; no need to bother with algorithms.
A machine 10× faster

4.9 million centuries → about 490 thousand centuries. Still hopeless.

The right algorithm

Coxeter’s rule: 25 steps, under a microsecond. Algorithms come before hardware.

Calculation: 25! / (10¹⁰ · 3.15·10⁹) ≈ 4.9·10⁵ centuries.

Magic Square · Run the code step by step

Code Trace: magic(3, sq)

Middle of the first row: i = 0, j = 1 → write 1.

s = 2: the up-left square (2, 0) is free (row wrapped → bottom row) → move there.

s = 3: the up-left square (1, 2) is free (column wrapped → rightmost column) → move there.

s = 4: the up-left square (0, 1) is taken (it holds 1) → one down: (2, 2).

s = 5: the up-left square (1, 1) is free → move there.

s = 6: the up-left square (0, 0) is free → move there.

s = 7: the up-left square (2, 2) is taken (it holds 4) → one down: (1, 0).

s = 8: the up-left square (0, 2) is free (column wrapped → rightmost column) → move there.

s = 9: the up-left square (2, 1) is free (row wrapped → bottom row) → move there.

s = 10 > 9: the loop ends. Every row, column and diagonal sums to 15 = 3·(9+1)/2.

void magic(int n, int sq[][MAX]) {
  int i = 0, j = (n - 1) / 2, s, r, c;
  sq[i][j] = 1;       /* sq must be all zeros */
  for (s = 2; s <= n * n; s++) {
    r = (i - 1 < 0) ? n - 1 : i - 1; /* up */
    c = (j - 1 < 0) ? n - 1 : j - 1; /* left */
    if (sq[r][c]) i = (i + 1) % n; /* down */
    else { i = r; j = c; }
    sq[i][j] = s;
  }
}

Number of processor clock ticks used by the program. Resolution is limited by the system’s tick interval.

time()

Wall-clock time with one-second resolution. Fine for long jobs, too coarse for short ones.

CLK_TCK is an old, nonstandard name; standard C uses CLOCKS_PER_SEC. I/O devices (screen, disk, printer) are slow: keep printf calls outside the timed region.

Exercise 1: Timing Selection Sort

#include <stdio.h>
#include <time.h>
#define MAX_SIZE 5001
#define ITERATIONS 20
void sort(int list[], int n);   /* selection sort */

int main(void) {
  int i, j, list[MAX_SIZE];
  int sizelist[] = { 0, 100, 300, 600, 900, 1200, 1500, 2000,
    3000, 3100, 3200, 3300, 3400, 3500, 3600, 3700, 3800,
    3900, 4000, 5000 };
  clock_t start, stop;  double ms;
  for (i = 0; i < ITERATIONS; i++) {
    for (j = 0; j < sizelist[i]; j++)
      list[j] = sizelist[i] - j;   /* descending */
    start = clock();
    sort(list, sizelist[i]);
    stop = clock();
    ms = 1000.0 * (stop - start) / CLOCKS_PER_SEC;
    printf("%4d elements: %6.1f ms\n", sizelist[i], ms);
  }
  return 0;
}
  • 20 values of n; for each, an array in descending order.
  • Only the sort call lies between the two clock() calls.
  • Writing (int)(1000*(stop-start)/CLK_TCK) drops the fraction through integer division; double arithmetic with 1000.0 is more accurate.

int seqsearch(int list[], int searchnum, int n) {
  int i;
  list[n] = searchnum;          /* sentinel */
  for (i = 0; list[i] != searchnum; i++)
    ;
  return (i < n) ? i : -1;
}

Solutions and Common Mistakes

long fact(long n) {
  if (n <= 1) return 1;
  return n * fact(n - 1);
}

long fib(long n) {
  if (n <= 1) return n;   /* f0 = 0, f1 = 1 */
  return fib(n - 1) + fib(n - 2);
}

long binom(int n, int m) {
  if (m == 0 || m == n) return 1;
  return binom(n - 1, m) + binom(n - 1, m - 1);
}
fib: + not *

A common mistake is writing fib(n-1) * fib(n-2); the product is always 0 or 1. By definition it must be a sum.

binom: parameters

A common mistake is writing long binom() with no parameters; n and m must be parameters.

Cost

fact is O(n); fib and binom as written are exponential: the same subproblems are solved again and again.

Summary

Common Mistakes

1Thinking “it compiled and ran, so it’s correct”: test data must cover every scenario.
2Confusing step counts with constants: 2n + 3 and 100n are in the same class, O(n).
3Finding O(n²) and calling it “the best bound”: write the smallest g(n) you can; use Θ for a tight bound.
4Timing a short job with a single clock() pair: the result is 0 or a multiple of the tick.
5Leaving printf in the timed region: I/O time swamps the algorithm.
6Passing an argument with side effects to a macro: SWAP(a[i++], …).

Exercises

  1. How many times does x++ execute in for (i = 0; i < n; i++) for (j = 0; j < i; j++) x++;? O(?)
  2. Show that 10n² + 100n + 1000 = O(n²) by giving c and n₀.
  3. How many comparisons does selection sort make on an already sorted array? Does it have a best case?
  4. An O(n log n) algorithm takes 10 ms for n = 1000. About how long for n = 10⁶?
  5. Why is calling rsum with n = 10⁶ dangerous?
  6. Write the first row of a 7×7 magic square using Coxeter’s rule (what must the sum be?).
Show answers / hints
  1. n(n−1)/2 → Θ(n²).
  2. 10n² + 100n + 1000 ≤ 1110n² for n ≥ 1: c = 1110, n₀ = 1 (other choices work too).
  3. Still n(n−1)/2; the comparison count does not depend on the input (only the swap count does).
  4. The ratio (10⁶·log 10⁶)/(10³·log 10³) = 2000 → ≈ 20 s.
  5. 10⁶ frames may overflow the stack; the iterative sum is safe.
  6. Sum 7·50/2 = 175; first row: 28 19 10 1 48 39 30.

Chapter Summary

Process

Requirements → analysis → design → coding → verification. Deferring the implementation leads to better choices.

Abstraction

ADT = specification ⟂ implementation. In C: a header file + an opaque struct.

Counting

Space: c + SP(I). Time: program steps (sum 2n+3, rsum 2n+2).

Classifying

O upper, Ω lower, Θ tight bound. The worst case is a guarantee; amortized analysis looks at the whole sequence.

Growth

Small n misleads; 2ⁿ and n! quickly become hopeless. Algorithms come before hardware.

Measurement

clock() + repetition + averaging; keep I/O out of the timing.
