Chapter 19: Basic Sorting Algorithms

Sorting is one of the most common things a computer does. This note first sets up the vocabulary of sorting: record, key, internal and external sorting, stability, and in-place sorting. It then writes the three basic algorithms, selection sort, insertion sort, and bubble sort, in C and traces them step by step on small arrays. For each one it computes the number of comparisons and moves in the best, worst, and average case. The average case of insertion sort is derived as an expected value over all permutations. The notion of an inversion ties the three algorithms to a single measure. Counting sort and bucket sort make no comparisons and run in linear time when the range or distribution of the data is known. Shell sort uses gapped insertion sort to destroy inversions quickly. The note ends with a theorem proved by a decision tree: no comparison-based sorting algorithm can use fewer than ⌈lg n!⌉ comparisons in the worst case.

19.1Sorting concepts

Names in a phone book, the results list of an exam, the pages returned by a search engine, a shop's products ordered by price: all of these are sorted data. Sorted data offers two big conveniences. First, searching gets faster. In a sorted array, binary search reaches its answer in O(lg n) steps, while in an unsorted array every element has to be examined. Second, many questions answer themselves on sorted data. The smallest and largest values sit at the two ends of the array. Equal values land next to each other, so finding duplicates takes a single pass. The common elements of two lists can be found by walking both sorted lists at once.

Sorting algorithms are also the best training ground for algorithm analysis. The problem is easy to understand and the solutions are short, yet their costs differ enormously. One algorithm sorts the same thousand numbers with half a million comparisons, another with fifteen thousand. This note first builds a common vocabulary. It then studies three basic algorithms in detail, followed by two algorithms that make no comparisons and by Shell sort. It closes with the lower bound that every comparison sort must obey.

19.1.1Record, field, and key

What gets sorted is often not individual numbers. A student-records program keeps a student's number, first name, surname, and grade average together. Each of these items is called a field, and the whole set of fields belonging to one student is a record. In C, a record is naturally represented by a struct:

typedef struct {
    int    no;          /* key */
    char   name[20];
    char   surname[20];
    double avg;
} student;

A collection of records held in memory is called a list; when the records are kept outside memory, for example on disk, the collection is called a file. Sorting is always done on one field or on several of them.

Definition 19.1

A field, or a group of fields, that distinguishes a record from all others, that is, identifies it uniquely, is called a key. Sorting is rearranging a list of n records so that their keys are in increasing (or decreasing) order.

Figure 19.1 shows three student records. The student number is the key: two students may have the same first name and surname, but not the same number. Name, surname, and average are data fields. Sorting compares only the keys, but all the fields of a record move together with the key. This distinction creates two costs: the cost of comparing keys and the cost of moving records. If the records are large, the second can dominate.

In real programs the key does not have to be unique. Students can also be sorted by grade average, and two students may have the same average. In that case the word "key" means the field the sorting is based on. What order records with equal keys keep after sorting is a matter of stability.

Sorting is also divided in two by where the data lives. In internal sorting all the data is in main memory and any element is reached in constant time. In external sorting the data does not fit in memory, and auxiliary storage such as a disk or tape is used. Reading one block from disk takes longer than thousands of comparisons in memory, so in external sorting the cost is determined by the number of disk accesses, not the number of comparisons. This note is about internal sorting. Still, its ideas are also the basis of external sorting: external sorting algorithms sort the pieces that fit in memory with an internal sort, then merge the sorted pieces.

19.1.2What do we measure?

Measuring the running time of a sorting algorithm directly in seconds is misleading, because the time varies with the machine, the compiler, and the input. Instead we count the basic operations the algorithm performs. Sorting has two basic operations:

  • Comparison. The order of two keys is queried, as in a[j] < a[min]. Comparison-based algorithms learn about the input only through such queries.
  • Move. An element is written to another place in the array. A swap consists of three assignments; the shifting in insertion sort is a single assignment. In this note, "move" covers both; when it matters, we say which one is counted.

An algorithm's running time is proportional to the sum of these two counts. Which one matters more depends on the data. If the keys are long strings, comparison is expensive. If the records are large, moving is expensive. On flash memory, every write wears the cell a little, so reducing the number of writes is valuable in its own right. Counts are given for three cases. The best case is the input on which the algorithm does the least work, the worst case the input on which it does the most. The average case is the expected work under the assumption that all possible inputs are equally likely. This definition of the average case matters, and it is worked out in detail for insertion sort.

19.1.3Stability

Definition 19.2

A sorting algorithm is stable if records with equal keys keep, after sorting, the relative order they had before. Precisely: if i < j in the input and the keys of a[i] and a[j] are equal, then a[i] also comes before a[j] in the output.

Figure 19.2 illustrates the definition with a small example. The input has five records; the number is the key, and the letter is added only to tell the records apart. 3a and 3c have the same key, and 3a comes first in the input. A stable algorithm also puts 3a before 3c in the output: 1b 1e 2d 3a 3c. Selection sort, however, produces 1b 1e 2d 3c 3a. The output is correctly sorted by key, but 3c has moved ahead. How selection sort arrives at this result is shown step by step once the algorithm is introduced.

When bare numbers are sorted, stability does not matter: there is no way to tell two 3s apart. Stability becomes important when the records have fields other than the key. The best-known use is sorting on several fields.

Example 19.1

A class list is to be sorted by surname, and students with the same surname by first name. The list consists of (first name, surname) pairs: (Mehmet, Kaya), (Ali, Yılmaz), (Zeynep, Kaya), (Ayşe, Yılmaz), (Can, Demir).

First the whole list is sorted by first name: (Ali, Yılmaz), (Ayşe, Yılmaz), (Can, Demir), (Mehmet, Kaya), (Zeynep, Kaya). Then the same list is sorted by surname with a stable algorithm. Demir is alone and moves to the front. The relative order of the two Kayas is preserved: after the first step Mehmet was before Zeynep, and he stays there. For the two Yılmazes, Ali also stays before Ayşe. The result: (Can, Demir), (Mehmet, Kaya), (Zeynep, Kaya), (Ali, Yılmaz), (Ayşe, Yılmaz). The surnames are in order, and those with the same surname are in first-name order.

If the second sort were unstable, the work of the first sort could be wasted: Zeynep Kaya could move ahead of Mehmet Kaya.

Note the order in the example: first the secondary field (first name) is sorted, then the primary field (surname). The last sort dominates, and the earlier ones remain to break ties. Radix sort applies the same idea to the digits of numbers. Numbers are sorted first by the ones digit, then by the tens digit, and finally by the most significant digit; a stable algorithm is used in each pass. That is exactly why the algorithm used in each pass must be stable.

19.1.4In-place sorting

Definition 19.3

A sorting algorithm that uses only a constant amount of extra memory beyond the array holding the input, that is, O(1), is called an in-place algorithm. Some sources also count O(lg n) extra memory as in-place, to allow for a recursion stack.

Selection, insertion, and bubble sort are in place: apart from a few loop variables and one temporary variable for swapping, they need no memory. Counting sort is not in place; it writes its output to a separate array b and uses an array c for the counters. Bucket sort also needs O(n) extra memory for the buckets and nodes. When memory is scarce, for example in an embedded controller, an in-place algorithm may therefore be the only option.

19.1.5Shared infrastructure: the less and SWAP macros

The comparison-based algorithms in this note use the same two building blocks: less, which compares two elements, and SWAP, which swaps two elements. Both are macros of the C preprocessor. A macro is an abbreviation that is replaced as text before compilation; it has no function-call cost.

#define N 15
#define less(A, B) ((A) < (B))
#define SWAP(A, B) do { int t_ = (A); (A) = (B); (B) = t_; } while (0)
  • Line 1. N is the number of elements the test program will sort.
  • Line 2. less(A, B) yields 1 if A < B and 0 otherwise. Parenthesizing the parameters and the whole expression is deliberate. A macro is expanded as text. With an unparenthesized definition, the call less(x & 1, y) would turn into the text x & 1 < y. Since the < operator is applied before & in C, this expression would be evaluated as x & (1 < y). When the algorithms do their comparisons through this macro, changing the comparison criterion is a one-line job. For example, to sort from largest to smallest, it is enough to write > instead of < in the definition.
  • Line 3. SWAP(A, B) saves the value of A in the temporary t_, writes B into A, and writes the old A into B. Three assignments are made. This version takes two arguments and uses int as the element type; for other element types, change the int in the definition.

Wrapping the body of the macro in do { … } while (0) looks odd at first. The loop runs once and nothing repeats. Its purpose is to make the macro a single statement syntactically. Let us see what would happen if the body were written with braces alone:

#define SWAP(A, B) { int t = A; A = B; B = t; }

if (a[0] > a[1])
    SWAP(a[0], a[1]);
else
    puts("sorted");

The preprocessor turns the line SWAP(a[0], a[1]); into the text { int t = a[0]; a[0] = a[1]; a[1] = t; };. The semicolon after the block is an empty statement and ends the if statement. The else that follows is left dangling, and the compiler reports an error. With the do { … } while (0) form, the trailing semicolon closes the while (0), and the if–else structure stays intact. This idiom is established practice in C for macros made of several statements.

In the algorithms the two macros often appear together: if (less(A, B)) SWAP(A, B);. This line swaps the two elements if A < B. The pattern is called compare-exchange. One has to watch its direction: if A is to the right of B in the array, this line moves the smaller element to the left. The line if (less(a[j], a[j - 1])) SWAP(a[j], a[j - 1]); in bubble sort is exactly that: if the right element a[j] is smaller than the left one, they trade places.

Common mistake

Passing an argument with side effects to a macro. A macro is not a function; arguments are copied as text without being evaluated. In the call SWAP(a[i++], a[j]), the text a[i++] appears twice in the body, so i is incremented twice and the swap is done with the wrong elements. With a = {10, 20, 30, 40}, i = 0, and j = 3, after this call i is 2 and the array becomes {10, 40, 30, 10}: 20 is lost and 10 is written twice. If a macro whose body contains its argument twice is given f(x), f is also called twice. Macro arguments should always be simple expressions without side effects.

The main program used to test the algorithms is also short:

int main(void) {
    int *a = malloc(N * sizeof *a);
    if (a == NULL) return 1;
    for (int i = 0; i < N; i++)
        a[i] = rand() % 50;
    selection(a, 0, N - 1);   /* call the sorting routine */
    for (int i = 0; i < N; i++) printf("%d ", a[i]);
    free(a);
    return 0;
}
  • Lines 2–3. An array of N integers is allocated from the heap. sizeof *a is the size of the element a points to, that is, sizeof(int). This form stays correct automatically if the array's type changes. If malloc finds no memory, it returns NULL; the program then exits with code 1. Without the check, writing a[i] would try to write to the NULL address and the program would crash.
  • Lines 4–5. The array is filled with random numbers between 0 and 49. rand() produces the same array on every run, because no seed (srand) is given. This is a convenience in testing: when a bug is found, the same input can be reproduced.
  • Line 6. The sorting routine is called. All routines sort the part a[L..R] of the array; to sort the whole array, pass L = 0 and R = N − 1. This interface also makes it possible to sort only a part of an array. Algorithms such as quicksort hand small parts over to insertion sort through this interface.
  • Lines 7–8. The result is printed and the memory is released. If free is forgotten, nothing happens in a small program. But if the same code is called repeatedly in a long-running program, memory leaks accumulate.

The program is compiled with the stdio.h and stdlib.h headers. The numbers rand() produces vary with the C library. On Linux (glibc) the output is 9 12 13 15 21 27 27 33 35 36 36 40 42 43 49; in another library, for example on Windows, the numbers are different.

19.2Selection sort

19.2.1Idea and code

Selection sort is perhaps the most natural way to sort. Someone putting a stack of exam papers on a desk into order of student number first looks for the paper with the smallest number and puts it on top. Then among the rest, they look for the smallest and put it second. This goes on until the papers run out. The algorithm takes three sentences to state:

  1. Find the element with the smallest value in the list.
  2. Swap it with the element in the first position.
  3. Repeat the same steps for the remaining sublist, starting from the second element.

The implementation in C:

void selection(int a[], int L, int R) {
    for (int i = L; i < R; i++) {
        int min = i;
        for (int j = i + 1; j <= R; j++)
            if (less(a[j], a[min]))
                min = j;
        SWAP(a[i], a[min]);
    }
}
  • Line 2. The outer loop walks i over the position where the next smallest element will settle. i goes up to R − 1, not to R. Once n − 1 elements are in place, the last one is necessarily in the right place: the one remaining element is the largest.
  • Line 3. min holds the index of the smallest element seen so far. Initially the candidate is the first element of the remaining sublist, a[i].
  • Lines 4–6. The inner loop scans the rest of the remaining sublist, a[i+1..R]. When a smaller element is seen, min is updated to its index. The comparison is made with the less macro, that is, with strict "less than": an equal element does not change min.
  • Line 7. The smallest element is swapped with a[i]. If min == i, the swap exchanges the element with itself; the array does not change, but the three assignments are still made.

The correctness of the algorithm is shown with a loop invariant. An invariant is a property that stays true at the end of every iteration of the loop.

At the end of each outer pass, a[L..i] is sorted and contains the i − L + 1 smallest elements of the array.

After the first pass, a[L] holds the minimum of the whole array; a one-element part is sorted. If the invariant holds for i − 1 at the start of a pass, the pass finds the smallest of the remaining elements and puts it in a[i]. This element is not smaller than any element in a[L..i−1] (those were chosen earlier) and is not larger than any of the remaining ones. The invariant therefore holds for i too. When the loop ends with i = R − 1, a[L..R−1] is sorted and carries the n − 1 smallest elements; the remaining a[R] is the largest. The array is sorted.

A notable property of selection sort is that it never looks at the state of the input. To select the minimum, the remaining sublist has to be scanned to the end in every pass. Even if the array is sorted from the start, the algorithm does not notice, because it learns that "no smaller element remains" only when it finishes the scan.

19.2.3Analysis

In pass i, the inner loop runs for j = i + 1, …, R. In an array of n elements (L = 0, R = n − 1), the first pass makes n − 1 comparisons, the second n − 2, and the last 1:

C(n) = (n − 1) + (n − 2) + … + 2 + 1 = n(n − 1)/2 ≈ n²/2

This total is the sum of the first n − 1 natural numbers. The familiar way to find it is to write the terms again in reverse order and add them column by column. Each column sums to n, and there are n − 1 columns. Twice the sum is n(n − 1), so the sum itself is half of that.

The number of comparisons is independent of the input: whether the array is sorted, reverse sorted, or random, the inner loop runs the same number of times. For selection sort the best, average, and worst cases are the same, and all are Θ(n²). The number of swaps is exactly n − 1: one swap per outer pass, and there is no pass for the last element. Some of them are swaps of an element with itself; guarding the code with if (min != i) avoids the needless swaps, but adds a comparison to every pass. The extra memory is only i, j, min, and the temporary variable of the swap: O(1). The algorithm is in place.

On flash memory every write wears the cell. In such cases the n − 1 swaps of selection sort are much cheaper than the moves of the other basic algorithms, which are of order n².

Selection sort is not stable. The cause is the long-distance swap. There can be many elements between a[i] and a[min]. a[i] jumps over them and may land behind an element with an equal key. On the input of Figure 19.2 (3a, 1b, 3c, 2d, 1e), this can be seen step by step:

  • Pass 0. The minimum is 1b (min = 1). 3a and 1b are swapped: (1b, 3a, 3c, 2d, 1e).
  • Pass 1. The smallest of the rest is 1e (min = 4). 3a and 1e are swapped: (1b, 1e, 3c, 2d, 3a). 3a jumped over 3c and 2d to the very end. Stability was broken at this step.
  • Pass 2. The minimum is 2d. 3c and 2d are swapped: (1b, 1e, 2d, 3c, 3a).
  • Pass 3. less(3a, 3c) is false; min does not change and the swap is with itself. The result is (1b, 1e, 2d, 3c, 3a).

On this input the order of 1b and 1e is preserved, but that is a coincidence. Stability is a property that must hold for all inputs; a single counterexample makes an algorithm unstable. The smallest counterexample has three elements and is taken up in the exercises.

19.3Insertion sort

19.3.1Idea and code

Insertion sort is the way someone playing cards arranges the cards in their hand. The cards are picked up from the table one by one. The cards in hand are sorted at every moment; the new card is inserted at the right place among them. To do this, the cards larger than the new one are pushed one place to the right and the new card is put into the gap that opens.

The same is done in an array. A sorted prefix grows at the left of the array. Initially the prefix is just the first element, and a single element is always sorted. In each pass, the element right after the prefix is taken and inserted into its place within the prefix. At the end of the pass the prefix is one element longer. The first of the two versions is this:

void insertion(int a[], int L, int R) {
    for (int i = L + 1; i <= R; i++) {
        int v = a[i];      // element to insert
        int j = i - 1;     // a[L..i-1] is sorted
        while (j >= L && a[j] > v) {
            a[j + 1] = a[j]; // shift right
            j--;
        }
        a[j + 1] = v;
    }
}
  • Line 2. i is the index of the element to be inserted and starts at L + 1. At this moment a[L..i−1] is sorted.
  • Line 3. The value to be inserted is saved in v. This step is mandatory: the first shift overwrites a[i] and the value would be lost.
  • Line 4. j starts at the right end of the prefix and moves left.
  • Line 5. The loop runs as long as two conditions are both true: j is inside the subarray (j >= L) and a[j] is greater than v. C's && operator short-circuits: if the first condition is false, the second is never evaluated. When j drops to L − 1, a[j] is not read; if it were, the access would go outside the array.
  • Lines 6–7. The element greater than v is shifted one place to the right and j is decremented. A shift is a single assignment, not a swap.
  • Line 9. When the loop ends, either a[j] is not greater than v or j is to the left of the subarray. In both cases the place of v is j + 1.

The loop invariant this time is: at the start of each pass of the outer loop, a[L..i−1] is the sorted version of the elements that were in those positions in the input. The difference from selection sort's invariant is important. In insertion sort the prefix is sorted, but it need not contain the smallest elements of the array: a small element arriving later can enter at the very front of the prefix. The algorithm does not know for certain the final place of any element until the last pass.

Common mistake

Writing the loop condition as j >= 0. When the whole array is sorted, L = 0, so the bug is invisible. When the routine is called on a subarray, for example insertion(a, 2, 5), j passes to the left of L and goes down to a[0] and a[1]. These elements do not belong to the part being sorted; the shifting corrupts them. The correct bound is j >= L. For a = [9, 8, 7, 1, 6, 5, 0], insertion(a, 2, 5) with the correct code gives [9, 8, 1, 5, 6, 7, 0]: only a[2..5] is sorted.

The trace counted 7 shifts and 9 comparisons. The number of shifts is no coincidence: 7 is the number of inverted pairs in the array. This connection is proved separately together with the notion of an inversion. The number of comparisons is slightly more than the number of shifts. A pass ends either when a[j] > v turns out false, and this last test is a comparison without a shift; or when j runs off the beginning of the array, in which case there is no extra comparison. Here the passes i = 2 and i = 3 ended the first way, and the passes i = 1 and i = 4 the second way. The comparison count came to 7 + 2 = 9.

19.3.3The sentinel version: insertion1

Each step of the inner loop makes two tests: j >= L and a[j] > v. The first is useful only if v will go all the way to the beginning of the array. That happens only when v is the smallest of the elements seen so far. If the smallest element of the array is placed at a[L] from the start, no v can pass to its left; a[L] stops every loop by itself. Such an element is called a sentinel. The second version uses this idea:

void insertion1(int a[], int L, int R) {
    for (int i = R; i > L; i--) // sentinel
        if (a[i] < a[i-1]) SWAP(a[i], a[i-1]);
    for (int i = L + 2; i <= R; i++) {
        int v = a[i], j = i;
        while (less(v, a[j - 1])) {
            a[j] = a[j - 1];
            j--;
        }
        a[j] = v;
    }
}
  • Lines 2–3. Preparation pass: neighbors are compared from the right end of the array to the left, and the right one is swapped if it is smaller. This single pass carries the smallest element to a[L] like a bubble. It makes n − 1 comparisons and at most n − 1 swaps.
  • Line 4. The main loop starts at L + 2. After the preparation pass a[L] is the smallest, so a[L..L+1] is already sorted.
  • Lines 5–10. In the inner loop only less(v, a[j − 1]) is tested. When j drops to L + 1, a[L] cannot be greater than v, so the condition becomes false and the loop stops. It is impossible for j to pass to the left of L.

This version is faster for two small reasons. The inner loop makes one test fewer per step; when the loop runs thousands of times, the difference is measurable. Also, since the condition is a single comparison, the compiler can compile the loop more tightly. The price is the preparation pass's extra n − 1 comparisons. The sentinel idea is not specific to sorting. In linear search on an array, if the sought value is temporarily written at the end of the array, the loop does not have to ask "is the array finished?" at every step. In linked lists, a header node does the same job: even when the list is empty, the first node has a predecessor and the special case disappears.

19.3.4Best and worst case

Unlike selection sort, the work of insertion sort depends heavily on the input. Figure 19.5 puts the two extreme cases side by side.

Best case: sorted input. In every pass v is compared with the rightmost element of the prefix. That element is less than or equal to v; the loop never runs and v stays where it is. One comparison is made in each of the n − 1 passes, and no shifts. The total is n − 1 comparisons; the running time is Θ(n). No algorithm can do better: to be sure the array is sorted, every element must be looked at at least once.

Worst case: reverse-sorted input. Every new element is smaller than all those seen so far. In pass i, v is compared with all i elements of the prefix, all of them shift one place right, and v is written at the very front. The total is

1 + 2 + … + (n − 1) = n(n − 1)/2

comparisons and the same number of shifts. The running time is Θ(n²). For n = 1,000 that is 499,500 comparisons and 499,500 shifts.

Insertion sort is stable. The condition of the inner loop is a strict inequality: a[j] > v. When an element equal to v is met in the prefix, the condition becomes false and v is written to the right of that element. An element that comes later in the input stays later in the output. If the condition were a[j] >= v, v would jump over the equal elements and land to their left; the array would still be sorted, but stability would be lost and needless shifts would be made. The algorithm is in place: it uses no memory beyond i, j, and v.

The real strength of insertion sort is "nearly sorted" data. If every element is a few positions from its final place, each pass ends in a few steps and the total work stays close to n. Applications that add an occasional new record to a sorted list, algorithms that make a final pass over a mostly sorted array, and small subarrays are in this situation. Practical implementations of quicksort switch to insertion sort when the parts fall below 10–20 elements.

19.3.5Average case: an example

The best case is n − 1 comparisons, the worst case n(n − 1)/2. How many comparisons should we expect for a random input? The first idea that comes to mind is to take the mean of the two extremes. That is wrong. In an average-case analysis, all cases in the sample space must be observed and each weighted by its probability. The mean of the extremes accounts for only two cases.

First the average of a single pass is found. In pass j (this section uses j for the pass index), a[0..j−1] is sorted and a[j] is to be inserted. If the input is random, the rank of a[j] among the j elements of the prefix is also random. The element is placed in any of the j + 1 positions with equal probability: at the right end of the prefix, one place to its left, …, at the very front.

Figure 19.6 shows these four cases for j = 3 on the sorted prefix [3, 6, 8].

  • Case 1, v = 10. 8 > 10 is false. 1 comparison.
  • Case 2, v = 7. 8 > 7 is true, 6 > 7 is false. 2 comparisons.
  • Case 3, v = 5. 8 > 5 and 6 > 5 are true, 3 > 5 is false. 3 comparisons.
  • Case 4, v = 2. 8 > 2, 6 > 2, 3 > 2 are true. Then j = −1, j >= 0 turns out false, and because of short-circuiting a[j] > v is never tested. 3 comparisons.

The last two cases need the same number of comparisons. If the element goes to the very front, the last comparison does not give a "stop" answer; the bounds test ends the loop. That is why there is no case with 4 comparisons. The four cases are equally likely, and the expected number of comparisons is

(1 + 2 + 3 + 3) / 4 = 9/4 = 2,25

This number differs from 2, the mean of the best pass (1) and the worst pass (3). Here the difference is small, but the method is wrong and leads to large errors in other algorithms. For bubble sort with early exit, the mean of the extremes gives ≈ n²/4 comparisons; counting over all permutations shows that the true average is ≈ n²/2.

19.3.6Average case: the general computation

To generalize the computation we need a notion from probability. A number whose value depends on chance is called a random variable. Let Cj be the number of comparisons made while inserting the jth element. Its value depends on the input, so it is a random variable. The expected value E(Cj) of a random variable is found by multiplying each value it can take by its probability and summing. If all cases are equally likely, the expected value is the simple arithmetic mean.

In pass j there are j + 1 cases. If the element is to land at the kth position from the right (k = 1, …, j), k comparisons are made. If it is to land at the very front, that is, in the (j + 1)th case, j comparisons are made. Thus

E(Cj) = (1 / (j + 1)) · [1 + 2 + … + j + j] = (1 / (j + 1)) · [2j + Σk=1j−1 k]

The expression in the brackets is j(j + 1)/2 + j. Dividing by j + 1 gives

E(Cj) = j/2 + j/(j + 1) = j/2 + 1 − 1/(j + 1) = (j + 2)/2 − 1/(j + 1)

For j = 3 this is 5/2 − 1/4 = 2.25, the value found by hand in the example. For j = 4 it is 3 − 1/5 = 2.8: the comparison counts of the five cases are 1, 2, 3, 4, and 4, with mean 14/5 = 2.8.

The total number of comparisons for the whole array is Y = C1 + C2 + … + CN−1. Expectation distributes over a sum: the expected value of a sum is the sum of the expected values. So, without having to deal with any relationship between the passes, we can write

E(Y) = Σj=1N−1 E(Cj) = Σj=1N−1 [(j + 2)/2 − 1/(j + 1)]

The first part is (1/2) · [N(N − 1)/2 + 2(N − 1)] = (N² + 3N)/4 − 1. The second part is 1/2 + 1/3 + … + 1/N = HN − 1, where HN = 1 + 1/2 + … + 1/N is the harmonic number. The harmonic number grows slowly: HN = ln N + O(1). When the two parts are combined, the −1s cancel:

Theorem 19.1 (Average of insertion sort)

If all N! arrangements of N distinct keys are equally likely, the expected number of comparisons of the insertion routine is

E(Y) = (N² + 3N)/4 − HN ≈ N²/4

The expected number of shifts is N(N − 1)/4.

The number of comparisons is the computation above. For the number of shifts the same route is followed: if the element lands at the kth position from the right, k − 1 shifts are made, for k = 1, …, j + 1. The mean is j/2. Summed over j = 1, …, N − 1, the total is N(N − 1)/4.

The formula was checked for small values of N by counting all arrangements one by one. In Table 19.5 the "all arrangements" column was found by sorting each of the N! permutations with an instrumented insertion and averaging the comparison counts. The result is exactly the same as the formula.

19.4Bubble sort

19.4.1Idea and code

Bubble sort compares only neighboring elements and swaps them if they are in the wrong order. In a pass that moves from the right end of the array to the left, a small element moves one position left with each neighbor swap. When the pass is over, the smallest of the remaining elements has reached the far left, just like an air bubble rising from the bottom of the water to the surface. The algorithm's name comes from this analogy.

void bubble(int a[], int L, int R) {
    int i, j;
    for (i = L; i < R; i++)
        for (j = R; j > i; j--)
            if (a[j] < a[j-1]) SWAP(a[j], a[j-1]);
}
  • Line 3. The outer loop runs n − 1 passes. At the end of pass i, the smallest of the remaining elements is in a[i].
  • Line 4. The inner loop brings j down from the right end of the array to i + 1. a[L..i−1] was settled in earlier passes; that region is not entered.
  • Line 5. Compare-exchange: if the right element a[j] is smaller than the left a[j − 1], they trade places. The comparison is strict; equal neighbors are not swapped.

Selection sort also puts the smallest of the remaining elements into a[i] in every pass. The difference lies in the method. Selection sort finds the minimum and carries it with a single long-distance swap. Bubble sort carries the small element step by step to the left with neighbor swaps. During this journey other elements also change places. For example, large elements drift a little to the right in every pass. For this reason bubble sort makes many more moves than selection sort, but in return it gains an important property: because only neighbors are swapped, it is stable.

19.4.2The early-exit version: bubble2

The last pass in the trace was in vain: the array was sorted after pass 2, but the algorithm did not know it. Yet the information was at hand. If no swap was made during a pass, every neighboring pair is in the right order, that is, the array is sorted. There is no need to enter the following passes. The code can be written a little more carefully with this observation:

void bubble2(int a[], int L, int R) {
    for (int i = L; i < R; i++) {
        int swapped = 0;      // swap in this pass?
        for (int j = R; j > i; j--)
            if (less(a[j], a[j - 1])) {
                SWAP(a[j], a[j - 1]);
                swapped = 1;
            }
        if (!swapped) return; // sorted: exit early
    }
}
  • Line 3. At the start of each pass the swapped flag is cleared.
  • Lines 5–8. When a swap is made, the flag becomes 1. This time the comparison is written with the less macro; its meaning is the same as the line in bubble.
  • Line 9. If the pass ended without a swap, the routine returns immediately.

19.4.3Analysis

bubble makes (n − 1) + (n − 2) + … + 1 = n(n − 1)/2 comparisons in every case; the bounds of the inner loop do not depend on the input. The number of swaps does depend on the input. On sorted input no swaps are made. On reverse-sorted input every comparison results in a swap, and n(n − 1)/2 swaps are made. On random input the average number of swaps is n(n − 1)/4; the reason is explained right below with inversions.

bubble2 with early exit is O(n) on sorted input, but it gains little on average. Counted over all arrangements, the average number of passes for n = 8 is 5.79; it could have run at most 7 passes. Bubble sort is stable: only neighbors are swapped, and equal neighbors are not swapped. Two equal elements can never jump over each other, so their relative order does not change. The algorithm is in place; the extra memory is O(1). The total complexity is O(n²).

In practice bubble sort is rarely used. Insertion sort does the same job with fewer comparisons and cheaper shifts. Bubble sort has two merits: it is easy to teach, and its early-exit version tells you in a single pass whether an array is sorted.

19.5Inversions: a common measure

Insertion sort sorted [7, 2, 9, 5, 1] with 7 shifts, and bubble sort with 7 swaps. That two different algorithms make the same number of moves is no coincidence. Both count the same thing: the pairs in the array that "stand upside down".

Definition 19.4

In an array a, an index pair (i, j) with i < j and a[i] > a[j] is called an inversion. The inversion count of the array is the number of such pairs.

Written by value, the inversions of the array [7, 2, 9, 5, 1] are (7, 2), (7, 5), (7, 1), (2, 1), (9, 5), (9, 1), and (5, 1). Figure 19.8 shows these seven pairs with arcs. A sorted array has 0 inversions. In a reverse-sorted array every pair is an inversion, and n(n − 1)/2 pairs can be chosen from n elements. The inversion count is therefore a measure of "how unsorted" an array is: it ranges from 0 to n(n − 1)/2.

Theorem 19.2 (Adjacent swap)

Swapping two adjacent elements that are in the wrong order reduces the inversion count by exactly 1. Every shift in insertion sort also reduces the inversion count by exactly 1. Hence the number of swaps of bubble sort and the number of shifts of insertion sort are equal to the inversion count of the input.

Let the adjacent pair a[k] > a[k + 1] be swapped. The pair these two elements form was an inversion and is not after the swap: a decrease of 1. Now consider any other pair. If neither of its elements is at k or k + 1, the pair is unaffected. Suppose one of its elements is outside, for example at a position m < k. a[m] is to the left of both elements, before and after the swap. The number of inversions it forms with these two elements does not change; only which position it is paired with changes. The same holds for m > k + 1. The total change is exactly −1.

In insertion sort, when a[j], which is greater than v, is shifted one place right, v ends up to the left of that element. This removes the inversion (a[j], v) and does not change the order of any other pair; the relative order of the other elements is preserved. The inversion count decreases by 1 per shift. Since the algorithms stop when the array is sorted, that is, when the inversion count is 0, the number of moves equals the inversion count.

Applying the theorem to the average case is completed by finding the average inversion count of a random array. For each pair (i, j), one of the two elements is greater; in a random arrangement the probability that the greater one is on the left is 1/2. To see this, it is enough to pair each arrangement with its reversal: a pair is an inversion in exactly one of the two. Each of the n(n − 1)/2 pairs contributes 1/2 inversion on average. The average inversion count is

n(n − 1)/2 · 1/2 = n(n − 1)/4

The average number of swaps of bubble sort and the average number of shifts of insertion sort are therefore n(n − 1)/4. The values 3, 5, 7.5, and 10.5 in the tables come exactly from this formula.

This result has a strong consequence. Any algorithm that only swaps adjacent elements, or shifts elements one at a time, removes at most one inversion per move. The average input has n(n − 1)/4 inversions. So every such algorithm does Ω(n²) work on average; a cleverer loop arrangement cannot get past this wall. The only way past the wall is to remove more than one inversion in a single move. That happens by swapping elements that are far apart. Shell sort and quicksort take this path.

Selection sort is outside this rule; it already makes long-distance swaps. A single long-distance swap can remove many inversions at once. For example, in the array [5, 2, 3, 4, 1], swapping 5 and 1 destroys 7 inversions at once and sorts the array. But the problem of selection sort is not moves but comparisons: regardless of the input it makes n²/2 comparisons.

19.6Counting sort

19.6.1Sorting without comparisons

So far the algorithms have learned about the input only by comparing two elements. Counting sort takes a completely different route: it never compares elements with each other. Instead it uses the values as array indices. The algorithm goes back to Harold H. Seward's work in 1954. It has a single condition: the values to be sorted are integers and their range is known, for example 0 … k.

The idea is this. If, for every value x, we know how many elements in the input are less than or equal to x, we also know the place of x in the output. If there are three elements in the input less than or equal to 3, the last 3 goes to the third position of the output, that is, index 2. To find these counts, first the number of occurrences of each value is counted, then the counts are summed from left to right.

int counting_sort(const int a[], int b[],
                  int r, int k) {
    int *c = malloc((k + 1) * sizeof *c);
    if (c == NULL) return -1;
    for (int i = 0; i <= k; i++) c[i] = 0;  // L1
    for (int j = 0; j <= r; j++) c[a[j]]++; // L2
    for (int i = 1; i <= k; i++)            // L3
        c[i] += c[i - 1];
    for (int j = r; j >= 0; j--) {          // L4
        b[c[a[j]] - 1] = a[j];
        c[a[j]]--;
    }
    free(c);
    return 0;
}

If L4 wrote from left to right, the output would still be sorted, but the order of equal elements would be reversed. In that case the 3 at a[0] is processed first and written to b[2], and the 3 at a[5] to b[1]. When bare numbers are sorted the difference is invisible. When counting sort sorts records, or one pass of radix sort, the difference breaks the result.

Common mistake

Not checking the value range. If the input contains a negative value or a value greater than k, c[a[j]]++ writes outside the array c. C does not catch this: the program either silently corrupts another variable or crashes. The routine's contract is "all values lie in the range 0 … k". If the data may not satisfy this contract, first find the minimum and maximum, shift the values by the minimum, and choose k accordingly.

Linear time comes at a price: the data range must be known and small. If the range grows, the k term dominates. Suppose 10 numbers are to be sorted, but the values can be anywhere between 0 and 1,000: L1 and L3 are loops of a thousand iterations. For n = 10, k = 1,000 = n³; the "linear" algorithm turns into an n³ algorithm on this input. Insertion sort sorts the same 10 numbers with at most 45 comparisons. For random 32-bit integers, k ≈ 4 · 10⁹ and the counter array would take 16 GB. Counting sort is therefore meant for narrow-range data such as age, grade, day, or letter code. Integers with a wide range are sorted with radix sort: the number is split into digits and each digit is processed by a narrow-range counting sort.

The algorithm's two-pass structure appears elsewhere too: in the first pass frequencies are counted, in the second pass each element is written directly to its computed place. The fast transpose of sparse matrices is exactly this. First the number of nonzero terms in each column is counted. The cumulative sum of the counts gives the starting position of each column in the transposed matrix. In the second pass each term is written directly into place, and the whole job finishes with a single output array in O(number of columns + number of terms) time.

19.7Shell sort

19.7.1Idea and code

The weakness of insertion sort is that it advances an element only one position per step. A small element at the end of the array needs n − 1 shifts to reach the front. In terms of inversions, each shift removes a single inversion, and a reverse-sorted array has n(n − 1)/2 inversions. In 1959 Donald Shell proposed a simple remedy: first sort elements that are far apart, then reduce the gap.

Choose a number h. The array is divided into h separate chains made of elements with h positions between them: a[0], a[h], a[2h], … is the first chain, a[1], a[h+1], … the second. Each chain is sorted separately with insertion sort. As a result the array is h-sorted: no element is greater than the element h places after it. This step starts with a large h, and h is reduced at each step. In the last step h = 1; this is ordinary insertion sort.

void shell_sort(int a[], int n) {
    for (int h = n / 2; h > 0; h /= 2) // gap
        for (int i = h; i < n; i++) {
            int v = a[i], j = i;
            while (j >= h && a[j - h] > v) {
                a[j] = a[j - h];    // shift back by h
                j -= h;
            }
            a[j] = v;
        }
}
  • Line 2. The gap starts at n/2 and is halved at each step: 4, 2, 1 for n = 8; 500, 250, 125, 62, 31, 15, 7, 3, 1 for n = 1,000. This is the gap sequence Shell himself proposed. Thanks to integer division, the sequence always ends with 1.
  • Lines 3–9. The inner part is insertion sort written with step h instead of 1. v = a[i] is set aside; j goes back in steps of h; elements greater than v are shifted h positions forward. The j >= h in the condition ensures that a[j − h] is inside the array.

In the code the chains are not sorted separately. The i loop goes in order from h to n − 1 and inserts each element into place in its own chain. The chains thus advance interleaved, element by element. The result is the same as sorting the chains one by one, because the insertion sort of each chain processes its elements in order from left to right.

The correctness of the algorithm comes from the last step: the h = 1 pass is a complete insertion sort and sorts any array. The earlier passes only reduce the work of this last pass. Whichever gap sequence is chosen, the result is correct as long as it ends with 1. The gap sequence determines only the speed.

In so small an array there is no gain in comparisons, but the number of shifts is halved. 7 shifts removed 13 inversions: long-distance shifts destroy several inversions in a single move. For example, the first shift at h = 4 made 35 jump over 33, 42, and 10. As the array grows, this effect becomes pronounced.

19.7.3Gap sequences and complexity

The running time of Shell sort depends on the gap sequence, and a full analysis is hard. Some of the known results are these:

  • For Shell's sequence n/2, n/4, …, 1 the worst case is Θ(n²). The problem is that when n is a power of 2, all the gaps are even until the last pass. Odd and even positions never meet until 1, and on a bad input the last pass again does work of order n².
  • For Knuth's sequence 1, 4, 13, 40, 121, … (h ← 3h + 1) the worst case is O(n3/2). Since consecutive gaps share no common divisor, the chains mix with each other.
  • With more complex sequences (for example Pratt's gaps of the form 2p3q) the worst case drops to O(n lg² n). No closed formula is known for the average case.

One reason Shell sort works is this property: an h-sorted array stays h-sorted when it is k-sorted. That is, later passes do not destroy the order gained by earlier passes, but add to it. The proof of this property is beyond the scope of this note; it is given in Knuth's book.

Shell sort is in place: it uses as much memory as insertion sort. It is not stable. Long-distance shifts can make equal elements jump over each other. The smallest example has four elements: [2a, 5, 2b, 2c]. In the h = 2 pass, v = 2c is taken for i = 3; since a[1] = 5 > 2, 5 shifts right and 2c is written to a[1]. The array becomes [2a, 2c, 2b, 5]. The h = 1 pass does not move the equal elements. 2c has passed ahead of 2b.

The code is short, needs no extra memory, and on medium-sized arrays is much faster than the n² algorithms. These three properties make Shell sort a favorite in embedded systems and small libraries. If the properties of the data are known, Shell sort can also be used together with bucket sort. The elements distributed into buckets are sorted separately in each bucket; a short in-place algorithm is suitable for this job.

19.8Bucket sort

19.8.1Idea

Bucket sort carries the idea of counting sort over to real numbers. The input is assumed to be n real numbers in the interval [0, 1), distributed uniformly over it. The interval is divided into n equal parts, that is, n buckets. Each number is thrown into its own bucket. Under a uniform distribution, on average one number falls into each bucket. Because the buckets are small, they are cheaply sorted internally with insertion sort. Finally the buckets are concatenated in order.

Figure 19.12 shows this method on an input of 10 numbers. There are 10 buckets and each bucket is 0.1 wide. A value x goes to bucket number ⌊10 · x⌋: 0.78 → 7, 0.17 → 1, 0.39 → 3.

19.8.2Implementation in C

Each bucket is a linked list. The bucket array holds the head pointers of these lists. The implementation below combines distribution with sorting inside buckets: as each number is thrown into its bucket, it is inserted into its sorted place in the list. This is exactly insertion sort within a bucket.

typedef struct bnode { double x; struct bnode *next; } bnode;

int bucket_sort(double a[], int n) {        /* 0 <= a[i] < 1 */
    bnode **bucket = calloc(n, sizeof *bucket);
    bnode *pool = malloc(n * sizeof *pool);
    if (!bucket || !pool) { free(bucket); free(pool); return -1; }
    for (int i = 0; i < n; i++) {           /* distribute + sorted insert */
        bnode **p = &bucket[(int)(a[i] * n)];
        while (*p && (*p)->x <= a[i]) p = &(*p)->next;
        pool[i].x = a[i]; pool[i].next = *p; *p = &pool[i];
    }
    int k = 0;                              /* concatenate buckets */
    for (int b = 0; b < n; b++)
        for (bnode *q = bucket[b]; q; q = q->next) a[k++] = q->x;
    free(bucket); free(pool);
    return 0;
}
  • Line 1. The list node: the value x and the link to the next node next. The structure is a self-referential struct.
  • Line 4. bucket is an array of n pointers of type bnode *. calloc zeroes the memory; all buckets start as NULL, that is, empty lists. If malloc had been used, the pointers would hold random addresses and the first read of (*p)->x would be undefined behavior.
  • Line 5. The nodes are taken not one by one with malloc but from a single pool array. pool[i] is the node of a[i]. Two allocations are made instead of n separate ones, and the memory is returned with a single pair of free calls. The allocation cost drops and the risk of leaks decreases.
  • Line 6. If either of the two allocations failed, both are released. free(NULL) is safe; there is no need to test separately which one failed.
  • Line 8. p is a pointer to a pointer (bnode **). Initially it points to the relevant cell in the bucket array, that is, the head pointer of the list. The bucket number is (int)(a[i] * n). Since 0 ≤ a[i] < 1, this number is between 0 and n − 1.
  • Line 9. p advances along the list: if the pointer it points to is not null and the value of that node is less than or equal to a[i], p starts pointing to the next field of that node. When the loop ends, *p points to the node the new node will go in front of (or to NULL); p is the address of the link to be changed.
  • Line 10. The new node is filled in, its link is directed to the node *p points to, and *p points to the new node. The insertion is complete.
  • Lines 12–14. The buckets are traversed in order from 0 to n − 1; the values of each list are written back to a in order.
  • Line 15. The two allocations are released. Since the nodes were not allocated separately, they are not released separately.

The pointer to a pointer is the subtlest point of this code. If the list were walked with an ordinary single-star pointer, insertion at the head of the list would be a special case. A node inserted at the head changes the head pointer in the bucket array. A node inserted in the middle changes the next field of the previous node. Because p holds "the address of the pointer to be changed", the two cases are handled by the same line. Figure 19.13 shows this in the insertion of 0.23.

The state in memory at the end of the routine is seen in Figure 19.14. The nodes sit in the pool array in input order: the node of 0.12 is pool[7], because 0.12 is at index 7 of the input. The links string the inside of each bucket into a sorted chain. This is where the strength of the linked list lies: elements do not move in memory, only links change.

Because the comparison is made with <=, an equal value is added after its equals in the list. The one that comes first in the input stays first; bucket sort is stable in this implementation. If the comparison were <, the new element would go in front of its equals and stability would be lost.

19.8.3Analysis

Distribution and concatenation are O(n): each element is thrown into a bucket once and written back once. The real question is the cost of sorting inside the buckets. If ni elements fall into bucket i, insertion sort does O(ni²) work in that bucket. The total cost is O(n + Σ ni²).

If the input is uniformly distributed, each element falls into each bucket with probability 1/n. In this case the expected number of elements in a bucket is 1 and the expected value of ni² is 2 − 1/n (proved in the book by Cormen and coauthors). Over n buckets the total is n · (2 − 1/n) = 2n − 1. The average running time is O(n).

If the uniform-distribution assumption fails, so does the result. In the worst case all elements fall into the same bucket. For example, if 5 numbers are 0.90, 0.91, 0.92, 0.93, and 0.94, then ⌊5x⌋ is 4 for all of them. Five elements are insertion-sorted in a single bucket and the cost rises to O(n²). The extra memory is O(n) for the bucket array and nodes; the algorithm is not in place.

Bucket sort also uses comparisons, but only inside the buckets. Which bucket an element goes to is found by a computation, ⌊n · x⌋. This computation is like comparing the element with all the other elements at once. That is why the algorithm is not caught by the lower bound for comparison sorting.

19.9A lower bound for comparison sorting

19.9.1The decision tree

Selection, insertion, bubble, and Shell sort made between n² and n3/2 comparisons. Is something better possible, and how much better? This question has to be answered not for one algorithm but for all algorithms based on comparison. The tool for this is the decision tree.

A comparison-based sorting algorithm learns about the input only from calls to less. Each call has two outcomes: yes or no. The algorithm's next step depends on this answer. All possible runs of the algorithm can be drawn as a binary tree. This tree is called a decision tree.

  • Every internal node is a comparison (an ellipse in the drawing): "a < b?".
  • The node has two children: the left one is the step following the "yes" answer, the right one the step following the "no" answer.
  • Every leaf is a decision (a rectangle in the drawing): in which arrangement the input was, that is, in what order the elements are to be written.

For a given input the algorithm starts at the root, goes left or right according to the answer to each comparison, and stops at a leaf. The length of the path from the root to the leaf is the number of comparisons made on that input. Figure 19.15 shows a decision tree that sorts three elements (a, b, c). For n = 3 there are 3! = 6 arrangements and hence 6 leaves.

Let the input be a = 5, b = 8, c = 2. The question at the root is "a < b?": 5 < 8, the answer is yes. At the left child "b < c?" is asked: 8 < 2, the answer is no, so c must come before b. At this point a < b and c < b are known, but the order of a and c is not. The third question is "a < c?": 5 < 2, the answer is no. The leaf is c < a < b and the output is 2, 5, 8. For this input 3 comparisons were made.

Some paths of the tree are shorter. If a < b and b < c, then a < c is also known by transitivity; the algorithm decides a < b < c with two comparisons. The worst-case number of comparisons is the length of the longest path, that is, the height of the tree. The height of this tree is 3.

Every comparison-based sorting algorithm corresponds to such a tree for each n. The tree of insertion sort has one shape, that of selection sort another; but every tree must satisfy the same condition. This condition is the source of the lower bound.

19.9.2The lower-bound theorem

Theorem 19.3 (Lower bound for comparison sorting)

Every decision tree that sorts n distinct elements has depth (number of levels) at least ⌈lg(n!)⌉ + 1. That is, every comparison-based sorting algorithm makes at least ⌈lg(n!)⌉ comparisons in the worst case. This number is Θ(n lg n).

Number of leaves. Each of the n! arrangements of the input needs a different output: if two different arrangements reached the same leaf, the algorithm would sort one of them wrongly. So the tree has at least n! leaves.

Relation between height and leaves. A binary tree of height h can have at most 2h leaves. The root is a single node; at each level the number of nodes at most doubles, and after h comparisons at most 2h different places are reached.

Conclusion. Combining the two observations gives 2h ≥ n!, that is, h ≥ lg(n!). Since h is an integer, h ≥ ⌈lg(n!)⌉. The number of levels is one more than the height: ⌈lg(n!)⌉ + 1.

Growth rate. Each of the last n/2 factors of n! is at least n/2; therefore n! ≥ (n/2)n/2 and lg(n!) ≥ (n/2) · lg(n/2), that is, Ω(n lg n). Also, since n! ≤ nn, lg(n!) ≤ n lg n. Together they give lg(n!) = Θ(n lg n).

A sharper approximation comes from Stirling's formula:

lg(n!) = n lg n − n lg e + Θ(lg n) ≈ n lg n − 1.4427 n

Here lg e = 1 / ln 2 ≈ 1.4427. Table 19.15 puts the lower bound, the Stirling approximation, and the worst case of the basic algorithms side by side. The values were computed in a C program with the sum lg(n!) = lg 2 + lg 3 + … + lg n.

From here on, the theorem gives a yardstick, a touchstone, for comparing all sorting algorithms. If a comparison-based algorithm has reached O(n lg n), nothing is better in order of magnitude; only constant factors and practical properties (memory, stability, cache friendliness) can be improved. The same bound holds for the average case: in a decision tree the average depth of the leaves is also at least lg(n!).

The theorem has one assumption: the algorithm learns about the input only through comparisons. Counting sort, bucket sort, and radix sort violate this assumption. The line c[a[j]]++ does not compare a[j] with another element; it uses the value itself as an index and with this single operation makes a k + 1-way decision. The decision tree stops being binary and the lower bound loses its validity. The price of linear time comes from here too: for the value to be usable as an index, the range must be known.

19.10.3Which one when?

There is no such thing as "the best sorting algorithm"; each algorithm suits a situation. The choice depends on the size of the data, its shape, and which operation is expensive.

  • Selection sort if swaps or writes are expensive. It makes exactly n − 1 swaps. It suits large records and settings such as flash memory where writing is expensive.
  • Insertion sort if the data is small or nearly sorted. It is stable, in place, and drops to O(n) on nearly sorted data. Practical versions of quicksort and merge sort leave small parts to insertion sort.
  • Bubble sort for teaching and for testing sortedness. The early-exit version detects in a single pass that an array is sorted. It rarely appears in production code.
  • Counting sort if the values lie in a small integer range. It is O(n + k) and stable. If k is much larger than n, memory and time are wasted.
  • Shell sort for medium-sized data when there is no extra memory. With a few lines of code it is clearly faster than the n² algorithms.
  • Bucket sort if the data is uniformly distributed in [0, 1). It is O(n) on average, but slows down to n² if the distribution is skewed.

19.11Common mistakes

  1. Keeping the value of the minimum in selection sort. If only the value is kept, as in int min = a[i];, the position of the smallest element is unknown at the end of the pass and the swap cannot be made. The swap needs the index (min = j).
  2. Not saving v = a[i] before shifting in insertion sort. The first shift overwrites a[i] and the value to be inserted is lost.
  3. Writing the bound as j >= 0. If the subarray a[L..R] is being sorted, the correct bound is j >= L. j >= 0 corrupts elements outside the part when L > 0.
  4. Mixing up the direction in the if (less(A, B)) SWAP(A, B); pattern. This line swaps if A < B. If the smaller element is to move left, A must be the element on the right: less(a[j], a[j − 1]).
  5. Forgetting the range in counting sort. A negative value or one greater than k writes outside c[]; C does not catch it.
  6. Writing L4 from left to right in counting sort. The array is still sorted, but the order of equal elements is reversed and stability is lost.
  7. Writing a multi-statement macro with braces alone. It gives a compile error in an if (…) SWAP(…); else … structure; the body must be wrapped in do { … } while (0).
  8. Taking the average case to be the mean of the best and worst cases. In bubble sort with early exit, the extremes are n − 1 and n(n − 1)/2 comparisons; their mean is ≈ n²/4. The true average is ≈ n²/2: for n = 8 the mean of the extremes is 17.5, the average over all arrangements is 26.0. The average is the expected value taken over all arrangements.

19.12Exercises and solutions

19.12.1Passes of selection sort

Question. For [5, 1, 4, 2, 8], write the array at the end of each pass of selection sort. How many swaps were made?

Solution. In pass 0 the minimum is 1 (min = 1); it is swapped with 5: [1, 5, 4, 2, 8]. In pass 1 the smallest of the rest is 2 (min = 3); it is swapped with 5: [1, 2, 4, 5, 8]. In pass 2 the minimum 4 is already at a[2]; the swap is with itself. In pass 3, 5 and 8 are compared; 5 is in place. Over the four passes the array goes [1, 5, 4, 2, 8] → [1, 2, 4, 5, 8] → [1, 2, 4, 5, 8] → [1, 2, 4, 5, 8]. SWAP is called four times, but only the first two are real swaps. The number of comparisons is 10 as always.

19.12.2The two extremes of insertion sort

Question. How many comparisons does insertion sort make for [1, 2, 3, …, n] and [n, …, 2, 1]?

Solution. On sorted input each pass ends with a single comparison: n − 1. On reverse-sorted input pass i makes i comparisons: 1 + 2 + … + (n − 1) = n(n − 1)/2. For n = 1,000: 999 and 499,500.

19.12.3Bubble sort with early exit

Question. How many passes does bubble2 run on the input [1, 2, 3, 5, 4]?

Solution. 2 passes. In the first pass, at j = 4, 4 < 5 is true and 5 and 4 are swapped; no swap occurs in the rest of the pass. The array is sorted, but the algorithm learns this only in the second pass: in the second pass no swap occurs and the routine returns. In total 4 + 3 = 7 comparisons and 1 swap are made.

19.12.4The counter array

Question. For a = [2, 5, 3, 0, 2, 3, 0, 3] and k = 5, write the array c of counting sort after L3.

Solution. At the end of L2 the counters are c = [2, 0, 2, 3, 0, 1]: two 0s, no 1, two 2s, three 3s, no 4, one 5. L3 accumulates them: c = [2, 2, 4, 7, 7, 8]. Reading example: c[3] = 7, there are seven elements less than or equal to 3; the last 3 is written to b[6]. The sorted output is [0, 0, 2, 2, 3, 3, 3, 5].

19.12.5Height of the decision tree

Question. What is the minimum height of a decision tree for 3 elements? For 4 elements?

Solution. ⌈lg 3!⌉ = ⌈lg 6⌉ = 3 and ⌈lg 4!⌉ = ⌈lg 24⌉ = 5. For 3 elements the tree in Figure 19.15 reaches this bound. For 4 elements, 4 comparisons are not enough: 4 comparisons can separate at most 2⁴ = 16 different outcomes, yet there are 24 arrangements. There are algorithms that sort 4 elements with 5 comparisons.

19.12.6Instability of selection sort

Question. Find the smallest example showing that selection sort is unstable.

Solution. Two elements are not enough: in a two-element array equal keys are not swapped, and for different keys the question of stability does not arise. The three-element [2a, 2b, 1] suffices. In the first pass the minimum is 1 and it is swapped with 2a at a[0]: [1, 2b, 2a]. In the second pass less(2a, 2b) is false and the swap is with itself. The result is [1, 2b, 2a]: 2b has passed ahead of 2a. The long-distance swap made 2a jump over 2b.

19.13Summary

  • Sorting arranges records by their keys. In internal sorting the data is in memory; in external sorting the cost is determined by disk accesses.
  • A stable algorithm preserves the relative order of records with equal keys; sorting on several fields and radix sort rely on this. An in-place algorithm uses O(1) extra memory.
  • The less and SWAP macros let the algorithms be written independently of type and criterion; a multi-statement macro is written inside do { … } while (0).
  • Selection sort is blind to the input: in every case n(n − 1)/2 comparisons and n − 1 swaps. It is unstable because of the long-distance swap.
  • Insertion sort makes n − 1 comparisons on sorted input and n(n − 1)/2 on reverse-sorted input. Its average over all n! arrangements is (n² + 3n)/4 − Hn ≈ n²/4; it is not the mean of the best and worst cases. It is stable and in place. The sentinel version removes the bounds test in the inner loop.
  • Bubble sort swaps neighbors; it is stable. The early-exit version is O(n) on sorted input, but on average still makes ≈ n²/2 comparisons.
  • An inversion is a pair that stands in the wrong order. An adjacent swap or a one-position shift removes exactly one inversion; since a random array has n(n − 1)/4 inversions on average, every such algorithm is Ω(n²) on average.
  • Counting sort makes no comparisons; it runs in O(n + k) time with O(n + k) extra memory. It is stable because placement is done from right to left. It is useless if the range is large.
  • Shell sort performs insertion sort with decreasing gaps; the last pass, h = 1, guarantees correctness. Long-distance shifts remove inversions quickly. Speed depends on the gap sequence; it is in place and unstable.
  • Bucket sort is O(n) on average on data uniformly distributed in [0, 1); it rises to O(n²) if all elements fall into one bucket. The C implementation does sorted insertion with a pointer to a pointer and takes the nodes from a single pool.
  • Every comparison sort is a decision tree. Since the tree has at least n! leaves, its height is at least ⌈lg n!⌉ = Θ(n lg n). This bound is the yardstick for advanced sorting algorithms; algorithms that make no comparisons are not caught by it.

19.15Try it yourself

  1. How many comparisons and how many real swaps does the selection routine make on the array [3, 1, 2]? What is the array at the end of each pass?

    Answer

    3 comparisons and 2 swaps. In pass 0 the minimum is 1: [1, 3, 2]. In pass 1, 2 < 3 and a swap is made: [1, 2, 3]. Both swaps are real.

  2. What is the inversion count of the array [4, 1, 3, 2]? With how many shifts and how many comparisons does insertion sort this array?

    Answer

    4 inversions: (4, 1), (4, 3), (4, 2), (3, 2). The number of shifts equals the inversion count: 4. There are 6 comparisons: 1 at i = 1 (1 goes to the front), 2 at i = 2, 3 at i = 3.

  3. How many passes does bubble2 run on the arrays [5, 1, 2, 3, 4] and [2, 3, 4, 5, 1]? Why is there a difference although both arrays have the same inversion count?

    Answer

    4 passes on the first, 2 on the second. Because the inner loop moves from right to left, a small element can go all the way left in one pass, but a large element advances only one position right per pass. In [5, 1, 2, 3, 4], 5 needs four passes to reach the end.

  4. counting_sort is called with a = [1, 0, 1, 2] and k = 2. What is c at the end of L3? To which index is the 1 at a[0] written in the output?

    Answer

    c = [1, 3, 4]. L4 traverses from right to left: a[3] = 2 → b[3], a[2] = 1 → b[2], a[1] = 0 → b[0], a[0] = 1 → b[1]. The 1 that comes first in the input is also first in the output; the algorithm is stable.

  5. What is the expected number of comparisons when the fifth element (j = 4) is inserted in insertion sort?

    Answer

    E(C4) = (4 + 2)/2 − 1/5 = 2.8. The comparison counts of the five cases are 1, 2, 3, 4, and 4; their mean is 14/5 = 2.8.

  6. What is the minimum number of comparisons a comparison-based algorithm sorting 5 elements must make in the worst case? How many does selection sort make?

    Answer

    ⌈lg 5!⌉ = ⌈lg 120⌉ = ⌈6.91⌉ = 7. Selection sort makes 10 comparisons on every input; three more than the lower bound.

  7. bucket_sort is called with n = 5 and the input 0.94, 0.93, 0.92, 0.91, 0.90. How is it distributed into the buckets, and why is this input bad?

    Answer

    ⌊5x⌋ is 4 for all five numbers; all of them fall into bucket 4. Since the numbers arrive in decreasing order, each new number goes to the front of the list, so the while loop makes only one comparison each time. If the input had arrived in increasing order, each insertion would have walked the whole list. For n elements falling into a single bucket the worst case is O(n²); the uniform-distribution assumption is violated.

  8. Which gaps does shell_sort use on a 10-element array? Why is the last gap always 1, and why does it matter?

    Answer

    5, 2, 1. The gap is halved with integer division at each step and cannot become 0 without passing through 1: when h = 1 the next value is 0 and the loop ends. The h = 1 pass is a complete insertion sort; whatever the earlier passes did, it sorts the array. The correctness of the algorithm comes from this last pass.
