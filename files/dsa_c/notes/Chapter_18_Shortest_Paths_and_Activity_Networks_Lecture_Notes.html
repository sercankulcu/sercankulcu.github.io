Chapter 18: Shortest Paths and Activity Networks

This chapter takes up two big questions about weighted directed graphs: what is the shortest path from one vertex to another, and when can a project made of interdependent tasks finish at the earliest? The first question starts with brute force, and counting shows why that solution is unusable. Dijkstra's greedy algorithm is then built in C, traced, and analyzed; the path itself is read from a single predecessor array. Bellman-Ford handles negative edges, and Floyd-Warshall handles all pairs of vertices. The second half is devoted to activity networks. In activity-on-vertex networks, a topological order is found in linear time with counted headers and an embedded stack. In activity-on-edge networks, the same routine computes the earliest times, and its twin running on the reversed graph computes the latest times. Together the two arrays give the slack of every activity and the critical path of the project. Each routine comes with a line-by-line walkthrough, a trace table, and a complexity analysis.

18.1The shortest-path problem

Picture a map of cities and the railway lines between them. Every line has a length, and the traveler's question is simple: what is the shortest route from one city to another? The same question arises in a computer network. There the vertices are routers, and the edges are links between two routers. The value of an edge is no longer a length but the time a packet waits on that link, which grows as traffic gets heavier. A router deciding which neighbor to forward a packet to is, in effect, solving the shortest-path problem again every second.

Both examples share one model, the weighted directed graph. Vertices stand for cities or routers, and edges stand for connections. Every edge has a cost (a weight). Making edges directed is realistic: a one-way road, or a link that is congested in only one direction, gives different costs in the two directions. The length of a path is the sum of the costs of its edges. The number of edges does not matter here; a path of three edges can be shorter than a path of one.

Definition 18.1

Let G = (V, E) be a weighted directed graph and let cost(<u, w>) be the weight of an edge. The length of a path v0, v1, …, vk is the sum cost(<v0, v1>) + … + cost(<vk−1, vk>). Among the paths from x to y, one of minimum length is called a shortest path.

The problem contains two separate questions. First, is there any path from x to y at all? This is a reachability question, answered by a depth-first or breadth-first traversal of the graph. Second, if there are several paths, which one is shortest? This chapter is about the second question. The problem can be posed in several forms. In the single-source single-destination version, a start and a target vertex are given. In the single-source all-destinations version, the shortest paths from one source vertex to every other vertex are wanted. In the all-pairs version, a separate answer is sought for every pair of vertices.

The shortest-path problem should not be confused with a similarly named one. Finding the shortest tour that visits every vertex once and returns to the start is the traveling salesman problem. In the traveling salesman problem the order of all vertices is chosen; in the shortest-path problem only the route between two vertices is sought. All known exact algorithms for the former take exponential time, while the latter is solved very efficiently.

Throughout this chapter we use the six-vertex graph of Figure 18.1. It is the example from the textbook by Horowitz and Sahni. The edges leaving 0 go to 1 (50), 2 (10), and 4 (45). There is an edge from 2 to 3 of cost 15 and one from 3 to 1 of cost 20. Vertex 5 has a single outgoing edge (5 → 3); no vertex has an edge into 5.

From 0 to 4, on the other hand, the direct edge (45) is best. The path 0 → 2 → 3 → 4 costs 10 + 15 + 35 = 60. No edge leads to 5, so there is no path from 0 to 5.

18.2The brute-force solution

The first solution that comes to mind for a problem is often brute force: try every candidate and pick the best. For shortest paths, the candidates are all simple paths from the source to the target. A simple path is one that never passes through the same vertex twice. When no weight is negative, it is easy to see that a shortest path is simple: if a path visits the same vertex twice, the cycle in between can be cut out without increasing the length. So it suffices to try only simple paths.

For the single-source single-destination version the algorithm goes as follows. Start at the source, move to every unvisited neighbor, and when the target is reached, compare the length of that path with the best value so far. This is a depth-first search done with backtracking. The logic is correct, and so is the result. The problem is the number of paths to try.

The worst case is the complete graph, in which every vertex is connected to every other. The complete graph on n vertices is written Kn. Figure 18.2 shows K4 and K5. In K4 there are five paths from 0 to 3: 0-3, 0-1-3, 0-2-3, 0-1-2-3, and 0-2-1-3. In K5, the paths from 0 to 4 are counted by the number of intermediate vertices. There is 1 path with no intermediate vertex (0-4). There are 3 paths with one intermediate vertex, which can be 1, 2, or 3. For paths with two intermediate vertices, the first can be chosen in 3 ways and the second in 2: 6 paths. For paths with three intermediate vertices, all orderings of 1, 2, and 3 are tried: 3! = 6 paths. The total is 1 + 3 + 6 + 6 = 16 paths.

The same count works for general n. Apart from the source and the target there are n − 2 vertices. A path with k intermediate vertices is an ordered selection of k of them. The number of ordered selections is (n − 2)(n − 3)⋯(n − 1 − k). Adding up all values of k gives the number of paths.

Theorem 18.1 (Number of paths in a complete graph)

The number of simple paths between two distinct vertices of Kn is

Y(n) = 1 + (n − 2) + (n − 2)(n − 3) + ⋯ + (n − 2)!

The last term of the sum is the largest, and Y(n) < e · (n − 2)! holds (e ≈ 2.718).

The first equality is the count above. For the upper bound, write the sum from the end backward: (n − 2)! · (1 + 1 + 1/2! + 1/3! + ⋯). The series in parentheses is part of the series 1/0! + 1/1! + 1/2! + …, whose sum is e.∎

The formula was also checked with a program. The program counts, one by one with backtracking, the paths from 0 to n − 1 in a complete graph. The results are shown next to the formula in Table 18.2; in every row the two values agree. The last column shows how many times the search advanced along an edge. This number is about twice the number of paths, so the amount of work grows at the same rate as the number of paths.

The O(nⁿ) notation used in the slides is a crude but correct upper bound on this growth. Since (n − 2)! ≤ nⁿ, we can write Y(n) = O(nⁿ). The tighter bound is O((n − 2)!); both are exponential and say the same thing in practice: this method is usable only on graphs of a few vertices. The logic of brute force is correct. But a method this expensive even for a single target does not solve the problem. For something better, we must exploit the structure in the paths.

18.3Dijkstra's algorithm

18.3.1The greedy idea

Brute force builds every path from scratch. Yet the observations in Table 18.1 point to something smarter: shortest paths can be found from short to long, and every new path is an earlier path extended by one edge. In 1959 Edsger W. Dijkstra turned this idea into a very efficient algorithm. The algorithm is greedy: at each step it makes the choice that looks best at that moment and never revises it.

The algorithm maintains a set S. S consists of the vertices whose shortest paths are final; at the start it holds only the source, 0. For every vertex w outside S, a value dist[w] is also kept.

Definition 18.2

For w ∉ S, dist[w] is the length of the shortest path that starts at the source, ends at w, and has all its intermediate vertices in S. If no such path exists, dist[w] = ∞.

The restriction in the definition matters: dist[w] is the shortest among the paths that pass only through S, not among all paths. Since S = {0} at the start, these paths consist of a single edge, and dist[w] equals the cost of the edge from 0 to w. The algorithm rests on three observations.

  1. The shortest path to the next vertex u to be finalized passes, apart from u itself, only through vertices in S. If some x outside S lay in the middle of the path, the part from the source to x would be shorter, and x would have been chosen earlier.
  2. Therefore the next vertex is the one outside S with the smallest dist value. If there is a tie, any of them may be chosen.
  3. Once u is chosen and joins S, new paths through u become available. For a vertex w outside S, if dist[u] + cost(<u, w>) < dist[w], then dist[w] is updated with this smaller value. In the new path there is no intermediate vertex between u and w; after u the path goes directly to w.

The operation in the third observation is called relaxation. The name comes from the fact that dist[w] is an upper bound: the value is never smaller than the true shortest distance. Relaxation pulls this bound down, that is, it loosens an overly "tight" estimate. Figure 18.3 shows one relaxation step: for the neighbors w1, w2, w3 of the newly added u, new paths through u are tried.

The justification of the first observation depends on one condition: edge weights must not be negative. Without it the algorithm goes wrong. To state the correctness precisely, we can write it as a theorem.

Theorem 18.2 (Correctness of Dijkstra's algorithm)

If all edge weights are non-negative, then for the vertex u outside S with the smallest dist value, dist[u] is the length of a shortest path from the source to u.

Take any path P from the source to u. P starts at the source, which is inside S, and ends at u, which is outside S. So P has a first vertex y outside S. The part of P from the source to y passes only through S; by definition its length is at least dist[y]. Because u was chosen as the vertex with the smallest value, dist[y] ≥ dist[u]. The remaining part of P, from y to u, has length 0 or more because the weights are non-negative. In total, the length of P cannot be smaller than dist[u]. Since dist[u] is itself the length of an actual path, it is the length of a shortest path.∎

The only weak link in the proof is the sentence "the remaining part is 0 or more." A negative edge breaks it: if one descends from y to u along a negative edge, P can be shorter than dist[u]. A concrete example of this situation, and its remedy, appear in the section on negative edges.

18.3.3The C implementation: data and min_vertex

The C version of the algorithm stores the graph as a cost matrix. cost[i][j] is the cost of the edge <i, j>. Where there is no edge, a large constant is written in place of ∞; the diagonal entries are 0. Finalized vertices are marked in the found array; this is the set S. The dist array holds the values from the definition. The code below gives the matrix of the example graph and the routine that finds the unmarked vertex with the smallest distance.

#include <limits.h>
#define MAX_VERTICES 6
#define INF 1000      /* no edge */
int cost[][MAX_VERTICES] = {
    {   0,   50,  10, 1000,   45, 1000},
    {1000,    0,  15, 1000,   10, 1000},
    {  20, 1000,   0,   15, 1000, 1000},
    {1000,   20, 1000,   0,   35, 1000},
    {1000, 1000, 1000,  30,    0, 1000},   /* missing row */
    {1000, 1000, 1000,   3, 1000,    0}};  /* 100 -> 1000 */
int min_vertex(int dist[], int n, short found[])
{
    int i, min = INT_MAX, pos = -1;
    for (i = 0; i < n; i++)
        if (dist[i] < min && !found[i]) {
            min = dist[i];  pos = i;
        }
    return pos;
}
  • Line 1. The constant INT_MAX is in the header limits.h; it is the largest value an int can hold. If the header is not included, the compiler does not recognize INT_MAX.
  • Lines 2–3. The number of vertices and the constant that represents infinity. 1000 is chosen for INF; no real path in the example is that long.
  • Lines 4–10. The cost matrix. The row gives the vertex the edge leaves, and the column the vertex it enters. The values 50, 10, 1000, 45 in row 0 are the edges 0 → 1, 0 → 2, 0 → 3 (no edge), and 0 → 4. The first dimension is left empty; the compiler infers the number of rows from the initializer list. The second dimension must be written, because the compiler has to know how many ints make up a row.
  • Lines 11–19. min_vertex. min starts at the largest int and pos at an invalid index (−1). The loop looks, among the unmarked vertices, for the one with the smallest dist value. The comparison is strict less-than (<); among equal values the first one seen, that is, the lower-numbered vertex, is kept.

Two rows of the matrix carry comments. In the textbook's matrix, row 4 is missing; it was completed by reading the graph (the only edge from 4 is 4 → 3, cost 30). In row 5, too, the book writes 100 for infinity; it was changed to 1000 to be consistent with the other rows. Small typos in textbooks come to light the moment you actually run the code. That is why it matters that the code traced on paper and the code that runs are the same.

The choice of the value INF is subtler than it looks. The first idea is INT_MAX, but that value causes overflow in relaxation: if either term of the sum dist[u] + cost[u][w] is INT_MAX, the result does not fit in an int. In C, signed integer overflow is undefined behavior; in practice the value often wraps to a negative number, and the code believes "a shorter path was found." With a constant such as 1000 there is no such danger: INF + INF is 2000 and fits easily. There is a price: the constant must be chosen larger than the longest real path in the graph. Otherwise a real path is confused with "no path."

The only case in which the routine returns −1 is when no unmarked vertex remains. If an unreachable vertex remains, the routine may still select it, because its value is 1000, which is less than INT_MAX. This is harmless. The value of an unreachable vertex is 1000; relaxations through it never produce a value below 1000, because the weights are non-negative. Still, the calling routine should check for a return of −1; an unchecked access found[-1] writes outside the array.

Common mistake

Writing the condition as !found(w). Round parentheses call the array as if it were a function, and the compiler reports an error such as "called object is not a function." An array element is accessed with square brackets: !found[w]. Another similar mistake is using FALSE and TRUE without defining them; they are not C keywords and must be defined with #define.

18.3.4shortest_path: the main routine

The main routine takes the source vertex, the cost matrix, and three arrays. dist and found are used with the meanings above. The pred array is kept to recover the path itself; the details are in the next section.

void shortest_path(int v, int cost[][MAX_VERTICES],
                  int dist[], int pred[],
                  int n, short found[])
{
    int i, u, w;
    for (i = 0; i < n; i++) {                  /* A1 */
        found[i] = FALSE;
        dist[i] = cost[v][i];
        pred[i] = v;             /* kept for the path */
    }
    found[v] = TRUE;  dist[v] = 0;
    for (i = 2; i < n; i++) {        /* n-2 rounds */
        u = min_vertex(dist, n, found);
        if (u < 0) break;            /* none left */
        found[u] = TRUE;
        for (w = 0; w < n; w++)
            if (!found[w] &&
                dist[u] + cost[u][w] < dist[w]) {
                dist[w] = dist[u] + cost[u][w];
                pred[w] = u;
            }
    }
}

The routine has four parts, and the analysis uses their names:

  • A1 (lines 6–10). Initial values. Every vertex is unmarked. dist[i] is the cost of the direct edge from the source to i; this is the value the definition gives for S = {v}. With the assignment pred[i] = v, every vertex initially counts the source as its predecessor.
  • Line 11. The source is marked and its distance set to 0. The diagonal of the matrix is already 0; the assignment is written out anyway, because code should not rely on the diagonal.
  • A2 (line 12). The outer loop runs from i = 2 to n − 1, that is, n − 2 rounds. The source is already final. Each round finalizes one more vertex. After n − 2 rounds a single unmarked vertex remains. For that vertex all other vertices are in S, so the value from the definition is the length of the shortest path. One more round would only mark it; no unmarked vertex would be left to update, so nothing would change.
  • A3 (lines 13–15). The unmarked vertex u with the smallest distance is found and marked. If −1 is returned, no unmarked vertex is left, and the loop exits.
  • A4 (lines 16–21). Relaxation. For every unmarked w, the path through u is tried. If it is shorter, both the distance and the predecessor are updated.

The condition in lines 17–18 has two parts, and their order matters. The && operator is evaluated left to right with short-circuiting: if found[w] is true, the addition is never performed. This keeps the values of finalized vertices from being corrupted. A shorter path to a finalized vertex cannot be found anyway (Theorem 18.2), but having the code check this explicitly improves both readability and safety.

The cost-matrix parameter is written as int cost[][MAX_VERTICES]. C does not copy an array into a function; it passes the address of the first element. In a two-dimensional array, computing the address of cost[u][w] requires the row length: the address is the base plus (u · MAX_VERTICES + w) · sizeof(int). That is why the second dimension must be written in the parameter. For the same reason, assignments to the arrays dist, pred, and found inside the routine change the caller's arrays; this is how the results come back.

18.3.6Analysis and better data structures

The cost is computed separately for each part. A1 runs n rounds once: O(n). The outer loop of A2 runs n − 2 rounds. In each round A3, that is min_vertex, scans the whole array: O(n). A4 also tries every w once: O(n). The total is

n + (n − 2) · (n + n) ≈ n + 2n² = O(n²)

This bound also holds in the best case: whatever the number of edges, every round makes two full scans. So the running time of the algorithm is Θ(n²). The extra memory is three arrays: O(n). Compared with the factorial growth of brute force, the difference is striking. With 20 vertices brute force takes months, while this routine finishes after a few hundred operations. Even finding the largest element of the matrix requires looking at n² entries; Dijkstra finds all the shortest paths in time of the same order.

O(n²) is good for dense graphs. For sparse graphs there are two bottlenecks. The first is A3: to find the smallest element, the whole array is scanned in every round. Yet returning the smallest element quickly is exactly the job of a priority queue implemented as a min-heap. If the distances are kept in a min-heap, the smallest element is removed in O(log n). The second is A4: because a matrix is used, n columns are scanned in every round, whereas in reality only the neighbors of u are of interest. With an adjacency list, A4 takes time proportional to the out-degree of u.

When both improvements are applied together, the total cost is easily miscalculated. A common mistake is to assume the result is O(n log n). The correct calculation is as follows. Every vertex is removed from the heap once: n times O(log n). Every edge is relaxed once, and each successful relaxation decreases a value in the heap, which takes O(log n). Since the number of edges is e, the total is

O(n log n + e log n) = O((n + e) log n)

A more complex structure called a Fibonacci heap brings the decrease-key operation down to O(1) amortized and improves the bound to O(e + n log n). Table 18.5 puts the three approaches side by side.

Which version is better depends on the graph. In a sparse graph, such as a road map, every vertex has a few neighbors and e is of the order of n. Here the heap version drops to O(n log n) and beats the array version by a clear margin. In a dense graph, however, e ≈ n² and the heap version rises to O(n² log n); the simple array version is faster. Once you have learned the priority queue, searching an array for the minimum may look clumsy. But the right question is not "which structure is more elegant?" but "which operation is performed how many times on this graph?"

18.4Recovering the path: the predecessor array

18.4.1Why one array is enough

shortest_path finds the lengths, but a traveler is not content with a length alone; the traveler also wants to know which cities the route passes through. Once the cost is known, the path is next. The first idea is to keep, for every vertex, all the vertices of its path in a separate list. This wastes memory and requires copying the list at every update. Building the path forward from the source is not possible either: when leaving the source, it is not known which edge to take until the algorithm has finished.

The solution is a single array. The shortest path to each vertex is obtained by appending a single edge to the shortest path of its predecessor. So it suffices to store, for every vertex, only the previous vertex on its path.

Definition 18.3

On the shortest path found from the source to t, the vertex immediately before t is called the predecessor of t and is stored in pred[t]. The array that holds the predecessors of all vertices is called the predecessor array.

A single array suffices because of a property of shortest paths. If a shortest path from the source to t passes through u, then the part of that path from the source to u is also a shortest path from the source to u. If the part could be replaced by a shorter one, the whole path would become shorter too. This property is called optimal substructure. As a consequence, all shortest paths form a tree. Its root is the source, and the parent of each vertex is its predecessor. This tree is called the shortest-path tree. Like the parent array used for sets, the predecessor array stores, for each vertex of this tree, the link to its parent.

The array is updated during relaxation. Line 20 of shortest_path performs the assignment pred[w] = u when a relaxation succeeds: the best path to w now passes through u. As the cost changes, the predecessor changes with it. In the example, while the value of 1 dropped from 50 to 45, its predecessor moved from 0 to 3. When the algorithm ends, the predecessor array of the example graph is pred = {0, 3, 0, 2, 0, 0}. The predecessor of 1 is 3, that of 3 is 2, and that of 2 is 0.

The array is read backward, not forward. Starting from the target and walking along predecessors, one arrives at the source: 1 ← 3 ← 2 ← 0. This order is the reverse of the path. To write it in the right order, either recursion or a stack is used. Both rely on the same principle: last in, first out.

18.4.2Recursive path printing

The recursive solution is short and elegant:

void print_path(int pred[], int s, int t)
{
    if (t == s) {
        printf("%d", s);
        return;
    }
    print_path(pred, s, pred[t]);   /* predecessor first */
    printf(" -> %d", t);
}
  • Lines 3–6. Base case: if the target is the source itself, the path is a single vertex; the source is printed and the routine returns.
  • Line 7. First the path up to the predecessor is printed. The recursive call moves one step closer to the source by replacing t with its predecessor.
  • Line 8. After the path to the predecessor has been printed, t is printed. Because the printing is done after the call, the vertices come out during the return, that is, from the source toward the target.

The routine works correctly only if the predecessor chain ends at the source. This holds for every reachable vertex, because the predecessors are the parent links of the shortest-path tree. For an unreachable vertex, however, the value of pred is meaningless. In the example pred[5] = 0, but there is no path from 0 to 5; this value is left over from the initial assignment in A1. If print_path(pred, 0, 5) is called, a path that does not really exist, such as "0 -> 5", is printed. So the caller should first check the condition dist[t] >= INF and, if it holds, print "no path."

18.4.3Printing the path with a stack

The same job can be done without recursion, using an explicit stack. First one walks from the target back to the source and pushes the vertices passed onto the stack. Then the source is printed, and the vertices on the stack are printed in the order they are popped. The stack reverses the order of the predecessor chain.

void print_path_stack(int pred[], int s, int t)
{
    int stack[MAX_VERTICES], top = -1;
    while (t != s) {                  /* walk from target to source */
        stack[++top] = t;
        t = pred[t];
    }
    printf("%d", s);
    while (top >= 0)                  /* print in reverse order */
        printf(" -> %d", stack[top--]);
}

Here the stack consists of an array and an index top. The expression stack[++top] = t first increments top and then writes to that cell; this is a push. stack[top--] first reads the cell and then decrements top; this is a pop. Since a path has at most n − 1 edges, an array of size MAX_VERTICES suffices. The program confirmed that the two routines produce the same output for the four reachable targets in the example graph. The recursive version is shorter, while the stack version does not depend on the depth of the call stack. On large graphs, where very long paths are possible, the latter is safer.

18.5Negative edges and all pairs

18.5.1Why Dijkstra fails on a negative edge

In real problems an edge weight is not always a length. An edge may represent a gain, an energy recovery, or a discount; in that case the weight is negative. The correctness proof of Dijkstra's algorithm relied on non-negative weights. The four-vertex graph in Figure 18.7 shows what happens when this assumption is broken. The edges are 0 → 1 (4), 0 → 2 (5), 1 → 3 (2), and 2 → 1 (−3).

Dijkstra's algorithm was traced by running a program. At the start the distances are 4 for 1, 5 for 2, and ∞ for 3. In the first round 1, with the smallest value (4), is selected and finalized; through 1 the value of 3 becomes 6. In the second round 2 is selected (5). The edge 2 → 1 opens a path of value 5 − 3 = 2, but 1 is already marked, so no relaxation takes place. The result is in Table 18.8: the values for 1 and 3 are wrong.

The source of the error is the assumption behind the greedy choice. Dijkstra assumes that a vertex, once selected, can never be reached later by a cheaper path. With non-negative weights this is true: the vertices not yet selected are farther away, and a path through them can only get longer. A negative edge, however, can return from a distant vertex and shorten the path. The wrong value of 1 carries over to 3 as well, because the path of 3 goes through 1. Adding the same constant to all weights to get rid of negativity is not a solution either. This transformation penalizes paths with many edges more than paths with one, and changes the shortest path itself.

With negative edges there is one more danger: a negative cycle. If a cycle whose weights sum to a negative number is reachable from the source, each trip around the cycle shortens the path a little more. In that case the shortest path is undefined; there is no "smallest" length, and the value decreases without bound. A good algorithm must be able to find and report such a cycle.

18.5.2The Bellman-Ford algorithm

The algorithm, named after Richard Bellman and Lester Ford, is not greedy; it finalizes no vertex early. Instead it relaxes all the edges over and over. The algorithm keeps the edges in an edge list. Each element carries the two endpoints of the edge and its weight:

typedef struct {
    int u, v, w;        /* edge <u,v>, weight w */
} edge;
int BellmanFord(edge edges[], int n, int e, int s, int d[])
{
    int i, j, t, u, v;
    for (i = 0; i < n; i++) d[i] = INF;
    d[s] = 0;
    for (t = 1; t <= n - 1; t++)          /* n-1 rounds */
        for (j = 0; j < e; j++) {
            u = edges[j].u;  v = edges[j].v;
            if (d[u] != INF && d[u] + edges[j].w < d[v])
                d[v] = d[u] + edges[j].w;
        }
    for (j = 0; j < e; j++)               /* round n */
        if (d[edges[j].u] != INF &&
            d[edges[j].u] + edges[j].w < d[edges[j].v]) return -1;
    return 0;              /* -1: negative cycle exists */
}

The body of the code is the same as the fragment in the slides; only the routine header and local variables were added around it. edges is the edge list, n the number of vertices, e the number of edges, s the source, and d the result array.

  • Lines 7–8. All distances are set to infinity and that of the source to 0. At the start, only the source is known to be reachable.
  • Lines 9–14. The main loop runs n − 1 rounds. In each round all the edges are relaxed in turn. The first part of the condition, d[u] != INF, prevents relaxing from a vertex that has not yet been reached. This check is mandatory because of negative edges: INF + (−3) is less than infinity, and without the check an unreached vertex would look "reached."
  • Lines 15–17. Round n: the edges are tried once more, but this time no value is changed. If some edge can still be relaxed, there is a negative cycle and the routine returns −1.
  • Line 18. If there is no cycle, it returns 0; the array d holds the shortest distances.

Why exactly n − 1 rounds? If there is no negative cycle, every shortest path can be chosen to be simple, and a simple path has at most n − 1 edges. What relaxation does is advance a path edge by edge.

Theorem 18.3 (Number of rounds in Bellman-Ford)

If there is no negative cycle reachable from the source, then after t rounds the value d is correct for every vertex that has a shortest path of at most t edges. Therefore n − 1 rounds suffice for all vertices.

Induction on t. For t = 0 the only vertex is the source, and d[s] = 0 is correct. Let the shortest path to v have t edges and let its last edge be <u, v>. The part of the path up to u is a shortest path of t − 1 edges. By the induction hypothesis, d[u] is correct after t − 1 rounds. When the edge <u, v> is relaxed in round t, d[v] ≤ d[u] + w, which is the shortest length. Since d[v] is always the length of an actual path, it cannot be smaller than this.∎

The converse of the theorem explains the cycle test. If there is no negative cycle, after n − 1 rounds all values are final and no edge can be relaxed. If an edge is still relaxed in round n, the assumption is broken: a reachable negative cycle exists. The program tried this case on a graph in which the cycle 1 → 2 → 1 sums to −1; the routine returned −1.

The cost is clear: in each of the n − 1 rounds e edges are tried, and the last round also tries e edges. The total is O(n · e). The extra memory is the array d: O(n). In a dense graph e ≈ n², so the time rises to O(n³). For this reason Bellman-Ford is slower than Dijkstra; it is preferred only when negative weights are present or when a negative cycle is being looked for. In practice, exiting the loop early when no value changes in a round is also a commonly used improvement. In the example the third round changed nothing; with this improvement the algorithm could have stopped there.

18.5.3All pairs: the Floyd-Warshall algorithm

Sometimes a single source is not enough; as with the distance table on a road map, the shortest length is wanted for every pair of vertices. This is the all-pairs shortest paths problem. Running Dijkstra once from every vertex is one solution, but it does not work if there is a negative edge. The algorithm named after Robert Floyd and Stephen Warshall solves the problem with very short code.

The idea of the algorithm is to release, one by one, the intermediate vertices that paths may use.

Definition 18.4

Ak[i][j] is the length of the shortest path from i to j all of whose intermediate vertices lie among 0, 1, …, k. A−1 is the case in which no intermediate vertex may be used; it is the cost matrix itself.

The link between Ak and Ak−1 comes from two cases. If the shortest path from i to j does not pass through k, its intermediate vertices go only up to k − 1 and its length is Ak−1[i][j]. If it passes through k, the path splits into two parts: from i to k and from k to j. Since there is no negative cycle, neither part uses k as an intermediate vertex, and their lengths are found in Ak−1. This gives the relation

Ak[i][j] = min { Ak−1[i][j], Ak−1[i][k] + Ak−1[k][j] }

Applying this relation in turn for k = 0, 1, …, n − 1 is a dynamic programming solution: the big problem is built from smaller subproblems whose results are stored in a table. An−1 is the case in which all vertices may be intermediate, and it is the result itself.

void Floyd(int cost[][MAX_VERTICES], int A[][MAX_VERTICES], int n)
{
    int i, j, k;
    for (i = 0; i < n; i++)
        for (j = 0; j < n; j++)
            A[i][j] = cost[i][j];
    for (k = 0; k < n; k++)              /* intermediate vertex k */
        for (i = 0; i < n; i++)
            for (j = 0; j < n; j++)
                if (A[i][k] + A[k][j] < A[i][j])
                    A[i][j] = A[i][k] + A[k][j];
}
  • Lines 4–6. The cost matrix is copied into the matrix A; this is A−1.
  • Line 7. The outer loop chooses the intermediate vertex. The order of the loops matters: k must be outermost. Each round of k uses the whole matrix of the previous round.
  • Lines 8–11. For every pair (i, j), the path through k is tried; if it is shorter, it is written.

The relation is written with two separate matrices, Ak−1 and Ak, but the code updates a single matrix A in place. This is safe. In round k, A[i][k] and A[k][j] do not change, because in the expression A[i][k] + A[k][k] we have A[k][k] = 0, and the sum cannot be smaller than A[i][k]. The values read during the round are therefore the same as those in Ak−1.

The algorithm is traced on Horowitz's three-vertex example. In the cost matrix, 0 → 1 = 4, 0 → 2 = 11, 1 → 0 = 6, 1 → 2 = 2, 2 → 0 = 3, and there is no direct edge from 2 to 1. The program printed the cells that changed in each round of k; in every round only one cell changed (Table 18.10).

The same routine was also applied to the six-vertex main example. Row 0 of the matrix came out as 0 45 10 25 45 1000, the same as Dijkstra's result. Row 5 is 58 23 38 3 33 0: since the only edge leaving 5 goes to 3, all paths from 5 pass through 3. The 1000s in column 5 show that no vertex can reach 5.

Floyd-Warshall allows negative edges but not negative cycles. If there is a negative cycle, a negative value appears on the diagonal at the end of the run: a path of negative length from a vertex to itself has been found. This is a simple way to test for the existence of a cycle.

Common mistake

Adding INF like an ordinary number in a graph with negative edges. In the code, the sum A[i][k] + A[k][j] is computed without a check. Let A[i][k] be infinite (1000) and A[k][j] be −5. The sum is 995, which is less than 1000; a path that does not exist is "found." The program tested this on a three-vertex graph: with no path at all from 0 to 2, A[0][2] = 995 came out. If there are negative edges, the condition must be written as A[i][k] != INF && A[k][j] != INF && …. The Bellman-Ford code already makes this check.

18.6Activity networks and topological order

18.6.1Projects and activities

A big job is the sum of smaller jobs. The construction of a building starts with laying the foundation; a certain time after the foundation sets, the first floor is poured, and then the second. The electrical wiring cannot be run before the walls are built, but painting and landscaping can go on at the same time. A university program is like this too: graduation comes from passing each of the courses, and some courses can be taken only after other courses. These smaller jobs are called activities, and the whole set of activities is called a project. A project ends when all its activities have ended.

The project manager's questions are clear. In what order can the jobs be done? When can the project finish at the earliest? Which jobs are critical, that is, which ones delay the whole project by a day if they slip by a day? Which jobs have slack, that is, can slip a little without consequence? To answer these questions, the activities and the before-and-after relations among them are shown in a graph. This graph is called an activity network.

18.6.2Activity-on-vertex networks and the precedence relation

The natural way to turn the information in the table into a graph is to make every course a vertex. If course i is a prerequisite of j, a directed edge is drawn from i to j. The graph with fifteen vertices and fourteen edges is in Figure 18.10.

Definition 18.5

A graph whose vertices are activities and whose directed edges show the precedence relation between activities is called an activity-on-vertex network (AOV network for short). If activity i must finish before j can start, the network contains the edge <i, j>.

A few terms are needed to name the relations in the network. They resemble family relations, but the direction is determined by the edges.

Definition 18.6

In an AOV network, if there is a directed path from i to j, then i is a predecessor of j and j is a successor of i. If the path consists of a single edge, that is, if <i, j> is an edge, then i is an immediate predecessor of j and j is an immediate successor of i.

In the course network, C3 and C6 are the immediate predecessors of C7. C9, C10, C12, and C13 are immediate successors of C7. C14 is a successor of C3 but not an immediate successor: C3 reaches C14 along the path C3 → C7 → C13 → C14. Figure 18.11 highlights the immediate predecessors and successors of C7. The precedence relation has two basic properties.

  • Transitivity. If i is a predecessor of j and j is a predecessor of k, then i is a predecessor of k. If C1 is a prerequisite of C3 and C3 is a prerequisite of C7, then C1 is also, indirectly, a prerequisite of C7.
  • Acyclicity. No activity can be its own predecessor. If A is a predecessor of B, then B cannot be a predecessor of A: B cannot start before A finishes, A cannot start before B finishes, and the project never ends. This means the graph contains no directed cycle.

The second property is not merely a theoretical condition; in real projects it is a common planning error. A directed graph that contains no directed cycle is called a directed acyclic graph (DAG). A valid AOV network is always a DAG. So when a network is built, it must be checked for cycles.

It is no accident that the course example is woven from courses such as numerical analysis and linear algebra. The roots of topics such as project planning, resource allocation, and shortest paths reach back to operations research. Dropping operations research and numerical analysis courses from curricula leaves students weak in the mathematics of such problems.

18.6.3Topological order

The course network puts a practical question to a student: in what order can the courses be taken? The order must be one in which the prerequisites of every course come before it.

Definition 18.7

A linear ordering of the vertices of an AOV network in which, whenever i is a predecessor of j, i comes before j in the order, is called a topological order.

The definition has three consequences. First, a topological order is often not unique. Two activities with no precedence relation between them can be written in either order. Second, if the graph has a directed cycle, there is no topological order: whichever vertex of the cycle is written first, some edge of the cycle points backward. Third, if there is no cycle, at least one topological order exists; the algorithm below is the proof.

Two valid orders for the course network are:

  • C1, C2, C4, C5, C3, C6, C8, C7, C10, C13, C12, C14, C15, C11, C9
  • C4, C5, C2, C1, C6, C3, C8, C15, C7, C9, C10, C11, C12, C13, C14

It is easy to check whether an order is topological. Find the position of every vertex in the order. Then, for each edge <i, j>, check that the position of i is smaller than that of j. The course network has 14 edges, and both orders satisfy all 14; this check was done with a program. When the topological_order routine, written below, was applied to the same network, it produced a third valid order: C15, C4, C5, C6, C2, C1, C3, C8, C7, C13, C14, C12, C10, C11, C9. All three orders are valid; which one comes out depends only on how the algorithm chooses vertices.

Topological order has wide uses. Course planning is only one of them. In a software project, the order in which source files are compiled (the job of the make tool), the scheduling of tasks in an operating system, and the order in which cells of a spreadsheet are recalculated are also topological orders. In a spreadsheet, if a cell's formula refers to other cells, those cells must be computed first; if two cells refer to each other, the program reports a "circular reference" error. This is another face of the cycle in an AOV network. The earliest-time computation in activity networks is also done in topological order.

18.6.4Deleting a vertex with no predecessor

The way to find a topological order rests on a simple observation: the first vertex of the order cannot have any predecessor. So a vertex with no predecessor is chosen and written. Then this vertex and the edges leaving it are deleted from the graph. The remaining graph is also an AOV network, and the same step is repeated on it. When all vertices have been written, the order is complete.

The method is traced on a network of six vertices (Figure 18.12). The edges are <0,1>, <0,2>, <0,3>, <1,4>, <2,4>, <2,5>, <3,4>, <3,5>.

At the start only v0 has no predecessor, and it is written first. When the three edges of v0 are deleted, v1, v2, and v3 are left with no predecessor. Any of the three may be chosen; in the example v3 is chosen. The edges <3,4> and <3,5> of v3 are deleted. Then v2, then v5, v1, and finally v4 are written. The result is v0, v3, v2, v5, v1, v4. Counting by program showed that this small network has 14 different topological orders; all of them can be reached by making a different choice at each step.

The method also finds cycles. If at some step there are vertices not yet written but none of them is free of predecessors, then in the remaining graph every vertex has at least one predecessor. Walking backward along predecessors, since there are finitely many vertices, some vertex is reached a second time: this is a directed cycle. The converse is also true: if there is no cycle, at least one predecessor-free vertex is found at every step, and the method writes all vertices. So the method both finds the order and tests whether the network is valid.

For the method to become efficient code, two operations must be fast: finding a predecessor-free vertex and deleting the outgoing edges of a vertex. If at every step all vertices are scanned to find a predecessor-free one, the cost rises to O(n²). A better way is to keep, in a counter, how many predecessors each vertex still has, and to collect the vertices whose counter drops to zero in a separate place.

18.6.5Data structure: counted headers

The graph is stored as adjacency lists. Each vertex has a header element. Besides the link to the first element of the list, the header has a count field. This field holds how many immediate predecessors the vertex has, that is, its in-degree.

typedef struct node *node_ptr;
typedef struct node {
    int vertex;
    node_ptr link;
} node;
typedef struct {
    int count;      /* for <i,j>: number of edges whose head is j */
    node_ptr link;
} head_node;
head_node head[MAX_VERTICES];
  • Line 1. node_ptr is a pointer type that points to a list element. The type name can be declared before the structure is defined; C allows this through an incomplete type. This lets the structure contain a field that points to its own type.
  • Lines 2–5. The list element: the vertex the edge leads to (vertex) and the next element in the list (link).
  • Lines 6–9. The header element: the predecessor counter and the head of the list. The headers sit in an array; the list elements are taken from heap memory with malloc.
  • Line 10. The headers of all vertices. Because it is a global array, all fields are zero when the program starts: the counters are 0 and the links are NULL.

When the edges are read, for each <i, j>, j is added to the list of i and head[j].count is incremented. The textbook does not write this step out separately; the routine below completes it. It appends the element to the end of the list, so the lists keep the order in which the edges were given.

int add_edge(head_node head[], int i, int j)
{
    node_ptr *tail = &head[i].link;   /* address of the link field */
    node_ptr new_node = malloc(sizeof(node));
    if (new_node == NULL)
        return 0;                     /* out of memory */
    new_node->vertex = j;
    new_node->link = NULL;
    while (*tail != NULL)              /* find the end of the list */
        tail = &(*tail)->link;
    *tail = new_node;
    head[j].count++;                /* j has one more predecessor */
    return 1;
}

The interesting part of the routine is the variable tail. tail points not to an element but to a link field; its type is pointer to pointer (node_ptr *). At first it holds the address of the field head[i].link. If the list is empty, this field is NULL and the new element is written directly there. If the list is not empty, at each step the loop moves to the link field of the next element and stops at the last link, which is NULL. The assignment *tail = new_node handles the empty list and the non-empty list with the same line. Without a pointer to a pointer, a separate if would be needed for the empty list.

The return value of malloc must always be checked. If memory runs out, malloc returns NULL, and the assignment new_node->vertex would cause undefined behavior. The routine reports this to the caller by returning 0. Because insertion is at the end of the list, the cost is O(d) if the out-degree of a vertex is d. Insertion at the head would take O(1), but the lists would be in the reverse of the edge order, which would change the output of the topological order.

When the edges of the six-vertex network are added in the order <0,1>, <0,2>, <0,3>, <1,4>, <2,4>, <2,5>, <3,5>, <3,4>, the structure in Figure 18.13 results. That v5 comes before v4 in the list of v3 is due to the edges being given in this order. The counters are 0, 1, 1, 1, 3, 2: v4 has three predecessors (v1, v2, v3), and v5 has two (v2, v3).

In memory, each list element consists of an int and a pointer. On a 64-bit system an int is 4 bytes and a pointer is 8. Because a pointer must sit at an address that is a multiple of 8, 4 bytes of padding are added after the int, and sizeof(node) is 16. The header element is 16 bytes for the same reason. These values were measured on x86-64 with the zig cc compiler. The six-vertex, eight-edge network uses 96 bytes for the headers and 128 bytes for the list elements. The total memory is O(n + e).

When the lists are no longer needed, the memory must be given back. The routine below walks each list from start to end and frees the elements one by one:

void free_lists(head_node head[], int n)
{
    int i;
    node_ptr p, next;
    for (i = 0; i < n; i++) {
        for (p = head[i].link; p; p = next) {
            next = p->link;         /* save before free */
            free(p);
        }
        head[i].link = NULL;
        head[i].count = 0;
    }
}

The variable next in the loop is essential. Accessing p->link after free(p) means reading freed memory, which is undefined behavior. So the address of the next element is saved before free. To check for leaks, malloc and free were replaced in the tests by small wrappers that count calls. In the chapter's topological-order tests, 24 malloc and 24 free calls were counted; there is no memory leak. This counting method was used because on Windows the zig compiler could not link the address sanitizer (-fsanitize=address).

18.6.6The topological_order routine

The routine collects the predecessor-free vertices on a stack. No separate array is set aside for the stack; the count field of a vertex whose counter has dropped to zero is now free and is used as the link of the stack.

void topological_order(head_node head[], int n)
{
    int i, j, k, top = -1;
    node_ptr p;
    for (i = 0; i < n; i++)      /* count 0: push on the stack */
        if (!head[i].count) {
            head[i].count = top;  top = i; }
    for (i = 0; i < n; i++) {
        if (top == -1) { printf("cycle"); break; }
        j = top;  top = head[top].count;
        printf("%d ", j);
        for (p = head[j].link; p; p = p->link) {
            k = p->vertex;
            if (--head[k].count == 0) {
                head[k].count = top;  top = k; }
        }
    }
}
  • Line 3. top is the vertex at the top of the stack. −1 means the stack is empty, that is, marks its bottom.
  • Lines 5–7. The first loop pushes all vertices whose counter is 0 onto the stack. The assignment head[i].count = top writes the vertex that lies beneath it in the stack into its count field. Then top = i brings the new vertex to the top. This is the same as the insertion at the head of a stack implemented with a linked list; count is used as the link field.
  • Line 8. The second loop runs n rounds; in each round one vertex is written.
  • Line 9. If the stack is empty when a vertex is about to be written, no predecessor-free vertex is left. Since not all n vertices have been written yet, the remaining vertices form a cycle. The routine prints "cycle" and stops.
  • Lines 10–11. Popping from the stack: the vertex at the top is taken into j, and the vertex beneath it (head[top].count) becomes the new top. j is printed.
  • Lines 12–16. The list of j is walked. The predecessor count of every immediate successor k is decreased by one; deleting j means deleting the edges leaving j. If the counter drops to 0, k has no predecessor left and is pushed onto the stack.

The embedded-stack technique is surprising at first. There is no variable called "stack" in the code; only the comment and the variable top give away what it is. This is exactly why comments matter: someone reading the code learns from them where and how the stack is used. The technique is similar to the parent array used for sets. There each element holds the number of its parent, and the links are embedded in an array. Here too the links of the stack are embedded in the header array. A field can serve two separate purposes because the two purposes do not overlap in time. Until the counter drops to 0, the field holds the predecessor count; after it drops, the predecessor count is never needed again.

The expression --head[k].count == 0 combines two jobs: it first decrements the counter, then compares the new value with 0. It means the same as the pair count--; if (!count) in the textbook. The prefix decrement operator matters here. If the postfix form were used (head[k].count-- == 0), the comparison would be made with the old value. When the last predecessor is deleted, the old value is 1, so no successor would ever enter the stack; in the example the output would be cut off with 0 cycle.

Common mistake

Calling topological_order a second time on the same header array. When the routine finishes, the count fields hold not predecessor counts but leftovers of the stack links. In the example the counters were left as −1, −1, 1, 2, −1, 1 after the routine. To run it again, the counters must be recomputed from the lists or the lists must be rebuilt.

18.6.8Cycle detection, analysis, and the queue version

A cycle means two activities are each other's predecessors, and it is a planning error: if there is a cycle, the project never ends. How the routine catches a cycle was tested on a small network. The edges are <0,1>, <1,2>, <2,1>, <2,3>; 1 and 2 are each other's predecessors. The routine first writes 0. The counter of 1 drops from 2 to 1 and does not reach zero, because the edge from 2 is still there. At the start of the second round the stack is empty, but only one vertex has been written. The output is 0 cycle.

The cost of the routine comes from two loops. The first loop looks at the n headers once: O(n). The second loop runs at most n rounds. In each round a vertex is taken from the stack and its list is walked. The list of j has dj elements, so the inner for runs as many times as the out-degree. Since every vertex is taken from the stack at most once, the total number of rounds of the inner loop is the sum of all out-degrees. In a directed graph this sum equals the number of edges. The result is

O(n + d0 + d1 + ⋯ + dn−1) = O(n + e)

The number of edges varies with how the graph is connected. In a sparse network e is of the order of n and the time is linear. In a very dense network e can reach the order of n². Since every edge must be read at least once, no algorithm can be faster than O(n + e); this routine is optimal.

A stack is not essential for collecting the predecessor-free vertices; any container will do. If a queue is used, the algorithm is named after Kahn (Arthur Kahn, 1962). The version below implements the queue with a simple array:

void queue_order(head_node head[], int n)
{
    int queue[MAX_VERTICES], front = 0, rear = 0, i, j, k;
    node_ptr p;
    for (i = 0; i < n; i++)
        if (!head[i].count)
            queue[rear++] = i;       /* enqueue */
    while (front < rear) {
        j = queue[front++];             /* dequeue */
        printf("%d ", j);
        for (p = head[j].link; p; p = p->link) {
            k = p->vertex;
            if (--head[k].count == 0)
                queue[rear++] = k;
        }
    }
    if (rear < n)
        printf("cycle");
}

In this version the cycle test is made at the end: if the number of vertices that entered the queue is less than n, the counters of some vertices never dropped to zero. On the same six-vertex network the queue version printed 0 1 2 3 5 4. This time v1, v2, v3 come out in the order they entered. While v3 is processed, the counter of v5 drops to zero first and then that of v4, because v5 is at the front of v3's list. The two outputs differ, but both are valid topological orders. The type of container only chooses among equally valid orders. The queue version also printed 0 cycle on the network with a cycle, and no memory leak was seen in any test of the two versions.

18.7Activity-on-edge networks and the critical path

18.7.1The activity-on-edge network

An AOV network shows the order of jobs but not their durations. To compute the project duration, a second model is used. In this model the activities are placed on the edges, and the moments that determine when activities finish are placed on the vertices.

Definition 18.8

A directed acyclic graph whose directed edges represent activities, whose edge weights represent the durations of the activities, and whose vertices represent events is called an activity-on-edge network (AOE network for short). An event is the moment at which all activities entering it have finished; the activities leaving the event can start only after this moment.

An event is an intermediate milestone that must be reached for the project to be completed. The job that has to finish is expressed by a vertex: "foundation done," "rough construction done." The network has a single start event (a vertex with no incoming edge) and a single finish event (a vertex with no outgoing edge). The start is the moment the project begins, and the finish is the moment it ends.

For the rest of the chapter the network in Figure 18.15 is used. The network has nine events (v0–v8) and eleven activities (a0–a10). v0 is the start event and v8 is the finish event.

The network shows parallelism directly. a0, a1, and a2 can start at the same time, on the first day of the project; the only condition of all three is the start event. a6 and a7 leave the event v4. a3 and a4 enter v4. So a6 and a7 cannot start until both a3 and a4 have finished. Similarly, a7 and a8 enter v7; a10 starts only when these two are done. The list of activities is in Table 18.14.

18.7.2From AOV to AOE: the dummy activity

An AOV network can be converted into an AOE network, but the conversion is not always a one-to-one mapping of edges. In the AOV network of Figure 18.16, activity 4 waits for both 2 and 3. In the AOE network, 2 and 3 are edges; for 4 to be able to start, both edges must arrive at the same event. If the two edges end at different events, these events are joined by an edge of duration 0.

Definition 18.9

An edge of duration 0 added to an AOE network solely to express a precedence relation is called a dummy activity.

A dummy activity may be needed in the main example too. If a6 and a7 were required to start after a5 finishes, in addition to a3 and a4, an edge would be needed from the event v5, where a5 finishes, to the event v4, where a6 and a7 start. This edge is not a job but only a waiting rule: the dummy activity <v5, v4>, duration 0.

Drawing a network with the fewest dummy activities is a problem that looks easy but is hard. It has been shown to be NP-hard; that is, no known algorithm solves it efficiently on large networks. It is a research topic, studied at thesis level in the field concerned with legible drawing of graphs (graph drawing).

AOE networks are the basis of the classical methods of project management. PERT (Program Evaluation and Review Technique) was developed in 1958 for the US Navy's Polaris missile program. CPM (Critical Path Method) arose in industry in the same years, for planning maintenance and construction projects. RAMPS (Resource Allocation and Multi-Project Scheduling) deals with sharing resources among several projects. Most of today's project-management software performs the computations of these methods.

18.7.3The critical path

Because activities can run in parallel, the project duration is not the sum of all durations. The sum is 6 + 4 + 5 + 1 + 1 + 2 + 9 + 7 + 4 + 2 + 4 = 45 days, but the project finishes in far less time. The finish event occurs when the activities on every path leading to it have finished. So the project duration is the length of the longest of the paths from start to finish.

Definition 18.10

In an AOE network, the longest path from the start event to the finish event is called the critical path. The length of the critical path is the shortest time in which the project can finish. A network may have more than one critical path.

The example network has two critical paths: v0-v1-v4-v6-v8 (6 + 1 + 9 + 2 = 18) and v0-v1-v4-v7-v8 (6 + 1 + 7 + 4 = 18). The project finishes in 18 days at the earliest. The other paths are shorter; for example the path v0-v3-v5-v7-v8 takes 5 + 2 + 4 + 4 = 15 days. Figure 18.17 shows the critical paths with thick lines.

That "shortest time" and "longest path" are the same thing looks contradictory at first. There is no contradiction: the project cannot finish sooner than the longest chain of waiting, but when that chain is done, no other job is left waiting. In a general graph, finding the longest simple path is NP-hard. An AOE network, however, is acyclic, and in an acyclic graph the longest path is found with a single pass in topological order. The computations below do exactly this.

The concept of the critical path tells the manager two things. If an activity on the critical path slips by a day, the project slips by a day. The foremen of these jobs are told: "Do not let 4 days stretch to 5; I would be glad if it finished in 3." For activities not on the critical path, a certain amount of delay does not affect the project. To find out what this amount is, the earliest and latest start times of every activity are computed. The problem is an operations research problem.

18.8Earliest and latest times

These computations look simple on paper. But running them by hand takes care: if one mixes up which value is final at which moment and which value may still change, the result is spoiled. That is why the computations below are given step by step in tables.

18.8.1The earliest start time

An activity can start as soon as its tail event occurs. The earliest start time of the activity ai = <k, m> is therefore equal to the earliest time of event k. The earliest times of events are kept in the array earliest.

For example, the tail of a1 is v0, and it starts on day 0 at the earliest. The tail of a5 is v3; only a2 enters v3, and it takes 5 days. a5 starts on day 5 at the earliest. The tail of a8 is v5; a5, which starts on day 5 and lasts 2 days, enters v5, so a8 starts on day 5 + 2 = 7 at the earliest.

When several activities enter an event, the situation changes. a3 and a4 enter v4. a3 starts on day 6 and finishes on day 6 + 1 = 7. a4 starts on day 4 and finishes on day 4 + 1 = 5. The event v4 waits for both to finish; so it waits for the one that finishes last, that is, day 7. In general the rule is

earliest[m] = max { earliest[k] + duration(<k, m>) : k ∈ P(m) }

where P(m) is the set of immediate predecessors of m. The value of the start event is 0. 0 stands for the day the project begins; if the project starts on May 8, day 0 is May 8. If the start were given 10, all values would shift by 10 days.

The formula has one condition: when earliest[m] is computed, the values of the predecessors must be final. This means the computation must be done in topological order. So the topological_order routine, with a small addition, performs this computation too. A duration field holding the duration of the activity is added to the list element:

typedef struct node *node_ptr;
typedef struct node {
    int vertex;
    int duration;            /* duration of the activity */
    node_ptr link;
} node;
typedef struct {
    int count;
    node_ptr link;
} head_node;
int earliest[MAX_VERTICES], latest[MAX_VERTICES];

With this structure the element size does not change: vertex and duration take 4 bytes each and fill the place of the earlier padding; sizeof(node) is still 16. The edge-insertion routine is also extended to write only the duration:

int add_edge(head_node head[], int i, int j, int duration)
{
    node_ptr *tail = &head[i].link;
    node_ptr new_node = malloc(sizeof(node));
    if (new_node == NULL)
        return 0;
    new_node->vertex = j;
    new_node->duration = duration;
    new_node->link = NULL;
    while (*tail != NULL)
        tail = &(*tail)->link;
    *tail = new_node;
    head[j].count++;
    return 1;
}

In the inner loop of topological_order, before the counter is decremented, these two lines are executed:

/* inside topological_order, before the count is decremented: */
if (earliest[k] < earliest[j] + p->duration)
    earliest[k] = earliest[j] + p->duration;

j is the vertex just taken from the stack and written, and k is one of its immediate successors. If the path to k through j requires a longer wait, the value of k is increased. This is exactly the relaxation of Dijkstra's algorithm; the only differences are the direction of the < comparison and that the value sought is the largest. earliest is initially filled with 0s. Since all durations are non-negative, 0 is a valid lower bound for every event. The complete routine with the additions is:

void compute_earliest(head_node head[], int n)
{
    int i, j, k, top = -1;
    node_ptr p;
    for (i = 0; i < n; i++)
        earliest[i] = 0;
    for (i = 0; i < n; i++)
        if (!head[i].count) {
            head[i].count = top;  top = i; }
    for (i = 0; i < n; i++) {
        if (top == -1) { printf("cycle"); break; }
        j = top;  top = head[top].count;   /* pop from the stack */
        printf("%d ", j);
        for (p = head[j].link; p; p = p->link) {
            k = p->vertex;
            if (earliest[k] < earliest[j] + p->duration)
                earliest[k] = earliest[j] + p->duration;
            if (--head[k].count == 0) {
                head[k].count = top;  top = k;  /* push on the stack */
            }
        }
    }
}
  • Lines 5–9. The array is initialized and the predecessor-free vertices are pushed onto the stack. This part is the same as the first loop of topological_order.
  • Lines 12–13. An event is taken from the stack. From this moment on earliest[j] never changes again, because all predecessors of j were processed earlier.
  • Lines 16–17. For every activity leaving j, the value of the successor is increased if necessary.
  • Lines 18–20. If the last predecessor of the successor has also been processed, the successor enters the stack. The order of the lines matters: the value update must be done before the counter is decremented. Otherwise, by the time the vertex enters the stack and is written in another round, the contribution from the last edge might not have been added yet.

18.8.3The latest start time

The earliest times answer the question "when can we start at the soonest?" The manager's second question is "when must we start at the latest, without delaying the project?" This time the computation starts at the finish and walks backward. The latest time of the finish event is taken equal to its earliest time: if the project can finish in 18 days, it must finish on day 18. So latest[8] = earliest[8] = 18.

The activity ai = <k, m> must start at latest[m] − duration at the latest; otherwise event m is late. a10 (v7 → v8, 4 days) must start by day 18 − 4 = 14 at the latest. a9 (v6 → v8, 2 days) must start by day 18 − 2 = 16 at the latest. Hence latest[7] = 14 and latest[6] = 16.

If several activities leave an event, the event must meet the activity that has to start earliest. So the smallest value is taken:

latest[k] = min { latest[m] − duration(<k, m>) : m ∈ S(k) }

where S(k) is the set of immediate successors of k. v0 is a good example. Three activities leave v0. For a0 we get 6 − 6 = 0, for a1 6 − 4 = 2, for a2 8 − 5 = 3. The smallest is 0, so latest[0] = 0. Had the largest, 3, been chosen, a0 would start three days late, v1 would slip to day 9, v4 to day 10, v6 to day 19, and the project would stretch to 21 days. The largest value is taken in the forward pass and the smallest in the backward pass; confusing the two is the most common mistake in such computations.

The computation needs the successors of every event, and the values of the successors must become final first. The easiest way is to reverse all the arrows. In the reversed graph, successors turn into predecessors, and the same topological-order routine can be used. The reversed graph is obtained by building the reverse of the adjacency list:

int build_reverse(head_node head[], head_node rev[], int n)
{
    int i;
    node_ptr p;
    for (i = 0; i < n; i++) {
        rev[i].count = 0;
        rev[i].link = NULL;
    }
    for (i = 0; i < n; i++)
        for (p = head[i].link; p; p = p->link)      /* <i, p->vertex> */
            if (!add_edge(rev, p->vertex, i, p->duration))
                return 0;
    return 1;
}

For every edge <i, j>, the routine adds i to the reverse list of j, with the same duration. add_edge also increments the count field in the reverse list; this counter is the in-degree in the reversed graph, that is, the out-degree in the original graph. The routine touches every edge once and finishes in O(n + e); the extra cost of appending to the end of a list is also bounded in total by the number of edges. The reverse lists are built only from the link and duration fields, either before the forward pass spoils the count fields or independently of it.

The loop of the backward pass is the same as that of the forward pass; only the relaxation line changes:

if (latest[k] > latest[j] - p->duration)
    latest[k] = latest[j] - p->duration;

Here j is the event written in the reverse list, and k is one of its predecessors in the original graph. latest is initially filled with the project duration, that is, 18, and values only decrease. The complete routine is:

void compute_latest(head_node head[], int n, int finish)
{
    int i, j, k, top = -1;
    node_ptr p;
    for (i = 0; i < n; i++)
        latest[i] = finish;
    for (i = 0; i < n; i++)
        if (!head[i].count) {
            head[i].count = top;  top = i; }
    for (i = 0; i < n; i++) {
        if (top == -1) { printf("cycle"); break; }
        j = top;  top = head[top].count;   /* reverse list */
        printf("%d ", j);
        for (p = head[j].link; p; p = p->link) {
            k = p->vertex;                        /* k: predecessor */
            if (latest[k] > latest[j] - p->duration)
                latest[k] = latest[j] - p->duration;
            if (--head[k].count == 0) {
                head[k].count = top;  top = k;
            }
        }
    }
}

18.8.5Slack and critical activities

Two times are now known for every activity. For ai = <k, m>, the earliest start time is earliest[k] and the latest start time is latest[m] − duration. The difference between them is the number of days the activity can be shifted without delaying the project.

Definition 18.11

The slack of the activity ai = <k, m> is the difference between its latest and earliest start times: latest[m] − duration(ai) − earliest[k]. An activity whose slack is 0 is called a critical activity.

A critical activity must start at its earliest time; a one-day delay in it delays the whole project by a day. All the activities of the example network are in Table 18.17. The table is the same as the program's output.

The slack in the table is the total float. Total float is shared among the activities on the same path. a2, a5, and a8 are on the same path, and all three have slack 3. But this does not mean that all three can be late by three days each. If a2 is three days late, the allowance of a5 and a8 is used up; both become critical. Slack can be spent once along a path.

For this a second measure is used. The free float is the slack an activity can use without delaying the earliest time of its successors: earliest[m] − earliest[k] − duration. For a2 it is 5 − 0 − 5 = 0, for a5 it is 7 − 5 − 2 = 0, and for a8 it is 14 − 7 − 4 = 3. That is, the slacks of a2 and a5 are not their own; they come from a8 on the same path. a8, on the other hand, can use its three days without affecting anyone. The free float of a4 is 7 − 4 − 1 = 2.

18.8.6Finding the critical path in a program

Once the two arrays have been computed, printing the slack of every activity takes a single double loop. The lists of the original graph are walked; each element is an activity.

void slacks(head_node head[], int n)
{
    int i;
    node_ptr p;
    /* after earliest[] and latest[] have been computed */
    for (i = 0; i < n; i++)
        for (p = head[i].link; p; p = p->link) {
            int early = earliest[i];
            int late   = latest[p->vertex] - p->duration;
            printf("<%d,%d> early=%d late=%d slack=%d%s\n",
                   i, p->vertex, early, late, late - early,
                   late == early ? " CRITICAL" : "");
        }
}

The first four lines of the output are:

<0,1> early=0 late=0 slack=0 CRITICAL
<0,2> early=0 late=2 slack=2
<0,3> early=0 late=3 slack=3
<1,4> early=6 late=6 slack=0 CRITICAL

The remaining lines are identical to Table 18.17. By keeping only the activities with slack 0, the routine also yields the critical path: the critical activities form one or more paths from v0 to v8. The ?: operator in printf selects a string conditionally: if the slack is 0, " CRITICAL" is printed; otherwise an empty string.

The cost of the whole computation is the sum of its parts. The forward pass is O(n + e), building the reverse list is O(n + e), the backward pass is O(n + e), and the slack scan is O(n + e). The total is O(n + e); however large the project, the computation finishes in linear time. In the chapter's tests, 22 malloc and 22 free calls were counted for the forward and reverse lists; there is no leak.

Common mistake

Taking the smallest value for the earliest time and the largest for the latest time. The correct rule is the reverse. An event waits for all the jobs entering it to finish, so the earliest time is the largest value. An event must meet all the jobs leaving it, so the latest time is the smallest value. In code this is the direction of the comparison signs: increasing with < in the forward pass, decreasing with > in the backward pass.

18.10Common mistakes

  1. Using Dijkstra on a graph with negative edges. The algorithm raises no error; it silently produces a wrong result. If there are negative weights, use Bellman-Ford, or relaxation in topological order for an acyclic graph.
  2. Choosing INT_MAX for infinity. The sum dist[u] + cost[u][w] overflows; signed integer overflow is undefined behavior, and the result is often a negative number. Choose a constant that is larger than the real paths but whose double still fits in an int.
  3. Taking the smallest for the earliest time and the largest for the latest time. The correct rule is the reverse: the earliest time waits for the largest of the entering activities, and the latest time must meet the smallest of the leaving activities.
  4. Computing the latest time before the successors are final. The backward pass must be done in a topological order of the reversed graph, or in the reverse of the forward order. In an arbitrary order, the value of an event whose successor has not yet been processed is mistaken for final.
  5. Starting the topological order from an arbitrary vertex. The earliest time of a vertex whose predecessors have not been processed is only a lower bound. A value becomes final only when the vertex is taken from the stack and written.
  6. Trying to build the path forward. When leaving the source, it is not known which edge to choose. The predecessor array is read backward from the target and written in the right order by reversing with recursion or a stack.
  7. Printing a path to an unreachable vertex. If dist[t] >= INF, then pred[t] is meaningless; this condition must be checked first.
  8. Calling topological_order a second time on the same structure. The counter fields have turned into stack links; the counters must be recomputed.

18.11Exercises and solutions

18.11.1A different source

Question. What distances would shortest_path find if the source in the six-vertex example graph were 2?

Solution. Initially the row of 2 is copied: 20 for 0, 15 for 3, 1000 for the rest. In the first round 3 is selected (15); through 3 we get 15 + 20 = 35 for 1 and 15 + 35 = 50 for 4. In the second round 0 is selected (20); no value is shortened through 0 (70 for 1, 65 for 4). In the third round 1 is selected (35); through 1 we get 35 + 10 = 45 for 4, which replaces 50. In the fourth round 4 is selected. Result: d(2→0) = 20, d(2→3) = 15, d(2→1) = 35 (through 3), d(2→4) = 45 (through 3 and 1); there is no path to 5.

18.11.2Number of rounds of the outer loop

Question. Why does the outer loop of shortest_path run n − 2 rounds? What would happen if it ran n − 1 rounds?

Solution. The source is final at the start; after n − 2 rounds, n − 1 vertices are marked. For the one remaining vertex, all other vertices are in S, and its dist value is by definition the shortest length. If one more round were run, this vertex would be selected and marked, but since no unmarked vertex would be left to relax, no value would change. The extra round is harmless but unnecessary.

18.11.3If an edge weight changes

Question. In the step-by-step seven-vertex example, what would be the order of joining S if the edge v3 → v6 were 15 instead of 2?

Solution. The first four selections do not change: v1 (10), v2 (20), then v3 and v4 (both 30; on a tie the smaller index goes first: v3, v4). When v3 joins, the value of v6 is this time 30 + 15 = 45. When v4 joins, v5 drops to 40. Since 40 < 45, v5 is selected before v6. There is no edge from v5 to v6; v6 stays at 45. The order is v1, v2, v3, v4, v5, v6. The program gave the same order and the result dist = 0 10 20 30 30 40 45.

18.11.4A queue instead of a stack

Question. If a queue were used instead of a stack in the topological-order routine, what would the output be in the v0…v5 example?

Solution. 0 1 2 3 5 4. When v0 is taken, v1, v2, v3 enter the queue in this order and leave in the same order. When v1 is taken, the counter of v4 drops to 2; when v2 is taken, to 1; the counter of v5 drops to 1. When v3 is taken, the counter of v5 and then that of v4 drops to 0, because v5 comes before v4 in the list of v3. The queue version printed this output in the program too.

18.11.5If an activity takes longer

Question. In the AOE example, what would the project duration and critical path be if a8 took 8 days instead of 4?

Solution. v7 is reached through v5 at 7 + 8 = 15, which is greater than the 14 coming through v4. earliest[7] = 15, and for v8 we get 15 + 4 = 19, so the project stretches to 19 days. The critical path is now v0-v3-v5-v7-v8 (5 + 2 + 8 + 4 = 19). The old critical paths took 18 days, so they are no longer critical; the program found a slack of 1 day for a0, a3, a6, a7, and a9. The slack of a8 was 3 days; a non-critical activity that grows by more than its slack (4 days) changes the critical path. This is why the computation must be redone after every change.

18.11.6A late change in Floyd-Warshall

Question. Why did A[1][0] change in round k = 2 of the Floyd-Warshall example?

Solution. The shortest path from 1 to 0 is 1 → 2 → 0: 2 + 3 = 5, while the direct edge is 6. This path uses 2 as an intermediate vertex. Since Ak allows only intermediate vertices among 0…k, using 2 becomes possible only in round k = 2.

18.12Summary

  • The shortest-path problem is posed on a weighted directed graph; the length of a path is the sum of its edge costs. It has single-source single-target, single-source all-targets, and all-pairs versions.
  • Brute force tries all simple paths. In a complete graph the number of paths is 1 + (n − 2) + ⋯ + (n − 2)!; even for a single target it needs work of the order of O(nⁿ).
  • Dijkstra's algorithm is greedy: it finalizes the vertex outside S with the smallest distance, then relaxes through it. It requires w ≥ 0. It takes O(n²) with a matrix and O((n + e) log n) with a min-heap and adjacency lists.
  • A constant that does not cause overflow is chosen for infinity. min_vertex returns −1 only when no unmarked vertex is left.
  • The predecessor array alone suffices: shortest paths form a tree. The path is read backward from the target and written in the right order with recursion or a stack.
  • Dijkstra goes wrong on a negative edge. Bellman-Ford relaxes all edges for n − 1 rounds and catches a negative cycle in round n: O(n · e). Floyd-Warshall releases the intermediate vertices one by one and finds all pairs in O(n³).
  • An activity-on-vertex network shows the precedence relation and must be acyclic. A topological order is found by deleting predecessor-free vertices one at a time. With counted headers and an embedded stack it takes O(n + e); the same routine also catches a cycle.
  • In an activity-on-edge network the edges are activities and the vertices are events. The project duration is the longest path from start to finish: the critical path.
  • Earliest times are found in topological order by taking the largest value (forward pass), and latest times on the reversed graph by taking the smallest value (backward pass). Slack is the difference between the latest and earliest start times. The activities with slack 0 form the critical path.

18.14Try It Yourself

  1. In the six-vertex example graph, if 5 is taken as the source, in what order does Dijkstra finalize the vertices, and what are the distances?

    Answer

    The only edge from 5 goes to 3 (3). The order is 3 (3), 1 (23), 4 (33), 2 (38); 0 is the last remaining vertex, and its value is 58 through 2. The distances to 0 through 4 are 58, 23, 38, 3, 33, respectively. Row 5 of Floyd-Warshall gives the same values.

  2. When shortest_path finishes, pred = {0, 3, 0, 2, 0, 0}. How many recursive calls does print_path(pred, 0, 3) make, and what does it print?

    Answer

    Three calls are made, including the first: t = 3, 2, 0. The output is 0 -> 2 -> 3; the cost is 10 + 15 = 25.

  3. In a Dijkstra code that uses INT_MAX as infinity, what can happen if an unreachable u is selected and dist[u] + cost[u][w] is computed?

    Answer

    The sum does not fit in an int; signed overflow is undefined behavior. In practice the result often wraps to a negative number, appears smaller than dist[w], and a nonexistent "short path" is written.

  4. In the four-vertex negative example, how many rounds does Bellman-Ford run and how many relaxation attempts does it make in total? After which round does no value change?

    Answer

    n − 1 = 3 rounds with 4 edges each: 12 attempts; in round n another 4 edges are checked. The last change happens in the second round (d[3] from 6 to 4); the third round changes nothing.

  5. What happens if the order of the loops in the Floyd-Warshall code is changed to i, j, k (with k innermost)?

    Answer

    The algorithm loses its correctness. The values A[i][k] and A[k][j] used in computing A[i][j] may have been taken before all the intermediate vertices were taken into account. The definition of Ak is satisfied when k is outermost.

  6. In the v0…v5 topological-order example, what would topological_order print if the list of v3 were v4, v5 instead of v5, v4?

    Answer

    0 3 2 5 1 4; the output does not change. While v3 is processed, the counter of v4 drops to 2 and that of v5 to 1; since neither reaches zero, the order of entering the stack is not affected. List order changes only the order of vertices whose counters drop to zero at the same time.

  7. In the AOE example, what would the project duration and critical path be if a6 took 10 days instead of 9?

    Answer

    v6 occurs at 7 + 10 = 17 at the earliest and v8 at 17 + 2 = 19; the project takes 19 days. The only critical path is v0-v1-v4-v6-v8. The slack of a7 and a10 becomes 1, because the path through v7 takes 18 days.

  8. In the AOE example, what are the total float and the free float of a4? What does it mean that the two are equal?

    Answer

    The total float is 6 − 4 = 2, and the free float is earliest[4] − earliest[2] − 1 = 7 − 4 − 1 = 2. That they are equal shows that a4 can use its two days of allowance without affecting the earliest time of any successor; the allowance is not shared with another activity.
