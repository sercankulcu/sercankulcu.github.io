Chapter 9: The List ADT and Generalized Lists

What can be done with a list and how a list is stored in memory are two separate questions. These notes first answer the first question: they write the operations of the list abstract data type as a contract, with preconditions and postconditions. They then implement the same contract with an array and with a linked list and compare the two implementations by cost. In the second half the notion of a list is generalized. Generalized lists come next: their elements may be not only single values but other lists as well. On this structure the routines for copying, equality, traversal, depth, and inversion are written recursively and traced step by step. The last sections cover how a tree can be stored as a single line of text, the problems caused by shared sublists, reference counting, and garbage collection.

9.1The list abstract data type

When a program uses a list, it wants to know two things: which operations can be applied to the list, and what state the list will be in at the end of each operation. Whether the list lives in memory as an array or as nodes linked to one another is not the business of the code that uses it. This separation is one of the basic ideas of software engineering and is the subject of this section.

9.1.1The linear list and the contract

Definition 9.1

A linear list is an ordered sequence of n ≥ 0 elements: L = (a0, a1, …, an−1). n is the length of the list; if n = 0, the list is empty. For every i < n − 1, ai comes before ai+1. The place of an element in the list, that is, i, is its position.

The definition speaks only of order. Whether the elements sit side by side in memory, or how one passes from one element to the next, is not in the definition. The days of the week, the student numbers of a class, or the lines of a text fit this definition. The jobs to be done with such lists are also clear: reading the i-th element, inserting an element at a position, deleting the element at a position, searching for a value, and learning the length.

A type that defines operations and their behavior while hiding the implementation is called an abstract data type (ADT). The list ADT is an abstract data type that offers insertion, deletion, and access by position. In C, the outward face of an abstract data type is usually declarations written in a header file. The slides give the interface of the list ADT as follows:

typedef struct list List;           // opaque type

List  *list_create(void);
void   list_destroy(List *L);
int    list_length(const List *L);
bool   list_get(const List *L, int i, int *x);
bool   list_insert(List *L, int i, int x);  // 0<=i<=n
bool   list_delete(List *L, int i, int *x);  // 0<=i<n
int    list_find(const List *L, int x);    // -1 if absent

Each function's name says what it does. list_create builds an empty list and returns its address; list_destroy returns all the memory belonging to the list. list_get(L, i, &x) writes the i-th element into x, list_insert(L, i, x) inserts x at position i, and list_delete(L, i, &x) removes the i-th element and writes it into x. list_find returns the position of the sought value, or −1 if it is not found. Operations that return a value deliver it through a pointer parameter; this leaves the return value free to report whether the operation succeeded.

The name and parameters of a function are not enough by themselves. What should the call list_insert(L, 7, x) do on a list of length 3? The answers to such questions are the precondition and the postcondition written for every operation. The precondition is the state that must be true before the operation is called. The postcondition is the state that is guaranteed to be true at the end of the operation if the precondition was met. Together they form the contract of the operation. The contract for list_insert is this:

  • Precondition: 0 ≤ i ≤ n. i = n means inserting at the end; the upper bound is therefore n, not n − 1.
  • Postcondition: x is at position i, the length has become n + 1, and the old elements ai, …, an−1 have each moved one position to the right. That is, the old ak is now at position k + 1. The elements before i stay in place.

For list_delete the precondition is 0 ≤ i < n; deleting from an empty list is therefore invalid for every i. In the postcondition the length decreases by one and the elements after i move one place to the left. The comments // 0<=i<=n and // 0<=i<n in the code fragment are a short way of writing these preconditions.

What happens when a precondition is violated is also part of the contract. In this interface the function returns false without changing anything. Another design may leave the precondition to the caller's responsibility and perform no check. This is faster, but a wrong call leads to undefined behavior. Whichever way is chosen, it must be documented. Without a written contract, one cannot even discuss whether a function works correctly.

9.1.2Opaque type: separating the interface from the implementation

The first line in the interface, typedef struct list List;, declares only the name of the structure, not its fields. After such a declaration, struct list is an incomplete type: the compiler recognizes its name but does not know its size. A variable cannot be defined of an incomplete type, but a pointer to it can. All pointers have the same size, and this is the only thing the compiler needs to know. All the functions in the interface therefore take List *, not List.

The fields of the structure are written only in the file list.c, which contains the implementation. A program that uses the header file cannot write an expression like L->n, because it does not know that a field called n exists. It can touch the list only through the functions in the interface. A type whose inside cannot be seen from outside is called an opaque type. FILE in the standard library is a familiar example: programs work with FILE * but do not use the fields of the structure.

The following program uses the list only through the interface. It first inserts five values at the front and then deletes the element at position 2:

#include <stdio.h>
#include "list.h"                       // interface only

int main(void) {
    List *L = list_create();
    int x, k;
    if (L == NULL) return 1;
    for (k = 1; k <= 5; k++)
        list_insert(L, 0, 10 * k);      // always at front: 50 40 30 20 10
    list_delete(L, 2, &x);              // removes 30
    printf("%d %d %d\n", list_length(L), x, list_find(L, 20));
    list_destroy(L);
    return 0;
}

Because every insertion is at the front, after the loop the list is (50, 40, 30, 20, 10). list_delete(L, 2, &x) removes 30 and the list becomes (50, 40, 20, 10). The position of 20 is now 2. The program prints 4 30 2. This program was compiled and run with two separate list.c files, one using an array and the other a linked list; both implementations appear in these notes. In both cases the output is the same and not a single line of main has changed. This is the gain of the opaque type. When the implementation changes, only list.c is recompiled; the hundreds of files that use the list stay as they are.

Common mistake

Writing List L; or malloc(sizeof(List)) in the using file. List is an incomplete type in that file and the compiler does not know its size; both lines give a compile error. Only list_create, which knows the size, can allocate the list. This rule is not a restriction but the very purpose of the opaque type.

9.2Implementation with an array

The most direct way to implement the list ADT is to keep the elements in order in an array. ai is written into the i-th cell of the array. This layout is called sequential allocation: the logical order and the order in memory are the same.

9.2.1Sequential layout and deletion

The first implementation in the slides uses a fixed-size array and an item counter:

#define CAPACITY 100
typedef struct {
    int a[CAPACITY];
    int n;                  // item count
} ArrayList;

bool array_delete(ArrayList *L, int i, int *x) {
    int k;
    if (i < 0 || i >= L->n) return false;
    *x = L->a[i];
    for (k = i; k < L->n - 1; k++)
        L->a[k] = L->a[k + 1];      // shift left
    L->n--;
    return true;
}

ArrayList has two fields. a is the array that can hold at most CAPACITY elements; n records how many cells are currently filled. The filled cells are always those from a[0] to a[n-1]; no gap is left between them. This rule is the invariant of the structure and must be preserved at the end of every operation. Since int is 4 bytes, the structure occupies 404 bytes. This size does not change whether the list holds one element or a hundred.

array_delete first checks the precondition. If i is not a valid position, it returns false without touching anything. If it is valid, it copies the value to be deleted into *x. Then it moves every element after i one place to the left: a[i] = a[i+1], a[i+1] = a[i+2], and so on up to a[n-2] = a[n-1]. This is why the loop condition is k < L->n - 1; if k reached n − 1, a[n] would be read, and there is no valid element in that cell. At the end n decreases by one. The old value stays in the last cell, but because it is now outside n, it is not considered part of the list.

Access to a[i] is a single address computation: i · sizeof(int) is added to the start address of the array. This computation is independent of the size of i; list_get is therefore O(1). In deletion, the number of elements moved is n − 1 − i. For i = n − 1, that is, deleting from the end, no move is needed and the cost is O(1). For i = 0, that is, deleting from the front, n − 1 moves are made and the cost is Θ(n). If all positions are equally likely to be deleted, the average number of moves is (n − 1)/2; the average case is also Θ(n).

9.2.2Code trace: array_insert(&L, 1, 9)

Insertion is like the mirror image of deletion. Where deletion closes the gap, insertion first makes room:

bool array_insert(ArrayList *L, int i, int x) {
    int k;
    if (L->n == CAPACITY || i < 0 || i > L->n)
        return false;          // full/invalid
    for (k = L->n; k > i; k--)
        L->a[k] = L->a[k - 1];     // shift right
    L->a[i] = x;
    L->n++;
    return true;
}

The function rejects in three cases: if the array is full, if i is negative, or if i > n. The || operator is evaluated from left to right with short-circuiting; at the first true condition the others are not looked at. Then the loop starts at k = n and moves backward. In each round it moves a[k-1] to a[k]. The loop stops when k == i. At this moment the old value of a[i] has been copied to a[i+1] and the cell is ready to receive the new value.

The direction of the move is critical. If the loop went from left to right, starting at k = i, the assignment a[i+1] = a[i] would destroy the old value of a[i+1]. In the next round, the value read from that cell would already be a copy of a[i], and the whole right side would be filled with the same value. In a right-to-left move, every cell is copied to the right before it is overwritten.

The number of shifts is n − i. Insertion at the end (i = n) makes no shifts; insertion at the front (i = 0) shifts all n elements. The worst case is therefore Θ(n). An experiment that inserts at the front of an empty array a hundred times confirms this: the total number of shifts came out as 0 + 1 + … + 99 = 4950. That is, n insertions at the front amount to n(n − 1)/2 shifts in total, Θ(n2) work. The hundred-and-first insertion into the full array returns false.

9.2.3Capacity and doubling

The fixed array has two drawbacks. The capacity is chosen at compile time and cannot be exceeded. If the chosen capacity is large, short lists also hold the same large space for nothing. The solution is to allocate the array in heap memory and grow it with realloc when needed. Such an array is called a dynamic array. The real question is by how much to grow it.

If the array is grown by one cell every time it fills up, every insertion calls realloc. If realloc cannot grow the block in place, it allocates a new block and copies all the old elements there. The number of elements copied over n insertions is, in the worst case, 1 + 2 + … + (n − 1), that is, Θ(n2). If the capacity is doubled each time, the picture changes. The list.c below implements the interface with this method. The capacity starts at 4 and doubles every time the array fills up:

// list.c: struct list is defined only here (opaque type)
struct list {
    int *a;                             // array on the heap
    int n, cap;                         // item count, capacity
};

List *list_create(void) {
    List *L = malloc(sizeof *L);
    if (L == NULL) return NULL;
    L->n = 0;
    L->cap = 4;
    L->a = malloc(L->cap * sizeof *L->a);
    if (L->a == NULL) { free(L); return NULL; }
    return L;
}

void list_destroy(List *L) {
    if (L) { free(L->a); free(L); }
}

int list_length(const List *L) { return L->n; }

bool list_get(const List *L, int i, int *x) {
    if (i < 0 || i >= L->n) return false;
    *x = L->a[i];
    return true;
}

bool list_insert(List *L, int i, int x) {
    int k;
    if (i < 0 || i > L->n) return false;
    if (L->n == L->cap) {               // full: double it
        int *bigger = realloc(L->a, 2 * L->cap * sizeof *L->a);
        if (bigger == NULL) return false; // old array stays intact
        L->a = bigger;
        L->cap *= 2;
    }
    for (k = L->n; k > i; k--)
        L->a[k] = L->a[k - 1];
    L->a[i] = x;
    L->n++;
    return true;
}

bool list_delete(List *L, int i, int *x) {
    int k;
    if (i < 0 || i >= L->n) return false;
    *x = L->a[i];
    for (k = i; k < L->n - 1; k++)
        L->a[k] = L->a[k + 1];
    L->n--;
    return true;
}

int list_find(const List *L, int x) {
    for (int k = 0; k < L->n; k++)
        if (L->a[k] == x) return k;
    return -1;
}

The structure now holds not the array itself but the address of an array on the heap. list_create allocates two separate blocks: one for the structure and one for the array. If the second allocation fails, the first is also returned; otherwise the structure would leak. list_destroy releases the blocks in reverse order. First the array and then the structure are returned, because the address of the array is inside the structure.

The realloc call in list_insert first puts its result into a separate variable. Had L->a = realloc(L->a, …) been written and memory run out, realloc would return NULL but would not release the old block. The moment NULL is written into L->a, the address of the old block is lost and the whole list leaks. The variable bigger keeps the old array safe in this case; the function returns false and the list stays intact.

When the example program above was run with this implementation, a single realloc call was seen at the fifth insertion: the capacity went from 4 to 8, and the block from 16 bytes to 32 bytes. The program made two malloc and two free calls; there is no leak.

Theorem 9.1 (Amortized cost of doubling)

Let n insertions at the end be made into a dynamic array that starts with capacity c0 ≥ 1 and doubles every time it fills up. The total number of elements copied during the growth steps is less than 2n. Hence the amortized cost of insertion at the end is O(1).

Proof. Growth happens when a new insertion arrives while the item count equals the capacity, and at that moment all the elements are copied. The capacities go c0, 2c0, 4c0, …. Suppose the last growth was made at capacity c02k; this growth copies c02k elements, and at that moment the array holds that many elements. Hence c02k < n. The total number of copies is a geometric sum: c0(1 + 2 + … + 2k) = c0(2k+1 − 1) < 2 · c02k < 2n. If there was no growth at all, the total is zero. The n insertions themselves make n writes. Together with the copies, the total work is less than 3n and the share per insertion is constant. ∎

Amortized cost is the total cost of a sequence of operations divided by the number of operations. Not every single insertion is cheap. The insertion that coincides with a growth takes Θ(n); but such insertions are so rare that the total work stays linear. The growth factor may be another constant, such as 1.5 instead of 2; the proof stays the same, only the constant changes. Adding a fixed amount (for example 10 cells each time), however, is not enough. In that case the number of growth steps is n/10 and the total number of copies is again Θ(n2).

Common mistake

Reading amortized O(1) as "every insertion is O(1)". In a real-time system, where even a single insertion taking long is unacceptable, the worst case matters, not the average. Then a linked list or a preallocated array is chosen instead of a dynamic array. Moreover, this theorem describes only insertion at the end. Insertion at the front remains Θ(n) because of shifting, even without growth.

9.3Linked implementation

In the linked implementation each element sits in a separate node, and each node carries the address of the next one. Insertion and deletion no longer move elements; they only change links. The node used in this section is the classic singly linked list node, made of an integer value and a link.

9.3.1Insertion with a pointer to a pointer

typedef struct node *node_pointer;
struct node { int data; node_pointer link; };
typedef struct { node_pointer head; int n; } LinkedList;

bool ll_insert(LinkedList *L, int i, int x) {
    node_pointer *pp = &L->head, new_node;
    if (i < 0 || i > L->n) return false;
    while (i-- > 0)
        pp = &(*pp)->link;       // walk to link i
    new_node = malloc(sizeof *new_node);
    if (new_node == NULL) return false;
    new_node->data = x;
    new_node->link = *pp;
    *pp = new_node;              // head or middle: same
    L->n++;
    return true;
}

The LinkedList structure holds the head of the list and its length together. Because the length is stored in a separate field, list_length does not have to count the list and answers in O(1). The price is that n must be updated in every insertion and deletion.

To insert at position i in a singly linked list, the link that will point to the new node has to be changed. If i = 0, the link to change is the head of the list, that is, L->head. If i > 0, the link to change is the link field of the (i − 1)-th node. In the classical formulation these two cases are handled separately: one branch is written for insertion at the head and another, which finds the previous node, for insertion in the middle.

ll_insert combines the two cases with a single idea. It holds not the link to be changed but the address of that link. node_pointer *pp is a variable that holds the address of a node pointer; it is therefore called a pointer to pointer. Initially pp = &L->head. In each round of the loop, pp = &(*pp)->link moves to the address of the next link. This expression is read from the inside out: *pp is the value of the current link, that is, the address of a node; (*pp)->link is the link field of that node, and &(*pp)->link is the address of this field. After i rounds, pp holds the address of the link that points to the node at position i.

The linking takes two lines. new_node->link = *pp links the new node to the node that currently stands at that position. *pp = new_node turns that link to the new node. If pp points to &L->head, the head of the list changes; if it points to the link field of a node, that node's link changes. The code does not distinguish the two cases, because both are "changing the value of a pointer". The order of the lines matters. Had *pp = new_node been written first, new_node->link = *pp would link the new node to itself and the rest of the list would be lost.

Because the function does not use i afterward, this value causes no problem. The cost has two parts. Walking to the position is i rounds, that is, O(i). Linking is a constant number of assignments, that is, O(1). The total is O(i): insertion at the head is O(1) and insertion at the end is O(n). In the array the opposite held. In a linked list no element moves and there is no capacity limit; the list grows as long as malloc provides memory. In the experiment, 7, 4, and 2 were inserted at positions 0, 0, and 2 in turn, and the list became 4 → 7 → 2. Then ll_insert(&B, 1, 9) gave 4 → 9 → 7 → 2, and invalid positions (6 and −1) were rejected with false. A single node is 16 bytes: a 4-byte int, 4 bytes of alignment padding, and an 8-byte pointer.

9.3.2The same interface, another implementation

To see the power of the opaque type, a linked implementation of the same interface can be written. The structure changes only inside list.c:

// linked version of list.c: list.h and the using code do not change
typedef struct node *node_pointer;
struct node { int data; node_pointer link; };
struct list { node_pointer head; int n; };

List *list_create(void) {
    List *L = malloc(sizeof *L);
    if (L) { L->head = NULL; L->n = 0; }
    return L;
}

void list_destroy(List *L) {
    node_pointer p, q;
    if (L == NULL) return;
    for (p = L->head; p; p = q) { q = p->link; free(p); }
    free(L);
}

int list_length(const List *L) { return L->n; }

static node_pointer *link_address(List *L, int i) {
    node_pointer *pp = &L->head;           // address of link i
    while (i-- > 0) pp = &(*pp)->link;
    return pp;
}

bool list_get(const List *L, int i, int *x) {
    node_pointer p = L->head;
    if (i < 0 || i >= L->n) return false;
    while (i-- > 0) p = p->link;
    *x = p->data;
    return true;
}

bool list_insert(List *L, int i, int x) {
    node_pointer *pp, new_node;
    if (i < 0 || i > L->n) return false;
    pp = link_address(L, i);
    new_node = malloc(sizeof *new_node);
    if (new_node == NULL) return false;
    new_node->data = x;
    new_node->link = *pp;
    *pp = new_node;
    L->n++;
    return true;
}

bool list_delete(List *L, int i, int *x) {
    node_pointer *pp, victim;
    if (i < 0 || i >= L->n) return false;
    pp = link_address(L, i);
    victim = *pp;
    *x = victim->data;
    *pp = victim->link;                 // skip the node
    free(victim);
    L->n--;
    return true;
}

int list_find(const List *L, int x) {
    int k = 0;
    for (node_pointer p = L->head; p; p = p->link, k++)
        if (p->data == x) return k;
    return -1;
}

The helper function link_address is the very walk in ll_insert. Because it is static, it is visible only from this file and is not part of the interface. list_delete uses the same walk for deletion. *pp = victim->link skips the node to be deleted, and then the node is returned. Deleting from the head and deleting from the middle are the same three lines. While walking over the nodes, list_destroy saves the address of the next one into q before free. Reading the link field of a node that has been freed is undefined behavior.

The example program was also compiled with this file and gave the same output, 4 30 2. This time six malloc calls were made: five for nodes and one for the structure itself. All were returned with six free calls. For the using code, the only visible difference between the two implementations is speed.

9.3.3Array or linked list?

The question of which of the two implementations is better has no single answer. The answer depends on which operations the program performs often. Table 9.3 gives the comparison from the slides.

Table 9.3: Comparison of the sequential (array) and linked implementations.

The asterisk in the table reminds us that insertion at the end of a dynamic array is amortized O(1). The row "insertion at a known position" carries a subtle difference. In an array, even if the position is known, insertion is O(n) because of shifting. In a linked list, if the node before the insertion point is at hand, two links change and the job is done. If one has to walk from the head to reach this node, the cost is again O(i).

Binary search relies on being able to reach the middle element in O(1). In a linked list, even going to the middle takes O(n), so binary search on a sorted linked list gains nothing; it takes as long as linear search.

The last two rows describe differences that asymptotic notation does not capture. In terms of memory, an array holds only the data for each element, but the unfilled part of the capacity is wasted. A linked list holds no empty cells, but each node carries a pointer. In a list of int this means a 16-byte node for 4 bytes of data. In terms of the processor the difference is even larger. The processor brings memory into the cache not byte by byte but in blocks of 64 bytes. When a cell of an array is read, its neighbors come along as well, and subsequent accesses are very fast. The nodes of a linked list may be scattered in memory; every p = p->link may require a new block to be fetched. The same O(n) traversal can be several times faster on an array than on a linked list.

The rule summarized in the slides is this: if frequent access or binary search is needed, use an array; if frequent insertion and deletion in the middle is done, or if the size cannot be predicted in advance, use a linked list. An opaque interface also makes it possible to postpone this decision. The program is first written with one implementation and measured; if necessary, only list.c is changed.

9.4Generalized lists

In a linear list each element is a single value: a number, a letter, or a record. Much data, however, is nested. In a file system, a directory contains subdirectories; in a menu, submenus; in a mathematical expression, parenthesized subexpressions. To hold such data naturally, it is enough to allow the elements of a list to be lists as well.

9.4.1Definition, head, and tail

Definition 9.2

Let A = (α0, α1, …, αn−1) be a finite sequence of elements. Each αi is either an atom (a single indivisible value) or itself a list of this form. Such an A is called a generalized list. The elements that are lists are called the sublists of A. A is the name of the list and n is its length. If n ≥ 1, then α0 is the head of the list and (α1, …, αn−1) is its tail.

The definition refers to itself: a generalized list is a list whose elements can be generalized lists. Definitions of this kind are called recursive definitions. It is therefore natural that the routines that process such a structure are recursive too. A linear list is a special generalized list all of whose elements are atoms.

Attention must be paid to the asymmetry between head and tail. The head is an element; it can be an atom or a list. The tail is always a list, if necessary the empty list. The head of the list (a) is the atom a and its tail is (). These two operations are the foundation of the LISP language designed by John McCarthy in 1958. In LISP the head is called car and the tail cdr. LISP programs are also written in the same way, as nested lists: the expression (+ 1 (* 2 3)) is both a program and a generalized list of three elements.

Table 9.4: Examples of generalized lists.
ListLengthDescription
D = ()0empty list
A = (a, (b, c))2the first element is an atom and the second is the sublist (b, c); head(A) = a, tail(A) = ((b, c))
B = (A, A, ())3shared sublist: the first two elements are the same A; the third is the empty list
C = (a, C)2recursive list: it contains itself, C = (a, (a, (a, …)))

Every row in the table carries its own lesson. The length of A is 2, not 3. The length counts only the elements at the top level; (b, c) is a single element. The tail of A is ((b, c)), not (b, c). The tail is the remaining list after the head is removed, and this list has a single element; that single element is the list (b, c).

Two of the three elements of B are the same list A. This does not mean two copies of A. There is a single A in memory, and two elements of B point to it. Such lists are called shared lists. The third element of B is the empty list. The empty list is also a list; it increases the length of B by one.

C contains itself as an element. If one tries to expand it on paper, it goes on forever as (a, (a, (a, …))). In memory, however, it is a finite structure: the second element points to the head of the list itself. Such lists are called recursive lists. Sharing and recursion are the power of generalized lists; but most of the routines written in these notes are correct for lists that contain neither. The limits are stated separately next to each routine.

9.4.2Example: a multivariate polynomial

A single-variable polynomial is easily held in a linked list in which each node carries a coefficient and an exponent. With polynomials that contain several variables, the job gets harder. A fixed structure that holds the exponent of every variable in each term grows as the number of variables grows, and most of its fields stay empty. A generalized list instead groups the polynomial in nested levels.

The example in the slides is the following polynomial:

P(x, y, z) = x10y3z2 + 2x8y3z2 + 3x8y2z2 + x4y4z + 6x3y4z + 2yz

The polynomial is first grouped by powers of z. There are three terms containing z2 and three terms containing z:

P = (x10y3 + 2x8y3 + 3x8y2) z2 + (x4y4 + 6x3y4 + 2y) z

The coefficients inside the parentheses are now polynomials in x and y only. These are grouped in turn by y:

P = ((x10 + 2x8) y3 + 3x8 y2) z2 + ((x4 + 6x3) y4 + 2y) z

The innermost coefficients contain only x and are ordinary polynomials with numeric coefficients. Every level has the same form: a variable and coefficients multiplied by powers of that variable. A coefficient is either an integer or a polynomial of a lower level. This fits the definition of the generalized list exactly. The slides hold each element with the following structure:

typedef enum { VAR, PTR, NO } tag_t;
typedef struct pnode *poly_pointer;
struct pnode {
    tag_t tag;              // three kinds
    union {
        char var;           // VAR: variable name
        poly_pointer dlink; // PTR: coef is a list
        int coef;           // NO : integer coef
    };
    int exp;                // exponent
    poly_pointer link;
};

The tag field says what kind of element this is and takes three values. A VAR element is the first element of a level and carries the variable name of that level in var; its exponent is 0 and unused. A PTR element is a term whose coefficient is a sublist; dlink points to that sublist. A NO element is also a term, but its coefficient is an integer held in coef. In both term kinds, exp is the exponent of the variable of the level. link points to the next element on the same level.

The three pieces of information are never needed at the same time: an element carries either a variable name, or a sublist, or an integer. The three fields are therefore put into a union. All the fields of a union start at the same memory address; the size of the union is that of the largest field. Which field is valid is known from tag. This arrangement, in which a union is used together with a field that indicates its kind, is called a tagged union. If the tag is read wrongly, for example if the dlink field of a NO element is followed, an integer is mistaken for an address and the program crashes. Checking the tag before every access is the programmer's responsibility.

Figure 9.2 shows the memory layout of two examples. The upper drawing is 3x2y. This term reads as (3x2) · y1. The outer level is the level of y and has a single term: a PTR element with exponent 1 whose coefficient is a sublist. The sublist is the level of x, and its only term is a NO element with coefficient 3 and exponent 2.

In the lower drawing the z level has three elements: VAR z and two PTRs. The first PTR has exponent 2 and its coefficient is the polynomial (x10 + 2x8) y3 + 3x8 y2. The list of this polynomial starts with VAR y and contains two PTRs with exponents 3 and 2. To save space, the drawing shows only the first term of the y-lists and shows the x-polynomials abbreviated. The coefficient of the term 2y in the second y-list is just the number 2; this term needs no sublist and a NO element suffices. The whole structure is thus 17 elements: 3 at the z level, 3 in each of the two y lists, and 8 in total in the three x lists. On x86-64 each element is 32 bytes: after each of the four-byte tag and exp fields, four bytes of padding remain to align the 8-byte pointers.

The routine that computes the value of such a structure is as orderly as the structure itself. At each level, the coefficient is either read directly or computed recursively as the value of the sublist; then it is multiplied by the power of the variable and added up:

// P: list starting with a VAR element; d['x'-'x'], d['y'-'x'], d['z'-'x']: variable values
long poly_value(poly_pointer P, const long d[]) {
    long sum = 0, v = d[P->var - 'x'];  // value of this level's variable
    long coef, pw;
    int k;
    for (poly_pointer p = P->link; p; p = p->link) {
        coef = (p->tag == PTR) ? poly_value(p->dlink, d)   // coef is a list
                               : p->coef;               // NO: integer
        for (pw = 1, k = 0; k < p->exp; k++) pw *= v;
        sum += coef * pw;
    }
    return sum;
}

The function reads the name of the variable from the VAR element and takes its value from the array d; 'x' is in cell 0, 'y' in cell 1, and 'z' in cell 2. Then it walks over the terms along link. In a PTR term the coefficient is the value of the sublist at the same point. For example, for x = 2, y = 3, z = 1, the outermost level adds up the z2 and z terms; because z = 1, the result is the sum of the values of the two y-polynomials. The first y-polynomial gives (210 + 2 · 28) · 27 + 3 · 28 · 9 = 1536 · 27 + 6912 = 48384 and the second (16 + 48) · 81 + 2 · 3 = 5190. The total is 53574. This value is the same as that of the expanded polynomial. The list was also compared with the explicit formula at all 343 points in the range −3 ≤ x, y, z ≤ 3, and no difference was found.

This representation is not the only option. The same polynomial can be stored by choosing a different variable order (grouping by x first), or with a flat list that holds each term with an exponent vector. What matters is that conversion routines can also be written for the chosen representation: from text to structure, from structure to text, from one representation to another. A representation counts as a solution only together with these routines.

9.4.3Element structure and memory layout

The polynomial example uses three kinds of elements. In a general-purpose generalized list, two kinds are enough: atom and sublist. All the routines in the rest of these notes use the following structure:

typedef enum { FALSE, TRUE } boolean;
typedef struct list_node *list_pointer;
struct list_node {
    boolean tag;          // FALSE: atom
    union {
        char data;        // atom value
        list_pointer dlink; // sublist head
    };
    list_pointer link;    // next on this level
};

The tag field is the tag. If it is FALSE, the element is an atom and its value is in data. If it is TRUE, the element is a sublist and dlink points to the first element of the sublist. In both cases link points to the next element on the same level. In short, an element has the form [tag | data/dlink | link]. In the drawings an atom element is marked with the letter F and a sublist element with the letter T.

Because the structure refers to itself, the pointer type list_pointer is named first; struct list_node is still an incomplete type at that moment, but defining a pointer to it is allowed. The type boolean is a two-valued enumeration (enum) defined by the slides themselves: FALSE takes the value 0 and TRUE the value 1. It must not be confused with bool from <stdbool.h>, available since C99. The two can be used side by side in the same program, because their names differ: true is lowercase and TRUE is uppercase.

The union has not been given a name. An anonymous union entered the standard with C11, and its fields are accessed directly as L->data and L->dlink. With a C99 compiler the union must be given a name, for example u; the access is then written L->u.data and L->u.dlink. All the code in these notes compiled without warnings with -std=c11.

The union lets the atom value and the sublist pointer share one field. A char is 1 byte and a pointer is 8 bytes, and the union takes 8 bytes. The tag is 4 bytes, the union 8, and the link 8; because pointers must sit at addresses that are multiples of 8, 4 bytes of padding remain after the tag. On x86-64, sizeof(struct list_node) is 24 bytes. Without the union, that is, if data and dlink were separate fields, the element would still be 24 bytes here, because the one-byte atom would fit into the padding after the tag; the union pays off only for larger atoms, such as a double (32 bytes without it).

Figure 9.3 shows these three lists in memory. A has two elements: the atom a and a T element. The arrow from the middle cell of the T element descends to the first element of the sublist (b, c). b and c are on the same row, linked to each other by link. Elements on the same level are always followed along one row; descending into a sublist means going one row down. This drawing convention makes it much easier to read nested structures.

B has three T elements. The arrows of the first two go to the same place, the first element of A. In the middle cell of the third there is a slash, that is, NULL: this element is an empty sublist. The difference between the empty list and "no element" shows here. The element () is an existing T element and increases the length of B by one; only the list it points to is empty. In C the arrow of the second element turns back and reaches the first element of the list. Any traversal that follows this arrow goes around forever between the same two elements.

Common mistake

Reading a field of the union without checking the tag. Writing if (L->dlink) may come out true for an atom element too: the character 'a' written into the data field makes the first byte of the union 97, and the 8-byte value containing this byte is nonzero. L->tag must be examined first, and only the field of the union that is valid must be read.

9.4.4Why generalized lists?

Three benefits of the generalized list stand out. The first is space. The whole structure of a tree, for example A(B(E(K, L), F), C(G), D(H(M), I, J)), can be written as a one-line text. This text carries all the information needed to rebuild the structure. A picture of the tree can be stored, or its image in memory can be dumped to disk as it is. Both work, but both take much more space than the text. The text is a kind of compression. A computer engineer should see this difference even when storing so small a piece of data.

The second is naturalness. Directories in a file system, drop-down menus, the nested elements of XML and JSON documents, and LISP expressions are hierarchical to begin with. The array [1, [2, 3], []] in a JSON document is itself the generalized list (1, (2, 3), ()).

The third concerns algorithms. When data is moved to a well-known structure, all the routines written for that structure become usable. This idea is common in engineering. In signal processing, a signal is moved to another space by a Fourier or Z transform, the processing is done there, and the result is converted back. Here too, data such as a tree is moved into a list; list routines such as copying, comparison, traversal, and printing are then ready.

9.4.5Building a list from its linear form

Building a generalized list by hand, allocating it element by element with malloc, is both long and error-prone. A text such as (a, (b, c)) is called the linear form of the list. A routine that reads the linear form and builds the list both lets programs take their data from outside and makes it easier to try out routines. All the example lists followed in these notes were built with this routine. The routine uses the following helper, which allocates an element for each item:

list_pointer get_node(void) {
    list_pointer p = malloc(sizeof *p);
    if (p == NULL) {                    // out of memory
        fprintf(stderr, "get_node: out of memory\n");
        exit(EXIT_FAILURE);
    }
    return p;                           // fields not initialized
}

get_node is a wrapper around malloc(sizeof *p) with a NULL check. The notation sizeof *p gives the size of the type that p points to; it leaves no need to write the type name again. If no memory is left, the program stops with an error message. This is a crude but honest choice: instead of doing a NULL check in each routine, the error is handled in one place. The fields of the returned element are not initialized; the caller must fill in every field.

The text is read character by character. The grammar is simple: a list begins with (, its elements are separated by commas, and it ends with ). Each element is either a single letter (an atom) or again a list. Because the grammar is recursive, the reader is recursive too:

// called while *s points at '('; once the list is built,
// *s points just after the matching ')'.
list_pointer parse(const char **s) {
    list_pointer head = NULL, *tail = &head, q;
    (*s)++;                             // skip '('
    while (**s != ')') {
        q = get_node();
        if (**s == '(') {               // sublist
            q->tag = TRUE;
            q->dlink = parse(s);
        } else {                        // atom
            q->tag = FALSE;
            q->data = **s;
            (*s)++;
        }
        q->link = NULL;
        *tail = q;                      // append at the end
        tail = &q->link;
        if (**s == ',') (*s)++;         // skip the separator
    }
    (*s)++;                             // skip ')'
    return head;
}

The function takes the position in the text as const char **s. The address of the position is passed because, after a sublist has been read, the caller must continue reading from where the sublist ended. The inner call advances *s, and this advance is visible from outside as well. This is another use of the pointer-to-pointer idea in ll_insert.

The loop runs until ) is seen. In each round an element is allocated. If the next character is (, the element is a sublist and its dlink field is filled with the list built by the recursive call. Otherwise the character is an atom. The element is appended at the end. For this, the variable tail holds the address of the link field of the last element, or the address of head in an empty list. *tail = q fills head at the first element and the link of the previous element at later ones. Again two cases come down to one line. If a comma follows the element, it is skipped. On leaving the loop, the closing parenthesis is skipped and the list is returned.

The reader does not check for malformed text. An unclosed parenthesis leads to reading past the '\0' character. In a real program, every character should be checked against the expected one, and on an error the elements allocated so far should be released. Throughout these notes the reader was used only with correct texts. It was also tried together with the routine print_linear, which converts a list back to text, on 20,000 random texts: every text, read and written back, gave the same text.

Example 9.2

Let "(a,(b,c))" be read. The outer call skips ( and sees a: an atom element is built, head is linked to it, and the comma is skipped. The next character is (. A new element is allocated, tag = TRUE is set, and the inner call begins. The inner call builds the atoms b and c, stops on seeing ), skips this parenthesis, and returns the first element of (b, c). The outer call writes this address into the dlink of the T element and links the element behind a. Next comes the ) of the outer list, and the outer loop ends too. 9.5Basic recursive routines

Most routines that work on a generalized list follow the same skeleton. When an element is reached, its kind is examined first. If the element is an atom, it is processed: copied, compared, or printed. If the element is a sublist, the same routine is called for that sublist. Then, with link, the routine moves on to the next element on the same level; this step is done either with a loop or, again, with a recursive call. In short: if an atom, process it; if a sublist, descend; then continue. The four routines in this section are four different uses of this pattern.

The way to write and read a recursive routine is to look at each call as a small contract. The contract has the form "if this call is given this list, it returns this". While writing the routine, the inner calls are assumed to obey this contract, and only the work of this call itself is considered. This assumption is the programming counterpart of mathematical induction. If the base case (the empty list) is handled correctly and every call is made with a smaller list, the routine is correct for all finite lists.

9.5.1Copying

The first question in the slides asks for a routine that makes a copy of a list that has no sharing and no recursion. The copy must be a list of the same structure but made entirely of new elements: a change made in the copy must not affect the original list.

list_pointer copy(list_pointer L) {
    list_pointer q = NULL;
    if (L) {                    // L not NULL?
        q = get_node();         // get a node
        q->tag = L->tag;
        if (!L->tag) q->data = L->data; // atom
        else q->dlink = copy(L->dlink);
        q->link = copy(L->link);
    }
    return q;
}

The contract of the routine is this: copy(L) returns the first element of an independent copy of the list that L points to, that is, of the element L and all the elements reachable from it by link. For the empty list it returns NULL.

In the first line, q is initialized with NULL. If L is empty, the if block is skipped and this NULL is returned: the copy of the empty list is the empty list. That is the base case. If L is not empty, a new element is obtained with get_node and the tag is copied. In an atom element the value is copied as it is. In a sublist element, however, dlink is not copied; had it been copied, the new element would point to the old sublist and the copy and the original list would share the same sublist. Instead, a copy of the sublist itself is requested and the new element points to it. The last line copies the rest of the list, that is, the list starting at L->link, and links the new element to this copy.

The routine has two recursive calls, and both are made with a smaller list. The sublist in L->dlink and the remaining list starting at L->link contain only some of the elements of L. The calls therefore reach the empty list in the end and stop. This reasoning rests on the assumption that the list contains no recursion. In a list such as C = (a, C), the sublist is the list itself and does not shrink.

At the moment a new element is allocated, its fields hold garbage values. The code always fills every field: tag at once, data or dlink according to the kind, and link last. A value can be written into the link field only when the copy of the rest of the list is complete. Elements are allocated from front to back, while links are updated from back to front. This order is seen in all the recursive routines in this section. A student who finds recursive thinking hard may propose doing the same job with a queue. It can be done, but the code gets longer and extra bookkeeping is needed to link the copies of the sublists to the right place. The recursive version translates the definition of the structure directly into code.

The most important observation of the trace is that the call stack goes at most five calls deep. The path is this: from a to (b, c) by link, from there to b by dlink, from there to c again by link, and then the empty list arrives. The depth of the stack depends not only on nesting but also on the number of elements on the same level, because moving along link is also a call. This detail matters for long lists.

By counting these calls we find the cost of the routine. For (a, (b, c)), copy is called six times: once for each of the four elements and twice for NULL. This number is no coincidence.

Theorem 9.2 (Number of calls)

Let a generalized list with no sharing and no recursion contain n elements in total, of which s are sublist elements. copy is called exactly 1 + n + s times for this list. Of the calls, n are made with an element and 1 + s with NULL. The running time of the routine is therefore Θ(n).

Proof. Every element becomes the parameter of a call exactly once. The first element of the top level comes in through the call from outside; the other elements come through the call copy(L->link) of the element before them, or through the call copy(L->dlink) of the T element that owns the sublist they are in. Because there is no sharing, no element is reached by two routes. Every call made with an element makes one call for link; T elements also make one call for dlink. So in addition to the call from outside, n + s more calls arise, and the total is 1 + n + s. Since n of them go to elements, the remaining 1 + s calls were made with NULL. Every call does a constant amount of work apart from its inner calls. Since s ≤ n, the total work is Θ(n). ∎

The theorem was also confirmed by an experiment. With a copy instrumented with a counter, 8 calls were counted for (a, (b, (c))) (n = 5, s = 2), 12 for ((a, b), ((c, d), e)) (n = 8, s = 3), and 1 for the empty list. Copying also calls malloc n times and allocates Θ(n) memory for the copy itself. The extra memory needed for the stack is the length of the deepest call chain.

9.5.3The limits of copying and freeing a list

The test list suggested by the slides is L = ((a, b), ((c, d), e)). This list has three levels, its first element is not an atom, and the first element of a sublist is itself a sublist. It therefore catches bugs that do not show up in simple examples. Figure 9.5 shows the memory layout of the list. The experiment showed that 8 malloc calls are made for this list, that the copy equals the original list, and that no element is common to the two lists.

The routine has two limits. The first is sharing. When B = (A, A, ()) is copied, copy does not know that the first two elements of B point to the same list. A separate call copy(L->dlink) is made for every T element, and A is copied twice. With A = (a, (b, c)), the experiment counted 11 malloc calls: three elements for B and 4 each for the two copies of A. The value of the copy equals the original list, but its structure is different. In the original list the first two elements point to the same list, whereas in the copy they point to two separate lists. A change made to the first copy of A in the copy is not reflected in the second. The sharing has been lost. A copy that preserves sharing keeps the sublists already copied in a table; such a version is among the exercise solutions.

The second limit is recursion. For C = (a, C), copy(C) first copies a, then asks for the copy of the sublist for the second element. The sublist is C itself; the same call starts over from the beginning. The calls never end. Because every call occupies space on the stack, after a while the call stack overflows and the operating system stops the program. This situation is called stack overflow. In an experiment on Windows, the program terminated with the code 0xC00000FD (STATUS_STACK_OVERFLOW).

A copied list must be freed when its job is done. The routine that frees a list with no sharing and no recursion is the reverse of copying:

// Frees all elements of a list with no sharing and no recursion.
void free_list(list_pointer L) {
    list_pointer q;
    while (L) {
        if (L->tag)
            free_list(L->dlink);        // sublist first
        q = L;
        L = L->link;                    // link is read before free
        free(q);
    }
}

The routine walks the same level with a loop; it calls itself only for sublists. At every element the sublist is freed first. The address of the next element is read before free; the link field of a freed element can no longer be read. All the experiments in these notes were cleaned up with this routine, and the absence of leaks was checked with counting wrappers for malloc and free. In the main verification program, 216,150 malloc calls and the same number of free calls were counted.

Common mistake

Freeing a shared list with free_list. When B = (A, A, ()) is freed, A is first released for the first T element. The second T element hands the same addresses to free once more. Releasing the same block twice is undefined behavior and corrupts the heap. The way to free shared lists safely is reference counting.

9.5.4Equality

When are two lists equal? When their structures are the same and the corresponding atoms carry the same values. The structure being the same means that the two lists have the same length and that at every position both have either an atom or a sublist. For sublists the same definition is applied recursively. The question in the slides asks for this definition to be turned into code for lists with no sharing and no recursion:

boolean equal(list_pointer T, list_pointer L) {
    boolean x = TRUE;
    if (!T && !L) return TRUE;
    if (T && L && T->tag == L->tag) {
        if (!T->tag)             // atoms?
            x = (T->data == L->data) ? TRUE : FALSE;
        else                    // sublists
            x = equal(T->dlink, L->dlink);
        if (x == TRUE) return equal(T->link, L->link);
    }
    return FALSE;
}

The first condition is the base case: if both lists are empty, they are equal. The second condition checks that both elements exist and that their tags are the same. If one of them is empty, or if one is an atom and the other a sublist, this condition is false, the block is skipped, and the function returns FALSE. Inside the block the elements are compared first. For atoms the data fields are compared; for sublists the sublists themselves are compared recursively. The result is in x. If x is true, the answer depends on the equality of the remaining lists, and the result of that call is returned as it is. If x is false, the block ends and FALSE is returned again.

The code works correctly but is not tidy. The variable x is unnecessary; the form (T->data == L->data) ? TRUE : FALSE is long, considering that the comparison already gives 0 or 1. Three separate return flows make it hard to follow. A better version can be written. There is also a restriction that holds for both versions: two recursive lists such as C = (a, C) cannot be compared. When the sublists are compared at the second element, the same call starts over and the stack overflows, as in copying.

9.5.6A shorter version and shared lists

bool same(list_pointer T, list_pointer L) {
    if (T == L) return true;        // same node/both NULL
    if (!T || !L || T->tag != L->tag) return false;
    if (T->tag ? !same(T->dlink, L->dlink)
                  : T->data != L->data)
        return false;
    return same(T->link, L->link);
}

This version uses C's bool type, and each condition is one line. The first line carries a new shortcut: if T == L, the two pointers point to the same element, or both are NULL. In both cases the lists are equal and there is no need to descend into them. The second line eliminates the first differences: if one is empty or the tags differ, the result is false. The third line compares the contents of the elements. The conditional operator here selects not a value but a condition: in a T element, the sublists being unequal, and in an atom element, the values being different, gives a false result. The last line moves on to the rest.

The last line has one more property. The call return same(T->link, L->link); is the last thing the function does; no computation remains to be done after it returns. Such calls are called tail calls. With optimization on, compilers can turn a tail call into a jump, and moving along link then takes no space on the stack. The C standard does not guarantee this; but the way it is written allows it.

The real value of the shortcut shows in shared lists. On lists that are shared but not recursive, both routines give the right result. Sharing does not break equality; the same sublist is merely walked several times. same does not descend where it sees the same address on both sides. For example, when B is compared with itself, the first line returns true at once. When B is compared with a copy of itself that preserves sharing, the shared sublist in the copy is walked once.

A program's robustness is tested with inputs that try to break it. "I pressed the key and it worked" is not an adequate test. Knowing on which lists a routine is correct and on which it is wrong requires much broader knowledge than running it on a given example. Writing a proof lays this knowledge out explicitly. For equal this knowledge is as follows: correct on lists with no sharing and no recursion; correct on shared lists but doing needless work; not terminating on recursive lists.

9.5.7Traversing and printing, and a faulty version

The third question asks for a routine that traverses the list and prints the atoms in order. A faulty version often seen in exams is the following:

void print_atoms( list_pointer L ){
    if(L)
        if(!L->tag)
            printf("%c", L->data);
        else
            print(L->dlink);
        print( L->link );
}

There are two errors in this code. The first is the name: the routine is named print_atoms, but the recursive calls call print. No such function is defined. Since C99, calling an undeclared function is an error. In the experiment the compiler stopped with the error "call to undeclared function 'print'".

The second error is more insidious and appears once the name is fixed. There are no braces after if (L). An if without braces covers only the single statement that follows it. Here that statement is the whole inner if-else. The call print( L->link ); on the last line is outside the if (L); even though its indentation shows it inside, C does not look at indentation. This line also runs when L == NULL, and NULL->link is read. The compiler points to this with two warnings: "misleading indentation" and "add explicit braces to avoid dangling else". These warnings appear with -Wall; compiling without -Wall is therefore harming oneself.

When the name error was fixed and the code was run with (a, (b), c), ab was printed to the screen and then the program crashed. After b was printed, print_atoms(b->link), that is, print_atoms(NULL), was called; the last line of this call tried to read link through a NULL pointer. UBSan caught this access with the message "member access within null pointer of type 'struct list_node'". The compiler also gave the warning "all paths through this function will call itself". According to this warning, every path of the routine calls itself at least once, that is, no call can end without recursion. This warning says directly that the base case is missing. The correct way to write it puts both calls inside if (L) { … }:

void print_atoms(list_pointer L) {
    if (L) {
        if (!L->tag)
            printf("%c", L->data); // print an atom
        else
            print_atoms(L->dlink);
        print_atoms(L->link);
    }
}
Common mistake

Trusting the indentation. In C a block is formed with braces; indentation is only for the reader. Putting braces even around single-statement if bodies prevents a line added later from being left outside by accident. Compiling with -Wall -Wextra shows most bugs of this kind before the program is even run.

Something interesting happens when the same routine is applied to a list in tree form. Figure 9.8 shows the list that holds the tree A(B(E(K, L), F), C(G), D(H(M), I, J)). Each sublist first prints its own head, that is, the label of the node, and then walks its children from left to right by the same rule. This is the preorder traversal of trees: first the root, then the subtrees in order. The list routine has thus run a tree algorithm without knowing anything about trees. This is exactly the gain of moving data to a well-known structure.

9.6Depth

How deeply nested a generalized list is determines how much space the recursive routines that process it will occupy on the stack. In a list that holds a tree, the same measure corresponds to the height of the tree. In this section depth is first defined and then computed with two routines, one recursive and one iterative.

9.6.1Recursive depth

Definition 9.3

The depth of the empty list is 0. The depth of a non-empty list L is 1 plus the largest of the depths of the sublists of L; if there are no sublists, this largest value is taken to be 0. Atoms contribute nothing to depth.

By the definition, the depth of (a, b) is 1: it has no sublists. The depth of (a, (b, c)) is 1 + 1 = 2 and that of (a, (b, (c))) is 3. (()) is an interesting example. This list is not empty; its only element is an empty sublist. Because the depth of the sublist is 0, the depth comes out as 1 + 0 = 1. By the same reasoning the depth of ((())) is 2. The question in the slides asks for this definition to be turned into code recursively:

int depth(list_pointer L) {
    list_pointer p = L;  int m = 0;  // m: the max
    if (!L) return 0;
    while (p) {
        if (p->tag) {
            int n = depth(p->dlink);
            if (m < n) m = n;
        }
        p = p->link;
    }
    return m + 1;
}

The routine follows the definition almost word for word. For the empty list, 0 is returned. In a non-empty list the elements of the same level are walked with a while loop, and m holds the depth of the deepest sublist seen so far. Atom elements are skipped. At every sublist element the depth of the sublist is computed recursively and m is updated if necessary. When the loop ends, m + 1 is returned: the deepest sublist plus this level.

Unlike copying, this routine does not recurse along link; it walks the same level with a loop. A recursive call is made only when descending into a sublist. The number of calls is therefore 1 + s: one call from outside and one call for each sublist. Every element is visited exactly once inside a loop, and the time is Θ(n). The number of calls on the stack at the same time is at most the depth of the list. The extra memory of the routine is therefore O(depth), and long but shallow lists cause no stack problem. In the experiment, the depth of a flat list of a million atoms was computed without trouble; the same list drove copy into a stack overflow.

The examples in the slides were confirmed by experiment: (a, b) → 1, (a, (b, c)) → 2, (a, (b, (c))) → 3, (()) → 1. In addition, () → 0, ((())) → 2, and the exam-question list (d, (c, (e, (m, k), (()), z, y, (x, (r), b, a, ())))) → 5 were found.

9.6.3A faulty iterative solution

An iterative answer given to the same question in an exam is the following:

int depth( tree_pointer L ){
    tree_pointer pop(); void push(tree_pointer);
    int max = 0;
    for( int current = 1, p = L ; p ; p->link ){
        if( p->tag ){ // enter the sublist
            push(p);
            p = p -> dlink;
            current++;
        }
        if( !p->link ){   // end of list, go up
            p = pop();
            if( max < current ) max = current;
            current--;
        }
    }
    return max;
}

The idea is this: current holds the current level and max the largest level seen. When descending into a sublist, the T element is pushed onto a stack and the level increases; when the end of a level is reached, an item is popped from the stack and the search goes back up. There is nothing wrong with the idea; a correct iterative solution follows the same path. What is wrong are the details, and all of them matter.

The code does not compile. The declaration int current = 1, p = L makes both variables int; in declarations separated by commas, the type is the one at the start of the line. When p is an integer, none of the expressions p->tag, p->dlink, and p->link is valid. The compiler gave seven errors; the first is the message "incompatible pointer to integer conversion initializing 'int'". The p->link in the third part of the for is not an assignment either. The value is computed and discarded; p never advances. Even if this error alone were fixed, the loop would stay at the same element forever. The right form is p = p->link.

Even if these are fixed, the code crashes on edge cases. When it descends into an empty sublist, p = p->dlink becomes NULL and right afterward p->link is read. When the list ends, pop is called even if the stack is empty. The search goes back to the T element popped from the stack itself, but not on to its sibling, that is, T->link. It therefore descends into the same sublist again. Moreover, the stack operations rely on a global stack outside.

This solution is criticized from two separate angles. First, the expected solution is recursive. Building a loop with the counters current and max is a first-year-level approach and moves away from the recursive definition of the structure. Second, global variables are forbidden. A routine written with a global stack or a global counter works while it is tested alone. But the same routine may become part of another component. For example, when the depths of two lists are computed nested, or when two threads call it at the same time, the shared variable is corrupted. The whole state of a routine must be in its own local variables.

9.6.4Iterative depth with a local stack

An iterative solution can be written correctly. What is needed is to keep, explicitly in a local array, the call stack that recursion leaves to the compiler:

int iter_depth(list_pointer L) {
    list_pointer stack[100];   // local stack (depth<100)
    int top = 0, d = 1, m = 0;
    list_pointer p = L;
    if (!L) return 0;
    for (;;) {
        if (p == NULL) {             // level done
            if (top == 0) return m;
            p = stack[--top]->link;  // the node after T
            d--;
        } else {
            if (d > m) m = d;
            if (p->tag && p->dlink) {
                stack[top++] = p;    // descend
                p = p->dlink;
                d++;
            } else p = p->link;
        }
    }
}

The stack array holds the T elements of the sublists that have been entered; top is the number of items in the array. d is the current level and m the largest level seen. In each round of the loop, one of two cases holds.

  • If p is not empty, we are on an element. This element is at level d, so m becomes at least d. If the element is a non-empty sublist, the T element is pushed onto the stack, p moves to the first element of the sublist, and d increases by one. If the element is an atom or an empty sublist, p moves to the next element on the same level.
  • If p is empty, the end of a level has been reached. If the stack is also empty, the top level is finished and m is returned. Otherwise the T element entered last is popped from the stack and the search moves on to its sibling, T->link; d decreases by one.

All the defects of the faulty solution are fixed in this version. p is a pointer. An empty sublist is never entered, because p->dlink is checked separately. Popping is done only when the stack is not empty. After a pop, the search moves not to the popped element itself but to its sibling. There is no global variable. The contribution of an empty sublist to depth is also right. The only element of the list (()) is seen at d = 1 and m becomes 1; it does not become 2, because the sublist is not entered.

Common mistake

Returning to the T element popped from the stack in iterative traversal. The sublist of the T element is already finished. The traversal must continue from T's sibling, that is, from T->link. Code that returns to T itself descends into the same sublist again and can never leave the loop.

9.6.5Thinking recursively and extreme examples

When the two solutions of the depth question are put side by side, the difference is clear. The recursive version is ten lines and follows the definition exactly. The iterative version has to do by hand what recursion does by itself: keep track of which sublist we are in and where to return from there. This version is longer, carries a fixed limit, and is much easier to get wrong when writing.

Thinking recursively is a habit and takes time to acquire. A one-semester course is not enough for this foundation. For every recursive call one should ask, "If I give it this list, what will it return to me?", and not move on to the rest of the routine without writing down the answer. Running the code step by step with a debugger and following which value goes where at every return is the best way to see the answer to this question. The trace tables in these notes do the same job on paper.

Code that works only on the given example is not enough. A routine may give the right result on the given example and crash on others. Correctly working code is code that works correctly on extreme examples too. For generalized lists the extreme examples are well defined. 9.7Inversion

Inverting a generalized list means reversing the order of the elements on every level. Inversion is applied to every level: the inverse of the list L = (a, (b, c)) is ((c, b), a). If only the top level were reversed, the result would be ((b, c), a). This operation corresponds to taking the mirror image of the picture in a list that holds a tree or a nested shape.

9.7.1Three pointers and two extra lines

The classic routine that reverses a singly linked list in place uses three pointers. p holds the head of the part not yet reversed, q the head of the reversed part, and r the previous q. In each round the element at p is taken onto the head of the reversed part. For the generalized list, only two lines are added to this routine:

void invert(list_pointer *L) {
    list_pointer r, p = *L, q = NULL;
    while (p) {
        if (p->tag)                 // not an atom
            invert(&p->dlink);
        r = q;
        q = p;
        p = p->link;
        q->link = r;
    }
    *L = q;
}

The four assignments of the loop are the same as in the classic routine. r = q saves the element reversed in the previous round. q = p moves to the element to be reversed in this round. p = p->link advances to the rest of the list; this assignment must be made before the link is changed, otherwise the rest of the list is lost. q->link = r turns the link of the element backward. When the loop ends, q points to the last element of the old list, that is, the first element of the new list, and *L = q makes it the head of the list.

The two added lines first reverse the sublist itself when a sublist element is reached. Here it is the address of p->dlink, not its value, that is given to invert. The reason is that inversion changes the head of the list. When (b, c) is reversed, the first element of the sublist becomes c, not b. The dlink field of the T element must point to this new head. The inner call writes *L = q on its last line. Because L is the address of the dlink field of the T element, this assignment updates that field directly. The outer call has nothing left to do after the return. Had the value been given, the inner call would have updated its own local copy. The T element would have kept pointing to the old head, that is, to b, now the last element, and c would have become unreachable and leaked.

For the same reason the call from outside is also made by address: invert(&L). The head of the top level changes too, and the caller's variable L must be updated. Passing the list by value to a routine that changes the head is one of the most frequent mistakes with linked lists.

9.8Building a tree with a list

A tree consists of a root node and zero or more subtrees, each of which is again a tree. This definition is also recursive and very similar to the definition of the generalized list. This similarity makes it possible to store a tree with a one-line text and with a list built from that text.

9.8.1The linear form of a tree

In the linear form of a tree every node is written with its label; if it has children, they are listed right after the label, in parentheses, separated by commas. C(G) says that C is the parent of G. A(B…, C…, D…) says that A is the parent of B, C, and D. Figure 9.11 gives the tree in the slides and its linear form.

The text carries the whole structure of the tree. Which node is the child of whom and the order of siblings can be read unambiguously from the text. For this much data, a one-line text suffices. The notation is also a choice: a period can be used instead of a comma, and braces instead of ordinary parentheses. What matters is that the routines that go from text to structure and from structure to text can be written. When both directions are provided, nobody outside needs to know the structure inside the program.

For the transition from text to list, the tree is held as a list whose first element is the root label: the tree A(B, C) becomes the list (A, B, C). A child that has children is again a sublist of this form. The tree in the slides thus turns into the list (A, (B, (E, K, L), F), (C, G), (D, (H, M), I, J)). This transformation amounts to replacing every piece X( in the tree text with (X,, and the linear-form reader builds the list directly.

9.8.2The left–right problem in binary trees

In a general tree the order of the children is enough information: the first child, the second child, and so on. In a binary tree, however, each node has at most two children, and they are distinguished as left and right. In a node with a single child, whether this child is left or right is part of the structure. If two trees differ only in this respect, they are different trees.

Figure 9.12 shows the problem. The linear form of all three trees is A(B(C(D(E), G(I)))). The text says that B is the only child of A but cannot say on which side. The same ambiguity exists for C, E, and I. The linear form loses information in a binary tree.

The solution is to add the missing information to the text. Either an L or R mark is kept next to each node, or a special symbol is written in place of an empty child. In the second way, the left tree can be written as A(B(, C(…)), ): the left child of B is empty, so nothing is written before the comma. The abbreviation A(B(, C(…))) in the slides shows this idea. The list of children of every node then has exactly two positions and no information is lost.

9.8.3From tree to text: print_tree

Two of the assignments in the slides are related to this topic. The first asks for the memory layout and the tree structure of the list A(B(E(H, I(J, K)), F), C(G), D) to be drawn. The second asks for a routine that outputs the list notation when the tree structure is given.

The tree structure is given in Figure 9.13. Its list is (A, (B, (E, H, (I, J, K)), F), (C, G), D). In the memory layout the top row consists of the elements A, T, T, D. Below the first T are B, T, F; below that T are E, H, T; at the bottom are I, J, K. Below the second T are C and G. This list has 4 + 3 + 3 + 3 + 2 = 15 elements and depth 4. The solution of the second assignment is this:

void print_tree(list_pointer L) { // L: (root, subtrees...)
    printf("%c", L->data);          // root label
    if (L->link) {
        printf("(");
        for (list_pointer p = L->link; p; p = p->link) {
            if (p->tag) print_tree(p->dlink);
            else printf("%c", p->data);   // leaf
            if (p->link) printf(",");
        }
        printf(")");
    }
}

The parameter of the routine is a list whose first element is the root label. First the root label is printed. If there are elements in the list after the root, that is, if the node has children, an opening parenthesis is printed and the children are walked in order. A child that is a sublist is a subtree and is printed with the same routine. A child that is an atom is a leaf and only its label is printed. A comma is put after every child except the last. At the end the parenthesis is closed.

Unlike print_atoms, this routine prints parentheses and commas as well. But it opens the parenthesis not at the head of each sublist but after the root label. This small difference converts list notation to tree notation. In the experiment, the list of the tree in the slides gave the output A(B(E(K,L),F),C(G),D(H(M),I,J)) and the list of the tree in the assignment gave A(B(E(H,I(J,K)),F),C(G),D). Both are the same as the linear forms of the trees. For the one-node list (A), only A is printed. The routine is not defined for the empty list; for an empty tree L->data would be read and the program would crash. The caller must check that the tree is not empty.

The time is Θ(n): every element is printed once. Because the same level is walked with a loop, the stack depth equals the height of the tree.

9.9Sharing, reference counting, and garbage collection

Shared lists save memory; the same sublist is used in many places without being copied. But this saving has a price. When can a shared sublist be freed? If it is freed because one of the places pointing to it no longer uses it, the other places point to returned memory. If it is never freed, memory leaks.

9.9.1The header node and the reference count

In the solution proposed by Horowitz and Sahni, every list begins with a header node. The header node is not an element of the list; it is the identity of the list. Everyone who points to the list points to the header node, not to the first element. A field ref is kept in the header. This field is the number of pointers that point to the header; it is called the reference count of the list. In the example, the field int ref; has been added to the element structure.

// header ref: how many pointers point to this list
void list_free(list_pointer *L) {
    list_pointer p, q;
    if (*L == NULL) return;
    if (--(*L)->ref > 0) {      // still in use
        *L = NULL; return;
    }
    p = (*L)->link;             // first real node
    free(*L);
    while (p) {
        if (p->tag) list_free(&p->dlink);
        q = p; p = p->link; free(q);
    }
    *L = NULL;
}

list_free announces that a pointer to the list will no longer be used. First it decreases the counter by one. If the counter is still greater than zero, others are using the list as well. The routine only sets the caller's pointer to NULL and returns. If the counter has dropped to zero, nobody points to the list any more. The header is freed, and then the elements are freed in turn. For sublist elements, the sublist itself is freed with the same routine. This is a chain rule: if the sublist has other pointers to it, its counter merely decreases and it stays in memory.

Three details of the routine matter. First, the address of the first element is taken into p before the header is freed; after free(*L), (*L)->link cannot be read. Second, in the loop the link of each element is read before free. Third, the parameter is list_pointer *L and the routine writes *L = NULL in every case. The caller's pointer thus does not remain as a dangling pointer. Keeping the counter right is up to the programmer: every piece of code that creates a new pointer to the list must increase the counter by one, and every piece of code that drops a pointer must call list_free.

9.9.2Step by step: B = (A, A, ())

Let A = (a, (b, c)) and B = (A, A, ()). Three pointers point to the header of A: the variable named A and the first two T elements of B. Its counter is therefore 3. Only the variable B points to the header of B, and its counter is 1. The empty list that the third element of B points to also has its own header, and its counter is 1.

  1. list_free(&B): the counter of B goes from 1 to 0. The header is freed and the walk over the elements begins.
  2. The first T element calls list_free(&p->dlink). The counter of A goes from 3 to 2; because it is not zero, A is not touched, and only the dlink of the T element becomes NULL. The T element is freed.
  3. The second T element does the same: the counter of A goes from 2 to 1.
  4. The third T element makes a call for the header of the empty list. The counter of that header goes from 1 to 0; the header is freed, and since it has no first element, the loop never runs. The T element is freed. B is now NULL.
  5. When the program frees A as well, list_free(&A) lowers the counter from 1 to 0. The header of A, a, the T element, and the header of (b, c), b, and c are freed.

This scenario was run with counting malloc/free wrappers. The structure uses 11 blocks: 6 for A (two headers and four elements), 1 header for the empty list, and 1 header and 3 elements for B. list_free(&B) freed 5 blocks and left the counter of A at 1. list_free(&A) freed the remaining 6 blocks. A total of 11 allocations and 11 releases were counted; no block was freed twice and there was no leak. Sharing was managed safely.

The same idea can be applied to copying as well. Instead of copying a shared sublist, its counter is increased by one and the new list points to the same header. Copying thus becomes both faster and cheaper in memory. The counterpart is that care must be taken when lists are modified: a change made in a shared list is visible everywhere that points to it.

9.9.3The limit of reference counting and garbage collection

Reference counting falls short with recursive lists. Two pointers point to the header of C = (a, C): the variable C and the T element of the list itself. The counter is 2. When the program calls list_free(&C), the counter drops to 1 and the list is not freed. But now no variable of the program can reach this list. The only pointer that could bring the counter down to zero is inside the list itself. The list stays in memory forever. This situation was observed in the experiment: after list_free(&C), C became NULL, the counter stayed at 1, and none of the 3 allocated blocks was freed. The same problem arises with every cycle, such as two lists pointing to each other.

Another method is needed to collect cycles as well: garbage collection. Its best-known form is the mark and sweep method, which consists of two phases:

  1. Marking. The search starts from the program's variables, that is, from the root pointers. All the elements reachable from them are traversed and the mark bit of each is set. The traversal stops when it sees an element a second time; cycles are therefore no problem.
  2. Sweeping. The memory in which the elements live is scanned from beginning to end. Every unmarked element is garbage that cannot be reached from anywhere and is added to the list of free nodes. The marks of marked elements are cleared for the next collection.

In the example C = (a, C), after the variable C is deleted, none of the root pointers reaches the list. The marking phase never touches the elements of the list and the sweep collects them. Unlike with reference counting, the cycle is no obstacle here.

Garbage collection has a cost too. While the collector runs, the program stops or slows down; in a large memory this pause is noticeable. Every element needs space for a mark bit. LISP, Java, and Python use refined variants of this idea. Python, for example, first counts references and finds cycles with a separate collector. C has no automatic garbage collection. The responsibility for copying, sharing, and freeing lies entirely with the programmer. A C programmer therefore must know how each routine they write behaves on shared and recursive lists.

9.10.1Element count and sublist counters

Question. The element structure has been given an int count field. Write recursively the routine that writes into the counter of every element whose tag is TRUE the number of elements beneath it, and returns the total number of elements.

int count_nodes(list_pointer L) {
    int total = 0;             // an empty list has 0 nodes
    for (; L; L = L->link) {
        if (L->tag) {           // is there a sublist?
            L->count = count_nodes(L->dlink);
            total += L->count;  // count the sublist's nodes too
        }
        total++;                // the current node
    }
    return total;
}

The routine walks the same level with a for loop and accumulates the elements in total. In an empty list the loop never runs and 0 is returned. Every element is counted once for itself. At a sublist element, the number of elements in the sublist is additionally found recursively, written into the count field of the element, and added to the total. The counter of a T element thus counts only the elements beneath it; the T element itself is counted one level up.

For (a, (b, c)) the counter of the T element is 2 and the return value is 4: a, the T element, b, and c. The experiment confirmed this and more complex lists. For ((a, b), ((c, d), e)) the result is 8 and the counters of the T elements are 2, 4, and 2. For (()) the result is 1 and the counter of the single T element is 0. The list in the last exam question of the slides has 19 elements.

9.10.2Printing in linear form

Question. Write the recursive routine that prints a generalized list in memory in linear form.

void print_linear(list_pointer L) {
    printf("(");
    for (; L; L = L->link) {
        if (L->tag) print_linear(L->dlink);
        else printf("%c", L->data);
        if (L->link) printf(",");
    }
    printf(")");
}

Each call of the routine prints one list, so the opening and closing parentheses are there in every call. In between, the elements are walked: a sublist element is printed with the same routine, and an atom with just its value. A comma is put after every element except the last. For an empty sublist the call is made with NULL; the loop never runs and () is printed. Empty sublists therefore do not disappear: (a, (()), b) is reproduced exactly.

This routine and the linear-form reader are inverses of each other. When a text that was read is printed, the same text must come out. This property was tested on 20,000 random texts and no difference was found. A pair of routines that convert a structure to text and rebuild it from text is the basis for saving the structure, sending it over a network, and testing it.

9.12Common mistakes

  1. Assuming a shared list is unshared. copy copies a shared sublist separately wherever it is pointed to; free_list returns it twice. The second is undefined behavior.
  2. Calling copy or equality on a recursive list. For C = (a, C) the calls never end and the stack overflows.
  3. Forgetting braces in if statements. In the faulty print_atoms, the last call also runs for NULL and the program crashes while reading NULL->link.
  4. Passing the list by value to a routine that changes the head. Inversion needs list_pointer *L; for sublists, &p->dlink is passed.
  5. Confusing the empty sublist () with the empty list (NULL). () is an element: the T element exists, only its dlink is NULL.
  6. Counting depth with a global variable. When the routine becomes part of another component or is called in a nested way, the shared variable is corrupted.
  7. Reading a field of the union without checking the tag. The dlink of an atom element is not an address.
  8. Returning to the T element popped from the stack in iterative traversal. The place to continue is T's sibling, T->link.
  9. Writing the result of realloc directly into the same pointer. If memory runs out, the old block is lost.

9.13.3Copying that preserves sharing

Question. How is copy changed so that it preserves sharing? The path suggested by the slides: keep the sublists already copied (old address → new address) in a table.

#define TABLE_SIZE 100
typedef struct { list_pointer from, to; } pair;

// t[0..*n-1]: sublists already copied (old head -> new head)
list_pointer copy_shared(list_pointer L, pair t[], int *n) {
    list_pointer head = NULL, *tail = &head, q;
    int k;
    for (; L; L = L->link) {
        q = get_node();
        q->tag = L->tag;
        if (!L->tag) q->data = L->data;
        else {
            for (k = 0; k < *n && t[k].from != L->dlink; k++)
                ;                       // search the table
            if (k < *n) q->dlink = t[k].to;   // shared
            else {
                q->dlink = copy_shared(L->dlink, t, n);
                if (*n < TABLE_SIZE) {
                    t[*n].from = L->dlink;
                    t[*n].to = q->dlink;
                    (*n)++;
                }
            }
        }
        *tail = q;
        tail = &q->link;
    }
    *tail = NULL;
    return head;
}

The routine walks the same level with a loop and appends the elements at the end with the tail pointer. At a sublist element, the table is consulted first. If the old head of the sublist is in the table, the new element points to the copy in the table and the sublist is not copied again. If not, the sublist is copied and the pair is added to the table. For B = (A, A, ()) the routine allocated 7 elements (copy had allocated 11). The first two elements of the copy point to the same list, and same finds the copy equal to the original list. The table has 3 pairs: A, (b, c), and the empty list.

The limits of the solution are clear. Because the table is searched linearly, O(t) work is done for every sublist; with many sublists, a hash table is more suitable. If the table fills up, sharing is silently lost. On recursive lists the routine still does not terminate, because the record of a sublist is made only after its copy is finished. To fix this, the new head would have to be written to the table before the sublist starts to be copied; this becomes easier with a representation that has header nodes.

9.13.4Searching for an atom

Question. Write the routine contains(L, x) that finds whether an atom x occurs in the list. The path suggested by the slides: compare at an atom, search recursively in a sublist; return at the first find.

bool contains(list_pointer L, char x) {
    for (; L; L = L->link)
        if (L->tag ? contains(L->dlink, x) : L->data == x)
            return true;                // return at the first find
    return false;
}

The conditional operator selects one of two questions according to the kind of the element: is x in the sublist, or is this atom x. If the answer is yes, the search ends at once. In the exam-question list, r (one of the deepest atoms) and d were found and q was not. In the worst case, that is, when the atom is absent, all the elements are walked: O(n).

9.13.5A growing array

Question. Rewrite the array-based list so that it doubles in size when it fills up. The path suggested by the slides: realloc(a, 2*cap*sizeof *a); average O(1) insertion.

The solution was given at the beginning of the notes as the array implementation of the list ADT. struct list holds the address of the array on the heap, the item count, and the capacity; list_insert doubles the capacity when the array is full. The result of realloc is put into a separate variable. A geometric sum proves that doubling gives amortized O(1) cost for insertion at the end.

9.14Summary

  • The list ADT is a contract of operations: for list_insert the precondition is 0 ≤ i ≤ n and the postcondition is "x is at position i, the length is n + 1". The opaque type (typedef struct list List;) hides the implementation; when the implementation changes, the using code does not.
  • In the array implementation, access is O(1) and insertion and deletion are O(n) because of shifting. When a dynamic array is doubled in size, insertion at the end becomes amortized O(1).
  • In the linked implementation, walking to a position is O(i) and linking is O(1). A pointer to pointer (node_pointer *pp) reduces insertion at the head and in the middle to one piece of code.
  • The elements of a generalized list are atoms or sublists. An element has the form [tag | data/dlink | link]; tag is the tag, and data/dlink is a tagged union. A list may be shared or recursive.
  • The recursive pattern: if an atom, process it; if a sublist, descend; then continue with link. copy, equal, and print_atoms run in Θ(n) with this pattern and make 1 + n + s calls. They are correct on lists with no sharing and no recursion.
  • Depth: the empty list is 0; otherwise 1 + the largest depth of the sublists. The recursive version is short and direct; the iterative version needs a local stack and uses no global variable.
  • Inversion adds two lines to the three-pointer routine: the sublist is first reversed with invert(&p->dlink). It works in place and makes no malloc calls.
  • A tree is stored with nested lists whose first element is the root label, and with a one-line linear form. print_atoms performs a preorder traversal on such a list. In a binary tree the linear form loses the left–right information; an L/R mark or an empty-child symbol must be added.
  • Reference counting frees shared lists safely with ref in the header node; but on a cycle the counter never drops to zero. Garbage collection (mark and sweep) collects cycles as well. C has no garbage collection.

  3. ll_insert(&B, 0, 5) is called on the list 4 → 7. How many times does the loop run, what does pp point to, and which pointer does *pp = new_node change?

    Answer

    Because i = 0, the loop never runs and pp stays at &B.head. new_node->link = *pp links 5 to 4; *pp = new_node turns B.head to 5. The list becomes 5 → 4 → 7 with n = 3. No separate branch is needed for insertion at the head.

  4. array_insert(&L, 0, v) is performed ten times on an empty ArrayList. How many shifts are made in total? What if the same ten values were always added at the end?

    Answer

    At the k-th insertion the list holds k − 1 elements and all of them shift: 0 + 1 + … + 9 = 45. For insertion at the end, since i = n, the loop never runs: 0 shifts.

  5. (a, (b)) and (a, b) are compared with equal. What is the result and how many times is the function called?

    Answer

    In call 1, a/a are equal and call 2 is made for the rest. In call 2, one element is a T and the other an atom; because the tags differ, the block is skipped and FALSE is returned. The result is FALSE, with 2 calls in total.

  6. What does invert(&L) turn the list L = (a, (b, (c, d)), e) into? How many malloc calls are made?

    Answer

    Every level is reversed: (c, d) → (d, c), (b, (c, d)) → ((d, c), b), top level → (e, ((d, c), b), a). The routine only changes links; no malloc is made.

  7. Inside invert, if list_pointer t = p->dlink; invert(&t); is written with a new local variable instead of invert(&p->dlink), what happens for (a, (b, c))?

    Answer

    The inner call inverts the sublist correctly and writes the new head c into t. But the dlink field of the T element is not updated; it still points to b. Because the link of b is now NULL, the list appears as ((b), a); c becomes unreachable and leaks. The fix is either to add p->dlink = t or to pass the address of the field directly.

  8. A = (x) and B = (A, A, A) have been built with header nodes with reference counts. What is the counter of A at the start? What is it after list_free(&B), and is A freed?

    Answer

    A is pointed to by the variable A and by the three T elements of B: the counter is 4. While B is being freed, the three T elements lower the counter 4 → 3 → 2 → 1. Because the counter is not zero, A is not freed; the variable A still points to it.

  9. What do print_atoms and print_tree print for the list (A, (B, (E, H, (I, J, K)), F), (C, G), D)?

    Answer

    print_atoms prints the atoms in preorder: ABEHIJKFCGD. print_tree prints the linear form of the tree: A(B(E(H,I(J,K)),F),C(G),D).
