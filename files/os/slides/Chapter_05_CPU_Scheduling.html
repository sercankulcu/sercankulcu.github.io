Basic Concepts

What Is Scheduling?

  • In a multiprogrammed system many processes wait ready in memory; when the CPU becomes free, the short-term scheduler (CPU scheduler) decides which one runs.
  • Goal: never leave the CPU idle, and improve the chosen objectives (response, throughput, fairness, deadlines).
  • Ready queue: processes ready to run. Wait queues: those waiting for I/O or an event. Running: at most one per core.
  • The ready queue need not be FIFO: it can be a priority queue, a tree or an unordered list.
  • Modern kernels actually schedule kernel threads; “process scheduling” is used in this sense.

Basic Concepts

The CPU–I/O Burst Cycle

What matters is not how long the I/O wait is but how short the CPU burst is. An I/O-bound process that runs as soon as it is ready keeps the disk and network busy.

Basic Concepts

Overlapping with I/O: Treating Bursts as Separate Jobs

A and B each need 50 ms of CPU; A runs 10 ms and then waits 10 ms for the disk, B does no I/O.

If A counts as one 50 ms job, the CPU is idle while A is at the disk: B starts only when A ends.

Each burst is a separate job: B runs while A is at the disk; the short returning A preempts B (STCF).

Basic Concepts

When Are Scheduling Decisions Made?

1. Running → waiting: the process requests I/O or calls wait(). The CPU is free; a choice is required.

2. Running → ready: a clock interrupt arrived, the time slice expired. Preempting the running process is optional.

3. Waiting → ready: I/O completed; the woken process may preempt the running one if it is more important.

4. Termination: the process ends with exit(); the CPU is free, a choice is required.

A scheduler that decides only at 1 and 4 is nonpreemptive (cooperative); one that also decides at 2 and 3 is preemptive.

Basic Concepts

Preemptive and Nonpreemptive Scheduling

Nonpreemptive

The chosen process runs until it blocks, exits or yields the CPU (yield). No clock interrupt needed; few switches.

Windows 3.x and classic Mac OS (≤ 9) used cooperative multitasking; one faulty program could hang the system.

Preemptive

A process is suspended when its time slice expires or a higher-priority process becomes ready. Needs a clock interrupt; every modern general-purpose OS does this.

The price: race conditions on shared data and more context switches.

  • Kernel preemption: since Linux 2.6 kernel code is preemptible too, but only when it holds no lock (preempt_count = 0).
  • After 20 years, the PREEMPT_RT patches entered mainline in Linux 6.12 (2024): interrupt handlers run as threads; latency drops to microseconds.
  • Batch jobs can use nonpreemptive or long-slice algorithms; interactive and server systems need preemption.

Basic Concepts

The Dispatcher and the Context Switch

  • The dispatcher gives the CPU to the process the scheduler chose: it switches context, switches to user mode and jumps to the right place in the program.
  • It runs on every switch, so it must be fast; the direct cost today is a few microseconds.
  • Measuring on Linux: the cs column of vmstat 1; voluntary_ctxt_switches and nonvoluntary_ctxt_switches in /proc/<pid>/status.

Basic Algorithms

FCFS Step by Step

First-come, first-served: the ready queue is FIFO; a process that gets the CPU keeps it until it finishes or blocks. The simplest algorithm to implement.

t = 0: only P1 is in the queue; it takes the CPU and keeps it for 8 ms (nonpreemptive).

t = 8: P1 is done. The queue advances in arrival order → P2 at the head runs (it waited 7 ms).

t = 12: P2 is done. The queue advances in arrival order → P3 at the head runs (it waited 10 ms).

t = 21: P3 is done. The queue advances in arrival order → P4 at the head runs (it waited 18 ms).

Basic Algorithms

FCFS: The Convoy Effect

Long job first: the short P2 and P3 wait behind P1. Average waiting 17 ms.

The same jobs in a different arrival order: average 3 ms. Under FCFS the result is very sensitive to arrival order.

Convoy effect: the CPU-bound C holds the CPU; the I/O-bound processes pile up behind it and the devices sit idle in turn.

The CPU-bound process holds the CPU until it terminates; I/O-bound processes release it after short bursts. FCFS is nonpreemptive; there is no starvation, but it is unsuitable for interactive systems.

Basic Algorithms · Step through the code

Computing FCFS Waiting Time

/* p[] sorted by arrival time */
void fcfs(Proc p[], int n) {
  int t = 0, sum = 0;
  for (int i = 0; i < n; i++) {
    if (t < p[i].arrival) t = p[i].arrival;
    int wait = t - p[i].arrival;
    t += p[i].burst;         /* completion */
    sum += wait;
    printf("%s: %d\n", p[i].name, wait);
  }
  printf("avg = %.2f\n", (double) sum / n);
}

The clock t and the total waiting sum start at zero. The processes are in arrival order.

P1 arrived at 0; the CPU was free at 0 → wait = 0 − 0 = 0.

P1 runs 8 ms; the clock becomes 8; total waiting 0.

P2 arrived at 1; the CPU was free at 8 → wait = 8 − 1 = 7.

P2 runs 4 ms; the clock becomes 12; total waiting 7.

P3 arrived at 2; the CPU was free at 12 → wait = 12 − 2 = 10.

P3 runs 9 ms; the clock becomes 21; total waiting 17.

P4 arrived at 3; the CPU was free at 21 → wait = 21 − 3 = 18.

P4 runs 5 ms; the clock becomes 26; total waiting 35.

Average waiting = 35 / 4 = 8.75 ms, the same as the FCFS Gantt chart.

Basic Algorithms

SJF: Shortest Job First

  • Shortest-job-first: among the ready processes, pick the one with the shortest next CPU burst; ties are broken FCFS.
  • If all jobs are ready at once, it provably minimizes the average waiting time: the first job's length is added to everyone's wait, so the shortest should go first (in the formula on the right, a has the largest coefficient).
  • If arrivals are at different times, nonpreemptive SJF is not optimal; its preemptive version, SRTF, is.
  • The problem: the next burst length is unknown. Batch systems use the user's estimate (e.g. Slurm --time); short-term scheduling predicts it from history.
  • Long jobs can starve if short jobs keep arriving.

When all jobs are ready at once, SJF minimizes average waiting and turnaround time; it does not aim to raise CPU utilization, since the CPU is busy under every algorithm as long as there is work.

Basic Algorithms

Predicting the Next CPU Burst: Exponential Average

τn+1 = α · tn + (1 − α) · τn,  0 ≤ α ≤ 1

  • tn: actual length of the n-th burst; τn: the prediction made for it; τ0: a constant (e.g. the system average).
  • α = 0 → the last measurement is ignored and the prediction never changes; α = 1 → only the last burst counts. A common choice is α = ½.
  • Expanded: τn+1 = αtn + (1−α)αtn−1 + … + (1−α)n+1τ0: older measurements weigh exponentially less.
  • Tanenbaum's “aging” estimate is the same idea: T0, T0/2 + T1/2, T0/4 + T1/4 + T2/2, …
  • Example (α = ½, τ0 = 10): t0 = 6 → τ1 = ½·6 + ½·10 = 8.

Basic Algorithms · Step through the code

Computing the Exponential Average

double tau = 10.0;      /* τ0 */
const double a = 0.5;  /* α */
int t[] = { 6, 4, 6, 4, 13, 13, 13 };
for (int n = 0; n < 7; n++) {
  printf("%.1f %d\n", tau, t[n]);
  tau = a * t[n] + (1 - a) * tau;
}
printf("next: %.1f\n", tau);

Initial prediction τ0 = 10, α = 0.5. No burst has been measured yet.

n = 0: actual 6, predicted 10 → τ = 0.5·6 + 0.5·10 = 8.

n = 1: actual 4, predicted 8 → τ = 0.5·4 + 0.5·8 = 6.

n = 2: actual 6, predicted 6 → τ = 0.5·6 + 0.5·6 = 6.

n = 3: actual 4, predicted 6 → τ = 0.5·4 + 0.5·6 = 5.

n = 4: actual 13, predicted 5 → τ = 0.5·13 + 0.5·5 = 9.

n = 5: actual 13, predicted 9 → τ = 0.5·13 + 0.5·9 = 11.

n = 6: actual 13, predicted 11 → τ = 0.5·13 + 0.5·11 = 12.

The bursts jumped to 13; the prediction catches up in a few steps: 5 → 9 → 11 → 12.

Basic Algorithms

SRTF Step by Step

Shortest-remaining-time-first (SRTF / SRTN): the preemptive version of SJF. When a new process arrives, its length is compared with the remaining time of the running one.

t = 0: only P1 exists and starts running.

t = 1: P2 arrives (4); the running P1 has 7 left. 4 < 7 → P1 is preempted and P2 runs.

t = 2: P3 arrives (9). The running P2 has 3 left ≤ 9 → no preemption.

t = 3: P4 arrives (5). The running P2 has 2 left ≤ 5 → no preemption.

t = 5: P2 is done. Remaining times: P1 7, P3 9, P4 5 → shortest P4 (5).

t = 10: P4 is done. Remaining times: P1 7, P3 9 → shortest P1 (7).

t = 17: P1 is done. Remaining times: P3 9 → shortest P3 (9).

Basic Algorithms

Priority Scheduling

  • Each process gets a priority number; the highest-priority ready process runs. In this course a smaller number = higher priority (Linux and Windows differ in direction).
  • Priorities come from internal factors (memory, open files, measured I/O/CPU ratio) or external ones (importance, payment, policy). SJF is the special case where the priority is the predicted next burst; if all priorities are equal, the algorithm becomes FCFS.
  • It can be preemptive or nonpreemptive; RR can be used among processes of the same priority (b).
  • A side effect is priority inversion: while a high-priority job waits for a lock held by a low-priority one, medium-priority jobs cut in; the fix is priority inheritance.

Basic Algorithms

Starvation and Aging

Starvation: if high-priority jobs keep arriving, a low-priority job never runs. Aging: its priority is raised step by step while it waits. Rule: for every 4 ms spent ready, the priority number drops by 1. L (3 ms, pr 7) arrives at t = 0; a new H (4 ms, pr 2) arrives every 4 ms. Nonpreemptive priority.

t = 0: L's priority is 7, the newly arrived H1's is 2 → H1 runs. After L waits another 4 ms its priority becomes 6.

t = 4: L's priority is 6, the newly arrived H2's is 2 → H2 runs. After L waits another 4 ms its priority becomes 5.

t = 8: L's priority is 5, the newly arrived H3's is 2 → H3 runs. After L waits another 4 ms its priority becomes 4.

t = 12: L's priority is 4, the newly arrived H4's is 2 → H4 runs. After L waits another 4 ms its priority becomes 3.

t = 16: L's priority is 3, the newly arrived H5's is 2 → H5 runs. After L waits another 4 ms its priority becomes 2.

t = 20: L's priority is 2, equal to H6's; ties go to the earlier arrival → L finally runs (it waited 20 ms).

Aging turns an unbounded wait into a bounded one: in the worst case L waits priority gap × 4 ms = 20 ms.

Round Robin

Round Robin (RR)

  • Round robin: FCFS + preemption. Each process runs for at most one time quantum (q), then goes to the tail of the queue.
  • With n ready processes (a fixed number) and quantum q, ignoring context switches, no process waits longer than (n − 1) · q: response time is bounded, and there is no starvation.
  • Turnaround is usually worse than SJF, response time better.
  • An I/O-bound process uses a small part of its quantum and blocks for I/O (moving to a wait queue), returning to the tail of the ready queue when the I/O completes; CPU-bound processes get a bigger share (hence refinements such as MLFQ and virtual RR).

Round Robin · Step through the code

Round Robin: Code Trace

/* p[] sorted by arrival time */
void rr(Proc p[], int n, int q) {
  int t = 0, k = 0;     /* k: next arrival */
  add_arrivals(p, n, &k, t);
  while (!empty() || k < n) {
    if (empty()) {       /* CPU idle */
      t = p[k].arrival;  /* next arrival */
      add_arrivals(p, n, &k, t);
    }
    Proc *s = dequeue(); /* head */
    int slice = min(q, s->left);
    t += slice; s->left -= slice;
    add_arrivals(p, n, &k, t);  /* first */
    if (s->left > 0) enqueue(s); /* then */
    else printf("%s %d\n", s->name, t);
  }
}

t = 0: only P1 has arrived; it enters the queue. The quantum is q = 4 ms.

t = 0–4: P1 leaves the queue and runs 4 ms (4 left). Meanwhile P2, P3, P4 arrived; they enter the queue first, then P1.

t = 8: P2 ran its last 4 ms and is done; its completion time is printed.

t = 12: P3 used up its quantum (5 left) and returns to the tail.

t = 16: P4 used up its quantum (1 left) and returns to the tail.

t = 20: P1 ran its last 4 ms and is done; its completion time is printed.

t = 24: P3 used up its quantum (1 left) and returns to the tail.

t = 25: P4 finished its last 1 ms before the quantum ran out (slice = 1); it does not go back in the queue.

t = 26: P3 finished its last 1 ms before the quantum ran out (slice = 1); it does not go back in the queue.

The queue is empty and no process is left to arrive (k = n), so the loop ends: 8 dispatches, 7 context switches. New arrivals are queued before the preempted process because of the order of lines 13 and 14. Lines 6–9 never run in this example.

Round Robin

Time Quantum and Context Switches

  • Fraction lost = s / (q + s) (each process uses its full quantum, with a switch after each one; it differs for processes that finish early or block): with q = 4 ms and switch time s = 1 ms, 20% of the CPU is wasted; at q = 100 ms it is ≈ 1%, but the system responds sluggishly.
  • Today a switch takes a few µs and a typical quantum is 1–100 ms (Linux EEVDF base slice 0.75 ms × (1 + log₂ CPUs), 3 ms on 8+ cores; on Windows client ≈ 2 clock ticks). Rule of thumb: ≈ 80% of CPU bursts should be shorter than q.
  • Turnaround does not improve monotonically with q (right). With q = 4, the set P1 24, P2 3, P3 3 has average waiting 17 / 3 ≈ 5.67 ms (17 under FCFS).

Multilevel Queues

Multilevel Queue (MLQ)

  • The ready queue is split into classes; each process is permanently assigned to one queue by type (e.g. foreground / background).
  • Each queue has its own algorithm: RR (short q) for the foreground, FCFS for the background.
  • Scheduling among queues: fixed priority (a lower queue runs only when the upper one is empty → starvation) or time slicing (e.g. 80% of the CPU to the foreground, 20% to the background).
  • Low overhead but inflexible: a process cannot change queues.

A structure with fixed assignment is MLQ; one where processes change queues based on their behavior is the feedback queue, MLFQ.

Multilevel Queues

Multilevel Feedback Queue (MLFQ)

  1. Priority(A) > Priority(B) → A runs; if equal, RR.
  2. A new job enters the top queue (assumed short at first).
  3. A job that uses up its allotment at a level moves down one level, no matter how many times it gave up the CPU.
  4. Every S time units all jobs move to the top queue (priority boost): this prevents starvation and gives a job whose behavior changed a new chance.

Parameters: number of queues, each queue's algorithm and quantum, the rules for moving down/up, the entry queue for new jobs. The rules follow OSTEP (Chapter 8); short jobs finish at the top, long CPU jobs sink down.

Multilevel Queues

MLFQ Step by Step

Three queues: Q0 (q = 8), Q1 (q = 16), Q2 (FCFS). Jobs: A (0, 30), B (2, 6), C (4, 20), D (25, 4). A preempted job returns to the head of its queue and completes its quantum.

t = 0: A arrives and enters Q0; it runs with an 8 ms quantum. B (t = 2) and C (t = 4) are added to Q0.

t = 8: A used up its quantum → down to Q1. B, next in Q0, runs.

t = 14: B finished in 6 ms (before its quantum ran out, in Q0). Now C runs 8 ms in Q0.

Multilevel Queues

MLFQ in Practice

Gaming the scheduler

A job that does I/O just before its quantum ends can monopolize the CPU under the “blocked jobs stay on top” rule. The fix: count the total usage at a level (rule 3).

Starvation and changing behavior

Many interactive jobs starve long ones; and a long job that later becomes interactive goes unnoticed. The fix: periodic priority boost (rule 4).

History: CTSS (1962)

Priority classes ran for 1, 2, 4, 8 quanta; a job that used up its quanta moved down a class. Pressing Enter at the terminal moved the process to the top class; users noticed and sped up their jobs by pressing Enter.

Today

The Solaris TS class (table-driven quanta and priorities), FreeBSD ULE, Windows dynamic priorities and macOS use the MLFQ idea. Since 2.6.23 Linux uses fair sharing (CFS, then EEVDF) instead of priority heuristics.

Proportional Share

Guaranteed and Fair-Share Scheduling

Guaranteed scheduling: with n users (or processes), each is promised 1/n of the CPU. For each, ratio = CPU received / CPU entitled is computed, and the lowest ratio runs. One at 0.5 (half its share) goes ahead; one at 2.0 waits.

Fair-share scheduling: shares go not to processes but to users or groups; a user who starts many processes cannot get more CPU.

Today: group scheduling with Linux cgroup v2 cpu.weight; systemd puts each user in a user-UID.slice, and Kubernetes CPU requests are turned into weights too.

Guaranteed scheduling in Tanenbaum's sense is the share guarantee above, not running to a predetermined timetable.

Proportional Share

Lottery Scheduling

  • Each process gets tickets; in every time slice a random ticket is drawn and its holder runs. In the long run, share = tickets / total tickets.
  • Simple to implement: a random number + a running total over a list (Waldspurger and Weihl, 1994).
  • A new process has a chance as soon as it gets tickets: responsive; priority means “more tickets”.
  • Ticket transfer: a client waiting on a server hands its tickets to the server. Ticket currency and, in a trusted environment, inflation.
  • It is probabilistic: it can be unfair in the short run (two jobs with equal tickets may split 10 slices 7–3). Its deterministic counterpart is stride scheduling.

Lottery scheduling is one of the simplest algorithms; priority is expressed as a number of tickets.

Proportional Share · Step through the code

Lottery Scheduling: Code Trace

/* one draw per time slice */
int counter = 0;
int winner = getrandom(0, totaltickets);
node_t *current = head;
while (current) {
  counter = counter + current->tickets;
  if (counter > winner)
    break;          /* found the winner */
  current = current->next;
}
/* current: process that gets the CPU */
run(current);

Ticket list A 30, B 10, C 60 (100 in total). The number drawn is 47; counter holds the running total.

A: counter = 30, not above 47 → the drawn ticket is not in A's range; next node.

B: counter = 40, not above 47 → the drawn ticket is not in B's range; next node.

C: counter = 100 > 47 → C wins; the loop breaks.

Next slice: a new draw, 35; the counter starts from zero and the list is scanned from the head again.

A: counter = 30, not above 35 → the drawn ticket is not in A's range; next node.

B: counter = 40 > 35 → B wins; the loop breaks.

Next slice: a new draw, 12; the counter starts from zero and the list is scanned from the head again.

A: counter = 30 > 12 → A wins; the loop breaks.

In three slices A, B and C each ran once; the share approaches 30 : 10 : 60 only in the long run. Sorting the list by tickets in decreasing order shortens the scan.

The code is the decision loop from OSTEP Chapter 9; the drawn numbers are fixed for the example.

Proportional Share

Stride Scheduling Step by Step

Stride = large number / tickets (10,000 / tickets): A 100, B 200, C 40. In each slice the process with the smallest pass value runs and adds its stride to its pass; ties go in the order A, B, C.

Step 1: pass values A 0, B 0, C 0 → smallest A runs; pass(A) += 100.

Step 2: pass values A 100, B 0, C 0 → smallest B runs; pass(B) += 200.

Step 3: pass values A 100, B 200, C 0 → smallest C runs; pass(C) += 40.

Step 4: pass values A 100, B 200, C 40 → smallest C runs; pass(C) += 40.

Step 5: pass values A 100, B 200, C 80 → smallest C runs; pass(C) += 40.

Step 6: pass values A 100, B 200, C 120 → smallest A runs; pass(A) += 100.

Step 7: pass values A 200, B 200, C 120 → smallest C runs; pass(C) += 40.

Step 8: pass values A 200, B 200, C 160 → smallest C runs; pass(C) += 40.

In 8 slices A ran 2 times, B once, C 5 times: exactly 100 : 50 : 250 = 2 : 1 : 5. With a lottery this ratio holds only in the long run.

Stride is the deterministic form of lottery (Waldspurger, 1995). Its drawback is global state: a newcomer with pass 0 would monopolize the CPU, so it starts at the current minimum pass. The vruntime of Linux CFS is a very close idea.

Multiprocessor Scheduling

Thread Scheduling: PCS and SCS

  • The kernel schedules kernel threads, not processes. A library manages user threads.
  • PCS (process-contention scope): in the N:1 and M:N models the library has user threads compete for the LWPs within their process.
  • SCS (system-contention scope): the kernel chooses among all threads in the system. Linux, Windows and macOS, with the 1:1 model, use only SCS.
  • A current PCS example: Java 21 virtual threads and Go goroutines are mapped onto a few carrier threads by the run-time's own scheduler.
pthread_attr_t attr;

  printf("PCS\n");
/* Linux, macOS: SYSTEM only */

Multiprocessor Scheduling

Approaches to Multiprocessor Scheduling

  • Asymmetric (AMP): a single master processor does all scheduling and I/O; simple but a bottleneck.
  • Symmetric (SMP): each processor schedules itself; most modern general-purpose systems. AMP-like arrangements are still used in embedded/heterogeneous systems.
  • (a) Common queue: the load balances itself, but there is lock contention and poor cache affinity.
  • (b) Per-core queues (two-level scheduling): a job is first assigned to a core, then runs from that core's queue. Locking is almost nil and caches stay warm. Linux, Windows and FreeBSD use this.
  • The price: queues can become unbalanced → load balancing is needed.

Multiprocessor Scheduling

Multicore and Hardware Threads

  • Memory stall: on cache misses a core can spend up to 50% of its time waiting for data.
  • SMT (Intel Hyper-Threading, AMD SMT): 2 hardware threads per core; one runs while the other waits. The OS sees each hardware thread as a separate logical CPU.
  • Two-level scheduling: the OS chooses which software thread runs on which logical CPU; the core's hardware chooses which hardware thread executes at the moment.
  • Sibling logical CPUs share execution units: putting two heavy jobs on the same core while a physical core is idle is a bad decision.

Multiprocessor Scheduling

Load Balancing

Start: CPU0's queue has 5 jobs, CPU3 is idle. With per-core queues the imbalance does not fix itself.

Push migration: a periodic balancer compares loads and pushes 2 jobs from the overloaded CPU0 to CPU3.

The only job on CPU2 finished; CPU2 is now idle.

Pull migration: the idle CPU2 steals a job from the busiest queue. Linux uses both.

Balance is restored, but the moved job's cache is cold on the new CPU. Linux balances first within SMT siblings and shared caches, and less often across NUMA nodes (scheduling domains).

Multiprocessor Scheduling · Step through the code

Load Balancing: Code Trace

void balance(int me) {    /* idle CPU */
  int max = me;
  for (int c = 0; c < NCPU; c++)
    if (q[c].n > q[max].n) /* busier */
      max = c;
  int t = (q[max].n - q[me].n) / 2;
  for (int k = 0; k < t; k++)
    migrate(&q[max], &q[me]); /* from tail */
}

CPU 1's queue is empty. Pull balancing: balance(1). Initially max = me = 1.

c = 0: n = 3 > the busiest so far → max = 0.

c = 1: n = 0, not busier.

c = 2: n = 5 > the busiest so far → max = 2.

c = 3: n = 2, not busier.

t = (5 − 0) / 2 = 2: moving half the difference brings the two queues close to equal (CPU 2: 3, CPU 1: 2).

k = 0: H, at the tail of CPU 2's queue, migrates to CPU 1. Jobs at the tail are not the longest-waiting but the most recent arrivals: those with the coldest caches.

k = 1: G, at the tail of CPU 2's queue, migrates to CPU 1. Queue lengths 3, 2, 3, 2. Migrated jobs find a cold cache and TLB on the new CPU: the price of affinity.

Multiprocessor Scheduling

Processor Affinity, NUMA and Heterogeneous Cores

  • Processor affinity: keeping a thread on the CPU where its cache and TLB are warm. Soft: the scheduler tries but does not guarantee it. Hard: an allowed CPU set (sched_setaffinity(), taskset -c 0-3).
  • NUMA: running a thread on the node where its memory is; Linux automatic NUMA balancing moves pages and tasks closer together.
  • Load balancing and affinity conflict: migration restores balance but breaks cache warmth and locality.
Heterogeneous multiprocessing: ARM big.LITTLE / DynamIQ, P/E cores since Intel's 12th generation (Thread Director gives hardware hints), Apple M series. Linux EAS (Energy Aware Scheduling) places work on the core that meets the performance target with the least energy; background jobs go to efficiency cores.

Real-Time Scheduling

Real-Time Systems and Latency

Hard real time

Missing a deadline means system failure: ABS brakes, airbags, industrial robot control, flight control.

Soft real time

Critical tasks get preference but there is no guarantee; a miss lowers quality: video streaming, VoIP, games, audio playback.

  • Conflicts: preempting any work running in the kernel, and the release of resources held by low-priority processes. Hence a preemptive, priority-based kernel is needed; for hard guarantees, admission control as well.
  • Algorithms can be static (priorities computed in advance, e.g. RM) or dynamic (decisions at run time, e.g. EDF).

Real-Time Scheduling

Periodic Tasks and Rate-Monotonic (RM) Scheduling

  • Periodic task: 0 ≤ t ≤ d ≤ p; utilization U = t / p.
  • Rate-monotonic (RM): static priority = 1 / p; a shorter period means higher priority. It is optimal among static-priority algorithms.
  • Liu–Layland bound: if ΣU ≤ n(21/n − 1), RM meets every deadline. n = 1: 1 · n = 2: ≈ 0.828 · n = 3: ≈ 0.780 · n → ∞: ln 2 ≈ 0.693. A sufficient condition, not a necessary one.

Example: U = 20/50 + 35/100 = 0.40 + 0.35 = 0.75 ≤ 0.828 → schedulable with RM. Recomputed from Silberschatz Figure 5.21.

Real-Time Scheduling

RM and EDF Step by Step

U = 25/50 + 35/80 = 0.5 + 0.4375 = 0.94 > 0.828: no guarantee for RM. RM: P1 (shorter period) first, 0–25; P2 25–50.

t = 50: P1's next job arrives and, with its higher static priority, preempts P2. P2 runs 5 more ms at 75–80 but time is up: deadline missed.

EDF: the deadline sets the priority. At t = 50 P1's deadline is 100 and P2's is 80 → P2 continues and finishes at 60.

At t = 80 P2's next job has deadline 160 and P1's is 100 → P1 runs until 85. At 100, P1 (150) goes first again. Every deadline is met.

For EDF the condition is ΣU ≤ 1 (preemptive, independent tasks, d = p): 0.94 ≤ 1, and there is no miss over the 400 ms hyperperiod. The price: dynamic priorities and unpredictable losses under overload.

Proportional-share scheduling: T shares in total are allocated; an application with N shares gets N/T of the CPU, and admission control rejects requests that exceed the total. Linux SCHED_DEADLINE (3.14+) combines EDF with CBS bandwidth protection.

Real-Time Scheduling · Step through the code

The Liu–Layland Test: Code Trace

int rm_test(Task g[], int n) {
  double U = 0;
  for (int i = 0; i < n; i++)
    U += (double) g[i].t / g[i].p;
  double bound = n * (pow(2, 1.0/n) - 1);
  if (U <= bound) return 1; /* enough */
  if (U <= 1.0) return 0;   /* unknown */
  return -1;            /* impossible */
}

Tasks: T1(p=20, t=5), T2(p=50, t=10), T3(p=100, t=30). The total utilization U starts at zero.

T1: 5 / 20 = 0.25 is added → U = 0.25.

T2: 10 / 50 = 0.2 is added → U = 0.45.

T3: 30 / 100 = 0.3 is added → U = 0.75.

bound = 3(21/3 − 1) = 0.7798; U = 0.75 ≤ bound → 1: RM meets every deadline.

The second call, on the set from the RM and EDF example: P1(p=50, t=25), P2(p=80, t=35).

P1: 25 / 50 = 0.5 is added → U = 0.5.

P2: 35 / 80 = 0.4375 is added → U = 0.9375.

bound = 0.8284; U = 0.9375 exceeds the bound but is ≤ 1 → 0: the test cannot decide. On this set RM really does miss a deadline, while EDF meets them all.

The test is a sufficient condition: if it returns 1, RM certainly works; if it returns 0, a schedule must be drawn to decide (e.g. from 0 to the longest period).

Real-Time Scheduling · Step through the code

The EDF Scheduler: Code Trace

/* A(P=3,C=1) B(P=4,C=1) C(P=6,C=2) */
for (int t = 0; t < 12; t++) {
    for (int i = 0; i < n; i++)
        if (t % P[i] == 0) {      /* new job */
            left[i] = C[i];
            due[i] = t + P[i];
        }
    int s = -1;
    for (int i = 0; i < n; i++)
        if (left[i] > 0 &&
            (s < 0 || due[i] < due[s]))
            s = i;
    if (s >= 0) left[s]--;     /* 1 ms */
}

Three periodic jobs, U = 1/3 + 1/4 + 2/6 = 0.917 ≤ 1. The common period is 12 ms; a decision is made every millisecond. Arrows mark job arrivals; the due array holds each job's deadline.

t = 0: A, B, C start a new period. Ready: A, B, C; deadlines A 3, B 4, C 6 → the earliest, A, runs.

Ready: B, C; deadlines B 4, C 6 → the earliest, B, runs.

t = 2–3: C → A. Arriving: A at t = 3. Every millisecond the ready job with the earliest deadline is chosen.

t = 4: B starts a new period. Ready: B, C; deadlines B 8, C 6 → the earliest, C, runs.

Ready: B; deadline 8 → the earliest, B, runs.

t = 6–7: A → C. Arriving: A and C at t = 6. Every millisecond the ready job with the earliest deadline is chosen.

t = 8: B starts a new period. Ready: B, C; deadlines B 12, C 12 → the earliest, B, runs.

t = 9: A starts a new period. Ready: A, C; deadlines A 12, C 12 → the earliest, A, runs.

t = 10–11: C → idle. 11 ms of work in 12 ms: 1 ms idle (1 − 0.917). No job missed its deadline.

Operating-System Examples

Linux CFS: Virtual Runtime

  • Completely Fair Scheduler (2.6.23–6.5): instead of a fixed time slice, each task's virtual runtime (vruntime) is tracked; the smallest runs.
  • vruntime += Δ × 1024 / weight. The weight comes from nice: nice 0 → 1024, nice 5 → 335, nice −5 → 3121; each nice step is ≈ ×1.25 (≈ 10% CPU difference).
  • Example: CPU-bound A (nice 0) and B (nice 5): A gets 1024 / 1359 ≈ 75%, B ≈ 25%. When B runs 10 ms, its vruntime grows by 10 × 1024 / 335 ≈ 30.6 ms.
  • A sleeping I/O-bound task's vruntime grows little; when it wakes it goes straight to the front (though tasks that fell behind get only a bounded advantage).
  • The tree: insertion O(log n), the leftmost is cached → selection O(1).

Operating-System Examples · Step through the code

CFS: vruntime Code Trace

#define DELTA 3000  /* 3 ms, in µs */
/* nice 0 → 1024, nice 5 → 335 */
void tick(void) {
  Task *g = leftmost();   /* leftmost */
  run(g, DELTA);
  g->vruntime += DELTA * 1024 / g->weight;
  tree_insert(g);     /* re-sort */
}

A (nice 0, weight 1024) and B (nice 5, weight 335) are CPU-bound; both have vruntime 0. On a tie A, inserted first, is leftmost in the tree.

A's vruntime (0) is less than or equal to B's (0) → A runs; 3000 × 1024 / 1024 = 3000 is added.

Now B is leftmost (0 < 3,000) → B runs; 3000 × 1024 / 335 = 9170 is added: a low weight means fast “aging”.

A's vruntime (3,000) is less than or equal to B's (9,170) → A runs; 3000 × 1024 / 1024 = 3000 is added.

A is leftmost again (6,000 ≤ 9,170) → A runs, +3000.

A is leftmost again (9,000 ≤ 9,170) → A runs, +3000.

Now B is leftmost (9,170 < 12,000) → B runs; 3000 × 1024 / 335 = 9170 is added: a low weight means fast “aging”.

A's vruntime (12,000) is less than or equal to B's (18,340) → A runs; 3000 × 1024 / 1024 = 3000 is added.

A is leftmost again (15,000 ≤ 18,340) → A runs, +3000.

A is leftmost again (18,000 ≤ 18,340) → A runs, +3000.

In 9 ticks A ran 7 times and B twice; in the long run the share approaches the 1024 : 335 weight ratio (≈ 75% – 25%). There is no fixed time slice; the share comes from the weight.

A simplified tick handler: the real CFS measures time in ns and uses a “scheduler latency” instead of a slice; the selection rule is the same.

Operating-System Examples

EEVDF: The Successor to CFS

EEVDF (Earliest Eligible Virtual Deadline First, Stoica 1995; Linux 6.6+): a task is eligible if it is behind or exactly at its share (lag ≥ 0, i.e. v ≤ V); its virtual deadline is vd = v + slice / weight. Among eligible tasks the one with the earliest vd runs. Three tasks of equal weight:

v: A 12, B 12, C 15 → V = average = 13. C is ahead (v > V, negative lag): not eligible. A and B are eligible; vd: A 15, B 13 → B (short slice, early deadline).

B ran 1 ms → v = 13, new vd = 14. V = 13.33; eligible: A and B → earliest vd: B.

B advanced to 14; V = 13.67. Now only A is eligible (B and C are ahead of the average) → A runs its 3 ms slice.

A ran 3 ms → v = 15, new vd = 18. V = 14.67; only B (v = 14) is eligible → B.

V = 15: all three are eligible. vd: A 18, B 16, C 18 → B. B, asking for a short slice, runs more often but briefly; thanks to the eligibility rule its long-run share is still equal.

Two crisp criteria (eligibility and deadline) replace CFS's latency heuristics; a latency-sensitive task can ask for a short slice with sched_setattr() (6.12+). Weights come from nice, as in CFS.

Evaluation and Summary

Evaluating Algorithms

Deterministic modeling

Compute each algorithm's result for a given workload (the Gantt charts in this chapter). Exact and simple, but valid only for that input.

Queueing models

Averages from arrival and service distributions. Little's law: n = λ × W. If λ = 7 processes arrive per second and each stays W = 2 s on average, there are on average n = 14 processes in the system.

Simulation

A programmed model of the system is driven by randomly generated data or a trace recorded from a real system. Accurate, but can take hours.

Implementation

Try the algorithm in a real kernel. Today, with sched_ext, BPF schedulers can be loaded without rebuilding the kernel and A/B-tested in production. The catch: user behavior adapts to the algorithm too.

Exercises: Turnaround, Response and Fairness

  1. A, B, C all arrive at t = 0 and each needs 5 ms of CPU. What are the average turnaround and average response time under SJF and RR (q = 1 ms)?
  2. A (arrival 0, length 100), B (10, 10), C (10, 10). What are the average turnaround and response time under nonpreemptive SJF and STCF (SRTF)?
  3. Unfairness metric U = completion time of the first job to finish / that of the second. Two jobs with equal tickets each need L slices. What is U under RR? How does U change with L under lottery?
Answers
  1. SJF (here the same as FCFS): completions 5, 10, 15 → turnaround 10, response (0 + 5 + 10) / 3 = 5 ms. RR: A, B, C finish at 13, 14, 15 → turnaround 14, response (0 + 1 + 2) / 3 = 1 ms. With equal-length jobs RR is best in response and among the worst in turnaround.
  2. SJF: A 0–100, B 100–110, C 110–120 → turnaround (100 + 100 + 110) / 3 ≈ 103.3, response (0 + 90 + 100) / 3 ≈ 63.3 ms. STCF preempts A at t = 10: B 10–20, C 20–30, A 30–120 → turnaround (120 + 10 + 20) / 3 = 50, response (0 + 0 + 10) / 3 ≈ 3.3 ms.
  3. RR (and stride) alternate: one finishes at 2L − 1, the other at 2L → U = (2L − 1) / 2L (0.95 for L = 10). Under lottery the expected U is ≈ 0.82 for L = 10 and ≈ 0.94 for L = 100: it approaches 1 as jobs get longer, while for short jobs chance creates noticeable unfairness.
