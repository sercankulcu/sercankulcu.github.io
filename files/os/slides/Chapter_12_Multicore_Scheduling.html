Multicore Scheduling & Load Balancing Simulator

Explore how tasks are distributed across multiple CPU cores. Compare a global shared queue with per-core queues, and observe the effects of processor affinity and load balancing.

Each core runs the task at the head of its queue for one tick and then puts it back at the tail (round robin, quantum = 1 tick). With per-core queues and load balancing enabled, one balancing pass runs at the start of every tick; Rebalance now runs an extra pass immediately. Changing the core count, queue model, or affinity rebuilds the queues from the preferred cores.

Migration (as counted here): a task runs on a different core than the one it ran on last time. It is counted exactly once, at the moment the task runs. Moving a queued task to another core's queue is logged as a move; it only becomes a migration if the task had already run somewhere else. Load imbalance = longest minus shortest per-core queue (always 0 with a shared queue).

Concept Guide

Shared queue: all idle cores pull work from one global ready queue. Balancing is simple, but the shared queue can become a synchronization bottleneck.

Per-core queues: each core maintains its own ready queue. This improves locality and scalability but may create uneven load.

Soft affinity: the scheduler prefers keeping a task on the core it last ran on (its cache is warm there) but may migrate it. In this simulator a shared-queue core first looks for a task that last ran on it, and load balancing prefers to move tasks that are not cache-warm on the busy core.

Hard affinity: the task is constrained to its preferred core; it never runs anywhere else and load balancing cannot move it.

Load balancing: moves queued tasks from the busiest core's queue to the least busy one while their lengths differ by more than one.

If you reduce the core count, a preference for a core that no longer exists is shown clamped to the highest available core; the original preference is kept and comes back when you add cores again. This is a conceptual scheduler model. Real kernels consider priorities, NUMA topology, cache hierarchy, interrupts, power states, and many other factors.
