Introduction

Why a File System?

  • Three requirements: very large data (it won't fit in an address space), persistence (it outlives the process), and concurrent access (many processes use the same data).
  • A disk offers only numbered blocks: "read / write block k". The file system builds the file and directory abstractions on top.
  • A file is a logical unit, much like an address space in memory; processes create files, and the OS manages naming, structure, access, protection, and placement.
  • Two viewpoints:
    • User: name, type, directory, permissions, operations: what is visible?
    • Implementer: how are blocks allocated, free space tracked, and consistency kept after a crash?

The File Concept

File Structure

  • Maximum flexibility: the OS sees a file only as a sequence of bytes; anything can go in it, and the application decides the structure.
  • With records, the unit of reading/writing is a record; with a tree, requests like "get the record whose key is Pony" are supported directly.
  • Today structured access is implemented in libraries and databases (SQLite, B+ trees), not in the OS.

The File Concept

File Types

  • Regular files hold user data: text (lines of printable characters, ending in LF or CRLF) or binary (the program knows the structure).
  • Directories are system files that hold the structure of the file system.
  • Special files model I/O devices: character devices (printer, terminal) and block devices (disk).
  • "Everything is a file": the same open/read/write interface works for devices, pipes, and sockets. The letter in the table is the first character of ls -l output.

The File Concept

Open-File Tables

  • fd: an index into the kernel's per-process table; 0, 1, 2 are standard input/output/error, and open returns the lowest free number.
  • An open-file entry holds the position (offset) and access mode: fork and dup share the entry (a common position); a second open creates a new entry (a separate position).
  • The i-node is in memory once per file; further opens don't reread it from disk. The Windows equivalent is the handle table.

The File Concept · Step through the code

open, read, close, Step by Step

#include <fcntl.h>
#include <unistd.h>

int main(void) {
  char buf[4096];
  int fd = open("notes.txt", O_RDONLY);
  ssize_t n = read(fd, buf, sizeof buf);
  n = read(fd, buf, sizeof buf);
  n = read(fd, buf, sizeof buf);
  close(fd);
  return 0;
}

Initially only 0, 1, 2 are open (inherited from the shell: the terminal).

open: the path is resolved, i-node 4711 is brought into memory, and an open-file entry with position 0 is set up; the lowest free number, 3, is returned.

First read: the block(s) are read/cached, 4096 bytes are copied to buf, and the position becomes 4096.

Second read: only 1904 bytes are left in the file; a short read is not an error. Position 6000.

The third read returns 0: end of file (EOF). On an error it would return −1 and set errno.

close: fd 3 is freed; the entry's reference count drops to 0 → it is deleted, and the i-node's to 0 → it can be evicted from memory.

The File Concept · Step through the code

Copying a File: copy abc xyz

#define BUF 4096

int copy(const char *src, const char *dst) {
  char buf[BUF];
  int in  = open(src, O_RDONLY);
  int out = open(dst, O_WRONLY | O_CREAT
                      | O_TRUNC, 0644);
  ssize_t n;
  while ((n = read(in, buf, BUF)) > 0)
    write(out, buf, n);
  close(in);
  close(out);
  return 0;
}

in = 3; out = 4. O_TRUNC: if xyz exists its contents are erased; otherwise O_CREAT creates it with mode 0644.

First read: 4096 bytes into the buffer.

write writes the same 4096 bytes to xyz (to the page cache first; it reaches the disk later).

Second round: 8192 bytes copied.

The third read returns only 1808 bytes; write writes exactly n bytes (not BUF!).

read returns 0 → the loop ends; both descriptors are closed. In total 4 read + 3 write calls.

Real code must check every call for a −1 return and complete a short write in a loop; with O_CREAT the third argument (the mode) must be given.

The File Concept

Access Methods

  • Sequential: from start to end in order; rewinding instead of jumping. Tapes and cassettes worked this way; it is still the most common pattern for logs and streams.
  • Direct: the file is a sequence of numbered blocks/records; you start where you like (lseek, pread). Disks and SSDs support this.
  • Indexed: a small index (and if needed an index of the index) finds the right block by key; it is built on top of direct access.
  • With memory-mapped access (mmap) the file's pages are mapped into the address space; reads and writes are ordinary memory accesses.

Directories · Step by step

Directory Structures

Single-level: simple, but has naming and grouping problems.

Two-level: path = user/file. System programs need a separate "user" directory; the idea of a search path comes from here.

Tree (hierarchical): users create as many subdirectories as they like; every file has a single absolute path. The basis of all general-purpose systems today.

Acyclic graph (DAG): project.c appears under both ali/hw and ayşe/shared (a link). Problems: a traversal may count it twice, and deletion becomes ambiguous.

General graph: linking a directory creates a cycle; searches may never end, and unreachable cycles need garbage collection. That's why UNIX forbids hard links to directories.

Directories

Path Names

  • An absolute path starts at the root: /home/sercan/os/slides. Windows: C:\Users\sercan\os; a network share \\server\share.
  • A relative path starts at the working directory (pwd, cd): from /home/sercan/course, ../os/slides.
  • . is the current directory, .. the parent; at the root, .. leads back to the root.
  • The separator is / on UNIX and \ on Windows (the API accepts / too).

In historical UNIX, user directories were under /usr; today they are under /home (/Users on macOS), and /usr is for read-only system software.

Directories · Step by step

Path Resolution, Step by Step

Absolute path: the root directory's i-node is known (1 in this example; 2 in V7 UNIX and ext4). usr is looked up in the root directory → i-node 6.

i-node 6 is read: /usr is a directory whose contents are in block 132. (Permissions are checked here too: x on the directory is required.)

Block 132 is read and ast is looked up → i-node 26.

i-node 26: the contents of the /usr/ast directory are in block 406.

In block 406, mbox → i-node 60. Without caching that's 5 disk reads; that's why Linux keeps name → i-node mappings in the dentry cache.

The example is Tanenbaum's figure: /usr/ast/mbox is looked up. For a relative path the search starts at the working directory's i-node instead of the root.

Directories · Step by step

Hard and Symbolic Links

echo hello > a.txt: directory entry a.txt → i-node 812, link count 1.

ln a.txt b.txt (a hard link): the new entry points to the same i-node; link count 2. The two names are equal; neither is the "original".

ln -s a.txt c.txt (a symbolic link): a small file with its own i-node (905), whose contents are the target's path.

rm a.txt: link count 1 → the data stays, and b.txt works. c.txt dangles. (Tanenbaum: if owner C deletes the file, B's link remains but C still owns the i-node, so it counts against C's quota.)

Hard links: within one file system, not to directories, no extra cost. Symbolic links: can point to directories, files on other file systems, even network paths; each access needs extra path resolution, and the kernel limits loops (ELOOP). Windows: mklink /H, mklink, junctions.

Directories · Step by step

Mounting

Two separate file systems. /mnt/usb is an ordinary directory containing old.txt.

mount /dev/sdb1 /mnt/usb: the kernel adds an entry to the mount table; when path resolution reaches /mnt/usb it jumps to the USB's root i-node. The old contents are hidden, not deleted.

umount /mnt/usb: detached if no files are open (otherwise EBUSY); old.txt is visible again.

At boot the root file system is mounted, the others via /etc/fstab or systemd units; findmnt shows the tree. Windows gives each volume a drive letter (C:, D:), but NTFS can also mount on an empty folder. Crossing a mount point applies permissions and options such as nosuid, noexec, ro.

Protection

Access Rights: rwx

  • Order of checks: owner? → owner rights; if not, in the group? → group rights; otherwise, other. The first match is used.
  • setuid: the program runs with the identity of the file's owner (passwd). sticky on a directory: anyone can write, but only the owner can delete (/tmp: drwxrwxrwt). Example drwxrwx--T: sticky on, no x for others → a capital T.
  • Owner/group/other is coarse-grained; for named users and groups an access-control list (ACL) is used, shown as + in ls output.

Disk Layout

Disk Partitioning: MBR and GPT

  • A disk is divided into one or more partitions; each can hold a separate file system (or swap space, LVM, an encrypted container).
  • The partition table is at the end of the MBR: each entry holds a start and a length; the BIOS boots only from the partition marked active.
  • GPT is part of the UEFI standard; it is required for disks over 2 TiB and for Windows 11. The protective MBR stops old tools from treating the disk as "empty".

Disk Layout · Step by step

Booting: BIOS/MBR and UEFI/GPT

On power-up the hardware tests itself (POST). The BIOS runs in 16-bit real mode; UEFI in 32/64 bits, with its own drivers and file-system support.

The BIOS loads the disk's first sector (the MBR) into memory and runs it. UEFI instead reads the boot entries in NVRAM (efibootmgr); it looks for a file, not a sector.

The MBR code finds the active partition in the partition table and runs its first block (the boot block). UEFI loads the .efi program from the ESP (FAT32); the active flag isn't used.

In both layouts the boot loader then loads and runs the kernel; the only difference is how the boot loader is reached.

PCs have shipped with UEFI since around 2012; after 2020 the BIOS compatibility mode (CSM) was dropped from most new systems.

Disk Layout

File-System Layout

  • Superblock: the file system's identity (magic number), block size, block and i-node counts, free counters, mount state. It is the first structure read when mounting.
  • The boot block is the first block of the partition (the disk's first block is the MBR); space is reserved for it in every partition even if it is empty.
  • ext4 places related i-nodes and their data in the same group to reduce head movement (the cylinder-group idea of BSD FFS).

Disk Layout · Step-by-step calculation

From i-node Number to Disk Address

Example layout: 4 KiB blocks, 128 B i-nodes, i.e., 32 i-nodes per block. Block 0 is the superblock, 1–2 the bitmaps, 3–10 the i-node table. Question: where on disk is i-node 77 (numbered from 0)?

Byte offset from the start of the table: 77 × 128 = 9856 = 2 × 4096 + 1664. So block 2 of the table, byte 1664 within it (that block's 13th i-node).

Disk block = table start + 2 = 3 + 2 = block 5. That's why the superblock's "where is the i-node table" field is needed.

The disk reads sectors: byte address 5 × 4096 + 1664 = 22,144 → 22,144 / 512 = sector 43, byte 128 within it. A sector holds 4 i-nodes.

In ext4 numbers start at 1 and the table is split across block groups: group = (n − 1) div g, index = (n − 1) mod g. With g = 8192 i-nodes/group and 256 B i-nodes, i-node 20,000 → group 2, index 3615 → block 225 of the group's table, offset 3840.

Allocation Methods · Step by step

Allocation Methods: One File, Four Ways

Contiguous: 5 blocks side by side (9–13). The directory entry holds only the start and length.

Linked list: the blocks are scattered over the disk (9, 16, 1, 10, 25); each points to the next.

FAT: the same chain, but the pointers live in a table in memory, not in the blocks; the blocks are all data.

Indexed: all addresses are in a single index block (19); block i is accessed directly.

Allocation Methods · Step by step

Contiguous Allocation

Each file was placed in consecutive blocks; directory entry = (start, length).

Deleted files leave holes; free space is broken into pieces.

The new file fits no hole: the same external fragmentation as in memory management. Worse, the file's final size must be known up front.

Remedies: defragmentation/compaction (expensive), or splitting the file into several contiguous pieces, extents.

Pros

Simple; block i = start + i, so random access is easy; the whole file is read in one seek, back to back (the best HDD performance).

Cons

External fragmentation; files can't grow or must be moved. Suited to write-once media: CD-ROM/DVD (ISO 9660, UDF).

Allocation Methods · Step by step

Linked Allocation

The directory entry knows the first block (4 for A) (and the last one too in Silberschatz's layout). The first/last few bytes of each block hold the next block's number.

We want logical block 3: first physical 4 is read → next is 7.

Physical 7 is read → next 2.

Physical 2 is read → next 10.

Physical 10 = logical 3: 4 disk reads. Random access is O(n); on an HDD each may be a separate seek.

  • No external fragmentation, and files grow easily; internal fragmentation (in the last block) exists with every method.
  • The data per block isn't a power of two (4096 − 4 bytes); if one pointer is corrupted, the rest of the chain is lost.

Allocation Methods · Step by step

FAT: Allocation with a Table

A: 4 → 7 → 2 → 10 → 12; B: 6 → 3 → 11 → 14.

Entry 4 = 7.

Entry 7 = 2.

Entry 2 = 10.

Entry 10 = 12.

Entry 12 = EOF. The chain was followed in memory: no disk reads.

  • The pointers of the linked list are taken out of the blocks and moved into one file-allocation table (FAT); the blocks are left entirely for data.
  • Random access still follows the chain, but in memory: fast. Two copies of the table are kept on disk.
  • The problem: the table grows with the disk, and all of it must be in memory.
Example: a 200 GiB disk with 1 KiB blocks → 200 × 220 = 209,715,200 entries; at 4 B per entry → 800 MiB (600 MiB at 3 B). In FAT32 a 2 TiB volume with 32 KiB clusters → 67,108,864 entries = 256 MiB.

Allocation Methods · Step through the code

Following a FAT Chain: Code Trace

int find_block(int first, long off) {
  int b = first;
  long n = off / BLOCK;  /* block index */
  while (n > 0 && b != END) {
    b = fat[b];          /* follow chain */
    n--;
  }
  return b;          /* END: past EOF */
}

find_block(4, 3500): file A starts at block 4. 3500 / 1024 = 3: we want the file's block 3 (counting from 0), so the chain must advance 3 steps.

fat[4] = 7: next block 7; n = 2.

fat[7] = 2: next block 2; n = 1.

fat[2] = 10: next block 10; n = 0.

n = 0: the loop ends at disk block 10; byte 3500 is byte 3500 − 3·1024 = 428 of this block. All three steps were in memory: no disk reads.

find_block(6, 5000): file B has 4 blocks (at most 4096 bytes), but 5000 / 1024 = block 4 is requested.

fat[6] = 3: next block 3; n = 3.

fat[3] = 11: next block 11; n = 2.

fat[11] = 14: next block 14; n = 1.

fat[14] = END: the chain is over and the end of the file reached; n = 0.

At the fourth step b = END: the file has no block 4, and the offset lies past the file. read returns 0 bytes (end of file); write instead allocates a new block and links it into entry 14.

Allocation Methods

Indexed Allocation and the i-node

  • Each file's block addresses are gathered in an index block (on UNIX, the i-node): entry i is the address of block i. Fast random access, no external fragmentation.
  • An i-node is in memory only while the file is open: K open files × i-node size. Proportional to the number of open files, not to the disk size as with FAT.
  • An i-node has a fixed size; for very large files the last entries point to further index blocks (indirect blocks).
  • The cost: even a small file uses index space; a large file needs indirect-block reads (caching reduces this).

Allocation Methods

i-node Structure: Indirect Blocks

The ext2/ext3 and classic UNIX (V7: 10 direct) structure. Small files use only the direct pointers and never allocate an indirect block; as a file grows, the tree deepens.

Allocation Methods · Step-by-step calculation

Maximum File Size

Assumptions: 4 KiB blocks = 4096 B, 4 B pointers → an indirect block holds 4096 / 4 = 1024 addresses; the i-node has 12 direct, 1 single, 1 double, 1 triple indirect pointer.

Direct: 12 × 4 KiB = 48 KiB (49,152 B) · Single indirect: 1024 × 4 KiB = 4 MiB

The first 12 blocks come straight from the i-node; the next 1024 from one index block.

Double indirect: 1024² × 4 KiB = 1,048,576 blocks = 4 GiB

Each of 1024 index blocks points to 1024 data blocks.

Triple indirect: 1024³ × 4 KiB = 1,073,741,824 blocks = 4 TiB

One more level: ×1024.

Total: 12 + 1024 + 1024² + 1024³ = 1,074,791,436 blocks × 4096 = 4,402,345,721,856 B ≈ 4.004 TiB

Nearly all of it comes from the triple indirect block.

Tanenbaum's example (1 KiB blocks, 256 addresses, 10 direct): 16,843,018 blocks ≈ 16 GiB. ext2/ext3 with 4 KiB blocks actually stop at 2 TiB (32-bit counter × 512 B); ext4 extents reach 16 TiB.

Allocation Methods · Step by step

From Offset to Disk Block

40,000 / 4096 = 9 → below 12: direct pointer 9. One read.

1,000,000 / 4096 = 244; 244 − 12 = 232 < 1024 → entry 232 of the single indirect block. 2 reads.

5,000,000 / 4096 = 1220; 1220 − 12 − 1024 = 184 < 1024² → double indirect: outer index 184 div 1024 = 0, inner index 184. 3 reads.

6 GB / 4096 = 1,464,843; minus 12 + 1024 + 1024² leaves 415,231 → triple indirect: 0, 405, 511. 4 reads; the cache holds the first levels.

Allocation Methods

ext4: Extents

  • An extent = (logical start, length, physical start): a run of contiguous blocks described by one record. 48-bit physical addresses → 1 EiB volumes; files up to 16 TiB.
  • Four extents fit in the i-node; if more are needed, the entries point to index nodes of an extent tree (depth > 0).
  • Delayed allocation and the multiblock allocator choose large contiguous areas when writing data to disk. XFS, Btrfs, NTFS (run lists), and APFS use extents too.

Allocation Methods

NTFS: The Master File Table (MFT)

  • In NTFS everything is a file, including the MFT itself (record 0). Every file is at least one 1 KiB record whose contents are a list of attributes.
  • Large data is kept as a run list (extents); directories are B+ trees ($INDEX_ROOT, $INDEX_ALLOCATION). $LogFile is the metadata journal.
  • Extra features: hard links, reparse points, alternate data streams (ADS), compression, EFS encryption, quotas. Servers also have ReFS (CoW, checksums).

Implementing Directories

Directory Entries and Long Names

To locate a directory it suffices to know the first block's address (contiguous), the first block's number (linked list/FAT), or the i-node number (UNIX). With long names, fixed entries like (a)/(b) waste space; (c) leaves holes on deletion and a name may cross a page boundary; (d) requires managing the heap.

Implementing Directories · Step by step

Directory Lookup: List, Hash, Tree

Linear list: simple, but lookup is O(n). Inserting first checks that the name doesn't exist; deleting marks the entry free or moves the last entry into it.

Hash table: the name's hash selects the bucket; lookup is O(1) on average.

Collisions are resolved by chaining. A fixed number of buckets is a problem for a growing directory; that's why modern systems use trees.

For large directories ext4 uses an htree ordered by name hash; NTFS, XFS, and Btrfs use B+ trees: sorted listing and O(log n) lookup together. Linux also keeps recently used name → i-node mappings in the dentry cache.

Free-Space Management

Choosing the Block Size

  • Model (Tanenbaum): all files are 4 KiB; average seek 5 ms, rotation 8.33 ms, a 1 MB track. Time = 5 + 4,165 + (b / 1 MB) × 8.33 ms. Computed with Python.
  • Larger blocks → better data rate, worse space utilization; smaller blocks the opposite.
  • Measurements show that most files are small while most space is taken by a few large files. Today's default is 4 KiB (the page size); large files are served by extents and cluster options.

Free-Space Management · Step by step

Free-Space Management: Four Methods

Example disk: 32 blocks, 15 free (the Silberschatz example).

Bitmap: 1 bit per block. Fixed and small; finding contiguous free blocks is easy. It must be kept in memory.

Linked list: free blocks are linked together. Taking one free block is cheap; finding many contiguous blocks is expensive.

Grouping: the first free block holds the addresses of the next n−1 free blocks and of the next group block (UNIX's free-list blocks).

Counting: (start, length) pairs; the extent idea applied to free space. XFS keeps these in two B+ trees.

Free-Space Management · Step through the code

Allocating a Block with a Bitmap: Code Trace

int alloc_block(int hint) {
  for (int k = 0; k < N; k++) {
    int i = (hint + k) % N;
    if (bitmap[i] == 0) {  /* free? */
      bitmap[i] = 1;
      return i;
    }
  }
  return -1;               /* disk full */
}

The file ends at block 3 and needs 3 more blocks. For locality the search starts right after the last block: alloc_block(4).

k = 0: i = (4 + 0) mod 16 = 4; bit 1, block in use. Move on.

k = 1: i = (4 + 1) mod 16 = 5; bit 1, block in use. Move on.

bitmap[6] = 0: free. The bit is set and block 6 is returned.

alloc_block(7): i = 7, bitmap[7] = 0: free. The bit is set and block 7 is returned. Consecutive blocks reduce head movement on sequential reads.

alloc_block(8): k = 0, i = 8; bit 1, in use.

k = 1: i = (8 + 1) mod 16 = 9; bit 1, block in use. Move on.

k = 2: i = (8 + 2) mod 16 = 10; bit 1, block in use. Move on.

bitmap[11] = 0: free. The bit is set and block 11 is returned. The file got blocks 6, 7, 11: not contiguous, but close together.

Free-Space Management

Disk Quotas

  • Every open-file entry points to its owner's quota record; on every new block or i-node allocation the counters go up and are compared with the limits.
  • The soft limit may be exceeded, but a warning is given and a grace period (e.g., 7 days) starts; when it expires, or the hard limit is reached, writes fail with EDQUOT.
  • Today: Linux quota tools (ext4, XFS project quotas), NTFS volume quotas, ZFS dataset and Btrfs subvolume (qgroup) quotas.

Performance · Step by step

How Many I/Os Does Creating a File Take?

The cache is empty; the root's i-node location is known from the superblock. The path is resolved component by component: for each directory, its i-node + data block, and finally the file's i-node. 5 reads; more for longer paths.

Each read finds the block address from the i-node, reads the block, and writes the access time. The noatime/relatime mount options usually eliminate that write.

Creating is costlier: a free i-node is chosen from the bitmap, the new i-node initialized, an entry added to the directory, and the directory's i-node (size, times) updated. 10 I/Os.

Every write that needs a new block: allocate a block from the data bitmap (read + write), write the data, write the address and size into the i-node. 5 I/Os, only 1 of them actual data.

Creating a file and writing 12 KiB without a cache costs 25 I/Os. That's why the buffer cache and delayed writes are indispensable; the order of writes also determines crash consistency.

Assumption: a simple file system with i-nodes and bitmaps, single-block directories, no cache. In real systems the dentry and i-node caches remove most reads; journaling and delayed writes also change the number and order of writes.

Performance · Step through the code

The Buffer Cache: Code Trace

Buffer *bread(int blk) {
  Buffer *t = hash_find(blk);
  if (t != NULL) {         /* hit */
    lru_to_tail(t);
    return t;
  }
  t = lru_head();          /* oldest */
  if (t->dirty)
    disk_write(t);       /* write back */
  t->blk = blk; t->dirty = 0;
  disk_read(t);            /* miss: I/O */
  lru_to_tail(t);
  return t;
}

The cache holds 3 buffers: blocks 5, 9, 2 (9 is dirty: modified but not written to disk). Requests in order: 9, 7, 2, 4.

bread(9): found in the hash table, a hit. No disk I/O.

Block 9 moves to the tail of the list (newest) and is returned. Now block 5 is the oldest.

bread(7): not in the cache, a miss. To make room, the buffer at the head of the LRU list (block 5) is chosen.

Block 5 is clean: its copy on disk is current, so no write-back is needed.

The buffer is reused for block 7; the contents are read from disk (1 read) and it is added to the tail of the list.

bread(2): a hit; block 2 moves to newest. Dirty block 9 is now at the head of the list.

bread(4): a miss. The oldest buffer holds block 9.

Block 9 is dirty: so the change isn't lost, the buffer is written to disk before reuse (1 write). This doubles the cost of the miss.

Block 4 is read. 2 hits out of 4 requests; 2 reads and 1 write in total. Without a cache it would take 4 reads plus a separate write for block 9.

Performance · Step by step

The Page Cache and the Unified Buffer Cache

Not unified: mmap data is in the page cache, read/write data in the buffer cache, and it's copied between them (double caching): wasted memory and consistency problems.

Unified buffer cache: file pages live in one place, and both paths see the same pages. The page cache since Linux 2.4, the Windows cache manager, and Solaris all work this way.

The page cache shares the page-replacement algorithms of virtual memory. The exception: ZFS keeps its own ARC cache. O_DIRECT lets databases bypass the cache.

Performance

Read-Ahead, Placement, and Defragmentation

  • Read-ahead: when block k is requested, block k+1 is read too (if not cached). It helps only with sequential access; a "sequential?" hint is tracked per file. Linux adapts the window (default 128 KiB); applications give hints with posix_fadvise.
  • Reducing arm motion: place blocks that will be read consecutively close together; a bitmap makes it easy to find contiguous blocks. Allocate blocks two at a time (an old suggestion), or, as today, use extents, delayed allocation, and a multiblock allocator.
  • Defragmentation: over time files get fragmented. Windows has "Defragment and Optimize Drives"; Linux has it too: e4defrag, xfs_fsr, btrfs filesystem defragment. ext4's allocation policy reduces the need.
  • An SSD has no seek time: defragmentation just means unnecessary writes (wear); Windows sends TRIM instead of defragmenting an SSD.

Performance

SSD Caveats: FTL and TRIM

  • A flash page can't be updated in place; the SSD's FTL redirects every write to a new page, so internally an SSD is log-structured.
  • When the file system deletes a file it only marks the blocks free in its own bitmap. Unless it tells the SSD with TRIM (NVMe: Deallocate), the SSD thinks those pages are valid and copies them needlessly during garbage collection.
  • On Linux the notification is sent either in batches by the weekly fstrim.timer or on every delete with the discard mount option.

Backup Strategies

  • Two goals: recovery from disaster (disk failure, fire, ransomware) and recovery from carelessness (an accidentally deleted file).
  • Full + incremental: e.g., a full dump monthly, and daily only what changed since the last dump. Restore: the latest full dump onto an empty file system (directories first, then files), then the incrementals in order.
  • Temporary and special files (/dev, /proc, /tmp) aren't backed up. For a consistent backup while the system is in use, take a snapshot (LVM, ZFS/Btrfs, Windows VSS).
  • The 3-2-1 rule: 3 copies, on 2 different media, with 1 copy elsewhere (offline or immutable). Tape is still used for archiving: an LTO-10 cartridge holds up to 40 TB uncompressed.

Consistency and Recovery · Step by step

The Logical Dump Algorithm

Squares are directories, circles files; the numbers are i-node numbers. Orange: modified since the last dump (3, 6, 10).

Phase 1: walk the tree from the root, marking every modified file and all directories.

Phase 2: unmark directories with nothing modified beneath them: 7 (it contains only the unmodified 9).

Phase 3: dump the marked directories in i-node order (1, 2, 4, 8), even if unmodified, so paths can be rebuilt.

Phase 4: dump the marked files (3, 6, 10). On restore, directories are written first, then files.

More details: the free list isn't dumped but rebuilt on restore; a file with several hard links must be dumped only once; holes in sparse files and FIFO/device files need special handling.

Consistency and Recovery · Step by step

Consistency Checking: fsck

(a) Consistent: fsck reads all i-nodes and the free list/bitmap, keeping two counters per block.

(b) Missing block: harmless but wastes space; it goes on the free list.

(c) Duplicate block in the free list: the same block could be handed out twice; the list is rebuilt. (This can't happen with a bitmap.)

(d) Duplicate data block: the worst case; the block is copied so each file gets its own, and the user is informed.

  • File consistency: walk all directories from the root, counting how often each i-node is seen, and compare with the i-node's link count. A link count that's too high just wastes space; one that's too low is dangerous (the file would be deleted early) → it is fixed. Orphaned i-nodes go into lost+found.
  • The Windows equivalent is chkdsk (called scandisk in Windows 9x). A full scan of a terabyte disk takes hours; that's why journaling and CoW were born.

Consistency and Recovery

Crashes and Atomicity: Why a Journal?

  • One file operation changes several blocks; disks make only single-sector writes atomic. A crash in between leaves the structure inconsistent.
  • The family of solutions: (1) repair afterward: fsck; (2) write the intent first: journaling; (3) never overwrite: CoW and LFS; (4) order the writes: BSD soft updates.
  • Idempotence: the operations in the journal must give the same result however many times they are replayed. "Mark block n free" is idempotent; "append n to the free list" is not (it could be added twice).

Consistency and Recovery · Step by step

Journaling: Write to the Log First

1. Data: the block Db added to the file is written to its final location first (ordered mode, ext4's default).

2. Journal write: the transaction begin TxB and the metadata blocks to change (i-node I, bitmap B) are written to the journal sequentially.

3. Commit: once the earlier writes reach the disk (barrier/FLUSH), TxE is written. Once TxE is on disk, the transaction is committed.

4. Checkpoint: I and B are written to their final locations; if these writes are interrupted, they can be repeated from the journal.

5. Free: the transaction is marked complete in the journal superblock; the journal is reused like a circular buffer.

Recovery: at boot the journal is scanned; transactions with a TxE are replayed from the start (redo, idempotent), the others discarded. No fsck needed; it takes seconds.

Modes: journal (data journaled too: safest, slowest), ordered, writeback (no data ordering). Journaling file systems: ext3/ext4 (jbd2), XFS, NTFS ($LogFile), JFS. At Apple, HFS+ gave way to the CoW-based APFS.

Consistency and Recovery · Step through the code

Recovering from the Journal: Code Trace

void recover(Rec g[], int n) {
  int i = 0;
  while (i < n && g[i].type == TXB) {
    int j = i + 1;
    while (j < n && g[j].type == BLOCK)
      j++;
    if (j == n || g[j].type != TXE)
      break;              /* uncommitted: drop */
    for (int k = i + 1; k < j; k++)
      write(g[k].dest, g[k].data);
    i = j + 1;          /* next */
  }
}

The system crashed while transaction 3 was being written. The journal holds three transaction headers; the blocks in their final locations are still old (v0). At boot, recover runs.

g[0] is a TxB: transaction 1 begins.

At j = 3, TxE 1 is found: the transaction is committed and its blocks can be replayed.

I7's v1 copy is written to its final location. Even if it was written before the crash, that's fine: rewriting is idempotent.

B's v1 copy is written to its final location.

g[4] is a TxB: transaction 2 begins.

At j = 7, TxE 2 is found: the transaction is committed and its blocks can be replayed.

I9's v2 copy is written to its final location.

D40's v2 copy is written to its final location.

g[8] is a TxB: transaction 3 begins.

Skipping the block records, j = 10 = n: the journal ended but there's no TxE. Transaction 3 wasn't committed: it is discarded, and I7's v3 is never written.

Result: transactions 1 and 2 were applied in full, transaction 3 as if it never happened. The file system is consistent; no whole-disk fsck is needed.

Consistency and Recovery · Step by step

Copy-on-Write (CoW): ZFS, Btrfs, APFS

The file system is a tree of blocks: superblock (the uberblock in ZFS) → root → internal nodes → data.

L3 is to change: it is not written in place; a new copy, L3', goes to a free location. The old L3 is still intact.

The parents pointing to L3' are copied too: I2', root R'. Unchanged subtrees (I1, L4) are shared.

One atomic write: the superblock points to R'. After a crash either the old or the new tree is visible, never an intermediate state; no journal is needed.

If the old root is kept, a snapshot is free. ZFS/Btrfs keep a checksum in every pointer: silent corruption is caught on read and repaired from a mirror (scrub).

ZFS (Sun 2005, now OpenZFS), Btrfs (Linux), APFS (Apple, 2017), ReFS (Windows Server). The cost: fragmentation and write amplification on random overwrites; CoW can be turned off for database files.

Consistency and Recovery · Step by step

The Log-Structured File System (LFS)

Writes are buffered in memory: data blocks, modified i-nodes, and pieces of the i-node map (imap).

When the buffer fills, everything is written sequentially to the end of the log as one segment (e.g., 1–2 MiB). i-nodes have no fixed location; the imap finds them, and the checkpoint region (CR) points to the latest imap.

When A's block changes, the new version goes to a new segment; the old D(A,0), I(A), and imap in segment 1 become dead.

The cleaner: it reads segments with few live blocks, compacts the live ones into a new segment, and frees the old. Cleaning cost under load is LFS's weak spot.

Rosenblum and Ousterhout, Sprite LFS (1991). Designed on the assumption that reads are served from a large cache; it brings write bandwidth close to the disk's sequential speed. The idea lives on in F2FS (Android), NILFS2, NetApp WAFL, ZFS/Btrfs CoW, and SSD FTLs.

VFS and Networking · Step by step

The Virtual File System (VFS)

Registration: a file system registers with the VFS at boot or when its module loads, handing over a table of the functions the VFS will call.

Mount: the VFS asks that file system to build a superblock object, which carries the operations table (s_op).

open: the path is resolved through dentries; the concrete system fills a VFS i-node (v-node) with its i-node data; a file object is created and added to the fd table.

read: the VFS just calls the file->f_op->read_iter function pointer; for an ext4 file ext4's function runs, for an NFS file an RPC goes over the network. The application sees no difference.

The VFS's purpose is to offer one interface to different file systems at the same time (several systems on one disk are already possible via partitioning). Its overhead is one indirect call; the performance loss is small. The Windows counterpart is the I/O manager and file-system drivers.

VFS and Networking

The Network File System (NFS)

  • A remote directory is mounted into the local tree, and applications use it like local files. Sun designed it for SunOS in 1984, and it became an open standard.
  • Machine and architecture independence come from RPC and XDR. NFSv3 is stateless (UDP or TCP); NFSv4 is stateful, TCP only, on a single port (2049), with Kerberos security, ACLs, locking, and delegation; v4.1 adds pNFS.
  • The Windows-world counterpart is SMB 3 (encryption, multichannel). NFS originally ran over UDP/IP; today TCP is preferred; the only requirement is an IP network.
