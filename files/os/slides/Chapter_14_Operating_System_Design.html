Introduction

Why Is Designing an OS Hard?

1 · Sheer size

Linux is ≈ 40 million lines; no one can grasp the whole.

2 · Concurrency

Devices, interrupts and threads all at once: races, deadlocks.

3 · Hostile users

Some want to break the system or steal data; every input is suspect.

4 · Sharing despite isolation

Users must be kept apart, yet able to share information with whom they choose.

5 · Long life

Lives 20–30 years; future hardware and applications must be anticipated.

6 · Generality

No one knows how it will be used: from phones to supercomputers.

7 · Portability

Different processors and platforms: x86-64, ARM64, RISC-V…

8 · Backward compatibility

Old programs must keep running; new ideas are bound by old constraints.

Tanenbaum's eight factors. The need for long-term maintenance follows naturally from items 5 and 8.

Introduction · Step by step

Goals of an Operating System

1. Define abstractions: concepts such as processes, address spaces, files and sockets hide the complexity of the hardware. Finding the right abstraction is the hardest part of design.

2. Provide primitive operations: the operations on those abstractions, i.e. system calls. E.g. open/read/write/close for files.

3. Ensure isolation: users and processes must not interfere with each other, yet controlled sharing (file permissions, shared memory) must be possible.

4. Manage the hardware: interrupts, timers, the MMU, device controllers; most low-level work happens in this layer.

Interface Design

Guiding Principles for Interface Design

1 · Simplicity

“Perfection is reached not when there is no longer anything to add, but when there is no longer anything to take away.” (A. de Saint-Exupéry). A few well-chosen concepts are easy to learn, implement and verify.

2 · Completeness

“Everything should be as simple as possible, but no simpler.” (attributed to Einstein). The interface must let users do everything they need. Much work with few mechanisms: the MINIX 3 kernel offers only a few communication primitives (send, receive, sendrec, notify).

3 · Efficiency

If a feature or system call cannot be implemented efficiently, it is probably not worth having. Programmers should be able to guess a call's rough cost: lseek is cheap, read may be expensive.

Rule of thumb: each system call should do one thing well. Adding features is easy; removing them is nearly impossible (backward compatibility).

Interface Design

“Small Is Beautiful”

  • Small is beautiful: a few general calls beat many special ones.
  • seL4's kernel is about 10,000 lines and formally verified; that is impossible for a kernel of millions of lines.
  • Linux gains a few calls every year (e.g. io_uring_*, landlock_*, mseal).
  • On Windows the documented interface is the Win32 API; kernel calls change from release to release.

Interface Design

User-Interface Paradigms

Command line (CLI)

Shells, text commands, pipes. Still indispensable for automation and remote administration.

WIMP / GUI

Windows, Icons, Menus, Pointer. Mouse buttons should mean the same thing in every application.

Touch and mobile

Gestures (swipe, pinch), full-screen apps, a notification center.

Voice, chat and agents

Voice assistants and natural-language interfaces; a new entry point into OS services.

The user interface is often not part of the kernel, but the paradigm shapes the whole system design: a GUI needs an event-driven execution model, a fast window system and a consistent application framework. What matters is consistency: the same action should give the same result everywhere.

Interface Design

Execution Paradigms

(a) Algorithmic code

int main(void)
{
    int x, y;
    init();
    do_something();
    read(fd, &x, sizeof x);
    do_something_else();
    write(fd, &y, sizeof y);
    keep_going();
    exit(0);
}

The program sets the flow and calls the OS for services. Compilers, sorters, batch jobs.

(b) Event-driven code

int main(void)
{
    msg_t msg;
    init();
    while (get_message(&msg)) {
        switch (msg.type) {
        case 1: ... ; break;
        case 2: ... ; break;
        case 3: ... ; break;
        }
    }
}

External events (keys, clicks, packets, timers) set the flow. GUIs, servers, microkernel servers.

The choice of execution paradigm shapes the system calls too: the algorithmic model wants a blocking read; the event-driven model wants a “give me the next event” call (get_message, epoll_wait, io_uring_enter).

Interface Design · Step through the code

How Does an Event Loop Work?

int main(void) {
    msg_t m;
    init();
    while (get_message(&m)) {
        switch (m.type) {
        case KEY:   on_key(&m);   break;
        case CLICK: on_click(&m); break;
        case TIMER: on_timer(&m); break;
        }
    }
    return 0;
}

The program starts; init() sets up the window and resources. The queue is empty.

The user clicks, presses a key, and a timer fires. The OS/window system collects the events and appends them to the application's queue.

get_message returns the CLICK at the head of the queue; the switch routes it to on_click.

The handler finishes quickly and the loop goes around. The next event is KEY: on_key runs.

The TIMER event goes to on_timer (e.g. blinking the cursor). A long-running handler freezes the whole UI; long jobs go to a separate thread.

The queue is empty: get_message blocks, the process sleeps and uses no CPU. A new event wakes it.

The user closes the window: a QUIT event arrives in the queue.

For QUIT get_message returns 0, the loop ends and the program exits. nginx/Node.js (epoll) and microkernel servers use the same pattern.

Interface Design

Data Paradigms

  • A common data paradigm lets the same tools (cat, dd, redirection) work on every resource: cat /proc/loadavg.
  • The price: some devices do not fit the file model, and everything piles up behind “escape hatches” like ioctl.

Interface Design

The System-Call Interface

  • Separation: few, general calls, with convenience functions in the library. Adding a convenience never changes the kernel.
  • Independent components: UNIX splits process creation in two: fork + execve. Redirection, chdir and so on can happen in between.
  • On Windows, CreateProcess takes 10 parameters in one call: powerful but complex.
  • The modern trend: posix_spawn (avoids the cost of fork) and batched-call interfaces (io_uring: many requests in one crossing).

System Structure · Step by step

Layered Systems: A Seven-Layer Design

The seven-layer design Tanenbaum proposes. Layer 1 hides hardware differences; each upper layer works only with the abstractions the one below offers.

The application calls read; the trap arrives at layer 7. Parameters are checked here (is the fd valid, is the buffer in user space?).

The file system (ext4) maps the file offset to a disk block. If the block is not cached, it is requested from the layers below.

Virtual memory allocates the page-cache frame for the data and validates the mapping of the user buffer.

The NVMe driver writes the read command into the device's queue.

The calling thread blocks until the I/O completes; the scheduler runs another thread.

When done, the device raises an interrupt; layer 2 handles it and makes the sleeping thread ready. The result travels back up through the layers.

The layer order follows from dependencies: virtual memory writes pages to disk, so it sits above the drivers; the file system allocates page frames, so it sits above virtual memory. Layer 1, which hides the hardware, provides portability; the price is the cost of every layer crossing.

System Structure

Extensible Systems

  • The kernel provides the core functions; new components are added at run time as needs change.
  • Third parties can add features to the system; compatibility and security are the biggest issues.
  • A classic module has full privileges: one bug crashes the kernel. SPIN (1995) confined extensions with a safe language (Modula-3).
  • Today Linux has eBPF: small, verified programs for tracing, networking, security and, since 6.12, the scheduler (sched_ext).

System Structure

Kernel Threads

  • Created and managed by the kernel (kthread_create); they have no user address space and run only in kernel memory.
  • They are scheduled like ordinary threads and can block and sleep: long jobs that cannot be done in an interrupt handler are deferred here.
  • Context switches are cheap: the address space (page table) does not change.
  • Examples: deferred work (kworker), soft interrupts (ksoftirqd), page reclaim (kswapd), journal writes (jbd2).
  • They show up in square brackets in ps -ef output: [kswapd0].

User processes cannot create kernel threads; system calls can only hand work to threads the kernel already runs (e.g. the io_uring worker pool).

Design Principles · Step by step

Separating Mechanism and Policy

The kernel offers only a mechanism: “run the highest-priority ready thread”. Right now T3 (backup, priority 8) is chosen.

The database process knows its own threads best: it decides that queries matter and the backup can wait. That is a policy, handed down through a system call.

Without any change to kernel code, T2 is now chosen. The same mechanism with a different policy gives different behavior.

Another application applies another policy. sched_ext in Linux 6.12 goes a step further: the entire scheduling policy can be loaded as an eBPF program.

Other examples: paging (mechanism: MMU, frame allocation; policy: which page to evict), CPU frequency (mechanism: the cpufreq driver; policy: the schedutil/powersave governor), security (mechanism: LSM hooks; policy: SELinux rules).

Design Principles

Orthogonality

  • Orthogonality: the ability to combine separate concepts independently. Changing one does not affect another.
  • Linux clone: separate flags choose what is shared. Processes and threads are two ends of the same mechanism; containers are built with the CLONE_NEW* flags too.
  • Windows: a process is a resource container and a thread is the unit of scheduling; the two concepts are separate.
  • C has an example too: static (lifetime) is chosen independently of the type.

Design Principles · Step by step

Name Resolution Step by Step

The kernel receives open("/usr/ast/mbox"). The path is split into components; if nothing is cached, each component needs disk reads.

The root directory's i-node (i-node 1) is read, then the root directory's data (block 1). A linear search: usr → i-node 6. 2 reads.

i-node 6 for /usr is read, then the /usr directory (block 132). ast → i-node 26. 4 reads.

i-node 26 for /usr/ast is read, then directory block 406. mbox → i-node 60. 6 reads.

Finally the file's own i-node (60) is read. Just finding the file took 7 disk accesses: hence caching is essential.

Design Principles

Binding Time

Early binding

The link between a name and an object is fixed in advance. Simple and fast, but less flexible: the program runs only at a given address and must be recompiled when a library changes.

Late binding

The link is made at the last possible moment. More complex (extra indirection, run-time cost) but more flexible: pages can load anywhere, and the program is unchanged when a library is updated.

Binding time asks “at what moment is a name bound to a real object?” Operating systems generally choose late binding; virtual memory, for example, re-resolves a page's physical location on every access (with the TLB's help).

Design Principles · Step through the code

Static and Dynamic Structures

found = 0;
for (p = &proc_table[0];
     p < &proc_table[PROC_TABLE_SIZE];
     p++) {
    if (p->proc_pid == pid) {
        found = 1;
        break;
    }
}

A static process table: six entries, some free (pid 0). We look for pid 42. found is cleared.

The pointer starts at the head of the table. proc_table[0] has pid 1: no match.

p++ advances to the next structure (not the next byte). 314 ≠ 42.

Free entries (pid 0) are scanned one by one too: the price of linear search.

A match: found = 1, and break leaves the loop. In the worst case the whole table is scanned: O(n). For a small, fixed table this simple code is enough.

A static table is simple and needs no allocator, but when it fills no new process can be created (NPROC in old UNIX). A dynamic structure (linked list, hash table, Linux's xarray) is flexible, and lookups in a hash table or xarray are near O(1), but it brings an allocator, fragmentation and complex locking. A middle ground: tunable table sizes (/proc/sys/kernel/pid_max).

Design Principles

Top-Down and Bottom-Up Implementation

Top-down

System-call handlers are written first and the lower layers are left as stubs. The interface firms up early, but realistic testing is hard until the whole system exists.

Bottom-up

First the layer that hides the hardware, then interrupts, the timer, threads… Each layer is tested as it is finished. Tanenbaum recommends this route for implementation, while design should be thought out top-down.

Design Principles

Synchronous and Asynchronous Communication

  • Synchronous: easy to program, the flow reads sequentially; but a thread waits for each request.
  • In microkernels IPC is usually synchronous (L4, seL4): no buffering needed, very fast.
  • Asynchronous: one thread can drive thousands of requests; but races, error handling and buffering get harder.
  • Linux io_uring: submission (SQ) and completion (CQ) rings; requests can be submitted even without a system call.

Useful Techniques

Hiding the Hardware

Conditional compilation by CPU type

#include "config.h"
void init(void)
{
#if (CPU == X86_64)
    /* x86-64 init code */
#endif
#if (CPU == ARM64)
    /* ARM64 init code */
#endif
#if (CPU == RISCV64)
    /* RISC-V init code */
#endif
}

Conditional compilation by word length

#include "config.h"
#include <stdint.h>
#if (WORD_LENGTH == 32)
typedef int Register;
#elif (WORD_LENGTH == 64)
typedef long Register;
#else  /* today: portable */
typedef uintptr_t Register;
#endif
Register R0, R1, R2, R3;
Collecting hardware-dependent code in a few files is the key to portability: the HAL (Hardware Abstraction Layer) in Windows, the arch/x86, arch/arm64 and arch/riscv directories in Linux. Porting to a new processor means rewriting only that part. Use conditional compilation sparingly: #ifdefs scattered everywhere make code unreadable.

The code updates Tanenbaum's Pentium/UltraSPARC example.

Useful Techniques · Step by step

Indirection

The user presses the key to the right of U. The keyboard reports the key's position, not a character.

The keyboard sends scan code 0x17 (USB keyboards send a HID usage code, which the driver maps to a common code). With the US keymap it becomes i.

Only the table is swapped for Turkish Q: the same key now produces ı. Neither hardware nor application changed.

With the Turkish F keymap the same key gives n. One extra step (indirection) buys flexibility; the cost is a table lookup.

“All problems in computer science can be solved by another level of indirection.” (David Wheeler). In operating systems: virtual memory (page tables), file descriptors, symbolic links, i-nodes, device classes.

Useful Techniques

Reusability and Reentrancy

Reusability

Using the same code in different places: a single bitmap module can track free disk blocks, memory frames and PIDs. In Linux: the shared list.h, red-black trees, xarray.

Reentrancy

A piece of code must be able to run twice at the same time: an interrupt may call the same function while it executes, or another core runs the same code. The rule: no shared static variables, and locks where needed.

char *strtok(char *s, const char *d)
{
    static char *last; /* shared state! */
    ...
}

/* reentrant version: state lives in the caller */
char *strtok_r(char *s, const char *d,
               char **saveptr);

The static variable inside strtok breaks when two threads, or an interrupt handler, use it at the same time.

Useful Techniques · Step through the code

strtok and Reentrancy: Code Trace

char *my_strtok(char *s, char sep) {
    static char *rest;      /* shared by all! */
    if (s) rest = s;
    if (!rest || !*rest) return NULL;
    char *tok = rest;
    while (*rest && *rest != sep) rest++;
    if (*rest) *rest++ = '\0';
    return tok;
}
/* main:  my_strtok(a, ',')  a = "ali,veli" */
/* irq:   my_strtok(b, ';')  b = "x;y"      */
/* main:  my_strtok(NULL, ',')              */

The main program is splitting comma-separated names. The function's state lives in one static pointer: rest records where the next call should resume.

First call: rest = a. It advances to the comma, writes \0 over it, and rest points to the start of “veli”. Returns ali.

At exactly this moment an interrupt arrives; the handler starts splitting its own string (b = “x;y”) with the same function.

The handler's call with s = b overwrites the static rest: it now points inside b (“y”). main's place is lost.

main passes NULL to resume, but rest points into b: it returns y, not the expected “veli”. The bug shows up rarely and depends on timing.

Root cause: the state between calls lives in a static (shared) variable. The reentrant strtok_r keeps it in a pointer the caller supplies, so every caller has its own rest.

Useful Techniques

Brute Force and Checking for Errors First

Brute force

  • The simple, “slow-looking” solution is often enough: a linear search of a 50-entry table can be faster and less buggy than a hash table.
  • Use a complex algorithm only when measurements demand it: when n is large or the code is on a hot path.
  • Sorting: insertion sort for small arrays, merge sort/heapsort for large ones.

Check for errors first

Bad: checking after acquiring resources

lock(&tbl_lock);
buf = kmalloc(n, GFP_KERNEL);
if (n > MAX || !access_ok(u, n)) {
    kfree(buf);
    unlock(&tbl_lock);
    return -EINVAL;
}

Good: check first, then acquire

if (n > MAX || !access_ok(u, n))
    return -EINVAL; /* check first */
buf = kmalloc(n, GFP_KERNEL);
if (!buf)
    return -ENOMEM;
lock(&tbl_lock);
...

Validating parameters before taking locks and memory removes the undo code on the error path (and forgotten-unlock bugs).

Performance

Performance: Why Slow, and What to Speed Up?

Why are systems slow?

Feature bloat: every release adds features and cannot remove old ones. Backward-compatibility layers, security measures (Spectre/Meltdown patches raised system-call costs, for example), indirection added for generality.

What should be optimized?

Only the parts measurements show to be bottlenecks. “Good enough is good enough”: doubling code complexity for a 5% gain is rarely worth it.

First correct, then fast

“Premature optimization is the root of all evil.” (D. Knuth). Measurement tools: perf, eBPF-based bpftrace, flame graphs.

Classic techniques

Space–time trade-offs · caching · hints · exploiting locality · optimizing the common case.

Hardware got thousands of times faster over the decades, but perceived speed did not rise as much: software growth ate much of the gain.

Performance · Step through the code

Space–Time Trade-offs: (a) Counting Bits with a Loop

#define BYTE_SIZE 8
int bit_count(int byte)
{
    int i, count = 0;
    for (i = 0; i < BYTE_SIZE; i++)
        if ((byte >> i) & 1)
            count++;
    return count;
}

The sample byte is 0xB7 (183). The loop tests each bit in turn; the counter starts at zero.

(byte >> 0) & 1 = 1: the counter goes up.

Shift, mask, compare: a few instructions and a branch per bit.

Bit 2 is 1 too.

Bit 3 is zero: the branch is not taken and the counter stays.

Bits 4 and 5 are 1 too.

Bit 6 is zero.

The last bit is 1. The loop ran 8 times.

The result is 6. Almost no memory, but about 8 iterations × a few instructions per byte. To go faster we must spend space to save time.

Performance · Step through the code

Counting Bits with a Nibble Table: Code Trace

char nib[16];            /* 16 bytes */
void build_table(void) {
    nib[0] = 0;
    for (int i = 1; i < 16; i++)
        nib[i] = (i & 1) + nib[i >> 1];
}
int bit_cnt(unsigned char b) {
    return nib[b & 0x0F] + nib[b >> 4];
}

A 16-byte table instead of a 256-byte one: one count for each 4-bit value. 0 has no bits set.

i = 1 … 3: the bit count of i = its last bit + the bit count of (i ≫ 1), which is always filled in already. E.g. nib[3] = 1 + nib[1] = 2.

i = 4 … 7: the bit count of i = its last bit + the bit count of (i ≫ 1), which is always filled in already. E.g. nib[7] = 1 + nib[3] = 3.

i = 8 … 15: the bit count of i = its last bit + the bit count of (i ≫ 1), which is always filled in already. E.g. nib[15] = 1 + nib[7] = 4.

bit_cnt(0xB7): the byte splits into two halves: low 7 = 0111, high B = 1011. No loop, no branch.

Two memory reads and an add: 3 + 3 = 6. The loop version needed 8 iterations for the same byte.

bit_cnt(0x5C): nib[C] + nib[5] = 2 + 2 = 4. 16 bytes of memory, 2 reads: a middle point between the 256-entry table and the loop.

Caching

Path → i-node cache

Pathi-node
/usr6
/usr/ast26
/usr/ast/mbox60
/usr/ast/books92
/usr/bal45
/usr/bal/paper.ps85
  • Without a cache, finding /usr/ast/mbox takes: the root i-node, the root directory, the /usr i-node, the /usr directory, the /usr/ast i-node, the /usr/ast directory → 6 disk reads (+ the file's i-node).
  • If the full path is cached: one memory lookup, zero disk accesses.
  • If only /usr/ast is cached, the search continues from there: a partial hit is a gain too.
  • Linux: the directory-entry cache (dcache), the i-node cache and the page cache. That is why free RAM looks “used”.
  • The price of caching is consistency: if a file is deleted or renamed, its entry must be invalidated.
General rule: if the same result is computed again and again, store it. Caches in an OS: the TLB, CPU caches, the page cache, the dcache, ARP and DNS caches.

Performance · Step through the code

Name Resolution with a Path Cache: Code Trace

/* c[]: "usr","bal","thesis.tex"; n = 3 */
int resolve(char *c[], int n) {
    int k = n, ino = ROOT, reads = 0;
    while (k > 0 && !in_cache(c, k, &ino))
        k--;              /* longest prefix */
    for (int j = k; j < n; j++) {
        ino = dir_lookup(ino, c[j]);
        reads += 2;       /* i-node + block */
        cache_add(c, j + 1, ino);
    }
    return ino;
}

The cache holds five paths. We look up /usr/bal/thesis.tex: the full path is not cached.

Drop the last component: /usr/bal is cached, ino = 45. No need to start from the root: two components for free.

The one remaining component comes from disk: i-node 45 and its directory block are read, thesis.tex → 131. The result is added to the cache.

When the same path is opened again the full path is cached: neither loop runs, 0 disk reads.

/etc/passwd: neither the full path nor /etc is cached; k drops to 0 and resolution starts at the root i-node (ROOT = 1).

The root i-node and root directory block are read: etc → 14; /etc enters the cache.

The /etc i-node and directory block: passwd → 212. On the uncached path, 2 reads per component: 4 in all. In Linux this cache is the dcache.

Performance

Hints

How it differs from a cache

A cached value must always be correct. A hint may be wrong, so no invalidation is needed, but a cheap check before use is a must.

Examples

“The file is probably on server B” in a distributed file system; redirect caches on the web; branch prediction; an access hint from an application to the kernel via madvise(MADV_SEQUENTIAL).

Performance

Exploiting Locality

  • Temporal locality: what was used recently will be used again (the basis of caching). Spatial locality: what is nearby will be used too (read-ahead, huge pages).
  • Put data used together side by side: FFS cylinder groups, ext4 block groups; on NUMA, allocate memory from the thread's own node.

Performance · Step by step

Optimizing the Common Case

Most locks are taken uncontended. If that is the common case, it is the case to speed up.

A uses an atomic compare-and-swap (CAS) to turn 0 into 1. The kernel is never entered: a few nanoseconds.

The rare case: B also wants the lock and its CAS fails. It sets the value to 2 and sleeps in the kernel with futex(FUTEX_WAIT). Only here is the slow path taken.

On release, if the old value was 2, A calls futex(FUTEX_WAKE); had it been 1, A would not call it at all. B wakes and takes the lock.

The general principle (Lampson): make the common case fast and the rare case correct. Other examples: system-call fast paths, clock_gettime via the vDSO without entering the kernel, TLB hits.

Project Management · Step by step

The Mythical Man-Month

The “man-month” is a misleading unit: it assumes work can be divided among people. Two people have just 1 communication path.

4 people have 6 paths. Every newcomer must coordinate with everyone; meetings, documents and interface agreements multiply.

6 people have 15 paths. Training someone added to a late project also eats the existing team's time.

8 people have 28 paths. Brooks's law: “Adding manpower to a late software project makes it later.”

Brooks's time split from his OS/360 experience: 1/3 planning, 1/6 coding, 1/4 module testing, 1/4 system testing. Writing code is only one-sixth of the job.

Project Management

Team Structure, Experience and “No Silver Bullet”

Team structure

Mills/Brooks's surgical team: the chief programmer designs and codes, the others support. Conceptual integrity stays with a few people.

The role of experience

Good programmers are many times more productive than average. “Plan to throw one away”; beware the second-system effect.

No silver bullet

Brooks (1986): tools reduce only accidental complexity; essential complexity remains. AI-assisted coding does not remove design responsibility either.

Testing and Debugging

Why Is Testing OS Code Hard?

Why is it hard?

  • Privileged mode: there is no higher layer to catch the error; one bad pointer in the kernel brings down the whole system, test harness included, with an oops/panic.
  • Concurrency: interrupts, preemption and multiple cores create countless interleavings; a bug may show up only under a rare timing.
  • Nondeterminism: “heisenbugs” do not repeat on every run; even adding a printk can change the timing and hide the bug.
  • Diversity: thousands of drivers, several architectures (x86-64, arm64, RISC-V) and tens of thousands of Kconfig options; not every combination can be tried.
  • Long-lived state: leaks and counter overflows appear only after days of running.

Kinds of tests

KindWhat it tests (kernel example)
UnitA single function or module, in isolation (KUnit)
IntegrationSubsystems working together, the user-space interface (kselftest)
SystemThe whole OS, on a real or virtual machine (LTP, boot tests)
RegressionDid a fixed bug come back? Rerun on every change (KernelCI)
Stress / loadOverload, long runs, resource scarcity (stress-ng, rcutorture)

A failed OS test often means losing the machine itself, so tests run in VMs with timeouts and automatic reboots.

Testing and Debugging · Step through the code

KASAN Shadow-Memory Check: Code Trace

/* 1 shadow byte per 8-byte region:
   0: all valid, 1..7: first k bytes,
   < 0: redzone or freed */
void kasan_check(void *a, int size) {
    int8_t s = *(int8_t *)(((uintptr_t)a >> 3)
                           + SHADOW_OFS);
    if (s == 0) return;            /* fast path */
    if ((int)((uintptr_t)a & 7) + size - 1 >= s)
        report(a, s);
}
/* p = kmalloc(13); p[3]; p[12]; p[13]; */
/* kfree(p); p[0]; */

kmalloc(13) returns a 16-byte slot. Shadow: the first 8 bytes fully valid (0), the first 5 bytes of the next region valid (13 − 8), the rest a redzone (0xfc).

p[3]: the shadow byte for region p+3 ≫ 3 = 0 is read: 0, so the check ends with one comparison.

p[12]: shadow 5; offset within the region 12 & 7 = 4. 4 ≥ 5 is false: the last valid byte, access allowed.

p[13]: 5 ≥ 5: one byte past the array. In a real kernel this byte might belong to another object and the bug would stay silent; KASAN reports the first invalid access.

kfree(p): the object's shadow is marked 0xfb (freed); the slot sits in quarantine for a while so it is not reused at once, which would hide the bug.

p[0]: s = −5. Since the (int) comparison is signed, a negative shadow satisfies “≥ s” at any offset: a use-after-free report, with the allocation and free stack traces.

Testing and Debugging · Step through the code

lockdep's Lock-Order Graph: Code Trace

void lock_acquire(task *t, int L) {
    for (int i = 0; i < t->n; i++) {
        int H = t->held[i];
        if (path_exists(L, H))   /* L → … → H */
            warn("possible deadlock", H, L);
        add_edge(H, L);    /* H before L */
    }
    t->held[t->n++] = L;
}
void lock_release(task *t) { t->n--; }
/* T1: A,B   T2: B,C   T3: C,A */

lockdep tracks lock classes, not instances, and accumulates the relation “this lock was taken while that one was held” in a graph. The graph starts empty.

T1 takes A: no other lock is held, so the loop does not run; A goes onto the held list.

T1 takes B while holding A: no path from B to A, no warning. Edge A → B is added. Then both locks are released.

Later T2 takes C while holding B: edge B → C. The graph now has the order A → B → C.

At another time T3 first takes C; a single lock, no problem.

T3 wants A while holding C: there is a path from A to C (A → B → C). The new edge C → A closes a cycle: lockdep warns.

The three tasks never ran at the same time, and no real deadlock happened. But if T1, T2 and T3 ever run together, each waits for the next one's lock. lockdep shows this in a single run, before it happens.

Testing and Debugging · Step by step

Fuzzing: The syzkaller Loop

syzkaller knows system-call signatures from syzlang descriptions: which argument is a file descriptor, which a flag, which a pointer. The corpus starts empty or with seed programs.

The generator picks a program from the corpus and mutates it, or makes a new one: e.g. openat → ioctl → mmap → close. Arguments match their types, so calls are not rejected at once with EINVAL.

The program runs in QEMU VMs booting a test kernel with KASAN/KCSAN/lockdep on. Even if a VM crashes the host is unaffected; syz-manager restarts the VM.

KCOV records the basic blocks (PC values) executed in the kernel. This coverage feedback turns random trial into a guided search.

A program that opens a new code path joins the corpus and seeds later mutations. The loop never stops, with hundreds of programs per second in each VM.

On a crash or KASAN report, syzkaller reproduces the program, minimizes it and often produces a C reproducer. syzbot reports it to developers automatically.

A fuzzer alone sees only crashes; checkers like KASAN make silent memory corruption visible at the first invalid access. That is why the two are used together.

Hunting Regressions: git bisect

git bisect start
git bisect bad v6.12
git bisect good v6.11
# #500: build, boot, test
git bisect bad
git bisect good   # #250
git bisect good   # #375
git bisect bad    # #437
git bisect run ./test.sh
git bisect reset

The known good (v6.11) and bad (v6.12) ends are given. The first bad commit is among these 1000; git checks out the middle one, #500.

#500 is built and tested: the bug is there, git bisect bad. It began at #500 or earlier; the right half is eliminated.

No bug at #250: good. The first bad commit lies between 251 and 500.

#375 is good too. Each answer halves the candidates: 1000 → 500 → 250 → 125.

#437 is bad: the range is 376–437. Instead of going on by hand, we can leave the testing to a script.

git bisect run carries out the remaining steps itself: 406 good, 421 bad, 413 bad, 409 good, 411 good, 412 bad. 10 tests in all: 210 = 1024 ≥ 1000.

Result: “#412 is the first bad commit”. reset returns to the starting branch. Even with a million commits only ⌈log₂ 106⌉ = 20 tests would be needed.

If ./test.sh exits with 0 the commit is good; 1–127 (except 125) means bad; 125 means “this commit cannot be tested, skip it”.

Trends

Multicore and Large Address Spaces

Multicore chips

128–192 cores per socket in servers, mixed big/little (big.LITTLE) cores in phones. One big kernel lock does not scale: fine-grained locks, RCU and per-core data structures are needed.

Large address spaces

Mapping every file into memory (mmap) or single-address-space systems become possible. The price: deeper page-table walks, more TLB pressure.

Trends

Rust, eBPF and Unikernels

Kernels in Rust

Rust support entered mainline with Linux 6.1 (December 2022), followed by the first Rust drivers. The goal: prevent memory bugs such as use-after-free and overflows at compile time. The Windows kernel has Rust components too.

eBPF

Extending the kernel with small verified programs, without recompiling: tracing, networking (XDP), security, scheduling (sched_ext).

Unikernel

The cloud version of the exokernel's libOS idea: MirageOS, Unikraft. For single-application microservices.

Exercise: Testing and Debugging

  1. With which tools, and in what order, would you catch an occasional use-after-free in a driver? Why is syzkaller run with a KASAN-enabled kernel?
  2. There are 12,000 commits between v6.11 and v6.12, and a performance regression appeared in v6.12. At most how many tests does git bisect need? Which exit codes should the test script use?
  3. A race disappears when you add a printk. Why, and which tools would you investigate with next?
Answers
  1. Trigger the bug with syzkaller or a stress test on a KASAN-enabled kernel; recover the object's lifetime from the allocation and free stack traces in the report; step through with QEMU+gdb if needed. A fuzzer alone sees only crashes; KASAN reports silent corruption at the first bad access.
  2. ⌈log₂ 12,000⌉ = 14, since 213 = 8192 < 12,000 ≤ 16,384 = 214. The script should return 0 for good, 1–127 (except 125) for bad, and 125 for an untestable commit; if measurements are noisy, average several runs.
  3. Heavy printk changes timing (a heisenbug). Check for data races with KCSAN and lock order with lockdep; observe the event order with low-overhead ftrace/eBPF traces.

Review Questions

  1. Explain four of the eight factors that, according to Tanenbaum, make OS design hard.
  2. Discuss the principles of simplicity, completeness and efficiency, each with a system-call example.
  3. Compare the algorithmic and event-driven execution paradigms. Why is a long-running handler a problem in an event loop?
  4. In the seven-layer design, why does virtual memory sit above the device drivers?
  5. What happens when a driver crashes in a microkernel? Why is the same thing more dangerous in a monolithic kernel?
  6. Explain separating mechanism from policy with the scheduler example. How does sched_ext apply this principle?
  7. How many disk accesses does resolving /usr/ast/mbox take without caching? How does a cache differ from a hint?
  8. Compare the loop, macro and table methods of the bit-counting example in terms of space and time.
  9. Why is the futex a good example of optimizing the common case?
  10. Justify Brooks's law with the number of communication paths: how many paths does a 10-person team have?
Answers
  1. E.g. sheer size, concurrency, hostile users, sharing despite isolation, long life, generality, portability, backward compatibility.
  2. Simplicity: UNIX's small set of calls; completeness: the exec family meeting every need with a single execve; efficiency: lseek cheap, read expensive; the cost should be predictable.
  3. Algorithmic: the program sets the flow. Event-driven: external events set it. In a single-threaded loop, no other event is handled until a long handler finishes, so the UI freezes.
  4. Virtual memory calls the disk driver when evicting and fetching pages; each layer can use only those below it, so the drivers sit lower.
  5. Only the driver process dies, and the reincarnation server restarts it. In a monolithic kernel the driver lives in the kernel address space, and its bug crashes the whole system.
  6. The kernel provides the “pick the highest priority” mechanism; the application sets the priorities. With sched_ext the policy is loaded as an eBPF program while the kernel mechanism stays the same.
  7. 6 reads (3 i-nodes + 3 directory blocks), 7 with the file's i-node. A cache is always correct; a hint may be wrong and is verified before use.
  8. Loop: no space, 8 iterations. Macro: no space, no branches, but ~24 instructions. Table: 256 bytes, one read. In hardware, POPCNT is a single instruction.
  9. An uncontended lock is taken in user space with one atomic operation; the kernel is entered only in the rare contended case.
  10. 10·9/2 = 45 paths. Each person added grows the communication load quadratically and consumes the existing team's time for training.
