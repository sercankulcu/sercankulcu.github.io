Introduction

Why Multiple Processors?

Symmetric (SMP)

All processors have equal access to memory and I/O; kernel code can run on any of them.

Asymmetric (AMP)

Processors are not equal: one runs the OS, or each runs separate software.

Cluster

Independent computers on a network act as one system; each node has its own OS.

  • Clock rates have been stuck at 3–5 GHz since ≈ 2005 (the end of Dennard scaling); the transistor budget now goes to more cores.
  • The OS handles processor allocation, synchronization, interprocess communication and the consistency of shared data.

Amdahl: with parallel fraction p, the speedup on n processors is 1 / ((1 − p) + p/n). For p = 0.95: 5.93 on 8 processors, 15.42 on 64, with a limit of 20. “More processors, more performance” holds only when the serial part is small.

Multiprocessor Hardware

UMA: Bus-Based Architecture

  • UMA (Uniform Memory Access): every CPU reaches every memory word in the same time, which makes parallel programming easier.
  • (a) Single bus: as CPUs are added the bus saturates; beyond 2–4 processors the CPUs spend most of their time waiting.
  • (b) Caches serve most reads locally and cut traffic, but copies of the same line must be kept coherent (MESI).
  • (c) Private memory holds program code, constants, stacks and locals; shared memory is used only for shared variables.

UMA: Uniform Memory Access. Today an on-chip ring or mesh replaces the single shared bus (Intel mesh, AMD Infinity Fabric).

Multiprocessor Hardware

Crossbar Switch

8 CPUs (rows) and 8 memory modules (columns); each crosspoint is a small electronic switch. All are open.

CPU 2 wants M5: crosspoint (2, 5) closes, creating a direct path.

CPU 0 → M1 and CPU 6 → M3 are set up at the same time. A crossbar is nonblocking: requests to different modules never wait for each other.

CPU 4 also wants M5: the network has a path, but the module is busy; the only contention is at the memory module. The cost: n² crosspoints.

Example: the old Sun Fire E25K used an 18 × 18 crossbar; today small crossbars between cores and L3 slices are common on chip.

Multiprocessor Hardware

Routing in an Omega Network

The building block is a 2 × 2 switch: two inputs, two outputs. Switches look only at the message's Module field, the target memory module.

8 CPUs, 8 memories, 3 stages × 4 switches. The wiring between stages is a perfect shuffle (address bits rotate left by one).

CPU 011 reads memory 110. Stage 1 (1D) checks the first target bit: 1 → lower output; 2D, second bit 1 → lower; 3D, third bit 0 → upper. Arrives at 110.

The reply returns through the same network: each switch writes the source bit into the Module field, and memory uses that tag to reply to 011.

Meanwhile CPU 001 wants memory 111; both requests need 2D's lower output → one waits. Omega is a blocking network.

An omega network carries many transfers concurrently (not “synchronously”), making conflicting ones wait; with (n/2)·log₂n switches it needs far less hardware and power than a crossbar.

Multiprocessor Hardware

NUMA Multiprocessors

  • NUMA (Non-Uniform Memory Access): every CPU sees a single address space; remote memory is also reached with ordinary LOAD/STORE.
  • Remote access is slower than local. NC-NUMA: no cache coherence; CC-NUMA: directory-based coherence (every server today).
  • The OS keeps a process and its pages on the same node (first-touch policy, Linux automatic NUMA balancing, numactl).
Average access = y · tlocal + (1 − y) · tremote
y = 0.9 → 0.9·80 + 0.1·140 = 86 ns
y = 0.5 → 110 ns (28% slower)

The term is Non-Uniform Memory Access. Even single-socket chips can be NUMA inside (NPS setting on AMD EPYC, Intel SNC).

Multiprocessor Hardware

Directory-Based CC-NUMA

Tanenbaum's example: 256 nodes, 16 MiB per node, 64-byte lines. Each node keeps the directory for the lines in its own memory.

A CPU on node 20 executes LOAD 0x24000108: node = 0x24 = 36, block = 4, offset = 8. Not local → the request goes to 36.

Node 36 checks its directory: entry 4 is empty, so the line is in no cache. The current copy is in its own RAM.

The line goes to node 20 and directory entry 4 is set to 20: “a copy of this line is at 20”.

Now node 20 wants block 2 (0x24000080). The directory says the line is cached at node 82.

Node 36 sends 82 an “invalidate” (with write-back if needed), then sends the line to 20; entry 2 ← 20. Point-to-point messages replace bus snooping.

In this simple design a line can be cached at only one node. Real systems track the set of copies with a bit vector or a limited pointer list; on multicore chips a “snoop filter” does the same job.

Multiprocessor Hardware

The Cache Coherence Problem

  • Each core's private cache holds copies of the same memory. When one writes, the other's copy goes stale.
  • Coherence: all cores see writes to the same address in the same order, and a read returns the latest written value.
  • Snooping: every cache controller listens on a shared bus; fine for a few cores.
  • Directory: a list of copies is kept and messages go only to the nodes involved; scales to many cores and NUMA.
  • Two basic policies: write-invalidate (common) and write-update.

Coherence concerns a single address; the order of different addresses is the business of the memory consistency model (x86-TSO, ARM's weak model), which is why locks include memory barriers.

Multiprocessor Hardware

The MESI Protocol

StateMeaning
M ModifiedOnly copy, dirty; memory is stale. Written back on eviction.
E ExclusiveOnly copy, clean. A write turns it into M without touching the bus.
S SharedThere may be several clean copies. To write, invalidate the others first.
I InvalidThe copy is invalid; an access is a cache miss.

Intel MESIF (F: the copy that responds) and AMD MOESI (O: dirty but shared) are variants of this protocol.

Multiprocessor Hardware

MESI Step by Step

Start: x is only in memory (0). The line is I in both caches.

C0 reads: BusRd, no other copy → E (only and clean).

C1 reads: C0 snoops the request and says “I have it” → both S. Memory is still current.

C1 writes: to write in state S it broadcasts BusUpgr (invalidate) → C0 I, C1 M; memory is now stale.

C0 reads: a miss. C1 flushes the dirty line (data to C0 and memory); both S, memory = 1.

C0 writes: another invalidation → C0 M, C1 I.

C0 writes again: already M, so no bus traffic. That is why write-heavy private data is cheap.

Multiprocessor Hardware

False Sharing

struct counters {      /* bad */
  long a;   /* offset 0 */
  long b;   /* offset 8 */
};

struct padded {        /* good */
  _Alignas(64) long a;
  _Alignas(64) long b;
};

/* thread 0: for(..) s.a++;
   thread 1: for(..) s.b++; */
  • The unit of coherence is the line (64 B), not the variable.
  • Java: @Contended; Linux: ____cacheline_aligned.
  • DSM has the same problem at page granularity: if two independent variables share a page, the page bounces between machines.

a and b are independent counters but sit in the same line.

C0 a++: takes the line in M; C1's copy is invalidated.

C1 b++: the line moves to C1 (M); C0's copy becomes invalid.

When two cores write in quick alternation, the line moves every time: “ping-pong”. Two threads can run slower than one.

Fix: align or pad so each counter gets its own line. The memory cost is 56 B per counter; the gain is often a manyfold speedup.

Multiprocessor Hardware

Multicore and Heterogeneous Chips

Multicore (CMP)

Private L1/L2, shared L3. A server socket: 192 cores (AMD EPYC 9005), 288 E-cores (Xeon 6900E).

Chiplets

Groups of cores sit on separate dies; even within one socket, L3 and memory distances differ.

Big–little cores

big.LITTLE, Apple and Intel P/E: the OS places work by energy (Linux EAS, Thread Director).

Accelerators

GPUs and NPUs on the same chip share the same memory; they are scheduled through the driver.

Multiprocessor Hardware

Simultaneous Multithreading (SMT)

  • One physical core appears as two logical CPUs (Intel Hyper-Threading, AMD SMT): two register sets, shared execution units and L1/L2.
  • The gain is typically 10–30%, and zero when both threads want the same unit. The scheduler should fill idle physical cores first.
  • Security: a shared cache opens side channels (L1TF, MDS) → Linux core scheduling places only mutually trusted threads on one core. Intel Lunar Lake (2024) dropped SMT on its P-cores.

Multiprocessor Hardware

GPUs and Heterogeneous Computing

  • A GPU runs thousands of simple lanes in groups of 32 (warps/wavefronts) on the same instruction: data-parallel work (graphics, AI, scientific computing).
  • Programming: CUDA, ROCm/HIP, OpenCL, SYCL; the CPU launches a kernel, moves data and waits for the result.
  • The OS and driver manage GPU memory, time-share contexts, and provide unified/shared virtual memory (IOMMU, page faults).
  • Clusters put 4–8 GPUs per node linked by NVLink; nodes talk via RDMA over InfiniBand/RoCE.

Multiprocessor Operating Systems

Each CPU Has Its Own OS

  • Memory is split into one partition per CPU; each CPU runs an independent copy of the OS in its partition. The OS code can be shared; the data is separate.
  • A system call is caught and handled on the local CPU.

Pros

  • Simple: a uniprocessor OS runs almost unchanged.
  • No locks between partitions.

Cons

  • Processes are not shared: one CPU may be overloaded while another idles.
  • Pages are not shared; each OS keeps its own buffer cache → inconsistent disk blocks.

Today's equivalent: partitioned systems and separate VMs on a hypervisor; in research, the Barrelfish “multikernel” treats each core as a separate node that communicates by messages.

Multiprocessor Operating Systems

The Master-Slave Model

  • The only copy of the OS and its tables lives on the master CPU only; every system call is redirected to the master.
  • Slaves run user processes handed out by the master; with a single ready list, the load stays balanced.

Pros

  • Simple and consistent: only one CPU touches kernel data.
  • Load balancing comes for free.

Cons

  • The master becomes a bottleneck: with system-call-heavy work it does not scale past a few CPUs.
  • If the master crashes, the whole system stops.

This is the classic form of asymmetric multiprocessing (AMP). Asymmetry lives on in embedded chips today: a Cortex-M core running an RTOS beside Cortex-A cores running Linux (OpenAMP, remoteproc).

Multiprocessor Operating Systems

Symmetric Multiprocessors (SMP)

  • There is a single copy of the OS in memory; any CPU can run kernel code. A system call is handled on the CPU that made it.
  • Problem: two CPUs may touch the same kernel table at once → locks.
  • The first step was one big kernel lock (Linux BKL, 2.0), removed completely in 2.6.39 (2011). Today: thousands of fine-grained locks, RCU and per-CPU data.

Pros

  • No bottleneck; every CPU runs the kernel.
  • Memory and processes are balanced dynamically.

Cons

  • Kernel tables must be split into critical sections.
  • A lock-ordering bug → deadlock.

A multiprocessor OS differs from a multicomputer OS: in a multiprocessor all CPUs see the same physical memory; in a multicomputer each node has its own memory and communicates only by messages.

Synchronization

TSL and Bus Locking

On a uniprocessor TSL (test and set lock) is an indivisible instruction. On a multiprocessor, reading and writing the memory word are separate bus cycles.

CPU 1 reads the lock: 0 (free).

Before CPU 1 writes, CPU 2 reads too: still 0.

CPU 1 writes 1, and CPU 2 writes 1.

Result: both think “the lock is mine” and mutual exclusion breaks. Disabling interrupts does not help either: it stops only its own CPU.

Fix: TSL locks the bus for the whole read–write. Today the x86 LOCK prefix usually just holds the cache line in state M; ARM uses LDXR/STXR or LSE CAS.

Synchronization

Ticket Lock

import java.util.concurrent.atomic.*;
public class Ticket {
  static AtomicInteger next = new AtomicInteger();
  static volatile int serving = 0;
  static int counter = 0;
  static void lock() {
    int my = next.getAndIncrement();
    while (serving != my) Thread.onSpinWait();
  }
  static void unlock() { serving++; }
  public static void main(String[] a)
      throws Exception {
    Runnable job = () -> {
      for (int i = 0; i < 100_000; i++) {
        lock(); counter++; unlock(); } };
    Thread t0 = new Thread(job);
    Thread t1 = new Thread(job);
    t0.start(); t1.start(); t0.join(); t1.join();
    System.out.println("counter = " + counter);
  }
}

Two counters: next hands out tickets, serving shows whose turn it is.

T0 takes a ticket: getAndIncrement is atomic (x86 LOCK XADD) → my = 0.

T1 takes a ticket too: my = 1. Even if two CPUs call at the same moment, the tickets differ.

T0: serving == 0 → leaves the loop and does counter++.

T1 spins: it reads serving from the S copy in its own cache without loading the bus; onSpinWait = x86 PAUSE.

T0 releases: serving++. The write invalidates T1's copy (a single coherence message).

T1 reads the new value: 1 == my → it enters. The lock is fair: nobody starves.

2 × 100,000 increments, none lost. With an unlocked counter++, most runs end below 200,000.

Synchronization

Spinlocks and Cache Traffic

  • (a) A plain TSL loop writes on every try: the lock line moves between CPUs nonstop, slowing the owner's work too.
  • (b) Test-and-test-and-set (TTAS): spin on the local copy; try TSL only when the lock looks free. Exponential backoff further reduces collisions.
  • (c) MCS (Mellor-Crummey & Scott, 1991): each waiter spins on its own flag in a separate line; a release is a single remote write. Linux qspinlock builds on this idea.

These locks do not prevent data inconsistency; they prevent coherence traffic (cache thrashing).

Synchronization · Step through the code

TTAS Lock: Code Trace

void lock(int *k) {
  for (;;) {
    while (*k == 1)   /* spin locally */
      ;
    if (tsl(k) == 0)  /* looked free */
      return;         /* acquired */
  }
}
void unlock(int *k) {
  *k = 0;
}

CPU 0 holds the lock (k = 1, the line is M in its cache). CPU 1 and CPU 2 call lock.

CPU 1 reads *k: a miss, fetched over the bus. CPU 0's M copy is shared; both are S.

CPU 2 reads too: three S copies. 2 bus transactions so far.

As long as they see k = 1 they spin in their own caches: the bus counter does not move. A plain TSL loop would pull the line for writing on every try.

CPU 0 calls unlock: writing k = 0 invalidates the other copies (I); the line is M on CPU 0.

CPU 1's copy is invalid: it rereads (a miss), sees k = 0 and leaves the while.

CPU 2 also misses and sees k = 0. Both think the lock is “free” at the same time.

CPU 1 does TSL first: it takes the line for writing (M), old value 0 → lock acquired.

CPU 2's TSL also pulls the line (CPU 1's copy goes I), but the old value is 1: it fails. This race costs one more bus transaction.

CPU 2 spins on its local copy again. 7 bus transactions in all, and the count stays put however long the wait.

Synchronization

Spin or Switch?

  • Spinning: the CPU is wasted, but work resumes the moment the lock frees. For short critical sections.
  • Switching (blocking): the CPU is given to other work; the cost is two context switches + a cold cache.
  • Rule: if the expected wait is shorter than 2C, spin; otherwise sleep.
  • Competitive strategy: spin for as long as a switch costs (2C), then sleep → at worst twice the optimal cost.
  • In practice: Linux futex + adaptive mutexes (spin while the owner runs), Windows CRITICAL_SECTION spin counts, lock inflation in Java.
  • In the kernel, only spinlocks may be used where interrupts are disabled.

Scheduling

Time Sharing: A Shared Ready Queue

  • With independent processes, all CPUs take work from one priority ready queue: the load balances itself, but the single lock becomes a bottleneck and a process may land on a CPU with a cold cache.
  • If a thread holding a spinlock runs out of quantum, the other CPUs spin in vain. Smart scheduling: the lock holder sets a flag, and the scheduler does not preempt a flagged thread but gives it a little extra time to finish its critical section.

Scheduling

Space Sharing

  • Related threads run at the same time on separate CPUs: when a job starts it gets as many CPUs as it asks for and keeps them until it finishes.
  • No multiprogramming per CPU → no context switches. If there are not enough CPUs, the job waits until enough are free (simplest: FCFS).
  • Drawback: when a thread blocks on I/O its CPU sits idle. HPC cluster job schedulers (Slurm, PBS) partition nodes this way today.

Scheduling

Gang Scheduling

The problem: A0 and A1 communicate, but their slices are staggered. A1 sees A0's request from t = 0 only 100 ms later, and the reply waits 100 ms too.

In gang scheduling, related threads form a gang. Slice 0: all 6 threads of A at once, on 6 CPUs.

Slice 1: B (3) and C (3) together; all CPUs start and end slices in sync (synchronized time slicing).

Slices 2–3: D (5) + E0, then E's remaining 6 threads. All members of a gang run in the same slice, so messages get immediate replies.

The cycle repeats. Two conditions: gang members start at the same time and all sit on different CPUs. Co-scheduling the vCPUs of a VM today is the same idea.

Multicomputers

Multicomputers and Network Interfaces

  • A multicomputer (cluster): each node is CPU + RAM + network interface; memory is not shared and each node runs its own OS copy. Communication is by messages only.
  • In the worst case a message is copied 5 times, each copy costing microseconds. The fix: map NIC memory into user space and use DMA and RDMA (InfiniBand, RoCE), so the kernel never steps in.
  • Uses: large-scale simulation, HPC, AI training; TOP500 systems are multicomputers with tens of thousands of nodes.

Multicomputers

Routing in a Hypercube

A 4D hypercube: 16 nodes, each linked to 4 neighbors that differ in exactly one bit. A message goes from 0000 to 1011.

Source ⊕ target = 1011: three bits differ. The leftmost differing bit is fixed first → 1000 (from the lower to the upper cube).

Next differing bit: 1010.

Last bit: 1011. Hops = number of differing bits (Hamming distance) = 3; the worst case is d = log₂16 = 4. The rule is local, so no routing table is needed.

Multicomputers · Step through the code

E-Cube Routing: Code Trace

void route(int src, int dst, int d) {
  int u = src;
  for (int b = d - 1; b >= 0; b--) {
    int m = 1 << b;
    if ((u ^ dst) & m) {  /* bit differs */
      u ^= m;             /* go to neighbor */
      printf("%d ", u);
    }
  }
}

A message from 0110 (6) to 1101 (13). u ⊕ dst = 1011: three bits differ, so the shortest path is 3 hops. Dashed edges are the 4th dimension (between the two 3-cubes).

b = 3: the bit differs → flip bit 3 of u; the message moves to neighbor 1110 (14).

b = 2: this bit is the same (1) in u and dst; no hop.

b = 1: the bit differs → flip bit 1 of u; the message moves to neighbor 1100 (12).

b = 0: the bit differs → flip bit 0 of u; the message moves to neighbor 1101 (13).

The target is reached in 3 hops: 0110 → 1110 → 1100 → 1101. Each node decides from its own address and the target alone; since bits are always fixed left to right, the path has no cycles.

Multicomputers

Store-and-Forward or Cut-Through

Example: a 4 KiB packet over 10 Gb/s links; crossing one link takes 4096 × 8 / 10¹⁰ ≈ 3.28 µs.

Store-and-forward: switch 1 buffers the whole packet, checks it, then forwards it.

Three links → 3 × 3.28 = 9.83 µs. Latency grows linearly with the hop count.

Cut-through and wormhole routing: the path is set up when the header arrives and the packet flows like a pipe → ≈ 3.38 µs. HPC networks and data-center switches work this way.

Multicomputers

Blocking and Nonblocking Send

(a) Blocking (synchronous) send: the call does not return until the message has been transmitted.

(b) Nonblocking (asynchronous) send: returns at once, but the buffer is off-limits until transmission ends.

OptionCost
Blocking sendCPU idles during transmission
Nonblocking + copy to kernelCPU time for the extra copy
Nonblocking + interrupt when donehard to program (race conditions)
Copy on write (CoW)an extra copy anyway if the buffer is written

Tanenbaum's four options. The receiver side is similar: a blocking receive, polling, or a pop-up thread / active message.

In MPI, MPI_Send/MPI_Recv are blocking and MPI_Isend/MPI_Irecv + MPI_Wait are nonblocking; on Linux, io_uring and zero-copy MSG_ZEROCOPY are modern answers to the same problem.

Multicomputers

Remote Procedure Call (RPC)

The client says result = add(3, 4); it looks like an ordinary local call.

1: The client calls the client stub as if it were a local procedure.

2: The stub marshals the parameters into a message and makes a system call into the kernel.

3: The kernel sends the message over the network to the server machine.

4: The server kernel hands the message to the server stub.

5: The stub unpacks the parameters and calls the server procedure locally; the reply returns the same way.

Difficulties: pointers (another address space → copy/restore), arrays of unknown length, global variables, partial failures (at least once or at most once?). Stubs are generated automatically from an interface definition; today gRPC + Protocol Buffers, Thrift, Java RMI.

Multicomputers

Distributed Shared Memory (DSM)

DSM gives machines that share no memory the illusion of shared memory. The layer can be hardware (NUMA), the OS (page-based, Li and Hudak 1989) or a user library.

Pages are spread across the machines. When CPU 0 touches page 10, the MMU raises a page fault.

The OS finds who has the page and requests it; the page moves to CPU 0 and the instruction is restarted.

A read-only page is replicated: both CPUs read locally. On a write the other copies are invalidated; independent variables on the same page cause false sharing.

A 4 KiB page is expensive and coarse-grained on a network, so DSM gave way to message passing (MPI) and PGAS languages. Its modern counterpart is cross-machine memory pooling with CXL.

Multicomputers

Graph-Theoretic Deterministic Allocation

9 processes (vertices) and the message traffic between them (edge weights). Assign 3 processes to each of 3 machines; goal: minimize network traffic.

Alphabetical assignment: the cut (intermachine) edges total 24.

The best partition (all 280 balanced options tried): 15. Chatty processes share a machine; the problem is NP-hard in general and is solved with heuristics.

Multicomputers

Distributed Heuristic Load Balancing

Sender-initiated: when a new job arrives, a node over its threshold probes random nodes (Eager et al., 1986).

Probing is limited (e.g. N = 3); if a node below the threshold turns up, the job goes there, otherwise it runs locally.

The job has moved. Drawback: when the system is fully loaded, every probe is wasted and adds load.

Receiver-initiated: a node that finishes a job and goes idle looks for work itself; the probing cost falls on the idle node.

A loaded node handed off a job. Works well under high load. Its modern form is work stealing: Cilk, Java ForkJoinPool, the Go and Tokio runtimes.

Virtualization

Hypervisors: Type 1 and Type 2

  • Type 1: VMware ESXi, Xen (XCP-ng), Microsoft Hyper-V; Linux KVM makes the kernel a hypervisor (most clouds: AWS Nitro, Google). With Hyper-V on, Windows itself runs in a root partition.
  • Type 2: VirtualBox, VMware Workstation/Fusion, Parallels, UTM. A pure type 2 interprets or binary-translates (QEMU without KVM); a practical one uses VT-x/AMD-V via a kernel module.
  • Popek–Goldberg (1974): a machine is virtualizable if all sensitive instructions are privileged (trap in user mode).
  • Classic x86 failed this test (e.g. POPF fails silently in user mode) → binary translation, then VT-x/AMD-V.

Uses: server consolidation, moving a running VM to another host (live migration), snapshots; the foundation of the cloud. In type 2, I/O goes through the host OS, so overhead is higher.

Virtualization

Trap and Emulate: VT-x / AMD-V

The guest OS believes it runs in kernel mode, but the hypervisor is really in control. Intel VT-x / AMD-V (2005–06) add a new mode: root (hypervisor) and non-root (guest).

The guest kernel executes a sensitive instruction: changing the page table (CR3), an I/O port, HLT…

The hardware does not execute it: a VM exit traps to the hypervisor, and the reason is written to the VMCS.

The hypervisor emulates the instruction's effect, updates the virtual hardware state and returns to the guest with a VM entry. An exit costs ~1 µs; frequent exits hurt performance.

Before hardware support, VMware (1999) replaced sensitive instructions at run time through binary translation. Only the guest OS's sensitive instructions trap; the rest run directly on the hardware.

Virtualization

Paravirtualization

  • The guest OS is modified: instead of sensitive instructions it makes hypercalls straight to the hypervisor — the one-layer-down analogue of a system call.
  • No trap-and-emulate cost, so it is faster; but it needs an OS whose source can be changed (Xen 2003).
  • VMI (Virtual Machine Interface) was proposed so one kernel could run on bare metal and on different hypervisors; it was removed from Linux in 2011. Paravirtualization lives on in drivers today: virtio disk/network, paravirtual clocks, Hyper-V enlightenments.

In today's clouds, CPU and memory are fully virtualized with hardware support; I/O uses virtio or direct device assignment with SR-IOV.

Virtualization

Memory Virtualization: Shadow Tables and EPT

  • Shadow page tables: the hypervisor makes the guest's tables read-only, traps every change and updates its GVA → HPA copy. Lots of VM exits.
  • EPT (Intel, 2008) / NPT (AMD): the hardware walks both tables together; the guest changes its own table without traps.
  • TLB misses get more expensive → huge pages (2 MiB / 1 GiB) and VM-tagged TLBs (VPID/ASID) are used.
  • Overcommit: a balloon driver reclaims memory from the guest; KSM merges identical pages (copy on write).

Distributed Systems

Distributed Systems and Middleware

  • Distributed system: autonomous computers communicating over a network; each manages its own OS, memory and resources, yet the whole tries to look like one coherent system to the user.
  • Nodes may run different hardware and OSes, belong to different organizations and span the globe. The common ground is the middleware layer.
  • Four paradigms: document (the Web), file (NFS, SMB), object (CORBA, RMI, gRPC), coordination (Linda, publish-subscribe).

True distributed operating systems (Amoeba, Plan 9) stayed in research; today each node runs its own OS and distribution is handled by middleware and cluster managers (Kubernetes).

Document-Based Middleware: The Web

The user types www.example.org/index.html. The Web is a huge directed graph of linked documents.

1–2: The browser (through the OS resolver) asks DNS for www.example.org's address; answer: 203.0.113.10 (cached).

3: A TCP connection to the server's port 443 and the TLS handshake (one step in HTTP/3, with QUIC).

4–5: A GET /index.html request; the server returns the HTML and the browser starts rendering text.

6: Images, CSS and scripts in the HTML are fetched over the same connection, as parallel streams in HTTP/2–3; the connection stays open for a while.

Port 80 and a new TCP connection per object belong to the HTTP/1.0 era; today the defaults are HTTPS (443), persistent connections and HTTP/2–3 multiplexing.

Distributed Systems

File-System-Based Middleware

Upload/download model: the whole file is copied to the client, used and sent back (FTP-like; early AFS). Simple, but costly for large files.

Remote access model: the file stays on the server; the client sends read/write requests over the network (NFS, SMB).

Two file servers, each with its own directory tree.

All clients mount the servers in the same place → a single shared namespace.

If clients mount different things, each sees a different view; the same path may name different files on different clients.

Naming: machine:/path (not location transparent) → mounting remote systems into the local tree → one namespace identical on all machines (location independence). Today: NFSv4, SMB 3, object storage (S3).

Distributed Systems

Semantics of File Sharing

On one processor operations are sequential: A appends “c”, then B reads and sees “abc” (sequential consistency).

In a distributed system client 1 changes the file in its cache; the server does not know yet. Client 2 reads from the server and sees the stale “ab”.

ApproachRuleExample
UNIX semanticsevery write is visible to all at oncesingle machine; remote access without caching
Session semanticschanges become visible when the file is closedAFS; NFS close-to-open consistency
Immutable filesfiles cannot be written; a new one is createdobject storage, Git objects
Transactionsall or nothing, serializabledatabases

Each solution trades consistency against performance.

Object-Based Middleware: CORBA

  • IDL: interfaces are defined independent of language; the compiler generates the client stub and the server skeleton.
  • ORB: locates the object, marshals the call and sends it over IIOP: network transparency.
  • SII (static invocation): through stubs generated from IDL at compile time; fast and type-checked.
  • DII (dynamic invocation): the interface is discovered at run time (interface repository).

SII and DII are separate mechanisms; SII is not a compiled form of DII. CORBA (OMG, 1991) survives in legacy systems; new systems prefer gRPC/Protobuf, REST and Java RMI.

Distributed Systems

Coordination-Based Middleware: Linda

Linda (Gelernter, 1985): processes do not know each other; they communicate through a shared, persistent tuple space. A tuple is a record of typed fields.

out puts a tuple into the space (nonblocking).

in searches with a template: same number of fields, matching types field by field, equal constant fields. ? i is a formal parameter. With several matches, one is chosen arbitrarily.

The matching tuple is removed from the space and i = 5 is assigned. With no match, in blocks. rd reads without removing; eval starts a new process. Synchronization comes for free.

Linda in(): Code Trace

Tuple *in_find(Template *s) {
  for (Tuple *d = space; d; d = d->next) {
    if (d->n != s->n) continue;
    int ok = 1;
    for (int k = 0; ok && k < s->n; k++)
      if (d->type[k] != s->type[k] ||
          (s->fixed[k] && !equal(d, s, k)))
        ok = 0;          /* field mismatch */
    if (ok) { remove(d); return d; }
  }
  return NULL;           /* block */
}

The space holds 5 tuples. A process calls in("abc", 2, ? int i): 3 fields, the first two constant, the third a formal parameter of type int.

d1: 2 fields, but the template has 3 → skipped at once (continue).

d2, field 0: "xyz" ≠ "abc" → ok = 0, move to the next tuple.

d3, field 1: 1 ≠ 2 → ok = 0, move to the next tuple.

d4: field count and types fit, constants are equal; the formal field i gets 5. The tuple is removed from the space.

d4 is gone from the space; d5 would also have matched, but the first one found was taken (Linda does not define which is chosen). The same call is made again.

d1: 2 fields, but the template has 3 → skipped at once (continue).

d2, field 0: "xyz" ≠ "abc" → ok = 0, move to the next tuple.

d3, field 1: 1 ≠ 2 → ok = 0, move to the next tuple.

d5: field count and types fit, constants are equal; the formal field i gets 9. The tuple is removed from the space.

A third in("abc", 2, ? int i) finds no match and returns NULL: the process blocks until someone outs a matching tuple.

Distributed Systems

Publish-Subscribe and Jini

  • A publisher publishes on a topic and a subscriber subscribes to topics it cares about; neither knows the other's identity: decoupled in time and space.
  • Subscribers and topics are added dynamically → scalable and flexible. Delivery guarantees depend on broker settings (at most once / at least once / durable queue).
  • Today: MQTT (IoT), Apache Kafka, RabbitMQ, cloud queues.
  • Jini (Sun, 1998): Java devices discover each other on a network without prior configuration, register with a lookup service and use each other via Java RMI; leases make registrations expire on their own.
  • It continued as Apache River but is no longer active; its ideas live on in service discovery (mDNS/DNS-SD, Consul, Kubernetes services).

Distributed Systems

Cloud and Clusters

  • Cluster: servers linked by a fast network under one administration (HPC, data centers). Cloud: those resources offered over the network on demand, pay as you go (AWS, Azure, Google Cloud).
  • Infrastructure: KVM/Nitro virtualization, containers and Kubernetes (schedules pods onto nodes and restarts failed ones: today's counterpart of a distributed OS).
  • Every topic in this chapter comes together here: NUMA servers, virtual machines, RDMA networks, load balancing, publish-subscribe queues.

Review Questions

  1. How many crosspoints does a 64 × 64 crossbar have, and how many 2 × 2 switches does a 64-input omega network have?
  2. In the omega network, which switches and outputs does a CPU 011 → memory 110 request pass through?
  3. Local 80 ns, remote 140 ns, 75% of accesses local: what is the average access time?
  4. In MESI, what is the bus-level difference between writing a line in state E and in state S?
  5. Why can two threads' separate counters slow each other down? What is the fix?
  6. In which two ways is a ticket lock better than a plain TSL loop?
  7. What are the two conditions of gang scheduling, and what problem does it solve?
  8. What is the diameter of a 256-node hypercube? Of a 16 × 16 torus?
  9. With 4-level tables and EPT, how many memory accesses does a TLB miss need in the worst case?
  10. Which of the tuples ("abc", 2, 5) and ("abc", 2.0, 5) does in("abc", ? x, 5) (x int) match?
Answers
  1. 64² = 4,096 crosspoints; log₂64 = 6 stages × 32 = 192 switches.
  2. 1D (bit 1 → lower), 2D (bit 1 → lower), 3D (bit 0 → upper).
  3. 0.75 · 80 + 0.25 · 140 = 95 ns.
  4. E → M is silent (no bus traffic); S → M must broadcast an invalidation (BusUpgr).
  5. They share one 64 B line: every write steals the line from the other core (false sharing). Align or pad them onto separate lines.
  6. It is fair (FIFO, no starvation), and waiters only read, never write → less coherence traffic.
  7. Members run at the same time on different CPUs, and slices start in sync. Communicating threads no longer wait a whole slice for each other.
  8. log₂256 = 8; 2 · ⌊16/2⌋ = 16.
  9. (4 + 1)² − 1 = 24.
  10. Only ("abc", 2, 5): the second field must be of type int.
