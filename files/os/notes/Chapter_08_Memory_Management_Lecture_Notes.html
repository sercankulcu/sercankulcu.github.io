Chapter 8: Memory Management

A program can run only after it has been loaded into main memory. The CPU reads instructions and data only from registers and main memory; the disk is a slow store reached only through I/O operations. In a system that runs many processes at once, main memory has to be shared among them. Sharing raises three questions. How can one process be kept from reaching another's memory? How do addresses stay correct when a program is loaded anywhere in memory? How is free space tracked, and how is it kept from breaking into pieces? These notes begin with the memory hierarchy and the cache. They then describe address translation, starting from base and limit registers. Binding and loading, swapping, contiguous allocation, and free-space management follow. The emphasis is on paging, the foundation of today's systems: the page table, the TLB, effective access time, and multilevel, hashed, and inverted tables. The last sections cover segmentation and compare the real designs of x86-64, ARMv8, and RISC-V.

8.1Memory hardware

To understand memory management one must first look at memory itself. The operating system sees memory as an abstract array of bytes, but behind that array lie several layers of very different speeds and sizes. Knowing which layer the hardware manages and which the operating system manages explains all the later design decisions.

8.1.1The memory hierarchy and the memory manager

The CPU can reach storage directly in only two places: registers and main memory. An instruction takes its operand from a register or from memory; it cannot reach data on disk directly. Data on disk must first be brought into memory by an I/O operation. That is why the code and data of a running program must be in main memory.

The memory unit also offers a very simple interface. It receives only a stream of addresses: either “read this address” or “write this data to this address.” The memory unit does not know where an address came from. It may have been produced from a program counter, an array index, or a pointer; to memory they are all the same. This simplicity also shows why a layer of hardware that modifies addresses before they reach memory is possible.

The speed gap is very large. A register is read in one clock cycle. A DRAM access in main memory takes hundreds of cycles, and the CPU stalls in the meantime. The gap is closed by small, fast memories inside the processor, the caches. Figure 8.1 shows typical values today: registers under a nanosecond, L1 and L2 cache 1–5 ns, L3 10–20 ns, DRAM 80–120 ns, NVMe SSD 10–100 µs, hard disk 5–10 ms. Going from top to bottom, latency and capacity grow and the cost per byte falls.

What a programmer expects of memory is in fact an impossible list: that it be unlimited, very fast, persistent, and protected. No single technology gives all these properties at once. The real solution is the hierarchy. Small, fast layers hold the frequently used data, and large, slow layers hold the rest. A well-built hierarchy gives the programmer the impression of a memory “almost as fast as the top layer and almost as large as the bottom layer.”

Different managers control the layers of the hierarchy. Hardware manages the caches entirely; the operating system does not interfere with their contents. The operating system manages main memory. The part of the operating system that handles this job is called the memory manager.

Definition 8.1

Memory management is the sharing of main memory among processes. The memory manager keeps track of which regions of memory are free and which are in use; it allocates memory to processes, takes it back when they finish, and protects processes from one another. When memory runs short, moving some of the processes or pages to disk is also its job.

The memory manager's job is often confused with the CPU scheduler's job. Choosing the next process from the ready queue is the scheduler's task. The memory manager deals with questions such as “which process is where, how much room does it occupy, and how much more can be given to whom.”

8.1.2Types of main memory

In everyday language the word “memory” is used for several different kinds of hardware. Table 8.1 compares the four basic types. The type used as main memory is RAM (random access memory). RAM can be read and written, is fast, but is volatile: its contents are lost when power is cut. DRAM cells are tiny capacitors, and because charge leaks away they must be refreshed at regular intervals. SRAM needs no refresh and is faster, but it is more expensive and takes more space. That is why main memory is DRAM (today DDR5, LPDDR5X) and the caches are SRAM.

ROM (read-only memory) is written during manufacture and cannot be changed afterward. It is persistent and cheap; in simple devices and microcontrollers it holds code that will never change. EEPROM and its variant flash memory can be erased and rewritten electrically. They are persistent, but writing is much slower than reading, and a cell can be written only a limited number of times. In today's computers the BIOS/UEFI code is not in ROM but on an SPI flash chip on the motherboard, which is why firmware can be updated. SSDs, USB sticks, and phone storage also use NAND flash. Finally, CMOS or NVRAM is a small area kept alive by a battery or flash; the clock and the boot settings are kept there.

Memory management is concerned with only one of these types: the main memory in which processes run, that is, DRAM. In the rest of the chapter the word “memory” is used in this sense.

8.1.3Cache lines and locality

Data moves between the cache and main memory not byte by byte but in fixed-size blocks. This block is called a cache line. In most processors today a line is 64 bytes. Memory is thought of as divided into consecutive lines of this size: line 0 covers addresses 0–63, line 1 covers 64–127, and so on.

Which line an address a lies in is found by a simple division. The line number is ⌊a / 64⌋ and the position within the line is a mod 64. Since 64 = 26, the division is really a bit-splitting operation: the low 6 bits of the address give the position within the line, and the remaining upper bits give the line number. Figure 8.2 takes address 200 as an example. In binary 200 is 11001000. The low six bits are 001000, that is, 8; the upper two bits are 11, that is, 3. Indeed 3 × 64 + 8 = 200.

When the CPU reads a word, the hardware looks in the cache first. If the line is in the cache, this is a hit, and the data arrives from L1 in 4–5 cycles. If not, there is a miss; the request goes down a level, in the worst case to DRAM, and takes hundreds of cycles. Because the cache is expensive it is small. Instead of one big cache, levels such as L1, L2, and L3 are built, each larger and slower than the one before.

A small cache is useful in front of a large memory because of how programs behave. Programs do not access memory at random; their accesses follow two patterns.

Temporal locality
A piece of data used a moment ago is used again soon. A loop counter, the instructions of a loop body, and a frequently called function are examples.
Spatial locality
A program that accesses one address soon accesses neighboring addresses too. Walking through an array from start to end and executing consecutive instructions are examples.

The cache line exploits spatial locality: because all 64 bytes are fetched on a miss for one byte, later accesses to neighboring bytes are hits. Temporal locality is exploited by the line staying in the cache.

8.1.4The path of a read through the hierarchy

Suppose the CPU wants to read variable x with the instruction LOAD R1, [x]. The hardware first looks at the nearest and fastest level, L1. If the line is not in L1, about 1 ns has been lost and the search continues in L2. If L2 and L3 miss too, the latencies of the levels add up: 1 + 4 + 15 = 20 ns. Finally the data comes from DRAM; this adds about 80 ns, for a total of 100 ns (Figure 8.3).

What comes from DRAM is not a single word but the whole 64-byte line containing the word. On the way the line is placed in L3, L2, and L1 as well. When another piece of data in the same line is accessed a second time, it is now an L1 hit and about 1 ns suffices (Figure 8.4). The 100 ns cost of the first access is thus shared with the accesses to the rest of the line. This is the locality that makes the cache worthwhile.

8.1.5Code trace: a direct-mapped cache

Where in the cache can a line be placed? The simplest answer is direct mapping: the cache is divided into a number of sets, and each block can go to only one set. If the block number is b and the number of sets is K, block b goes to set b mod K. If another block is currently in the set, the newcomer evicts it.

The C fragment below simulates a direct-mapped cache with four sets and 64-byte lines. The array tag records which block is currently in each set; −1 means empty.

int addr[6] = {0, 8, 64, 256, 0, 72};
int tag[4] = {-1, -1, -1, -1};
int hits = 0, misses = 0;
for (int i = 0; i < 6; i++) {
  int block = addr[i] / 64;
  int set = block % 4;
  if (tag[set] == block) hits++;
  else { tag[set] = block; misses++; }
}

For each address the loop first computes the block number (addr / 64) and then the set (block % 4). If the tag in the set equals this block, the hit counter is incremented. Otherwise the block is written into the set and the miss counter is incremented. In this simplified model the whole block number is stored as the tag. Real hardware already knows the set number from the address, so it stores only the upper bits, the real tag.

The first three misses are unavoidable: the blocks come into the cache for the first time. These are called compulsory misses. The misses at steps 3 and 4 have a different cause. The way to reduce conflict misses is to give a block more than one place. In a k-way set-associative cache each set holds k lines. A block still goes to a single set, but it can be placed in any of the k slots of that set.

Example 8.1

Let the same four-line cache be organized as 2 sets with 2 ways, and let the least recently used line be evicted when a set needs room. How many hits are there on the same sequence 0, 8, 64, 256, 0, 72?

  1. Sets. The blocks are 0, 0, 1, 4, 0, 1. The set number is now block mod 2: 0, 0, 1, 0, 0, 1.
  2. Trace. 0: set 0 empty, miss. 8: block 0 is in set 0, hit. 64: set 1 empty, miss. 256: block 4 goes to set 0; since the set has one more free slot, block 0 stays where it is, miss. 0: block 0 is still in set 0, hit. 72: block 1 is in set 1, hit.
  3. Result. 3 hits, 3 misses. Direct mapping had 2 hits. The gain comes entirely from the disappearance of the conflict miss.
Common mistake

Computing the set number from the address itself (for example 256 mod 4 = 0, 72 mod 4 = 0). What determines the set is not the address but the block number. First the address is divided by the line size, then the remainder of the block number modulo the number of sets is taken: 72 / 64 = 1, 1 mod 4 = 1.

8.1.6Code trace: average access time

How well a hierarchy works can be summarized in a single number: the average memory access time. Every access first goes to the top level and spends that level's time. If it misses, the request goes down a level and that level's average time is added. If a level's time is s, its miss rate is m, and the average time of the level below is Tbelow:

T = s + m · Tbelow

The formula repeats itself: the time of the level below is computed in the same way. DRAM, at the very bottom, satisfies every request, so there T is just DRAM's time. The code below does the computation from the bottom up.

/* L1, L2, L3, DRAM access time (ns) */
double lat[4] = {1, 4, 20, 80};
double miss[3] = {0.10, 0.40, 0.50};
double t = lat[3];          /* DRAM */
for (int k = 2; k >= 0; k--)
  t = lat[k] + miss[k] * t;
printf("average = %.1f ns\n", t);

t starts with DRAM's 80 ns. The loop goes down from k = 2 (L3) to k = 0 (L1) and computes the time of the next level up in each round. Table 8.3 shows each round.

The form of the formula also shows how much the miss rates matter. If L1's miss rate falls from 10% to 5%, the 28 ns below stays the same and the average becomes 1 + 0.05 × 28 = 2.4 ns. Reducing L1's own time from 1 ns to 0.5 ns saves only 0.5 ns. Misses dominate the average.

Example 8.2

L1 responds in 2 ns and misses on 5% of requests. L2 takes 10 ns and misses on 20% of the requests that reach it. DRAM takes 100 ns. What is the average access time? What would it be without L2?

  1. The L2 level. TL2 = 10 + 0.20 × 100 = 30 ns.
  2. The L1 level. T = 2 + 0.05 × 30 = 2 + 1.5 = 3.5 ns.
  3. Without L2. The L1 misses go straight to DRAM: 2 + 0.05 × 100 = 7 ns. The second level has halved the average.
Common mistake

Expressing the second level's miss rate relative to all accesses. L2's 20% miss rate applies to the requests that reach L2; only 5% of all accesses reach L2. So the fraction of accesses that go down to DRAM is not 20% but 0.05 × 0.20 = 1%. The formula performs this multiplication automatically.

8.1.7The four questions of cache design

Every cache design has to answer four questions.

  1. When is data put into the cache? Usually on a miss. The hardware also fetches the next lines ahead of time (prefetch) by predicting the access pattern.
  2. Where is it put? This is the mapping question: direct-mapped, k-way set-associative, or fully associative.
  3. Which line is evicted when room is needed? This is the replacement policy: approximations of LRU, random choice, or FIFO.
  4. Where does the evicted line go? If the line has been modified (is “dirty”), it is written to the level below when evicted (write-back). The other option is to pass every write to the level below at once (write-through).

Besides these four questions there are three trade-offs. A big cache gives more hits but is slower and more expensive. A smarter replacement policy increases hits but complicates the hardware. In multicore processors, copies of the same line in different cores have to be kept up to date; this is called coherence and is provided by protocols such as MESI.

The same four questions are not specific to hardware caches. They also appear in the “caches” managed by the operating system: the page cache that holds files, virtual memory, and the TLB. The TLB described in these notes is a cache directly; virtual memory uses main memory as a cache for the disk.

8.2The address space

For several programs to run safely in the same memory, two problems must be solved. The first is protection: a program must not be able to reach another program's memory. The second is relocation: a program must work correctly wherever in memory it is loaded. This section describes where the two problems come from and the simplest hardware solution.

8.2.1Memory without abstraction

The earliest computers had no abstraction for memory. On mainframes before the 1960s and personal computers before the 1980s every program saw physical memory as it was. The instruction MOV REGISTER1, 1000 read the word at physical address 1000. The address the program saw was the same as the address the memory chip saw.

In this arrangement two programs cannot be in memory at the same time. Both use the same physical addresses, and one overwrites the other's data. Memory can still be shared between the operating system and a single user program. Figure 8.7 shows three common layouts. In (a) the operating system is at the bottom of RAM. In (b) the operating system is at the top, in ROM. In (c) the device drivers are at the top in ROM and the rest of the operating system is at the bottom in RAM. In layouts (a) and (c) a bug in the user program can write into the region holding the operating system and crash it. Layout (b) was used in some embedded systems, and (c) in the first PCs running MS-DOS, where the BIOS drivers were in ROM.

This approach has not become history. Microcontrollers without a memory management unit still work this way today. Most of them nevertheless have a memory protection unit (MPU). An MPU does no address translation; it only checks access permissions for certain regions.

8.2.2The relocation problem

The problem that arises when two programs are put in memory at once is shown clearly by Tanenbaum's example. A and B are two 16 KB programs, both compiled on the assumption that they start at address 0. A's first instruction is JMP 24 and B's first instruction is JMP 28. The operating system loads A at address 0 and B right above it, at address 16384.

A runs without trouble. B crashes at its first instruction. JMP 28 wants to jump to the CMP instruction at byte 28 of B. But 28 is an absolute address, and at physical address 28 there is A's ADD instruction. Instead of its own code, B jumps into the middle of A (Figure 8.8).

This is called the relocation problem. The addresses in a program must be corrected according to where the program is loaded in memory. The first solution, found on the IBM 360, is static relocation: when the loader puts the program into memory, it adds the program's starting address to every address word. Since B is loaded at 16384, JMP 28 becomes JMP 16412 (Figure 8.9).

Static relocation has two weaknesses. First, loading becomes slower, because every word of the program has to be examined. The second is subtler: the loader cannot tell which words are addresses and which are ordinary numbers. B's second instruction MOV REG1, 28 loads the number 28 into a register. This 28 is not an address; if 16384 is added to it, the program goes wrong. For the loader to decide correctly, the compiler has to produce extra relocation information indicating which words of the program are addresses.

8.2.3Base and limit registers

The abstraction that solves protection and relocation together is the address space.

Definition 8.2

An address space is the set of addresses a process can use in memory. Each process has an address space of its own, independent of those of other processes.

The simplest hardware for implementing an address space is two registers. The base register holds the process's starting address in memory, and the limit register holds the length of the region. The program is loaded as it is into a contiguous area of memory. In the example of Figure 8.10 the base is 300040 and the limit is 120900. The process can access addresses from 300040 to 300040 + 120900 − 1 = 420939.

These two registers can be loaded only by privileged instructions, in kernel mode. A user program cannot change its own base or limit; if it could, protection would be meaningless. When the operating system switches context, it puts the new process's base and limit values into these registers.

History offers two extreme examples of this arrangement. The CDC 6600 supercomputer worked exactly this way. The segment registers of the Intel 8088 served only as a base; since there was no limit register, there was relocation but no protection.

8.2.4Hardware address protection

Base and limit registers provide protection with two comparisons on every memory access. The address produced by the CPU is first compared with the base: if the address is smaller than the base, a trap occurs. Then it is compared with base + limit: if the address is not smaller than this value, a trap occurs again. If both conditions hold, the access goes to memory (Figure 8.11). The comparisons are made by special hardware working in parallel and do not slow the access down.

In kernel mode there is no check, because the operating system must be able to reach all of memory: loading a process into memory and reading a system-call argument from a user buffer both require it.

Common mistake

Counting the address base + limit as valid. The limit is the length of the region; the valid addresses are base, base + 1, …, base + limit − 1. The last byte of a 120900-byte region is at 300040 + 120899 = 420939. 420940 is already outside the region.

8.2.5Address binding times

On its way from source code to a process in memory, a program passes through several stages (Figure 8.12). The compiler turns main.c into an object file (main.o). The linker combines this file with other object files and static libraries to produce the executable (a.out). The loader brings this file into memory, adds the dynamic libraries, and the process starts to run.

Addresses change form along this journey. In source code addresses are symbolic: the programmer writes a variable called count. The compiler binds this symbol to a relative address: “14 bytes from the start of this module.” The linker or loader converts the relative address into an absolute one, for example 74014. When a symbol is bound to an absolute address determines whether the program can be moved in memory. Table 8.5 compares the three options.

If the starting address changes, the program is reloaded. In execution-time binding, address translation is done on every access while the program runs. A process can be moved from one memory region to another while it is running. Special hardware is needed for this. All of today's general-purpose operating systems use execution-time binding.

8.2.6Logical and physical addresses, the MMU

Execution-time binding separates two kinds of addresses.

Definition 8.3

A logical address, also called a virtual address, is the address the CPU produces. A physical address is the address the memory unit sees, the one loaded into the memory address register (MAR). The set of all logical addresses a program produces is the logical address space, and the set of the corresponding physical addresses is the physical address space.

In compile-time and load-time binding the two addresses are the same. In execution-time binding they differ, and the conversion between them is done at run time by a piece of hardware: the memory management unit (MMU). The program sees and works with logical addresses only; it never sees physical addresses. A C program that prints the value of a pointer therefore always prints a logical address.

Figure 8.13 shows where the MMU sits. In older systems the MMU was a separate chip. In today's processors the MMU, with its TLBs and page-table walker, is inside every core. Every address that goes out on the memory bus is already a physical address.

8.2.7Dynamic relocation with the MMU

In its execution-time form, the base–limit arrangement has the MMU do two jobs. First it compares the logical address with the limit; if the address is not smaller than the limit, it raises a trap. Then it adds the base value to the address and obtains the physical address. Silberschatz calls this register the relocation register; it is the same thing as Tanenbaum's base register.

Example 8.3

Let the limit be 3000 and the base 14000. Where do logical addresses 346, 2999, and 3500 go?

  1. 346. 346 < 3000, valid. The physical address is 346 + 14000 = 14346.
  2. 2999. 2999 < 3000, the last valid logical address. Physical 2999 + 14000 = 16999.
  3. 3500. 3500 ≥ 3000: a trap occurs before any addition. Because the comparison is made on the logical address, the result is the same whatever the base value is.

The program sees itself as occupying 0 through 2999. If the operating system moves the process somewhere else, it changes only the base register; not a single address in the program changes.

This arrangement also rescues program B in the relocation example. For B let base = 16384 and limit = 16384. The instruction JMP 28 stays in memory as it is. When the instruction executes, the MMU compares 28 with the limit, finds it valid, and produces the physical address 28 + 16384 = 16412 (Figure 8.15). Neither static relocation nor extra relocation information is needed; the constant in MOV REG1, 28 never changes, because only addresses that go to memory are translated.

This has a price: every memory access needs an addition and a comparison. The comparison is fast. The addition, because of carry propagation, remains slow relative to an access unless special circuits are used. This price is the first sign of a problem that will grow with paging: address translation lies on the path of every access, and it has to be very fast.

8.3Linking and loading

Loading a program into memory is not as simple as “copy the whole file into memory.” The program refers to libraries; will these libraries be loaded together with the program or separately? Should a large piece of code that may never be used be loaded up front? This section describes today's answers to these questions.

8.3.1Dynamic loading

Dynamic loading means that a routine is not brought into memory until it is called. The main part of the program is loaded and starts to run. When a routine is needed, the program has it loaded itself. Code that is never called is never loaded. This is useful for large but rarely executed parts such as error-handling code.

Dynamic loading needs no special hardware; the program is designed accordingly. The operating system only provides the necessary library functions. On POSIX systems these are dlopen, dlsym, and dlclose; their Windows counterparts are LoadLibrary and GetProcAddress. The program below loads the math library at run time and calls the sqrt function in it.

#include <dlfcn.h>
#include <stdio.h>

int main(void) {
  void *h = dlopen("libm.so.6", RTLD_LAZY);
  if (!h) { puts(dlerror()); return 1; }
  double (*root)(double) =
      (double (*)(double)) dlsym(h, "sqrt");
  printf("%.3f\n", root(2.0));
  dlclose(h);
  return 0;
}

The program runs line by line as follows.

  1. When the program starts, the address space contains only the code of main, the C library (libc), the heap, and the stack. The math library (libm) is not loaded.
  2. The call dlopen("libm.so.6", RTLD_LAZY) runs the dynamic linker (ld.so). The dynamic linker finds the file and maps it into the process's address space with mmap (Figure 8.16). Loading happens at the program's request, now. The returned h is a handle that represents the library; if the file is not found, NULL is returned and dlerror() reports the reason.
  3. dlsym(h, "sqrt") looks up the name sqrt in the library's symbol table and returns its address in this process's address space. The returned void * value is cast to a function pointer that takes a double and returns a double.
  4. The call root(2.0) is made through the function pointer, and 1.414 is printed (√2 in the %.3f format).
  5. dlclose(h) decrements the library's reference count. When the count reaches 0, the library is removed from the address space.

With older glibc versions the option -ldl was needed when compiling this program. Since glibc 2.34 these functions are inside libc and no extra option is needed.

8.3.2Static and dynamic linking

When a program calls a library function, the code of that function has to be somewhere. There are two ways. In static linking the linker (ld) copies the library routines into the executable after compilation; for example ld *.o -lc -lm. In dynamic linking only a small stub is left in the file. The real address of the routine is resolved at run time. Table 8.6 compares the two approaches.

The confusion that results when this precaution is not taken is known in the Windows world as “DLL hell.”

8.3.3Lazy binding: the PLT and GOT

Textbooks usually describe dynamic linking like this: when the stub is called for the first time, it finds the routine's address and replaces itself with that address. This account is conceptually right, but on systems that use ELF files, like Linux, what changes is not the code. The real mechanism rests on two tables.

PLT (procedure linkage table)
A table of small jump stubs in the executable. The program does not call printf directly but calls the stub printf@plt. This is the “stub” of the textbooks.
GOT (global offset table)
A per-process, writable table of addresses. The PLT stub jumps indirectly to the address the corresponding GOT entry points to.

On the first call the GOT entry points not to the real printf but to the dynamic linker's resolver. The resolver looks the symbol up in the loaded libraries, writes the address it finds into the GOT entry, and jumps to printf. Later calls follow the path PLT → GOT → printf; only one indirect jump is added. This arrangement is called lazy binding, because a symbol is resolved only when it is first used. Table 8.7 lists the steps.

Lazy binding has a weakness from the security point of view: because the GOT is writable, an attacker can use a buffer overflow to change an address there and take over control. That is why many distributions compile programs with the -z now option. In this “full RELRO” arrangement all symbols are resolved at load time and the GOT is then made read-only.

Common mistake

Thinking that after the first call the target of the call printf@plt instruction changes, or that the body of libc's printf is rewritten. Neither happens: the code pages are read-only and shared among processes. The only place that changes is the process-specific GOT entry.

8.3.4Building static and shared libraries

Two kinds of library can be built from a C source file (func.c). A static library is built and used with these commands:

$ gcc -c func.c -o func.o
$ ar rcs libfunc.a func.o
$ gcc main.c -o main -static -L. -lfunc
$ ./main

The ar tool gathers object files into a single archive (libfunc.a). The linker copies from this archive only the objects the program actually uses. The -static option asks for the static version of the C library (libc.a) to be used as well; the result is a file that depends on no shared library.

For a shared library the steps are as follows:

$ gcc -fPIC -c func.c -o func.o
$ gcc -shared -o libfunc.so func.o
$ gcc main.c -o main -L. -lfunc
$ export LD_LIBRARY_PATH=$(pwd)
$ ./main
$ ldd ./main   (libfunc.so => ./libfunc.so)

The key option here is -fPIC: position-independent code. Code compiled this way uses no absolute addresses. Jumps are made relative to the program counter, and global data is reached through the GOT. This allows the same physical page to be mapped at a different virtual address in each process. Address space layout randomization (ASLR) also rests on this. The ldd command shows which shared libraries the program will take from which files.

The LD_LIBRARY_PATH variable is handy for experiments but is not a permanent solution. The permanent solution is either to embed the library's search path in the executable (-Wl,-rpath,'$ORIGIN') or to install the library in a system directory and run ldconfig. Today's distributions also compile the programs themselves as position-independent executables (PIE). In this way the program's own code is also loaded at a different address on each run, thanks to ASLR.

8.4Swapping

What happens if the total needs of the processes in memory exceed physical memory? One solution is to move the processes that are not running at the moment to disk temporarily. This idea is called swapping.

8.4.1Standard swapping

In standard swapping an entire process is written temporarily to a backing store, usually a fast disk. When the process is about to run again, it is brought back into memory (Figure 8.20). Thanks to swapping, the total memory needs of the processes can exceed physical memory and more processes can be run at the same time; that is, the degree of multiprogramming rises.

A process returning from a swap may be placed not at its earlier location in memory but in some other place that happens to be free. That is why swapping requires execution-time binding. A process bound at compile or load time can return only to exactly its old place.

The cost of standard swapping is the transfer time. In Silberschatz's example a 100 MB process is written to a disk with a transfer rate of 50 MB/s. Writing it out takes 100 / 50 = 2 s and reading it back takes another 2 s; the round trip is 4 seconds. During this time the swapped process cannot run.

There is one more constraint in choosing the process to swap: a process with a pending I/O operation should not be swapped out. If the process is waiting for data from a device, the device will write the data into the process's buffer by direct memory access (DMA). If the process is swapped out and another is loaded in its place, the DMA transfer writes to the old physical address, that is, now into another process's memory. The remedy is either not to swap such a process or always to perform I/O through kernel buffers.

Example 8.4

A 200 MB process is swapped to a disk with a transfer rate of 50 MB/s; latencies are ignored. How long does the round trip take?

  1. Out. 200 / 50 = 4 s.
  2. In. Again 4 s.
  3. Total. 8 s. Considering that a time slice is tens of milliseconds, it is clear why moving a whole process is not acceptable today.

8.4.2Page swapping and today's systems

Today the sizes of processes are measured in gigabytes. A 1 GiB process takes about 2 × 1.07 / 3 ≈ 0.72 s for a round trip even on an NVMe SSD with a 3 GB/s read-write rate. That is why Linux, Windows, and macOS swap processes not as wholes but page by page (Figure 8.21). Only pages that have not been used for a long time, the “cold” pages, go to disk. A 4 KiB page comes back in tens of microseconds.

Today's systems use one more intermediate step before going to disk: compression. Cold pages are first compressed in memory to make them smaller. In Linux zswap and zram, in Windows memory compression, and in macOS the compressor do this. Decompressing a compressed page is much faster than reading it from disk.

On mobile systems the situation is different. The write endurance of flash memory is limited, and every write costs energy. That is why phones have either no traditional swap or a very limited one. Android compresses with zram; if memory is still short, lmkd kills background applications. iOS also uses compression and kills applications when necessary (jetsam). From the user's point of view this shows up as an application restarting from scratch when one returns to it in the background.

8.5Contiguous allocation

In a system that works with base and limit registers, each process occupies a single unbroken region of memory. This section describes how free regions are chosen in such a system and why, over time, they break up into small, useless pieces.

8.5.1Contiguous memory allocation

Memory is first divided into two regions: one for the operating system and the other for user processes. The operating system can be placed at the low or the high end of memory. The Linux and Windows kernels put it at high addresses. In the user region each process occupies a single contiguous region, and protection is provided by the base–limit registers.

Definition 8.4

Contiguous allocation is giving each process a memory region made up of a single run of consecutive addresses.

There are two ways of dividing the user region among processes. In fixed partitioning memory is divided in advance into a certain number of partitions of certain sizes; the MFT version of IBM OS/360 worked this way. One process goes into each partition, so the number of partitions determines the number of processes that can be in memory at once, that is, the degree of multiprogramming. If a small process goes into a large partition, the rest of the partition is wasted. In variable partitioning (OS/360 MVT), each process is given exactly the space it needs. The free blocks left between processes are called holes.

There is one more problem: processes grow. A program asks for space from the heap with malloc, and function calls deepen the stack. If another process sits right above a contiguous region, growth is impossible. That is why processes are left some room to grow from the start (Figure 8.22). In (a) only the data segment grows. In (b) the stack grows from top to bottom and the data from bottom to top, and the spare room lies between the two. When the process is swapped out and brought back, only the part it uses is moved, not the free room.

8.5.2Variable partitioning

In variable partitioning the operating system keeps a table or list: which regions belong to which processes and which regions are holes. When a process arrives, a hole large enough to take it is found. The process is placed at one end of the hole, and the remainder stays as a smaller hole. When the process ends, its space returns to the hole list and is merged at once with neighboring holes.

8.5.3Placement algorithms

If several holes could take an incoming request, which should be chosen? The classic answers to this question are as follows.

First fit
The list is scanned from the start and the search stops at the first hole that is large enough. It is fast. Over time, small holes accumulate at the head of the list.
Next fit
A variant of first fit; the search continues from where the previous search stopped, not from the start. In Bays's 1977 simulations it gives slightly worse results than first fit.
Best fit
The whole list is scanned and the hole closest in size to the request is chosen. It is slow unless the list is kept sorted by size. It leaves behind holes too small to be of any use.
Worst fit
The largest hole is chosen; the aim is for the remainder to stay large enough to serve another request. It does not give good results in simulations.
Quick fit
Separate lists are kept for frequently requested sizes (4 K, 8 K, 12 K …). Finding a suitable hole is very fast; but finding the neighbors of a freed block and merging them is expensive.

All the algorithms can be sped up by keeping separate lists for processes and holes: the search is then made in the hole list only. Today's malloc implementations (jemalloc, tcmalloc) use a generalized form of quick fit, size classes. The outcome of the simulations reported by Silberschatz and Knuth is clear. In terms of both time and memory utilization, first fit and best fit are better than worst fit. First fit is usually faster.

8.5.4Code trace: best fit

The function below performs a best-fit search in an array holding hole sizes. It shrinks the hole it finds by the size of the request and returns the hole's index; if there is no room it returns −1.

int best_fit(int hole[], int n, int req) {
  int best = -1;
  for (int i = 0; i < n; i++)
    if (hole[i] >= req &&
        (best == -1 || hole[i] < hole[best]))
      best = i;
  if (best != -1) hole[best] -= req;
  return best;
}
/* hole = 120, 450, 230, 300, 180 (K) */
/* best_fit(hole, 5, 210); best_fit(hole, 5, 160); */

The first is that the hole is large enough for the request (hole[i] >= req). The second is that either there is no candidate yet or this hole is smaller than the current candidate. If both hold, the candidate changes. When the loop ends, the chosen hole is shrunk by the size of the request. The function walks the whole list on every call, so it spends O(n) time for n holes.

In this sequence only best fit can place all four requests. In the others the total free space is more than 426 K, but it is not a single piece.

This result does not mean that best fit is always superior. The example is a sequence in which keeping the large hole whole pays off. With other sequences the outcome changes. Take, for instance, holes of 150, 400, 80, 250, and 600 K and requests of 230, 120, 380, and 90 K. This time worst fit cannot place the 380 K request, while first fit and best fit satisfy all four requests.

Common mistake

In worst fit, still counting the hole chosen by the first request as the largest hole for later requests. Holes shrink after every placement. After 212 K the 600 hole drops to 388; for 417 K the largest hole at that moment is now 500.

8.5.6Internal and external fragmentation

The problem that arises in variable partitioning and that we saw in the earlier examples is called external fragmentation.

Definition 8.5

External fragmentation is the situation in which there is enough total free memory to satisfy a request but that memory is not contiguous. Internal fragmentation, on the other hand, is the situation in which the block given to a process is larger than requested and the difference is wasted inside the block.

The extent of external fragmentation is summarized by Knuth's 50-percent rule. In a system running first fit, with N allocated blocks, on average about 0.5 N blocks are lost to fragmentation. The share of lost blocks is 0.5 N / (N + 0.5 N) = 1/3; that is, one third of memory can become unusable.

Internal fragmentation appears in every arrangement that works with fixed-size blocks: in fixed partitioning, in paging, and in the buddy system described below. Tanenbaum's example shows an interesting cause as well (Figure 8.26). If there is a hole of 18,464 bytes and a process of 18,462 bytes arrives, a hole of 2 bytes would be left. The cost of tracking these 2 bytes as a separate hole in the list is greater than the hole itself. So the process takes all 18,464 bytes, and 2 bytes are wasted inside the block.

External fragmentation has two remedies. The first is compaction: processes are shifted and the holes are gathered into a single block. The second is more radical: remove the requirement that a process's address space be contiguous in physical memory. Paging and segmentation follow this second route.

A well-known source of internal fragmentation is the buddy system, which is also used in Linux for allocating physical frames. In this scheme blocks are always a power of two in size. A request is rounded up to the smallest power of two that satisfies it. If there is no free block of the right size, a larger block is split in two; the two halves are called each other's “buddies.” When a block is freed and its buddy is also free, the two merge again. The buddy's address is found with a single XOR: address ⊕ size.

Example 8.6

In a buddy system that starts with one free block of 1024 K, let A = 100 K, B = 240 K, C = 64 K, and D = 256 K be requested in turn. Where do the blocks go and how much internal fragmentation results?

  1. A = 100 K. Rounded up to 128 K. 1024 is split (512 + 512), the left 512 is split (256 + 256), the left 256 is split (128 + 128). A gets the 128 K block at address 0. Internal fragmentation 28 K. Free: 128 K @ 128, 256 K @ 256, 512 K @ 512.
  2. B = 240 K. Rounded up to 256 K and goes into the free block at 256. Internal fragmentation 16 K.
  3. C = 64 K. Exactly 64 K. The free block at 128 is split (64 + 64); C takes the half at 128. Free: 64 K @ 192, 512 K @ 512.
  4. D = 256 K. There is no free 256 K block; the block at 512 is split and D takes the half at 512. Free: 64 K @ 192, 256 K @ 768.
  5. Freeing. When A is freed, its buddy (0 ⊕ 128 = 128) is inside C's region, so there is no merging. When C is freed, its buddy at 192 is free: 128 K @ 128 results; its buddy, the block at 0 that was A's, is free too: 256 K @ 0 results. When B and D are also freed, the blocks merge up to 512 and then to 1024.

Total internal fragmentation is 28 + 16 = 44 K. (Traced step by step with Python.)

8.5.7Compaction

Definition 8.6

Compaction is shifting the processes in memory toward one end and gathering all the holes into a single large block.

Figure 8.27 shows the initial state. The operating system is at 0–128 K. P1 starts at 128 (160 K), P2 at 384 (192 K), P3 at 640 (128 K), and P4 at 928 (64 K). Between them are four holes of 96, 64, 160, and 32 K; although there is a total of 352 K of free space, the largest hole is 160 K.

Compaction moves the processes down in turn. P1 is already right above the operating system. P2 moves from 384 to 288 (128 + 160). P3 moves from 640 to 480 (288 + 192), and P4 from 928 to 608 (480 + 128). In the end a single 352 K hole remains between 672 and 1024 (Figure 8.28). For this, 192 + 128 + 64 = 384 K has been copied. The base register of each moved process is updated with the new address.

Compaction is possible only in systems that use execution-time binding. If the addresses in a process were fixed at load time, after the process is moved they would point to the wrong places. In a system that uses a base register, only the value of the register changes.

Compaction is expensive. By Tanenbaum's calculation, a machine that copies 8 bytes in 8 ns, that is, 1 GB per second, compacts 16 GB of memory in about 16 s. Even at today's copy rate of about 20 GB/s the job takes about a second (16 / 20 = 0.8 s; ≈ 0.86 s for 16 GiB). The processes stop in the meantime. Compaction must not be confused with data compression. The aim is not to make data smaller but to make blocks adjacent.

Compaction has not entirely become history, either. To produce contiguous physical frames for huge pages, Linux performs page migration in the background; the kcompactd kernel thread does this work.

8.6Free-space management

The placement algorithms all rest on the same information: which regions are free? How this information is kept determines how fast searching and freeing can be. There are two basic structures: the bitmap and the linked list.

8.6.1Bitmaps and linked lists

Memory is first divided into fixed-size allocation units; a unit can be a few words or a few kilobytes.

Definition 8.7

A bitmap is an array that keeps one bit for each allocation unit: 0 shows that the unit is free and 1 that it is in use. In the linked-list approach, a node is kept for every process and every hole; the node holds the kind (P: process, H: hole), the starting unit, and the length.

8.6.2Code trace: searching for free space in a bitmap

The weakness of the bitmap is searching. Finding room for a process of k units means finding k consecutive 0s in the array. The function below does this with a linear scan.

/* find k consecutive free (0) units */
int find(const char bit[], int n, int k) {
  int start = 0, len = 0;
  for (int i = 0; i < n; i++) {
    if (bit[i] == 0) {
      if (len == 0) start = i;  /* new run */
      if (++len == k) return start;
    } else
      len = 0;                /* run broken */
  }
  return -1;
}

len holds the length of the run of zeros currently in progress, and start the index at which the run began. When a 0 is seen and the run has just begun (len == 0), the start is recorded and the length goes up by one. When the length reaches k, the start is returned. 8.7Paging

All the problems of contiguous allocation come from a single assumption: that the process sits in one piece in physical memory. Paging removes this assumption. The process is divided into small, equal pieces, and each piece can be put in any free place in memory. All of today's general-purpose operating systems use paging.

8.7.1The basic idea

Definition 8.8

In paging, physical memory is divided into fixed-size blocks, frames. Logical memory is also divided into blocks of the same size, pages. Each process has a page table; the table records in which frame each page of the process is located.

The consequences of this arrangement are seen at once. The process's location in physical memory need not be contiguous; consecutive pages can sit in frames far apart (Figure 8.33). Hence there is no external fragmentation: every free frame is suitable for every page of every process. For a process of N pages, any N free frames are enough. Internal fragmentation remains only in the last page of the process, because the process size need not be an exact multiple of the page size.

The operating system keeps track of which frames are free and builds each process's page table. The backing store used for swapping is also divided into blocks of the same size; thus a page can be written to any block on disk and read back into any frame.

8.7.2Splitting the address into (p, d)

In paging, every logical address the CPU produces is split into two parts: the page number p and the offset d within the page. If the logical address space is 2m bytes and the page size is 2n bytes, the low n bits of the address give the offset and the upper m − n bits give the page number (Figure 8.34).

The page table translates p into a frame number f. The offset never changes. The physical address is found by adding the offset to the start of the frame:

p = ⌊a / page size⌋,   d = a mod page size,   physical = f × page size + d

Because the page size is a power of two, this division and remainder are a bit shift and a mask. With 4 KiB pages, p = a >> 12 and d = a & 0xFFF. The hardware does this for free; a page size that is not a power of two would need a real divider circuit.

8.7.5Page size and internal fragmentation

In paging, internal fragmentation arises only in the last page, but it is important enough to influence the choice of page size.

Example 8.10

The page size is 2048 bytes and the process is 72,766 bytes. How many frames does the process occupy, and how much internal fragmentation results?

  1. Division. 72,766 = 35 × 2048 + 1086. The process occupies 35 full pages and a remainder of 1086 bytes.
  2. Frames. The remainder also needs a frame: 36 frames.
  3. Internal fragmentation. In the last frame 2048 − 1086 = 962 bytes are wasted.

In the worst case the process spills over a page by only one byte, and the internal fragmentation is one page minus one byte. If process sizes are randomly distributed, the average internal fragmentation is half a page. This is an argument in favor of small pages. On the other hand, small pages mean more pages and hence a larger page table and more TLB misses. Large pages give more efficient transfers between disk and memory and fewer table entries.

Tanenbaum measures this trade-off with a simple model. Let the average process size be s bytes, the size of a table entry e bytes, and the page size p. A process needs about s / p pages and s·e / p bytes of table per process; the internal fragmentation is p / 2 on average. The total overhead is:

overhead = s·e / p + p / 2

As p gets smaller the first term grows, and as it gets larger the second term grows. Differentiating and setting the derivative to zero gives −s·e / p2 + 1/2 = 0, that is, p = √(2·s·e). For s = 1 MiB and e = 8 bytes, p = √(2 × 220 × 8) = √(224) = 212 = 4096 bytes (Figure 8.37). At this value the overhead is 2048 + 2048 = 4096 bytes; with pages of 2048 and 8192 bytes it rises to 5120 bytes.

Real systems stay in this neighborhood too. On x86-64 the base page is 4 KiB; there are also huge pages of 2 MiB and 1 GiB. ARM64 can use pages of 4, 16, or 64 KiB; Apple Silicon uses 16 KiB.

8.7.6Free frames

When a new process arrives, the operating system takes as many frames from the free-frame list as the process has pages and fills in the page table. In the example of Figure 8.38 the free list is 14, 13, 18, 20, 15. A process of four pages takes the first four frames of the list: page 0 → 14, 1 → 13, 2 → 18, 3 → 20. Only 15 stays on the list.

For this the operating system keeps a frame table: for every physical frame, whether the frame is free and, if it is in use, which page of which process it holds. This table is needed not only for allocation but for other jobs as well. For example, when a process gives a buffer address to the read system call, this address is logical. To be able to write the data there, the kernel translates the address into a physical address with the process's page table.

Because each process has a separate page table, on a context switch the hardware must be pointed at the new process's table. The dispatcher does this by updating a register; on x86 this register is CR3. This extra work lengthens the context-switch time.

8.7.9Protection bits

In paging, protection is also done at the page level. The permission bits are kept separately in every PTE and are checked on every access, together with the TLB entry.

Read / write (R/W)
Code pages are mapped read-only; an attempt to write to code produces a protection fault.
User / supervisor (U/S)
Kernel pages cannot be accessed in user mode. In this way the same table can hold both the kernel's and the process's mappings.
No-execute (NX / XD)
Code cannot be executed from data, stack, and heap pages. Operating systems enforce the W^X rule: a page is either writable or executable, never both. In this way attack code written onto the stack cannot be executed.
SMEP / SMAP
While in kernel mode, they prevent the execution of code in user pages (SMEP) and unauthorized access to user data (SMAP).
Protection keys (PKU)
With a 4-bit key in the PTE and a user register (PKRU), the permission of a group of pages can be changed without a system call.
Valid / invalid
The crudest form of access permission: if the page does not exist in the address space at all, every access is a trap.

8.7.10Shared pages

An important gain of paging is that common code can be shared easily. Reentrant code, that is, code that does not modify itself while running, can be shared among many processes. If three users run the same text editor, the editor's code pages are in memory only once. Each process's page table points to these frames; only the data pages are separate for each process (Figure 8.41).

Shared libraries are shared in this way too. Sharing has a consequence: when the process that “owns” a page terminates, the frame cannot be freed at once, because other processes may be using it. That is why a reference count is kept for every shared frame.

Today's systems have other forms of sharing as well. On a fork() call the parent and child share all pages by copy-on-write (COW). The pages are marked read-only in both processes; when one of the processes tries to write to a page, a protection fault occurs and the kernel makes a copy of only that page. Memory-mapped files (mmap) and shared memory (shm_open), on the other hand, let two processes see the same frames; the processes communicate without copying data.

8.8The TLB

Paging eliminates external fragmentation, but it has a price: every memory access first needs a table access. This section describes how this price is brought down to almost nothing.

8.8.1Where does the page table live?

If the page table were small, it could be kept inside the processor in special registers. But with a 32-bit address and 4 KiB pages a table has 220, that is, more than a million entries. That many entries do not fit in registers. The table therefore lives in main memory. Its starting address is held in the page-table base register (PTBR); on x86 this register is CR3, and on ARM it is TTBR0/TTBR1. On a context switch only this register changes.

The problem with this solution is obvious: every data access is now two memory accesses. First the entry at address PTBR + p is read, then the data is accessed. The memory access time doubles. The solution is a small hardware cache that holds recently used translations.

Definition 8.9

The TLB (translation look-aside buffer) is a small, fast, associative cache inside the MMU. It holds recently used (page number, frame number) pairs. Being associative means that a page number is compared with all the entries at the same time, in parallel.

Translation proceeds as follows (Figure 8.42). When the CPU produces an address, the page number is first looked up in the TLB. If it is found (a TLB hit), the frame number is obtained at once and no table access is made. If it is not found (a TLB miss), the table in memory is reached through the PTBR, the entry is read, and it is loaded into the TLB for the next access. If the TLB is full, an entry is evicted.

In today's processors each core typically has an L1 TLB of 64 entries and an L2 TLB of 1–3 thousand entries. TLB entries can be tagged with an address-space identifier (ASID; PCID on Intel). In this way each entry knows which process it belongs to, and the TLB need not be flushed on a context switch.

8.8.2Tracing TLB hits and misses

Let the page table of Tanenbaum's MMU example (0 → 2, 2 → 6, 5 → 3, 9 → 5, 11 → 7) now be used with a TLB. The TLB has 4 entries and evicts the least recently used (LRU) entry when room is needed. The TLB starts out empty. The pseudocode below summarizes what is done on each access.

p = addr / 4096;  d = addr % 4096;

  f = page_table[p];
  if (TLB full) evict the oldest entry;
  add (p, f) to the TLB;
}
physical = f * 4096 + d;

8.8.3Effective access time

The gain from the TLB is measured with a single number.

Definition 8.10

The effective access time (EAT) is the average memory access time, found by taking into account the probabilities of TLB hits and misses. If the TLB lookup time is ε, the memory access time t, and the TLB hit ratio α, then for a single-level table:

EAT = (t + ε) · α + (2t + ε) · (1 − α) = 2t + ε − t · α

The logic of the formula is simple. On a hit the TLB is consulted and a single memory access is made: t + ε. On a miss the TLB is consulted, and then one memory access is made for the table entry and one for the data: 2t + ε. The average is the sum of these two times weighted by their probabilities.

Example 8.11

Let ε = 20 ns and t = 100 ns. What is the effective access time for α = 80% and α = 98%?

  1. Two cases. Hit: 20 + 100 = 120 ns. Miss: 20 + 100 + 100 = 220 ns.
  2. α = 80%. 120 × 0.80 + 220 × 0.20 = 96 + 44 = 140 ns. With the closed form, 2 × 100 + 20 − 100 × 0.80 = 140 ns.
  3. Interpretation. Without a TLB every access would take 200 ns; 140 ns is better than that, but it is still 40% slower than the plain memory time.
  4. α = 98%. 120 × 0.98 + 220 × 0.02 = 117.6 + 4.4 = 122 ns. The slowdown falls to 22%. In real workloads the ratio is usually above 99%; at α = 99% the EAT is 121 ns.

With multilevel tables a miss is much more expensive. In x86-64's four-level table a miss needs four table accesses and one data access: 20 + 4 × 100 + 100 = 520 ns. In that case for α = 98% the EAT = 120 × 0.98 + 520 × 0.02 = 117.6 + 10.4 = 128 ns, and for α = 99% it is 118.8 + 5.2 = 124 ns. The more expensive a miss is, the more the hit ratio matters. That is why the hardware also keeps the intermediate levels of the table walk in a separate cache (a page walk cache). A real miss thus often comes down not to four but to one or two memory accesses.

Example 8.12

The memory access takes 80 ns, the TLB lookup 10 ns, the table is single-level, and the hit ratio is 95%. (a) What is the EAT? (b) What must the hit ratio be at least for the EAT to fall to 92 ns?

  1. Two cases. A hit takes 10 + 80 = 90 ns, a miss 10 + 80 + 80 = 170 ns.
  2. (a) 0.95 × 90 + 0.05 × 170 = 85.5 + 8.5 = 94 ns.
  3. (b) 90α + 170(1 − α) ≤ 92 → 170 − 80α ≤ 92 → α ≥ 78 / 80 = 0.975. The hit ratio must be at least 97.5%.

It is also instructive to count the effect of the TLB over a loop.

Example 8.13

  2. No TLB. A PTE is read before every access: 10 per iteration, 10 × 1000 = 10,000 accesses in total.
  3. With a TLB. To the 5 × 1000 = 5000 accesses are added only the PTE reads on TLB misses. The array lies between 40,000 and 43,999 and spans pages ⌊40,000 / 4096⌋ = 9 and ⌊43,999 / 4096⌋ = 10. Together with the code page there are three misses: 5000 + 3 = 5003 accesses.

8.9Page-table structures

A single-level, linear page table works for small address spaces. As the address space grows, the table itself becomes a memory problem. This section describes three ways of shrinking the table: hierarchical, hashed, and inverted tables.

8.9.1The hierarchical page table

With a 32-bit address and 4 KiB pages, a single-level table has 220 entries; with 4-byte entries the table takes 4 MiB. This table must be separate for each process and contiguous in memory. In a system with 100 processes, the page tables alone amount to 400 MiB. On 64 bits the situation is far worse. With 4 KiB pages and 8-byte entries, a single-level table takes 252 × 8 B = 32 PiB, about 33.6 million GiB. Even if only 48 bits of the address are used, 236 × 8 B = 512 GiB is needed.

The solution is to page the table itself. The virtual address is split into two indexes and an offset. On 32-bit x86, 10 bits index the top-level table (the page directory), 10 bits index the second-level table, and 12 bits are the offset (Figure 8.45). What is split here is not the table entry but the virtual address.

Definition 8.11

A hierarchical page table is a page table kept as a multilevel tree. Each entry of the top-level table points to a lower-level table; only the regions in use have lower-level tables.

The gain comes from sparse address spaces. Consider a process that uses 4 MiB of code, 4 MiB of data, and 4 MiB of stack. Each second-level table covers a region of 1024 pages × 4 KiB = 4 MiB. For this process one top-level table and three lower tables are enough: 4 × 4 KiB = 16 KiB. A single-level table would take 4 MiB. The lower tables of unused regions are never created; their entries in the top-level table are simply marked “absent.”

8.9.2A two-level translation example

Example 8.14

In Tanenbaum's example the virtual address is 0x00403004 (4,206,596). This address lies between 4 MiB and 8 MiB, in the data region. How is it translated in a two-level table?

  1. Splitting. 0x00403004 = 0000000001 0000000011 000000000100. The upper 10 bits give PT1 = 1, the middle 10 bits PT2 = 3, and the offset = 4.
  2. Top-level table. Entry 1 of the top-level table points to the second-level table of the 4–8 MiB region. Each top-level entry covers a region of 4 MiB.
  3. Second level. Entry 3 of that table is consulted. This entry is the page at byte range 12,288–16,383 within the region; in absolute terms 4,206,592–4,210,687. If the entry's present bit were 0, a page fault would occur.
  4. Physical address. The entry gives the frame number (0x1F3 in the example). The offset is added: 0x1F3004.

On a TLB miss this translation needs two table accesses and one data access. The frame numbers in the example are for illustration.

On 32-bit x86 the address of the top-level table is in CR3. Each of the tables at the two levels fills exactly one 4 KiB page: 1024 entries × 4 bytes. This choice is no coincidence. That a table fits exactly in a page means that the lower tables can be placed in any frame like ordinary pages and, if necessary, swapped to disk.

8.9.3Code trace: two-level translation

What the MMU does can be written in C as follows:

/* 32 bits: 10 + 10 + 12 bits */
uint32_t translate(uint32_t va) {
  uint32_t p1 = va >> 22;
  uint32_t p2 = (va >> 12) & 0x3FF;
  uint32_t d  = va & 0xFFF;
  pte_t e1 = outer[p1];
  if (!e1.p) page_fault(va);
  pte_t e2 = e1.table[p2];
  if (!e2.p) page_fault(va);
  return (e2.frame << 12) | d;
}

va >> 22 takes the upper 10 bits. (va >> 12) & 0x3FF first drops the offset and then keeps the lower 10 bits, that is, the middle index. va & 0xFFF is the offset. The function goes to the entry of the top-level table and from there to the entry of the second-level table; at both steps it raises a page fault if the present bit is 0. At the end it shifts the frame number left by 12 bits and combines it with the offset.

  2. Total. 4 lower tables + 1 top-level table = 5 tables = 20 KiB. A linear table would be 4 MiB.

8.9.4x86-64: four- and five-level paging

On x86-64 each page table is 512 entries × 8 bytes = 4 KiB; that is, again exactly one page, and each level uses a 9-bit index. With four levels and a 12-bit offset, 4 × 9 + 12 = 48 bits of virtual address are obtained; this is an address space of 256 TiB (Figure 8.48). The levels are named, from top to bottom, PML4, PDPT, PD, and PT.

The upper 16 bits of a 64-bit address are unused, but they cannot be arbitrary either: all of them must be copies of bit 47. Such addresses are called canonical addresses. As a result the address space is divided in two: the lower half goes to the user and the upper half to the kernel. Five-level paging (LA57) adds a PML5 level and gives a 57-bit, 128 PiB virtual address. Intel Ice Lake server processors and AMD Zen 4 and later support it; Linux has been able to use it since 4.14.

This is why the hierarchical table works on 64 bits too: not all 64 bits are used, and the address space in use is sparse. Today's x86-64 and ARMv8 use exactly a hierarchical table. If the PS bit in an intermediate-level entry is 1, the walk ends there: a huge page has been found, 2 MiB at the PD level or 1 GiB at the PDPT level.

8.9.5The four-level walk

Example 8.16

How is VA = 0x00007FFE12345678, an address near the user stack, translated in four levels?

  1. Splitting (9 + 9 + 9 + 9 + 12). PML4 = (VA >> 39) & 0x1FF = 255, PDPT = (VA >> 30) & 0x1FF = 504, PD = (VA >> 21) & 0x1FF = 145, PT = (VA >> 12) & 0x1FF = 325, offset = 0x678.
  2. PML4. CR3 gives the frame of the PML4 table (0x1A2B). Entry 255 is read; the frame of the PDPT table is 0x3C4.

Common mistake

Using a 10-bit index on x86-64 as on 32-bit x86. Because the entry grows to 8 bytes, 512 entries fit in a 4 KiB table; the index is 9 bits. Indexes are masked with 0x1FF, not 0x3FF.

8.9.6Huge pages

Programs with a large working set, such as databases, virtual machines, and AI workloads, suffer constant TLB misses with 4 KiB pages. The measure of the problem is the TLB reach: the number of entries × the page size. A TLB of 1536 entries covers only 6 MiB with 4 KiB pages; with 2 MiB pages the same TLB covers 3 GiB (Figure 8.50).

The table size shrinks as well. Mapping 1 GiB with 4 KiB pages takes 230 / 212 = 262,144 PTEs, that is, a 2 MiB table. With 2 MiB pages only 512 PD entries, that is, 4 KiB, are enough.

Linux offers huge pages in three forms. hugetlbfs is for programs that explicitly ask for pre-reserved 2 MiB or 1 GiB pages. With transparent huge pages (THP), the kernel maps suitable regions with huge pages on its own. mTHP in recent versions uses intermediate sizes of 16–64 KiB. On Windows the same job is done by “large pages.”

Huge pages have two costs: internal fragmentation increases, and a contiguous 2 MiB physical region has to be found. The problem of finding contiguous regions explains why the buddy allocator and compaction are still important today. ARMv8 offers an intermediate solution to this problem: 16 adjacent 4 KiB entries marked with the contiguous bit can be held as a single TLB entry, as 64 KiB.

8.9.7The hashed page table

For address spaces larger than 32 bits, another approach is the hash table.

Definition 8.12

In a hashed page table the virtual page number is passed through a hash function. Each bucket of the table is a linked list of the entries (virtual page, frame, next) that fall on the same hash value.

Example 8.17

In a table with 8 buckets, h(p) = p mod 8. The chain of bucket 2 is (p = 10 → f = 7), (p = 26 → f = 3). Where is virtual address 0x1A0AB translated to? (4 KiB pages)

  1. Splitting. p = 0x1A = 26, d = 0x0AB.
  2. Hash. h(26) = 26 mod 8 = 2.
  3. Chain. The first entry is p = 10: no match, move on to the next. The second entry is p = 26: it matches, frame 3.
  4. Physical address. 3 × 4096 + 0xAB = 0x30AB.

The size of a hash table is proportional to the number of pages in use, not to the size of the address space. This is an attractive property for sparse 64-bit address spaces. In the clustered variant each entry holds the frames of several (for example 16) consecutive pages instead of a single page. This variant suits address spaces that are sparse but locally dense.

8.9.8The inverted page table

In all the tables so far there was one table per process, and the size of the table depended on the virtual address space. The inverted table turns the point of view around.

Definition 8.13

An inverted page table is a single table in the system that keeps one entry per physical frame. Each entry records which page of which process is in that frame, that is, a (pid, page) pair. The index of the entry is the frame number.

Translation is a search. For the address (pid = 2, p = 5, d = 0x123) the table is scanned from the start. Entry 0 (1, 0), entry 1 (2, 3), entry 2 (1, 5), and entry 3 (3, 1) do not match. Entry 4 (2, 5) matches. Since the index itself is the frame number, the physical address is 4 × 4096 + 0x123 = 0x4123 (Figure 8.52).

The size of the table is proportional to physical memory and independent of the number of processes. With 16 GiB of RAM and 4 KiB frames there are 4,194,304 entries; with 8 bytes per entry the table takes 32 MiB. This is a single table for the whole system.

There are three costs. The first is searching: a linear scan is unacceptably slow on every access. Real systems therefore hash the (pid, p) pair, go straight to the relevant entry, and put a TLB in front. The second is sharing: since a frame can hold only one (pid, page) pair, shared memory becomes hard. The third is page faults: the place on disk of a page that is not in memory cannot be found in the inverted table; for this a separate external table per process is needed. The PowerPC and IBM POWER architectures use a hashed inverted table; IA-64 also adopted this approach.

8.10Segmentation

Paging is a mechanism completely hidden from the programmer: the address space is a one-dimensional array of bytes, and page boundaries have nothing to do with the logical structure of the program. Segmentation, on the other hand, divides the address space according to the program's own parts.

8.10.1Why segmentation?

Tanenbaum's example is a compiler. While running, a compiler builds many tables: the source text, the symbol table, the table of constants, the parse tree, and the call stack. All of these tables grow and shrink during the run. In a one-dimensional address space each table is given a consecutive region. When a table fills up, it collides with its neighbor even if the neighbor has free space (Figure 8.53). The symbol table overflows into the source text's region; the compiler either stops or has to shift the tables by hand.

Definition 8.14

Segmentation is giving a process several independent, variable-length address spaces. Each address space is called a segment. An address has two parts: (segment number, offset within the segment).

Segmentation matches the programmer's view. The programmer thinks of the program not as a single array of bytes but as separate units such as the main program, functions, the stack, arrays, and the symbol table. Segmentation gives each of these units its own address space. Each segment starts at 0 and can grow and shrink without affecting the other segments.

8.10.2Translation with the segment table

Translation is done with a segment table. Each entry of the table holds the base (physical starting address) and the limit (length) of one segment. The location of the table in memory is held by the segment-table base register (STBR), and the number of entries by the segment-table length register (STLR). For an address (s, d) the hardware first checks the condition d < limit[s]. If it holds, the physical address is base[s] + d; if not, a trap occurs. Segmentation is really a separate base–limit pair for each segment.

The segment number need not be a separate part of the address; the upper bits of the virtual address can also select the segment. In an example similar to the one in OSTEP, the virtual address is 14 bits (16 KiB). The upper two bits select the segment: 00 code, 01 heap, 11 stack. Protection bits also make sharing possible. A code segment with r-x permission can be mapped to the same physical region in many processes. Because the segment is read-only, if one of the processes tries to write to it, a protection fault occurs and the others are not affected.

8.10.4Pros and cons of segmentation

The advantages of segmentation come from the logical structure of the program:

  • Tables that grow or shrink do not affect one another.
  • Segments can be compiled separately. If a function is in its own segment, the addresses of the other segments do not change when the function changes.
  • A library can be put in a separate segment and shared among processes.
  • Protection is set per segment: code is only executable, constants only readable, data readable and writable.

The disadvantages are familiar from contiguous allocation. Segments are of variable length; as they move around in memory, holes form between them. This external fragmentation is also called checkerboarding because of its pattern (Figure 8.56). The remedy is again compaction. In addition, a segment has to be in memory in its entirety; a very large segment may not fit in memory. The solution to this last problem is to page the segments as well; MULTICS and the Intel 386 followed this route.

8.11Real architectures and practice

8.11.1x86: segmentation, paging, and the flat model

The x86 family carries the whole history of segmentation. In the 8086's real mode the physical address is computed as segment × 16 + offset. The result is 20 bits, giving a 1 MiB address space; there is no protection. In the 80386's protected mode, a logical address consists of a selector and an offset. Of the 16-bit selector, 13 bits are the index, one bit selects the table (GDT or LDT), and two bits are the requested privilege level (RPL). The selector picks an 8-byte descriptor from the table; the descriptor holds the base and limit of the segment. Base + offset gives the linear address. The linear address then goes through two-level paging and is translated into a physical address (Figure 8.58). This is the hardware counterpart of MULTICS's idea of “paged segments.”

Despite this rich hardware, Linux and Windows effectively turned segmentation off even on 32 bits. All segments were given base 0 and limit 4 GiB. The linear address is then the same as the logical address; this is called the flat model. Protection is provided entirely by page bits. One reason for this is portability: segmentation existed only on x86, whereas paging exists on every architecture.

The long mode of x86-64 reflected this in hardware. The bases of the CS, DS, ES, and SS segments are taken as 0 by the hardware and the limit is not checked. Only the bases of the FS and GS segments are still used: in user space to point to thread-local storage (TLS), in the kernel to point to per-CPU data. CS additionally carries the current privilege level.

8.11.3Separating policy from mechanism

The operating system takes part in paging at four moments. When a process is created, the page table is built. On a context switch the new process's table is activated and the TLB is set up. On a page fault the missing page is brought in. When the process terminates, the frames and the swap space are released.

Some of these jobs depend on the machine (the MMU's table format) and some do not (which page is placed where and when). The Mach kernel made this distinction explicit. The mechanism stayed in the kernel: a machine-dependent MMU handler and a machine-independent page-fault handler. The policy was given to an external pager running in user space (Figure 8.60). On a page fault, the handler in the kernel asks the external pager for the needed page. The pager reads the page from disk and hands it back. The MMU handler then maps the page into the process's address space.

This design gives flexibility and modularity: different applications can use different paging policies. The price is crossing the user–kernel boundary several times on every page fault. The idea has present-day counterparts too. Linux's userfaultfd mechanism forwards page faults to a program in user space; live migration of virtual machines and freezing a process and resuming it on another machine (CRIU) rest on it. In microkernels such as seL4 and Fuchsia the pager is already in user space.

8.12Summary

  • The CPU reaches only registers and main memory directly. In the memory hierarchy hardware manages the caches and the operating system manages main memory. The cache works with 64-byte lines and pays off thanks to temporal and spatial locality.
  • In a direct-mapped cache, block b goes to set b mod K; blocks that fall in the same set evict one another (conflict misses). The average access time is computed from the bottom up with T = s + m · Tbelow; in the example it is 3.8 ns, about 21 times faster than DRAM.
  • The address space solves the problems of protection and relocation. With base and limit registers the valid addresses are base … base + limit − 1; anything outside raises a trap.
  • Address binding can be done at compile, load, or execution time. Today's systems bind at execution time: the CPU produces a logical address and the MMU translates it into a physical address.
  • Dynamic loading (dlopen) loads code when it is called. With dynamic linking the library code is in memory once and shared; in ELF, what changes on the first call is not the code but the process-specific GOT entry. -fPIC produces position-independent code.
  • Standard swapping moves a whole process and is slow; today's systems swap cold pages and compress them first.
  • In contiguous allocation the hole is chosen by first fit, next fit, best fit, or worst fit. In external fragmentation the total free space is enough but not contiguous; by the 50-percent rule one third of memory can be lost. Internal fragmentation is the unused part inside a block. Compaction merges the holes but is expensive.
  • Free space is tracked with a bitmap (one bit per unit; looking for k consecutive zeros is linear) or a linked list (merging takes constant time if it is sorted by address). malloc embeds the free list inside the free chunks.
  • In paging logical memory is divided into pages and physical memory into frames; the address becomes (p, d) and physical = f × page size + d. There is no external fragmentation; internal fragmentation averages half a page. The optimal page size is about √(2se).
  • The page-table entry holds the P, R/W, U/S, NX, A, D, and G bits along with the frame number. The valid/invalid bit catches addresses outside the address space, but protection is at page granularity.
  • The TLB holds recent translations. The effective access time is EAT = (t + ε) α + (2t + ε)(1 − α); for ε = 20 and t = 100 ns it is 140 ns at α = 80% and 122 ns at 98%. With multilevel tables a miss is much more expensive.
  • The hierarchical table keeps lower tables only for the regions in use; x86-64 uses four (48-bit) or five (57-bit) levels with 9 bits per level. Huge pages enlarge the TLB reach. The size of a hashed table is proportional to the number of pages in use, that of an inverted table to physical memory.
  • Segmentation divides the address space into logical pieces of the form (segment, offset); each segment is a base–limit pair, and it leads to external fragmentation. On x86-64 only the FS/GS bases remain of segmentation; ARMv8 and RISC-V have no segmentation.

8.14Test Yourself

  1. A direct-mapped cache with 4 sets and 64-byte lines starts out empty, and addresses 16, 80, 40, 272, and 20 are accessed in turn. Which accesses are hits?

    Answer

    The blocks are 0, 1, 0, 4, 0; the sets are 0, 1, 0, 0, 0. 16: miss. 80: miss. 40: block 0 is in set 0, hit. 272: block 4 evicts block 0, miss. 20: block 0 is gone, miss. In total 1 hit and 4 misses.

  2. A process's base register is 5000 and its limit register is 2000. The MMU first checks the limit and then adds the base. What happens to logical addresses 1999 and 2000?

    Answer

    1999 < 2000, so it is valid and goes to physical 6999. 2000 equals the limit; since the valid offsets are 0 … 1999, a trap occurs.

  3. The holes, in address order, are 300, 120, 500, and 200 K. The requests, in order, are 180, 100, and 450 K. In which of first fit, best fit, and worst fit can a request not be satisfied?

    Answer

    First fit: 180 → 300 (120 remains), 100 → the 120 remainder of the same hole (20 remains), 450 → 500 (50 remains); all are placed. Best fit: 180 → 200 (20), 100 → 120 (20), 450 → 500 (50); all are placed. Worst fit: 180 → 500 (320), 100 → 320 (220); for 450 the largest hole is 300, so the request cannot be satisfied.

  4. The page size is 1 KiB and page 4 is mapped to frame 9. What is the physical address corresponding to logical address 5000?

    Answer

    p = ⌊5000 / 1024⌋ = 4, d = 5000 − 4096 = 904. Physical = 9 × 1024 + 904 = 9216 + 904 = 10120.

  5. The TLB lookup takes 5 ns, a memory access 100 ns, the table is single-level, and the hit ratio is 90%. What is the effective access time? What must the hit ratio be for the EAT to be 125 ns?

    Answer

    A hit takes 105 ns and a miss 205 ns. EAT = 0.9 × 105 + 0.1 × 205 = 94.5 + 20.5 = 115 ns. From 205 − 100α = 125, α = 0.8, that is, 80%.

  6. In 32-bit x86 two-level paging (10 + 10 + 12), what are the top index, the bottom index, and the offset for virtual address 0x00C05123?

    Answer

    The top index is 0x00C05123 >> 22 = 3, the bottom index is (0x00C05123 >> 12) & 0x3FF = 0xC05 & 0x3FF = 5, and the offset is 0x123. The address lies in the 12–16 MiB region.

  7. How much space does an inverted page table occupy with 8 GiB of RAM, 4 KiB frames, and 8-byte entries? Would this value change if the system had 200 processes?

    Answer

    233 / 212 = 221 = 2,097,152 entries; × 8 bytes = 16 MiB. It would not change: the inverted table is proportional to physical memory and is a single table in the system, independent of the number of processes.

  8. In Silberschatz's segment table (segment 2: limit 400, base 4300; segment 4: limit 1000, base 4700), where do addresses (4, 999) and (2, 400) go?

    Answer

    (4, 999): 999 < 1000, physical 4700 + 999 = 5699. (2, 400): the offset equals the limit; since the valid offsets are 0 … 399, a trap.

  9. In a 1024 K buddy system, what size of block does a 70 K request get, and how much internal fragmentation results?

    Answer

    The smallest power of two that satisfies 70 K is 128 K. The process gets a 128 K block; the internal fragmentation is 128 − 70 = 58 K.

  10. In a dynamically linked program, which page changes after puts is called for the first time, and why does it matter?

    Answer

    Only the puts entry in the process-specific GOT page changes; the resolver writes the real address there. Because the code pages of the program and of libc do not change, they stay read-only and continue to be shared among all processes.
