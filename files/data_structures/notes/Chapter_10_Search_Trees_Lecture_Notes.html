Chapter 10: Search Trees

Binary search in a sorted array is fast, but inserting means shifting everything after the new element. A linked list makes insertion easy but forces a search to walk the whole list. Search trees combine the strengths of both. Elements are placed by key so that at every node “left or right?” has exactly one answer, and search, insertion and deletion follow a single path down from the root, at a cost set by the tree's height. We start with the binary search tree (BST) and its operations, see why height decides everything, and then study AVL, red-black and splay trees, which keep the height small by themselves. The last part covers B-trees and B+ trees, built for large data on disk.

10.1Search trees

Nobody looks up “Smith” in a phone book by starting at page one. You open it in the middle, see which half the name is in, and discard the other, which works only because the book is sorted. On a computer this is binary search: about log2 n comparisons among n sorted elements.

The weakness of a sorted array is updating: adding an entry shifts everything after it, n moves in the worst case. A linked list inserts and deletes cheaply but cannot jump to its middle, so a search steps through it one element at a time. Search trees sit in between. Being linked, they update by changing a few links; being ordered, they let each search step eliminate part of the candidates.

10.1.1What is a search tree?

First, the vocabulary. A tree consists of nodes joined by edges. The topmost node is the root; nodes without children are leaves. The depth of a node is the number of edges from the root down to it, so the root has depth 0, and the height h of the tree is the depth of its deepest node. A single node has height 0; the empty tree, by convention, −1.

Each node of a search tree holds an element with a key, a comparable value that identifies it: a student ID, a dictionary word, a surname. The rest of the element (name, address, GPA) is stored alongside. To keep examples simple, our keys are mostly integers and nodes hold nothing else.

Definition 10.1

A search tree is a tree whose nodes hold elements kept in an order determined by their keys, arranged so that a search for a key needs to descend into only one subtree at each node. A search therefore starts at the root, chooses one branch per level, and visits at most h + 1 nodes.

That last sentence is the whole chapter in brief. Search, insertion and deletion each follow one path down from the root, at most as long as the height, so they cost O(h): fast while the tree stays short, slow when it grows tall.

How tall can an n-node tree be? At worst every node has one child, the tree is a chain, and the height is n − 1. At best every level is full. Depth d holds at most 2d nodes, so a binary tree of height h has at most 1 + 2 + 4 + … + 2h = 2h+1 − 1 nodes, and n ≤ 2h+1 − 1 gives h ≥ log2(n + 1) − 1: about log2 n.

Example 10.1

Store a million keys (n = 106) in a search tree. Perfectly balanced, it has height log2 106 ≈ 19.93, so a search makes about 20 comparisons. Degenerated into a chain, it has height 999,999, and the worst search makes a million. Same keys, same operation, different shape: a ratio of about 50,000.

This gap is why the rest of the chapter exists. A plain BST promises nothing about height. AVL and red-black trees repair themselves locally after each update and guarantee h = O(log n). A splay tree meets that bound on average over long sequences, and a B-tree packs many keys per node, making the tree short and wide.

Common mistake

Counting height in nodes. Height counts edges from the root to the deepest leaf: the path 6 → 2 → 4 → 3 in Figure 10.1 has four nodes but three edges, so the height is 3. Some books count nodes, which shifts every formula by one. Here height always counts edges, and the empty tree has height −1.

The order supports further queries: the minimum and maximum key; the successor of a key (the smallest larger key) and its predecessor (the largest smaller key); and all keys within a range. Each follows a single path from the root, so everything except traversal takes O(h); traversal visits every node once, in O(n).

A hash table also searches and inserts in constant average time; ordered queries are what set a search tree apart. Because a hash table scatters its keys, questions like “the smallest key above 50” or “the keys from 20 to 45, in order” force it to scan everything. A search tree answers them in O(h) or O(h + s), where s is the number of keys returned.

10.1.3Kinds of search trees

We cover four kinds of binary search tree and two multiway trees. The binary kinds share one ordering rule and differ in how, and how tightly, they control height. Figure 10.2 shows a small example of each.

  • Binary search tree (BST): each key is greater than every key in its left subtree and smaller than every key in its right subtree. No balance guarantee; the shape depends on insertion order.
  • AVL tree: at every node the subtree heights differ by at most 1 (the balance factor); rotations restore the condition when it breaks.
  • Red-black tree: nodes are red or black, and color rules bound the height by 2 log2(n + 1).
  • Splay tree: rotations move each accessed node to the root. One operation can be costly, but the amortized cost is O(log n).

In multiway trees (B-trees and B+ trees) a node holds several keys and more than two children. Designed mainly for data on disk, they are the subject of Section 10.7.

10.2Binary search trees

In a binary tree each node has at most two children, left and right. A binary search tree adds an ordering rule that makes it behave like a “linked” sorted array.

10.2.1The BST property

Definition 10.2

A binary search tree (BST) is a binary tree in which, for every node x, all keys in the left subtree of x are smaller than x.key and all keys in its right subtree are larger. This is the BST property.

“All” matters: the condition relates a node to every descendant, not just its children. In Figure 10.3, the left tree is a valid BST; in the right one, 7 has been added as the right child of 4. That pair is fine, but 7 lies in the left subtree of 6 while being larger than 6, so the tree is not a BST.

So a node's key splits its subtree in two, smaller keys left and larger right, like the middle element of a sorted array. As binary search halves its range, a BST search knows at each node which side to take and discards the other.

Can a key appear twice? Not under this definition, with its strict inequalities. In practice you either reject duplicates, as our code does, or consistently send equal keys to one side, say the right. Search, insertion and deletion must follow the same rule, or an inserted key may never be found again.

Common mistake

Checking the BST property only between parents and children. “Every left child smaller, every right child larger” also holds for the right-hand tree in Figure 10.3, which is not a BST. The correct check carries lower and upper bounds down from the root (Section 10.3.12).

10.2.2Node structure

A BST node has three fields: the data (the key) and references to its left and right children (Figure 10.4). A missing child is null, so a leaf has two null references. Compared with a linked-list node, there are two child references instead of one “next.”

The slides write the node in two forms. The first holds only an int key:

class TreeNode {
    int data;
    TreeNode left, right;

    TreeNode(int data) {
        this.data = data;
        this.left = null;
        this.right = null;
    }
}

The constructor stores the data and sets both children to null, which Java does anyway; the assignments just show intent. The successor, range query and validation code use this class, with the short field names left and right.

The second form is a generic class. The key need not be an integer; any comparable type will do:

class BinaryTreeNode<E extends Comparable<E>> {
    E data;                    // element
    BinaryTreeNode<E> leftChild; // left child
    BinaryTreeNode<E> rightChild; // right child

    BinaryTreeNode(E data) {
        this.data = data;
        // children start out null
    }
}

The bound E extends Comparable<E> means two E objects can be compared with compareTo. Integer, String and LocalDate implement Comparable, so any of them can be a key. a.compareTo(b) is negative if a < b, 0 if equal, and positive if a > b; search, insertion and deletion look only at this sign. Here the fields are leftChild and rightChild.

Each node carries two references besides its data, so n nodes take O(n) memory. Balanced trees add a constant per node, a height for AVL or a one-bit color for red-black, and total memory stays O(n).

10.2.3Minimum and maximum keys

The BST property tells us where the extremes are. A node with a left child cannot be the minimum, since something smaller is on its left. So the minimum is found by going left from the root until a node has no left child, and the maximum by going right (Figure 10.5).

The slides give both methods together:

BinaryTreeNode<E> minValue(
        BinaryTreeNode<E> node) {
    while (node.leftChild != null)
        node = node.leftChild; // go left
    return node;  // minimum
}
BinaryTreeNode<E> maxValue(
        BinaryTreeNode<E> node) {
    while (node.rightChild != null)
        node = node.rightChild; // go right
    return node;  // maximum
}

minValue starts at the given node and, while it has a left child, moves node there; when the left child is null, it returns the current node. maxValue does the same on the right. Both assume a nonempty tree: if node starts as null, node.leftChild throws a NullPointerException.

No keys are compared; the methods just follow links, one level per iteration, so they take at most h iterations, O(h) time, and O(1) extra memory.

Taking any node rather than the root is deliberate: deletion calls minValue on the right subtree of a two-child node to find its replacement. The same method serves for the whole tree or any subtree.

Common mistake

Writing the condition as while (node != null). The loop then runs past the leftmost node to null, and the method always returns null. Stop one step earlier, at the node with no left child: check that a next node exists before moving.

10.2.5Inorder traversal

A traversal visits every node in a fixed order. Binary trees have three classic recursive orders, preorder, inorder and postorder, named for when the root is visited relative to its subtrees. Inorder visits the left subtree, then the root, then the right subtree.

void inorder(BinaryTreeNode<E> d) {
    if (d == null) return;
    inorder(d.leftChild);  // left
    System.out.print(d.data + " ");
    inorder(d.rightChild);  // right
}

On an empty subtree (d == null) the method returns at once: the base case. Otherwise its three lines traverse the left subtree, print the node's data, and traverse the right subtree.

In a BST this order prints the keys in increasing order. Take any node: its whole left subtree, all smaller keys, is printed before it, and its right subtree, all larger keys, after it. Every node thus comes after all smaller keys and before all larger ones, which is exactly sorted output.

Theorem 10.1 (Inorder traversal is sorted)

The inorder traversal of a binary search tree lists its keys in increasing order.

By induction on height. The empty tree gives empty output. For a tree of height h with root r, both subtrees are shorter, so by hypothesis each traversal lists its keys in increasing order. The output is “left list, r, right list,” and by the BST property every left key is below r and every right key above it, so the whole list increases. □

The converse holds too: a binary tree whose inorder traversal is strictly increasing is a BST. So one way to check a tree is to traverse it inorder and test that the output increases.

Each node is printed once and makes two recursive calls, O(n) calls in all (n nodes produce n + 1 empty calls), so the time is O(n). The stack holds at most h + 2 frames, counting the empty call: O(h) memory.

Common mistake

Expecting sorted inorder output from any binary tree. That holds only for a BST; without the ordering rule, the order depends on the tree's shape. And in a BST, preorder and postorder are not sorted either. Only inorder is.

10.3BST operations

All BST operations share one skeleton: start at the root, compare, go left if smaller and right if larger. They differ in where they stop and what follows. Search stops at an equal key or an empty link; insertion hangs a new node on the empty link; deletion removes the found node in one of three ways, depending on its children.

10.3.1Search

Search follows three rules:

  1. Start at the root. If the node's key equals the target, the search succeeds.
  2. If the target is smaller, repeat in the left subtree; if larger, in the right subtree.
  3. If you reach a null link, the key is not in the tree.

The third rule follows from the BST property: a key in the tree must lie in the subtree chosen at each step, since the other subtree's keys are all smaller or all larger. If that subtree is empty, the key is nowhere.

The slides give a recursive search on the generic node class:

boolean search(BinaryTreeNode<E> root, E data) {
    if (root == null)
        return false;            // absent
    int k = data.compareTo(root.data);
    if (k == 0)
        return true;             // found
    else if (k < 0)
        return search(root.leftChild, data);
    else
        return search(root.rightChild, data);
}

The first if is the base case: an empty subtree has no keys, so the answer is false. Otherwise the target is compared once with the node's data, the result is kept in k, and the method returns true for k == 0 or recurses left for k < 0 and right for k > 0, passing the result up unchanged.

Comparing once and saving the result is clearer and cheaper: compareTo may be costly for a String or a complex object, and two ifs would call it twice.

Common mistake

Comparing object keys with ==, which tests whether two references are the same object, not whether values are equal. With Integer keys, the 1000 in a node and the 1000 searched for are separately boxed, so data == root.data is false and the key is missed. Java caches −128 to 127, so the bug appears only with larger numbers. Use compareTo for order and compareTo(...) == 0 or equals for equality.

Each call descends one level with constant work. A successful search examines one node more than the found node's depth; an unsuccessful one at most h + 1. Both are O(h), using O(h) stack. Since the recursive call comes last, a while loop assigning root = root.leftChild or root = root.rightChild does the same in O(1) extra memory.

10.3.3Insertion

A new key goes where a search for it ends: at a null link. Every node on the way sent the search to the correct side, so that link is the only place the key fits without breaking the BST property. The new node becomes a leaf there.

BinaryTreeNode<E> insert(
        BinaryTreeNode<E> root, E data) {
    if (root == null)
        return new BinaryTreeNode<>(data);
    int k = data.compareTo(root.data);
    if (k < 0)
        root.leftChild = insert(root.leftChild, data);
    else if (k > 0)
        root.rightChild = insert(root.rightChild, data);
    // k == 0: key already present, not inserted
    return root;
}
// usage: root = insert(root, 5);

The key feature is the return value: insert returns the root of its subtree after the insertion. For an empty subtree it creates and returns the new node, now that subtree's root. Otherwise the root stays the same: the method updates a child link with the recursive result and returns its own root.

The line root.leftChild = insert(root.leftChild, data) looks redundant, since the child is already there. Only the assignment at the bottom does real work: in the new node's parent, root.rightChild is still null, and the assignment links in the returned node. Elsewhere each link is rewritten with its own value. These “redundant” assignments save the code from tracking the parent.

The caller follows the same pattern, root = insert(root, 5);. For an empty tree, the first insertion creates the root, and only this assignment stores it.

Common mistake

Calling insert(root, 8); and ignoring the result. Arguments are passed by value, so the caller's root never changes: on an empty tree the new node is lost. On a nonempty tree the bug hides, since an inner root.leftChild = … links the leaf, until the root changes (empty tree, deleted root, rotation at the root) and the tree breaks.

An equal key (k == 0) skips both ifs, so the method returns root unchanged and no duplicate is inserted. Insertion costs the same as search, O(h) time and O(h) stack. The new node is always a leaf and existing nodes never move, which is also why a plain BST's shape depends entirely on insertion order.

10.3.5Successor, predecessor, ceiling and floor

Each element of a sorted list has a “next” and a “previous” neighbor; in a BST they are the successor and the predecessor.

Definition 10.3

The successor of a key x is the smallest key in the tree greater than x; its predecessor is the largest key smaller than x. x itself need not be in the tree. In inorder, they come right after and right before x.

For x in the tree there are two cases (Figure 10.12):

  1. With a right subtree, the successor is its minimum: right once, then left all the way. The keys just above x are in that subtree, and the smallest of them is the successor.
  2. Without a right subtree, it is the nearest ancestor that the root-to-x path passes on its left. The path to 5 is 6 → 4 → 5: it turns left at 6, so 5 < 6, and right at 4, so 4 < 5 cannot qualify. The successor is 6.

The code merges both cases into one loop down from the root that keeps the “best candidate so far”:

TreeNode successor(TreeNode root, int x) {
    TreeNode candidate = null; // smallest key greater than x
    while (root != null) {
        if (x < root.data) {
            candidate = root;     // root is a candidate
            root = root.left;  // anything smaller is on the left
        } else
            root = root.right;  // keys greater than x are on the right
    }
    return candidate;
}

At each node, if x < root.data, the node is larger than x and a candidate; a better one, larger than x but smaller than this node, can only be on its left, so we record it and go left. If x ≥ root.data, the node and its left subtree are all at most x and cannot qualify, so we go right. The loop ends at an empty link and returns the last candidate, or null if there was none, meaning no key exceeds x.

Both cases come out automatically. With a right subtree, the loop passes x, goes right once, then left while collecting candidates, ending at that subtree's minimum. Without one, the loop ends right after x, and the last candidate is the nearest ancestor passed on its left. The code does not even need x to be in the tree.

Example 10.2

In the same tree, find floor(root, 7) and predecessor(root, 7).

  1. floor: 7 ≥ 6, candidate 6; right (8). 7 < 8, left (7). 7 ≥ 7, candidate 7; right (null). Result 7: a key in the tree is its own floor.
  2. predecessor: 7 > 6, candidate 6; right (8). Not 7 > 8, left (7). Not 7 > 7, left (null). Result 6, the largest key below 7.

Same path; the only difference is whether 7 itself counts as a candidate.

10.3.7Deletion: three cases

Deletion is the most delicate BST operation. A search finds the node in O(h), which is then removed, according to its number of children, without breaking the BST property. The examples use the tree of Figure 10.14.

  1. Leaf. Set the parent's link to null. Deleting 70 nulls the right link of 60.
  2. One child. Link the parent directly to the only child. Deleting 45 points 40 at 42; deleting 60 points 50 at 70.
  3. Two children. The parent has one link to offer but the node has two children, so it cannot be removed directly. Instead, replace the node's value with that of its inorder successor (minimum of the right subtree) or predecessor (maximum of the left subtree), then delete that node from its own position. Example: deleting 40.

The one-child case clearly preserves the BST property. 45 and all its descendants lie in the right subtree of 40 and exceed 40, so linking 42 to the right of 40 changes nothing; 42 also stays in the left subtree of 50, below 50. The subtree simply moves up a level, its order intact.

Why the successor? The replacement must exceed everything in the left subtree and be smaller than everything in the right. The keys adjacent in inorder, predecessor and successor, both qualify. The successor of 40 is 42: as the minimum of the right subtree it is below the other keys there, and being above 40 it exceeds the whole left subtree. Putting 42 in place of 40 keeps the BST property.

Deleting the successor from its old position is always easy. It was found by going left in the right subtree until there was no left child, so it is a leaf or has only a right child: Case 1 or Case 2. The recursion never meets a two-child node again.

10.3.8The deletion code

With the same “return the subtree's new root” pattern as insertion, one recursive method handles all three cases:

BinaryTreeNode<E> delete(
        BinaryTreeNode<E> root, E data) {
    if (root == null) return null;   // absent
    int k = data.compareTo(root.data);
    if (k < 0)
        root.leftChild = delete(root.leftChild, data);
    else if (k > 0)
        root.rightChild = delete(root.rightChild, data);
    else if (root.leftChild == null)
        return root.rightChild;  // leaf/right child
    else if (root.rightChild == null)
        return root.leftChild;  // left child only
    else {                    // two children
        root.data = minValue(root.rightChild).data;
        root.rightChild = delete(root.rightChild, root.data);
    }
    return root;
}

The first half is a search. If the key is absent (root == null), it returns null, leaving the tree unchanged. For k < 0 or k > 0 it recurses into the corresponding subtree and assigns the result to the child link.

At k == 0 the node is found, and three branches handle the cases:

  • If root.leftChild == null, return root.rightChild. This covers two cases: for a leaf it returns null, emptying the parent's link; for a node with only a right child it returns that child, which the parent then links to directly.
  • If root.rightChild == null (left child only), return the left child.
  • With two children, minValue(root.rightChild) finds the successor, whose value is copied into the node; delete(root.rightChild, root.data) then removes the successor, since root.data now holds its value.

The node is detached when the returned value is assigned to the parent's link: in the leaf and one-child cases the method returns the node's replacement, and the reference to the deleted node disappears, leaving it for the garbage collector. Calls are written root = delete(root, 40);, since a deleted root can only be replaced through this assignment.

The descent costs O(h). In the two-child case minValue and the second delete continue below the node, together within O(h). Deletion takes O(h).

Common mistake

Copying the successor's value into a two-child node but forgetting to delete the successor. Then 42 appears twice and the tree is no longer a BST. Equally wrong is deleting with the old key: delete(root.rightChild, data) looks for 40 in the right subtree and finds nothing. Use the copied value: delete(root.rightChild, root.data).

10.3.10Analysis of BST operations

Every operation so far costs time proportional to the depth of the deepest node it reaches, at worst the height: O(h). So the real question is how tall a BST with n keys gets.

That depends on insertion order. Inserting 4, 2, 6, 1, 3, 5, 7 gives a perfect tree of height 2. Inserting 1, 2, …, 7 puts each key right of the previous one, producing a chain of height 6. Such a degenerate tree is just a linked list that wastes memory.

Real data, however, is seldom random. Records from a file may be sorted already, student IDs grow with enrollment, timestamps only increase. Such input drives a plain BST to its worst case, with every operation O(n), and inserting n sorted keys costs 1 + 2 + … + (n − 1) = n(n − 1)/2 = O(n2) comparisons: half a trillion for a million keys.

Common mistake

Saying “BST search is O(log n).” Only for a balanced tree. A plain BST guarantees nothing about height; the correct bound is O(h), with h = n − 1 in the worst case. O(log n) is guaranteed only by balanced trees such as AVL and red-black trees.

10.3.11Range queries

A range query reports, in order, every key in [lo, hi]: “keys between 5 and 10,” or “students with a GPA from 2.5 to 3.0.” Traversing the whole tree inorder works but takes O(n) however few keys qualify. The BST property lets us do far better by never entering a subtree that cannot hold a key in range, a technique called pruning.

void range(TreeNode k, int lo, int hi) {
    if (k == null) return;
    if (lo < k.data)           // candidates on the left
        range(k.left, lo, hi);
    if (lo <= k.data && k.data <= hi)
        System.out.print(k.data + " ");
    if (k.data < hi)           // candidates on the right
        range(k.right, lo, hi);
}

This is inorder traversal pruned by two tests. All left-subtree keys are below k.data, so if k.data ≤ lo none can be in range and the left subtree is skipped; likewise, if k.data ≥ hi, the right subtree is skipped. The middle if prints the node when it is in range, and the left–node–right order keeps the output sorted.

10.3.12Is a tree a BST?

To check whether a binary tree is a BST, remember that the property applies to whole subtrees: each node must agree with all its ancestors, not just its parent. Going left adds an upper bound, going right a lower bound, and every node must lie within all the bounds on its path from the root.

boolean isBST(TreeNode k, long min, long max) {
    if (k == null) return true;
    if (k.data <= min || k.data >= max)
        return false;          // out of range
    return isBST(k.left, min, k.data)
        && isBST(k.right, k.data, max);
}
// first call: isBST(root, Long.MIN_VALUE,
//                   Long.MAX_VALUE)

Each node receives an allowed interval (min, max). The root's is unbounded, with Long.MIN_VALUE and Long.MAX_VALUE standing in for ±∞; since keys are ints, these long values never equal a key. A node outside its interval yields false; otherwise its value becomes the upper bound for its left child and the lower bound for its right, and the two results are joined with &&.

10.4Balance and AVL trees

BST operations take O(h), and h can reach n − 1. Is there a cheap way to keep the height O(log n) no matter what? Yes; Adelson-Velsky and Landis showed the first in 1962.

10.4.1Why balance matters

A plain BST's shape follows the insertion order: 1, 2, 3, 4 gives a chain of height 3, yet the same keys fit in trees of height 2, such as 2(1, 3(—, 4)) and 3(1(—, 2), 4) (Figure 10.21). All three trees have inorder 1 2 3 4; they hold the same sorted set in different shapes.

Definition 10.4

A self-balancing search tree, or simply balanced tree, is a BST that guarantees O(log n) height by repairing itself after every insertion and deletion with small local changes: rotations and recoloring.

“Local” is the key word. Rebuilding an unbalanced tree from its inorder sequence would work but costs O(n) per update, destroying the tree's advantage. Balanced trees touch only a few nodes on the updated path, which has length O(log n), with constant work per node, so updates stay O(log n).

10.4.2A balancing example

A larger example shows local repair at work. The tree on the left of Figure 10.22 holds 11 keys; its branches 9 → 14 → 12 and 76 → 54 → 72 → 67 have grown long, giving height 4. Rearranging those two subtrees fits the keys into height 3, with 12 and 72 as new subtree roots.

Rearranging leaves the inorder sequence, 9 12 14 17 19 23 50 54 67 72 76, unchanged; only parent–child relations change. In the left subtree of 17, the median of 9, 14, 12 became the root with 9 and 14 as children. On the right, 54, 72, 67 and 76 were rearranged and the middle key, 72, moved up. The rest of the tree was untouched.

AVL and red-black trees make such repairs automatically. An update can disturb only its own path, and the repair runs along that path from the bottom up.

10.4.3AVL trees and the balance factor

The AVL tree, named after the Soviet mathematicians Georgy Adelson-Velsky and Evgenii Landis and published in 1962, was the first self-balancing binary search tree. Its idea is simple: at every node, the two subtree heights differ by at most 1.

Definition 10.5

The balance factor of node x is bf(x) = h(left) − h(right), the difference of its subtree heights, where an empty subtree has height −1. An AVL tree is a binary search tree with bf ∈ {−1, 0, +1} at every node.

A positive balance factor means “left-heavy,” a negative one “right-heavy.” A leaf has bf = −1 − (−1) = 0; a node with only a left child, bf = 0 − (−1) = 1. This is why an empty subtree must count as −1: with 0, a leaf and a one-child node would look alike.

The right-hand tree has two unbalanced nodes. We fix the lowest, the one nearest the new node, here 20. That shortens its subtree by one, and 30 rebalances by itself.

Each AVL node stores its height, and balance factors are computed from the children's heights. Insertion and deletion proceed as in a plain BST; then, as the recursion unwinds, each node on the path updates its height and checks its balance factor, and a node with |bf| = 2 is fixed by rotation.

Common mistake

Computing the balance factor from subtree node counts. The AVL condition is about height. In 4(2(1, 3), 5) the root has three nodes on the left and one on the right, but heights 1 and 0, so bf = 1: a valid AVL tree.

10.4.4Why is AVL height O(log n)?

The AVL condition is local, so to see that it bounds the height, ask the reverse: how few nodes, N(h), can an AVL tree of height h have? In such a sparsest tree one subtree of the root has height h − 1, the other the least allowed, h − 2, and both are sparsest trees themselves. Hence:

N(0) = 1,   N(1) = 2,   N(h) = 1 + N(h − 1) + N(h − 2)

Theorem 10.2 (AVL height)

An AVL tree with n nodes has height h < 2 log2 n; a tighter Fibonacci argument gives h < 1.44 log2(n + 2). Search, insertion and deletion therefore take O(log n).

A tree of height h has n ≥ N(h) > 2h/2 nodes; taking base-2 logarithms, log2 n > h/2, so h < 2 log2 n. □

So an AVL tree is at worst about 44% taller than a perfectly balanced one; with a million keys its height never exceeds 28, compared with a million-long chain for a plain BST.

10.4.5Rotations

The basic repair tool is the rotation, which reverses the parent–child relation between a node and one of its children: the child moves up, the old parent down. To preserve the BST property, one subtree changes owner.

In a right rotation, y is the parent and x its left child, with subtrees T1 and T2; T3 is the right subtree of y. The inorder sequence is T1, x, T2, y, T3. Afterward x is on top with right child y; T1 and T3 keep their places, and T2, whose keys lie between x and y, becomes the left subtree of y. The sequence is unchanged.

Theorem 10.3 (Rotation)

A rotation preserves the inorder sequence and hence the BST property. It changes only three links and takes O(1) time; one side of the rotated subtree gets a level shorter, the other a level longer.

The three links: the left link of y now points to T2, the right link of x to y, and the parent's link to x instead of y. Three assignments suffice for any tree size. T1 rises a level, T3 drops one, T2 stays put, so if T1 is the heavy side of a left-heavy node, a right rotation evens things out.

Common mistake

Losing T2. If x.right = y comes first, the only reference to the old right subtree of x is gone. Move T2 to safety with y.left = x.right first, then write x.right = y.

10.4.6Single rotations: LL and RR

Let z be the lowest unbalanced node after an insertion. There are four cases, named for the first two steps from z toward the new node (L for left, R for right). In LL the new node went into the left subtree of the left child of z; RR is the mirror image. Here z and its child lean the same way, and one rotation suffices.

LL shows up as bf(z) = 2 (left-heavy) with the left child at 1 or 0; the fix is a right rotation at z. RR shows up as bf(z) = −2 with the right child at −1 or 0; the fix is a left rotation at z.

After an insertion, a single rotation returns the subtree to its pre-insertion height. In Figure 10.26, the subtree of 30 had height 1, the insertion of 10 made it 2, and the rotation restored 1. Ancestors never see a change, so one repair per insertion suffices.

10.4.7Double rotations: LR and RL

In the other two cases the new node ends a “zigzag.” In LR it went into the right subtree of the left child of z: z leans left, its child right, and the three nodes form a triangle. A single right rotation at z merely flips the triangle, leaving the tree unbalanced.

The fix takes two rotations: left at the child, straightening the triangle into the LL case, then right at z. The median of the three keys ends on top with the smaller on its left and the larger on its right. RL is the mirror image.

10.4.8The AVL code

An AVL node holds a key, a height and two child references. The slides first give three helpers and the right rotation:

int h(AvlNode d) {
    return d == null ? -1 : d.height;
}
int bf(AvlNode d) {
    return h(d.left) - h(d.right);
}
void update(AvlNode d) {
    d.height = 1 +
        Math.max(h(d.left), h(d.right));
}
AvlNode rotateRight(AvlNode y) {
    AvlNode x = y.left;
    y.left = x.right;  // T2 → y.left
    x.right = y;       // y → x.right
    update(y);         // lower node first
    update(x);
    return x;          // new root
}

h returns −1 for an empty subtree, sparing other methods a null check; bf is the difference of the children's heights; update recomputes a node's height from its children's, which must already be correct, so heights are always updated bottom-up.

rotateRight(y) codes Figure 10.25: x is the rising left child, y.left = x.right moves T2, and x.right = y reverses the relation. y is updated before x, since y is now the child and the height of x depends on it. The method returns the new subtree root x, which the caller assigns to the parent's link, the third link.

The slides abbreviate the left rotation as the “left ↔ right mirror”; in full:

AvlNode rotateLeft(AvlNode x) {
    AvlNode y = x.right;
    x.right = y.left;  // T2 → x.right
    y.left = x;        // x → y.left
    update(x);         // lower node first
    update(y);
    return y;          // new root
}

rebalance combines the four cases:

AvlNode rebalance(AvlNode d) {
    update(d);
    if (bf(d) > 1) {       // left-heavy
        if (bf(d.left) < 0)  // LR
            d.left = rotateLeft(d.left);
        return rotateRight(d); // LL
    }
    if (bf(d) < -1) {      // right-heavy
        if (bf(d.right) > 0)  // RL
            d.right = rotateRight(d.right);
        return rotateLeft(d); // RR
    }
    return d;
}
// rotateLeft: mirror of left ↔ right
// insert/delete as in a BST; on return:
//   return rebalance(root);

rebalance(d) updates the height of d. If the node is left-heavy (bf > 1) and its left child leans right, the case is LR: rotate left at the child, storing the result in d.left. In both cases, then rotate right at d. The right-heavy case mirrors this; a balanced node is returned as is.

Insertion changes only the last line of the BST version:

AvlNode insert(AvlNode d, int k) {
    if (d == null) return new AvlNode(k);
    if (k < d.key)
        d.left = insert(d.left, k);
    else if (k > d.key)
        d.right = insert(d.right, k);
    else return d;          // no duplicates
    return rebalance(d);
}

return rebalance(d) replaces return d, so as the recursion unwinds, every node from the new leaf to the root updates its height and is fixed on the spot if unbalanced. Deletion likewise adds rebalance to the returns of BST deletion.

The descent covers O(log n) levels with constant work per rebalance and rotation, so insertion and deletion take O(log n). Insertion needs at most one repair (a single or double rotation). In deletion a repair may shorten the subtree and push the imbalance up, so there may be a rotation at every level, O(log n) in all.

10.5Red-black trees

An AVL tree keeps a tight balance, and pays for it: after a deletion the imbalance can climb to the root, with a rotation at every level. A red-black tree accepts looser balance in exchange for very few rotations, doing most repairs by recoloring. Guibas and Sedgewick defined it in today's color terms in 1978; Java's TreeMap and TreeSet and C++'s std::map use it.

10.5.1The rules

Definition 10.6

A red-black tree is a binary search tree whose nodes are colored red or black, subject to five rules:

  1. Every node is red or black.
  2. The root is black.
  3. All leaves, the empty children (NIL), count as black.
  4. A red node has black children: no two reds in a row.
  5. Every path from a node down to the NIL leaves below it has the same number of black nodes, the node's black height.

Rule 3 just means that in code null children count as black, so rules 4 and 5 still make sense where a child is missing. When counting black nodes we count the root but not the NIL leaves.

Check the rules on Figure 10.32. The red 8 and 17 have black children (1, 11 and 15, 25), and the red leaves 6, 22, 27 have NIL children, so rule 4 holds. For rule 5: 13 → 8 → 1 → NIL has blacks 13 and 1; 13 → 8 → 1 → 6 → NIL the same, since 6 is red; 13 → 17 → 25 → 27 → NIL has 13 and 25. Two on every path.

Common mistake

Checking rule 5 only on the longest and shortest paths. Black counts must match on every path down to NIL, including the empty side of a one-child node. Take a black root 20 with black children 10 and 30, and a black 25 as left child of 30: 20 → 10 → NIL has 2 blacks, 20 → 30 → 25 → NIL has 3. Rule 5 fails.

10.5.2How the rules guarantee balance

The height bound comes from two rules acting together. Let b be the root's black height. Every root-to-NIL path has exactly b black nodes, so the shortest, all black, has b nodes. The longest also has b blacks, with reds in between, but rule 4 allows at most one red after each black, so it has at most 2b nodes.

Theorem 10.4 (Height of a red-black tree)

In a red-black tree the longest root-to-NIL path is at most twice the shortest, and with n internal nodes the height is h ≤ 2 log2(n + 1).

The first claim follows from the count above. For the second, a node of black height b has at least 2b − 1 internal nodes in its subtree, by induction: black height 0 means a NIL, with 20 − 1 = 0 nodes; otherwise each child has black height at least b − 1 and thus at least 2b−1 − 1 nodes, for a total of at least 2(2b−1 − 1) + 1 = 2b − 1. At the root rule 4 gives b ≥ h/2, so n ≥ 2h/2 − 1 and h ≤ 2 log2(n + 1). □

Search, insertion and deletion thus take O(log n). Fix-up uses at most 2 rotations after an insertion and 3 after a deletion; the rest is recoloring. The height bound is looser than AVL's (about 1.44 log2 n), so the tree can be somewhat taller, but updates are cheaper and each node needs only one extra bit.

10.5.3Insertion and the fix-up cases

Insertion has two phases. First the new node is attached as a leaf by BST insertion and colored red: a black node would add a black to its paths and break rule 5, whereas a red one changes no black height. Only rule 4 can break, if the parent is red too. The second phase repairs that.

The fix-up involves four nodes (Figure 10.34): the new node x, its parent p, grandparent g and uncle u, the parent's sibling. A red parent cannot be the root, so g exists, and it is black, or two reds would already have been adjacent. The uncle's color decides what happens.

Recoloring preserves rule 5: g goes from black to red and p, u from red to black, and every path down from g passes through exactly one of p, u, so it still has one black here. But a red g may now have a red parent, breaking rule 4 higher up, so the loop continues from g. The problem climbs two levels per step and at worst ends at the root, which is then colored black.

Recoloring is no use when the uncle is black: making g red would remove a black from the uncle's paths. Rotate instead. In the line case (x and p are children on the same side), rotate at g; p rises and turns black, g drops and turns red. In the triangle case, first rotate at p to get a line, just like AVL single and double rotations. The subtree root is then black and the loop ends.

10.5.4The fix-up code

A red-black node has, besides the key and children, a color and a parent reference that lets the fix-up climb. The slides' fix-up code:

void fixUp(Node x) {       // x: new, red
    while (x != root && isRed(x.parent)) {
        Node p = x.parent, g = p.parent;
        Node u = (p == g.left) ? g.right : g.left;
        if (isRed(u)) {           // red uncle
            p.color = u.color = BLACK;
            g.color = RED;
            x = g;                // problem moves to g
        } else {                  // black uncle

                rotate(p, x);     // make it a line
                Node t = x; x = p; p = t;

}

Forgetting root.color = BLACK after the loop. Recoloring can turn the root red, after which the loop stops because x is the root, leaving rule 2 broken. This line is also the only way the black height of the whole tree grows.

10.5.7Deletion in balanced trees

Deletion in both AVL and red-black trees begins with plain BST deletion; a two-child node is replaced by its successor or predecessor, so the node actually removed is always a leaf or has one child. Its removal may break the AVL height condition or the red-black black-height rule.

  • AVL repair: Update heights from the removed node up to the root, rotating (LL, RR, LR or RL) at every node with |bf| = 2. Unlike insertion, a rotation can leave the subtree shorter than before and unbalance an ancestor, so several ancestors may need repair.
  • Red-black repair: Deleting a red node changes no black counts. Removing a black node leaves its paths one black short, which recoloring and rotations fix according to the colors of the sibling and its children. Textbooks call this the “double black” fix-up; the deficit can climb to the root, but there are at most three rotations.

10.6Splay trees

AVL and red-black trees store balance information in each node and use it to repair the tree after each operation. A splay tree stores none and does not even try to stay balanced; instead, each access moves the accessed node to the root. Proposed by Sleator and Tarjan in 1985, it is also called a self-adjusting BST.

10.6.1A self-adjusting tree

Definition 10.7

A splay tree is a binary search tree that, after every access (search, insertion, deletion), moves the accessed node to the root through a sequence of rotations, an operation called splaying. Nodes store no balance information.

A splay tree has no height guarantee and can even become a chain, whose bottom node costs O(n) to reach. But that access also roughly halves the depth of the nodes on its path. Sleator and Tarjan showed that any m operations from an empty tree take O(m log n) in total, an amortized cost of O(log n) per operation: the bound covers the whole sequence, with cheap operations paying for expensive ones.

The structure has three notable properties:

  • Locality: Frequently accessed keys stay near the root, so the tree acts like a cache and can beat balanced trees when accesses concentrate on a few keys.
  • Simplicity: No extra fields; one splay routine serves all operations, applied to the node found, the node inserted, or the node about to be deleted.
  • Drawback: Even a search modifies the tree, a problem when several threads read it, and no single operation has a time guarantee, which real-time systems may not accept.

10.6.2Zig, zig-zig and zig-zag

Splaying repeats three kinds of step until the accessed node x is the root; which step applies depends on its parent p and grandparent g.

  • Zig: p is the root. One rotation at p makes x the root; this can only be the last step.
  • Zig-zig: x and p are children on the same side. Rotate at the grandparent first, then the parent.
  • Zig-zag: they are on opposite sides. Rotate at the parent, then the grandparent, as in an AVL double rotation.

The zig-zig order differs from AVL and matters. Rotating at the grandparent first “folds” the path, shortening the upper chain too; single rotations from the parent also bring x to the root but can leave the chain long. The amortized bound relies on the grandparent-first order.

Common mistake

Rotating the parent first in zig-zig. That is plain move-to-root, which lacks the amortized O(log n) guarantee: repeatedly accessing the bottom of a sorted chain keeps the chain long, and each access can cost O(n). Rotate at g first, then p.

The slides' code puts the three steps in one loop:

void splay(Node x) {
    while (x != root) {
        Node p = x.parent, g = p.parent;
        if (g == null)                // zig
            rotate(p, x);
        else if (sameSide(x, p, g)) {  // zig-zig
            rotate(g, p);   // grandparent first
            rotate(p, x);
        } else {                      // zig-zag
            rotate(p, x);   // parent first
            rotate(g, x);
        }
    }
}

rotate(a, b) is the single rotation from the red-black code, lifting b, a child of a, into the place of a. sameSide(x, p, g) checks whether x hangs on the same side of p as p of g. The zig-zag branch ends with rotate(g, x) because after the first rotation x has replaced p as the child of g.

10.7Multiway search trees

So far every tree has been binary, which suits main memory, where following a link takes nanoseconds. On disk, reading a block is thousands of times slower than reading memory, hundreds of thousands on old spinning disks. A binary tree indexing a billion records has height at least 30; with one disk read per node, a search costs 30 accesses. Multiway trees cut this to a few.

10.7.1The B-tree

Definition 10.8

A B-tree is a balanced multiway search tree whose nodes hold several keys and many children. In a B-tree of order (degree) m:

  • A node holds at most m children and m − 1 keys.
  • Every internal node other than the root has at least ⌈m/2⌉ children.
  • Keys in a node are sorted. An internal node with k keys has k + 1 children, and the child between two adjacent keys holds the keys between them.
  • All leaves are at the same depth.

A node's keys act as boundaries between its children. The root [20, 40] in Figure 10.39 sends keys below 20 left, keys between 20 and 40 to the middle, and larger keys right: the BST property generalized. A BST resembles a B-tree of order 2, but the B-tree's strength is the rule that all leaves share one depth, which keeps it perfectly balanced.

Why? Each node fills one disk block, which holds hundreds of keys. With order 200, a tree of height 3 holds 2004, over a billion keys, and a search reads four blocks, fewer from disk since the root usually stays in memory. Being wide and shallow, B-trees, introduced by Bayer and McCreight in 1972, underlie database and file-system indexes.

A B-tree of order 4 is a 2-3-4 tree, whose nodes have 2, 3 or 4 children, and it is equivalent to a red-black tree: merging each black node with its red children yields a 2-3-4 tree, and “equal black height” becomes “all leaves at the same depth.”

10.7.2Search and insertion in a B-tree

Search generalizes BST search. At each node the keys are compared with the target; if it is not found, the search descends to the child for its interval. One node, one disk block, is read per level, so the cost is O(logm n) reads; binary search within a node takes O(log m) comparisons, O(log n) in total.

Insertion always starts at a leaf: follow the search path and put the key in sorted position. If the leaf then reaches m keys, it splits: the median moves up to the parent and the remaining keys form two nodes. The parent, gaining a key and a child, may split in turn, and so on up to the root, whose split creates a new root and adds a level.

The four-key leaf [25, 30, 33, 35] has no single median. The slides pick the right middle key, 33, leaving two keys on the left and one on the right; the left one would also do, as long as the choice is consistent. Odd orders avoid the issue: with m = 3 an overflowing node has three keys and one median.

Splitting means a B-tree grows from the bottom up. A BST grows downward as leaves are added, but a B-tree gains height only when its root splits, pushing all leaves down at once, so they always stay at the same depth.

Deletion reverses insertion. A node that falls below minimum occupancy borrows a key from a sibling or merges with it; a merge takes a key from the parent, and the shortage may propagate upward. If the root loses its last key, it is removed and the height drops by one.

10.7.4The B+ tree

The B+ tree, the variant most used in databases, differs from the B-tree in three ways:

  • Data in the leaves: All keys and records live in the leaves; internal nodes hold only routing keys, copies of leaf keys.
  • Linked leaves: The leaves form a left-to-right linked list, so range queries like “20 to 50” walk along it.
  • Wider internal nodes: Without records, more keys fit in a block, so the order rises and the tree gets shallower.

Every search ends at a leaf, where the records are; there is no B-tree-style early exit at an internal node. In return, every search descends the same number of levels, so its cost is predictable. Most relational database systems use B+ trees for table indexes.

  3. Leaf [20, 25, 30]: take all three and follow the link.
  4. Third leaf [40, 50, 60]: take 40; stop at 50 > 45.

The result 10 20 25 30 40 is sorted. The cost is one descent plus the leaves read: O(log n + k) for k results. In a B-tree, with keys spread over internal nodes too, the query would climb up and down repeatedly; the leaf chain avoids that.

Example 10.8

A registration system stores 2 million student records in a B+ tree of order 100, keyed by ID. Internal nodes are at least half full, so each has at least 50 children, and the height is at most about ⌈log50(2 · 106)⌉: since 503 = 125,000 and 504 = 6,250,000, at most 4 levels. Finding a student reads at most 4 blocks; listing the 150 students with IDs 2020001 to 2020150 takes one descent and a few leaf reads. A balanced binary tree would have height at least 20.

Two misconceptions lie behind these mistakes. One is seeing the tree only locally, a node with its parent and children, when the BST property, the AVL condition and the black-height rule all constrain whole subtrees. 10.9Summary

  • A search tree keeps elements ordered by key; search, insertion and deletion follow one path from the root in O(h), where h ranges from about log2 n to n − 1.
  • The BST property: all keys in a node's left subtree are smaller and all in its right subtree larger, for whole subtrees. Inorder traversal gives sorted output in O(n). The minimum is leftmost, the maximum rightmost.
  • Insertion descends as in a search and attaches a leaf at the empty link reached. Methods return the subtree's new root: root = insert(root, x).
  • The successor of x is the smallest larger key, the predecessor the largest smaller one; ceiling and floor also accept equality. All take O(h).
  • Deletion has three cases: remove a leaf; bypass a one-child node; replace a two-child node's value with its successor's (or predecessor's) and delete that node, which, having no left child, is an easy case.
  • A range query with pruning takes O(h + s). BST validation carries an allowed interval down from the root and takes O(n).
  • A plain BST's shape follows insertion order (sorted input gives a chain; random order, average depth about 1.39 log2 n). Balanced trees guarantee h = O(log n) by small local changes.
  • An AVL tree has bf = h(left) − h(right) ∈ {−1, 0, 1} at every node. The sparsest AVL tree grows like the Fibonacci numbers, so h < 1.44 log2(n + 2). LL and RR need one rotation, LR and RL two; a rotation is O(1) and preserves the inorder sequence.
  • A red-black tree has a black root, no adjacent reds, and equal black counts on all paths, so the longest path is at most twice the shortest and h ≤ 2 log2(n + 1). Insertion fix-up depends on the uncle: red means recolor, black means at most two rotations.
  • A splay tree moves each accessed node to the root by zig, zig-zig and zig-zag steps: O(n) worst case per operation, O(log n) amortized.
  • A B-tree node holds at most m − 1 keys and m children, and all leaves share a depth. Overflowing nodes split, sending the median up, so the tree grows from the bottom. A B+ tree keeps data only in linked leaves; range queries take O(log n + k).

10.11Test Yourself

  1. Insert 35, 18, 52, 10, 25, 44, 60, 22, 48 into an empty BST. What is its height and its inorder traversal? How many nodes does search(root, 48) compare?

    Answer

    The tree is 35(18(10, 25(22, —)), 52(44(—, 48), 60)). The deepest nodes, 22 and 48, are at depth 3, so the height is 3. Inorder: 10 18 22 25 35 44 48 52 60. Searching for 48 compares 35 (right), 52 (left), 44 (right) and 48: 4 nodes, the depth of 48 plus one.

  2. Delete 18 and then 35 from the same tree, using the inorder successor for two-child nodes. What is the tree after each deletion?

    Answer

    The successor of 18 is 22 (right to 25, then left); 22 is copied into the node of 18 and the old leaf deleted: 35(22(10, 25), 52(44(—, 48), 60)). The successor of 35, left from 52, is 44; it is copied to the root and the old 44, having one child, is bypassed: 44(22(10, 25), 52(48, 60)).

  3. In the tree of question 1, what are successor(25), predecessor(44), ceiling(45) and floor(21)?

    Answer

    successor(25) = 35 and predecessor(44) = 35: 25 has no right subtree and 44 no left subtree, and in both cases the nearest qualifying ancestor is the root. ceiling(45) = 48 and floor(21) = 18; 45 and 21 are not in the tree.

  4. In the tree of question 1, what does range(root, 20, 46) print? Which nodes are never visited?

    Answer

    22 25 35 44, visiting 35, 18, 25, 22, 52, 44, 48. At 18, 20 < 18 is false, pruning 10; at 52, 52 < 46 is false, pruning 60. 48 is visited (right of 44, since 44 < 46) but is out of range. 10 and 60 are never visited.

  5. Insert 30, 20, 10, 40, 50, 35 into an empty AVL tree. Which insertions trigger which case, and what is the final tree?

    Answer

    10: bf(30) = 2, bf(20) = 1 → LL; right at 30 gives 20(10, 30). 40: balanced. 50: bf(30) = −2, bf(40) = −1 → RR; left at 30 gives 20(10, 40(30, 50)). 35 lands right of 30: bf(20) = −2, bf(40) = 1 → RL; right at 40, then left at 20. Final tree 30(20(10, —), 40(35, 50)), height 2.

  6. Insert 30, 20, 10, 25, 27 into an empty red-black tree. Which case applies at each insertion needing a fix-up? Give the final tree with colors.

    Answer

    10: red parent 20, NIL uncle, a line → right at 30; 20B(10R, 30R). 25: red parent 30, red uncle 10 → recolor (10, 30 black, 20 red), and the root 20 turns black again. 27: red parent 25, NIL uncle, a triangle (27 right, 25 left child) → left at 25, right at 30; 27 black, 30 red. Final tree 20B(10B, 27B(25R, 30R)), 2 blacks on every path.

  7. Given the splay tree 50(30(20(10, —), 40), 70), which step does splay(40) use, and what is the result?

    Answer

    The path is 50 → 30 → 40 (p = 30, g = 50); 40 is a right child, 30 a left child: zig-zag. Rotating left at 30 and right at 50 gives 40(30(20(10, —), —), 50(—, 70)) in one step.

  8. Insert 5, 15, 25, 35, 45 into an empty B-tree of order 3. Which insertions cause splits, and what is the final tree?

    Answer

    25 overflows [5, 15, 25], and 15 moves up into a new root: [15]{[5] [25]}. 35 joins the right leaf: [25, 35]. 45 overflows [25, 35, 45]; 35 moves up to the root, which has room: [15, 35]{[5] [25] [45]}. Two splits, one at the root; height 1.

  9. In a red-black tree whose root has black height 3, how many nodes can the shortest and longest root-to-NIL paths contain? What is the minimum number of nodes in such a tree?

    Answer

    Every path has 3 black nodes. The shortest is all black: 3 nodes. On the longest, a red can follow each black: at most 6 (black, red, black, red, black, red, as the root is black). The minimum is 23 − 1 = 7 nodes: the all-black perfect tree of height 2.

  10. In the B+ tree of Figure 10.42, which keys lie between 22 and 55, and how many leaves are read?

    Answer

    At the root, 20 ≤ 22 < 40 leads to the middle leaf [20, 25, 30]: skip 20, take 25 and 30. The link leads to [40, 50, 60]: take 40 and 50, stop at 60 > 55. Result 25 30 40 50; 2 leaves read, with no return to the root.
