Collection Interfaces

The Iterable Interface

At the top of the hierarchy, it lets us traverse an object's elements. If an object is Iterable, we can:

iterator()get an Iterator that visits the elements in order.
spliterator()get a Spliterator that splits the elements into parts for parallel processing.
forEach(...)run an action (a lambda) on every element.
// what we write
for (var x : a) {
    System.out.println(x);
}
// what the compiler generates (a is Iterable)
Iterator<T> it = a.iterator();
while (it.hasNext()) {
    var x = it.next();
    System.out.println(x);
}

A for-each loop compiles only if a is an array or an object of a class that implements Iterable. (For arrays it becomes an indexed loop.)

Code Trace: Our Own Iterable Class

for (int x : new Range(2, 5)): the constructor runs first; the range is [2, 5).

for-each quietly calls iterator(): an anonymous inner class, k = start.

hasNext(): 2 < 5 → true

next(): returns 2, then k++ → 3. The body prints x = 2.

hasNext(): 3 < 5 → true

next(): returns 3, then k++ → 4. The body prints x = 3.

hasNext(): 4 < 5 → true

next(): returns 4, then k++ → 5. The body prints x = 4.

hasNext(): 5 < 5 → false; the loop ends.

The contract: next() with no elements left → NoSuchElementException.

class Range implements Iterable<Integer> {
  private final int start, end;
  Range(int s, int e) { start = s; end = e; }
  public Iterator<Integer> iterator() {
    return new Iterator<Integer>() {
      int k = start;
      public boolean hasNext() { return k < end; }
      public Integer next() {
        if (k >= end)
          throw new NoSuchElementException();
        return k++;
      }
    };
  }
}

Collection Interfaces

The List Interface

  • Part of the Java Collections Framework, in the java.util package.
  • An ordered collection (a sequence): elements stay where they were inserted.
  • The user decides where each element goes and reaches it by an integer index, starting at 0.
  • Allows duplicates and, in most implementations, null.
  • Supports searching: indexOf, contains.
List is an interface, so new List() won't compile; we use a class that implements it (ArrayList, LinkedList, …).

Code Trace: subList Is a View

An ArrayList with 5 elements.

subList(1, 3) makes no copy: it is a view that stores only a start (offset) and a length. [1, 3) → B, C.

Printing the view reads indices 1 and 2 of the original list.

sub.set(0, …) → l.set(offset + 0, …) on the original: l[1] = X.

sub.add("Y") appends to the view, which means inserting at index 3 of l; D and E shift right and the view grows.

sub.clear() removes the view's 3 elements (indices 1–3) from the original list…

…and D, E shift left. l.subList(a, b).clear() is the short way to delete a range.

The result is [A, D, E]. Careful: if l itself is structurally modified (add/remove), the old sub becomes invalid → ConcurrentModificationException.

The List ADT

Mutable and Immutable Lists

MutableElements can be added, removed, and replaced after creation.new ArrayList<>(), new LinkedList<>()
ImmutableThe contents never change after creation; to "change" it, we build a new list.List.of(...), List.copyOf(...)
List<String> fixed = List.of("Ann", "Dan");
fixed.add("Ben");    // UnsupportedOperationException
List<String> copy = new ArrayList<>(fixed);   // mutable copy
copy.add("Ben");     // [Ann, Dan, Ben]; fixed is still [Ann, Dan]
  • Immutability is a core idea of functional programming: immutable data is safe to share and to use in parallel.
  • Persistent data structures are immutable; each "update" keeps the old version and avoids a full copy by sharing the unchanged parts.
  • Collections.unmodifiableList(l) is only a read-only view: if the underlying l changes, so does the view.

The List ADT · Step through the code

Code Trace: Copy, View, or Immutable?

List.of builds an immutable list (and rejects null).

If uncommented: structural changes are forbidden → UnsupportedOperationException (a runtime error, not a compile error).

new ArrayList<>(fixed) copies the elements into a new array; now there are two separate objects.

The copy is mutable, so Ben is added. fixed is still [Ann, Dan].

unmodifiableList copies nothing: it returns a view that wraps copy and refuses writes.

If uncommented: writing through the view is forbidden → UnsupportedOperationException.

But the underlying copy can change, and since the view looks at the same array, it sees the change.

Read-only ≠ immutable. For true immutability, use List.copyOf(copy).

List<String> fixed = List.of("Ann", "Dan");
// fixed.add("Ben");     → error
List<String> copy = new ArrayList<>(fixed);
copy.add("Ben");
List<String> view =
    Collections.unmodifiableList(copy);
// view.set(0, "Eve"); → error
copy.set(0, "Eve");
System.out.println(view);

A Trap: remove(int) or remove(Object)?

When a list holds Integers, the two methods are easy to mix up: an int argument is taken as an index.

List<Integer> nums = new ArrayList<>(List.of(10, 20, 30));
nums.remove(1);                    // removes index 1 → [10, 30]
nums.remove(Integer.valueOf(10));  // removes the value 10 → [30]
nums.remove(Integer.valueOf(99));  // absent → false, no change
nums.remove(5);                    // IndexOutOfBoundsException
remove(int index)Returns the removed element.E remove(int)
remove(Object o)Returns whether anything was removed.boolean remove(Object)
CostIn an array-based list, both shift the later elements.O(n)

Code Trace: Which remove Is Called?

[10, 20, 30]. On a List<Integer>, both remove overloads apply.

The argument is an int, so the compiler picks remove(int index), which needs no boxing. Index 1 goes.

30 shifts one place left; the removed element is returned: a = 20.

An Integer argument → remove(Object o): search by value. Integer.valueOf(10).equals(10) → a match at index 0.

The first match is removed and 30 shifts; the result is a boolean: b = true.

Searching for 99: 30 ≠ 99, end of list → not found, no change, c = false.

remove(5): the index check 5 < size (1) fails → IndexOutOfBoundsException: "Index 5 out of bounds for length 1".

Spliterator: A Splittable Iterator

List<String> words = new ArrayList<>();
words.add("Java");
words.add("Python");
words.add("C++");
Spliterator<String> split =
        words.spliterator();
while (split.tryAdvance(
        System.out::println)) {
    // each call handles one element
}
  • tryAdvance(action): if there is a next element, applies the action and returns true; otherwise false.
  • trySplit(): hands part of the remaining elements to a new Spliterator, so the work can be shared among threads.
  • Parallel streams (parallelStream()) use Spliterators behind the scenes.

Code Trace: trySplit and tryAdvance

A list of 4 words.

spliterator(): index 0, fence −1 → the bound is set from size() on first use (lazily).

trySplit(): fence = 4, mid = (0 + 4) / 2 = 2. The first half [0, 2) goes to the new b; a keeps [2, 4).

b.tryAdvance: index = fence → nothing left, false; the loop ends.

a.tryAdvance: an element is left → "C++" goes to the action (println), index moves to 3; true.

a.tryAdvance: an element is left → "Go" goes to the action (println), index moves to 4; true.

a.tryAdvance: index = fence → nothing left, false; the loop ends. The two halves could just as well run on two threads.

Three Ways to Traverse a Collection

     i < n; i++) {
  String s =

  ...
}

Lists only; when you also need the index.

2 · forEach 
list.forEach(
  System.out::println);

// or for-each:

Any Iterable; the shortest form.

3 · Iterator

Traversal · Step through the code

Code Trace: The Cost of an Indexed Loop on LinkedList

A doubly linked list with 6 nodes.

steps counts how many links the get calls walk in total.

get(0): 0 < n/2 = 3 → walks from first, 0 links. Total 0.

get(1): 1 < n/2 = 3 → walks from first, 1 link. Total 1.

get(2): 2 < n/2 = 3 → walks from first, 2 links. Total 3.

get(3): 3 ≥ n/2 = 3 → walks from last, 2 links. Total 5.

get(4): 4 ≥ n/2 = 3 → walks from last, 1 link. Total 6.

get(5): 5 ≥ n/2 = 3 → walks from last, 0 links. Total 6.

Total 6 = n²/4 − n/2 ≈ n²/4 → O(n²). An Iterator walks 1 link per next(): n − 1 = 5 in total → O(n).

List<String> list = new LinkedList<>(
    List.of("A", "B", "C", "D", "E", "F"));
int n = list.size(), steps = 0;
for (int i = 0; i < n; i++) {
  String s = list.get(i);  // node(i) walks
  steps += Math.min(i, n - 1 - i);
}
System.out.println(steps);

Removing While Traversing: ConcurrentModificationException

Wrong 
for (String s : names)
    if (s.startsWith("A"))
        names.remove(s);
// ConcurrentModification-
// Exception (fail-fast)
Right 
Iterator<String> it =
        names.iterator();
while (it.hasNext())
    if (it.next().startsWith("A"))
        it.remove();
// or, shorter:
names.removeIf(s -> s.startsWith("A"));
  • for-each quietly uses an Iterator; if the list is modified behind the iterator's back, the next next() notices and stops (fail-fast).
  • it.remove() may be called only once per next(); otherwise IllegalStateException.

Traversal · Step through the code

Code Trace: ConcurrentModificationException

An empty ArrayList. Every structural change (add/remove) increments the list's modCount.

Two add calls → modCount = 2.

modCount = 3. Now we trace the for-each loop as the compiler expands it.

iterator(): cursor 0; the iterator records the current count as expectedModCount = 3.

hasNext(): cursor 0 ≠ size 3 → true.

next() first checks modCount == expectedModCount: 3 == 3 ✓ → "Ann", cursor = 1.

"Ann" starts with A → true.

names.remove(s) removes directly from the list → elements shift left, modCount = 4. The iterator doesn't know (expected is still 3).

hasNext(): cursor 1 ≠ size 2 → true. ("Ben" is now behind the cursor and would never be visited!)

next(): modCount 4 ≠ expectedModCount 3 → ConcurrentModificationException. The iterator notices the change at once and stops (fail-fast).

names.add("Alice");            // modCount = 3
// for (String s : names) ... compiled:
Iterator<String> it = names.iterator();
while (it.hasNext()) {
  String s = it.next();
  if (s.startsWith("A"))
    names.remove(s);          // not through it!
}

Code Trace: Safe Removal with it.remove()

The same list [Ann, Ben, Alice], modCount = 3. Iterator: cursor = 0, lastRet = −1 (nothing returned yet).

hasNext(): cursor 0 ≠ size 3 → true.

next(): 3 == 3 ✓ → "Ann"; cursor = 1, lastRet = 0.

Does "Ann" start with A? Yes.

it.remove() removes the element at lastRet; cursor = 0 (the shifted element is not skipped), lastRet = −1, expectedModCount = modCount = 4.

hasNext(): cursor 0 ≠ size 2 → true.

next(): 4 == 4 ✓ → "Ben"; cursor = 1, lastRet = 0.

Does "Ben" start with A? No.

hasNext(): cursor 1 ≠ size 2 → true.

Does "Alice" start with A? Yes.

it.remove() removes the element at lastRet; cursor = 1 (the shifted element is not skipped), lastRet = −1, expectedModCount = modCount = 5.

hasNext(): cursor 1 = size 1 → false. The loop ends with no error.

The result is [Ben]: the names starting with A were removed safely. A second it.remove() with no next() in between → IllegalStateException.

  String s = it.next();

The ListIterator Interface

Available only on Lists (list.listIterator()). Beyond what an Iterator does, it moves in both directions and can add, remove, and replace elements on the way. The cursor sits between elements.

MethodWhat it does
hasNext() / next()is there an element ahead? / return the next element and move the cursor forward
hasPrevious() / previous()is there an element behind? / return the previous element and move the cursor back
nextIndex() / previousIndex()the index of the element next() / previous() would return (0 / −1 at the start)
add(e)inserts the element before the cursor (the next next() is unaffected)
remove()removes the element returned by the last next()/previous()
set(e)replaces the element returned by the last next()/previous()

Calling remove/set right after add or remove, with no next/previous in between → IllegalStateException.

Code Trace: ListIterator, Step by Step

listIterator(): the cursor is at the start; nextIndex = 0, previousIndex = −1. Orange: the last returned element (lastRet).

next() → "Ann"; the cursor moves forward, lastRet = 0.

next() → "Tom"; lastRet = 1.

set("TOM") replaces the element at lastRet ("Tom"); the cursor stays put.

add("Alice") inserts before the cursor, and the cursor moves past the new element (the next next still returns "Bob"); lastRet = −1.

previous() → "Alice", moving backward; the cursor steps back, lastRet = 2.

remove() deletes "Alice" at lastRet; lastRet = −1 (an immediate second remove/set → IllegalStateException).

it.next();          // "Ann"
it.next();          // "Tom"
it.set("TOM");    // [Ann, TOM, Bob]
it.add("Alice");     // [Ann, TOM, Alice, Bob]
it.previous();      // "Alice"
it.remove();        // [Ann, TOM, Bob]

List Implementations

ArrayList: A Growable Array

  • Keeps its elements in an internal array. Capacity (array length) ≥ size (number of elements).
  • When the array fills up, a new one about 1.5 times larger is created and the elements are copied (O(n)). Since this is rare, appending is amortized O(1).
  • It does not shrink on removal; trimToSize() cuts the capacity down to the size.

Real Java: an empty new ArrayList<>() gets capacity 10 on the first add; new capacity = old + old/2. The demo starts at 4.

public boolean add(E e) {
  if (size == data.length) {
    int newCap = Math.max(data.length + 1, data.length + data.length / 2);
    data = Arrays.copyOf(data, newCap);
  }
  data[size++] = e;
  return true;
}

List Implementations

Amortized Analysis: Why Grow Geometrically?

  • Doubling (×2): n adds copy 4 + 8 + 16 + … < 2n elements → amortized O(1) per operation.
  • Java's ×1.5 is geometric growth too: about 3n in total (integer division can shift this slightly), still amortized O(1).
  • Fixed increments (+c): c + 2c + 3c + … ≈ n²/(2c) copies → O(n) per operation.
  • Goodrich–Tamassia's "banker's" method: each cheap add deposits a few "tokens," and those tokens pay for the expensive resize.

The chart shows copies actually counted over 40 adds to a dynamic array that starts at capacity 4.

public E remove(int i) {
  Objects.checkIndex(i, size);
  E old = data[i];
  for (int k = i; k < size - 1; k++)
    data[k] = data[k + 1];
  data[--size] = null;
  return old;
}

LinkedList: A Doubly Linked List

  • Elements are not contiguous in memory: each one lives in its own node object.
  • Each node holds its data and references to the previous / next nodes; the list knows first and last.
  • Besides List, it implements Deque, so it can serve as a stack or a queue.
  • Random access is slow: get(i) walks node by node (from the nearer end) → O(n).

void addLast(E e) {
  Node<E> l = last;
  Node<E> n = new Node<>(l, e, null);
  last = n;
  if (l == null) first = n;
  else l.next = n;
  size++;
}

Code Trace: LinkedList remove(i)

[A, B, C]. remove(1): to find B, we first have to walk.

0 ≤ 1 < 3 → a valid index.

x = first (A). There is no direct indexed access as in an array.

k = 0 < 1: x = x.next → B.

k = 1 < 1 is false → the walk ends after i steps: O(i). (If i ≥ size/2, Java walks backward from last.)

p = x.prev = A, s = x.next = C: the two neighbors of the node to remove.

p is not null → p.next = s: A now points straight to C (B is bypassed).

s is not null → s.prev = p: C points back to A. B is cut off in both directions.

return "B". Relinking is O(1), but walking is O(n) → remove(i) is O(n) overall.

E remove(int i) {
  Objects.checkIndex(i, size);
  Node<E> x = first;
  for (int k = 0; k < i; k++) x = x.next;
  Node<E> p = x.prev, s = x.next;
  if (p == null) first = s; else p.next = s;
  if (s == null) last = p; else s.prev = p;
  size--;
  return x.data;
}

header ⇄ A ⇄ C ⇄ trailer; p is the position of A. We call addAfter(p, "B").

validate(p): is p a valid node of this list? Yes → it is cast to a Node.

The neighbors are known: pred = A, succ = A.next = C. The work is handed to addBetween.

The new node points to both neighbors, but nothing points to it yet.

pred.next = newest: forward, A → B → C.

  Node<E> n = validate(p);
  return addBetween(e, n, n.next);
}
Position<E> addBetween(E e, Node<E> pred, Node<E> succ) {
  Node<E> newest = new Node<>(pred, e, succ);
  pred.next = newest;
  succ.prev = newest;
  size++;
  return newest;
}

ArrayList and LinkedList in Memory

ArrayList

About 1 reference per element (4–8 bytes) + spare capacity. The array is contiguous, so the CPU cache prefetches the next elements.

LinkedList

One node object per element: an object header + 3 references (~24–40 bytes). Following each next may cause a cache miss.

List Implementations

Vector

  • A growable array like ArrayList: indexed access, grows as needed (by default the capacity doubles).
  • Its methods are synchronized, so individual operations are thread-safe.
  • The price: every call pays for a lock, even with a single thread.
  • Compound operations such as "check, then act" are still not atomic.
Vector<Integer> v = new Vector<>();
v.add(10);            // [10]
v.add(20);            // [10, 20]
v.get(0);             // 10
v.remove(0);          // [20]
v.size();             // 1
v.capacity();         // 10

// compound action: needs an external lock
synchronized (v) {
    if (!v.isEmpty()) v.remove(0);
}
Vector is a legacy class from Java 1.0. New code should use ArrayList for a single thread, and Collections.synchronizedList or CopyOnWriteArrayList for many.

List Implementations

Vector: The "Check, Then Act" Race

Every Vector method is synchronized, but the gap between two calls is unprotected. One possible interleaving of two threads:

Start: v = [20]. Both threads will run if (!v.isEmpty()) v.remove(0);.

T1: isEmpty() takes the lock, returns false, and releases the lock.

T2 slips in: v still has 1 element, so it sees false too. Both think they can remove.

T1: remove(0) → 20. v is now empty.

T2: remove(0) on an empty vector → ArrayIndexOutOfBoundsException. Each method is synchronized on its own, but the pair is not atomic.

The fix: put the compound action under one lock with synchronized (v) { … }. T2 waits until T1 leaves the block.

When T2 gets the lock, it sees v is empty and does not remove: "check, then act" is now safe.

List Implementations

CopyOnWriteArrayList: Copy on Write

  • On every change (add, set, remove), the internal array is copied, the change is made on the copy, and the list then switches to the new array.
  • Reads take no lock and are very fast; writes queue up behind a short lock and pay an O(n) copy.

Readers read the internal array without locking; each iterator walks the array as it was when the iterator was created (a snapshot).

add("d"): the writer takes the lock, copies the array, and appends the new element to the copy → O(n)

The list reference switches to the new array. The old iterator keeps walking A: no ConcurrentModificationException.

Good forLists that are traversed often and rarely change: event listeners, configuration.
Bad forLarge lists that change often: every write copies the whole array. it.remove() is not supported.

public boolean add(E e) {
  synchronized (lock) {
    Object[] old = array;
    int n = old.length;
    Object[] copy = Arrays.copyOf(old, n + 1);
    copy[n] = e;
    array = copy;       // one reference assignment
    return true;
  }
}
