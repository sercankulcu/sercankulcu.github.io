6.1Collection interfaces

A data structure can be described at two levels: what it does (which operations exist, what each changes and returns) and how (how the data sits in memory, which steps each operation takes). The first is an abstract data type (ADT); the concrete structure at the second level is an implementation of it.

Java builds this split into the language. An ADT's operations go in an interface, which gives method names, parameters, and return types but no bodies; the code that does the work lives in a class that implements the interface. Java's ready-made data structures follow this pattern in the Java Collections Framework, package java.util. This section walks down its list side.

6.1.1The Java Collections Framework: the list side

A collection is an object holding a group of elements; lists, sets, and queues are collections. The framework's interfaces form an inheritance tree: the top asks for the least, and each step down adds abilities. Figure 6.1 shows its list side.

Two verbs describe the arrows. An interface extends another: List inherits all of Collection's methods and adds more. A class implements an interface: ArrayList supplies a body for every method of List. So an ArrayList is at once a List, a Collection, and an Iterable.

Interface versus class is ADT versus data structure: what versus how. List says "get the element at an index"; ArrayList reads an array cell, LinkedList walks nodes. Code that knows only the interface works whichever implementation runs.

Hence the Java habit of declaring the variable with the interface type and creating the object from a concrete class:

List<String> l = new ArrayList<>();

The left side says "l is a list," the right side "for now, an ArrayList." If the program turns out to insert at the front a lot, only the right side becomes new LinkedList<>(); the hundreds of lines using l stay. Had l been declared ArrayList<String>, some line might use an ArrayList-only method such as trimToSize(), and the change would not compile.

Common mistake

Creating an object from an interface: List<String> c = new List<>(); does not compile, because an interface has no method bodies to run. new must be followed by a class that implements the interface. Iterable<String> d = new ArrayList<>(); does compile, since ArrayList also implements Iterable.

6.1.2Iterable and the for-each loop

At the top, Iterable asks only that an object's elements can be visited in order. It offers three things:

  • iterator() returns an Iterator over the elements. It is the only abstract method; writing it makes a class Iterable.
  • spliterator() returns a Spliterator, which splits the elements into parts for parallel processing.
  • forEach(...) runs a given action (a lambda expression) on each element.

The last two have default bodies built on iterator() or a similar tool, so the real contract of Iterable is: "Ask me, and I will hand you an iterator."

An iterator is a separate object that hands out a collection's elements one at a time and remembers where it is. It answers "Is there another?" (hasNext()) and "Give me the next" (next()). The for-each loop is built on these two; we write the short form, and the compiler produces the long one:

// what we write
for (var x : a) {
    System.out.println(x);
}
// what the compiler produces (if a is Iterable)
Iterator<T> it = a.iterator();
while (it.hasNext()) {
    var x = it.next();
    System.out.println(x);
}

The compiler checks the type of a. If a is Iterable, it produces the second fragment: call a.iterator(), then, while hasNext() is true, fetch an element with next() and run the body. If a is an array, it produces an ordinary indexed loop from i = 0 to a.length − 1.

So a for-each loop compiles only over an array or an object of a class that implements Iterable; to loop over our own class with for-each, the class must implement Iterable.

6.1.3Code trace: an Iterable class of our own

Here is a collection that stores no elements at all: Range(2, 5) stands for 2, 3, and 4, the half-open interval [2, 5), and the iterator generates the numbers as it goes.

class Range implements Iterable<Integer> {
  private final int start, end;
  Range(int s, int e) { start = s; end = e; }
  public Iterator<Integer> iterator() {
    return new Iterator<Integer>() {
      int k = start;
      public boolean hasNext() { return k < end; }
      public Integer next() {
        if (k >= end)
          throw new NoSuchElementException();
        return k++;
      }
    };
  }
}

Line by line:

  • class Range implements Iterable<Integer>: an Iterable of Integers. The type argument is Integer because a type parameter cannot be primitive.
  • The bounds start and end are final; they never change.
  • Each iterator() call returns a new iterator, an object of the anonymous inner class new Iterator<Integer>() { … }. Its field k starts at start, and it can read the enclosing Range's fields.
  • hasNext() checks that the next value is in range: k < end.
  • next() first guards the contract: with nothing left (k >= end) it throws NoSuchElementException. Otherwise return k++ returns the current k and then increments it.

Now trace for (int x : new Range(2, 5)). Since x is an int, each Integer from next() is unboxed.

Common mistake

Dropping the k >= end check in next() because "hasNext() is called first anyway." A for-each loop does call it first, but code using an iterator by hand need not. Without the check, next() would silently return 5, 6, 7. An iterator that gives wrong answers quietly is far harder to catch than one that throws.

6.1.4The Collection interface

Below Iterable sits Collection. Lists, sets, and queues behave very differently but share a core, gathered in this interface: add, remove, count, and test whether an element is present.

Mind the return values. add(e) returns true if the collection changed: always for a list, which accepts duplicates, while a set that already holds the element returns false. remove(o) returns true if it found and removed the element.

What Collection lacks matters too: there is no index. A set may have no order, so "the third element" is meaningless, and position-based operations such as get(i) live one level down, in List.

Common mistake

Forgetting the variable's type. After Collection<String> c = new ArrayList<>(List.of("x", "y"));, c.get(0) does not compile: the object is an ArrayList with a get, but the compiler looks only at the variable's type, Collection. An interface type buys flexibility at the price of using only that interface's methods.

6.1.5The List interface

List, in java.util, extends Collection with order. Its documentation calls it an ordered collection or sequence; "ordered" means the elements have a positional order, not that they are sorted.

Definition 6.1

A list is an abstract data type that keeps elements in positional order and accesses each through an integer index starting at 0. The user decides where an element goes; elements stay put and shift only when something is inserted or removed before them. Duplicates are allowed.

Its main properties:

  • Order is preserved. Elements added as "Ann", "Dan", "Ben" come back in that order.
  • The user picks the position. add(e) appends; add(i, e) inserts at a position.
  • Indexed access. get(i), set(i, e), and remove(i) work by position, from 0.
  • Duplicates are allowed. Most implementations also accept null.
  • Search. indexOf(o) gives the first occurrence; contains(o) tests presence.

Think of a to-do list. Items are written one below another and named by position; a new item can be squeezed in, a finished one crossed out, and the same item ("drink water") written twice. List mimics exactly this.

List is an interface too, so new List() is impossible; choose a class. Java's main ones are ArrayList, LinkedList, Vector, Stack, and CopyOnWriteArrayList. They share the methods, but different internals make the same operation cost different amounts.

6.2The list ADT

First the list in the abstract: the concepts that describe it and the operations it offers. None of this depends on a language; Python's list, C#'s List<T>, and Java's List are faces of one ADT.

6.2.1Basic concepts

Four concepts recur; Figure 6.4 shows them in one picture.

Element
A piece of data in the list: a name, a number, an object. Java list elements are always objects; primitives are boxed into wrapper classes.
Index
The integer giving an element's position: 0 for the first, length − 1 for the last. In Figure 6.4, "Alice" has index 2.
Empty list
A list with no elements; isEmpty() returns true. It is not null: the empty list exists and its methods can be called, while null refers to no object.
Length
The number of elements, size() in Java. Not to be confused with capacity, the number of cells reserved in an array-based list's internal array, which is usually larger.

On a bus, the seats are the capacity and the seated passengers the length. Users see only the passengers; empty seats are the list's internal business.

6.2.2List operations and their Java methods

The list ADT has seven basic operations; Table 6.3 pairs each with its Java List method.

"Later elements shift" is the heart of a list. Inserting X at position 1 of [A, B, C] gives [A, X, B, C]: B moves from index 1 to 2, C from 2 to 3. Removal does the reverse. A list has no gaps; its indices run unbroken from 0 to length − 1.

[start, end) is Java's half-open interval convention: start included, end excluded. subList(1, 3) selects indices 1 and 2, 3 − 1 = 2 elements. A slice's length is one subtraction, and subList(0, size()) is the whole list.

subList differs from the other operations in one way: it returns not a copy but a view of the original.

Definition 6.2

A view stores no elements of its own and operates on those of another collection. Changes through the view show up in the underlying collection, and changes to that collection are visible through the view.

Hence a short idiom: l.subList(1, 3).clear() removes indices 1 and 2 from the original, with no "remove range" method needed.

6.2.3Code trace: subList is a view

A view on a five-element ArrayList, modified:

List<String> l = new ArrayList<>(
    List.of("A", "B", "C", "D", "E"));
List<String> sub = l.subList(1, 3);
System.out.println(sub);
sub.set(0, "X");
sub.add("Y");
sub.clear();
System.out.println(l);

subList(1, 3) allocates no array and copies nothing. The view holds a reference to the original, an offset, and a length — here 1 and 3 − 1 = 2. sub.get(j) reads l.get(1 + j), and every operation is translated the same way.

Table 6.4: Trace of subList. The view's offset is 1 throughout.

Three moments deserve a closer look.

Reading and writing. sub.set(0, "X") becomes l.set(1, "X") once the offset is added, so X replaces B in the original. The view keeps no copy, so printing it now gives [X, C].

Adding. sub.add("Y") appends at the view's end, position offset + length = 1 + 2 = 3 of the original: l.add(3, "Y"). D and E shift right, and the view grows to length 3.

Clearing. sub.clear() removes X, C, and Y (indices 1–3) from the original; D and E shift three places left. The original becomes [A, D, E], the view empty.

A view's power brings a danger. Its arithmetic is relative to the original as it was when the view was opened. If the original is changed structurally (elements added or removed) other than through the view, the offset and length may be wrong, so Java makes the stale view throw ConcurrentModificationException on its next use. The check uses the same modCount counter as iterators (Section 6.4.4).

Example 6.1

Let l = [A, B, C, D]. After List<String> v = l.subList(1, 3); v.clear(); and l.add("E"), what does v.size() do?

  1. The view. v has offset 1 and length 2: [B, C].
  2. Clearing. v.clear() removes indices 1 and 2: l = [A, D], v empty. The removal went through the view, which updated its bookkeeping and stays valid.
  3. Adding from outside. l.add("E") bypasses the view: l = [A, D, E].
  4. Using the stale view. v.size() notices the original changed behind its back and throws ConcurrentModificationException.
Common mistake

Assuming subList returns an independent list. Code that writes List<String> firstThree = l.subList(0, 3); and then modifies firstThree modifies l too. For an independent piece, copy the view: new ArrayList<>(l.subList(0, 3)).

6.2.4Modifiable and unmodifiable lists

So far every list could be changed freely after creation. Not all can; Java has two kinds.

Mutable list
Elements can be added, removed, and replaced after creation: new ArrayList<>(), new LinkedList<>().
Immutable list
Contents never change after creation; a different list means a new list: List.of(...), List.copyOf(...).

The two side by side:

List<String> fixed = List.of("Ann", "Dan");
fixed.add("Ben");    // UnsupportedOperationException
List<String> copy = new ArrayList<>(fixed);   // mutable copy
copy.add("Ben");  // [Ann, Dan, Ben] — fixed is still [Ann, Dan]

List.of("Ann", "Dan") is immutable. The variable's type is still List<String>, so fixed.add("Ben") compiles; the error surfaces only at run time as UnsupportedOperationException. fixed.set(0, "X") throws the same. List.of also rejects null: List.of("a", null) throws NullPointerException.

new ArrayList<>(fixed) gives a modifiable version by copying the elements into a new array. The two objects are separate: at the end copy is [Ann, Dan, Ben] and fixed still [Ann, Dan].

Why want a structure that cannot change? When many parts of a program share a list, the restriction becomes a guarantee: no method that receives it can corrupt anyone else's data, and threads can read it without locks, since it cannot change mid-read. Immutability is a basic tool of functional programming.

A more advanced form is the persistent data structure, where every "update" makes a new version and old versions stay usable. Rather than copying everything, it shares the unchanged parts and rebuilds only the changed path. Adding to the front of a linked list, for example, creates one new node pointing to the untouched old list; the two share the tail.

A third option is often confused with these: Collections.unmodifiableList(l). It does not make an immutable list; it returns a read-only view wrapped around l. Writing through it is forbidden, but when l changes, so does the view.

Treating "read-only" and "immutable" as synonyms. A class that hands out Collections.unmodifiableList(list) stops outside code from changing the list, but its own internal changes show up in what the outside holds. To hand out a frozen snapshot, return List.copyOf(list).

6.3List methods

Beyond what it inherits from Collection, List defines many position-based methods. This section covers the common ones and their traps. The examples use ArrayList; every List class behaves the same, only the costs differ.

6.3.1The main methods and index bounds

Table 6.7: The main methods of the List interface.

Index-based methods first check the index and throw IndexOutOfBoundsException if it is invalid. The valid range depends on the method:

  • get, set, remove(int): 0 … size() − 1; index < 0 or index ≥ size() is an error.
  • add(int, E): 0 … size(). add(size(), e) appends and is legal; only index > size() is an error.

This makes sense: get asks for an existing element, while add opens a slot. A list of n elements has n + 1 gaps: before the first, between each pair, and after the last.

Example 6.2

Let l = [A, B, C] (length 3). Which calls are valid?

  1. l.get(3): valid indices are 0–2; 3 ≥ 3, so IndexOutOfBoundsException.
  2. l.add(3, "D"): add's bound is size(), and 3 ≤ 3, so D is appended: [A, B, C, D].
  3. l.set(0, "X"): valid; [X, B, C, D], returning "A".
  4. l.add(5, "E"): 5 > size() = 4, an error. A list cannot grow by leaving a hole.

6.3.2Code trace: duplicates, null, and search

Two properties set a list apart from a set: duplicates are allowed and order matters. This program tests both, plus a null element:

public class ListDemo {   // import java.util.ArrayList; import java.util.List;
    public static void main(String[] args) {
        List<String> names = new ArrayList<>();
        names.add("Ann");
        names.add("Ann");              // duplicate: allowed
        names.add(null);               // null: allowed
        names.add("Ann");
        System.out.println(names);            // [Ann, Ann, null, Ann]
        System.out.println(names.size());     // 4
        System.out.println(names.indexOf("Ann"));        // 0 (first occurrence)
        System.out.println(names.lastIndexOf("Ann"));    // 3
    }
}

indexOf scans from the front and stops at the first match, comparing with equals, not ==: "Ann".equals(data[0]) is true, so it returns 0. lastIndexOf scans from the back and matches at once in cell 3. Both return −1 if the element is absent, and both cost O(n) in the worst case.

The last line is subtle. For a null target, o.equals(data[i]) would throw a NullPointerException, so ArrayList has two loops: data[i] == null for a null target, o.equals(data[i]) otherwise. Cells 0 and 1 hold "Ann", cell 2 null, so the call returns 2.

The list holds "Ann" three times, each at its own position. If each value may appear only once, use a Set.

Common mistake

Assuming every list accepts null. ArrayList and LinkedList do, but a List.of(...) list throws NullPointerException on a null element, and even its contains(null) or indexOf(null) may throw.

6.3.3remove(int) or remove(Object)?

List has two remove methods, one taking an index (remove(int index)), the other an element (remove(Object o)). Such same-named methods with different parameters are overloaded; the compiler picks one by the argument's type.

With Strings there is no confusion: remove(1) is by index, remove("Ann") by element. With Integers an integer can be either.

List<Integer> nums = new ArrayList<>(List.of(10, 20, 30));
nums.remove(1);                    // removes index 1 → [10, 30]
nums.remove(Integer.valueOf(10));  // removes the value 10 → [30]
nums.remove(Integer.valueOf(99));  // absent → false, list unchanged
nums.remove(5);                    // IndexOutOfBoundsException

6.3.6Spliterator: a splittable iterator

An iterator delivers elements one at a time, front to back. To process a large list on a multicore processor, we want to split the work and give each part its own thread. Spliterator ("split" + "iterator") grew out of this need.

List<String> words = new ArrayList<>();
words.add("Java");
words.add("Python");
words.add("C++");
Spliterator<String> split =
        words.spliterator();
while (split.tryAdvance(
        System.out::println)) {
    // each call processes one element
}

Spliterator has two basic methods:

  • tryAdvance(action): if an element remains, applies the action and returns true; otherwise returns false. It merges hasNext() and next(). Here the action is the method reference System.out::println; the loop body is empty because the work happens in the condition. Output: Java, Python, C++, one per line.
  • trySplit(): hands part of the remaining elements to a new Spliterator and returns it, so two threads can take the two parts; returns null if too few remain.

Parallel streams (parallelStream()) use exactly this: trySplit to divide, tryAdvance to process each part. The slides trace a split:

6.4Traversal

Visiting every element in order is traversal: summing, finding the largest, printing, removing matches. It looks simple, but with the wrong tool a linear loop turns quadratic or the program stops with an exception.

6.4.1Three ways to traverse a collection

There are three ways. All yield the same elements in the same order; they differ in what they allow and what they cost.

1. Indexed for loop.

int n = list.size();
for (int i = 0;
     i < n; i++) {
  String s =
      list.get(i);
  ...
}

Only for a List, since it needs get(i); natural when the loop needs the index, say to print "item 3" or compare neighbors.

2. forEach or for-each.

list.forEach(
  System.out::println);

// or for-each:
for (String s : list) ...

Works for any Iterable and is shortest. list.forEach(...) takes a lambda or method reference; the for-each loop compiles to an iterator.

3. An explicit iterator.

Iterator<String> it =
    list.iterator();
while (it.hasNext()) {
  String s = it.next();
}

Longest, but it alone lets you remove elements safely mid-traversal, for reasons explained in Section 6.4.4.

Cost depends on the list. On an ArrayList, get(i) is O(1) and all three take O(n). On a LinkedList, get(i) walks the nodes in O(n), and the indexed loop repeats the walk at every step: O(n2), against O(n) for forEach and the iterator.

6.4.2Code trace: the cost of an indexed loop over a LinkedList

LinkedList is doubly linked: each node knows its successor and predecessor, and the list keeps first and last. get(i) walks to the node with the internal node(i), forward from the front if i < n/2, else backward from the end, so it walks min(i, n − 1 − i) links.

6.4.3The Iterator interface and the cursor

Iterator defines three methods:

hasNext()
Any elements left? Returns false at the end. It changes no state, so repeated calls give the same answer.
next()
Returns the next element and advances; throws NoSuchElementException if none is left.
remove()
Removes the element returned by the last next(). Optional: collections that do not support it throw UnsupportedOperationException.

Picture a cursor that, like a word processor's, sits between elements. It starts before the first; each next() jumps over one element and returns it. Past the last element, hasNext() is false.

An iterator is separate from the list; several can be open at once, each with its own cursor. In ArrayList's iterator the cursor is an integer, cursor, the index the next next() will return, and hasNext() just checks cursor != size.

6.4.4Removing while traversing: ConcurrentModificationException

Removing matching elements during traversal is a common need, and the natural-looking code is wrong:

for (String s : names)
    if (s.startsWith("A"))
        names.remove(s);
// ConcurrentModification-
// Exception (fail-fast)

Correct code uses the iterator's own remove() or removeIf:

Iterator<String> it =
        names.iterator();
while (it.hasNext())
    if (it.next().startsWith("A"))
        it.remove();
// or, briefly:
names.removeIf(s -> s.startsWith("A"));

The wrong version fails because of a counter. Every ArrayList has a field modCount, incremented by every structural modification, any add or remove that changes the element count (set does not count). A new iterator saves the counter as expectedModCount, and each next() compares the two. If they differ, the list changed behind the iterator's back, and it throws ConcurrentModificationException.

Definition 6.3

A fail-fast iterator detects that its collection was structurally modified from outside during traversal and throws at once, making the error visible instead of silently producing wrong results.

6.5ArrayList

Having seen what List does, we now open up how its classes do it, starting with ArrayList, the most used list class in Java.

6.5.1Classes that implement List

Six List structures stand out in the standard library. They share methods but differ inside, and so in strengths and weaknesses.

ArrayList
A growable array; fast indexed access; the default choice.
LinkedList
A doubly linked list; fast at the ends, slow by index.
Vector
An old ArrayList with synchronized methods.
Stack
A stack derived from Vector: push, pop, peek (last in, first out).
CopyOnWriteArrayList
Copies its array on every write; suited to many reader threads.
Arrays.asList()
Turns an array into a fixed-size List view.

6.5.2A growable array

An array's length is fixed at creation, yet a list's eventual size is usually unknown. ArrayList keeps its elements in an ordinary array and hides that array's length. The length is the capacity, the element count the size (size); always capacity ≥ size, the spare cells awaiting future adds.

When the array is full and another add arrives, ArrayList allocates an array about 1.5 times larger, copies everything over, and drops the old one. The copy is O(n) but rare, since many adds fit before the next one; appending is therefore amortized O(1).

ArrayList never shrinks by itself: add a million elements and remove them, and the capacity stays a million. trimToSize() cuts it to the current size.

Two details of real Java: new ArrayList<>() allocates nothing until the first add, which creates 10 cells; and the new capacity is old + old/2, coded as old + (old >> 1), since a one-bit right shift halves an integer. The slides' trace starts at capacity 4 to keep the steps few.

6.5.3Code trace: add(e) and growth

The heart of ArrayList's append:

public boolean add(E e) {
  if (size == data.length) {
    int newCap = Math.max(data.length + 1, data.length + data.length / 2);
    data = Arrays.copyOf(data, newCap);
  }
  data[size++] = e;
  return true;
}

If the array is full (size == data.length), the method computes a new capacity — Math.max ensures growth even at capacity 0 or 1, where 1 + 1/2 = 1 — and Arrays.copyOf creates the bigger array, copying the old elements to its front and leaving the rest null. data then points to the new array, and the unreferenced old one is garbage-collected. Finally data[size++] = e fills the first empty cell and increments the size.

6.5.4Amortized analysis: why grow by doubling?

An add that grows the array takes O(n). Appending counts as O(1) because we look at a long sequence of operations, not one.

Definition 6.4

The amortized cost of an operation is the total cost of a long sequence divided by its length. No probability is involved: it is an upper bound for every possible sequence. Finding one is amortized analysis.

The growth rule decides everything. Figure 6.19 counts the copies actually made over 40 adds, starting at capacity 4, when the capacity doubles, grows by 1.5, or grows by a fixed 4.

The chart's numbers can be checked by hand.

Example 6.3

Forty elements go into an empty dynamic array of capacity 4. How many copies does each rule make?

  1. Doubling (×2). 4 → 8 → 16 → 32 → 64, growing at 4, 8, 16, 32 elements: 4 + 8 + 16 + 32 = 60.
  2. ×1.5. 4 → 6 → 9 → 13 → 19 → 28 → 42 (old + old/2, integer division): 4 + 6 + 9 + 13 + 19 + 28 = 79.
  3. +4. 4 → 8 → … → 40, growing at 4, 8, …, 36: 4 + 8 + … + 36 = 4 · (1 + 2 + … + 9) = 4 · 45 = 180.

At 40 elements the gap is threefold, and it widens fast. A general calculation shows why.

Theorem 6.1 (Amortized cost of geometric growth)

Adding n elements to a dynamic array that doubles when full makes fewer than 2n copies; growing by 1.5 makes at most about 3n. Either way appending is amortized O(1).

With doubling the copy counts are c, 2c, 4c, …, K, where K, the last, is below n because the array held K elements then. Read backward they halve, so the sum is K · (1 + 1/2 + 1/4 + …) < 2K < 2n.

With 1.5, each term is about 2/3 of the next, so the sum is about K · (1 + 2/3 + 4/9 + …) = K · 1/(1 − 2/3) = 3K, at most about 3n. Integer division nudges the ratio from 2/3, changing the constant slightly but not the linear bound; with Java's growth from 10, the total stays below 3n throughout the first three million adds.

Adding the n writes, the total is under 3n for doubling and about 4n for 1.5: constant per operation. □

A fixed increment reverses the picture. Starting at c and adding c when full, growth happens at c, 2c, 3c, …, and the copies total

c + 2c + 3c + … + (n/c)·c ≈ c · (n/c)2/2 = n2/(2c)

O(n2) in all, O(n) per operation; a larger c only shrinks the constant. For 100 elements from capacity 10, adding 10 each time costs 10 + 20 + … + 90 = 450 copies, ×1.5 costs 202, doubling 150.

Goodrich and Tamassia explain amortization with the "accounting method": charge each cheap add a little more than it costs and bank the surplus as tokens. With doubling, the cheap adds between growths number half the array; at 2 tokens each, the bank can pay for copying every element at growth time. Since the balance never goes negative, each add costs a constant number of tokens.

Common mistake

Reading "amortized O(1)" as "every add is O(1)." A growing add still takes O(n), a pause that can hurt a real-time system; if the size is known, preallocate: new ArrayList<>(10000).

6.5.6Code trace: add(i, e)

Inserting in the middle means opening a slot:

Running the shift loop from the left when inserting or from the right when removing. Each step then overwrites the next element, and part of the list fills with copies of one element. 6.6LinkedList and the positional list

An array-based list is weak at the front, where every insertion or removal shifts all elements. A linked list avoids this by not storing elements contiguously. This section covers Java's LinkedList, the code of two of its operations, and the positional list ADT, which exploits linking fully.

6.6.1The doubly linked list

In LinkedList (Figure 6.22) each element lives in its own node, holding the data and references to the previous (prev) and next (next) nodes; with links both ways, this is a doubly linked list. The list object knows only first, last, and the count size.

Two consequences follow. The ends are cheap: inserting at the front creates a node and points first at it, shifting nothing, and last makes appending walk-free too. Random access is expensive: with no address calculation for element 500, the nodes are walked link by link, from the nearer end but still in O(n).

LinkedList also implements Deque (double-ended queue), so it has addFirst, addLast, removeFirst, removeLast, push, pop, offer, and poll, and works as a stack or a queue.

void addLast(E e) {

6.6.5The positional list ADT

Indices suit arrays, not linked lists, and they are unstable: one insertion at the front shifts every index, so "element 5" then names a different element. A text editor's cursor stays beside its word when text is inserted before it; it is a place, not a number. Goodrich, Tamassia, and Goldwasser make this idea an ADT.

Definition 6.5

A position is an object representing an element's place in a list, valid and unaffected by other insertions and removals until that element is removed. A positional list is a list ADT accessed through positions rather than indices, inserting, removing, and replacing at a given position.

In the book, Position<E> has one method, getElement(). In the linked implementation the node itself is the position, its class implementing Position; users can read the element and pass the position back, but not see the node's fields.

The second key idea is sentinel nodes, header and trailer, which hold no data and exist even in an empty list, pointing to each other. Every real node then has neighbors on both sides, insertion is always between two nodes, and null checks ("empty? first? last?") vanish.

Every method is constant-time because the position is the node: nothing is searched, only neighboring links rewired. The standard library has no direct counterpart. ListIterator comes closest, with O(1) insertion and removal at its cursor, but a cursor stands in one place, and two iterators making structural changes cannot share a list.

Common mistake

Reusing a removed position. After remove(p), a good implementation nulls the node's links so that validate throws; without that, addAfter(p, e) could corrupt the list through a node already cut out.

On paper it looks balanced; in practice ArrayList wins. Most programs mostly read and append, where it is at least as good, and LinkedList's advantages are often eaten by memory and cache effects (Section 6.6.8). ArrayList is the default.

For heavy use at both ends, as a queue or deque, LinkedList is an option, though ArrayDeque, a circular array with amortized O(1) at both ends and no per-node overhead, is usually better. LinkedList shines when a ListIterator sweep makes many insertions and removals.

6.6.8Two lists in memory

ArrayList spends about one reference (4 or 8 bytes, depending on the JVM) per element, plus spare capacity. LinkedList adds a node per element, with a header and three references, about 24–40 bytes: several times the memory.

The bigger difference is the cache. The processor fetches memory in blocks into its fast cache. ArrayList's contiguous references arrive several at a time, so traversal runs from the cache; LinkedList's scattered nodes mean each next may hit an address not in the cache, a cache miss, and main memory is tens of times slower. Both traverse in O(n), but ArrayList is usually clearly faster in real time.

6.7Other list classes

ArrayList and LinkedList cover almost everything. Four more structures serve special cases or survive from older versions; most concern lists shared by threads.

6.7.1Vector

Vector is a growable array like ArrayList, except that it doubles its capacity by default and all its methods are synchronized.

synchronized guards a method with a lock: while one thread runs it, other threads wait to enter any synchronized method of the same object. So two threads cannot add at once and corrupt the array; single operations are thread-safe.

Vector<Integer> v = new Vector<>();
v.add(10);            // [10]
v.add(20);            // [10, 20]
v.get(0);             // 10
v.remove(0);          // [20]
v.size();             // 1
v.capacity();         // 10

// compound operation: needs an outside lock
synchronized (v) {
    if (!v.isEmpty()) v.remove(0);
}

v.capacity() returns 10: the first array has 10 cells and never shrinks. Every call pays for the lock, even with one thread. Worse, locks guard only single methods; a compound check-then-act such as "remove the first element if not empty" is still unsafe, hence the synchronized (v) { … } block at the end.

Vector dates from Java 1.0. New code uses ArrayList for one thread and Collections.synchronizedList(...) or CopyOnWriteArrayList for several.

6.7.2The check-then-act race

One interleaving shows why the compound operation is unprotected. Let v = [20], and let threads T1 and T2 both run if (!v.isEmpty()) v.remove(0);.

Table 6.33: One interleaving of two threads. Each method is locked on its own, but the gap between two calls is unprotected.
StepT1T2v
1isEmpty() → false—[20]
2—isEmpty() → false[20]
3remove(0) → 20—[ ]
4—remove(0) → ArrayIndexOutOfBoundsException[ ]

T1 locks isEmpty(), sees false, and releases the lock; the scheduler may now run T2, which also sees one element. Both decide to remove: T1 succeeds, T2 throws on the empty vector. Each method is synchronized, but the pair is not atomic, not one indivisible unit. An error whose outcome depends on thread interleaving is a race condition. The fix puts the whole operation under one lock:

synchronized (v) { if (!v.isEmpty()) v.remove(0); }

The block takes the very lock Vector's methods use. While T1 is inside, T2 waits; then it sees an empty vector and does not remove.

Common mistake

Thinking "the class is thread-safe, so my code is." Vector, Collections.synchronizedList, and the like protect single calls only; every multi-call operation (check and remove, add if absent, traverse and modify) needs its own lock.

6.7.3The Stack class

Stack extends Vector with a last-in, first-out (LIFO) stack whose operations touch only the top, handy for undo/redo, where the last action is undone first.

6.7.4CopyOnWriteArrayList

Some lists are read constantly but rarely changed, like the event listeners notified when a button is clicked: traversed on every event, seldom extended. With many threads traversing, waiting for locks is costly. CopyOnWriteArrayList is built for this.

The idea is in the name: a change (add, set, remove) copies the internal array, edits the copy, and repoints the list; the old array is never touched. Consequences:

  • Reads are lock-free and fast. A reader reads the current array, which never changes in place.
  • Writes are expensive. Each copies the whole array, O(n); writers queue on a short lock so that none overwrites another's copy.
  • Iterators traverse a snapshot, the array current when they were created. Later writes leave them on the old array, so ConcurrentModificationException never occurs; in exchange they miss new elements and it.remove() is unsupported.

Good for lists traversed often, changed rarely, and shared by threads: listeners, configuration. Bad for large, frequently changed lists, where every add copies everything.

6.7.6Arrays.asList: a list view of an array

6.8Summary

  • A list keeps elements in positional order, indexed from 0, duplicates allowed. Basic operations: append, insert, remove, index, slice, search, length. Length (size) is not capacity.
  • In Java an ADT is an interface, an implementation a class. Iterable → Collection → List: for-each, common operations without indices, then position-based methods. Declare variables by interface: List<String> l = new ArrayList<>();.
  • subList is a view: changes reach the original, and outside structural changes invalidate it. List.of/List.copyOf are immutable, Collections.unmodifiableList only read-only, new ArrayList<>(…) an independent copy.
  • remove(int) removes by index, returning the element; remove(Object) by value, returning a boolean; in a List<Integer> a primitive argument is an index. Type parameters cannot be primitive; boxing is automatic, and unboxing null throws NullPointerException.
  • Traverse with an indexed loop, for-each/forEach, or an iterator; on a LinkedList the first is O(n2), the others O(n). An iterator is a cursor between elements.
  • Outside modification during traversal trips the fail-fast modCount check: ConcurrentModificationException. Remove safely with it.remove() (once per next()) or removeIf. ListIterator moves both ways and can add, set, remove; Spliterator splits for parallel work.
  • ArrayList: a growable array; get/set O(1), append amortized O(1), insert/remove O(n); grows about 1.5 times when full (10 on the first add). Geometric growth costs O(n) copies in all, a fixed increment O(n2).
  • LinkedList: doubly linked; O(1) at the ends, O(n) by index. Relinking is cheap, finding the place expensive. The positional list, with the node as position and sentinel nodes, makes every operation O(1).
  • ArrayList is the default; memory and cache behavior favor it. For heavy use at both ends, consider ArrayDeque or LinkedList.
  • Vector and Stack are legacy synchronized classes that leave compound operations unprotected; use ArrayDeque for stacks. CopyOnWriteArrayList copies on write and iterates over snapshots. Arrays.asList is a fixed-size view of the array: set works, add/remove do not.

6.10Test Yourself

  1. Let l = [A, B, C, D, E, F] be an ArrayList. We run l.subList(1, 4).clear(); and then l.subList(0, 2).set(1, "Q");. What is l at the end?

    Answer

    The first view, [1, 4), is B, C, D, and clear() removes them: [A, E, F]. The second view, [0, 2), is [A, E]; set(1, "Q") changes its element 1, index 0 + 1 = 1 of the original. Result: [A, Q, F].

  2. On List<Integer> m = new ArrayList<>(List.of(4, 0, 2, 1)); we call m.remove(m.get(1)); and then m.remove(1);. What is the list?

    Answer

    m.get(1) returns an Integer (0), so remove(Object) removes the value 0: [4, 2, 1]. m.remove(1) passes a primitive int, so remove(int) removes 2 at index 1: [4, 1].

  3. Twenty-five elements are added to an empty list created with new ArrayList<>(). At which adds does the capacity grow, and to what? How many elements are copied in total?

    Answer

    0 to 10 at the 1st add (no copies), 10 to 15 at the 11th (10 copies), 15 to 22 at the 16th (15), 22 to 33 at the 23rd (22): 10 + 15 + 22 = 47 copies, ending at size 25, capacity 33.

  4. How many links are walked in total if a 7-element LinkedList is traversed with an indexed for loop using get(i)? How many with an iterator?

    Answer

    The integer part of n/2 is 3. i = 0, 1, 2 walk 0, 1, 2 links from the front; i = 3, 4, 5, 6 walk 7 − 1 − i = 3, 2, 1, 0 from the end: 0 + 1 + 2 + 3 + 2 + 1 + 0 = 9. An iterator walks one link per next(): n − 1 = 6.

  5. On r = [P, Q, R] we take ListIterator<String> it = r.listIterator(3); and call, in order, it.previous(), it.previous(), it.set("X"), it.add("Y"), it.next(). What does the list become, and what does the last call return?

    Answer

    Start: P Q R |. The two previous() calls return R, then Q: P | Q R. set("X") replaces the last returned Q: P | X R. add("Y") inserts before the cursor: P Y | X R. next() returns X. The list is [P, Y, X, R].

  6. We take a five-element ArrayList's spliterator as a and call Spliterator b = a.trySplit();. Which indices do a and b cover?

    Answer

    The fence becomes 5 and the midpoint (0 + 5) / 2 = 2. The first half goes to the new spliterator: b covers [0, 2) (indices 0, 1), a [2, 5) (2, 3, 4).

  7. A hundred elements are added to an empty dynamic array of capacity 10. How many copies are made if the capacity, whenever it fills, (a) grows by 10, (b) becomes old + old/2?

    Answer

    (a) Growth at 10, 20, …, 90 elements: 10 + 20 + … + 90 = 450 copies. (b) 10 → 15 → 22 → 33 → 49 → 73 → 109: 10 + 15 + 22 + 33 + 49 + 73 = 202. A fixed increment grows quadratically, proportional growth linearly.

  8. Let Stack<String> s be an empty stack. After s.push("a"); s.push("b"); s.push("c"); s.add(0, "z");, what does s.pop() return, and what is s.search("z") afterwards? What design problem does this show?

    Answer

    add(0, "z"), inherited from Vector, puts "z" at the bottom: [z, a, b, c]. pop() returns "c", leaving [z, a, b]; search("z") counts b 1, a 2, z 3. Inheriting from Vector gives Stack methods that break LIFO.

  9. A CopyOnWriteArrayList c = [a, b, c, d] is traversed with for-each; the body calls c.add("e") if the element is "a" and prints every element. What is printed, and is there an exception? What would happen with an ArrayList?

    Answer

    The iterator traverses its snapshot. Adding "e" repoints the list at a new array while the iterator continues on the old one: abcd is printed, no exception, and the list ends as [a, b, c, d, e]. With an ArrayList, the add would bump modCount and the next next() would throw ConcurrentModificationException.

  10. For int[] d = {1, 2, 3};, what does Arrays.asList(d).size() return, and why?

    Answer

    1. A type parameter cannot be primitive, so the ints are not boxed; the array itself is the single element of a List<int[]>. For three elements, declare Integer[].
