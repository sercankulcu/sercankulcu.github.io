Chapter 4.3: Introduction to Programming

However clearly an algorithm is written on paper, a processor cannot run it directly. The only language a processor understands is machine language, made of zeros and ones. A programming language sits between the two worlds: people can read it, and a translation tool can turn it into machine language. This note first explains what a programming language is, how source code becomes machine code, and how the compiler, the interpreter, and the virtual machine share that work. It then classifies languages by level, type, paradigm, and typing discipline. The last sections show how a problem becomes a program and what stages software development goes through. The basic constructs (variables, decisions, loops, functions, and arrays) and the ways of finding bugs are illustrated with step-by-step trace tables. The code examples are in Java, Python, and C; the outputs of the Java and Python examples come from real runs.

4.3.1Basic concepts

A recipe tells you, step by step, what to do in the kitchen. A person reading it fills in a vague phrase such as "a pinch of salt" from experience. A computer has no such experience. Every step it is given must have exactly one meaning, and that meaning must be defined precisely in advance. Programming languages were born from this need.

4.3.1.1What is a programming language?

Everyday language is flexible. The sentence "See you tomorrow" does not say at what time; the listener completes the meaning from context. A machine cannot be expected to infer meaning from context. To make a machine do work, we need a language in which every statement has a single interpretation and whose rules are written down beforehand. Such languages are called formal languages.

Definition 4.3.1

A programming language is a formal language that lets people express computational steps to a computer. A collection of commands written in such a language is called a program.

A programming language is the tool for writing an algorithm in a form the computer can execute. An algorithm is an idea: "add a and b, then print the result." That idea can be written in Java, in Python, or in C. The notations differ, but all of them describe the same steps and produce the same output for the same input. Figure 4.3.1 shows this for a = 3 and b = 5: all three languages print 8.

The lines in the figure are only the addition part of complete programs. For a program to run, other lines are needed around them. Below is the complete version of the same task in Java and in C. The Java program was compiled and run with JDK 21; the output of the C program was determined by tracing it line by line.

Example 4.3.1

How is a complete program that adds a = 3 and b = 5 and prints the result written in Java and in C?

Java program:

public class Add {
    public static void main(String[] args) {
        int a = 3;
        int b = 5;
        System.out.println(a + b);
    }
}

C program:

#include <stdio.h>

int main(void) {
    int a = 3;
    int b = 5;
    printf("%d\n", a + b);
    return 0;
}

Both programs produce the same output:

8

In Java every program is written inside a class, and execution starts at the main method. In C, execution starts at the main function; to print to the screen, printf from the stdio.h library is used. In printf, %d means "an integer goes here" and \n is the end of a line. In Python the same job takes one line: print(a + b). The details differ, but the three steps of the algorithm (set up a, set up b, print the sum) appear in the same order in all three programs.

That the same problem can be solved in different languages raises a question of choice: which language? The answer depends on the needs of the problem and on the environment in which the program will run. An app for a phone, a calculation on a server, and the control software of a washing machine may call for different languages.

Common mistake

Thinking that programming means memorizing a language. The real work of writing a program is building the algorithm: understanding the problem, finding the steps, and making sure the steps run in the right order and under the right conditions. The language is the tool for writing those steps down. A well-built algorithm can be moved from one language to another in a few hours; no language can rescue a badly built one.

4.3.1.2Syntax and semantics

In English, the sentence "Ali went to school" is well formed. "Went school to Ali" can still be understood but breaks the rules. "The school went to Ali" follows the rules but makes no sense. Programming languages also define these two dimensions separately: whether a piece of text follows the rules, and what a well-formed piece of text does.

Definition 4.3.2

The syntax of a programming language is the set of rules that determines which constructs may be written in which order. Semantics determines what every well-formed construct does when it is executed.

In Java, ending every statement with a semicolon is a syntax rule. If the line int b = 5 has no semicolon at the end, the text breaks the rule and the program cannot be translated. That the expression a + b computes the sum of a and b is a semantic rule. Python has different syntax: statements need no semicolon, but the indentation of blocks is part of the rule.

A program with correct syntax does not necessarily give the desired result. A line that divides by 4 instead of 3 when computing the average of three grades follows the rules perfectly. The translator accepts the line without complaint, the program runs, and it prints a wrong number. The text is valid, but what it says is not what the programmer wanted. Such errors are called logic errors.

Example 4.3.2

In what way is each of the following three Java lines problematic: syntax or semantics?

  1. int b = 5 (no semicolon at the end of the line)
  2. double avg = (n1 + n2 + n3) / 4; (the average of three grades is wanted)
  3. System.out.println("Sum: " + a + b); (for a = 3, b = 5, "Sum: 8" is wanted)

The first line is a syntax error; the compiler stops with the message "';' expected". The second line follows the rules but divides by the wrong divisor: its meaning does not match the programmer's intent. The third line also follows the rules, but in Java + is evaluated from left to right: first "Sum: " is joined with 3, then 5 is appended, and the screen shows "Sum: 35". To get the intended result, the addition must be parenthesized: "Sum: " + (a + b). Only someone who knows the semantic rules of the language can spot the problem in the last two lines.

4.3.1.3Source code, assembly, and machine language

The text a programmer writes lives in a text file. This file can be opened in Notepad, read, and changed. A processor, however, cannot read this text. The commands a processor understands are encoded as binary numbers, and every processor family has its own instruction set.

Definition 4.3.3

Source code is the text form of a program that a developer can read and change. Machine language consists of the binary instructions the processor runs directly; a program made of these instructions is called machine code. Assembly language is the human-readable form of the machine instructions, written with symbolic names.

Figure 4.3.2 shows how a single line passes through these three forms. The compiler translates the source line sum = a + b; into three processor instructions. The first loads the value of a from memory into a processor register (R1). The second adds b to R1. The third writes the result in R1 to the location of sum in memory. Assembly writes these instructions with short names such as LOAD, ADD, and STORE. A tool called an assembler turns these names into binary codes. The binary codes in the figure are only an example; real encodings vary from processor to processor.

Two consequences follow from this translation. First, a programming language and a processor's language are not the same thing. Java or Python is not the language of any processor; for text written in these languages to reach the processor, a translation is needed. The programs that do this translation are generally called translators: compilers and interpreters. Second, one high-level line often corresponds to several machine instructions. The programmer says "add and store"; the translator spells out the load, add, and write steps.

Common mistake

Thinking that the processor "understands" Java or Python source code. The processor runs only its own machine language. That is why double-clicking a .java or .py file does not run it. The file must first pass through a compiler or an interpreter. In Java this job is split in two: javac translates the source code into bytecode, and the JVM runs the bytecode.

4.3.2Running a program

After source code is written, several things happen before a result appears on the screen. The text passes through a translator, the translated code runs on the processor or on a virtual machine, and the running program reads its input and produces its output. A different kind of error can arise at each stop along this path.

4.3.2.1From source code to output

Figure 4.3.3 shows the path of a Java program in five stops. The programmer writes the source code in a text file named Add.java. The computer cannot run this text as it is. At the translation stop, the compiler reads the text and checks whether it obeys the rules of the language. If there are no errors, it produces an output file. In languages such as C, this file is machine code directly. In Java it is an intermediate-code file named Add.class. At the execution stop the instructions are carried out on the processor; in Java this is done through the Java Virtual Machine (JVM). At the last stop the program produces its output: 8 for a = 3 and b = 5.

In Java this path is walked with two commands at the command line. javac Add.java runs the compiler and produces the file Add.class. java Add starts the JVM and runs the program in that file. It matters that the two steps are separate: compilation is done once, and the resulting file can be run as many times as you like. If the source code is changed, compilation must be repeated; otherwise the JVM keeps running the old .class file.

Common mistake

Fixing the source code, running java Add without recompiling, and concluding that "the fix did not work." The JVM runs the compiled .class file, not the source code. Every time the source code changes, javac must be run again. IDEs do this step automatically when you save or press the run button; for that reason the step is often overlooked.

4.3.2.2Kinds of errors

Every stop on the path exposes its own kind of error. Knowing at which stop an error shows up also tells us where to look for it.

Definition 4.3.4

A compile error is source code that does not obey the rules of the language; it is found during translation and the program never runs. Syntax errors and type errors are of this kind. A runtime error is an error that arises while the program is running and stops it. A logic error is when the program runs without any error message but produces a wrong result.

It is easy to see the three kinds in three small Java programs. In the first program, the semicolon at the end of the second assignment line has been forgotten:

public class MissingSemicolon {
    public static void main(String[] args) {
        int a = 3;
        int b = 5
        System.out.println(a + b);
    }
}

The compiler refuses to translate the program and reports the location of the error with a line number:

MissingSemicolon.java:4: error: ';' expected
        int b = 5
                 ^
1 error

The message gives the file name, the line number (4), and the expected token (;). The ^ below it shows where the compiler expected the semicolon. In this case no .class file is produced and no line of the program runs; "8" never appears on the screen. Figure 4.3.4 shows this situation with the red mark at the translation stop of the pipeline.

In the second program the syntax is flawless, but line 5 contains a division by zero:

public class DivideByZero {
    public static void main(String[] args) {
        System.out.println("Hello");
        int x = 10;
        System.out.println(x / 0);
        System.out.println("End");
    }
}

Compilation finishes successfully. When the program runs, "Hello" is printed first, then the JVM tries to evaluate x / 0 and stops the program:

Hello
Exception in thread "main" java.lang.ArithmeticException: / by zero
	at DivideByZero.main(DivideByZero.java:5)

In the output, ArithmeticException: / by zero names the division-by-zero error, and DivideByZero.java:5 gives the line of the error in the source file. The "End" line never runs. The compiler cannot catch this error, because the value of x and the division are computed only at run time. If the divisor were user input, it would be impossible to know at compile time whether it would be zero.

The third program computes the average of three grades, but a parenthesis is missing:

public class AverageBug {
    public static void main(String[] args) {
        int n1 = 70, n2 = 85, n3 = 90;
        System.out.println(n1 + n2 + n3 / 3);
        System.out.println((n1 + n2 + n3) / 3);
        System.out.println((n1 + n2 + n3) / 3.0);
    }
}
185
81
81.66666666666667

The program compiles without trouble, runs without any error message, and prints 185 on the first line. The expected result is a number between 81 and 82. Because division happens before addition, only n3 is divided by three: 70 + 85 + 90 / 3 = 70 + 85 + 30 = 185. This is a logic error. The second line adds the parentheses but is still not quite right. In Java the quotient of two integers is an integer; the fractional part of 245 / 3 is discarded and the result is 81. The third line divides by 3.0; the computation is done in floating point and the correct value, about 81.67, comes out. This is what logic errors have in common: the program "works," and only someone who compares the expected result with the actual one notices the problem.

Example 4.3.3

What kind of error is each of the following? (a) In Java, the line System.out.println("Hello") has no semicolon at the end. (b) When the user enters 0 for the number of students, the program stops while computing the average. (c) When computing a class average, the total is divided by n + 1 instead of the number of students n.

  1. (a) A compile error. The semicolon is a syntax rule; the compiler reports it with a line number and no program is produced.
  2. (b) A runtime error. The code obeys the rules and compiles; but the moment the divisor is 0, execution stops. The same program runs fine with non-zero inputs, so the error shows up only with certain inputs.
  3. (c) A logic error. The program runs with every input and prints a number; the number it prints is always smaller than it should be. For grades 60, 70, and 80, for example, it prints 210 / 4 = 52.5; the correct value is 210 / 3 = 70.
Common mistake

Counting the absence of an error message as proof that a program is correct. The compiler only checks whether the rules were followed; it cannot know whether the program does the intended job. Every program must be tried on a few inputs whose results have been computed by hand.

4.3.2.3Compiled, interpreted, and hybrid languages

There are three common ways to run source code. The difference lies in when the translation is done and how much of it is done.

Definition 4.3.5

A compiler is a program that translates the whole program into target code before it runs; this process is called compilation. An interpreter is a program that runs a program by evaluating it command by command at run time, without first translating it into an executable file; this process is called interpretation. In hybrid execution, the source code is first compiled to an intermediate code, and the intermediate code is executed on a virtual machine.

Table 4.3.2: Execution approaches
ApproachHow it worksExample languages
CompiledThe program is translated beforehand into target machine codeC, C++, Rust
InterpretedCommands are evaluated at run timePython, JavaScript
HybridIntermediate code is executed on a virtual machineJava, C#

Figure 4.3.5 shows the three paths side by side. On the compiled path, the file source.c goes through the compiler and an executable such as program.exe comes out. This file runs on the processor directly; at run time the compiler is no longer needed. On the interpreted path, the file source.py is handed to the interpreter every time it runs. The interpreter processes the commands in order and has the processor carry them out. There is no lasting machine-code file in between. On the hybrid path, Add.java is first compiled with javac into Add.class. The JVM runs this file, and the JVM itself is a program running on the processor.

Which path is chosen also determines how the program is distributed. A compiled C program is valid only for the processor and operating system it was compiled for. An .exe file compiled for Windows does not run on Linux or on a computer with a different processor. An interpreted Python program is distributed as source code; it runs on every computer that has the Python interpreter installed. Java's .class file, on the other hand, is processor-independent: the same file runs on every platform that has a JVM. Java's well-known slogan "write once, run anywhere" comes from this property.

Common mistake

Putting Java in the same group as C as a "compiled language." Java source code is compiled, but what the compiler produces is not machine code but bytecode, which the JVM understands. This code does not run directly on the processor; a JVM is needed to run it. Placing Java in the hybrid class describes this two-stage structure correctly.

4.3.2.4The compiler and the interpreter step by step

The difference between a compiler and an interpreter is best seen on the same small program. The third line of the following three-line pseudocode contains a division by zero:

LinePseudocode
1print "Hello"
2x ← 10
3print x / 0

In pseudocode, assignment is written with ←: x ← 10 means "give x the value 10." This keeps assignment from being confused with an equality comparison. Let the program be processed first by a compiler and then by a simple interpreter that runs line by line. What happens at each step is listed in Table 4.3.3.

Table 4.3.3: Processing the same program with a compiler and with an interpreter
StepCompilerSimple interpreter
1Lines 1, 2, and 3 are read and translated from start to end; no line has run yetLine 1 is translated and runs immediately: Hello
2The division is well formed; translation succeeds and an executable is producedLine 2 is translated and runs: x = 10; line 3 has not been read yet

In this program both paths end with the same screen: "Hello" followed by an error. The difference lies not in the kind of error but in the order of the work. The compiler translates the whole text first, and execution comes later as a separate stage. The interpreter interleaves translating and running line by line. Because division by zero is a runtime error, in both paths it shows up only when the third line runs. Figure 4.3.6 shows the final state of the two paths.

When the error is a syntax error, the two paths part ways. Suppose a parenthesis is left unclosed on the third line: print (x + 2. The compiler stumbles on this line during translation and produces no executable. The screen shows only the message "line 3: syntax error"; not even "Hello" is printed. A simple line-by-line interpreter, however, runs line 1 and prints "Hello," assigns 10 to x on line 2, and notices the error only when it reaches line 3.

Modern interpreters such as those for Python and JavaScript depart a little from this simple model: before they start running, they parse the whole file. They therefore report syntax errors at the very start. The following Python file shows this:

print("Hello")
x = 10
print((x + 2)
print("End")
  File "syntax_error.py", line 3
    print((x + 2)
         ^
SyntaxError: '(' was never closed

"Hello" does not appear on the screen. Before running the first line, Python read the whole file and found the unclosed parenthesis on line 3. When the same file has a division by zero instead of a syntax error, the situation changes:

print("Hello")
x = 10
print(x / 0)
print("End")
Hello
Traceback (most recent call last):
  File "zero_division.py", line 3, in <module>
    print(x / 0)
          ~~^~~
ZeroDivisionError: division by zero

This time "Hello" is printed, because a division by zero is detected only when the third line runs. Python's message resembles Java's: the file name, the line number, the kind of error (ZeroDivisionError), and a short description.

Example 4.3.4

A four-line program has a syntax error on line 2 and a division by zero on line 4. What appears on the screen if the program is run (a) with a compiler, (b) with a simple line-by-line interpreter, (c) with Python? Line 1 prints "Start" and line 3 prints "Middle".

  1. (a) The compiler first translates all four lines. It stops at the syntax error on line 2 and produces no executable. The screen shows only a compile error message for line 2; "Start" is not printed.
  2. (b) The simple interpreter translates and runs line 1: "Start". When it tries to translate line 2, it stops with the syntax error. Lines 3 and 4 are never reached. The screen shows "Start" and the error message.
  3. (c) Python first parses the whole file and finds the error on line 2. The screen shows only the SyntaxError message; the behavior is the same as in (a). The division by zero on line 4 never shows up in any of the three cases, because the program would have to run that far.

4.3.2.5Bytecode, the virtual machine, and JIT compilation

Python is called an "interpreted language," but the Python interpreter also contains a compilation step. CPython, the most common implementation of Python, first compiles the source code into an intermediate code called bytecode. It then executes this bytecode command by command on a virtual machine inside it. No machine-code file results. The compilation step is hidden from the programmer: the command python file.py performs the two stages one after the other.

Definition 4.3.6

Bytecode is an intermediate code made of simple instructions designed for a virtual machine rather than for a particular processor. A virtual machine is software that reads and executes these instructions; it imitates the work of a real processor in software.

The bytecode Python produces can be seen with the dis module. The following program compiles the line area = width * height + 2 and prints its bytecode:

import dis
dis.dis(compile("area = width * height + 2", "<code>", "exec"))
  0           RESUME                   0

  1           LOAD_NAME                0 (width)
              LOAD_NAME                1 (height)
              BINARY_OP                5 (*)
              LOAD_CONST               0 (2)
              BINARY_OP                0 (+)
              STORE_NAME               2 (area)
              RETURN_CONST             1 (None)

Each line of the output is a virtual machine instruction. LOAD_NAME pushes the value of a variable onto the virtual machine's stack. BINARY_OP 5 (*) multiplies the top two values on the stack, LOAD_CONST pushes the constant 2, and BINARY_OP 0 (+) adds. STORE_NAME binds the result to the name area. Instruction names may change slightly between Python versions; Python 3.13 was used here. The order, however, is the same in every version: first width and height are multiplied, then 2 is added. This order comes from operator precedence.

Executing bytecode instruction by instruction is slower than running machine code directly. For every instruction the virtual machine has to answer the question "what does this instruction mean?" The way to reduce this slowness is JIT compilation.

Definition 4.3.7

A just-in-time (JIT) compiler is a compiler that translates frequently executed pieces of code into machine code while the program is running. The translated piece is not interpreted on later runs; it runs directly on the processor.

Figure 4.3.7 shows this idea using JavaScript. The V8 engine in the Chrome browser first interprets the code. When it sees that a function has been called thousands of times, it compiles it to machine code. The JVM follows the same path: bytecode is interpreted at first, and frequently run methods are translated into machine code by the JIT. For this reason, long-running Java programs can reach speeds close to those of compiled C programs.

These examples bring out an important point: "compiled" or "interpreted" is a property not of a language but of an implementation of that language. Implementations of Python that compile to machine code have been written, and so have interpreters for C. Most real systems combine the two methods. Calling a language "interpreted" is a short way of saying how its most common implementation works.

Common mistake

Saying "Python is an interpreted language, so no compilation takes place." CPython compiles the source code to bytecode on every run. It stores the bytecode of imported modules as .pyc files in the __pycache__ folder and reuses these files on later runs if the source has not changed. What makes Python interpreted is that the bytecode is executed command by command on a virtual machine, not as machine code.

4.3.2.6The phases of a compiler

A compiler does not work in one big step. It splits its job into five consecutive phases; the output of each phase is the input of the next. Following the phases on a single line also explains which error the compiler catches and where. The line to follow is this:

area = width * height + 2;

1. Lexical analysis. The compiler sees the line as a sequence of characters: a, r, e, a, space, = ... The first phase splits these characters into meaningful pieces called tokens. Whitespace and comments are discarded in this phase. Eight tokens come out of the example line, and the type of each is known (Figure 4.3.8).

The errors caught in this phase are character sequences that match no token of the language. In Java the # character is not an operator. An unclosed string cannot be turned into a token either. The JDK 21 compiler reports these two cases as follows:

IllegalCharacter.java:4: error: illegal character: '#'
        int area = width # height;
                         ^
IllegalCharacter.java:4: error: not a statement
        int area = width # height;
                           ^
2 errors
UnclosedString.java:3: error: unclosed string literal
        System.out.println("Hello);
                           ^
1 error

2. Syntax analysis (parsing). The tokens are arranged into a tree according to the rules of the language; this tree is called a syntax tree. Figure 4.3.9 shows the tree of the example line. 4. Intermediate code generation and optimization. The checked tree is turned into simple instructions, each of which performs a single operation. This form is called three-address code, because each instruction mentions at most three names:

t1 = width * height
t2 = t1 + 2
area = t2

Here t1 and t2 are temporary names the compiler invents. Code optimization is performed on this form: unnecessary operations are dropped, and operations whose results are known at compile time are computed in advance. If width = 3 and height = 4 are constants that never change, the computation 3 × 4 + 2 = 14 is done before the program runs, and only area = 14 is left in the code. This optimization is called constant folding (Figure 4.3.11).

5. Code generation. In the last phase the instructions of the target processor are selected and translated into binary code. For the example line, a processor would get LOAD, MUL, ADD, and STORE instructions (Figure 4.3.12). The target of the Java compiler is not a real processor but the JVM. For this reason javac produces bytecode instead of machine instructions.

4.3.2.7The linker and the loader

Real programs do not consist of a single file. In a calculator program, the user interface may live in one file and the calculation functions in another. For the program to print to the screen, open a file, or take a square root, ready-made library code is also used. The compiler translates each source file separately. Combining these pieces into one program and loading it into memory to run is the job of two separate tools.

Definition 4.3.8

An object file is a machine-code file, produced by compiling a single source file, that cannot run on its own (.o or .obj). The linker is the program that combines object files and the library code in use into a single executable file. The loader is the part of the operating system that brings the executable file into memory and starts it running.

Figure 4.3.13 shows the path of a C program. main.c contains the main program and calc.c contains the calculation functions. The compiler translates them into the object files main.o and calc.o. In main.o there is a call to a function in calc.c, but the address of that function is not yet known. The compiler only leaves a note: "a function with this name is being called here." The linker resolves these notes. It finds the called function in calc.o and ready-made functions such as printf in the library. It ties every call to the correct address and finally writes the file program.exe.

If a called function cannot be found in any piece, the linker reports a linking error. This error differs from a compile error. Each file may have compiled flawlessly on its own; what is missing is the connection between the pieces. For example, if the function average called in main.c is misspelled averge in calc.c, the two files compile separately, but the linker cannot find the name average anywhere.

When the program is double-clicked or invoked from the command line, the loader steps in. It copies the file from disk into memory. It also loads and links the shared libraries the program needs: .dll files on Windows, .so files on Linux. Finally it directs the processor to the first instruction of the program. Many programs share a shared library; the same code does not have to be copied into each program separately.

In Java there is no separate linking step. Each class is compiled into its own .class file. The JVM's class loader finds and loads a class's file at the moment the class is first needed while the program runs. If a class file is missing, the error appears not during compilation or linking but at run time.

Common mistake

Mistaking an object file (.o, .obj) for an executable program. An object file contains machine code, but calls to other files and libraries are not yet linked. To run, it must go through the linker.

4.3.3Programming languages

The number of programming languages in use today is counted in the hundreds. It is neither possible nor necessary to know them all. Grouping languages by a few criteria makes it easier to place a new language when you meet one. The main criteria are closeness to the hardware, the era of origin, the purpose of use, the way of thinking, and the time of type checking.

4.3.3.1Language levels

Definition 4.3.9

A low-level language is a language whose instructions correspond one-to-one or nearly one-to-one to processor instructions: machine language and assembly. A high-level language is a language that lets you write a problem close to the way people express it and hides hardware details: C, Java, Python.

Figure 4.3.14 arranges languages on a ladder. At the bottom is machine language: 10110000 01100001. On Intel-compatible processors, these two bytes are the instruction "load the value 61h (hexadecimal 61, decimal 97) into the AL register." Assembly writes the same instruction as MOV AL, 61h. One rung up is C: the line x = x + 1; says nothing about registers; it talks about a variable. Java and C# are higher still; they take memory management away from the programmer. Python is at the top: writing print(x) needs no class or type declaration.

Climbing the ladder brings a gain and a cost. The gain is writing the same job in fewer and clearer lines. Printing a string to the screen takes one line in Python; in assembly it can take dozens. The cost is less control over the hardware. If a driver has to write to a specific memory address at a specific moment, languages on the lower rungs such as C or assembly are needed. So level is not a measure of quality; it describes a language's degree of abstraction. A high-level language is not "better" than a low-level one; it is better suited to other jobs.

Example 4.3.7

What number is the second byte in the machine instruction 10110000 01100001? Why is this number written as 61h in assembly?

  1. The second byte is 01100001. By place values: 0·128 + 1·64 + 1·32 + 0·16 + 0·8 + 0·4 + 0·2 + 1·1 = 64 + 32 + 1 = 97.
  2. The byte splits into two groups of four bits: 0110 = 6 and 0001 = 1. Every four bits make one hexadecimal digit; the number is 61 in base 16. Check: 6 · 16 + 1 = 97.
  3. The trailing h shows that the number is hexadecimal. Assembly programmers like hexadecimal notation because each digit corresponds to exactly four bits, which makes conversion to binary easy. 97 is the code of the lowercase letter "a" in the ASCII table.

4.3.3.2The evolution of programming languages

The first computers were programmed directly in machine language. Programmers wrote instructions as binary numbers, sometimes flipping switches by hand one at a time. Assembly appeared in the late 1940s: instructions were given memorable names, and assembler programs were written to translate these names into binary. Figure 4.3.15 summarizes the following seventy years on a timeline.

The development can be divided into three periods.

  • 1940–1970. The era of machine language and assembly. In 1957, John Backus's team at IBM developed FORTRAN. FORTRAN was the first widely used high-level language that let scientific formulas be written almost as in mathematics. In 1959, COBOL was designed for business and accounting applications. In 1964, BASIC was developed at Dartmouth College so that students could learn programming.
  • 1970–1990. In 1972, Dennis Ritchie developed the C language at Bell Laboratories. The UNIX operating system was largely rewritten in C. Because C was close to the hardware yet portable across processors, it became the basic language of systems programming. In 1983, Bjarne Stroustrup announced C++, which added the concepts of classes and objects to C.
  • After 1990. Python appeared in 1991, Java and JavaScript in 1995, and C# in 2000. What these languages share are managed environments that take memory management away from the programmer, and suitability for the web. Rich libraries and open-source ecosystems also helped them spread. More recently, Go (2009) focused on concurrent server programs and Rust (version 1.0 in 2015) on safe systems programming.

One trend stands out in this history: each new generation took over a job the previous one left to the programmer. Assembly took binary encoding off the programmer's hands, FORTRAN took register management, and Java took memory management. What was left to the programmer moved a little closer to the problem itself.

4.3.3.3Application areas and choosing a language

Programs run in very different environments, and each environment has different needs. The main application areas are these:

  • Web: interfaces that run in the browser (the client), server programs that answer requests, and web services.
  • Mobile: phone and tablet apps.
  • Data and artificial intelligence: data analysis, statistical modeling, machine learning, and automation.
  • Systems: operating systems, device drivers, and the embedded software inside a household appliance.
  • Scientific computing: simulation and engineering solutions; the behavior of a bridge under load or the frequency response of a circuit.
  • Games: game engines, graphics, and interaction with the user.

In each area some languages stand out (Figure 4.3.16). For interfaces that run in the browser, JavaScript (and its typed extension TypeScript) is almost the only choice, because it is the language browsers run directly. Android apps are written in Kotlin or Java and iOS apps in Swift; the official tools of these platforms support these languages. In data analysis, Python and R are common thanks to their rich libraries. In embedded systems, memory and processing power are limited, so C, C++, and Rust are preferred. On enterprise servers, Java, C#, and Go are common.

When choosing a language, first consider the problem area and the platform the program will run on. Then ask these questions. Are there ready-made libraries that do the needed work? Is the language's community large enough to find answers to questions? If the program will be maintained for years, is it easy to find developers who know the language? How important are speed and memory use? Does the language have a weakness from a security point of view? Which language does the team already know? How will the program be distributed?

Example 4.3.8

A group of electrical and electronics engineering students will do two projects: (a) a program that runs on a microcontroller, reads a temperature sensor, and switches a fan on and off, and (b) an analysis that plots a week of data collected from the sensor and finds its mean and maximum. Which languages are suitable?

  1. (a) A microcontroller may have only a few kilobytes of memory and no operating system. The program must access hardware registers directly. These conditions call for a compiled language close to the low level: C or C++. Rust is also an increasingly common option.
  2. (b) The program will run once on a laptop; speed is secondary. Ready-made libraries for graphics and statistics and quick experimentation matter. Python (or R) is suitable.
  3. Choosing different languages for the two projects is not a contradiction. The choice follows from the needs of the problem and the platform.
Common mistake

Choosing a language only because it is popular. The most popular language may not fit on a microcontroller, or the library you need may not exist in that language. Popularity is a plus in terms of community and abundance of resources, but it alone is not enough for the right choice.

Counting HTML as a programming language. HTML defines the heading, paragraph, and link on a page but computes nothing: it cannot add two numbers, test a condition, or repeat a task. The "programmed" part of a web page is the JavaScript code that works alongside it.

4.3.3.5Programming paradigms

There are several ways of thinking about solving the same problem. One counts off the steps in order, one sees the problem as objects talking to each other, and one builds a chain of functions that transform data. These ways of thinking are called programming paradigms.

Definition 4.3.10

A programming paradigm is a fundamental approach to how a program is organized. Imperative programming specifies step by step how operations are to be done and changes the state of the program with those steps. Object-oriented programming combines data and the behavior that works on that data in objects. Functional programming builds the program as a composition of functions that work on immutable data.

Figure 4.3.17 compares the three approaches on the same task: finding the sum of the array grades = {70, 90, 80}. The Java program below contains all three approaches.

import java.util.Arrays;

public class Paradigms {
    static class Student {
        private final int[] grades;
        Student(int[] grades) { this.grades = grades; }
        int total() {
            int t = 0;
            for (int g : grades) t += g;
            return t;
        }
    }

    public static void main(String[] args) {
        int[] grades = {70, 90, 80};
        /* imperative */
        int total = 0;
        for (int g : grades)
            total += g;
        System.out.println(total);
        /* object-oriented */
        Student student = new Student(grades);
        System.out.println(student.total());
        /* functional */
        System.out.println(Arrays.stream(grades).sum());

The imperative solution starts a variable named sum at 0 and changes it on every turn of the loop. The successive values of the sum are 0, 70, 160, and 240. The program reads like a recipe: "first do this, then do that." C and assembly are fundamentally imperative languages.

In the object-oriented solution, the grades live inside a Student object. The job of computing the sum belongs to the same object: student.sum(). The code that uses the object does not need to know how the sum is computed; it just asks the object. This arrangement pays off as programs grow. Everything about the student lives in one place, and when a change is needed it is clear where to look. Java, C++, and C# are object-oriented languages.

In the functional solution, the expression Arrays.stream(grades).sum() turns the array into a stream of values and sums the stream. No variable holds an intermediate state, and the array itself does not change. The last line of the program confirms this: the array is still [70, 90, 80]. The functional approach favors functions that always give the same output for the same input and change nothing outside themselves. Such functions are easy to test and to combine. Haskell is a purely functional language; Python, JavaScript, and Java also offer functional features.

Example 4.3.9

The largest of the numbers in an array is to be found. How do the imperative and functional approaches express this job? Let the array be {12, 45, 7, 30}.

  1. Imperative: a variable named max starts at the first element of the array (12). Each element is compared with max; if it is larger, max is updated. The state changes step by step: 12 → 45 → 45 → 45. The result is 45.
  2. Functional: Arrays.stream(array).max().getAsInt() in Java, max(array) in Python. The expression says "the maximum of the array"; the order of comparisons and the intermediate variable are invisible to the programmer. The array does not change, and the result is again 45.
  3. In both solutions the computer makes the same comparisons. The difference lies in how the program reads: one puts "how" in front, the other "what."

4.3.3.6Static and dynamic typing

Every value has a type: 5 is an integer, "five" is a string, and true is a Boolean. Languages split in two according to when types are checked.

Definition 4.3.11

Static typing is the discipline in which a variable's type is known in the source code and checked at compile time: Java, C, C#. Dynamic typing is the discipline in which the type is carried by the value rather than the variable and is checked at run time: Python, JavaScript.

In Java, a variable's type is written when it is declared: int x = 5;. From then on x can hold only integers. The line x = "five"; is caught in the compiler's semantic analysis phase: "incompatible types: String cannot be converted to int". The error is found before the program ever runs.

In Python, a variable's type is not declared. The same name can refer first to a number and then to a text. The type is carried by the value itself:

4.3.4Problem solving

Writing a program does not begin at the keyboard. First you understand what the problem is, then you solve a few examples by hand, and only at the end do you write code. When this order is skipped, the result is often programs that "run but do the wrong job."

4.3.4.1From problem to program

The example problem is a simple one: a program that computes the area of a rectangle. Figure 4.3.18 shows this problem turning into a program in five stages. The output of each stage is the input of the next.

  1. Define the problem. What is wanted becomes clear: the area of a rectangle. The program's input is the width and height, and its output is the area. There is also a constraint: a length cannot be zero or negative, so width and height must be greater than 0. Constraints are often not written down explicitly in the problem; whoever defines the problem has to find them.
  2. Try examples. A few examples are solved by hand: 3 × 4 = 12, 5 × 5 = 25. A boundary case is also considered: what should happen if the width is 0? By the constraint, this input is invalid. The examples solved by hand also supply the expected results for later checking whether the program works correctly.
  3. Build the algorithm. The language-independent steps are written in pseudocode: read the width, read the height, compute the area, print the area.
  4. Convert to code. The algorithm is translated into the chosen language. In Java, the computation line becomes area = width * height; and the printing line System.out.println(area);.
  5. Test. The program is run with the examples solved by hand. For 3 and 4 it gives 12: correct. For −2 and 4 it gives −8: since an area cannot be negative, this is wrong. The error is not in the code but in the algorithm; the algorithm never checks the constraint. We go back to the algorithm and add the step "if width and height are not greater than 0, report an error."

The return in the last stage is a natural part of the process. The stages form not a straight line but a loop: if testing finds something missing in the coding or the algorithm, we go back to the relevant stage. The corrected algorithm is this:

read width
read height
if width > 0 and height > 0 then
    area ← width × height
    print "Area: ", area
else
    print "Invalid size"

The Java version of this algorithm is below. In Java, && is the "and" operator: the result is true if both conditions are true.

import java.util.Scanner;

public class Area {
    public static void main(String[] args) {
        Scanner in = new Scanner(System.in);
        int width = in.nextInt();
        int height = in.nextInt();
        if (width > 0 && height > 0) {
            int area = width * height;
            System.out.println("Area: " + area);
        } else {
            System.out.println("Invalid size");
        }
    }
}

Starting to write code without defining the problem. A badly defined problem turns into a program that works correctly but does the wrong job. The request "a program that computes a grade average" leaves several questions unanswered. Are the grades weighted? How many grades will be entered? What happens if an invalid grade (−5, 120) is entered? A program written without asking these questions has to be changed on its first real use.

4.3.5Software development

A small program such as the rectangle area is one person's work for an hour. A bank's mobile application or a hospital's appointment system, on the other hand, is the work of dozens of people over months or even years. At this scale, organizing the work is at least as important as the code itself.

4.3.5.1The software development process

The path from problem to program is divided, at large scale, into six stages (Figure 4.3.19). The stages can be explained with an "app that computes a student's grade average."

  1. Requirements. What does the user want? The student will enter the grade and credit of each course, and the app will show the weighted average. A grade must be between 0 and 100. The app will run on a phone. Requirements are written by talking with the user, and all later stages rest on this text.
  2. Design. The screens, the data, and the algorithms are planned. What will be entered on which screen? Where will the grades be stored? By what formula will the average be computed? Flowcharts and pseudocode are the tools of this stage.
  3. Coding. The design is written in a programming language.
  4. Testing. Expected results are compared with actual results. For two courses, one with 60 points and 3 credits and one with 90 points and 2 credits, the expected average is (60 · 3 + 90 · 2) / 5 = 360 / 5 = 72. If the app shows 75 (the unweighted mean of the two grades), there is a bug and we go back to coding.
  5. Deployment. The program is delivered to the user: it is published in an app store or an installation file is shared.
  6. Maintenance. After use begins, new bugs are found and new requests arrive: "show the letter grade too." These requests are new requirements, and the cycle starts again.

Depending on the project, the stages are carried out sequentially or iteratively. Feedback from users can change the requirements and the design. Most of the effort spent over a software's lifetime goes not to the first version but to maintenance. That is why it matters to write code from day one so that it is readable and changeable.

Common mistake

Thinking the testing stage means "seeing that the program works." The aim of testing is not to prove that the program works correctly but to find the cases in which it works incorrectly. A good test suite includes normal inputs whose results have been computed by hand beforehand, boundary cases (0, an empty list, the smallest and largest values), and invalid inputs.

4.3.5.2Development approaches

There are different approaches to organizing the six stages (Figure 4.3.20).

In the waterfall model the stages are done in order and once each. Design does not start until the requirements are fully written, and coding does not start until the design is finished. A document is produced at the end of each stage. The strength of this arrangement is its clarity: who does what and when is known. Its weakness is that it is closed to change. If a gap in the requirements is noticed during coding, the cost of going back is high.

In the agile approach the work is divided into short cycles, each a few weeks long. In each cycle there is a little planning, a little coding, and testing. At the end of the cycle a working version is shown to the user and feedback is collected. A misunderstood requirement thus surfaces within a few weeks rather than months later. The price of this approach is the need for constant communication with the user.

In prototyping, a quick draft is prepared before starting on the real product. The draft has screens, but there may be no real computation or database behind them. If the user cannot fully explain what they want, the idea becomes clear once they see the draft. The purpose of the draft is to make the requirements visible. It must not be mistaken for the product itself and put straight into use.

4.3.5.3Development tools

A developer's daily work is a loop: write the code, translate and run it, test the result, find the bug if there is one, fix it, and try again. A different tool comes into play at each step of this loop (Figure 4.3.21).

  • Code editor and IDE. Code can be written in a text editor, but programmers mostly use an integrated development environment (IDE). An IDE colors the code, completes names, underlines syntax errors as you type, and organizes the project's files. IntelliJ IDEA, Eclipse, and Visual Studio Code are common examples.
  • Compiler and runtime. It translates and runs the program: javac and the JVM, the Python interpreter, a C compiler.
  • Debugger. It stops the program at a chosen line, shows the current values of the variables, and steps through line by line.
  • Version control. It records every change to the files and makes teamwork possible.
  • Testing tools. They verify expected behavior automatically. The programmer writes once, "for this input this output is expected," and the tool reruns all the tests within seconds after every change. In Java, JUnit is the well-known tool for this.
  • Package manager. It downloads the ready-made libraries (dependencies) the program uses, tracks their versions, and updates them: pip for Python, npm for JavaScript, Maven and Gradle for Java.
Common mistake

Assuming code the IDE does not underline is free of errors. An IDE can show syntax and type errors as you type, because it runs the first phases of the compiler in the background. It cannot see runtime and logic errors. The absence of a red underline says only that compilation will succeed.

4.3.5.4Version control

If a student keeps copies of a file while writing an assignment as hw_final.java, hw_final2.java, hw_REALLYFINAL.java, they are trying to do version control by hand. This method gets muddled within days. Which copy has which change is forgotten; and if two people work on the same file, things become hopeless.

Definition 4.3.12

Version control is a system that stores the history of changes to files and organizes how several people work on the same files. A commit is the storing of the state of the files at a given moment together with who changed what and when. A branch is a line of changes that splits off from the main code and proceeds independently. A merge is the transfer of one branch's changes into another branch.

Figure 4.3.22 shows the history of the rectangle program. C1 is the first version. In C2 the area computation was added, and in C3 the perimeter computation. After C2, a developer opened a branch (B1) to try a new computation and worked there without breaking the main code. When the experiment succeeded, the branch was merged into the main branch (C4). Had the experiment failed, the branch would have been deleted and the main branch never affected. If a change in C3 introduced a bug, the project can be returned to its C2 state with a single command.

The most common version control tool is Git. In Git the history above is created with a few commands. git init turns a folder into a repository. git add stages the changed files for the next commit. git commit -m "area added" creates the commit with its message. git branch experiment opens a new branch; git merge experiment merges that branch into the current one. git log lists all commits with their author, date, and message.

In teamwork, every developer has a copy of the repository on their own computer. Services such as GitHub and GitLab store the repository on the network and serve as a common meeting point between the copies. If two people changed different lines of the same file, Git merges the changes automatically. If they changed the same line, a merge conflict occurs. Git shows the two versions side by side and asks a person to choose which one stays.

Example 4.3.13

Ayşe and Mehmet are working from the same repository. Line 12 of the program is double vat = price * 0.18;. Ayşe changes this line to price * 0.20 and commits. Mehmet changes the same line to price * VAT_RATE and adds the constant at the top of the file. What happens when they try to merge their changes?

  1. The constant line added at the top of the file is only Mehmet's change; Git takes it without trouble.
  2. Both changed line 12. Git cannot know which is correct and reports a conflict. Both versions of the line are shown, marked, in the file.
  3. The two developers talk and decide the final form of the line: price * VAT_RATE, with the constant's value 0.20. The chosen form is committed and the merge is complete.
Common mistake

Thinking version control is a tool only for big teams. A student working alone also benefits from being able to go back in time. When a change breaks the program, returning to the last working version takes one command. The commit messages also help you remember later why the code was changed.

4.3.6Basic programming constructs

However different languages may look, they are all built on the same few building blocks. Values are stored in named places and computed with expressions. Different paths are chosen according to conditions, and work is repeated. Frequently performed jobs are given names, and many values are gathered under a single name. The constructs are given first in pseudocode and then with their Java and Python counterparts.

Definition 4.3.13

A variable is a named place in memory that holds a value; its value can change during the program. A data type determines how a value is represented in memory and which operations can be performed on it.

Keeping a value that may be fractional in an integer type. In Java, the line int avg = 245 / 3; gives no error; it stores 81, and the fractional part is silently lost. 4.3.6.2Operator precedence

When an expression contains several operations, operator precedence determines which is done first. The rules in programming languages are the same as the mathematics rules learned at school:

  1. What is inside parentheses is computed first.
  2. Multiplication, division, and mod (remainder) are done before addition and subtraction.
  3. Addition and subtraction are done last.
  4. Operations at the same level are done from left to right.

The mod operation (% in Java and Python) gives the remainder of a division: 7 mod 3 is 1, the remainder of dividing 7 by 3. Table 4.3.13 shows these rules applied to five expressions.

4.3.6.3Decisions and loops

If a program ran only from top to bottom in order, it would take the same steps for every input. Real problems, however, require behaving differently depending on conditions and doing the same work over and over. The two constructs that provide this are the decision and the loop (Figure 4.3.25).

Definition 4.3.14

A selection, or decision, chooses one of several paths of operations depending on whether a condition is true or false. A loop repeats a group of operations as long as a condition is true. The repeated group of operations is the loop's body, and each run of the body is an iteration.

In a decision, only one of the two paths is followed on each run. In the area algorithm, if the condition is true the area is computed, and if it is false a warning is printed; the two never happen together in the same run. In a loop, however, the flow returns to the condition at the end of the body. The condition is checked again at the start of every iteration. When the condition becomes false, the loop is exited and execution moves to the line after the loop.

For a loop to be able to end, the body must contain a change that affects the condition. If the condition is i ≤ 3, the body must push i above 3 someday. If there is no such change, the condition stays true forever and the loop never ends.

4.3.6.5Functions and arrays

As programs grow, two needs arise. The first is that the same job is done in many places in the program; the area of a rectangle may be computed in ten places. The second is storing many similar values; defining 40 separate variables for the grades of the 40 students in a class makes no sense. The function meets the first need and the array the second (Figure 4.3.27).

Definition 4.3.16

A function is a block of code that performs a specific task and is called by a name. It can take parameters as input and can return a result. The values given when calling the function are called arguments. An array is a structure that stores many values of the same type under a single name, by sequence number. The sequence number of an element is called its index.

A function names a task. The function square(x) is the name of the task "take the square of a number." The code that uses the function does not care how the square is computed; it just writes square(4) and gets 16. The formula lives in one place. If there is a bug in the formula, it is fixed once, and the fix is reflected everywhere the function is called.

In an array, values are selected by sequence number. In Java, C, and Python the sequence number starts at 0. In the four-element array grades, the first element is grades[0] = 85 and the last is grades[3] = 64. The last index is always length − 1. This rule may seem odd at first, but there is logic to it: the index says how many steps the element is from the start of the array; the first element is zero steps from the start.

These two constructs divide a program into small pieces that can be tested separately. A program that computes a grade average can be split into three functions that read the grades, compute the average, and find the letter grade; the grades are also kept in a single array.

Trying to use a variable defined inside a function outside the function. 4.3.6.8Libraries and APIs

Taking a square root, sorting a list, or reading a file are jobs every programmer often needs. If every programmer had to write them from scratch, it would waste time and be a source of bugs. For this reason languages come with ready-made, tested functions.

Definition 4.3.17

A library is a collection of ready-made functions that others have written and tested. An API (application programming interface) defines the functions a library or a service exposes to the outside, along with their inputs and return values.

An API is like a contract (Figure 4.3.30). The API of the square root function says three things: the function's name, that it takes a number, and that it returns the square root of that number. Which method is used inside the function and how floating-point details are handled do not concern the user. Even if the library's authors replace the inside with a faster method, programs that use it keep working unchanged as long as the API stays the same.

4.3.7Debugging

Every programmer makes mistakes; what sets an experienced programmer apart is knowing an orderly way to find the error. Finding and removing an error in a program is called debugging.

4.3.7.1Debugging techniques

Debugging is not a guessing game but an investigation that proceeds step by step. The following techniques are the tools of this investigation.

  1. Reproduce the bug. Does the same input trigger the error every time? Starting the search before finding an input that brings out the error on demand is wasted effort. This input is also needed to check that the error is really gone after the fix.
  2. Print intermediate values. Before and after the suspicious line, the values of the variables are printed to the screen. The first place where the expected and the actual value part ways is the location of the bug.
  3. Set a breakpoint. In the debugger, a breakpoint is placed on a line. The program stops when it reaches that line, and all the variables at that moment can be inspected.
  4. Step through. After the program stops, it is advanced line by line. After each line, look at which value has changed.
  5. Narrow the search. Half of the code is temporarily disabled and you find which half contains the bug. Then that half is split in two again. In a hundred lines of code, the bug comes down to a single line in seven splits, because 27 = 128 ≥ 100.
  6. Explain it aloud. Explaining the code line by line to someone, even to a toy on the desk, often reveals the bug. While explaining you say "this line does this," and suddenly you notice that the line actually does something else.

Figure 4.3.31 imitates the look of a debugger. The program has stopped at the breakpoint on line 4 and has not yet run that line. The variables panel shows the three grades. The line is avg ← n1 + n2 + n3 / 3. When the "Step" button is pressed, first n3 / 3 = 30 is computed, then 70 + 85 + 30 = 185. The average comes out as 185; the expected value is 245 / 3 ≈ 81.67. Common mistake

Hiding the symptom of a bug without finding its cause. Because the average comes out as 185, dividing the result by 2.27 gives about 81.5 for this input but produces a wrong result for every other input. The fix is made at the root cause of the bug: the missing parenthesis is added.

Example 4.3.19

A program computes the average of the entered grades with avg ← total / n. Which edge cases should be tried, and which error can each reveal?

  1. No grades entered (n = 0): division by zero. The program is fixed to print "no grades entered" when n = 0.
  2. A single grade (n = 1): the average must be the grade itself. If the loop bound is off by one, the result comes out 0.
  3. The smallest and largest grades (0 and 100): the input check must not reject these values by mistake; for example, grade ≥ 0 should be written rather than grade > 0.
  4. An invalid grade (−5 or 120): the program must not accept this value.
  5. A fractional result (70, 85, 90): the average should come out around 81.67. If there is integer division, 81 comes out.

4.3.7.4The cost of software bugs

A bug in an assignment results in a low grade. The cost of bugs in real systems can be millions of dollars, even human lives. Three famous examples show the real-world counterparts of the kinds of errors described in this note.

Ariane 5 (1996). On its first flight, the European Space Agency's new rocket Ariane 5 veered off course about 37 seconds after liftoff and broke apart within seconds. According to the inquiry board's report, the cause was a number conversion. The navigation software was converting a 64-bit floating-point horizontal velocity value into a 16-bit signed integer. A 16-bit signed integer can hold at most 32,767. The software had been taken from the slower-climbing Ariane 4, where this limit was never exceeded. Ariane 5's horizontal velocity was much larger, the conversion raised an overflow error, and the navigation system shut down.

    public static void main(String[] args) {
        double speed = 40000.0;
        short narrow = (short) speed;
        System.out.println(narrow);
        System.out.println(Short.MAX_VALUE);
    }
}

32767

The largest value of the short type is 32,767. 40,000 exceeds this limit. Java gives no error; it keeps only the last 16 bits of the number's binary representation. Because 16 bits can hold 216 = 65,536 different values, the result is 40,000 − 65,536 = −25,536. A positive speed has silently turned into a negative number. Ariane 5's software was written in the Ada language and, instead of staying silent on overflow, it raised an error. But there was no code to catch and handle that error, and the system shut down. In both cases the root cause is the same: it was never tested whether the value could leave the range the type can hold.

Mars Climate Orbiter (1999). The probe NASA sent to Mars came too close to the planet while entering orbit and was lost. Software at the ground station produced the effect of the thrusters in English units (pound-force seconds). The other software that used this data expected metric units (newton-seconds). One pound-force second is about 4.45 newton-seconds. As a result, the effect of the thrust was computed about 4.45 times too small, and the orbit calculation drifted gradually over the journey of more than nine months. Each of the two programs worked correctly on its own; the bug was in the interface between them.

Therac-25 (1985–1987). The software of a radiotherapy machine used in cancer treatment had a timing bug. When the operator entered settings in a particular order and very quickly, the safety check was skipped. In earlier models hardware interlocks also performed this check; in the Therac-25 this job was left to software alone. In six accidents between 1985 and 1987, patients received radiation doses far above normal; at least three patients died.

All three bugs are of the kind a compiler cannot catch. One is an edge case, one a unit inconsistency, one a timing-dependent logic error. The shared lessons can be gathered in a few points. Edge cases must be tested, and units must be stated clearly in variable names and documentation. Software taken from one system must be retested under the conditions of the new system, and code should be reviewed by someone else.

Common mistake

Not stating the unit in the variable name. From the code you cannot tell whether a variable named speed is in km/h or m/s. Names such as speedKmh or speedMs prevent two programmers from interpreting the same number in different units. The loss of Mars Climate Orbiter shows the value of this small habit.

4.3.7.5Readable code

Code is written once and read many times. It is read by its own author weeks later, by teammates, and by others who take over maintenance. Readable code both prevents bugs and makes them easier to find. The following two pieces of pseudocode do the same job.

It works but is unreadable:

a ← read()
b ← read()
c ← a*b/2
print c

The same program, readable:

// area of a triangle = base × height / 2
base ← read()
height ← read()
area ← base × height / 2
print "Area: ", area

Whoever reads the first program has to work out the formula to understand what c is; a*b/2 could be a triangle's area, or a mistyped average computation. The second program explains itself. The differences are these:

  • Meaningful names. area is written instead of c, and base instead of a. The reader understands a variable's role from its name.
  • Consistent indentation and spacing. The spaces around operations and the regular indentation of nested blocks show the boundaries of the structure at a glance.
  • Named constants instead of magic numbers. A number embedded in the code whose meaning is not explained is called a magic number. Instead of price * 0.20, define VAT_RATE ← 0.20 and write price * VAT_RATE. When the rate changes, a single line is corrected.
  • Moving repetition into a function. If the same formula is written in three places, one fix must be made three times, and one of them will surely be forgotten.
  • Comments. A comment says not what the code does but why it does it. The comment // add 1 to x repeats the code and adds nothing. The comment // the array starts at 0, add 1 for the ordinal number, however, explains an intention.

4.3.8Summary

  • A programming language is a formal language that expresses an algorithm in a form a computer can execute. Syntax determines what may be written, and semantics what the written text does. A program with correct syntax can do the wrong job.
  • Source code is the text people read; machine language is the binary instructions the processor runs; assembly is the symbolic notation of machine instructions. One high-level line often corresponds to several machine instructions.
  • Source code is run in three ways. In compiled languages (C) the program is translated to machine code beforehand. In interpreted languages (Python) commands are evaluated at run time. In hybrid languages (Java) the source code is compiled to bytecode and the bytecode is executed on a virtual machine (the JVM). A JIT compiler translates frequently run code into machine code at run time. The compiled/interpreted distinction is a property of the implementation, not of the language.
  • There are three kinds of errors. A compile error is found during translation, and the program never runs. A runtime error stops the program during execution. A logic error gives no error message, produces a wrong result, and is found only by testing.
  • A compiler works in five phases: lexical analysis (tokens), syntax analysis (syntax tree), semantic analysis (names and types), intermediate code and optimization (e.g. constant folding), and code generation. The first three phases look for errors. The linker combines object files and libraries, and the loader brings the program into memory and starts it.
  • Languages are classified by level (low: machine language, assembly; high: C, Java, Python), by kind (general-purpose, domain-specific, scripting, markup), and by paradigm (imperative, object-oriented, functional). Level is not a measure of quality but of abstraction. The choice of language is determined by the problem area, the platform, libraries, performance, security, and team experience.
  • In static typing (Java), type errors are found at compile time; in dynamic typing (Python), when the line in question runs.
  • The path from problem to program: define the problem (input, output, constraints), solve examples by hand, build the algorithm, convert it to code, and test. If testing finds a gap, return to an earlier stage.
  • The software development process is an iterative process made up of requirements, design, coding, testing, deployment, and maintenance. The waterfall model passes through the stages once, in order. The agile approach proceeds in short cycles. Prototyping makes vague requirements visible. The IDE, compiler, debugger, version control, testing tools, and package manager are the tools of this process.
  • Variables, decisions, loops, functions, and arrays are the basic programming constructs. Operator precedence is as in mathematics. For a loop to end, the body must affect the condition. Every function call opens its own frame on the call stack. Array indices start at 0, and the last index is length − 1.
  • Bugs are found by testing with edge cases (0, an empty list, a negative number, the smallest and largest values) and by tracing the program step by step with a trace table. Readable code (meaningful names, named constants, functions, comments that explain "why") both prevents bugs and makes them easier to find.

4.3.10Test Yourself

  1. What kind of error is each of the following Java errors? If it is a compile error, in which phase of the compiler is it caught? (a) System.out.println("Hello); (b) Using an undeclared variable total. (c) A loop that runs with the condition i <= n over an array of n elements. (d) Dividing the total by n − 1 when computing an average.

    Answer

    (a) A compile error; because the unclosed string cannot be turned into a token, it is caught in the lexical analysis phase (javac: "unclosed string literal"). (b) A compile error; whether a name has been declared is checked in the semantic analysis phase ("cannot find symbol"). (c) A runtime error; in the last iteration i = n and array[n] is outside the array, so Java throws ArrayIndexOutOfBoundsException. (d) A logic error; the program runs with every input but finds the average larger than it is.

  2. A three-line Python file reads: print("A"), print(1 / 0), print("B" (the parenthesis on the last line is unclosed). What appears on the screen when the file is run? What would a simple line-by-line interpreter have shown?

    Answer

    Python parses the whole file before it starts running. It finds the unclosed parenthesis on line 3 and gives only the message SyntaxError: '(' was never closed. "A" is not printed, and the division by zero is never reached. A simple line-by-line interpreter would print "A" first, stop at the division by zero on the second line, and never see the syntax error on the third line.

  3. Into how many tokens is the line total = total + 1; split in lexical analysis? What are the types of the tokens?

    Answer

    Six tokens: total (identifier), = (operator), total (identifier), + (operator), 1 (constant), ; (separator). Whitespace is discarded. Because the same name appears twice, it counts as two separate tokens.

  4. What does the following pseudocode print? How many times does the body run, and how many times is the condition checked? s ← 0; i ← 1; while i ≤ 4: s ← s + i × i; i ← i + 2; print s.

    Answer

    Iteration 1: 1 ≤ 4 is true; s = 0 + 1 × 1 = 1, i = 3. Iteration 2: 3 ≤ 4 is true; s = 1 + 3 × 3 = 10, i = 5. Check: 5 ≤ 4 is false, and the loop ends. 10 is printed. The body runs 2 times and the condition is checked 3 times. Because multiplication is done before addition, no parentheses are needed in s + i × i.

  5. function f(x): return 2 × x + 1 is defined. What does print f(f(2)) print? How many frames are opened, and are the two on the stack at the same time?

    Answer

    The inner call runs first: a frame is opened for f(2), x = 2, 2 × 2 + 1 = 5 is returned, and the frame closes. Then a new frame is opened for the outer call f(5): 2 × 5 + 1 = 11. 11 is printed. Two frames are opened but they are not on the stack at the same time: the outer call starts after its argument has been computed and the inner frame has closed.

  6. In Java, what is s after the line int s = 17 % 5 * 2 + 9 / 2;? Write out the order of computation.

    Answer

    %, *, and / are at the same precedence level and are done before addition, from left to right. 17 % 5 = 2, 2 × 2 = 4. Then 9 / 2 is 4, because it is the quotient of two integers (not 4.5). Finally 4 + 4 = 8. s = 8.

  7. A Python function returns "a" + 5 if x is greater than 10 and "small" otherwise. The program calls message(3) and then message(20). When does the error show up? What would happen if the same logic were written in Java?

    Answer

    Python parses the file without trouble, because the syntax is correct. message(3) returns "small" and it is printed. At the call message(20) the faulty line runs for the first time and raises a TypeError. In dynamic typing a type error is seen only when the line runs; if x never exceeded 10, the error would never be seen. In Java, in a method whose return type is String, "a" + 5 is string concatenation and is valid: it returns "a5". If the return type were int, the compiler would report the type mismatch before the program ever ran.

  8. A program to find the smallest element of an array starts with min ← 0 and compares each element with if d[i] < min then min ← d[i]. What is the output for d = [3, 8, 1, 6]? What is the bug, and how is it fixed?

    Answer

    None of the four comparisons is true: none of 3, 8, 1, and 6 is less than 0. min never changes and the output is 0; the correct result is 1. The bug is in the initial value: 0 is a value from outside the inputs and acts like the smallest value for positive numbers. The fix is min ← d[0]. Trace: min = 3; 8 < 3 is false; 1 < 3 is true, min = 1; 6 < 1 is false. The output is 1.
