Basic Concepts

What Is a Programming Language?

  • A formal language that lets people express the steps a computer should carry out.
  • Syntax defines which constructs can be written; semantics defines what they do.
  • The same problem can be solved in different languages; the choice depends on requirements and environment.

Basic Concepts

Source Code and Machine Language

  • Source code is the program text a developer can read and edit; machine language is the binary instructions the CPU executes.
  • A compiler or interpreter bridges the gap: the programming language and the processor's language are not the same thing.

Execution · Step by step

How Does a Program Run?

The programmer writes the source code in a text file. The computer cannot run this text directly.

Translation: the compiler checks the syntax. A forgotten semicolon causes a compile error here, and the program never runs.

If there are no errors, machine code is produced, or, as in Java, intermediate code (bytecode).

Execution: the instructions run on the CPU (in Java, via the JVM). Runtime errors such as division by zero show up here.

The output depends on the input (a = 3, b = 5) and on the program's logic. With a logic error, the program runs but gives a wrong result.

Kinds of errors: compile-time (a syntax rule), runtime (during execution), logic (a wrong result).

Execution · Step by step

Compiler and Interpreter Step by Step

The compiler reads the whole program from start to end; no line has run yet.

Dividing by zero on line 3 is not a syntax error; translation succeeds and an executable file is produced.

Now execution starts: line 1 → output Hello.

Line 3 causes a runtime error (division by zero), the kind of error a compiler cannot catch.

An interpreter works in a translate-run loop: line 1 is translated and run at once → Hello.

Line 2 is translated and run: x = 10. Line 3 has not even been read.

At line 3, an error. The earlier lines have already run. A simple line-by-line interpreter would notice even a syntax error only on reaching that line.

A compiler catches syntax errors before the program runs; an interpreter starts at once and (in simple interpreters) sees an error only on reaching that line. Modern interpreters such as Python and JavaScript parse the whole file first and report syntax errors up front; Python also compiles to bytecode.

  • CPython first compiles the source to bytecode, then executes it instruction by instruction on a virtual machine; no machine-code file is produced.
  • The “interpreted” label comes from this way of executing; the compile step is hidden from the programmer.
  • Modern JavaScript engines (e.g. V8) use a JIT: they translate frequently run code into machine code while the program runs.
Compiled versus interpreted is a property of the implementation, not the language; in practice most systems combine both.

Execution · Step by step

Phases of a Compiler

Lexical analysis: the character stream is split into meaningful pieces called tokens; whitespace and comments are dropped. A character the language lacks, such as #, or an unclosed string is caught here.

Syntax analysis: the tokens are arranged into a syntax tree by the language's grammar. A missing ; or an unclosed parenthesis is caught at this phase.

Semantic analysis: checks that names are declared and types are compatible. Undefined variables and type mismatches are found here.

Intermediate code and optimization: the expression is broken into simple instructions that each do one operation; unnecessary work is removed and constant expressions are precomputed.

Code generation: instructions for the target CPU are chosen and encoded in binary. The Java compiler's target is not a real CPU but the JVM.

The first three phases look for errors and report them with a line number; the last two produce the code that runs. No phase catches value-dependent errors such as division by zero.

Execution

Linker and Loader

  • Large programs consist of many source files; the compiler turns each into a separate object file.
  • The linker combines the object files and any library code used into one executable. If a called function is defined nowhere, it reports a link error.
  • The loader is part of the operating system: it brings the file into memory, attaches shared libraries (.dll, .so) and starts execution at the first instruction.
  • Java has no separate link step: the JVM's class loader loads .class files as they are needed.

Languages

Language Levels

  • Low-level languages are close to the hardware; high-level languages let you express a problem in human terms.
  • Level describes the degree of abstraction, not whether a language is good or bad.

Languages

Programming Paradigms

  • The imperative approach states step by step how the work is done.
  • The object-oriented approach combines data and behavior in objects.
  • The functional approach emphasizes transformations and immutable data.
  • Java can combine several approaches.

Languages

Choosing a Language

  • Consider the problem domain and the target platform.
  • Weigh the library ecosystem, the community and the maintenance cost.
  • Think about performance, security, team experience and deployment together.
Popularity alone is not enough to pick the right language.

Static and Dynamic Typing

Java: static

int x = 5;
x = "five";   // won't compile
error: incompatible types:
String cannot be converted to int

Python: dynamic

x = 5
x = "five"    # fine
print("a" + 1)
TypeError: can only concatenate
str (not "int") to str
  • With static typing, a variable's type is declared in the source and checked at compile time: Java, C, C#. Errors are found before the program ever runs.
  • With dynamic typing, the type travels with the value and is checked at run time: Python, JavaScript. The same name can hold a number, then text; Python reports the error only when that line runs.
  • Some languages convert types silently: in JavaScript "5" * 2 → 10, but "5" + 2 → "52".

Problem Solving · Step by step

From Problem to Program

First pin down what is asked: the area of a rectangle. Write the input, output and constraint.

Solve a few examples by hand; consider the boundary case (0) too.

Write a language-independent algorithm (pseudocode).

Translate the algorithm into the chosen language (Java).

Test: a negative input gave a wrong result → orange arrow: go back to the algorithm and add the step "error unless width, height > 0".

  • Each stage's output is the next stage's input.
  • A badly defined problem can become a program that works correctly but does the wrong job.

Problem Solving · Run the pseudocode step by step

Tracing the Algorithm: Rectangle Area

Run 1: read width = 3; it goes into the memory box named "width".

Read height = 4.

Condition: 3 > 0 and 4 > 0 → true.

area = 3 × 4 = 12.

The result is printed. The "else" branch is skipped this time.

Run 2: read width = -2; it goes into the memory box named "width".

Read height = 4.

Condition: -2 > 0 and 4 > 0 → false (width is negative) → take the else branch.

A warning is printed; the area is never computed. The bug found in testing is now fixed.

read width
read height
if width > 0 and height > 0 then
    area ← width × height
    print "Area: ", area
else
    print "Invalid size"

Software · Step by step

The Software Development Process

Requirements: what does the user want? E.g. "an app that computes a student's grade average".

Design: plan the screens, data and algorithms (this is where flowcharts come in).

Coding: implement the design in code.

Testing: compare expected and actual results; if there are bugs, go back to coding.

Deployment: deliver the program to users (installation, release).

Maintenance: bugs are fixed and new requests arrive → the cycle restarts with new requirements.

  • Depending on the project, the stages can run in sequence or iteratively; user feedback can change the requirements and the design.

Software

Version Control

  • Each commit stores the files as they are at that moment, with who changed what and when. After a bad change you can go back to an earlier version.
  • A branch lets you experiment without breaking the main code; when the work is done, the branch is merged into the main branch.
  • Team members work on the same files; if two people change the same line, the tool flags the conflict and asks someone to choose.
  • The most widely used tool is Git; GitHub and GitLab are services that host repositories online.

Basic Constructs

Variables and Data Types

  • A variable is a named box in memory holding a value; the value can change while the program runs.
  • A data type fixes how a value is represented and which operations apply to it.
  • Meaningful names make a program's purpose visible.

In Java: int, double, String, boolean.

Basic Constructs

  1. Parentheses
  2. Multiplication, division, mod (remainder)
  3. Addition, subtraction

Basic Constructs

Decisions and Loops

Decision: only one of two paths

Loop: an arrow going back

  • A decision picks one of several paths by a condition; a loop repeats a group of steps while a condition holds.
  • In both, it must be clear when the condition changes (otherwise: an infinite loop).

Basic Constructs · Run the pseudocode step by step

Loop Trace: An Infinite Loop

First version: line 4 is missing. i ← 1 sets up the loop variable.

Condition 1 ≤ 3 → true: enter the loop body.

print i → 1. The body is done; back to the condition.

The condition is again 1 ≤ 3 → true: no line in the body changes i.

The same output again: 1. The state is identical to the previous round.

Nothing ever makes the condition false, so the loop never ends: an infinite loop. A console program can only be stopped with Ctrl+C.

Fixed version: i ← i + 1 added to the body. Start again: i = 1.

1 ≤ 3 is true: print 1, then i ← 2. The loop variable now advances each round.

2 ≤ 3 is true: print 2, i ← 3.

3 ≤ 3 is also true (equality): print 3, i ← 4.

Condition 4 ≤ 3 → false: leave the loop.

The line after the loop: done. The body ran 3 times and the condition was checked 4 times.

i ← 1
while i ≤ 3 repeat
    print i
    i ← i + 1      // missing at first
print "done"

Basic Constructs

Functions and Arrays

  • A function names a task; it can take input and return a result.
  • An array stores many values of the same type, by index.
  • These constructs help split a program into small, testable pieces.

Basic Constructs · Run the pseudocode step by step

Function Trace: Call and Return

A function definition is only recorded, not run. The program starts at line 5 and meets the call area(3, 4).

A new frame for area is pushed onto the call stack: 3 → width, 4 → height.

The body runs: result = 12. This variable lives only in this frame.

return result: 12 goes back to the caller and the function ends.

The frame is popped; the returned value is assigned to a: a = 12.

The same function is called with different arguments: a brand-new frame, width = 2, height = 5.

result = 10. The 12 from the previous call is not visible in this frame.

10 is returned and the frame closes.

The returned value is assigned to b: b = 10.

22 is printed. A function written once was used twice; the area formula lives in one place.

function area(width, height)
    result ← width × height
    return result
end
a ← area(3, 4)
b ← area(2, 5)
print a + b

Basic Constructs · Run the pseudocode step by step

Array Trace: Average of Grades

The array holds four grades under one name; cells are selected by the indices 0, 1, 2, 3.

sum ← 0: the accumulator starts at zero. Without a starting value, the sum would be undefined.

i = 0: grades[0] = 85 → sum = 0 + 85 = 85.

i = 1: grades[1] = 72 → sum = 85 + 72 = 157.

i = 2: grades[2] = 90 → sum = 157 + 90 = 247.

i = 3: grades[3] = 64 → sum = 247 + 64 = 311.

The loop ends after 4 rounds. avg = 311 / 4 = 77.75. The last index is 3: length − 1.

The result is printed. Had the loop reached grades[4], it would have gone past the end: a 4-element array has no cell 4.

grades ← [85, 72, 90, 64]
sum ← 0
for each i ← 0, 1, 2, 3 do
    sum ← sum + grades[i]
avg ← sum / 4
print "Average: ", avg

Debugging

Debugging Techniques

  • Reproduce the bug: does the same input trigger it every time?
  • Print intermediate values: print variables before and after the suspicious line.
  • Set a breakpoint: the program pauses at that line so you can inspect variables.
  • Step through: after each line, see which value changed.
  • Narrow it down: disable half the code and find which half holds the bug.
  • Explain it out loud: walking someone (or a toy on your desk) through the code line by line often reveals the bug.

Paused, the program shows that n3 / 3 = 30 will be computed: the average comes out as 185, but 81.67 is expected.

Debugging · Run the pseudocode step by step

Finding a Bug by Tracing: The Largest Number

Test 1: inputs 7, 12, 5; expected output 12.

max ← 0: a starting value for the largest.

7 > 0 is true: max = 7.

12 > 7 is true: max = 12.

5 > 12 is false: max stays. Output 12 ✓. One passing test does not prove a program correct.

Test 2: all negative, −5, −2, −9; expected output −2.

max ← 0. This value comes from none of the inputs.

All three comparisons are false: no input exceeds 0, so max never changes.

Output 0 ✗. The trace points to the culprit: the starting value on line 2 comes from outside the inputs.

Fix: max ← a. max = −5 → −2 > −5 true, max = −2 → −9 > −2 false. Output −2 ✓. Test 1 is rerun as well: still 12.

read a, b, c
max ← 0
if a > max then max ← a
if b > max then max ← b
if c > max then max ← c
print "Largest: ", max

Debugging

The Cost of Software Bugs

Ariane 5 (1996)

A 64-bit floating-point velocity value overflowed when converted to a 16-bit integer. The navigation software shut down; about 37 seconds after liftoff the rocket veered off course and broke up within seconds.

Mars Climate Orbiter (1999)

One piece of software produced thrust data in imperial units (pound-force·seconds) while another expected metric units (newton·seconds). The probe came too close to Mars and was lost.

Therac-25 (1985–1987)

A timing bug in a radiotherapy machine's software bypassed a safety check when the operator typed quickly; patients received massive radiation overdoses.

  • None of the three could be caught by a compiler: one was a boundary case, one a unit mismatch, one a timing-dependent logic error.
  • The shared lesson: test, try boundary cases, state units explicitly, and have someone else review the code.

Readable Code

Works, but unreadable

a ← read()
b ← read()
c ← a*b/2
print c

The same program, readable

// triangle area = base × height / 2
base ← read()
height ← read()
area ← base × height / 2
print "Area: ", area
  • Meaningful names: area instead of c; the reader learns the variable's role from its name.
  • Consistent indentation and spacing: the bounds of nested blocks are visible at a glance.
  • A named constant instead of a magic number: VAT_RATE ← 0.20 instead of 0.20; when the rate changes, you fix one line.
  • Move repetition into a function: if the same formula appears in three places, every fix must be made three times.
  • A comment explains why the code does something, not what it does. Code is written once and read many times.

Summary

Chapter Summary

  • A programming language expresses an algorithm in a form the computer can execute.
  • Source code runs through compilation, interpretation or a hybrid process.
  • Languages are classified by level, kind and paradigm.
  • Software development is an iterative process from requirements to maintenance.
  • Variables, decisions, loops, functions and arrays are the basic programming constructs.
  • Bugs are found by testing with boundary cases and tracing the program step by step.
