Addressing

Protocols Work in Layers

The browser produces an HTTP request (data). The application layer decides “what to say”.

The transport layer splits the data and adds a TCP header to each piece: port number, sequence number. A lost piece can be requested again.

The Internet layer adds an IP header: source and destination IP addresses. Routers choose a path by looking only at this header.

The link layer adds a frame header (MAC address) and sends the bits over a cable or radio.

At the receiver the process reverses: each layer reads and strips its own header, and the data reaches the server application just as the browser sent it.

Addressing

Data Travels in Packets

The message is not sent in one piece: it is split into 4 packets. Each packet's header holds a sequence number and the source and destination addresses.

Packets travel independently: #1 and #3 take R1 → R2 → R4.

#2 and #4 take R1 → R3 → R4. Routers choose the best path for each packet at that moment.

Packets arrive out of order: first #1, #3, #4. #2 was lost at a busy router.

TCP notices the missing sequence number; #2 is resent (via R3 again).

All packets have arrived. The receiver orders them by sequence number and reassembles the message: “HELLO, WORLD!”.

Addressing · Step by step

A Packet's Path Through Routers, Step by Step

The laptop (192.168.1.10) sends a packet to the server at 203.0.113.10. The IP header has TTL = 64. The destination is not on the local network → the packet goes to the default gateway (R0, the home router).

R0 receives the packet and decrements TTL (63). The destination matches only 0.0.0.0/0 (the default route) → the ISP's router R1. (With NAT, the source address is also changed here.)

R1: TTL 62. Two entries match: /24 and /0. Longest prefix wins: 203.0.113.0/24 is more specific → R2. The routes to R4 and R5 are not used.

R2: TTL 61. Both 203.0.0.0/16 and 203.0.113.0/24 match; /24 is longer → R3. Had /16 been chosen, the packet would have gone to R6.

R3: TTL 60. The destination network is directly connected to R3; the packet is delivered to the server.

The packet crossed 4 routers and TTL dropped from 64 to 60. TTL keeps a packet caught in a loop from circulating forever: when it hits 0, the packet is dropped and a “time exceeded” message goes back to the sender. tracert / traceroute sends packets with TTL 1, 2, 3… to list the routers on the path.

receive packet, look at destination IP
TTL = TTL − 1;  if 0, drop and notify source
find table entries that match the destination
pick the longest-prefix (most specific) entry
forward to that entry's next hop

Addressing

IP Addresses

An IP address identifies a network interface and lets packets be routed to it.

IPv4

32 bits: four numbers separated by dots (each 0–255), called dotted-decimal notation.

192.168.1.25
IPv6

128 bits: groups of hex digits; a much larger address space.

2001:db8::25
A device's local IP address need not be the same as the public IP address seen on the Internet.

Addressing

Local and Public IP Addresses (NAT)

The laptop sends a packet to the server. The source is its local IP (192.168.1.10); private addresses are not routed on the Internet. The router replaces it (together with the port number, NAPT) with a public IP.

The router replaces the source address with its own public IP (203.0.113.7) and records the mapping in its NAT table.

The server sees only 203.0.113.7 and sends its reply there. From outside, every device in the home looks like one address.

The router checks its NAT table: the reply belongs to the laptop at 192.168.1.10. It rewrites the destination and forwards the packet.

A domain name is a name people can read. DNS translates it into an IP address you can connect to.

Addressing

DNS Resolution, Step by Step

1. The user types www.ornek.edu.tr into the address bar. Connecting requires this name's IP address.

2. The browser and operating system check their own caches first: no record.

3. The question goes to the DNS resolver in the network settings (usually the ISP's server).

4. The resolver starts at the top: the root server doesn't know the name but says “ask the .tr servers”.

5. The .tr server doesn't know the full name either: “ask the authoritative server for ornek.edu.tr”.

6. The authoritative server knows the record and answers: 203.0.113.10.

7. The resolver passes the answer to the browser and caches it for a while (TTL); the next question is answered at once.

8. Now that it knows the IP address, the browser connects to the web server at 203.0.113.10.

Addressing · Step by step

The DNS Resolver and Its Cache, Step by Step

The browser asks the resolver for www.ornek.edu.tr. The resolver's cache is empty (it just started).

Not in the cache, and no known server either → ask a root server.

The root doesn't know the name; it points to the .tr servers. This is written to the cache.

The .tr server is asked.

.tr points to the authoritative server for ornek.edu.tr; that is cached too.

The authoritative server is asked.

The authoritative server knows the record: 203.0.113.10. It is cached for its TTL (here 1 hour) and passed to the browser. 3 queries.

Within the same minute, another page asks for ogrenci.ornek.edu.tr.

That name isn't cached, but the authoritative server for ornek.edu.tr is known: root and .tr are skipped, and the authoritative server is asked directly.

The answer is 203.0.113.20; just 1 query.

Another user asks for www.ornek.edu.tr: the record is cached → 0 queries, an instant answer. When the TTL expires the record is removed and the next question goes back to the authoritative server; that is why an address change doesn't reach everyone at once.

is the name in the cache?  Yes → answer, done
server = closest known (else root)
ask that server for the name
referral: cache it, ask the referred server
IP received: cache it (TTL), answer

Addressing

Ports: IP Is the Building, Port Is the Apartment

An IP address is like a building, a port number like an apartment in it. Common ports: 80 HTTP, 443 HTTPS, 22 SSH, 53 DNS.

1. The browser opens https://ornek.edu.tr. DNS supplies the IP; the default port for HTTPS is 443. The packet is addressed to IP:port.

2. Routers first deliver the packet to the IP address (the building). The IP only decides which computer to reach.

3. The server's operating system looks at the port number (the apartment) and hands the packet to the service listening on it, here the HTTPS web server. :80 and :22 go to other services.

4. If the URL includes a port, it replaces the default: http://203.0.113.10:8080 goes to another application listening on :8080. One IP can host many services on different ports.

Addressing · Step by step

TCP: Three-Way Handshake, Data and Teardown

The client asks to connect: a SYN segment with initial sequence number 1000 (random in practice). The server was listening on port 443.

The server accepts: its own sequence number is 5000 and ack = 1001, meaning “got 1000, expecting 1001”. A SYN consumes one sequence number.

The client confirms with an ACK (ack = 5001). Three segments set up the connection: the three-way handshake. No data has been sent yet.

The client sends a 100-byte HTTP request: bytes 1001–1100. With HTTPS, a TLS handshake also runs over this channel first.

With ack = 1101, the server reports that all 100 bytes arrived. Without the ACK, the client would resend the same bytes after a timeout.

Done; the client closes its direction with a FIN.

The server acknowledges the FIN (ack = 1102). If it still has data to send, it can keep sending.

The server sends its own FIN.

The client sends the final ACK; the connection is closed in both directions. Setup took 3 segments, teardown 4. UDP has none of these steps.

client → SYN
server → SYN + ACK
client → ACK        // connected
client → data (HTTP request)
server → ACK
client → FIN;  server → ACK
server → FIN;  client → ACK  // closed

Addressing

HTTP vs. HTTPS: What Does Encryption Change?

HTTP: If you log in over HTTP on public Wi-Fi, someone on the same network can read the packets and see the password in plain text.

HTTPS: Data is encrypted with TLS: an interceptor sees only meaningless bytes. The browser's “connection is secure” indicator in the address bar shows this (a padlock in older versions).

Certificate: The browser also checks the server's certificate: it verifies that you really reached the organization behind ornek.edu.tr. The padlock doesn't mean the site is honest; phishing sites use HTTPS too.

Addressing

Encryption Basics

Symmetric encryption

The same key encrypts and decrypts. It is fast; the problem is getting the key to the other side safely. Example: AES.

Asymmetric encryption

The public key is given to everyone (encrypts/verifies); the private key stays secret (decrypts/signs). Slower, but it solves key distribution. Examples: RSA, elliptic curves.

Hash

Produces a fixed-length fingerprint of the data. It is not encryption: it cannot be reversed; used for storing passwords and checking integrity. Example: SHA-256.

HTTPS uses both together: asymmetric for agreeing on a key, symmetric for the actual data. A hash is no substitute for encryption; “encrypted” and “hashed” are different things.

Addressing · Step by step

How Encryption Works Together in HTTPS

1. The server sends the browser its certificate and public key. The private key stays secret on the server.

2. The browser generates a random session key (K), encrypts it with the server's public key and sends it (the asymmetric step). An eavesdropper can't decrypt K. This is the older “RSA key transport” model. In TLS 1.3 both sides derive a shared key with Diffie–Hellman; the certificate's public key only proves the server's identity (with a signature).

3. The server decrypts K with its private key. Both sides now share the same secret key; asymmetric encryption has done its job.

4. The actual data (page, form, password) flows both ways encrypted symmetrically with K: symmetric encryption is fast, and asymmetric is used only to deliver the key safely.

Web

HTML and the Web Browser

  • HTML defines the structure of a page.
  • CSS controls its appearance.
  • JavaScript adds interaction and behavior.
  • The browser interprets these resources and displays them.

Web

The Journey of a Web Request

1. The user types https://www.ornek.edu.tr/announcements and presses Enter; the browser splits the URL into its parts.

2. The browser asks for the domain's IP address (DNS resolution).

3. The answer arrives: the server is at 203.0.113.10.

4. The browser opens a TCP connection to the server; since this is HTTPS, the two sides agree on encryption keys with TLS.

5. The HTTP request goes over the encrypted channel: “give me /announcements”.

6. The server handles the request: it reads a file, or pulls the announcements from a database and generates HTML.

7. The response comes back: status code 200 OK (success) and the page's HTML. (404 if not found.)

8. While reading the HTML, the browser fetches the CSS, JavaScript and images it needs with separate requests.

9. The browser combines the HTML structure, CSS styling and JavaScript behavior and draws the page on screen.

Web

How Does a Search Engine Work?

  • Web crawlers discover pages by following links.
  • The content is stored in a search index.
  • A query is answered by intersecting the pages that contain each word in the index (the Web itself is not searched).
  • Results are ranked by relevance, freshness, links and other signals.

The Web · Step by step

Search Engines: Crawl, Index, Rank

When you search, the Web is not visited at that moment; the answer comes from an index built in advance. Four stages: crawl, index, rank, results.

Crawl: the crawler follows links from seed pages to discover new pages and download their content. Only reachable, permitted pages are crawled, not the whole Web.

Index: the words on each page go into an inverted index (word → pages). At query time, pages aren't read one by one; the lists are consulted.

Rank: the candidates containing both words (the intersection: Page 1 and Page 4) are scored and ordered by relevance, freshness, incoming links and so on (the scores are just examples).

Results: the top-scoring pages are listed with title, address and snippet. The whole process usually takes a fraction of a second.

Digital Services

How Does an Email Get There?

1. Ali writes a message to ayse@ornek.com.tr and clicks Send.

2. The client sends the message over SMTP to his organization's outgoing mail server.

3. The server asks DNS for the mail server of the domain after the @ sign (the MX record).

4. DNS answers: mail for ornek.com.tr is accepted by mx.ornek.com.tr.

5. The message is transferred over SMTP to the recipient's mail server.

6. The receiving server runs the message through spam/virus filters and stores it in Ayşe's mailbox.

7. Ayşe reads the message over IMAP. Since it stays on the server, it looks the same on her phone and computer.

Security · Step by step

The Phishing Attack Chain and How to Break It

Fake email: the attacker sends an official-looking, urgent, threatening message. The sender's domain is not the organization's.

Fake page: the link leads to a login page that closely imitates the real one. The domain is different; https and the padlock only show that the connection is encrypted, not that the site is trustworthy.

Password entered: the credentials the user types go straight to the attacker's server. The victim is often redirected to the real site and never notices.

Account takeover: the attacker logs in, may change the password to lock the owner out, tries the same password on other accounts and sends new phishing to the contacts.

Protection: every link in the chain is a chance to break it. Break one link and the attack fails; multi-factor authentication protects the account even if the password is stolen.

Security

A Phishing Email, Annotated

1. The sender: the display name looks official, but the domain is support-info.example; the real one should be giresun.edu.tr.

2. The subject uses urgency and threats: “closed in 24 hours”. The goal is a click without thinking.

3. A generic greeting (“Dear user”): your organization knows your name.

4. A request to verify your password: real organizations never ask for it by email or through a link.

5. Hovering over the button (without clicking) reveals that the real address points to a completely different domain.

6. The attachment has a double extension: .pdf.exe is actually an executable program, not a document.

Security

Password Strength: Why Length Matters

  • Each added character multiplies the possibilities; length beats adding symbols.
  • Passwords that are dictionary words, contain personal information or are reused elsewhere fall outside this calculation: they are easy to guess.
  • A password manager generates and stores a long, unique password for every account.

Security

Multi-Factor Authentication, Step by Step

1. The user enters a username and password (factor 1: something you know).

2. If the password is correct, the server asks for a second proof: an authenticator app on the phone generates a code that changes every 30 seconds (factor 2: something you have).

3. The user enters the code; the server verifies it and logs the user in.

4. Even with a leaked password, the attacker usually fails without the phone. Real-time phishing and SIM swapping are still possible; the most resistant methods are FIDO2 passkeys and hardware keys.

Security

VPNs: What They Do and Don't Do

What a VPN does

Builds an encrypted tunnel between your device and the VPN server. It makes local eavesdropping on public Wi-Fi harder, shows sites the VPN server's IP instead of yours, and gives secure remote access to a corporate network.

What a VPN doesn't do

It doesn't make you anonymous. The VPN provider can see which sites your traffic goes to, so you have to trust it. If you're logged in or have cookies, sites still recognize you. It doesn't block malware or phishing either.

“No logs” claims are the provider's own statements. A VPN requires choosing a trustworthy provider; it complements HTTPS rather than replacing it.

Security

Firewall Rules: An Example

A firewall allows or blocks incoming and outgoing connections according to rules; the rules are tried top to bottom and are usually based on IP and port.

#DirectionDest. portSourceAction
1In443 (HTTPS)AnyoneAllow (web server)
2In22 (SSH)Admin IP onlyAllow
3In23 (Telnet)AnyoneBlock (unencrypted legacy protocol)
4InEverything elseAnyoneBlock (default deny)
Good practice: block everything by default and allow only the ports you need. A firewall limits what gets into the network; on its own it won't stop a malicious file the user downloads.

Security

Backups: The 3-2-1 Rule

3 copies

The original data and at least two backups.

2 media

Different kinds of storage, e.g. SSD and external drive, so they don't fail together.

1 offsite

In a different location (cloud or another building) to survive fire, theft or ransomware.

A backup is only useful if it can be restored: test it now and then. A drive left permanently connected can be hit by ransomware.
